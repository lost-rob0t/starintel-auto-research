* Research Scope

This research loop selects one issue only: how =star-server= should implement a first-class Prolog inference actor that is supervised, isolated by case or dataset, bounded by explicit budgets, driven by typed Target documents, described by an actor manifest, capable of producing machine-verifiable conclusions and proof traces, and usable by automatic-research or monitoring workflows.

LLM-native actors are included only where they interact with this Prolog actor. General LLM agent architecture, collection-provider design, and the complete Star-Lang language remain separate research topics.

* Decision

Implement a =PrologInferenceActor= as a managed =star-server= domain component with one durable Common Lisp actor as the authority for each inference run and one isolated Prolog worker process or engine as its replaceable execution resource.

The Common Lisp actor owns:

- manifest validation;
- Target validation;
- budget reservation and accounting;
- knowledge-base identity and version selection;
- fact import;
- query submission;
- result and proof normalization;
- persistence of run events;
- cancellation;
- health reporting;
- restart policy;
- deterministic replay metadata.

The Prolog worker owns only the bounded logical computation. It must not own durable StarIntel state, credentials, scheduling policy, budget authority, or final document persistence.

An LLM actor may propose facts, queries, rule candidates, source-search tasks, or explanatory text. It may not directly assert durable facts or publish conclusions. Its output must pass schema validation and, where applicable, deterministic evidence or rule checks before being admitted to the Prolog knowledge base.

* Why This Boundary

A Prolog engine is good at explicit relations, recursive graph traversal, rule evaluation, tabled queries, negation models, and proof-oriented computation. It is not a supervisor, budget ledger, durable event journal, policy engine, or multi-tenant isolation boundary.

A Common Lisp actor is the stable integration boundary because =star-server= already centers managed actors and typed documents. Keeping persistence and authority outside the Prolog runtime makes the engine replaceable and makes crashes recoverable from the append-only run journal.

The worker/supervisor split follows the established supervision-tree model: workers perform computation while supervisors start, stop, monitor, and restart children; restart intensity must be bounded so a repeatedly failing child escalates instead of looping forever.[fn:otp-supervision]

Use =one-for-one= behavior for independent inference runs. A crash in one case must not restart unrelated cases. The registry and budget ledger are durable domain services and must not be children of a per-run supervisor.

A run actor may restart its Prolog worker after a transient transport or worker crash, but it must stop and escalate when either the restart-intensity budget or the run's retry budget is exhausted.

* Target Schema

The Target document must describe the requested inference, not contain arbitrary executable Prolog text. Queries must reference a declared query identifier exported by a signed or digest-locked rule package. Parameters are typed data.

The scheduler creates a new immutable inference run for each trigger. A monitor is therefore a durable schedule plus a sequence of reproducible runs, not one immortal mutable Prolog session.

* Budget Model

A single =max_tokens= value is inadequate. The run budget is a vector with independently enforced dimensions:

| Dimension | Enforcer | Exhaustion result |
|---+---+---|
| wall time | Common Lisp actor and OS process timeout | cancel worker; run =BUDGET-EXHAUSTED= |
| Prolog inference count | Prolog wrapper | return =inference_limit_exceeded= |
| answer count | query collector and table restraints | stop enumeration; partial result marker |
| memory | OS/cgroup/job object and worker telemetry | kill worker; run =BUDGET-EXHAUSTED= |
| restarts | supervisor | stop restart loop; escalate failure |
| LLM tokens | model gateway | deny next model call |
| LLM cost | budget ledger | deny reservation before call |
| tool calls | agent-loop controller | deny next tool call |
| source fetches | collection gateway | deny next fetch |

SWI-Prolog exposes =call_with_inference_limit/3=, which can terminate a goal when its inference allowance is exceeded.[fn:swi-inference-limit] Tabled execution also provides restraints on subgoal size, answer size, and answer count; these should be configured as secondary tripwires rather than treated as the sole resource boundary.[fn:swi-tabling-restraints]

Every debit must be appended to a budget ledger using a run ID, dimension, reserved amount, actual amount, and source event. LLM cost must be reserved before invocation and reconciled afterward. A worker cannot increase its own budget.

* Prolog Knowledge-Base Isolation

Use process-per-run isolation for the first implementation.

Reasons:

- an OS process gives a hard cancellation boundary;
- accidental dynamic predicates cannot leak into another case;
- foreign extensions cannot corrupt the Lisp runtime;
- memory limits can be enforced externally;
- engine replacement does not alter the actor protocol;
- a crashed worker can be reconstructed from a snapshot and journal.

Do not begin with one global SWI-Prolog process holding every case. Thread-local modules and private tables are useful optimization tools but are weaker isolation boundaries.

Each worker receives:

1. an immutable rule-package directory;
2. a generated fact file or fact stream for one knowledge-base snapshot;
3. one declared query ID and typed parameters;
4. explicit limits;
5. an output pipe containing only framed structured events.

The worker must have no network access and no writable access outside its temporary run directory.

* Fact Boundary

StarIntel documents must be translated through declared mapping rules. Never serialize arbitrary document fields directly into callable Prolog terms.

Example normalized facts:

#+begin_src prolog
entity('person:alice', person).
entity('org:example-corp', organization).
relationship('rel:1', 'person:alice', officer_of, 'org:example-corp').
evidence('rel:1', 'doc:filing-77', 'sha256:abc').
observed_at('rel:1', 1785427200).
#+end_src

Every asserted fact requires:

- stable fact ID;
- source document ID;
- source span or field path where available;
- source hash;
- mapping version;
- observation or validity interval;
- dataset/case identifier.

Conclusions are never inserted into the source-fact relation. They use a separate predicate namespace and output document type.

* Query Registry

Rule packages export named, typed queries:

#+begin_src prolog
:- module(star_rules_entity_resolution,
          [ star_query/4,
            beneficial_owner_path/4
          ]).

star_query(beneficial_owner_path,
           [organization_id-atom, maximum_hops-integer],
           conclusion(beneficial_owner_path),
           [tabled, explainable]).

:- table owner_path/4.

owner_path(From, To, 1, [Rel]) :-
    relationship(Rel, From, owns, To).
owner_path(From, To, Depth, [Rel|Rest]) :-
    Depth > 1,
    relationship(Rel, From, owns, Mid),
    NextDepth is Depth - 1,
    owner_path(Mid, To, NextDepth, Rest).

beneficial_owner_path(Organization, MaxHops, Person, Path) :-
    between(1, MaxHops, Depth),
    owner_path(Person, Organization, Depth, Path),
    entity(Person, person).
#+end_src

Tabling avoids repeated evaluation and can prevent left-recursive loops by suspending variant calls and resuming them as answers become available.[fn:swi-tabling] Incremental tabling can maintain dependencies when dynamic facts change, but the first implementation should prefer immutable per-run snapshots. Incremental tables become relevant later for long-lived bounded monitor workers.[fn:swi-incremental-tabling]

* Bounded Worker Entry Point

#+begin_src prolog
run_query(QueryId, Parameters, Limits, Event) :-
    validate_query(QueryId, Parameters),
    get_dict(inference_count, Limits, InferenceLimit),
    get_dict(answer_count, Limits, AnswerLimit),
    call_with_inference_limit(
        collect_answers(QueryId, Parameters, AnswerLimit, Event),
        InferenceLimit,
        Result),
    normalize_limit_result(Result, Event).
#+end_src

The actual implementation must also apply a wall-clock limit, table restraints, output framing, exception normalization, and cleanup of temporary tables.

* Proof Trace Contract

A proof trace is a typed derivation graph, not a string captured from Prolog tracing.

#+begin_src json
{
  "dtype": "starintel.proof-trace/1",
  "run_id": "run:01J...",
  "conclusion_id": "conclusion:01J...",
  "rule_package": {
    "id": "star.rules.entity-resolution",
    "version": "1.4.0",
    "digest": "sha256:..."
  },
  "root_step": "step:7",
  "steps": [
    {
      "id": "step:7",
      "rule": "beneficial_owner_path/4",
      "inputs": ["fact:rel-1", "step:6"],
      "bindings": {
        "Person": "person:alice",
        "Organization": "org:example-corp"
      }
    }
  ],
  "source_facts": [
    {
      "fact_id": "fact:rel-1",
      "document_id": "doc:filing-77",
      "source_hash": "sha256:abc"
    }
  ]
}
#+end_src

Proof construction should use explicit proof-carrying predicates or a source transformation that adds proof arguments. Do not rely on the interactive debugger trace because it is implementation-oriented, unstable, and excessively verbose.

A conclusion is publishable only when:

- its output schema validates;
- its proof trace references known rule and fact IDs;
- all referenced source facts belong to the target dataset/case;
- the run did not exceed a hard budget;
- the rule package digest matches the manifest;
- any required human-review policy is satisfied.

* Common Lisp Actor Interface

#+begin_src lisp
(defgeneric start-inference-run (supervisor target manifest))
(defgeneric cancel-inference-run (run reason))
(defgeneric inference-run-status (run))
(defgeneric reserve-run-budget (ledger run-id budget))
(defgeneric debit-run-budget (ledger run-id dimension amount event-id))
(defgeneric append-run-event (journal event))
(defgeneric normalize-prolog-event (actor frame))

(defmethod receive-message ((actor prolog-inference-actor)
                            (message inference-target))
  (let* ((target (validate-inference-target message))
         (manifest (resolve-actor-manifest actor target))
         (run (make-inference-run target manifest)))
    (reserve-run-budget (budget-ledger actor)
                        (run-id run)
                        (target-budget target))
    (append-run-event (journal actor)
                      (run-created-event run))
    (spawn-prolog-worker actor run)
    run))
#+end_src

The production implementation should use the existing managed-component and condition/restart conventions of the chosen =cl-gserver=/Sento runtime rather than inventing an unrelated actor loop.

* Failure Taxonomy

All failures become structured actor events:

- =VALIDATION-FAILED=: invalid manifest, Target, fact mapping, query parameters, or output;
- =RULE-PACKAGE-MISMATCH=: missing or wrong package digest;
- =WORKER-START-FAILED=: executable, package, or sandbox startup failure;
- =WORKER-CRASHED=: abnormal worker exit;
- =INFERENCE-LIMIT=: Prolog inference count exhausted;
- =ANSWER-LIMIT=: answer count exhausted;
- =WALL-TIME-LIMIT=: wall clock exhausted;
- =MEMORY-LIMIT=: external memory boundary crossed;
- =OUTPUT-LIMIT=: event or proof output too large;
- =RESTART-INTENSITY=: restart loop blocked by supervisor;
- =CANCELLED=: explicit user, policy, or parent cancellation;
- =PROOF-INVALID=: conclusion cannot be tied to a valid proof graph;
- =CASE-BOUNDARY-VIOLATION=: fact or proof references another isolated case.

Budget exhaustion is not a crash. It is a terminal run state with an explicit partial-results policy.

* LLM Research and Monitoring Integration

The LLM actor is a sibling worker coordinated by a research-run supervisor, not embedded inside Prolog.

#+begin_example
AutomaticResearchRunSupervisor
├── SourcePlannerAgent
├── CollectionActors...
├── EvidenceNormalizerActor
├── PrologInferenceActor
├── GapDetectorActor
└── ReportComposerAgent
#+end_example

Allowed LLM-to-Prolog requests:

- select a declared query ID;
- provide typed query parameters;
- propose a candidate fact with evidence references;
- request a proof explanation;
- ask which required predicates lack facts;
- propose a rule-package change for human review.

Forbidden direct actions:

- loading arbitrary Prolog source;
- asserting unvalidated facts;
- changing rule-package digests;
- increasing budgets;
- crossing case boundaries;
- publishing a conclusion without the deterministic gate.

For a monitor, the LLM may summarize newly derived conclusions or decide which declared follow-up tools to request, subject to its own token, cost, tool-call, and source-fetch budgets.

* Observability

Every run emits correlated structured events with stable identifiers:

- service name;
- actor ID and version;
- actor instance ID;
- run ID;
- target ID;
- dataset/case ID;
- knowledge-base snapshot;
- rule-package digest;
- query ID;
- supervisor path;
- restart count;
- budget reserved and consumed;
- worker process identity;
- terminal state.

OpenTelemetry resources identify the entity associated with telemetry using stable attributes, while spans and metrics provide correlated execution data; StarIntel should map actors and runs into those concepts without making telemetry the durable run journal.[fn:otel-resource]

Required metrics:

- active inference runs;
- queue depth;
- run latency;
- Prolog inferences consumed;
- answers produced;
- proof nodes produced;
- budget-exhaustion count by dimension;
- worker crash count;
- restart-intensity trips;
- invalid output count;
- cross-case violation count.

* Persistence and Replay

Persist an append-only sequence of run events plus immutable inputs:

1. target accepted;
2. manifest resolved;
3. budget reserved;
4. knowledge-base snapshot resolved;
5. rule package resolved;
6. worker started;
7. facts loaded;
8. query started;
9. answer/proof emitted;
10. budget debit recorded;
11. worker stopped;
12. run completed, failed, cancelled, or exhausted.

A replay must pin:

- Target document hash;
- actor manifest hash;
- fact-mapping version;
- knowledge-base snapshot hash;
- rule-package digest;
- Prolog engine family and version;
- worker image or Nix derivation hash;
- all budget values;
- query ID and parameters.

LLM-assisted portions are separately marked reproducible or non-reproducible. The deterministic Prolog run must remain replayable without calling an LLM.

* Implementation Sequence

** Phase 1: Contract Freeze

- define JSON Schemas for actor manifest, inference Target, inference run, conclusion, proof trace, and actor event;
- define condition/error taxonomy;
- define query-registry interface;
- define budget-ledger interface;
- define framed worker protocol.

** Phase 2: Process-Isolated Prototype

- Common Lisp actor starts one SWI-Prolog process per run;
- facts are generated into a temporary read-only input bundle;
- worker loads one digest-locked rule package;
- worker executes one named query;
- inference, answer, wall-time, memory, and output limits are enforced;
- conclusions and proof traces are validated before persistence.

** Phase 3: Supervision and Recovery

- add one-for-one run supervision;
- add restart intensity and retry budgets;
- reconstruct a run from journal plus immutable inputs;
- prove unrelated runs are unaffected by one worker crash.

** Phase 4: Automatic Research Integration

- connect a source-planner LLM actor through typed requests;
- enforce independent LLM and tool budgets;
- admit candidate facts only through validation and evidence gates;
- persist final conclusions separately from LLM summaries.

** Phase 5: Monitoring

- add dataset-revision triggers;
- debounce updates;
- create immutable run instances;
- compare conclusion sets between runs;
- notify only on policy-qualified deltas.

** Deferred Optimizations

- pooled Prolog workers;
- long-lived monitor engines;
- incremental or monotonic tables across revisions;
- in-process foreign-function integration;
- browser Prolog runtime;
- distributed inference across nodes.

These are deferred until the process-isolated protocol and replay tests are stable.

* Acceptance Tests

1. A valid Target produces a schema-valid conclusion and proof trace.
2. An unknown query ID is rejected before worker execution.
3. Arbitrary Prolog text in Target parameters is treated as data or rejected, never executed.
4. The inference-count limit terminates a recursive query.
5. The answer-count limit returns an explicit partial terminal state.
6. The wall-time limit kills a non-responsive worker.
7. The memory limit kills only the offending worker.
8. A worker crash is restarted only within the configured intensity and run retry budget.
9. Failure of run A does not restart or corrupt run B.
10. Facts from case A cannot be queried by a run scoped to case B.
11. A proof referencing an unknown fact ID is rejected.
12. A mismatched rule-package digest is rejected.
13. An LLM actor cannot increase its budget or directly persist conclusions.
14. Replay with pinned inputs produces the same deterministic conclusion set and proof hashes.
15. Monitor mode creates separate immutable runs and emits only qualified conclusion deltas.

* Rejected Alternatives

** One Global Mutable Prolog Knowledge Base

Rejected for the first implementation because it creates cross-case leakage risk, weak cancellation, difficult replay, and broad failure impact.

** LLM as the Inference Authority

Rejected because unstructured model output does not provide deterministic rule provenance, bounded logical recursion, or replayable proof paths.

** Raw Prolog Queries in Targets

Rejected because they collapse the data/code boundary and make permissions, validation, compatibility, and auditing substantially harder.

** Unlimited Automatic Restarts

Rejected because repeated deterministic failures become restart storms. Supervision must have restart intensity and the run must have an explicit retry budget.

** Persisting Interactive Prolog Traces

Rejected because debugger traces are not a stable proof interchange format. Use explicit proof terms normalized into a typed derivation graph.

* Result

The first StarIntel Prolog feature should not be a generic embedded REPL. It should be a narrow, supervised, process-isolated inference service with digest-locked rule packages, named typed queries, immutable knowledge-base snapshots, multidimensional budgets, explicit proof documents, and deterministic replay.

This design directly satisfies the fourth-generation backlog's Prolog, bounded-inference, proof-trace, schema-validation, actor-manifest, Target, LLM-agent, monitoring, and supervisor requirements while keeping the implementation small enough to test as one =star-server= vertical slice.
