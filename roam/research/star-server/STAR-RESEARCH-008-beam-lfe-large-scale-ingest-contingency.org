* Research Question

Should StarIntel keep the BEAM[fn:beam] runtime, Erlang/OTP[fn:otp], and Lisp Flavoured Erlang (LFE)[fn:lfe] in the pocket as a future large-scale ingest runtime if the existing Common Lisp[fn:common-lisp] actor stack reaches demonstrated limits at real operating scale?

This packet is deliberately *not* a rewrite proposal and contains *no ingest redesign*. The current Common Lisp, cl-gserver/Sento, RabbitMQ, and StarIntel ingest work remains the active implementation path. BEAM is being researched now so that a credible escape hatch already exists if production evidence later shows that the current actor runtime is the limiting factor.

* Scope Boundary

This research answers only four questions:

1. Whether BEAM/OTP is technically credible for a future high-concurrency ingest runtime.
2. Whether choosing LFE instead of Erlang materially changes the runtime scaling story.
3. Whether LFE's weaker tooling is a fatal blocker for StarIntel.
4. What evidence would justify reopening this contingency later.

It does not choose a migration date, module boundary, transport, supervision topology, mailbox policy, partitioning scheme, persistence layout, or replacement architecture. Those are intentionally left out until real measurements justify a design phase.

* Method

This was a bounded research pass using current primary or project-maintainer sources retrieved on 2026-08-09:

- Erlang/OTP 29 system limits, process efficiency, scheduler, and profiling documentation;
- current LFE project documentation on Core Erlang generation and Erlang/OTP interoperability;
- the =mdbergmann/lfe-ls= repository and README supplied by the operator;
- WhatsApp's Erlang Language Platform repository as the current comparison point for production-grade Erlang editor tooling.

Claims about StarIntel's future threshold remain hypotheses until measured against the current Common Lisp actor implementation under representative ingest workloads.

* Executive Finding

BEAM/OTP is a credible *large-scale ingest contingency* and is worth keeping in the pocket. Nothing found in this pass justifies rewriting the current StarIntel ingest stack today.

The strongest conclusion is that *LFE versus Erlang is primarily a language and tooling decision, not a different actor-runtime scaling decision*. LFE generates Core Erlang and interoperates with Erlang/OTP and third-party Erlang libraries. The process scheduler, mailboxes, garbage collection, distribution machinery, OTP behaviours, and runtime limits ultimately come from the same BEAM platform.

If cl-gserver/Sento eventually fails because StarIntel reaches genuinely difficult concurrency, scheduling, isolation, mailbox, or multi-node operating conditions, BEAM is a serious place to look. If the current runtime does not become the measured bottleneck, there is no research basis for paying rewrite cost merely because BEAM is attractive.

* Finding 1: BEAM is built for process counts that make it relevant to ingest-scale actor research

Current Erlang/OTP 29 documentation gives a default maximum of 1,048,576 simultaneously alive Erlang processes, configurable at startup. The efficiency guide shows a freshly spawned process using 327 words, 2,616 bytes in the documented example, and explicitly discusses systems with hundreds of thousands or millions of processes.

This does not prove that StarIntel should create one process per document, request, source, or record. It establishes that the runtime is intentionally engineered around extremely large populations of isolated lightweight processes and therefore belongs in the contingency set for a future actor-heavy ingest system.

* Finding 2: BEAM does not remove backpressure, mailbox, serialization, or memory physics

The Erlang efficiency guide states that message data is copied between processes except for reference-counted binaries and literals on the same node. Messages sent to another Erlang node are encoded into the Erlang external format, transported, decoded, and delivered. Selective receive can require searching a process mailbox until a matching message is found.

That means a BEAM rewrite would not magically cure bad queue topology or overloaded consumers. Very large mailboxes, excessive payload copying, badly selected process granularity, centralized actors, or expensive cross-node traffic can still become bottlenecks.

This is important to the contingency framing: BEAM is valuable because it provides a mature runtime for concurrency and failure isolation, not because it abolishes the need to measure queueing and data movement.

* Finding 3: OTP's operational tooling is one of the strongest reasons to keep it in reserve

OTP 29's official profiling guidance includes =tprof=, =fprof=, =dbg=, =lcnt=, allocator inspection, =observer=, =etop=, and =msacc=. The large-system guidance explicitly warns that bottlenecks can appear only when many things happen simultaneously and when multiple nodes are involved.

Scheduler utilization is directly measurable through runtime tooling, and scheduler counts are configurable while normally deriving from available logical processors.

For a future ingest system, this matters as much as raw throughput. At real scale the difficult question is often not whether another actor can be spawned, but whether the operator can determine which actors, locks, schedulers, allocators, ports, queues, or nodes are actually causing collapse.

* Finding 4: LFE inherits the BEAM scaling story rather than replacing it

The LFE project describes LFE as a Lisp-2 written for the Erlang VM with Core Erlang compatibility, seamless Erlang interoperability, and access to the BEAM ecosystem. Current LFE feature documentation states that its compiler generates Core Erlang and has full interoperability with Erlang/OTP and third-party Erlang libraries.

Therefore there is no separate "LFE runtime" that needs to prove itself against BEAM. LFE source ultimately enters the Erlang compiler/runtime pipeline. A future StarIntel implementation could use LFE while consuming ordinary Erlang/OTP libraries and behaviours.

This does *not* establish that arbitrary LFE and Erlang source programs have identical performance. Different source structures can produce different Core Erlang and BEAM code. It does establish that the fundamental scheduler, process, distribution, garbage-collection, and OTP properties under study are BEAM properties shared by both language choices.

* Finding 5: LFE is unusually attractive to StarIntel if the contingency is ever activated

LFE preserves properties that fit the existing StarIntel engineering culture: Lisp syntax, macros, homoiconicity, REPL-driven work, domain-specific language construction, and direct actor-model access through Erlang/OTP.

That makes LFE a more interesting contingency than treating Erlang syntax as the only way to reach BEAM. If StarIntel eventually has a measured reason to move a large-scale ingest runtime onto BEAM, LFE offers a path that keeps Lisp-level metaprogramming while gaining the OTP runtime.

This is a language-fit observation, not an implementation decision.

* Finding 6: =lfe-ls= is useful but currently confirms the tooling gap

The supplied =mdbergmann/lfe-ls= project is a real LFE language-server implementation written in LFE. Its README says it was tested with Erlang 25 through 27 and currently implements initialization, document open/change/close/save handling, basic completion, compile diagnostics, and hover documentation.

The same README describes the project as largely work in progress and calls auto-completion rudimentary. It notes that current document synchronization transfers the full document and lists signature support as future work. The repository also contains recent evidence of dependency/build maintenance work, including an issue where compilation failed after dependency changes and a subsequent dependency update pull request.

This is the clearest weakness found for LFE today: *developer tooling maturity, not BEAM runtime capability*.

* Finding 7: Erlang's tooling baseline is much stronger

WhatsApp's Erlang Language Platform (ELP) describes itself as a scalable, fully incremental, IDE-first semantic-analysis platform for Erlang and provides a full LSP server with features such as definition lookup, references, call hierarchy, linting, and refactoring infrastructure.

That gives ordinary Erlang a lower tooling-risk profile today. If a BEAM contingency had to be activated under schedule pressure, Erlang would be the conservative language choice because more mature semantic tooling already exists.

* Finding 8: AI-assisted engineering changes how heavily the LFE tooling deficit should be weighted

For StarIntel, missing LFE tooling is not automatically equivalent to "unusable language." The project can build and maintain targeted tooling when the payoff is high enough, and AI-assisted engineering sharply reduces the cost of producing repetitive editor, parser, protocol, test, and integration code.

A missing LFE feature such as richer completion, navigation, refactoring support, formatter integration, compiler diagnostics, or project-aware indexing can be treated as an engineering backlog rather than a permanent ecosystem constraint. LFE's direct relationship to Erlang and Core Erlang also gives generated tools an existing compiler and runtime to validate against instead of requiring a new language implementation.

The constraint is validation: AI can produce tooling quickly, but generated language tooling still has to be checked against actual LFE compiler semantics, OTP releases, rebar3 projects, macros, generated forms, and Emacs/Eglot behaviour. AI lowers the cost; it does not make correctness free.

This shifts the research conclusion from "Erlang wins because LFE tooling is thin" to:

- Erlang has the strongest ready-made tooling today.
- LFE reaches the same BEAM runtime and preserves Lisp advantages.
- StarIntel can plausibly manufacture missing LFE tooling if and when the runtime payoff justifies it.
- Therefore tooling maturity alone is not a reason to remove LFE from the contingency set.

* What Would Reopen This Research

Do not activate a BEAM design merely because ingest volume increases. Reopen this packet when measurements show that the *actor runtime itself* is a material limiting factor after ordinary application bottlenecks have been separated from it.

Useful evidence would include one or more of:

- repeatable scheduler or runtime saturation attributable to cl-gserver/Sento rather than parsing, storage, network, or upstream rate limits;
- actor population or mailbox behaviour that becomes operationally unmanageable at representative production concurrency;
- failure isolation or supervision behaviour that cannot meet ingest reliability requirements without disproportionate custom runtime work;
- multi-node actor operation becoming a primary requirement and the existing runtime/transport combination becoming the dominant engineering cost;
- observability deficits in the current actor runtime preventing reliable diagnosis of failures at scale;
- benchmark evidence showing materially better throughput, latency, memory behaviour, recovery, or operational simplicity on BEAM for a representative ingest slice.

Until such evidence exists, BEAM stays in the pocket.

* Research Gaps

No design work should start from this packet. The unresolved research questions are:

1. What are the actual process, mailbox, throughput, latency, memory, and recovery limits of the current cl-gserver/Sento ingest path on StarIntel's target hardware?
2. At what point, if any, does the Common Lisp actor runtime become a larger bottleneck than RabbitMQ, parsing, persistence, source latency, or document normalization?
3. How do Erlang and LFE compare on equivalent synthetic actor workloads once both compile to BEAM?
4. Which LFE language-server capabilities remain missing at the moment a contingency is activated, and which can be generated or adapted from existing Erlang tooling?
5. Which OTP release would be the supported baseline at that future date?

These are future research gates, not current implementation tasks.

* Footnotes and Glossary

[fn:beam] BEAM: The Erlang virtual machine and runtime system that executes Erlang bytecode and provides lightweight processes, scheduling, garbage collection, message passing, distribution, and the runtime substrate used by Erlang and LFE.

[fn:otp] Erlang/OTP: The Erlang runtime, libraries, behaviours, release tooling, supervision conventions, and operational facilities used to build fault-tolerant concurrent systems on BEAM.

[fn:lfe] Lisp Flavoured Erlang: A Lisp-2 language targeting the Erlang VM. LFE generates Core Erlang and interoperates with Erlang/OTP and Erlang libraries.

[fn:common-lisp] Common Lisp: StarIntel's current primary server and actor implementation language. In this packet it remains the active ingest implementation rather than a legacy system awaiting replacement.
