* REVIEW Objective

Amend =STAR-RESEARCH-PIPELINE-003= so its actor ownership, commands, events, results, checkpoints, routing, scheduling, leases, and replay semantics can execute revisioned jurisdiction-coverage contracts without mutable logical-ID shortcuts.

This amendment does not replace the parent supervision architecture. It supersedes the parent protocol fields and state rules identified below.

* REVIEW Problems Corrected

The parent v1 design currently:

- carries logical =source-profile-id= in command, event, result, checkpoint, routing, and scheduler contracts
- does not define durable source-deployment, search-plan, subfamily-decision, gap-revision, or route-assessment records
- does not define serialized ownership for route assessments
- mixes profile verification/access conditions into one lifecycle without an independent review authority
- treats adapter jobs and network attempts as one object even though leases are issued after job planning
- records lease generation but not a fencing token on each request attempt
- cannot pin applicability-contract and policy-snapshot versions into historical decisions

These gaps make historical replay and deterministic county completion impossible.

* REVIEW Amendment Status

This node is normative for protocol v1.1. Where it conflicts with v1 fields in =STAR-RESEARCH-PIPELINE-003=, this amendment controls after approval.

No implementation may claim conformance until both the parent design and this amendment are approved.

* REVIEW Authority Changes

Add these pinned state owners:

- Source Deployment Authority
- Search Plan Authority
- Gap Authority
- Route Assessment Authority
- Independent Review Authority

The existing Source Profile Authority remains the only canonical writer for source-profile revisions. The Coverage Ledger remains append-only observation storage and current-state materialization; it is not the canonical writer for route decisions or reviews.

Required root readiness now includes replay completion for identity, deployment, profile, search-plan, gap, route-assessment, review, adapter-registry, raw-artifact, rate/lease, and coverage authorities.

* REVIEW Durable Document Families

Protocol v1.1 requires:

- government-unit and government-component records
- source-deployment revisions
- source-profile revisions
- route-applicability-contract revisions
- search-plan revisions
- subfamily-decision revisions
- gap revisions
- route-assessment revisions
- review-state revisions or revisioned review fields under one-writer authority
- adapter-job revisions
- adapter-attempt records
- immutable retrieval events, raw artifacts, evidence records, and checkpoints
- policy snapshots and manifest-set snapshots

Every canonical state transition creates a new immutable revision with logical ID, revision ID, predecessor, and superseded-revision references.

* REVIEW Job and Attempt Separation

A durable adapter job revision binds logical work, exact source/proposal/search-plan revisions, contract, policy, adapter version, manifest hash, runtime hash, bounds, artifact policy, and idempotency key.

A job does not contain a future lease.

After validating the job, the dispatcher obtains a lease and creates:

#+begin_src lisp
(defstruct government-data-adapter-attempt
  attempt-id attempt-number job-revision-id prior-attempt-id
  rate-lease-id rate-lease-generation rate-lease-fence
  rate-lease-key-hash worker-generation started-at deadline input-hash)
#+end_src

Every network request validates the current fence. Retry creates a new attempt; logical scope changes create a new job revision.

* REVIEW Checkpoint v1.1

#+begin_src lisp
(defstruct government-data-checkpoint-v1.1
  protocol command-id job-revision-id attempt-id
  source-profile-revision-id deployment-revision-id
  adapter-id adapter-version adapter-manifest-hash runtime-environment-hash
  partition cursor page newest-source-time oldest-source-time
  object-count byte-count request-count artifact-ids evidence-ids
  completed-partitions outstanding-partitions
  prior-checkpoint-id checkpoint-hash policy-snapshot-id configuration-hash)
#+end_src

A checkpoint cannot advance beyond artifact and evidence commits. Resume creates a new attempt referencing the checkpoint; the checkpoint is never mutated.

* REVIEW Routing Changes

| Work | Revision-aware key |
|------|--------------------|
| deployment writes | deployment logical ID |
| profile writes | profile logical ID |
| search-plan writes | search-plan logical ID |
| gap writes | gap logical ID |
| subfamily decisions | unit + route + subfamily + contract version |
| route assessments | unit + route + applicability-contract version |
| review decisions | subject kind + subject revision ID |
| acquisition cursor ordering | source-profile revision + cursor partition |
| schedules | current reviewed profile revision + policy snapshot |
| coverage materialization | unit + route + contract version |

Routing on logical IDs is allowed only to serialize writes. Reads and emitted decisions pin revisions.

* REVIEW State Ownership

** Source Deployment Authority

Serializes deployment revisions and host-alias/tenant reconciliation. It cannot grant jurisdiction delegation by itself.

** Source Profile Authority

Serializes profile revisions and source-state transitions. Every transition creates a new profile revision. It cannot mark human review state without an Independent Review Authority decision.

** Search Plan Authority

Owns immutable search-plan revisions and completed-state validation. A negative decision cannot reference an incomplete plan.

** Gap Authority

Owns immutable gap revisions, freshness, reassessment deadlines, and records-request links. Gap expiry produces a due-reassessment event, not in-place mutation.

** Route Assessment Authority

Serializes route-assessment revisions for one unit/route/contract key. It validates required subfamilies, exact revision bindings, terminal states, freshness, and explicit supersession.

** Independent Review Authority

Commits reviewed, changes-requested, or invalidated revisions. The proposing worker/authority cannot self-approve. Review transitions create new subject or review revisions; they never mutate prior reviewed state.

* REVIEW Coverage Ledger Boundary

The Coverage Ledger stores append-only observations and materialized views. It may report current route state only from the latest reviewed route-assessment revision under the selected contract/policy.

It may not invent route completion by aggregating adapter successes, profile counts, or coverage observations without a committed route-assessment revision.

* REVIEW Scheduler Changes

A scheduled job pins:

- current reviewed profile revision
- deployment revision
- policy snapshot
- adapter manifest/runtime hashes
- cursor checkpoint
- due reason and freshness basis

If the current reviewed revision changes before dispatch, the scheduler cancels or replans the stale job. A job cannot silently follow “latest profile.”

* REVIEW Lease Fencing

The Rate and Lease Authority issues ID, key hash, generation, fence, issued-at, expiry, and close state.

The dispatcher creates an attempt only after lease issue. Workers include the fence on every request event. The authority or dispatcher rejects stale-fence requests and emits =:adapter-attempt-fenced=.

Host aliases mapped to one deployment share vendor/deployment limits.

* REVIEW Artifact and Checkpoint Ordering

Required sequence:

1. job validation
2. lease issue
3. attempt creation
4. request
5. artifact reservation/stream
6. byte count and hash verification
7. artifact and retrieval-event commit
8. evidence/proposal commit
9. checkpoint commit
10. lease close
11. terminal result

A successful result is invalid when truncation is unexplained, artifacts are uncommitted, counts do not reconcile, or the attempt fence expired before the final request.

* REVIEW Protocol Migration

- v1 commands without revision IDs remain readable for historical replay but cannot create new canonical coverage decisions.
- v1 logical profile IDs resolve only through an explicit migration command that records the selected revision and evidence.
- existing source-profile versions migrate to profile revisions preserving prior version IDs as aliases.
- existing coverage observations remain observations; they do not become route assessments automatically.
- existing gaps migrate to first gap revisions with inferred fields marked and reviewed before use.
- schedulers stop issuing v1 acquisition commands after the cutover policy time.
- mixed v1/v1.1 operation is allowed only for read-only replay or migration, never current completion.

* REVIEW Capability Changes

Add explicit capabilities:

- source-deployment propose/commit
- search-plan propose/commit
- gap propose/commit
- subfamily-decision propose/commit
- route-assessment propose/commit
- independent review commit
- lease-fenced adapter attempt

Only owning authorities receive commit capabilities. Workers receive proposal capabilities.

* REVIEW Deterministic Fixtures

Required fixtures:

- v1 logical-ID command rejected for current completion
- profile revision changes after an old assessment without altering replay
- route assessment supersession after contract migration
- negative gap expiry and reassessment
- self-review rejection
- stale scheduled job after profile revision change
- adapter retry using same job revision and new attempt/fence
- stale-fence request rejection
- crash after artifact commit and before checkpoint
- coverage observations without assessment cannot produce completion
- migration of a v1 profile, gap, and checkpoint
- mixed v1/v1.1 command rejection outside migration/read-only scope

* REVIEW Acceptance Criteria

1. Every canonical decision pins exact revisions.
2. Route Assessment and Independent Review have explicit state owners.
3. Coverage Ledger cannot synthesize completion without an assessment revision.
4. Jobs and lease-bound attempts are separate.
5. Every request is lease-fenced.
6. Checkpoints cannot outrun artifact/evidence commits.
7. Scheduler jobs never silently follow latest state.
8. v1 migration is explicit and cannot create unreviewed completion.
9. Ohio contracts can execute without protocol-specific exceptions.
10. This amendment and the parent design are approved before implementation.
