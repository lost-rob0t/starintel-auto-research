* Research Question

How should StarIntel build a large, reusable corpus of Prolog facts and rules that can be consumed by many actors without duplicating knowledge or embedding a separate Prolog runtime in every actor, while preserving source provenance, reproducible releases, bounded inference, and a path to StarLang and learned-model evidence?

The immediate reference use case is a dialect-enrichment actor that can reason over linguistic observations and return explainable regional-language candidates. The architecture must generalize to geography, organizations, identity, infrastructure, social platforms, political structures, and later expert systems.

This document is research and design evidence only. It does not authorize repository creation, runtime changes, actor implementation, or dataset publication.

* Operator Requirements Captured

1. Build a large shared corpus of reusable Prolog facts and rules instead of actor-local knowledge bases.
2. Make that corpus available as a library/repository that multiple actors can consume.
3. Use the existing Prolog query server as the runtime boundary rather than spawning or embedding SWI-Prolog independently per Common Lisp actor.
4. Preserve Common Lisp actors as first-class consumers now and keep StarLang as a later orchestration/adapter consumer.
5. Keep deep learning as a third candidate for dialect evidence, not as the sole source of truth.
6. Self-source dialect knowledge over time rather than making a third-party survey dataset the permanent canonical corpus.
7. Preserve durable provenance so facts, rules, observations, derived claims, and model outputs remain distinguishable.

* Primary Finding: The Query Runtime Already Exists

The proposed shared knowledge system should not begin by creating another Prolog server.

=lost-rob0t/prolog-query-server= already implements the core runtime properties needed for a StarIntel knowledge plane:

- CouchDB is the durable knowledge store and SWI-Prolog is the inference engine;
- facts and rules are persisted as ordinary CouchDB documents;
- multiple named knowledge bases can coexist;
- JSON is converted through a safe structured term/goal representation rather than accepted as executable Prolog source;
- inference is bounded by depth and solution limits;
- explanation queries expose persisted source-document identifiers;
- the current proof-tree implementation can tie rule/fact proof nodes to exact CouchDB document revisions;
- per-KB synchronization protects concurrent runtime refresh/query operations;
- authentication distinguishes read and write capabilities;
- production deployments are expected to put bearer-authenticated traffic behind TLS.

The project also implements a native CouchDB =language: "prolog"= query server for map/reduce views. That view runtime and the HTTP expert-system service are deliberately separate abstractions. StarIntel actor inference should use the HTTP expert-system service; the native CouchDB query-server DSL remains useful for indexing and per-document view computation but is not the recursive knowledge API.

* Existing Runtime Capabilities That Must Be Reused

** Immutable logical releases

The query server already supports a =release= on knowledge documents plus a per-KB =prolog_kb_manifest= whose =active_release= selects the default release. A complete release can be staged, tested with pinned queries, then activated with a single revision-checked manifest update. Once a non-legacy release is active, writes to it are rejected.

This is a better runtime publication primitive than inventing a second lockfile protocol inside StarIntel. The proposed =star-kb= authoring repository should compile/publish *into* this release model rather than replace it.

** Incremental synchronization

After a first full snapshot, current =refresh: true= behavior consumes CouchDB's =_changes= feed in bounded pages, applies knowledge changes transactionally under the per-KB synchronization boundary, and advances its checkpoint only after a page succeeds. This matches CouchDB's documented role of =_changes= as a synchronization feed and its warning that consumers must tolerate repeated changes idempotently.

Therefore the shared corpus can grow without forcing every query to reconstruct the entire KB from scratch.

** Conflict behavior

CouchDB may retain conflicting leaf revisions and choose a deterministic winner for ordinary reads. The current query-server work already added fail-closed handling for unresolved knowledge conflicts instead of silently allowing a winner to influence inference. The shared corpus design should preserve this invariant.

** Static analysis

The runtime has a release analyzer covering predicate dependencies, undefined predicates, unreachable predicates/rules, recursion/strongly-connected components, negation cycles/non-stratified negation, and arity consistency. A =star-kb= publisher should invoke this gate before activation rather than writing its own competing analyzer.

** Proof trees

=/v1/explain= can return proof trees containing rule/fact nodes, resolved goals, source CouchDB IDs/revisions, builtin nodes, negation decisions, and ordered child proofs. This is directly useful for StarIntel provenance: an enriched document can retain the query/release identity and source proof references that produced the inference.

* Architectural Separation

The research supports four separate planes.

#+begin_src text
                         reviewed source knowledge
                                  |
                                  v
                         +-----------------+
                         | star-kb Git repo |
                         | authoring/build  |
                         +--------+--------+
                                  |
                      validate + compile + publish
                                  |
                                  v
                  +-------------------------------+
                  | prolog-query-server + CouchDB |
                  | immutable KB releases         |
                  | bounded inference + proofs    |
                  +---------------+---------------+
                                  ^
                                  |
       +--------------------------+--------------------------+
       |                          |                          |
       |                          |                          |
Common Lisp actors          prolog-rlm clients       StarLang adapters
       |
       v
StarIntel evidence/documents
(run/case observations stay outside canonical source knowledge)
#+end_src

The four responsibilities are:

1. *Authoring plane*: a source-controlled =star-kb= repository owns curated knowledge source, module manifests, citations/licenses, fixtures, and release-building inputs.
2. *Runtime knowledge plane*: =prolog-query-server= plus CouchDB owns executable fact/rule documents, active release manifests, synchronization, bounded execution, and proofs.
3. *Evidence plane*: StarIntel document/artifact stores own run-scoped observations and case-specific evidence. These do not silently become canonical general knowledge.
4. *Consumer plane*: actors, RLM agents, command-line research tools, and later StarLang query the same runtime knowledge plane through a structured API.

* Why Git Should Not Be the Runtime Database

The desired corpus can become very large. Git is appropriate for curated, reviewable knowledge source and build metadata, but not for an unbounded stream of actor observations.

Canonical facts and rules benefit from code review, provenance diffs, deterministic builds, and source history. In contrast, individual post observations, scraper events, model scores, and run-local evidence can grow orders of magnitude faster and already have natural homes in StarIntel's document/artifact storage.

The design should therefore prevent this failure mode:

#+begin_src text
one actor sees one token
        -> commits a .pl fact
        -> millions of observations become Git history
#+end_src

Instead, an actor sends a bounded projection of its current evidence as arguments to an exported knowledge predicate or records a durable StarIntel observation that can be selected for later queries.

Promotion from observations into canonical knowledge must remain explicit and provenance-bearing.

* Canonical Authoring Format

There is tension between two useful properties:

- humans and agents should author a real Prolog-shaped knowledge corpus;
- the production query server intentionally refuses arbitrary Prolog source and arbitrary =call/1= from HTTP/CouchDB knowledge.

The recommended resolution is a *restricted source Prolog profile* in =star-kb= that is compiled offline to the query server's safe JSON fact/rule AST.

Allowed source should be limited to declarative facts and Horn-style rules whose bodies use predicates permitted by the bundle dependency graph and the query server builtin registry. The publisher should reject at least:

- directives and initialization hooks;
- arbitrary module loading from source clauses;
- meta-call and dynamically constructed predicate invocation;
- shell, filesystem, network, process, and environment access;
- assert/retract/database mutation;
- term expansion or compile-time execution;
- unapproved foreign predicates.

Compiled CouchDB documents retain provenance back to the source repository commit, module, path, clause identity, citations, and licensing metadata.

This preserves Prolog as the human-facing knowledge language without weakening the current runtime security model.

* Modules and Bundles

The source repository should distinguish small reusable *modules* from actor-facing *bundles*.

Example source modules:

#+begin_src text
core.provenance
core.confidence
core.temporal
geo.core
geo.us
dialect.core
dialect.en-us.lexical
dialect.en-us.syntax
dialect.en-us.survey
dialect.en-us.scoring
organizations.core
social.core
#+end_src

An actor asks for a bundle, not paths. Example:

#+begin_src text
bundle: star.dialect.en-us
requires:
  - core.provenance
  - core.confidence
  - geo.core
  - geo.us
  - dialect.core
  - dialect.en-us.lexical
  - dialect.en-us.syntax
  - dialect.en-us.scoring
#+end_src

The current query server executes one named =(kb, release)= at a time. The least invasive v1 composition model is therefore to resolve a bundle's dependency closure *at publication time* and materialize the bundle as one immutable query-server KB release. Every generated fact/rule retains =originModule= and source provenance so flattening does not destroy authorship.

This avoids adding multi-KB join/import semantics to the runtime before there is evidence that the copy/storage cost is a real problem.

* Deterministic Identity and Reproducibility

A published bundle should have both a human version and deterministic content identity. At minimum record:

#+begin_src text
bundleName
bundleVersion
sourceCommit
contentHash
compilerVersion
querySchemaVersion
runtimeTarget
moduleClosure[]
sourceLicenses[]
publishedRelease
#+end_src

Each compiled CouchDB knowledge document should receive a deterministic ID derived from bundle/release plus normalized source-clause identity. The publication tool should be repeatable: identical source input produces the same compiled logical corpus and manifest metadata.

Default production queries use the active release. Reproducible analyses and stored StarIntel derivations should record or explicitly pin the exact release.

* Query Contract for Actors

The normal actor interface should remain the current structured query form rather than a raw Prolog text endpoint.

Conceptual request:

#+begin_src json
{
  "kb": "star.dialect.en-us",
  "release": "2026-09-10-a",
  "goal": {
    "predicate": "dialect_candidate",
    "args": [
      ["pop", "drinking_fountain", "freeway"],
      {"var": "Region"},
      {"var": "Score"}
    ]
  },
  "max_depth": 32,
  "max_solutions": 20,
  "refresh": true
}
#+end_src

A Common Lisp client library may wrap this in typed functions, but the network contract should remain query-server JSON. Actor code should not depend on CouchDB internals or parse Prolog source.

For decisions that need auditability, use =/v1/explain= and preserve the proof-source references with the derived StarIntel document or actor event.

* Dialect Enrichment as the First Reference Consumer

Dialect is a good first consumer because it stresses several parts of the shared-knowledge design without requiring privileged data.

** Evidence classes must remain separate

A dialect actor should not collapse every geographic clue into a language fact. At minimum distinguish:

1. *linguistic evidence*: lexical, syntactic, orthographic, and when available phonological observations;
2. *geographic lexical/context evidence*: regionally concentrated products, institutions, transport vocabulary, or place-associated context;
3. *named-entity geographic evidence*: explicit businesses, cities, teams, roads, or places;
4. *learned-model evidence*: model-produced regional scores with model/version metadata.

A statement such as a regional brand mention can support geographic context without becoming proof that a speaker has a dialect from that region.

** Output semantics

The actor should return candidate regions and evidence rather than a precise identity/location assertion.

Conceptual output:

#+begin_src text
linguisticProfile
  candidates:
    inland_north: 0.67
    north_midland: 0.18
    general_us: 0.09
  evidence:
    - lexical(pop)
    - lexical(drinking_fountain)
  contextualEvidence:
    - regional_entity(meijer)
  knowledgeRelease: ...
  proofSources: [...]
#+end_src

Confidence values must describe the scoring/model semantics actually used. They must not be presented as a calibrated probability unless calibration has been demonstrated.

* Dialect Corpus Acquisition Findings

** MyDialect / Harvard Dialect Survey

MyDialect currently exposes the original Harvard Dialect Survey in multiple quiz sizes; its full quiz states that it uses 122 original survey questions. It states that the survey data are from Bert Vaux and Scott Golder under =CC BY-NC-SA 3.0=.

That makes it useful for research, comparison, and validation, but the =NC= and =SA= terms create downstream constraints that should not be silently inherited by StarIntel's general-purpose canonical knowledge corpus. Treat this source as research/benchmark material unless a concrete intended use is reviewed for license compatibility.

** Self-sourced first-party survey

The preferred long-term corpus is a StarIntel-controlled survey with independently authored prompts grounded in published dialect phenomena and explicit provenance for each question.

Location labels should capture more than current residence:

- birthplace;
- locations lived at approximately ages 0-5, 6-12, and 13-18;
- current residence;
- optional self-described dialect/background;
- respondent/session identity sufficient to prevent train/test speaker leakage without publishing unnecessary personal identifiers.

The distinction matters because current location or posting location is not equivalent to dialect-acquisition geography.

An optional free-text response can pair structured survey answers with natural language from the same consenting respondent. Audio can be a later separately consented layer.

** Weakly labelled public corpora

Geo-Twitter2019 publishes tweet IDs for a geographically situated English corpus with 2,075,394 US tweets and 1,088,232 UK tweets (3,163,626 total) and accompanies DialectGram work on multi-geographic-resolution dialect variation.

Such corpora are useful for weakly supervised experiments and benchmark replication, but a posting/geographic label must be represented as =current/post location evidence= rather than =dialect origin=. Training/evaluation splits should be by speaker/respondent where possible, not by post, to avoid identity leakage across train and test.

* Symbolic, StarLang, and Learned-Model Roles

| Candidate | Recommended role | Reason |
|-----------+------------------+--------|
| Prolog query server | Primary shared symbolic inference runtime | Already implements safe persisted facts/rules, releases, bounded inference, synchronization, proofs, auth, and analysis |
| Restricted Prolog source in =star-kb= | Primary human/agent knowledge-authoring representation | Keeps facts/rules readable and reusable while compiling to safe runtime AST |
| Common Lisp actor wrapper | First production consumer integration | Matches current StarIntel actor/runtime ownership and keeps knowledge transport outside actor logic |
| StarLang | Later orchestration/adapter consumer | Current StarLang direction calls for generic process/RPC adapter boundaries rather than Prolog syntax in core language |
| Deep-learning dialect model | Independent evidence producer | Useful for free text/audio and interactions not explicitly represented by hand rules; should emit versioned observations into symbolic fusion rather than become knowledge authority |
| cplint | Future probabilistic-logic experiment | SWI package supports probabilistic logic inference/learning, but directly exposing it would bypass the query server's current restricted execution model |

* Alternatives Considered

** Load trusted =.pl= directly into every actor

Rejected as the default. It duplicates runtimes, complicates supervision and hot reload, fragments knowledge versions, and bypasses the query server's existing release/proof/security boundary.

** Put only query-server JSON documents in Git

Viable as a compiled artifact, but weak as the sole authoring format for a large human-maintained symbolic corpus. The source should preserve a compact Prolog-like declarative representation and compile it deterministically.

** Use SWI Pengines as the actor API

Not recommended for the production knowledge boundary. Pengines are designed to create remote Prolog engines and can accept injected clauses/source through mechanisms such as =src_list=, =src_text=, and =src_url=. StarIntel already has a narrower structured query API with a deliberately smaller attack and compatibility surface.

** Add cplint immediately

Deferred. =cplint= is an established SWI-Prolog pack for probabilistic logic inference and learning, but the first dialect slice can validate the knowledge/release/proof architecture using explicit weighted evidence and safe arithmetic. Probabilistic-program execution should get its own threat, performance, calibration, and serialization research pass before becoming a production builtin.

** Add tabling immediately

Deferred but architecturally useful. SWI tabling can avoid repeated evaluation and terminate some left-recursive programs; incremental tabling can invalidate/re-evaluate tables after dynamic predicates change. The current query server has a custom bounded meta-interpreter, so table declarations must not become an unrestricted per-document capability. A future optimized executor can expose explicitly approved tabled predicates behind the same query contract.

* Security and Correctness Invariants

1. No actor-supplied raw Prolog source reaches production inference.
2. No canonical KB publication bypasses the safe AST compiler and query-server validation.
3. Every release is staged completely, analyzed, tested, and only then activated.
4. Active non-legacy releases remain immutable.
5. Unresolved CouchDB conflicts fail closed.
6. Actor queries remain bounded by request, depth, solution, resource, and time policies.
7. Read and write credentials remain separate; production traffic uses TLS.
8. Proof/explanation metadata may contain source identifiers but must not accidentally expose secret payloads.
9. Canonical knowledge and case/run observations remain separate stores and separate provenance classes.
10. A learned model can contribute evidence but cannot silently promote its output into canonical knowledge.
11. Licensing metadata travels with imported/promoted source knowledge and is included in bundle publication validation.
12. Reproducible derivations record the exact active or pinned KB release.

* Recommended First Implementation Slice

After explicit approval:

1. Create =star-kb= with repository policy, restricted source profile, source/provenance schema, module/bundle manifest schema, and deterministic clause IDs.
2. Implement the compiler from restricted source facts/rules to =prolog-query-server= knowledge documents.
3. Implement bundle dependency closure and flatten one bundle into one named query-server KB release.
4. Invoke the existing query-server static-analysis endpoint and a fixture query suite before activation.
5. Publish and activate a tiny =star.core.test= bundle to prove deterministic rebuild, pinning, rollback, and proof provenance.
6. Add the Common Lisp query-server client boundary without a dialect-specific dependency.
7. Build =star.dialect.en-us= as the first real bundle and a dialect actor as the first real actor consumer.
8. Only after symbolic baseline metrics exist, benchmark learned text models and optional probabilistic-logic alternatives against the same held-out respondent splits.

* Research Gaps

The following should remain explicit follow-up questions rather than being guessed during implementation:

- exact restricted Prolog source grammar and whether comments/source spans survive compilation;
- maximum practical bundle size before publication-time dependency flattening becomes too duplicative;
- whether actor queries need transient per-query fact contexts beyond passing evidence as goal arguments;
- calibrated scoring semantics for dialect candidates;
- first-party survey consent, retention, deletion, and public-release policy;
- geographic hierarchy granularity beyond states and broad dialect regions;
- whether an optimized tabled executor is necessary after real workload benchmarks;
- whether probabilistic logic should be implemented as safe dedicated builtins, a separately isolated service, or remain an offline research tool;
- compatibility contract/version negotiation between a future StarLang adapter and query-server API versions.

* Footnotes and Glossary

[fn:kb] *Knowledge base (KB)*: a named set of facts and rules used by an inference engine.

[fn:bundle] *Bundle*: an actor-facing, versioned dependency closure of reusable source modules compiled into one deployable query-server knowledge release in the proposed v1 design.

[fn:release] *Release*: an immutable logical set of query-server fact/rule documents selected by a CouchDB manifest.

[fn:provenance] *Provenance*: metadata identifying where an assertion, rule, observation, or derivation came from and which exact versions participated.

[fn:observation] *Observation*: run/case-specific evidence produced or captured by an actor; it is not automatically canonical general knowledge.

[fn:pengine] *Pengine*: SWI-Prolog's remote Prolog-engine abstraction.

[fn:tabling] *Tabling*: memoized goal-directed evaluation that can avoid repeated work and some recursive nontermination patterns.
