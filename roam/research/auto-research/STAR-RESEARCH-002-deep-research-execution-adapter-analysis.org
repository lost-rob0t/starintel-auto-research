* Research Question

How should the Adaptive Design, Analysis, Research, and Development loop[fn:adard] use existing deep-research systems[fn:deep-research] without transferring control of budgets, candidate state, evaluation, provenance, or promotion to those systems?

The answer must distinguish research capabilities rather than selecting one universal engine. It must also define where browser JavaScript actors[fn:browser-worker] fit without making Quasar UI the owner of deep-research semantics.

* Required Boundary

The existing ADARD design remains authoritative:

- the Research Run Supervisor owns the run
- the Branch Supervisor owns candidate isolation and budgets
- append-only ledgers own durable state
- the deterministic validator rejects malformed or unsupported output
- independent reviewers score normalized candidate evidence
- the Promotion Gate is the only component allowed to create a canonical design proposal

A deep-research engine is therefore a worker behind an adapter[fn:adapter]. It may plan searches, retrieve sources, ask follow-up questions, summarize material, and generate a report. It may not:

- create or mutate ADARD run or candidate records directly
- write canonical Org-roam files
- promote architecture
- invent a second durable state machine
- expose provider-specific objects as the ADARD contract
- receive unrestricted repository or network access merely because the upstream engine supports it

Quasar may later display, start, pause, or inspect an ADARD run. It is not the research control plane.

* Systems Examined

** LangChain Open Deep Research

The current implementation is a configurable LangGraph[fn:langgraph] research agent. Its official repository separates model roles for summarization, research, compression, and final report generation. It supports multiple model providers, search tools, native web search, and Model Context Protocol[fn:mcp] servers. The repository also retains older workflow and supervisor/researcher implementations, providing evidence that plan-and-execute and parallel supervisor patterns can share one external interface.

Transferable strengths:

- clear separation of research phases
- broad search and Model Context Protocol integration
- configurable model roles
- explicit evaluation support
- parallel researcher architecture
- report compression before final synthesis

Integration risks:

- LangGraph state must not become ADARD state
- provider and search configuration is broad enough to bypass ADARD scope unless filtered
- benchmark scores measure report quality, not StarIntel provenance or promotion correctness
- the engine may return a polished report without the claim-level evidence structure ADARD requires

Best initial route: general web and mixed-tool research where broad retrieval and parallel research are more important than a domain-specific scientific corpus.

** GPT Researcher

GPT Researcher exposes planner, execution, crawler, source-tracking, aggregation, and publishing stages. Its deep-research mode uses recursive tree-like exploration with configurable breadth and depth, concurrent branch processing, and context sharing. It supports web, local documents, and Model Context Protocol retrievers.

Transferable strengths:

- explicit planner/executor/publisher split
- configurable recursive breadth and depth
- concurrent subtopic exploration
- source tracking per resource
- web and local-document research
- a direct Python package interface suitable for a process adapter

Integration risks:

- its internal research tree overlaps with the ADARD candidate graph and must remain subordinate
- recursive depth and breadth must be clamped by ADARD budgets
- a generated report is not sufficient evidence that every material claim is supported
- internal memory must not be mistaken for durable replayable state

Best initial route: a bounded deep exploration inside one ADARD candidate when the requested capability explicitly requires recursive subtopic expansion.

** STORM and Co-STORM

STORM[fn:storm] separates pre-writing research and outline generation from article writing. It improves question quality through perspective-guided question asking and simulated conversations grounded in retrieved sources. Co-STORM adds a collaborative discourse protocol, moderator and expert roles, and a dynamic mind map that organizes collected information.

Transferable strengths:

- perspective discovery before question generation
- grounded follow-up questions
- outline-first synthesis
- explicit information-curation boundary
- dynamic concept organization
- human steering in Co-STORM

Integration risks:

- Wikipedia-style article production is not the same as claim and evidence production
- simulated conversations can obscure which retrieved passage supports which conclusion
- a mind map is a useful artifact, not canonical ADARD state
- the engine is optimized for knowledge curation rather than adversarial evidence review

Best initial route: perspective enumeration, question-plan generation, outline construction, and concept-map artifacts before or alongside a normal ADARD candidate review.

** PaperQA2

PaperQA2 is an agentic retrieval-augmented generation system[fn:rag] focused on scientific literature and local document collections. Its workflow searches for papers, gathers evidence through embeddings, ranking, contextual summarization, and re-scoring, then generates an answer from the selected evidence. It includes metadata-aware retrieval, citation and journal information, local full-text indexes, iterative tool use, and support for multiple model providers.

Transferable strengths:

- scientific-literature specialization
- local and cached document collections
- metadata-aware retrieval
- page-level in-text citations
- iterative query refinement
- contradiction-oriented scientific workflows

Integration risks:

- its evidence and metadata model is specialized for papers rather than arbitrary public records
- external metadata providers can disagree or fail
- vector relevance is not a substitute for source authority or claim verification
- cached indexes require explicit version and content hashes for replay

Best initial route: scientific and technical literature questions, local paper collections, contradiction checks, and evidence packets that require page-level citations.

* Comparative Capability Matrix

| Capability route | Preferred first adapter | Permitted fallback | Reason |
|------------------+-------------------------+--------------------+--------|
| =general-web= | Open Deep Research | GPT Researcher | Broad provider, search, and Model Context Protocol support with parallel research |
| =recursive-web= | GPT Researcher | Open Deep Research | Explicit configurable depth, breadth, and concurrent branch exploration |
| =perspective-plan= | STORM | Open Deep Research | Perspective-guided questions and outline-first knowledge curation |
| =collaborative-curation= | Co-STORM | STORM | Human-steered discourse and dynamic concept map |
| =scientific-literature= | PaperQA2 | STORM with document retriever | Metadata-aware paper retrieval and page-level cited evidence |
| =local-document-rag= | PaperQA2 | GPT Researcher | Local indexes, contextual summaries, and source-grounded answers |

This is an initial routing hypothesis. It must be tested on fixed fixtures before becoming a production selection policy.

* Common Architecture Extracted

Despite different implementations, the systems share a usable external pattern:

1. accept a bounded question and source scope
2. plan subquestions or perspectives
3. retrieve documents or search results
4. summarize or compress evidence
5. repeat bounded follow-up research
6. synthesize a report or answer
7. return citations, traces, and metrics

ADARD should standardize this pattern as an execution port[fn:execution-port], not copy an upstream engine's internal graph.

* Normalized Adapter Requirements

Every adapter must accept:

- ADARD run and candidate identifiers
- capability route
- exact research question
- immutable input packet identifier and hash
- allowed source and repository scope
- allowed retrievers and tools
- fixed model configuration or declared local model route
- wall-clock, request, branch, depth, token, byte, and cost limits
- output schema version
- cancellation identifier

Every adapter must emit a normalized event stream containing:

- accepted
- planning
- query-issued
- source-discovered
- source-retrieved
- evidence-extracted
- branch-started
- branch-completed
- progress
- warning
- completed
- failed
- cancelled

Every adapter result must contain:

- engine name, version, adapter version, and configuration hash
- start and completion timestamps
- normalized source records
- claim records linked to supporting and contradicting evidence
- unanswered questions
- report or answer artifact
- optional outline, mind map, or branch-tree artifacts
- request, token, time, byte, and cost metrics when available
- raw artifact references
- stable hashes for inputs and outputs
- declared truncation, unsupported features, and fallback use

* Evidence and Provenance Boundary

A citation string inside a generated report is not enough. The adapter must normalize each retrieved source into a record containing at least:

- original locator
- retrieved timestamp
- title and publisher when available
- content or capture hash
- retrieval method
- local artifact reference when retained
- source excerpt or page locator used by a claim
- upstream engine and query that discovered it

Claims must be separated from prose. Each material claim must reference supporting evidence, contradicting evidence when found, or an explicit inference label. The deterministic validator may reject a polished report whose claims cannot be resolved to normalized evidence.

* Browser JavaScript Actor Boundary

Browser JavaScript actors belong to Auto Research as one optional worker runtime. They are useful for:

- operator-authorized browser sessions
- local document access selected by the operator
- JavaScript-rendered page extraction
- interactive or browser-only sources
- lightweight local transforms and evidence normalization

They must use the same adapter request, event, and result envelopes as process or service workers. A browser worker receives cloned bounded input and explicit capabilities. It does not receive direct access to ADARD ledgers, canonical Org files, Quasar internal state, or unrestricted browser globals.

Quasar may host the user interface that starts such a worker, but the actor manifest[fn:actor-manifest], capability route, run identity, budgets, and result validation remain Auto Research contracts.

* Evaluation Contract

The adapter study requires fixed fixtures covering:

1. a current general-web question requiring several independent sources
2. a recursive question whose answer requires at least two levels of subtopics
3. a disputed claim requiring supporting and contradicting evidence
4. a local-document question with an answer absent from the public web
5. a scientific-literature question requiring page-level citations
6. a no-answer case where the correct result is unresolved
7. a prompt-injection page that must remain quoted evidence rather than instructions
8. cancellation during active retrieval
9. budget exhaustion during branch expansion
10. replay using the same immutable input and configuration

Measurements:

- valid normalized envelope rate
- citation resolvability
- claim-to-evidence coverage
- contrary-evidence capture
- unsupported central claims
- source diversity and duplicate rate
- unanswered-question quality
- wall-clock time
- request and token use
- cost when applicable
- cancellation latency
- repeated-run stability
- adapter-specific information loss

A general report-quality score cannot override unresolved citations, unsupported central claims, scope violation, or a broken cancellation boundary.

* Recommendation

Create =STAR-RESEARCH-PIPELINE-002 Deep Research Execution Adapters= as a dependent design behind =STAR-RESEARCH-PIPELINE-001=.

The first implementation slice should contain:

- a runtime-neutral adapter registry
- versioned request, event, and result envelopes
- a supervised process runner using newline-delimited JSON[fn:ndjson]
- deterministic normalization and validation
- one Open Deep Research adapter
- one GPT Researcher adapter
- fixture-driven comparison against the same questions
- a browser-worker port with a fake deterministic adapter, not a full browser crawler

STORM, Co-STORM, and PaperQA2 should be second-wave adapters after the contract is proven. Their specialized perspective, concept-map, and scientific-evidence artifacts should be optional result artifacts rather than new ADARD document types.

* Negative Findings

- No examined engine provides the complete ADARD promotion and replay contract.
- No benchmark score proves claim-level provenance quality for StarIntel work.
- Recursive research trees must not be merged directly into the ADARD candidate graph.
- A generated bibliography does not prove that citations resolve to the claim being made.
- Browser execution does not make Quasar the owner of research semantics.
- Importing every engine into one Python process would couple dependencies, cancellation, logging, and failure modes; process or service adapters are the cleaner first boundary.

* Footnotes and Glossary

[fn:adard] Adaptive Design, Analysis, Research, and Development loop, or ADARD: The bounded StarIntel control plane that creates competing research candidates, records their state, evaluates them, and promotes at most one reviewed design proposal.

[fn:deep-research] Deep-research system: Software that plans subquestions, retrieves several sources, iteratively follows evidence, and synthesizes a cited answer or report rather than answering from one model prompt.

[fn:browser-worker] Browser JavaScript actor: A bounded JavaScript worker running in or beside a web browser that receives explicit input and capabilities and returns structured results through messages.

[fn:adapter] Adapter: A small boundary component that converts one system's request, events, errors, and results into the stable contract expected by another system.

[fn:langgraph] LangGraph: A library for implementing stateful language-model workflows as graphs of steps and transitions.

[fn:mcp] Model Context Protocol, or MCP: A protocol that lets a model-driven application discover and invoke external tools or data services through a common interface.

[fn:storm] Synthesis of Topic Outlines through Retrieval and Multi-perspective Question Asking, or STORM: A research system that gathers sources through perspective-guided questions and simulated expert conversations before creating an outline and article.

[fn:rag] Retrieval-augmented generation, or RAG: A method that retrieves relevant external text and supplies it to a language model so the generated answer can be grounded in those sources.

[fn:execution-port] Execution port: A runtime-neutral interface that defines what a worker receives and returns without requiring the control plane to depend on the worker's programming language or internal framework.

[fn:actor-manifest] Actor manifest: A versioned document that declares an actor's identity, runtime, accepted inputs, produced outputs, capabilities, dependencies, and resource limits.

[fn:ndjson] Newline-delimited JSON, or NDJSON: A stream format where each line is one complete JavaScript Object Notation value, allowing events and results to be processed incrementally.
