#+description: Compare RabbitMQ, LMDB, CouchDB, ZeroMQ, SQLite, NATS JetStream, Kafka, and Temporal for the StarIntel Titanic durable actor-job protocol without promoting comparative transport research into architecture by accident.

* Research Question

Which transport and persistence combination best fits Titanic v1 while keeping =star.titanic/1= backend-neutral and transport-neutral?

* Correction Notice

Earlier versions of this research first over-promoted RabbitMQ/JetStream and then over-corrected by declaring ZeroMQ the canonical Titanic worker transport.

Both moves confused comparative research with implementation selection.

[[id:starintel-star-server-research-037][STAR-RESEARCH-037 Titanic Polyglot ZeroMQ Research Boundary Correction]] records the transport correction.

[[id:starintel-star-server-research-038][STAR-RESEARCH-038 Titanic CouchDB Backend Fit]] evaluates CouchDB as a serious journal/projection candidate.

The selected v1 direction is:

- RabbitMQ for brokered actor-job delivery;
- LMDB for the first authoritative Titanic journal;
- CouchDB for a queryable/replicated projection and as a supported alternate backend candidate;
- ZeroMQ retained as transport research and an optional future specialized adapter;
- =star.titanic/1= semantics independent of all of those implementation details.

* Layer Separation

Titanic is not a broker and it is not a database.

#+begin_example
producer / caller
      |
      | star.titanic/1
      v
 RabbitMQ adapter
      |
      v
Titanic coordinator
      |
      | job-store contract
      v
     LMDB
 authoritative journal
      |
      +--------------------+
                           v
                        CouchDB
                 projection/query/UI
#+end_example

The transport moves work. The journal records authoritative job truth. Titanic defines the durable semantics.

* Evaluation Criteria

The chosen v1 must support:

- stable logical =job_id=;
- idempotent admission;
- durable acceptance before reporting =accepted=;
- at-least-once execution with duplicate-safe recovery;
- explicit broker settlement;
- bounded retry and dead-letter lineage;
- cancellation and absolute deadlines;
- attempt identity;
- retained result lookup after disconnect;
- correlation, causation, tracing, and provenance;
- target lease/fencing metadata where required;
- crash recovery at every journal/broker boundary;
- local-first deployment;
- Common Lisp ownership of the core coordinator;
- language-neutral job envelopes for polyglot workers;
- a backend contract that can be tested against fake, LMDB, CouchDB, and future stores.

* Comparison Matrix

| System | Best role | Strengths | Main limitation for Titanic | V1 decision |
|--------+-----------+-----------+-----------------------------+-------------|
| RabbitMQ | brokered work delivery | already deployed; confirms; ACK/NACK; competing consumers; DLX; prefetch; routing | broker state is not the complete durable job lifecycle | PRIMARY TRANSPORT |
| LMDB | embedded authoritative journal | local ACID; transactions across keys/sub-databases; tiny footprint; cheap reads | one concurrent writer; no built-in remote query/replication | PRIMARY JOURNAL |
| CouchDB | JSON journal candidate / projection | durable per-doc MVCC; =_rev= CAS; Mango/views; changes; replication; existing StarIntel infra | no atomic multi-document transaction; replication conflicts; distributed quorum is not serializable | PROJECTION + SERIOUS ALTERNATE BACKEND |
| SQLite | embedded journal comparison | ACID; SQL; constraints; easy inspection | relational impedance/locking model differs from desired KV journal | BENCHMARK / REFERENCE |
| ZeroMQ / ZMTP | specialized polyglot transport | broad language boundary; ROUTER/DEALER; no broker daemon | no durability; would add a second mandatory transport if promoted without need | RESEARCH / OPTIONAL ADAPTER |
| NATS JetStream | durable queue/stream comparison | durable consumers; redelivery; work-queue retention | adds another broker/control plane without a current requirement | COMPARISON ONLY |
| Kafka | durable event log | replay; partitioned stream scale | offsets/partitions are unnecessary for the v1 job problem | NON-V1 |
| Temporal | durable workflow runtime | deep long-running workflow semantics | separate execution/control model and platform | NON-V1 |

* RabbitMQ

RabbitMQ already solves the transport mechanics Titanic should not rebuild:

- persistent publication;
- publisher confirms;
- durable queues/exchanges;
- competing consumers;
- explicit ACK/NACK;
- redelivery;
- dead-letter exchanges;
- prefetch/backpressure;
- routing by capability.

RabbitMQ is therefore the first Titanic transport adapter.

It is not the Titanic journal.

The stable protocol must not contain AMQP delivery tags, channel identity, connection objects, exchange implementation details, or queue arguments.

The dual-write boundary between the job journal and RabbitMQ must use outbox/reconciliation semantics from [[id:starintel-star-server-research-036][STAR-RESEARCH-036 Titanic Failure Semantics and Contract Tests]].

* LMDB

LMDB is the selected first authoritative journal implementation.

The job-store contract should expose operations such as:

#+begin_example
put-job
get-job
compare-and-transition
append-attempt
put-result
get-result
claim-dispatch
renew-dispatch
release-dispatch
record-idempotency-outcome
record-outbox
confirm-outbox
record-dead-letter
record-replay
#+end_example

LMDB fits because Titanic itself owns the store. Worker languages never touch LMDB directly.

A single LMDB write transaction can update multiple logical records inside the same environment, which is useful for atomic job/outbox/idempotency transitions. LMDB's serialized-writer model also gives the coordinator one explicit mutation order rather than distributing execution authority across replicas.

Required validation includes:

- write throughput under expected actor-job admission rates;
- crash recovery at every state transition;
- long-lived reader behavior;
- map sizing and growth;
- backup/restore;
- corruption handling;
- deterministic export/rebuild;
- coordinator restart while RabbitMQ contains in-flight/redelivered work.

* CouchDB

CouchDB is stronger than the old comparison gave it credit for.

See [[id:starintel-star-server-research-038][STAR-RESEARCH-038 Titanic CouchDB Backend Fit]].

Useful properties:

- normal document commits are durable and crash-consistent;
- =_rev= provides optimistic compare-and-transition behavior;
- stale writes fail with =409 Conflict=;
- =validate_doc_update= can enforce state-machine invariants;
- JSON is directly inspectable and queryable;
- Mango/views support operational queries;
- =_changes= is useful for projection triggers;
- replication and clustering are built in.

Important constraints:

- =_bulk_docs= is non-atomic across documents;
- cluster quorum does not make CouchDB a serializable transaction system;
- replication can create conflicting revisions;
- normal reads choose one deterministic winning revision;
- revision bodies are not a permanent audit log because compaction removes old bodies;
- =_changes= is not guaranteed to expose every intermediate mutation of one document.

Therefore a CouchDB authoritative backend should use one aggregate document per logical job so each authoritative state change is one CAS update. Idempotent admission, active attempt, cancellation, result, and any outbox state that must change atomically should live in that aggregate or be modeled with explicit reconciliation.

For v1 the cleaner role is:

#+begin_example
LMDB authoritative state
        |
        v
CouchDB projection
        |
        +--> UI / dashboards
        +--> administrative query
        +--> replication/export
        +--> analytics
#+end_example

* SQLite

SQLite remains a useful benchmark because it offers strong local transactions plus SQL inspection.

It should be compared against LMDB using actual Titanic state-machine workloads rather than generic database benchmarks:

- submit + idempotency + outbox;
- dispatch claim;
- heartbeat/progress;
- retry transition;
- terminal outcome;
- dead-letter/replay;
- retention sweep.

No SQLite promotion is implied unless the benchmark shows a concrete operational or correctness advantage.

* ZeroMQ / ZMTP

ZeroMQ remains good research for cross-language boundaries.

That does not make it the default Titanic transport.

Potential future roles:

- remote actor gateway;
- low-latency specialized pool;
- Sento cross-process transport;
- non-durable internal process boundary;
- research/conformance peer for Common Lisp, Nim, Python, and JavaScript.

If a future =zmq= Titanic adapter is implemented, Titanic itself must still supply durable admission, state, retries, cancellation, and retained results. Transport choice cannot change the job contract.

* NATS JetStream

JetStream has useful durable queue semantics and remains worth studying.

Adopting it now would create another broker beside RabbitMQ without solving a concrete v1 gap. Keep it comparative unless a later independent requirement specifically selects NATS.

* Kafka

Kafka is a durable partitioned log and is excellent when the system problem is replayable streams with independent consumer groups.

Titanic v1 is narrower: accept one logical job, schedule it, retry/fail it, and retain one durable result. Do not introduce Kafka merely to model that state machine.

* Temporal

Temporal is a durable workflow platform rather than a simple transport or journal.

It becomes interesting if Titanic evolves into long-running, multi-step workflow orchestration where durable timers and workflow history become the dominant problem. It is unnecessary for v1 and would add another execution model beside Sento and StarIntel's own actor semantics.

* Backend-Neutral Contract

The first implementation choices must remain replaceable.

=star.titanic/1= should expose semantics such as:

#+begin_example
submit(job) -> accepted(job-id) | rejected | unknown-outcome
status(job-id) -> state
result(job-id) -> result | pending | failed | cancelled | unknown
cancel(job-id) -> requested | terminal-state
close(job-id) -> retention-released
replay(dead-letter-id) -> new-attempt-lineage
#+end_example

The =job-store= implementation decides how those semantics are persisted.

The transport adapter decides how attempts move to workers.

Neither implementation owns the protocol meaning.

* Recommendation

Titanic v1 should use:

#+begin_example
RabbitMQ
   |
   v
Titanic coordinator
   |
   v
LMDB authoritative journal
   |
   +--> CouchDB projection/operator store
#+end_example

Do not require ZeroMQ for v1. Keep it as researched transport capability and add it only when a concrete boundary benefits from it.

Keep CouchDB in active backend research and implement it behind the same =job-store= contract if distributed/queryable job authority becomes valuable enough to justify its consistency model.
