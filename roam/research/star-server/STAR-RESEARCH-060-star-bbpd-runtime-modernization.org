* Purpose

Reconcile the =star-bbpd= external actor service (Python/Pykka/pika) with the current StarIntel ecosystem so that:

1. BBPD receives targets through both the canonical durable target dispatch key and the legacy compatibility key;
2. BBPD events conform to the current starintel-server event contract instead of relying on lenient decode normalization;
3. BBPD carries canonical RFC 3986 =star://= actor identity per [[file:../../research/star-server/STAR-RESEARCH-041-unified-star-uri-authority-routing-and-fediwatch-rabbitmq.org][STAR-RESEARCH-041]] and [[file:../../design/star-lang/STAR-LANG-004-star-service-uri-discovery.org][STAR-LANG-004]];
4. the future BBPD domain actor to StarLang migration ([[file:../../research/star-lang/STAR-LANG-RESEARCH-014-bbp-tool-domain-remoting.org][STAR-LANG-RESEARCH-014]], [[file:../../research/star-lang/STAR-LANG-RESEARCH-016-bbp-recovery-idempotency.org][STAR-LANG-RESEARCH-016]], [[file:../../research/star-lang/STAR-LANG-RESEARCH-017-bbp-runtime-journal.org][STAR-LANG-RESEARCH-017]]) requires no further infrastructure rewrite;
5. no premature StarLang rewrite happens.

* Findings

** BBPD binds only the compatibility target key

BBPD queues bind =actors.<actor>.new.target= (spec section 2). The durable target coordinator emits =documents.target.dispatch.<actor>=. A deployment using only the coordinator silently never delivers targets to BBPD.

Correction: BBPD binds both keys to the same durable queue. The dispatch template stays optional TOML configuration (=routing.target_dispatch_key=) so legacy deployments keep working. This is a compatibility-preserving dual binding, not a protocol fork.

** BBPD events rely on server-side normalization

=bbp.events.create_event= omitted =dtype= and =generation=. The server's decode normalization masks this today, but the event contract is authoritative at validation time (=event-actor.lisp:94-114=) and any tightening would break BBPD intake events.

Correction: emit =dtype: "actorevent"= and =generation: 0= from BBPD.

** BBPD has no STAR identity

The approved URI model ([[file:../../research/star-server/STAR-RESEARCH-041-unified-star-uri-authority-routing-and-fediwatch-rabbitmq.org][STAR-RESEARCH-041]]) is =star://<authority>/<resource-kind>/<resource-path>=. STAR-LANG-004 already uses BBPD as the worked example (=star://bbpd.starintel.actor/actor/nmap=).

Correction: BBPD gains =service.star_authority= configuration, a canonicalization module that implements the RFC 3986 v1 rules (lowercase authority, no userinfo/port/dot-segments/query/fragment, pchar paths, reviewed resource kinds), and a startup actor manifest published as event details. The legacy =star://domain:address:actor-name= tuple is accepted only through an explicit compatibility parser and never emitted.

** The BBPD domain invariants are already StarLang-shaped

STAR-LANG-RESEARCH-016 run identity (=program-id + run-id + tool + target=, terminal =star.bbp.run-id-conflict=) and STAR-LANG-RESEARCH-017 reconnect semantics are the contracts the eventual StarLang actors must inherit. The Python actors do not need to change now; the seam is annotated in source with =TODO(starlang-migration)= markers so the migration points are greppable.

** Transport stays RabbitMQ

Per the STAR-RESEARCH-041 durable-dataflow rule, the publisher pool, connection management, and topology are settlement/transport adapters, not domain logic. They are explicitly not StarLang migration targets.

* Boundary

This research does not:

- port any BBPD actor to StarLang;
- define the production BBPD authority name (operator decision; =bbpd.starintel.actor= is the STAR-LANG-004 illustrative example);
- change starintel-server behavior;
- add per-actor AMQP authentication (none exists server-side);
- implement the durable coordinator on the BBPD side (BBPD remains a queue consumer).
