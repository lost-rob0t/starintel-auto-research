#+title: STAR-PRO-CAPTCHA-003 2Captcha Multi-Family Adapter
#+description: Exact-capability StarIntel Pro Actor design for 2Captcha family-specific task mappers, typed result validators, human-worker disclosure, runtime contract registration, ambiguous-create safety, and isolated hCaptcha probing.
#+status: REVIEW
#+filetags: :starintel:design:starintel-pro-actors:captcha:2captcha:adapter:multi-family:uml:

* Decision

Implement =TwoCaptchaAdapterActor= as a broad asynchronous provider adapter. Each provider task family is an independently versioned capability record with its own request mapper, result validator, context requirements, disclosure class, price, fixture, and state.

Do not globally disable the provider because the hCaptcha contract is uncertain. Keep hCaptcha capability-specific and non-routable until a current official contract, sandbox fixture, or bounded owned-system probe establishes the exact task. Independently verified reCAPTCHA, Turnstile, Arkose, GeeTest, Amazon, image/text, coordinates, grids, rotation, draw-around, drag-and-drop, and other tasks may remain eligible.

The actor accepts only broker-normalized messages and exposes no public solve route.

* Runtime Contract Record

Every configured provider task record contains:

- capability ID;
- provider task type;
- official source and retrieval date;
- issuer, family, variant, and integration version;
- create and result operations;
- required and optional normalized fields;
- provider request mapping version;
- expected result kind and required result fields;
- proxy, cookie, user-agent, browser-session, same-network, and mobile requirements;
- execution class and disclosure class;
- delivery model;
- cancellation;
- idempotency;
- ambiguous-create behavior;
- configured concurrency;
- price and billing evidence;
- retention evidence;
- error contract;
- request/result fixture fingerprint and freshness;
- live-probe requirement and maximum cost;
- unsupported variants and contradictions;
- state: =verified=, =experimental=, =degraded=, =invalidContract=, =disabled=, or =unsupported=.

A healthy provider account does not make every task mapper valid. Static manifests do not advertise active task capabilities.

* Candidate Task Families

The adapter framework can host exact current mappers for:

- reCAPTCHA v2 checkbox and invisible;
- reCAPTCHA v3;
- reCAPTCHA Enterprise checkbox, score, invisible, and policy integrations when exact tasks exist;
- Cloudflare Turnstile managed, non-interactive, and invisible when separately documented;
- Cloudflare Challenge Platform tasks when exact cookie/proof contracts exist;
- Arkose Labs FunCaptcha;
- GeeTest v3 and v4;
- Amazon Web Services Web Application Firewall CAPTCHA and Challenge;
- DataDome and Imperva/Incapsula;
- Friendly Captcha, MTCaptcha, ALTCHA, Prosopo Procaptcha, Tencent, and Yandex SmartCaptcha;
- image-to-text;
- arithmetic and question tasks;
- coordinates, boxes, and draw-around;
- grids and selections;
- rotation, slider, and drag-and-drop;
- hCaptcha only after its independent exact contract passes.

This list is an implementation framework, not a claim that every task is active.

* Request Mapping Rules

A mapper:

1. accepts one normalized exact capability and no wildcard issuer;
2. verifies all required fields before secret dereference;
3. verifies proxy, cookie, user-agent, source-session, network, mobile, execution, and disclosure requirements;
4. creates only the selected provider task type;
5. excludes unsupported or unneeded fields;
6. keeps the client key in the request body only as required by the provider contract;
7. records mapper version and fixture fingerprint with the attempt;
8. rejects capability widening.

Provider task names never appear in the broker-neutral challenge descriptor.

* Result Validation and Typed Results

| Exact provider output | Normalized result kind |
|-----------------------+------------------------|
| issuer token | =token= |
| score or risk metadata | =assessment= or exact token-plus-assessment structure |
| WAF clearance | =cookie=, =proof=, or =token= according to exact contract |
| image/text answer | =textAnswer= |
| points, rectangles, polygons, draw-around output | =coordinates= |
| selected cells or indexes | =selectionSet= |
| slider, rotation, drag sequence | =interactionPlan= |
| versioned family object | =customTypedResult= |

A validator checks exact required fields, types, coordinate systems, ordering, image dimensions, score semantics, token presence, cookie names, and provider status. It rejects a different result kind even when the provider marks the task =ready=.

Sensitive results are written to the ephemeral secret store. The actor returns only =resultRef= and non-sensitive task, price, timing, state, and binding metadata.

* hCaptcha Contract Probe

A hCaptcha probe runs only on explicit operator request and only against a provider sandbox or operator-owned test integration.

1. select one candidate task type and exact variant;
2. enforce credential gate and maximum cost;
3. journal probe attempt;
4. submit one task;
5. require a provider task ID;
6. retrieve the terminal result;
7. verify exact token/result fields and variant behavior;
8. record redacted request/result fixtures and contract fingerprint;
9. move the exact capability to =experimental= or =verified= according to review policy;
10. leave unrelated capabilities unchanged.

Historical software-development-kit names are candidates, not trusted constants. The probe never runs automatically at startup or in continuous integration.

* Human-Worker Disclosure

Register the provider execution class as =humanAssistedVendor= unless exact current evidence proves a narrower class for a specific task.

Before dereferencing target context, broker and adapter policy must permit human-assisted disclosure. The mapper sends only the minimum required fields and bounded artifacts. It does not send full authenticated pages, unrestricted browser snapshots, personal data, cookies, or session material unless the exact capability and target policy explicitly require them.

Disclosure denial is terminal before provider key, proxy, cookie, page data, image, audio, or other sensitive context is read.

* Context Binding

Each capability independently declares:

- proxy type and whether proxyless operation is allowed;
- cookie requirements;
- user-agent fidelity;
- source-browser session binding;
- same-network identity;
- mobile software-development-kit context;
- challenge page or enterprise data;
- result application binding.

A proxy-required task cannot widen to proxyless. A remote human-assisted task cannot satisfy a local same-session-only requirement unless an exact contract and policy establish that path.

* Idempotency, Duplicate Delivery, Cancellation, and Ambiguity

The adapter journals =attemptId= before =createTask= and records =taskId= immediately after a successful response. Duplicate local or RabbitMQ deliveries attach to the existing task or replay its terminal normalized result.

The generic contract does not provide a universal create idempotency key or cancellation operation. An ambiguous create without a recoverable =taskId= is never automatically recreated. Local cancellation stops polling, deletes unconsumed results, and reports =providerCancellationSupported=false= and =chargePossible=true= unless the exact task proves otherwise.

Fallback requires a terminal non-ambiguous prior attempt, new attempt ID, remaining budget, exact capability, deadline fit, and disclosure authorization. Speculative execution remains a separate policy gate.

* Contract Drift State Machine

#+begin_src plantuml
@startuml
[*] --> unsupported
unsupported --> experimental : current official task and fixtures added
experimental --> verified : mapper and validator fixtures pass review
experimental --> invalidContract : unsupported task or schema contradiction
verified --> degraded : known limitation or failure threshold
verified --> invalidContract : required request/result contract drifts
degraded --> verified : recovery fixture passes
degraded --> invalidContract : limitation violates exact request
invalidContract --> experimental : mapper/validator repaired with new fixtures
verified --> disabled : operator or circuit policy
experimental --> disabled
degraded --> disabled
disabled --> experimental : explicit bounded re-enable
verified --> unsupported : official task removed
@enduml
#+end_src

Only the exact affected task changes state. Shared client-key, balance, generic API, or provider outage may temporarily mark all tasks =disabled=.

* Cost, Concurrency, Feedback, and Health

Store price with exact task, official retrieval date, currency, and fixture. Reserve budget before create. Reconcile from provider evidence only. Health includes generic API status, balance, active concurrency, task-specific state, fixture age, provider completion, downstream acceptance, latency, cost per accepted result, and circuit state.

Feedback is sent only through a current documented family operation, under operator policy, and after downstream verification. Feedback never includes local secrets or unsupported target data.

* Shutdown

Stop new submissions, continue bounded polling for active tasks, expire unconsumed result leases, and report unresolved =taskId= values. Local cancellation does not claim provider cancellation. The adapter terminates only after journal and redacted outcome metadata are flushed or the shutdown deadline is reached.

* Security, Retention, and Redaction

Never log, persist, fixture with real values, publish, or place in ordinary messages:

- client key;
- result token;
- clearance cookie;
- text answer;
- coordinates;
- selections;
- interaction plan;
- proxy credential;
- cookie bundle;
- page data;
- authorization header;
- callback secret;
- full provider request/response body containing sensitive fields.

Provider human-worker access and retention require current terms review and explicit target policy. Sensitive values remain in the ephemeral secret store.

* Error Normalization

Normalize authentication, balance, invalid task, invalid fields, unsupported task, processing, unsolvable, timeout, service failure, malformed result, local cancellation, ambiguous create, contract drift, and internal adapter errors. Every failure includes =retryable=, =chargePossible=, and a safe provider code.

* Tests and Bounded Canaries

- generic create, processing, ready, balance, feedback, and every relevant error;
- one mapper and validator fixture per enabled task;
- all normalized result kinds;
- forbidden issuer, family, variant, version, field, result-kind, proxy, session, network, mobile, execution, and disclosure widening;
- hCaptcha unsupported, probe success, probe failure, and drift independent of other tasks;
- duplicate local and RabbitMQ delivery;
- ambiguous create without =taskId=;
- local cancellation with possible provider charge;
- budget exhaustion, concurrency, and deadline behavior;
- human-worker disclosure denial before context dereference;
- client key, context, artifact, result, trace, and error redaction;
- capability-local drift and shared outage behavior;
- static manifest has no active capability claims;
- callback listener absent in version one;
- shutdown with active tasks;
- no paid provider in continuous integration;
- one credential-gated, per-family, strict-cost canary on an operator-owned system.

* Footnotes and Glossary

- *Task mapper* — Versioned conversion from one normalized exact challenge descriptor into one provider-specific task object.
- *Result validator* — Versioned validation that a provider result has the exact kind, fields, and semantics promised by the capability.
- *Human-assisted provider* — Provider execution class in which workers may inspect submitted challenge material.
- *Runtime capability registration* — Startup or drift-event report of exact current task states and fixture evidence.
