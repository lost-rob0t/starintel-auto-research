* Research Question

How should StarLang gain serious Lisp-family metaprogramming without exposing arbitrary host Common Lisp, while retaining a closed parser, deterministic compilation, exact source diagnostics, reproducible manifests, and structural hygiene?

The revised answer is deliberately hybrid:

- use *Nim-style author-facing macro semantics*: macros are compile-time functions that receive syntax trees, inspect or transform them, and return syntax that the compiler checks;
- keep a separate *template* facility for simpler hygienic substitution and code generation;
- use *Racket-style compiler infrastructure*: syntax objects carry source spans, binding scopes, and expansion provenance, and hygiene is structural rather than based on generated textual names;
- do not import Racket's full arbitrary phase tower in the first generation;
- do not copy Nim's broad compile-time ambient authority without StarLang-specific capability and reproducibility controls.

This supersedes the original recommendation that V1 should be limited to =syntax-rules=-like declarative macros.

* Executive Finding

StarLang should support two related source-level expansion mechanisms:

1. =template= for concise, hygienic structural substitution;
2. =macro= for programmable compile-time transformation over StarLang syntax objects.

Both operate before ordinary runtime execution. A macro invocation itself is a compile-time transformation, but the code generated by a template or macro may perform ordinary runtime work.

The compiler architecture should therefore be:

#+begin_src text
.star source
    |
    v
closed StarLang reader
    |
    v
Racket-inspired syntax objects
(span + scope set + origin + datum)
    |
    +-------------------------------+
    |                               |
    v                               v
hygienic templates          programmable macros
(simple substitution)       (typed/untyped syntax)
    |                               |
    +---------------+---------------+
                    |
                    v
         expanded StarLang syntax
                    |
                    v
        semantic validation/checking
                    |
                    v
             normalized IR
                    |
                    v
               runtime
#+end_src

The expansion substrate is language-level compiler architecture. Current-generation implementation remains Common Lisp, but the semantics must not depend on observable Common Lisp reader, package, object-identity, or =EVAL= behavior.

* Canonical Source Audit

** The closed reader remains the correct boundary

The canonical parser in [[https://github.com/lost-rob0t/star-lang/blob/main/prototype/core-surface-prototype.lisp][=prototype/core-surface-prototype.lisp=]] uses a dedicated StarLang parser rather than the Common Lisp reader. That boundary should remain.

Macro support must not mean:

- feeding untrusted =.star= source to Common Lisp =READ=;
- translating user macro definitions into unrestricted host =DEFMACRO= bodies;
- interning attacker-controlled source identifiers into arbitrary CL packages;
- exposing host reader macros or host =EVAL= as the StarLang extension mechanism.

The compiler may be implemented in Common Lisp while the source-language macro model remains a distinct StarLang facility.

** Current source identity is insufficient

The current parser attaches source-position information primarily to list objects. Hygienic metaprogramming requires occurrence-level syntax identity for identifiers and atoms as well as lists.

A macro system must distinguish at least:

- syntax written at the macro use site;
- syntax written in the macro definition;
- syntax synthesized by the transformer;
- two equal textual identifiers with different bindings;
- definition-site and use-site binding context;
- complete source spans;
- the ordered expansion chain that generated a form.

The prerequisite is therefore still a first-class syntax-object layer.

* Research Findings

** Nim: macros are compile-time AST transformations

Nim distinguishes macros from ordinary runtime procedures. Its macro system exposes syntax trees as =NimNode= values, allows a transformer to inspect and construct AST nodes, and checks the produced result through the compiler.

Nim also distinguishes =untyped= and =typed= macro arguments:

- an =untyped= argument is passed to the macro before semantic checking and only needs to be syntactically parsable;
- a =typed= argument is semantically processed before macro invocation, with identifiers resolved and type information available;
- macro-generated syntax is subsequently checked by the compiler.

Nim provides both low-level AST construction and quotation-based generation, along with helpers such as =genSym= and =bindSym= for symbol control.

Sources:

- [[https://nim-lang.org/docs/tut3.html][Nim Tutorial Part III: Macros]]
- [[https://nim-lang.org/docs/macros.html][Nim std/macros]]

This is the correct high-level semantic inspiration for StarLang macros.

** Nim: templates and macros solve different problems

Nim retains templates alongside macros. That separation is useful for StarLang too.

A template should cover the common case where an author wants a small hygienic source abstraction without writing a general tree transformer. A macro should be used when the transformer needs to inspect tree shape, branch on syntax, query checked metadata, synthesize multiple declarations, or perform nontrivial compile-time reasoning.

StarLang should not force simple source abstraction through the most powerful metaprogramming interface.

** Racket: syntax objects provide the stronger hygiene substrate

Racket represents program fragments as syntax objects associated with lexical scope information. Binding and reference resolution operate through scope sets, and macro expansion introduces scopes that prevent accidental capture between generated syntax and use-site syntax.

Racket also tracks expansion history through syntax properties such as =origin=.

Source:

- [[https://docs.racket-lang.org/reference/syntax-model.html][Racket Reference: Syntax Model]]

StarLang should retain this infrastructure even though its author-facing macro semantics are closer to Nim than to =syntax-rules=.

The key distinction is:

#+begin_src text
Nim inspiration      -> what macro authors can do
Racket inspiration   -> how syntax identity, binding, hygiene, and provenance work
#+end_src

These are complementary, not competing choices.

** Racket's full phase system is not required initially

Racket supports bindings and evaluation across multiple phase levels. StarLang does not currently need that degree of module-phase generality.

The initial model should expose a much smaller distinction:

#+begin_src text
compile/expand phase
    -> templates and macro transformers operate here

runtime phase
    -> expanded StarLang program executes here
#+end_src

Additional compile-time phase levels should require a concrete future use case rather than arriving as inherited complexity.

** Common Lisp macros remain implementation evidence, not the source contract

Common Lisp =DEFMACRO= and =MACROEXPAND= remain useful implementation tools for trusted compiler code. They are not the direct StarLang macro API.

Sources:

- [[https://www.lispworks.com/documentation/HyperSpec/Body/m_defmac.htm][Common Lisp HyperSpec: DEFMACRO]]
- [[https://www.lispworks.com/documentation/HyperSpec/Body/f_mexp_.htm][Common Lisp HyperSpec: MACROEXPAND]]

StarLang macros operate on StarLang syntax objects under StarLang compiler rules, even when the current compiler engine implementing those rules is Common Lisp.

* Recommended Language Model

** 1. Hygienic =template=

=template= is the simple expansion facility.

Conceptually:

#+begin_src lisp
(template unless
  ((condition :syntax :untyped)
   (body :syntax :untyped))
  (quote
    (when (not (unquote condition))
      (unquote body))))
#+end_src

The exact quotation syntax remains a surface-design decision; the semantic point is that templates perform hygienic source construction without requiring authors to manually manipulate syntax-node structures.

Template properties:

- expansion occurs at compile time;
- parameters receive syntax, not runtime values;
- generated identifiers are hygienic by default;
- use-site syntax retains its existing scopes;
- definition-site references retain their intended binding identity;
- template output is checked like handwritten StarLang source;
- templates may generate runtime code.

Templates should cover most convenience syntax.

** 2. Programmable =macro=

=macro= is a compile-time StarLang transformer function over syntax objects.

Illustrative direction:

#+begin_src lisp
(macro derive-actor
  ((decl :syntax :untyped))
  (let ((name (syntax-field decl :name))
        (messages (syntax-field decl :messages)))
    (syntax-quote
      (actor (syntax-unquote name)
        ...))))
#+end_src

This is proposed StarLang syntax, not Common Lisp.

A macro may:

- inspect syntax-node kind and children;
- inspect source spans and expansion provenance;
- compare binding identities;
- construct new syntax;
- copy syntax while retaining use-site scopes;
- introduce fresh hygienic bindings;
- deliberately bind to an existing definition-site symbol through an explicit binding operation;
- return one form or a bounded sequence of forms appropriate to the expansion context;
- issue structured compile-time diagnostics.

A macro may not return arbitrary host objects into ordinary runtime IR.

** 3. Typed and untyped macro inputs

StarLang should research the Nim distinction directly.

Candidate parameter declarations:

#+begin_src lisp
(macro rewrite-query
  ((query :syntax :untyped))
  ...)

(macro derive-codec
  ((document-type :syntax :typed))
  ...)
#+end_src

=:untyped= means:

- parsing and syntax-object construction have occurred;
- ordinary semantic validation of that argument has not yet been required;
- the transformer can accept syntax that only becomes valid after expansion.

=:typed= means:

- the relevant semantic checker has run far enough to resolve names and attach checked semantic/type information;
- the transformer receives syntax plus immutable checked metadata;
- a typed macro cannot silently mutate that already-derived semantic information; generated output is checked again as appropriate.

StarLang need not use the literal keywords =:typed= and =:untyped= if later syntax review chooses different names, but the semantic distinction should remain.

** 4. Syntax construction and quotation

Programmable macros need both:

- a structured low-level syntax API for precise tree manipulation;
- a quotation mechanism for writing generated StarLang in readable StarLang syntax.

Candidate operations include:

#+begin_src lisp
(syntax-kind stx)
(syntax-children stx)
(syntax-child stx index)
(syntax-span stx)
(syntax-origin stx)
(syntax-binding stx)
(syntax-identifier "name")
(syntax-literal value)
(syntax-list ...)
(syntax-fresh-identifier "tmp")
(syntax-bind definition-identifier)
(syntax-quote ...)
(syntax-unquote ...)
#+end_src

These names are illustrative. The design requirement is the capability, not these exact spellings.

** 5. Hygiene is structural by default

StarLang should use Racket-inspired scope sets underneath both templates and macros.

Default rules:

1. syntax copied from a macro/template argument preserves its use-site scopes;
2. newly introduced identifiers receive a fresh introduction scope;
3. references intentionally copied from the definition context retain definition-site binding identity;
4. equal textual names do not imply equal bindings;
5. fresh names are compiler identities, not textual random suffix conventions;
6. intentional capture requires an explicit operation and is visible in expansion evidence;
7. converting plain text into an identifier does not implicitly grant a binding.

This is stronger than relying only on gensym-style textual uniqueness.

* Syntax Object Contract

Every parsed occurrence should become a StarLang syntax object with at least:

#+begin_src lisp
(star-syntax
 :datum <atom-or-children>
 :kind <identifier-keyword-string-number-list>
 :span <pathname-start-end>
 :scopes <immutable-scope-set>
 :origin <ordered-expansion-frames>
 :binding <binding-identity-or-nil>
 :semantic <immutable-checked-metadata-or-nil>
 :introduced-by <macro-or-template-id-or-nil>)
#+end_src

Required properties:

1. every occurrence has independent syntax identity;
2. every occurrence has a complete source span;
3. generated syntax can point both to its invocation and definition origin;
4. scope sets are immutable values or treated immutably;
5. binding identity is independent of textual spelling;
6. typed semantic metadata is explicit and immutable from the transformer viewpoint;
7. conversion to plain datum is explicit and lossy;
8. normalized runtime IR never depends on process-local syntax-object identity;
9. canonical serialization excludes object addresses and nondeterministic identifiers.

* Expansion and Checking Pipeline

The initial compiler should use a small explicit phase model.

** Phase 0: read

The closed StarLang reader produces syntax objects and performs lexical / structural parsing only.

** Phase 1: resolve and lock expansion dependencies

The compiler resolves template and macro libraries by exact identity, version, and digest.

The expansion environment must be fixed before transformer execution. No hidden global macro registry should influence compilation.

** Phase 2: expand untyped templates/macros

Transformers accepting untyped syntax may run before ordinary semantic checking of their arguments.

Their output is recursively expanded and then checked.

** Phase 3: semantic analysis sufficient for typed transformers

Names, declared types, capabilities, declaration classes, and other approved semantic metadata are resolved far enough to support typed macro inputs.

The exact semantic frontier must be explicit to avoid checker/expander cycles.

** Phase 4: run typed transformers

Typed macros receive syntax plus checked metadata and return new syntax.

Their output is re-entered through the required expansion and semantic-validation path rather than being trusted as valid merely because the macro received typed input.

** Phase 5: validate expanded core

All remaining syntax must belong to the versioned StarLang core grammar or another explicitly recognized post-expansion declaration class.

** Phase 6: normalize to IR

Template and macro definitions, syntax scope sets, and transformer execution machinery do not become runtime dispatch mechanisms.

Expansion provenance may remain referenced by source maps and compilation evidence.

* Runtime Boundary

The previous wording =DENIED: runtime macro expansion= was too easy to read as if macros were forbidden from generating runtime behavior.

The corrected rule is:

#+begin_quote
A StarLang macro or template is invoked during compilation/expansion. The StarLang code it generates may execute normally at runtime.
#+end_quote

For example, a macro invocation such as:

#+begin_src lisp
(traced
  (send worker message))
#+end_src

could expand into ordinary runtime StarLang such as:

#+begin_src lisp
(begin
  (trace :enter)
  (send worker message)
  (trace :exit))
#+end_src

The =traced= macro is gone after expansion. The generated =trace= and =send= operations execute at runtime.

What is *not part of ordinary macro semantics* is postponing the transformation itself until runtime, for example keeping an unresolved macro invocation inside normalized runtime IR and deciding later how to expand it.

If StarLang later wants runtime syntax interpretation, dynamic compilation, staged code generation, or runtime AST evaluation, those should be researched and named as separate language/runtime features. This node does not prohibit such a future feature; it merely does not redefine it as ordinary macro expansion.

* Compile-Time Transformer Authority

StarLang should copy Nim's programmable-transformer power more than the original 020 did, but it should not automatically copy unrestricted ambient compile-time effects.

A transformer can be powerful over compiler data while still having controlled external authority.

Default compile-time transformer authority should include:

- syntax inspection and construction;
- binding queries;
- immutable checked semantic metadata queries for typed macros;
- deterministic collection operations;
- structured diagnostics;
- compiler-provided fresh syntax identities;
- access to explicitly locked macro/template libraries.

Ambient access should not silently include:

- arbitrary filesystem traversal;
- network access;
- wall-clock time;
- random state;
- process/environment inspection;
- actor runtime state;
- mutable application globals;
- arbitrary Common Lisp function invocation.

If future compile-time tasks genuinely need external information, StarLang may define explicit compile-time capabilities or locked compiler inputs. Such inputs must participate in provenance and reproducibility evidence.

This is a StarLang safety/reproducibility constraint, not a rejection of programmable macros.

* Determinism and Resource Limits

For fixed source, compiler version, core grammar, transformer libraries, locked compiler inputs, and policy, expansion should be deterministic.

The compiler must bound or diagnose:

- recursive expansion cycles;
- expansion depth;
- transformer invocation count;
- generated syntax-node count;
- compile-time CPU/work budget;
- compile-time allocation/output budget;
- diagnostic origin-chain length;
- imported transformer-library count.

Pragma research in STAR-LANG-RESEARCH-027 may define the user-facing configuration mechanism for allowed compiler budgets, but pragmas cannot grant authority beyond mandatory deployment/compiler policy.

* Provenance and Diagnostics

Each expansion frame should record:

- transformer kind: template or macro;
- qualified transformer name;
- library version and digest;
- macro/template definition span;
- invocation span;
- input mode: typed or untyped;
- parent expansion identifier;
- deterministic expansion ordinal;
- output context;
- any explicit compile-time capability/input evidence used.

A diagnostic originating from generated syntax should be able to show:

1. the generated location;
2. the user-written invocation;
3. the transformer definition;
4. the ordered expansion chain;
5. whether the transformer received typed or untyped syntax;
6. the semantic validator that rejected the result.

Recommended compiler tooling:

#+begin_src text
expand-1
expand
expansion-trace
expanded-source
macro-dependencies
syntax-inspect
macro-explain
#+end_src

* Library and Versioning Rules

Template and macro libraries participate in the compilation lock.

Required rules:

- exact version and digest;
- explicit exports;
- explicit imports / aliases;
- deterministic dependency order;
- collision errors by default;
- no hidden global registry;
- macro ABI / syntax-object format versioning;
- compilation cache keys include transformer-library identity;
- generated schema declarations pass the same validators as handwritten declarations.

* Interaction with Pragmas

STAR-LANG-RESEARCH-027 owns the generic pragma/compiler-directive mechanism.

Macros and templates may eventually be usable in annotation-like positions where the grammar deliberately permits a transformation hook, similar in spirit to Nim's ability to use macro/template machinery with declarations.

However:

- =(pragma ...)= remains compiler-interpreted directive data unless a specific pragma definition says otherwise;
- a pragma must not become an implicit arbitrary macro escape hatch;
- backend selection remains governed by STAR-LANG-RESEARCH-026;
- pragma expansion and macro expansion must have explicit ordering if they interact.

This interaction needs a later focused design before implementation.

* Rejected Designs

** DENIED: expose Common Lisp =DEFMACRO= directly in =.star=

Reason: the source contract would become host-language execution and package semantics rather than StarLang syntax transformation.

** DENIED: textual substitution as the binding model

Reason: it cannot preserve lexical identity, source provenance, or compositional hygiene.

** DENIED: raw list rewriting without syntax objects

Reason: equal spellings cannot reliably represent distinct scopes, bindings, or source occurrences.

** DENIED: declarative-only macros as the complete StarLang macro model

Reason: the original 020 underfit the desired language. StarLang should retain simple templates but also support programmable compile-time AST transformation analogous to Nim macros.

** DENIED: generated-name conventions as hygiene

Reason: textual uniqueness is not a binding model. Fresh bindings must be represented structurally.

** DENIED: trusting typed-macro output without revalidation

Reason: typed input gives the transformer checked information; it does not make newly generated output automatically valid.

** DENIED: unresolved ordinary macro invocations in runtime IR

Reason: ordinary macro semantics are compile-time source transformation. Runtime dynamic compilation/evaluation is a separate feature if later desired.

** DENIED: macro-generated runtime behavior

This is *not denied*. Macro-generated code may execute normally at runtime. The old ambiguous wording is superseded.

* Implementation Order

1. Replace plain parsed atoms/lists with per-occurrence syntax objects while retaining the closed reader.
2. Record full spans and origin metadata for every syntax occurrence.
3. Introduce structural scope sets and binding identities.
4. Add deterministic syntax-object serialization/debug rendering.
5. Split compiler stages into read, expand, semantic-check, normalize, and compile/materialize boundaries.
6. Implement hygienic =template= first as a thin user-facing layer over the syntax-object expander.
7. Define the bounded StarLang compile-time macro execution language/API.
8. Implement untyped macro parameters and result revalidation.
9. Define the semantic frontier and immutable metadata contract for typed macro parameters.
10. Implement typed macro invocation and result revalidation.
11. Add syntax quotation/unquotation and low-level construction APIs.
12. Add fresh-binding and explicit-binding operations over structural scopes.
13. Lock transformer libraries by identity/version/digest.
14. Add expansion budgets, recursion/cycle detection, and deterministic ordering.
15. Add structured expansion provenance and diagnostic traces.
16. Add conformance fixtures covering templates, typed macros, untyped macros, hygiene, and runtime-generated behavior.
17. Design pragma/macro ordering separately before enabling annotation-style transformation hooks.
18. Consider controlled external compile-time capabilities only after deterministic core macro execution is stable.

This is a current-generation Common Lisp implementation order for the approved language semantics if/when this node is approved. It does not authorize a self-hosting migration.

* Acceptance Tests

The macro system is not complete until automated tests prove at least:

1. use-site syntax is not accidentally captured by a generated binder;
2. generated bindings do not capture equal-spelled use-site identifiers;
3. two macro invocations receive distinct fresh introduction scopes;
4. definition-site binding references remain stable when intentionally preserved;
5. textual identifier equality is insufficient to establish binding equality;
6. templates expand hygienically;
7. untyped macros can receive syntax that becomes valid only after expansion;
8. typed macros receive resolved immutable semantic/type information;
9. newly generated output from typed macros is validated before normalization;
10. quotation and low-level construction produce equivalent checked syntax where expected;
11. macro-generated runtime operations execute normally after expansion;
12. no ordinary macro invocation remains as runtime macro dispatch in normalized IR;
13. recursive macro cycles fail with bounded expansion traces;
14. expansion budgets fail deterministically;
15. source diagnostics preserve invocation and definition origins;
16. transformer-library digest changes alter manifest/cache identity;
17. macro expansion cannot silently observe ambient clock, random, network, environment, or actor state;
18. explicit future compile-time inputs, if added, appear in compilation evidence;
19. handwritten and macro-generated alpha-equivalent core programs normalize equivalently;
20. =.star= source never requires Common Lisp =READ= or unrestricted =EVAL=;
21. direct runtime and optional CL-GServer binding remain semantically equivalent after expansion;
22. existing non-macro fixtures continue to compile.

* Review Decisions Required

The rewritten research still requires explicit review on these details:

1. approve the overall *Nim-style macro semantics + Racket-style syntax-object/hygiene* architecture;
2. approve =template= and =macro= as distinct source concepts;
3. approve the typed/untyped macro-input distinction;
4. choose the exact StarLang quotation/unquotation surface syntax;
5. define the first public syntax-construction API and which operations remain compiler-internal;
6. choose whether explicit intentional capture/binding manipulation ships in the first macro release or follows later;
7. define the exact semantic frontier exposed to typed macros;
8. choose initial expansion/work budgets;
9. choose whether expansion traces are embedded in manifests or stored as separately addressed artifacts;
10. define pragma/macro ordering before annotation-style transformation hooks are enabled.

The current-generation Common Lisp host decision and future self-hosting authorization rule are already governed elsewhere and are not reopened by approving this macro architecture.

* Relationship to Future Self-Hosting

Nothing in this macro model permanently requires Common Lisp semantics.

A future explicitly authorized self-hosted StarLang compiler could reimplement:

- syntax objects;
- scope-set hygiene;
- template expansion;
- typed/untyped macro invocation;
- quotation and syntax construction;
- provenance;
- deterministic transformer execution;
- semantic revalidation.

That compatibility is a design property only. No self-hosting research, roadmap, prototype, migration, or implementation work may begin without explicit nsaspy authorization under STAR-LANG-RESEARCH-018 and STAR-LANG-001.

* Conclusion

The original 020 was too conservative for the intended StarLang macro system. Treating declarative pattern rewriting as the main macro model would leave StarLang with useful templates but not the programmable compile-time AST machinery expected from a serious Lisp-family language.

The revised direction is:

#+begin_src text
Racket-quality syntax identity + hygiene + provenance
                        plus
Nim-style programmable compile-time AST macros
                        plus
simple hygienic templates for the common case
                        plus
StarLang-specific deterministic/capability boundaries
#+end_src

Macro expansion itself is compile-time. Macro-generated StarLang may perform normal runtime behavior. Runtime dynamic compilation or AST evaluation, if ever desired, is a separate feature rather than something this node bans by accident.

* Footnotes and Glossary

[fn:starlang] *StarLang* — the current-generation Common Lisp-implemented declarative language and runtime used to define StarIntel documents, actors, domain servers, capabilities, adapters, dataflows, and reasoning operations.

[fn:cl] *Common Lisp (CL)* — the implementation language of the current-generation StarLang compiler/runtime. It is not the source-language macro API.

[fn:self-hosting] *Self-hosting* — a possible future architecture in which some or all of the StarLang compiler is implemented in StarLang. Planning requires explicit nsaspy authorization.

[fn:macro] *Macro* — a compile-time StarLang transformer that receives syntax objects, may inspect or construct syntax, and returns syntax that re-enters compiler checking.

[fn:template] *Template* — the simpler hygienic source-expansion facility intended for concise substitution/code-generation patterns without general tree-programming ceremony.

[fn:syntax-object] *Syntax object* — compiler data combining source datum/tree structure with exact source span, lexical scopes, binding identity, provenance, and optional immutable checked semantic metadata.

[fn:scope-set] *Scope set* — the structural lexical-context metadata used to determine binding identity and prevent accidental macro capture.

[fn:typed-syntax] *Typed syntax* — syntax passed to a macro after an explicitly defined semantic-checking frontier has attached resolved immutable metadata.

[fn:untyped-syntax] *Untyped syntax* — parsed syntax passed to a macro before ordinary semantic validation of that argument, allowing the macro to transform syntax that is not independently valid yet.

[fn:origin-chain] *Origin chain* — the ordered record of expansion steps connecting generated syntax to transformer definitions and source invocations.

[fn:source-span] *Source span* — exact source extent of one syntax occurrence, including pathname and start/end position information.

[fn:ir] *Intermediate representation (IR)* — normalized compiler data after expansion and semantic validation; ordinary macro transformer execution is not retained as runtime dispatch.

[fn:capability] *Compile-time capability* — an explicit authority/input contract allowing a transformer to access a bounded external compiler resource while preserving provenance and reproducibility requirements.

[fn:alpha-equivalence] *Alpha-equivalence* — structural program equivalence modulo consistent renaming of bound identifiers.

[fn:cl-gserver] *CL-GServer (Sento)* — optional Common Lisp actor runtime integration used after compilation; it does not define StarLang macro semantics.
