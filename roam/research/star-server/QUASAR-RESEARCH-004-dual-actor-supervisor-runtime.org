* Research Question

What actor-supervisor system should Quasar require when it must support both:

1. an installable browser-first Quasar application with limited local actors; and
2. a true local actor system implemented in Common Lisp, controlled through the same Quasar UI, with persistent supervision and plugin support?

The design must preserve Quasar's canonical graph-operation boundary. Neither browser actors, native actors, plugins, nor integrations may directly mutate the graph renderer or canonical workspace store.

* Decision Summary

Quasar must expose one versioned =ActorRuntime= contract with two implementations:

- =BrowserActorRuntime=: a limited, browser-contained runtime using Web Workers for bounded actions and short-lived actor runs;
- =LocalLispActorRuntime=: a full Common Lisp runtime using the extended Sento managed-component system for persistent actor trees, restart policies, plugins, integrations, background operation, and durable run state.

The browser application remains independently usable as a static offline-first PWA. Installing or connecting the Common Lisp runtime unlocks the full actor system. The UI must state the active runtime and capability limits explicitly; it must never present browser workers as equivalent to the native actor system.

The current browser class named =AgentSupervisor= should be renamed =AgentRunSupervisor=. It supervises persisted LLM run iterations, budgets, retries, checkpoints, and cancellation, but it is not the root actor supervisor described by this research.

* Required Product Statement

Quasar documentation and UI must state:

#+begin_quote
Quasar includes two actor runtimes. Browser actors run locally inside the PWA with strict capability and lifetime limits. The full local actor runtime runs as a Common Lisp service and provides persistent supervision trees, durable runs, native integrations, and plugin support through the same Quasar UI.
#+end_quote

* Architecture Conflict and Resolution

The current =quasar-ui= deployment roadmap describes a JavaScript-only static PWA and explicitly rejects a Common Lisp backend requirement. That rule should be narrowed rather than simply deleted:

- the browser build must still require no server to open, edit, import, export, inspect, and run limited actions;
- the Quasar core graph model must not depend on Common Lisp;
- the Common Lisp runtime is an optional local execution runtime, not a mandatory rendering or storage backend for the browser edition;
- the UI may connect to the runtime through a typed adapter;
- native runtime features must fail closed and disappear cleanly when disconnected;
- local graph editing must continue when the native runtime is absent or offline.

A new architecture decision should supersede only the single-runtime prohibition while preserving the browser-first and canonical-mutation boundaries.

* Browser Runtime

** Purpose

The browser runtime provides useful local automation without requiring SBCL or another local service. It is appropriate for:

- deterministic document transforms;
- bounded parsing and normalization;
- username candidate generation;
- local graph queries;
- small enrichment steps whose network policy allows browser execution;
- actor validation against fixtures;
- previews of graph-operation plans;
- short agent runs while the Quasar application remains open.

It is not the full StarIntel actor runtime.

** Execution model

Use:

- dedicated Web Workers for user-provided or failure-prone actors;
- a small worker pool for trusted built-in actors;
- an explicit lifecycle state machine for spawn, run, pause, cancel, failure, restart, and completion;
- IndexedDB for manifests, checkpoints, traces, and paused-run records;
- =BroadcastChannel= for same-origin tab and worker event propagation;
- =Web Locks= for one active browser supervisor leader per workspace;
- a =SharedWorker= only as an optional optimization, never as the baseline requirement;
- the service worker only for application caching and bounded background browser events, never as the persistent actor root.

Closing every Quasar execution context terminates browser actors. Persisted records permit later resume or restart, but they do not mean the actor process survived.

** Browser actor limits

Recommended defaults:

| Limit                              | Default         |
|------------------------------------+-----------------|
| Concurrent dedicated actors        | 4               |
| Trusted pooled actor jobs           | 8               |
| Runtime per invocation              | 30 seconds      |
| Output payload                      | 5 MiB           |
| Graph mutations per batch           | 1,000           |
| Automatic restarts                  | 2 per 30 sec    |
| Child actors per browser actor       | 16              |
| Queued messages per actor            | 100             |
| Continue after all UI contexts close | Unsupported     |

These are resource policies, not hard browser security guarantees.

** Security boundary

A Web Worker removes DOM access but does not create a secure same-origin sandbox. Worker code may still reach browser-global capabilities such as =fetch= and IndexedDB. Therefore Quasar must define two browser plugin tiers:

*** Trusted JavaScript actors

- bundled with Quasar or explicitly trusted by the operator;
- executed as module workers;
- restricted by CSP where possible;
- terminated on timeout or cancellation;
- clearly marked as having browser-origin privileges;
- never given direct references to the graph renderer or command repository.

*** Restricted actors

Restricted actors use Star-Lang or another data-only declarative actor format interpreted by Quasar. They may perform only granted operations exposed by the host:

- read a bounded selection snapshot;
- query bounded document projections;
- call named capabilities;
- execute bounded loops;
- return a declarative graph-operation plan.

Restricted actors do not execute arbitrary JavaScript. This is the required tier for plugins that claim they cannot directly access browser storage or arbitrary network targets.

* Common Lisp Native Runtime

** Purpose

The native runtime is the true Quasar actor system. It runs locally as a persistent Common Lisp service and remains active independently of browser windows.

It provides:

- persistent actor trees;
- background runs;
- hierarchical supervision;
- bounded mailboxes;
- restart intensity and escalation;
- durable journals and checkpoints;
- local filesystem and subprocess actors;
- RabbitMQ, CouchDB, MCP, web retrieval, Prolog, and local-model integrations;
- plugin loading and lifecycle;
- operation outbox delivery while the UI is disconnected;
- headless operation;
- multiple Quasar clients connected to one runtime.

** Runtime foundation

Use the extended Sento managed-component runtime defined by =SENTO-000=. Quasar should not recreate supervision, dispatchers, routers, registry, transport lifecycle, mailbox overload policy, and telemetry as private Quasar-only glue.

The native runtime should depend on:

- one Sento actor system per local runtime process by default;
- supervisor actors and child specifications;
- =one-for-one=, =one-for-all=, and =rest-for-one= restart strategies;
- permanent, transient, and temporary restart classes;
- structured termination reasons;
- bounded mailboxes with overload policy;
- component handles and registry;
- scoped event streams;
- durable run and event journals;
- HTTP control and WebSocket event adapters;
- optional ZeroMQ or RabbitMQ adapters only behind explicit integration actors.

** Restart strategies

| Strategy       | Quasar use                                                            |
|----------------+-----------------------------------------------------------------------|
| one-for-one    | Independent integrations, plugins, and tool actors                    |
| one-for-all    | Transport components sharing one session and protocol state           |
| rest-for-one   | Ordered run pipelines whose downstream actors depend on earlier state |
| permanent      | Registry, journal, protocol router, and core event services            |
| transient      | Integration and run workers restarted only after abnormal failure      |
| temporary      | One-shot transforms and isolated plugin jobs                           |

Restart intensity must be bounded per supervisor. Exceeding the bound escalates the failure to the parent supervisor. Plugin restart storms quarantine that plugin rather than repeatedly crashing the entire runtime.

* Graph Mutation Boundary

Both runtimes return the same immutable =GraphOperationBatch= format. No actor receives direct mutation access to Cytoscape, React state, IndexedDB internals, or the Common Lisp graph repository.

The Quasar command engine remains the commit authority:

1. receive a proposed operation batch;
2. verify protocol and schema versions;
3. resolve actor, run, plugin, and causation metadata;
4. validate every document and relation;
5. evaluate create, update, remove, and revision preconditions against a projected workspace;
6. mark destructive changes;
7. produce an exact preview;
8. require approval when policy demands it;
9. commit the batch atomically through the normal history path;
10. record the batch identifier as committed.

The native runtime stores completed batches in an outbox when no UI command authority is connected. The outbox is not a second canonical graph store.

* Message and Delivery Semantics

Quasar must not claim exactly-once execution for arbitrary external side effects.

| Boundary                         | Required semantics                                  |
|----------------------------------+-----------------------------------------------------|
| In-memory actor message          | At-most-once by default                             |
| Durable local command            | At-least-once with immutable message ID             |
| External tool side effect        | Explicit idempotency key where supported            |
| Graph operation batch            | Deduplicated by immutable batch ID                  |
| Runtime event stream             | Replayable cursor                                   |
| UI commit acknowledgment         | Persisted receipt                                   |

Every externally visible envelope should include:

- =message_id=
- =correlation_id=
- =causation_id=
- =actor_id=
- =run_id=
- =plugin_id=
- =batch_id= when applicable
- =idempotency_key= when applicable
- =protocol_version=
- =created_at=

* Plugin System

** Plugin classes

| Plugin class         | Runtime        | Purpose                                      |
|----------------------+----------------+----------------------------------------------|
| Browser actor plugin | Browser        | Limited transforms and bounded local actions |
| Native actor plugin  | Common Lisp    | Full actor capabilities and background work  |
| Integration plugin   | Common Lisp    | APIs, queues, databases, tools, models       |
| UI contribution      | Browser UI     | Commands, panels, inspectors, settings       |
| Hybrid plugin        | Both           | UI contribution paired with native actors    |

** Native plugin loading

Each trusted native plugin is an ASDF system with a data manifest and a defined factory entry point. Loading an ASDF system into the runtime process grants it the privileges of that process; ASDF is a build and loading mechanism, not a security sandbox.

Trust policy:

- bundled and explicitly trusted plugins may run in-process;
- unknown or third-party plugins should run in a separate SBCL process;
- isolated plugin processes communicate through the same versioned actor protocol;
- plugin capabilities are declared before activation;
- plugins may be disabled, restarted, inspected, and quarantined;
- restart storms quarantine the plugin;
- disabling a plugin prevents new actor spawns and drains or terminates existing children according to policy.

** UI contribution boundary

Initial UI plugins should be declarative. They may register:

- commands;
- context-menu actions;
- inspector panels;
- settings schemas;
- actor status views;
- routes;
- icons;
- documentation links.

UI plugins must not receive direct Cytoscape, React root, IndexedDB, or command-repository references. They invoke stable UI and runtime adapters.

* Local Runtime Transport and Pairing

Use native HTTP for bounded commands and queries and WebSocket for event, trace, mailbox, supervisor, and run updates.

Default security policy:

- bind to loopback only;
- require explicit remote-listen configuration;
- create a one-time pairing token on first connection;
- exchange the pairing token for a revocable local session credential;
- enforce an origin allowlist;
- negotiate protocol versions before actor operations;
- attach runtime and session identifiers to every event stream;
- reject unsupported protocol versions;
- redact secrets from logs and exported actor records;
- keep provider and integration credentials in the native credential store, not browser persistence.

CLOG may serve the compiled Quasar application and an optional Common Lisp runtime debugger. React remains the primary workbench UI. CLOG and React must not simultaneously own the same DOM subtree.

* Implementation Order

1. Supersede the JavaScript-only runtime decision with a dual-runtime ADR.
2. Freeze =ActorRuntime v1= and capability discovery.
3. Rename the current browser =AgentSupervisor= to =AgentRunSupervisor=.
4. Implement browser actor lifecycle, restart intensity, leader election, and trace records.
5. Split browser plugins into trusted JavaScript and restricted declarative tiers.
6. Define the Common Lisp protocol types from the same canonical schema.
7. Implement the native root supervisor on extended Sento.
8. Add durable run journal, replayable events, and the operation outbox.
9. Add HTTP control, WebSocket events, loopback pairing, and reconnect cursors.
10. Add ASDF plugin discovery, capability declarations, and lifecycle.
11. Add out-of-process SBCL plugin hosting for untrusted native plugins.
12. Build actor tree, supervisor, runtime status, plugin manager, and operation inbox UI.

14. Package the local runtime as a Nix service and standalone executable.

* Acceptance Criteria

- Quasar opens, edits, imports, exports, and runs limited actors without Common Lisp installed.
- The UI labels browser actors as =Browser -- Limited=.
- Browser actor shutdown and resume behavior is deterministic and documented.
- Closing all browser contexts does not falsely report browser actors as still running.
- The Common Lisp runtime continues native actor runs after every Quasar window closes.
- Reopening Quasar reconnects to the existing native runtime and replays events from a cursor.
- Native actor crashes invoke declared restart strategies.
- Restart storms escalate and quarantine the failing child or plugin.
- Browser and native actors return the same versioned graph-operation batch format.
- Neither runtime bypasses the canonical graph command and undo path.
- Native operation batches produced while disconnected appear in the operation inbox.
- Plugins declare capabilities before activation.
- Trusted native plugins can run in-process.
- Untrusted native plugins can run in a separate SBCL process.
- Plugins can be enabled, disabled, inspected, restarted, and quarantined.
- Protocol-version mismatch fails closed.
- Disconnecting the native runtime falls back to browser mode without disabling graph editing.
- Actor events, messages, restarts, tools, and graph batches remain traceable through actor, run, correlation, and causation identifiers.

* Risks and Rejected Alternatives

** One browser-only runtime

Rejected. It cannot provide reliable background operation after browser shutdown, native filesystem and subprocess actors, durable supervision, or a true local plugin runtime.

** One mandatory Common Lisp backend

Rejected. It would break the independently deployable static PWA and make basic graph editing depend on local service installation and health.

** Treat Web Workers as a secure plugin sandbox

Rejected. Same-origin worker code retains browser-global capabilities. Restricted plugins require a data-only interpreted format or a stronger process/origin boundary.

** Let native actors mutate the graph store directly

Rejected. It creates a second mutation authority, weakens undo and revision guarantees, and makes disconnected conflict handling unsafe.

** Load every native plugin into the main Lisp image

Rejected. Unknown plugin code would share the full runtime privilege and failure domain.

** Use a service worker as the actor root

Rejected. Browser service workers are event-driven and may be terminated when idle; they are not durable application actor supervisors.

* Conclusion

Quasar should remain a browser-first investigation workspace, but its complete actor architecture must be dual-runtime. The browser runtime provides bounded, explicit, limited actors. The Common Lisp runtime provides the actual persistent supervisor tree, durable execution, integrations, and plugins.

The two implementations meet at one versioned =ActorRuntime= protocol and one validated =GraphOperationBatch= boundary. This keeps the UI unified without reducing the native actor platform to browser-shaped concurrency or turning Common Lisp into a mandatory rendering backend.
