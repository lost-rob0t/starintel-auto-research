* Research Question

How should StarIntel align four active repositories without duplicating graph authority, actor authority, renderer responsibilities, or Auto-Dig integration work?

The repository roles used by this review are:

1. =lost-rob0t/quasar= is the canonical Quasar[fn:quasar] runtime and repository.
2. =lost-rob0t/quasar-ui= is the web-based Quasar implementation and web edition.
3. =lost-rob0t/auto-dig-quasar= is the Auto-Dig[fn:auto-dig] variant and fork[fn:fork] of =quasar-ui=.
4. =lost-rob0t/starintel-auto-research= is the durable research and design graph.

This corrects earlier wording that treated =quasar= as merely a JavaScript repository or sibling implementation. The canonical repository is the Common Lisp[fn:common-lisp] and CLOG[fn:clog] control plane around the preserved browser workspace.

* Executive Findings

** Finding 1: product intent is aligned, authority wording is not.

The four repositories agree on the product shape: typed investigation graph, renderer isolation, validated mutations, actor-driven transforms, local-first operation, and optional integrations. The drift is around who owns canonical[fn:canonical] state after =quasar= became the canonical repository.

The previous design corpus still contains text that can be read as Common Lisp prototype authority, browser-only authority, or two-tier shared authority. That was acceptable during discovery. It is now a P0 decision because the canonical repository exists and downstream work needs one source of truth.

** Finding 2: =quasar= should be documented as canonical without deleting the web edition.

The right reconciliation is not to throw away =quasar-ui=. The web application remains the editable browser workspace, mobile shell, renderer host, local offline mode, and projection surface. The canonical =quasar= repository owns the command channel, durable migrated operations, privileged execution, persistent actor supervision, and long-running runtime authority.

The browser edition can still open and edit locally when the Common Lisp runtime is absent. Once a subject is migrated behind canonical =quasar= commands, the browser must treat local stores as caches or standalone-mode stores rather than the higher authority for connected operation.

** Finding 3: Auto-Dig should remain a fork until a narrow adapter migration is approved.

=auto-dig-quasar= is currently a complete fork of =quasar-ui=. That is acceptable because Auto-Dig-specific code is isolated under =src/auto-dig/=, the host pins an exact fork commit, and upstream synchronization is scripted.

The risk is not the fork itself. The risk is letting bridge payloads, graph semantics, or actor results drift into a second protocol. The current bridge protocol is versioned but still uses =unknown= for params, results, and event payloads. That must become schema-checked before it becomes a long-term integration boundary.

** Finding 4: QUASAR-003 should be unblocked by observed implementation evidence, not blocked on the old prototype path.

=QUASAR-003= is blocked until manual graph edits, committed movement, inspector edits, graph batches, undo and redo, save/reopen, session reconstruction, and one action are exercised. Some of that evidence now exists in browser and canonical runtime work, not only in the original CLOG prototype path. The next step is to audit observed behavior against the evidence checklist and promote or supersede the blocked condition.

** Finding 5: renderer scale needs a tiered adapter strategy, not a naming-based framework swap.

Cytoscape[fn:cytoscape] remains appropriate for the editable graph workbench. It should not be forced to carry every large-corpus overview. Large graph scale should use a =GraphViewAdapter=[fn:graph-view-adapter] boundary with tiers:

| Tier | Role | Candidate implementation | Mutation authority |
|------+------|--------------------------|--------------------|
| 0 | Normal editable graph | Cytoscape canvas renderer | Canonical Quasar commands |
| 1 | Experimental accelerated Cytoscape | Cytoscape WebGL preview only after benchmark gate | Canonical Quasar commands |
| 2 | Large mostly-read overview | Sigma.js, cosmos.gl, or Cosmograph | Read-only projection plus selected command commits |
| 3 | Massive overview / tiled graph | WebGPU/WASM[fn:wasm] adapter such as Helios-style architecture or custom tile pipeline | Projection only; edits round-trip through canonical commands |

Every tier remains a projection[fn:projection]. No renderer becomes the database.

** Finding 6: storage atomicity wording must be tightened.

Command batches can be logically atomic inside a command engine. PouchDB[fn:pouchdb] and CouchDB-style bulk writes are not cross-document physical transactions. Documentation and tests must distinguish logical command atomicity from backend persistence atomicity. If a batch spans multiple documents, Quasar needs a journal, commit marker, or single-document transaction envelope before claiming crash-safe atomic persistence.

* Recursive Research Queue

The next research loop should ask these questions in order. Each answer must attach evidence and stop when the acceptance evidence is enough for an implementation design.

1. Which =quasar= topology is current: submodule, imported frontend, monorepo, or hybrid?
2. Which graph command shapes are already implemented in =quasar= and =quasar-ui=, and where do they differ?
3. Which QUASAR-003 evidence checklist items are already satisfied by code?
4. What is the measured graph size cutoff for editable Cytoscape on target hardware and mobile browsers?
5. Which renderer adapter handles 100k, 1M, and tiled overview cases with the least custom code?
6. What schema should replace =auto-dig-quasar.v1= =unknown= params/results?
7. What transaction journal shape gives crash-safe multi-document commits without making the renderer the store?

* Footnotes and Glossary

[fn:quasar] Quasar: The StarIntel investigation graph workspace. In this packet, =lost-rob0t/quasar= is the canonical repository and runtime for migrated Quasar operations.

[fn:auto-dig] Auto-Dig: The StarIntel-generated research site and workflow that consumes a specialized Quasar fork for dataset review, corrections, actor output, and tip workflows.

[fn:fork] Fork: A repository copied from another repository so it can carry local changes while periodically pulling upstream fixes.

[fn:common-lisp] Common Lisp: A programmable Lisp language used here for the canonical Quasar runtime, actors, command handling, and privileged local integrations.

[fn:clog] CLOG: A Common Lisp browser application library that serves browser sessions and communicates with them over WebSockets.

[fn:canonical] Canonical: The authoritative version that other views, caches, forks, or projections must treat as the source of truth.

[fn:webgl] WebGL: A browser graphics API that uses the graphics processing unit for accelerated rendering.

[fn:webgpu] WebGPU: A newer browser graphics and compute API intended to expose modern GPU capabilities more directly than WebGL.

[fn:wolfram] Wolfram: A computational knowledge and symbolic analysis system. It was considered but not needed for this architecture packet.

[fn:couchdb] CouchDB: A document database with replication and map-reduce views. Its bulk document API is not a cross-document transaction system.

[fn:cytoscape] Cytoscape: The graph visualization library currently used by Quasar for browser graph editing and interaction.

[fn:graph-view-adapter] GraphViewAdapter: A proposed interface that lets Quasar choose different graph renderers while keeping the canonical command and storage path unchanged.

[fn:wasm] WASM: WebAssembly, a browser-supported low-level execution format useful for portable high-performance code.

[fn:projection] Projection: A derived view of canonical data, such as a graph drawing, dashboard, table, map, or timeline. A projection can be rebuilt from canonical state.

[fn:pouchdb] PouchDB: A browser-side database compatible with CouchDB replication. It is useful for offline storage but does not make arbitrary multi-document writes crash-atomic.

[fn:adard] ADARD: Adaptive Research DAG, the StarIntel automatic-research control plane for bounded candidates, evidence, validation, review, and promotion.
