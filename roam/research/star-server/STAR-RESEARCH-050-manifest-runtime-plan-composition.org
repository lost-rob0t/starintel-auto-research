* Corrected Ownership Invariant

The architecture separates actor discovery from actor/domain routing.

**StarIntel Server owns the actor/service registry and discovery plane.** It consumes actor-emitted manifests, tracks the actors/services available to the deployment, joins static manifest data with deployment/runtime availability, and exposes safe discovery to callers.

**StarLang owns actor/domain-server semantics and routing/dispatch semantics.** Actor declarations freeze typed contracts and routing metadata. Domain-server declarations define keyed logical addresses, accepted commands, routing behavior, lifecycle, indexes, capabilities, and the semantics for dispatching typed commands to the correct domain authority. The runtime resolves those logical destinations to a current local or remote incarnation through the appropriate runtime boundary.

**StarRouter owns cross-authority route resolution and transport-profile selection.** It does not replace StarLang domain routing semantics and it does not become the StarIntel actor registry.

**Pro Actors, BBPD, and similar actor packages define actors and emit their manifests.** They do not own the global registry, routing control plane, or transport architecture merely because an actor happens to run in a particular process/runtime.

* Canonical Research Basis

- =STAR-LANG-RESEARCH-006 Specification Libraries and Domain Servers= establishes that actor declarations freeze contract, capabilities, **routing metadata**, and observable result type; domain servers have stable keyed logical addresses; mutations requiring domain invariants route through the keyed server; normalized IR includes =actor-command=, =domain-address=, and =domain-command=.
- =STAR-LANG-RESEARCH-014 BBP Tool Domain Remoting= provides historical concrete evidence for StarLang command routing through a domain gateway/dispatcher. Its transport/registration mechanics are not automatically current, but its domain-routing responsibility belongs to StarLang.
- =STAR-LANG-004 STAR Service URI Discovery and Dispatch= keeps deterministic actor/service dispatch and local runtime-directory resolution in StarLang while delegating cross-process authority routing to StarRouter.
- =STAR-RESEARCH-041 Unified STAR URI Authority Routing and FediWatch RabbitMQ= establishes RFC3986 =star://= identity, authority-first StarRouter resolution for cross-authority traffic, and RabbitMQ for FediWatch durable target/finding dataflow.
- =STAR-RESEARCH-013 Actor Capability Advertisement= provides the StarIntel registry/discovery precedent: actors emit machine-readable capability descriptions and the StarIntel discovery plane registers/searches those actor services.

* StarLang Actor and Domain-Server Authority

StarLang is authoritative for the semantics compiled from actor/domain-server definitions, including where applicable:

- actor/domain-server semantic identity;
- typed accepted and produced messages/documents;
- capabilities/tools;
- routing metadata;
- keyed domain address semantics;
- domain ownership and indexes;
- domain-command dispatch behavior;
- mailbox/backpressure constraints;
- lifecycle/restart semantics;
- manifest generation;
- canonical STAR resource references used by the language/runtime;
- runtime-neutral dispatch semantics.

A domain server is a keyed supervised authority over bounded domain state. Its logical address is stable even when the current activation/process changes. StarLang decides what typed command is being routed and which logical domain address it targets.

This does not mean StarLang owns the global StarIntel actor registry.

* StarIntel Actor/Service Registry

StarIntel Server owns the deployment-facing actor/service registry.

Registry entries are built from actor-emitted manifests plus server-owned deployment/runtime observations. The registry answers questions such as:

- what actors/services are available to this StarIntel deployment;
- which canonical resource identity and semantic manifest describes each actor;
- what capabilities and accepted/produced contracts are advertised;
- what deployment binding is configured;
- whether a registered actor/service is currently available/ready;
- which registered destination may be selected by application policy.

The registry must not rewrite StarLang semantic contracts. It records/validates them and combines them with deployment facts.

Manifest registration/discovery is not authorization. An actor appearing in the registry does not grant a caller permission to invoke it.

* Actor Packages

Actor repositories such as Pro Actors and BBPD have a deliberately narrow architectural responsibility:

1. define actors;
2. emit the manifests describing those actors.

Their package contract is not to implement the StarIntel registry, define a competing routing grammar, or own the system-wide transport/control plane.

Concrete runtime libraries used internally by an actor implementation do not change this architectural ownership.

* RuntimePlan Composition

StarIntel Server compiles deployment and dataset configuration against registered actor/service manifests into a pure deterministic =RuntimePlan= before long-lived side effects.

The plan may contain deployment/application routing indexes, but those are not a replacement for StarLang domain routing semantics. They answer deployment questions: which registered actor/domain endpoint is selected, which adapter/runtime binding is available, and what server policy applies.

Conceptual form:

#+begin_example
RuntimePlan
  planVersion
  registryEntries[]

No actor, thread, listener, broker/database connection, timer, or arbitrary plugin is started during plan compilation.

* Routing Layers

The word "routing" must not collapse distinct layers.

** StarLang logical/domain routing

#+begin_example
typed command
   -> actor/domain contract validation
   -> actor or keyed domain logical destination
   -> domain routing / dispatch semantics
   -> runtime-neutral dispatch operation
#+end_example

This is part of StarLang.

** StarIntel application routing

#+begin_example
validated target/document/application operation
   -> auth / tenant / dataset / target policy
   -> StarIntel actor-registry lookup / capability selection
   -> select registered actor/service destination
   -> invoke the StarLang-defined actor/domain operation
#+end_example

This is StarIntel Server application policy and registry composition.

** Cross-authority routing

#+begin_example
canonical star:// destination outside local authority
   -> StarRouter authority registration / resolution
   -> eligible authority instance
   -> compatible transport profile
   -> forward canonical operation
#+end_example

This is StarRouter.

** Durable distributed dataflow

For workloads such as FediWatch targets/findings, RabbitMQ may carry durable work/results. Queue/routing-key mechanics are transport/dataflow details, not actor identity and not actor-package ownership.

* FediWatch Consequence

A Lisp FediWatch port in Pro Actors should be modeled as actors that emit manifests. Its actor/domain control flow should use StarLang actor/domain-server semantics, including routing when a domain server is declared. StarIntel Server registers/discovers the emitted actors and selects them through application policy. Durable target/finding delivery may use the approved RabbitMQ boundary without making Pro Actors the transport owner.

* Validation Rules

At minimum reject:

1. duplicate actor/service registry identity in the StarIntel registry without an explicit version/instance rule;
2. a registered manifest whose semantic digest/contract conflicts with the actor-emitted manifest;
3. deployment/application routing that sends a message/document type not accepted by the actor/domain contract;
4. server configuration that attempts to redefine StarLang domain routing semantics;
5. actor packages that attempt to become the global registry or define a competing canonical URI grammar;
6. caller-controlled transport routes used as logical actor identity;
7. capability discovery treated as authorization;
8. unbounded or invalid runtime demand before realization.

* Implementation Boundary

The implementation order should preserve these authorities:

1. finish the required StarLang actor/domain-server and shared STAR identity/runtime semantics;
2. have actor packages emit conforming manifests;
3. build/consume those manifests in the StarIntel Server actor registry;
4. compile StarIntel deployment/dataset/application policy against that registry;
5. dispatch typed actor/domain operations through StarLang semantics;
6. use StarRouter only for cross-authority resolution and the selected transport/dataflow adapter for delivery guarantees.

* Acceptance

- StarIntel Server is the canonical actor/service registry/discovery owner;
- Pro Actors / BBPD define actors and emit manifests only;
- StarLang owns actor/domain-server semantics and logical routing/dispatch semantics;
- domain-server keyed routing is not reimplemented in StarIntel Server;
- StarRouter owns cross-authority route resolution/transport-profile selection rather than StarLang application semantics;
- RabbitMQ durable FediWatch dataflow remains transport/dataflow infrastructure rather than actor-package ownership;
- manifests advertise semantic contracts but do not grant authorization;
- server application routing selects only registered compatible actors/services;
- no second actor registry, second domain-routing language, or competing STAR URI grammar is introduced.
