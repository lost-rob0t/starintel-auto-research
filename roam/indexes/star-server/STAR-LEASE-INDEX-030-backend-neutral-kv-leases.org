* Issue 31 — Initial Valkey Adapter

Issue 31 is the authoritative backend decision: Valkey[fn:valkey] is the first deployable adapter.

The issue-30 research and design therefore specify:

- one atomic same-slot script for acquire;
- atomic compare renew, release, and revoke scripts;
- persistent non-expiring fence keys;
- atomic request result receipts;
- server-authoritative time and TTL;
- cluster hash tags;
- TLS, authentication, pooling, deadlines, retries, and health;
- optional =WAIT= and =WAITAOF= durability acknowledgements;
- explicit asynchronous failover limitations;
- recovery fencing floors that prevent token reuse.

A later etcd or Consul adapter may provide stronger consistency through the same issue-30 protocol. Target and HTTP code do not change.

* Issue 33 — Recovery and Race Proofs

** Design

- [[id:d0391f98-dc3f-4805-94df-dd23e9b6d945][STAR-SERVER-045 Target-Lease Recovery and Race Proof Harness]]

** Research

- [[id:7f4928c1-3c52-4a87-bf82-2dc889635a33][STAR-RESEARCH-033 Target-Lease Recovery and Race Matrix]]

Issue 33 owns proof that the implemented lease primitives and issue-32 execution boundary remain correct under:

- simultaneous acquisition;
- renew/expiry and release/reacquire races;
- response loss after backend commit and idempotent resolution;
- process and actor crash recovery;
- backend connection loss and restart;
- client clock skew;
- privileged revocation during live work;
- delayed stale generation effects after a successor fence exists;
- recovery where a safe fencing floor can or cannot be proven.

The recovery layer does not grant authority. It classifies persisted attempts against current typed lease state. A fresh acquisition remains the only operation that creates a new lease/fencing generation.

The strongest issue-33 acceptance proof is cross-layer: worker A with fence N stalls, worker B reacquires N+1 and commits through a production fenced side-effect seam, then A resumes and its delayed effect is rejected with no authoritative state/publication change.

* Critical Correctness Rules

1. A lease is temporary authority; it is not enough to stop a stale worker.
2. Every acquisition receives a strictly increasing fencing token.
3. Every authoritative side effect rejects stale/lost authority.
4. Release, revoke, and expiry never reset the fence counter.
5. Mutation retries reuse the same request identifier.
6. Unknown commit outcomes are resolved by receipt replay before new logical work.
7. Valkey failover does not justify a strong-consistency claim.
8. Recovery never treats actor/process liveness or persisted =running= state as lease authority.
9. Recovery/failover must not issue a fencing generation at or below a generation already accepted downstream.
10. HTTP and embedded callers use the same application service.
11. Target actors and HTTP routes never import Valkey packages.
12. Client clocks do not determine lease validity; backend time and the fenced commit boundary do.

* Implementation Order

1. Issue-29 canonical key, state machine, owner, handle, authority, and service outcomes.
2. Issue-30 protocol objects, key codec, serializers, deadlines, lifecycle, and hooks.
3. Deterministic memory backend and complete common contract suite.
4. Issue-31 Valkey scripts, same-slot key layout, pool, TLS, authentication, durability policy, and health.
5. Valkey concurrency, expiry, corruption, restart, and recovery-fence evidence.
6. Target lease application service combining authorization and semantic outcomes.
7. Issue-32 HTTP routes and embedded API adapters.
8. Manifest-controlled target dispatch and immutable execution envelopes.
9. Fencing gates at CouchDB, event, graph, attachment, result publication, RabbitMQ settlement, and external-effect boundaries.
10. Issue-33 deterministic recovery classifier and LR-* race schedule harness.
11. Issue-33 real-Valkey crash/TTL/ambiguous-response tests.
12. Issue-33 cross-layer stale-writer and revoke acceptance tests through the production fenced-effect seam.
13. Issue-33 restart/restore fencing-floor proof against the actual deployment durability configuration.
