* Scope

This node answers one narrow question: how does a StarLang author explicitly tell the compiler which inference backend policy to use?

It does not redesign the expert-system language in STAR-LANG-RESEARCH-023, define the general pragma/compiler-option system, or replace the backend capability/runtime research in STAR-LANG-RESEARCH-021 and STAR-LANG-RESEARCH-022.

The separate pragma research owns the general grammar, option typing, inheritance pipeline, diagnostics framework, reproducibility classes, and deployment-policy interaction. This node owns only the =:backend= option's source meaning and compatibility rules.

* Decision

The canonical source-level selector should be a Lisp-native compiler directive:

#+begin_src lisp
(pragma :backend :auto)
(pragma :backend :lisa)
(pragma :backend :swi-prolog)
(pragma :backend :n-prolog)
#+end_src

The supported initial values are exactly:

#+begin_example
:auto
:lisa
:swi-prolog
:n-prolog
#+end_example

=:auto= is deterministic backend-selection policy. The other values are explicit backend pins.

This is StarLang data consumed by the closed compiler. It is not Common Lisp =EVAL=, a Common Lisp declaration, native LISA syntax, or native Prolog syntax.

Nim pragmas are useful inspiration for source-local compiler directives, but Nim punctuation is explicitly rejected. StarLang remains Lisp-family syntax.

* Canonical Source Surface

** Module scope

#+begin_src lisp
(module fraud-analysis
  (pragma :backend :swi-prolog)
  ...)
#+end_src

The module policy becomes the inherited backend default for compatible contained reasoning declarations unless a narrower legal source scope overrides it.

** Expert-system scope

#+begin_src lisp
(expert-system transaction-risk
  (pragma :backend :lisa)
  ...)
#+end_src

This requests LISA only if the expert system's derived semantic profile and package requirements are compatible with the LISA adapter descriptor.

** Actor scope

#+begin_src lisp
(actor ownership-reasoner
  (pragma :backend :swi-prolog)
  ...)
#+end_src

Actor scope provides a default for logic operations lexically owned by the actor. It does not make the actor runtime itself Prolog-backed.

** Operation scope

#+begin_src lisp
(reason ownership-path
  (pragma :backend :swi-prolog)
  ...)
#+end_src

Operation scope is the narrowest source backend policy and overrides broader source defaults, subject to semantic compatibility and deployment restrictions.

* Normalized Meaning

The source directive should normalize to an engine-neutral compiler policy record before executable plan materialization.

#+begin_src lisp
(logic-backend-source-policy
  :requested :swi-prolog
  :selection :pinned
  :source-scope :operation
  :source-span <span>)
#+end_src

For =:auto=:

#+begin_src lisp
(logic-backend-source-policy
  :requested nil
  :selection :auto
  :source-scope :module
  :source-span <span>)
#+end_src

Native engine handles, Prolog modules, LISA networks, sockets, child-process IDs, package objects, and Common Lisp function designators never enter this record.

* Authority Boundary

Backend selection has three distinct authorities:

1. *Source request* — what the StarLang author asks for with =:backend=.
2. *Compiler semantic validation* — whether that backend can implement the required semantic profile, packages, proof contract, and enforceable limits.
3. *Deployment policy* — which backends/builds are installed, trusted, permitted, and usable in the target deployment.

Source controls only the first category.

A source directive cannot install an engine, trust a package, weaken isolation, enable forbidden native code, or grant a capability that deployment policy denies.

* Compatibility Rules

An explicit pin never means "force the compiler to make it work."

The compiler must reject a pin when the selected backend cannot satisfy independently derived requirements.

#+begin_src lisp
(reason recursive-ownership
  (pragma :backend :lisa)
  (pragma :logic-profile :tabled)
  ...)
#+end_src

If the active LISA descriptor does not advertise the required tabled profile, compilation fails.

Likewise:

#+begin_src lisp
(expert-system agenda-driven-review
  (pragma :backend :swi-prolog)
  ... production-rule forms requiring agenda/salience semantics ...)
#+end_src

must fail unless a future SWI adapter explicitly advertises the exact required production semantic profile. Similar surface syntax is not semantic compatibility.

N-Prolog must be checked against its declared portable/fixture-proven profile rather than treated as a transparent SWI replacement.

* =:auto= Semantics

=:auto= means deterministic capability-based selection during plan materialization using the versioned backend registry and policy researched in STAR-LANG-RESEARCH-022.

=:auto= does not mean:

- try engines until one succeeds;
- switch engine types after timeout or crash;
- pick the least busy engine type;
- use N-Prolog because SWI-Prolog is unavailable;
- weaken proof, isolation, or budget requirements;
- choose based on answer contents;
- perform runtime semantic failover.

Once materialized, the executable run plan pins one concrete backend identity and the runtime/package/mapping evidence required for replay.

* Source Precedence

The backend selector participates in the separate general pragma-resolution pipeline.

Expected source precedence for this option is:

#+begin_example
project default
    ↓
module pragma
    ↓
declaration pragma
    ↓
operation pragma
#+end_example

The nearest legal source scope wins, but deployment restrictions apply afterward and may reject or constrain the result.

A declaration with no =:backend= pragma inherits the nearest enclosing value. Absence is not equivalent to =:auto= until the project/compiler default layer is resolved.

Duplicate =:backend= pragmas in the same scope should be a compiler error. Silent "last one wins" behavior makes generated source and refactors too easy to misread.

* Diagnostics

Required diagnostics include:

** Unknown backend

#+begin_example
error STAR-BACKEND-001: unknown logic backend :foo
expected one of :auto, :lisa, :swi-prolog, :n-prolog
#+end_example

** Incompatible backend

#+begin_example
error STAR-BACKEND-002: backend :lisa does not provide required profile :tabled
required by reason ownership-path
selected at module pragma fraud-analysis
#+end_example

** Deployment-denied backend

#+begin_example
error STAR-BACKEND-003: source requested :swi-prolog but deployment policy forbids this backend
source request: module fraud-analysis
policy authority: deployment profile prod-restricted
#+end_example

** Duplicate same-scope selector

#+begin_example
error STAR-BACKEND-004: duplicate :backend pragma in the same scope
first:  fraud.star:4:3
second: fraud.star:5:3
#+end_example

Diagnostics preserve the originating source span and identify the policy layer that supplied the final or rejected value.

* Explainability

The separate compiler-option explanation facility should expose backend resolution.

Conceptual output:

#+begin_example
:backend
  compiler default: :auto
  project:          :auto
  module pragma:    :swi-prolog
  operation pragma: <none>
  deployment:       allowed [:swi-prolog :lisa]
  final policy:     :swi-prolog
  selection:        pinned
#+end_example

For =:auto=, explanation should also identify the versioned materialization rule and selected concrete backend once selection occurs.

* Reproducibility

The =:backend= directive is semantic/runtime-plan configuration, not diagnostic decoration.

Therefore:

- the resolved source backend policy participates in normalized compiler-option identity;
- the selected concrete backend participates in executable run-plan identity;
- engine build identity, adapter version, logic package digest, fact-mapping digest, semantic profile, and proof contract remain pinned as required by STAR-LANG-RESEARCH-022;
- changing =:backend= invalidates artifacts/run plans whose behavior can depend on engine selection;
- source span remains provenance/explanation metadata.

* Safety Rules

The selector must not become an executable compiler extension.

Illegal conceptual examples:

#+begin_src lisp
(pragma :backend (load "my-engine.lisp"))
(pragma :backend (shell "swipl ..."))
(pragma :backend :native-handle)
#+end_src

The value is a closed enum, not an expression.

Backend-specific tuning belongs to statically registered namespaced compiler options in the separate pragma research. Ordinary StarLang source cannot load arbitrary native libraries, invoke shell commands at compile time, or execute Common Lisp to construct a backend.

* Rejected Designs

** Nim punctuation

Rejected:

#+begin_example
{. backend: swi-prolog .}
#+end_example

Reason: it introduces a non-Lisp punctuation sublanguage.

** Arbitrary metadata bag

Rejected as the canonical backend-selection surface:

#+begin_src lisp
(reason ownership-path
  (:backend swi-prolog
   :whatever "anything")
  ...)
#+end_src

Reason: backend selection needs typed option registration, consistent scoping, explanation, conflict diagnostics, and deployment-policy interaction.

** Native engine forms

Rejected:

#+begin_src lisp
(reason ownership-path
  (swi:table ownership/2)
  ...)
#+end_src

Reason: this leaks engine syntax into core StarLang and backend-neutral IR.

** Runtime fallback chain

Rejected:

#+begin_src lisp
(pragma :backend '(:swi-prolog :n-prolog :lisa))
#+end_src

Reason: the engines are not generally semantically interchangeable. Operational failure cannot silently authorize a semantic change.

* Implementation Consequences

If approved, implementation should:

1. register =:backend= as a closed typed compiler option;
2. parse it through the closed StarLang reader;
3. allow it only in scopes approved by the general pragma research;
4. normalize it before logic/expert semantic lowering completes;
5. derive required semantic profiles independently of the requested backend;
6. validate explicit pins against the backend registry;
7. apply deployment restrictions after source-policy resolution;
8. emit source-linked diagnostics and option explanations;
9. pin the selected concrete backend before execution;
10. keep native backend objects outside normalized IR.

No implementation should begin from this research node alone while its approval rows remain pending.

* Footnotes and Glossary

- *Backend pin* — Explicit request for one concrete inference backend ID rather than deterministic =:auto= selection.
- *Semantic profile* — Versioned behavioral contract required from a logic backend, such as tabled-query or production-agenda semantics.
- *Materialization* — Compiler/deployment phase that resolves abstract policy into an immutable executable run plan.
- *Deployment authority* — Operator-controlled configuration that can restrict installed, trusted, or permitted runtime capabilities; source cannot override it.
- *Closed enum* — Finite compiler-recognized value set whose members are data and are not evaluated as expressions.
