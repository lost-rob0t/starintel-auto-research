#+title: STAR-RESEARCH-038 GServer Client Library and Administration Boundary
#+description: Deep research on the reusable Common Lisp gserver client, remote CLI layering, authentication and error semantics, testability, version compatibility, and the separate local administrative break-glass boundary.
#+status: REVIEW
#+created: [2026-08-18 Tue]
#+last_modified: [2026-08-18 Tue]
#+filetags: :starintel:star-server:gserver:client:sdk:cli:authentication:administration:common-lisp:research:org-roam:

* Purpose

StarIntel already contains both a Common Lisp HTTP client system and a separate command-line client, while the server now exposes first-class human-user authentication and administrator-only user lifecycle routes. The immediate question is not whether StarIntel should have a client library. It already does. The question is what boundary that library must own before new administrative commands are added, and how a remote client CLI should coexist with a server-local administrative interface.

This is research only. It does not approve a concrete package split, command syntax, credential-file format, retry policy, or implementation sequence. Those belong to design after operator review.

* Research Question

What should the architectural responsibility of =starintel-gserver-client= be, how should =star-cli= depend on it, and which administrative operations must remain available through a separate server-local path so StarIntel has both a reusable remote API client and a Gitea-like break-glass management interface without duplicating authentication or user-lifecycle semantics?

* Existing StarIntel State

The repository already encodes the intended dependency direction:

#+begin_example
star-cli
   |
   v
starintel-gserver-client
   |
   v
HTTP gserver
#+end_example

=star-cli.asd= depends explicitly on =starintel-gserver-client=. The client is therefore not a speculative new component. It is an existing public boundary that has not yet matured enough to carry the full protocol.

The current =star-client= object contains a base URL and default HTTP headers. =api-request= is a macro that directly invokes Dexador. Higher-level methods such as =get-targets=, =submit-document=, =get-document=, and =fts= mostly construct paths and return raw HTTP response bodies.

The current library does not yet provide a complete abstraction for:

- bearer/API-key authentication;
- password login and returned session credentials;
- user creation, listing, reset, or self-service password changes;
- structured success values;
- typed protocol errors;
- correlation identifiers;
- response metadata;
- explicit request timeout policy;
- transport injection for deterministic unit tests;
- API version or capability negotiation;
- credential redaction and safe debug representations;
- stable handling of future server route changes.

The current =star-cli.lisp= is a large command implementation and sometimes calls =api-request= directly with route strings. This means transport details have leaked through the intended client boundary. Adding administrator commands in the same style would deepen that coupling.

* Authentication State Changes the Client Boundary

The server now has a real human-user lifecycle rather than only document-oriented HTTP calls.

Current routes include:

- =POST /auth/login=;
- =POST /auth/users=;
- =GET /auth/users=;
- =POST /auth/users/:username/password=;
- =POST /auth/password=;
- API-key credential create/list/rotate/revoke/disable operations.

Password login returns an opaque StarIntel API key and user metadata. Subsequent requests use bearer authentication. Authentication responses include a correlation identifier. User records are kept in the dedicated authentication database and normal password operations are subject to the server password policy.

These facts make authentication, request identity, and structured error handling protocol concerns rather than CLI concerns. A reusable client must be able to make the same authenticated operations whether the caller is =star-cli=, Quasar, an Emacs integration, a Common Lisp application, a test harness, or another operator tool.

* Comparative Finding: Remote CLI and Local Administration Are Different Products

Gitea provides an especially useful distinction.

Its =tea= command-line client is a remote API consumer. The tool stores or selects Gitea server logins and uses the Gitea API SDK to interact with one or more running instances.

The =gitea admin user ...= command family is different. It is part of the server executable and initializes Gitea's internal configuration/database path. For example, the current password-change command initializes the database and invokes the user service directly rather than sending an HTTP request to the same Gitea process.

This separation provides two operational properties:

1. normal remote administration follows the same authenticated public API as other clients;
2. server-local recovery does not depend on the HTTP listener, a valid administrator API token, or the health of the remote API path.

StarIntel has the same need. A remote =star-cli= user-management command and a future local =star-server admin user= command may expose similar human intent, but they should not be the same transport implementation.

* Comparative Finding: Mature CLIs Inject Client Dependencies

GitHub CLI documents an options/factory pattern in which commands receive HTTP clients, configuration, repositories, and I/O abstractions as dependencies. Command tests can replace those dependencies. The =gh api= implementation obtains an authenticated HTTP client from the command factory rather than constructing ad-hoc transport state in every handler.

The important lesson is not Go-specific dependency injection. It is that command parsing and terminal presentation are kept above a reusable authenticated client boundary, and HTTP behavior can be replaced in tests.

For StarIntel this means a command handler should not need to know:

- which HTTP library is used;
- how bearer headers are encoded;
- how URL paths are joined;
- how JSON errors are decoded;
- which status codes map to protocol conditions;
- how correlation IDs are extracted;
- how a request timeout is applied.

Those are client-library responsibilities.

* Comparative Finding: Transport Configuration Is Part of the SDK

Kubernetes =client-go= makes the transport boundary explicit. Its REST client configuration includes host, bearer token or token file, user agent, timeout, TLS configuration, proxy behavior, custom transport, and transport wrappers. It also sanitizes credential-bearing configuration when rendered for debugging.

The exact Kubernetes feature set is far larger than StarIntel needs, but several principles transfer directly:

- authentication belongs in client configuration rather than individual commands;
- request timeout is a client/request concern;
- transport replacement or wrapping is a first-class test and integration hook;
- user-agent identification is useful operational metadata;
- credential-bearing objects require safe printing/redaction behavior;
- higher-level API operations should share one transport foundation.

StarIntel does not need to reproduce =client-go=. It should adopt the boundary discipline.

* Client Library Responsibility

The reusable client should be the authoritative Common Lisp representation of the remote gserver HTTP protocol.

At research level, that means it should own the following classes of concern.

** Connection configuration

The client needs a stable representation of at least:

- server/base URL;
- authentication credential when present;
- default request headers;
- user-agent/client identity;
- request timeout or deadline policy;
- transport implementation or injected request function;
- TLS policy when non-default behavior is supported.

The client should not own human CLI profile persistence. A library consumer may construct a client from environment variables, an encrypted credential store, an Emacs auth source, process-local configuration, tests, or other application state.

** Authentication operations

The library should represent the server authentication API directly, including:

- password login;
- bearer/API-key use after login;
- authentication context inspection;
- credential lifecycle operations;
- human-user lifecycle operations permitted by the authenticated principal.

The CLI should not parse login response JSON to discover the key itself if the library can return a structured login result.

** Domain operations

Existing document, target, search, view, bulk, and related API calls should migrate behind named client operations. A raw request escape hatch may remain useful for debugging or forward compatibility, but ordinary CLI commands should not require it.

** Serialization boundary

The library should encode request values and decode response values at the protocol boundary. Callers should not repeatedly build JSON strings or manually parse successful responses.

This does not require a large object hierarchy for every StarIntel document. Generic StarIntel documents may remain JSON/document values where that preserves flexibility. Control-plane responses with stable schemas, especially authentication, errors, capabilities, credentials, users, and operation receipts, benefit from explicit structured representations.

** Error boundary

Dexador conditions are transport-library implementation details. Callers need StarIntel protocol conditions.

A useful error model must distinguish at least:

- request construction/protocol errors before transport;
- connection, TLS, DNS, and transport failures;
- request timeout/deadline failure;
- HTTP non-success responses;
- authentication failure;
- authorization failure;
- validation failure;
- not-found and conflict outcomes when callers need to branch on them;
- malformed or incompatible server responses.

The client should preserve useful evidence from server failures, including:

- HTTP status;
- stable StarIntel error code when present;
- server message/detail;
- correlation identifier;
- selected safe response headers;
- raw response body for bounded diagnostics when safe.

This allows CLI code, agents, and interactive integrations to make decisions without depending on Dexador's condition taxonomy.

* Problem Details and Current Error Envelopes

StarIntel currently has custom JSON error envelopes in parts of the HTTP API, while existing lease research recommends RFC 9457 problem details for newer versioned service APIs.

The client therefore should not require the whole server to migrate error formats before it can be useful. The transport layer can normalize known StarIntel error representations into one client-side condition model and preserve unknown bodies for diagnostics.

This is an important compatibility boundary: server error-envelope migration and client error ergonomics can proceed independently.

* Correlation and Observability

Correlation identifiers already exist in authentication responses and request security contexts. The client should preserve them as response/error metadata.

This enables a human-facing CLI error such as:

#+begin_example
request denied: missing scope documents:write
correlation: 01J...
#+end_example

without forcing operators to enable verbose raw HTTP logging or exposing credentials.

A client user-agent should identify the calling surface sufficiently for server logs, for example a library/version token with an optional caller token supplied by =star-cli= or another integration. Exact syntax belongs to design.

* Retry Research

Automatic retries are dangerous at this layer if applied indiscriminately.

A transport failure before a request is sent, an idempotent GET, and a POST whose commit outcome is unknown have different semantics. The client must not turn a network interruption into a duplicate mutation.

Research conclusion:

- do not define blanket automatic retries as a client guarantee;
- preserve enough response and transport information for safe caller decisions;
- automatically retry only operations whose protocol contract explicitly makes replay safe;
- prefer server-supported idempotency keys or stable logical operation identifiers for mutable operations before adding retry behavior;
- expose retry policy as an explicit capability, not hidden magic.

The exact initial retry matrix belongs to design and must be derived from each endpoint's semantics.

* Timeout and Deadline Research

The current =api-request= wrapper does not expose a coherent StarIntel timeout contract. A reusable client needs bounded request behavior, but one global socket timeout is not equivalent to a server operation deadline.

The client should eventually distinguish:

- transport/connect timeout;
- bounded whole-request timeout;
- server-protocol deadline or =X-Request-Timeout-Ms= when supported;
- streaming or long-running operations whose lifetime differs from ordinary request-response calls.

The client should never silently reset a caller's logical deadline during nested operations.

Design must choose the exact Common Lisp representation and defaults after surveying current endpoint duration characteristics.

* API Version and Capability Boundary

The present server contains both older versionless routes and newer work that introduces versioned service boundaries. Hardcoding route strings throughout command handlers makes future migration expensive.

The client library is the correct compatibility choke point. It should centralize endpoint construction and provide a place for capability/version discovery or compatibility shims when server generations diverge.

Research does not conclude that StarIntel must immediately generate its client from OpenAPI or migrate every route to =/v1=. No current canonical OpenAPI contract exists in =starintel-server=. Premature generation would merely generate bindings around an unstable description.

The immediate requirement is simpler: callers depend on named client operations, not wire paths.

* Client Concurrency and Lifetime

The reusable client may be shared by interactive applications and actor-backed integrations, so its public state should not require mutation for ordinary concurrent requests.

Authentication replacement, connection pooling, and per-request headers need explicit semantics if the same client is shared across threads or actors. A client that mutates a shared header alist to switch users would be unsafe and difficult to reason about.

Research preference:

- immutable or effectively immutable connection/auth configuration during ordinary requests;
- per-request options passed explicitly;
- a new derived client/session object when changing principal identity;
- leave HTTP connection reuse to the transport implementation rather than recreating connections for every high-level operation.

Exact object construction is a design question.

* Secret Handling

The existing server correctly stores only password-derived material and returns raw API keys only at credential creation/login boundaries.

The client and CLI must preserve that discipline.

Requirements for later design:

- do not include bearer keys or passwords in printed object representations;
- do not log =Authorization= headers in normal debug output;
- distinguish credential values from ordinary strings in interfaces where practical;
- support secret input paths that do not require command-line arguments, because argv and shell history are poor secret stores;
- allow environment or file-based non-interactive credentials for automation;
- leave persistent human credential storage to the CLI/application layer, not the core SDK.

This also argues against making the client object itself responsible for a global =~/.config/starintel= profile database.

* Remote CLI Responsibility

Once the client boundary is complete, =star-cli= should become a terminal adapter over it.

The CLI owns:

- command and flag grammar;
- interactive prompting;
- selecting a named server/profile if profiles are later supported;
- reading secrets from terminal/stdin/files according to policy;
- table, text, JSON, or machine-readable presentation;
- terminal capabilities and color;
- confirmation for destructive actions;
- process exit codes.

The CLI should not own:

- HTTP route strings for ordinary supported operations;
- Authorization header construction;
- JSON protocol encoding/decoding;
- HTTP status interpretation;
- server error-code parsing;
- retry safety decisions that belong to the protocol operation;
- StarIntel user password policy.

The server remains authoritative for policy. Client-side validation may improve ergonomics but cannot replace server validation.

* Machine-Readable CLI Output

A management CLI will be used both by humans and scripts. GitHub CLI's explicit JSON output support is a useful precedent.

Research conclusion: the design should preserve a stable machine-readable output mode and keep human tables/messages as a presentation layer. Scripts should not need to scrape decorative text such as checkmarks or column spacing.

The exact flag names and schema are not approved here.

* Local Server Administration Boundary

A future Gitea-like command should live under the server executable or another server-local administrative executable and use server-domain lifecycle functions directly.

Conceptually:

#+begin_example
star-server admin ...
        |
        v
server configuration / auth initialization
        |
        v
star.auth lifecycle services
        |
        v
credential store
#+end_example

This path exists for bootstrap and recovery. It must continue to work when:

- the HTTP listener is stopped;
- an administrator API key was lost or revoked;
- the remote CLI cannot authenticate;
- the HTTP routing layer is broken during an upgrade;
- local recovery is intentionally restricted to host/container access.

It should not call =starintel-gserver-client= merely to loop back through HTTP.

This does not mean it should bypass domain rules. Gitea's local command is useful precisely because it invokes the same user-service logic after local database initialization. StarIntel should similarly reuse =star.auth= lifecycle behavior rather than writing password hashes or CouchDB documents directly from command handlers.

* Shared Semantics, Different Adapters

The desired topology is:

#+begin_example
                    remote callers
                         |
       +-----------------+-----------------+
       |                 |                 |
    star-cli          Quasar          other CL code
       |                 |                 |
       +-----------------+-----------------+
                         |
              starintel-gserver-client
                         |
                      HTTP API
                         |
                  service/domain layer
                         |
                    credential store

host-local operator
       |
star-server admin
       |
service/domain layer
       |
credential store
#+end_example

The remote and local paths share domain semantics below the HTTP adapter, not transport code above it.

* Why a Single "Client That Can Also Open CouchDB" Is Rejected

One tempting alternative is to make =starintel-gserver-client= support both HTTP mode and direct credential-store mode.

Research rejects that direction.

It would:

- make an ostensibly remote client depend on server persistence libraries and configuration;
- blur authentication and authorization boundaries;
- allow ordinary consumers to bypass the HTTP service contract;
- make packaging heavier;
- create ambiguous semantics when direct-store behavior differs from server behavior;
- undermine the recovery distinction between remote API tooling and server-local administration.

Direct-store access belongs behind server-domain services in the server administrative executable, not inside the reusable remote API client.

* Why a CLI-Only Wrapper Is Rejected

Another alternative is to add administrator routes directly to =star-cli= and leave =starintel-gserver-client= as a thin low-level helper.

That would duplicate protocol logic across every future consumer and permanently couple useful operations to terminal command handlers. The existing dependency direction already says the opposite: =star-cli= depends on the client library.

The client should become the reusable unit first.

* Why Full Generated SDK Work Is Deferred

A generated client can become attractive once StarIntel has a stable machine-readable HTTP specification. Today the route set spans older and newer conventions, and the current reusable client already exists in Common Lisp.

Making OpenAPI generation a prerequisite would enlarge this slice without resolving the immediate ownership bug.

The later design should keep generation possible by:

- centralizing endpoint schemas;
- keeping control-plane response types explicit;
- testing wire fixtures;
- avoiding CLI-only protocol knowledge.

But hand-written Common Lisp client code remains appropriate for the next boundary-hardening slice.

* Test Strategy Findings

The client library should be independently testable without booting the whole StarIntel stack for every behavior.

Minimum research-derived test layers are:

** Pure/request construction tests

Validate:

- URL/path encoding;
- query parameter encoding;
- authentication-header injection;
- content type and accept behavior;
- secret redaction;
- serialization of control-plane request values.

** Injected transport tests

A fake or injected transport should prove:

- successful response decoding;
- each error-family mapping;
- malformed response handling;
- correlation-ID retention;
- timeouts/transport conditions;
- no credential leakage into condition printing;
- request bodies and headers for user/auth operations.

This is analogous to GitHub CLI's HTTP registry tests and =client-go='s replaceable/wrapped transport boundary.

** Live HTTP integration tests

Run against the actual Ningle/Clack server and prove that the client matches the server contract for:

- health/context where applicable;
- password login;
- bearer-authenticated request;
- administrator user creation;
- user listing;
- new-user login;
- administrator password reset;
- self-service password change;
- credential lifecycle operations;
- representative document/search operations.

** Deployment/stack tests

The existing stack path should retain a small end-to-end smoke test using the built client or CLI so packaging failures cannot leave the SDK technically correct but absent from deployable artifacts.

* Contract Fixtures

Stable JSON fixtures should be captured for control-plane responses and errors. Tests should distinguish protocol fixture breakage from terminal-format changes.

Useful fixtures include:

- login success;
- login failure;
- user metadata;
- user conflict;
- password policy violation;
- authorization denial;
- credential create/rotate/revoke metadata;
- malformed/unknown server error;
- correlation-bearing success and failure.

This creates a practical path toward future generated bindings without requiring them now.

* Packaging Finding

=starintel-gserver-client= is already a distinct ASDF and Nix package. Keep that property.

A Common Lisp program should be able to depend on the client without pulling in the full gserver runtime, CouchDB credential store, RabbitMQ actor stack, or CLI parser.

The current ASDF system depends on =starintel=, =jsown=, =uuid=, =dexador=, and =quri=. The future design should audit which dependencies are truly needed, but should preserve a small remote-client dependency closure.

Likewise, =star-cli= should depend on the client system rather than the server runtime.

* Relationship to Quasar and Other Consumers

Quasar research has previously considered client/service boundaries, but this node is specifically about the existing Common Lisp StarIntel gserver client. It does not force Quasar's browser frontend to use Common Lisp or make StarIntel the mandatory Quasar backend.

The value for Quasar is indirect: connected Common Lisp control-plane code can consume a supported gserver client instead of duplicating StarIntel HTTP calls.

The same applies to:

- Lem integrations;
- Emacs/Common Lisp bridges;
- actor supervisors that intentionally call the HTTP service;
- administrative automation;
- test harnesses;
- future operator UIs.

* Security Boundary

Remote administrative operations must remain ordinary authenticated server requests. The client does not gain authority because it is an official SDK.

A remote =create-user= operation still requires an administrator credential and is authorized by the server. A remote client cannot silently fall back to direct database access.

The server-local administrative path is a separate trust boundary based on host/container execution authority and server configuration access. Its existence should be explicit and auditable.

* Research-Derived Requirements for Design

Any promoted design should satisfy all of the following:

1. retain =starintel-gserver-client= as a separately loadable Common Lisp system;
2. make it the normal remote HTTP protocol boundary for Common Lisp callers;
3. remove ordinary wire-path, auth-header, JSON-error, and Dexador knowledge from =star-cli= command handlers;
4. add first-class authentication, credential, and human-user client operations;
5. define structured protocol success and error values for control-plane operations;
6. preserve HTTP status, StarIntel code, and correlation metadata on failures;
7. provide an injectable or replaceable transport seam for unit tests;
8. define explicit timeout/deadline behavior;
9. avoid unsafe implicit retries for mutating operations;
10. keep secrets redacted in logging, printing, and error conditions;
11. centralize route construction so future API version changes do not fan out through callers;
12. keep CLI profile/credential persistence outside the core SDK;
13. preserve a machine-readable CLI output path;
14. keep a future server-local =star-server admin= path independent of HTTP availability;
15. make local administration reuse server-domain/auth lifecycle logic rather than write persistence records directly;
16. do not place direct CouchDB/server-store mode inside the remote client library;
17. retain a small client dependency closure independent of the full server runtime;
18. test the SDK independently, against live HTTP, and in deployable stack smoke tests.

* Open Questions for Design

Research intentionally leaves these unresolved:

- Should the public constructor remain =make-instance 'star-client= or become a constructor function that validates configuration?
- Should bearer authentication live in the client object, a derived session object, or a composable request-auth provider?
- What is the exact condition hierarchy and which status codes deserve subclasses versus fields?
- Should success values be CLOS classes, structures, property lists, JSOWN objects, or a small mixture by API stability?
- How should per-request deadlines compose with the existing =X-Request-Timeout-Ms= server behavior?
- Which existing mutating endpoints are currently replay-safe, and where are idempotency contracts required before any retry support?
- Is capability discovery needed immediately, or is centralized route ownership sufficient for the first slice?
- What profile format and secret store should =star-cli= use, if persistent profiles are added?
- What is the exact split between =star-cli= remote administrator commands and =star-server admin= local commands?
- Which server-domain functions need extraction or stabilization so local administration does not depend on HTTP handlers?
- Should the current single =api-client.lisp= be split immediately or only as behavior is migrated behind tests?
- How should streaming endpoints eventually fit the same client without forcing request-response APIs into a streaming abstraction?

* Promotion Gate

Do not promote this node into design until the operator explicitly approves the research boundary.

Approval means agreement with these architectural findings, not approval of exact implementation details:

- client library before new remote management CLI behavior;
- remote CLI over the reusable HTTP client;
- local server administration as a separate break-glass adapter;
- shared domain lifecycle semantics beneath both paths;
- no direct-store mode in the remote client;
- transport/auth/error/testability concerns owned by the reusable client.

After approval, the next artifact should be a focused design for the client-library boundary and its first authentication/user-management slice. Implementation follows only after that design is reviewed.

* Research Conclusion

StarIntel should not create another client library and should not start by bolting user-management commands onto the existing CLI.

The repository already has the correct coarse dependency direction: =star-cli= depends on =starintel-gserver-client=. The missing step is to make that client a real reusable protocol SDK rather than a thin Dexador convenience wrapper.

The remote client library should own connection configuration, bearer authentication, protocol serialization, structured control-plane results, error normalization, correlation metadata, timeout behavior, route compatibility, and a replaceable transport seam. The CLI should own terminal interaction and presentation.

Separately, StarIntel should preserve a future Gitea-like local administrative interface that can initialize server configuration and call the same user/auth lifecycle services without requiring HTTP. That path is operational recovery tooling, not another mode of the remote SDK.

This separation gives StarIntel one reusable remote protocol boundary, one thin remote CLI, and one independent local recovery path while keeping authorization and lifecycle policy authoritative in the server.

* Footnotes and Glossary

[fn:sdk] SDK: A reusable programmatic client library that presents named operations and protocol semantics above a raw transport.

[fn:break-glass] Break-glass administration: A deliberately privileged local recovery path intended for bootstrap or failure recovery when the normal remote management plane is unavailable.

[fn:transport] Transport seam: An interface or injectable function around network request execution that allows tests and specialized consumers to replace the concrete HTTP implementation without changing higher-level client operations.

[fn:correlation] Correlation identifier: A stable request identifier carried across service layers and returned to callers so an operator can connect a client-visible failure to server logs and traces.
