* Research Question

How should a StarLang author explicitly tell the compiler which logic or expert-system backend to use while keeping the language Lisp-native, deterministic, semantically exact, replayable, and independent of native engine objects?

The initial source policies are exactly:

#+begin_src lisp
:auto
:lisa
:swi-prolog
:n-prolog
#+end_src

The central design problem is not merely choosing a spelling. The source language needs one coherent answer for:

1. how backend policy is written;
2. where it may be written;
3. how nested scopes inherit and override it;
4. when an override is semantically unsafe and must fail;
5. what =:auto= means;
6. how compatibility is checked before an engine is selected;
7. what evidence the compiler retains after selection; and
8. how portability is described without pretending different inference models are equivalent.

This node is source-language and compiler-policy research. It does not redefine backend runtime adapters, engine lifecycle, capability truth, budgets, or proof normalization.

* Executive Decision

Use one universal compiler-directive form:

#+begin_src lisp
(pragma :backend :swi-prolog)
#+end_src

The initial accepted values are:

#+begin_src lisp
(pragma :backend :auto)
(pragma :backend :lisa)
(pragma :backend :swi-prolog)
(pragma :backend :n-prolog)
#+end_src

Do not create an equivalent backend-selection syntax using an ordinary metadata list such as:

#+begin_src lisp
(:backend :swi-prolog)
#+end_src

A =(:backend ...)= pair may remain ordinary declaration metadata inside a future grammar where the enclosing form explicitly defines such a field, but it is not a compiler backend directive and must not be accepted as an alternate spelling for backend selection.

This gives StarLang one language model:

- =pragma= carries compiler-owned, lexically scoped policy that affects compilation or plan materialization but is not a runtime expression;
- ordinary keyword metadata belongs to the declaration that owns it;
- runtime adapters consume the already-materialized plan and do not reinterpret source pragmas.

The spelling is Lisp-native and consistent with StarLang's parenthesized source language. Nim is useful evidence for the semantics of compiler annotations, but Nim punctuation such as ={. backend: swi-prolog .}= is explicitly rejected as StarLang syntax.

* Why =pragma= Rather Than =declare=

Common Lisp provides useful semantic precedent: declarations are non-evaluated information to the compiler or other program processors, have defined scope, and may be locally shadowed. Top-level proclamations provide a separate global policy mechanism.

StarLang should borrow those ideas without claiming that a StarLang =pragma= is Common Lisp =declare=. StarLang uses a closed reader and its own compiler; host Common Lisp declaration processing is not the source-language boundary.

The name =pragma= is preferable for StarLang because it communicates that the form is compiler policy rather than an ordinary runtime form while avoiding accidental expectations that every ANSI Common Lisp declaration rule applies unchanged.

The important semantic borrowings are:

- directives are not evaluated as runtime expressions;
- directives have explicit lexical scope;
- nested scope can refine inherited compiler information;
- the compiler owns validation and diagnostics;
- source locations remain attached to the directive for diagnostics and provenance.

The important rejection is surface imitation. StarLang remains Lisp-family source code.

* Current Compiler Boundary

The canonical StarLang compiler is Common Lisp, but =.star= source is parsed through StarLang syntax objects rather than the host Common Lisp reader. The current compiler already attaches span/origin information to compiler errors and normalizes declaration property lists into closed data.

At the inspected canonical StarLang main revision =067f12506f429c8d34f0383729972e3ee1337c05=, =prototype/compiler-ir-prototype.lisp= defines =star-lang-compiler-error= with structured code, span, origin, syntax kind, phase, and details fields. It compiles source declarations through dedicated validators rather than evaluating host forms.

That architecture is compatible with a source =pragma= node because a pragma can be parsed as ordinary StarLang syntax, normalized into compiler policy, and removed before runtime execution. No Common Lisp =READ=, =EVAL=, native LISA object, or Prolog engine handle is required.

This research does not implement the compiler change. The current compiler remains the observed baseline, not evidence that the proposed syntax is already supported.

* Source Syntax Decision

** Universal directive

Backend selection uses exactly this source shape:

#+begin_src lisp
(pragma :backend <policy>)
#+end_src

where =<policy>= is one of:

#+begin_example
:auto
:lisa
:swi-prolog
:n-prolog
#+end_example

The backend name is a StarLang keyword value, not an unqualified symbol and not a string. This keeps the policy vocabulary closed and prevents package/readtable behavior from entering source semantics.

** Singleton per scope

A scope may contain at most one =:backend= pragma.

This is invalid:

#+begin_src lisp
(module fraud-analysis
  (pragma :backend :swi-prolog)
  (pragma :backend :lisa)
  ...)
#+end_src

The compiler must not use last-one-wins behavior because source reordering would silently change semantics. It reports =STAR.LOGIC.BACKEND-DUPLICATE= with both source spans.

** Directive prefix

Pragmas belong to a declaration prefix for the scope they govern. They appear before ordinary executable/body forms in that scope.

This is valid:

#+begin_src lisp
(reason ownership-path
  (pragma :backend :swi-prolog)
  (pragma :requires :tabled-recursion)
  ...)
#+end_src

A backend pragma discovered after ordinary body forms is rejected as misplaced. This keeps scope visible to both humans and the compiler and prevents control-flow-looking directives.

** =pragma :requires= is additive

This node uses =pragma :requires= to illustrate semantic requirements. Multiple requirement directives may be additive because they accumulate required capabilities or semantic features.

By contrast, =pragma :backend= is singleton because it selects one policy for a scope.

The precise vocabulary of semantic profiles and backend capabilities remains under STAR-LANG-RESEARCH-022. This node defines how source requirements participate in policy resolution, not the runtime capability registry itself.

* Scope Model

Backend policy may originate at five levels:

1. project/compiler default;
2. module or file scope;
3. actor scope;
4. expert-system scope;
5. individual =reason= operation scope.

The project/compiler default is an outer compilation input. The remaining levels are source lexical scopes.

** Project/compiler default

The compiler invocation or locked project configuration provides the outer default policy.

Conceptually:

#+begin_src lisp
(:backend-default :auto)
#+end_src

This is compiler configuration, not a second source-level spelling for =pragma=. The exact project manifest syntax is outside this node unless and until StarLang defines a canonical project form.

A project default is overridable policy. A deployment administrator who needs to forbid engines or impose a non-overridable backend constraint needs a separate deployment constraint concept. Do not overload =:backend-default= or =(pragma :backend ...)= with both meanings.

** Module or file scope

An explicit module may declare:

#+begin_src lisp
(module fraud-analysis
  (pragma :backend :swi-prolog)

  ...)
#+end_src

The directive supplies the inherited backend request for logic-bearing descendants that do not declare a more specific safe override.

If StarLang permits a file without an explicit =module= wrapper, one backend pragma in the file prelude may act as the implicit module policy. A file must not simultaneously declare two competing module-level backend policies through both an implicit prelude and an explicit module wrapper.

** Actor scope

An actor may declare:

#+begin_src lisp
(actor ownership-reasoner
  (pragma :backend :swi-prolog)

  ...)
#+end_src

The pragma is a default for logic operations lexically owned by the actor. It does not change the actor runtime, mailbox, supervision policy, transport, or scheduling semantics. It says which inference policy descendants request when they need a logic backend.

This distinction matters because actor execution and inference execution are separate authorities.

** Expert-system scope

An expert system may declare:

#+begin_src lisp
(expert-system transaction-risk
  (pragma :backend :lisa)

  ...)
#+end_src

For a stateful expert system, the selected backend is normally session-wide. LISA working memory, an SWI module/session, and an N-Prolog process do not share one implicit mutable state model.

Therefore a nested override cannot be treated as harmless textual shadowing when it would require the compiler to migrate live expert state between different engine semantics.

** Reason-operation scope

An individual operation may declare:

#+begin_src lisp
(reason ownership-path
  (pragma :backend :swi-prolog)
  (pragma :requires :tabled-recursion)

  ...)
#+end_src

This is the most specific source request for that operation, but specificity alone does not grant permission to violate an enclosing stateful semantic boundary.

* Deterministic Precedence

The candidate hierarchy

#+begin_example
operation
  >
actor/expert-system
  >
module
  >
project default
#+end_example

is directionally correct but too ambiguous to become the language rule as written. =actor= and =expert-system= are not necessarily peer scopes; one may lexically contain the other.

Use lexical specificity instead:

#+begin_example
reason operation
  >
nearest enclosing logic owner (expert-system or actor)
  >
module/file
  >
project/compiler default
#+end_example

Examples:

1. A =reason= directly inside an actor inherits the actor pragma before the module default.
2. An =expert-system= nested inside an actor inherits the actor policy but may safely replace it for the expert system as a whole if its required semantic profile is compatible.
3. A =reason= inside that expert system sees the expert-system policy as its nearest inherited request.
4. A reason-level pragma is the most specific request, but it is accepted only if changing policy at that boundary is semantically safe.

This makes precedence structural rather than dependent on a hard-coded assertion that actor always outranks expert system or vice versa.

** Resolution algorithm

For each logic-bearing plan node:

1. collect the project/compiler default and every enclosing backend pragma in lexical order;
2. reject duplicate backend pragmas within any one scope;
3. choose the most specific source/compiler request by lexical ancestry;
4. derive the node's exact semantic profile and required capabilities;
5. check whether the chosen request is legal at this semantic boundary;
6. if explicitly pinned, validate the requested backend against the semantic requirements;
7. if =:auto=, perform deterministic capability-based selection using the versioned policy owned by the logic runtime research;
8. materialize the exact selected backend and why-selected evidence;
9. freeze that result into the executable run plan.

Precedence selects a request. It never overrides semantic compatibility checking.

* Override Safety

** Safe defaults

Project and module policies are defaults. Replacing them in a narrower independent logic scope is safe when the narrowed scope has a self-contained semantic state boundary and the selected backend satisfies every requirement.

Actor policy is likewise a default for actor-owned inference calls. Changing that policy for an independent =reason= call is safe if the call's inputs, outputs, proof obligations, and state boundary are completely described by the logic-call contract.

** Stateful expert systems are different

A persistent expert-system session can own mutable facts, agenda state, pending activations, table state, uncertainty state, question/answer state, and justification history.

A nested backend override that would move one operation to another engine can therefore change observable behavior even if both engines can represent the individual predicates or rules.

Initial StarLang rule:

#+begin_example
A reason-level backend override inside a stateful expert-system session is rejected
when it would select a different backend from the session backend, unless the
semantic profile explicitly defines that cross-backend boundary and a
conformance-tested state mapping proves it.
#+end_example

No such general cross-backend state mapping is assumed in v1.

The compiler reports =STAR.LOGIC.BACKEND-OVERRIDE-UNSAFE= rather than copying working memory, translating agenda state, or materializing a second engine approximately.

An isolated/pure child reason operation may be eligible for its own backend only when the expert-system profile explicitly declares it an isolated logic call whose complete input is projected by value and whose result returns through a checked result contract.

** =:auto= does not escape the safety rule

A child may write:

#+begin_src lisp
(pragma :backend :auto)
#+end_src

This means “perform deterministic selection for this scope instead of inheriting the outer backend preference.” It does not mean “ignore enclosing state ownership.”

If an enclosing stateful expert session is pinned to =:lisa= and a child =:auto= would select =:swi-prolog=, the same cross-backend safety rule applies. The override fails unless the child is an explicitly isolated semantic boundary.

* Semantic Compatibility Is Mandatory

Backend selection is policy, not permission to change program meaning.

This source:

#+begin_src lisp
(reason ownership-path
  (pragma :backend :lisa)
  (pragma :requires :tabled-recursion)

  ...)
#+end_src

must fail under the initial capability model because LISA does not claim the exact tabled-recursion semantic profile.

Likewise:

#+begin_src lisp
(expert-system fraud-rules
  (pragma :backend :swi-prolog)
  (pragma :requires :production-agenda)

  ...)
#+end_src

must fail unless the SWI adapter genuinely implements the exact production-agenda semantics required by that program.

It is not sufficient that a translator could imitate some outcomes.

*Never translate approximately merely because translation is technically possible.*

The validation order is:

1. parse and validate the backend policy;
2. derive the semantic profile from the compiled program/package;
3. derive required capabilities and forbidden semantic weakenings;
4. validate package and fact-mapping compatibility;
5. validate proof, isolation, and mandatory resource-limit requirements;
6. only then accept an explicit backend pin or construct the =:auto= candidate set.

An explicit pin that fails compatibility is a compile/materialization error. The compiler may report compatible alternatives as diagnostics, but it must never silently rewrite the pin.

* =:auto= Semantics

#+begin_src lisp
(pragma :backend :auto)
#+end_src

means deterministic capability-based selection during semantic compilation or plan materialization.

The selection inputs are explicit, versioned data such as:

- required semantic profile;
- required and forbidden capabilities;
- exact logic/expert package identity and digest;
- fact-mapping identity and digest;
- required proof contract;
- required limit/isolation properties;
- versioned backend descriptors;
- versioned backend-selection policy;
- workload/benchmark identity only where the policy explicitly uses benchmark-backed routing after semantic compatibility is established.

=:auto= must not mean:

- try engines until one works;
- switch engines after a timeout;
- choose an engine type from current runtime load;
- use N-Prolog because SWI-Prolog happens to be unavailable;
- change backend according to returned answers;
- weaken a proof requirement to admit another backend;
- select an approximately translatable backend;
- rerun backend selection after execution has begun.

Backend health may choose among equivalent instances of the same already-selected backend build. It does not choose engine semantics.

If an eligible backend is unavailable after selection, materialization or execution fails according to the pinned backend's operational contract. Absence is not permission to change engines.

Once =:auto= resolves, the selected backend is part of the immutable executable run plan.

* Stable Selection and Ties

=:auto= is deterministic only if its versioned policy defines a total result for the eligible candidate set.

The policy may use a stable priority table, benchmark class, project constraint, or another explicit deterministic rule, but every input that can affect selection must be represented in the selection-policy identity or evidence.

If the configured policy cannot resolve a tie, compilation fails with =STAR.LOGIC.BACKEND-AUTO-AMBIGUOUS=. It must not depend on hash-table iteration order, process discovery order, environment installation order, or current worker load.

* Compiler Diagnostics

Backend diagnostics should use stable StarLang condition codes and retain source spans through the existing compiler error model.

Initial codes:

#+begin_example
STAR.LOGIC.BACKEND-UNKNOWN
STAR.LOGIC.BACKEND-DUPLICATE
STAR.LOGIC.BACKEND-DIRECTIVE-MISPLACED
STAR.LOGIC.BACKEND-INCOMPATIBLE
STAR.LOGIC.BACKEND-OVERRIDE-UNSAFE
STAR.LOGIC.BACKEND-AUTO-NO-CANDIDATE
STAR.LOGIC.BACKEND-AUTO-AMBIGUOUS
#+end_example

** Incompatible explicit pin

Example diagnostic:

#+begin_example
STAR.LOGIC.BACKEND-INCOMPATIBLE

Requested:
  :lisa

Required:
  :tabled-recursion

Semantic profile:
  "star.logic.tabled/1"

  :production-rules
  :working-memory
  :agenda
  :salience

  :swi-prolog

  project/compiler  :auto
  module            :swi-prolog
  reason            :lisa

#+end_example

The “Compatible backend” field is an explanation/suggestion. The compiler does not substitute it automatically for the explicit =:lisa= request.

** Unsafe stateful override

#+begin_example
STAR.LOGIC.BACKEND-OVERRIDE-UNSAFE

Enclosing expert session:
  transaction-risk

Session backend request:
  :lisa

Nested reason request:
  :swi-prolog

Reason:
  The operation shares state owned by semantic profile
  "star.logic.production/1" and no approved cross-backend
  state mapping is declared.

Required action:
  Keep the operation on the session backend or declare an
  explicitly isolated logic boundary whose mapping is proven.
#+end_example

* Compiler Representation

The source directive should normalize early into compiler policy data, while concrete engine selection is filled only during plan materialization.

A research target for the final materialized record is:

#+begin_src lisp
(:backend-policy
  (:requested :auto)

  (:request-origin
    (:scope :reason
     :node-id "reason:ownership-path"
     :source-span (:file "fraud.star"
                   :start 42
                   :end 44)))

  (:inherited-policy
    (:requested :swi-prolog
     :origin
       (:scope :module
        :node-id "module:fraud-analysis"
        :source-span (:file "fraud.star"
                      :start 1
                      :end 3))))

  (:selection-mode :capability)
  (:selection-policy "star.logic.backend-selection/1")
  (:policy-digest "sha256:...")

  (:semantic-profile "star.logic.tabled/1")
  (:required-capabilities (:tabled-recursion))
  (:portability :backend-neutral)

  (:candidate-evidence
    ((:backend :lisa
      :eligible nil
      :reasons (:missing-semantic-profile)
      :descriptor-digest "sha256:...")
     (:backend :swi-prolog
      :eligible t
      :reasons ()
      :descriptor-digest "sha256:...")
     (:backend :n-prolog
      :eligible nil
      :reasons (:missing-semantic-profile)
      :descriptor-digest "sha256:...")))

  (:selected :swi-prolog)
  (:engine-version "...")
  (:engine-build-digest "sha256:...")
  (:adapter-version "...")
  (:adapter-descriptor-digest "sha256:...")
  (:package-digest "sha256:...")
  (:fact-mapping-digest "sha256:...")
  (:compiler-version "..."))
#+end_src

The exact wire/schema representation remains implementation work. The important research requirements are the information classes and their immutability boundary.

Before materialization, =:selected= and exact engine/build fields may be absent. Such a plan is not executable.

After materialization, the record is immutable for that run plan.

* Why-Selected Evidence

The compiler must retain enough evidence to answer:

#+begin_quote
Why was this backend selected?
#+end_quote

without rerunning selection.

At minimum retain:

- effective requested policy;
- source span and lexical scope that produced it;
- inherited policy chain or a digest plus sufficient human-readable origin records;
- selection-policy ID/version and digest;
- required semantic profile;
- required capabilities;
- portability category;
- every considered backend descriptor identity;
- eligibility outcome for each candidate;
- stable rejection reasons;
- exact selected backend;
- adapter descriptor/version;
- engine build/version;
- package and fact-mapping digests;
- compiler version;
- benchmark record identity when benchmark-backed routing affected selection.

Do not include ambient worker load, answer contents, or transient runtime health as backend-selection reasons because those are not legal selection inputs.

A why-selected query should be a projection over the immutable run plan, not a second invocation of =select-logic-backend=.

* Portability Categories

The source/compiler should distinguish portability from backend selection.

Initial categories:

** =:backend-neutral=

The program depends only on a named Star-Logic semantic profile and portable StarLang constructs. It contains no engine-specific semantic dependency.

A backend-neutral program may temporarily have only one compatible implementation. Lack of a second implementation does not make the source engine-specific.

** =:portable-prolog=

The program stays inside the conformance-tested Prolog subset intentionally shared by SWI-Prolog and N-Prolog.

This is narrower than “valid Prolog text” and narrower than either engine's full feature set.

** =:swi-specific=

The program/package depends on SWI-specific semantics or extensions outside the portable profile, such as a semantic feature whose contract is implemented only by the SWI adapter.

** =:n-prolog-specific=

The program/package depends on N-Prolog-specific behavior or an N-Prolog package outside the shared portable profile.

** =:lisa-specific=

The program/package depends on LISA production-rule semantics or features not defined by a backend-neutral profile shared with another backend.

*Technically emulatable does not mean semantically portable.*

A translator that can produce similar data is not evidence that agenda ordering, negation, tabled recursion, working-memory updates, proof structure, uncertainty behavior, or failure semantics are equivalent.

** Selection and portability are independent axes

Pinning a =:backend-neutral= operation to =:swi-prolog= does not make the source =:swi-specific=.

Likewise an =:swi-specific= package may request =:auto=; =:auto= can still deterministically select only SWI-Prolog if every other descriptor is rejected by the semantic requirements.

The compiler should therefore record both the portability category and the requested/selected backend.

* Interaction With Macros

STAR-LANG-RESEARCH-020 proposes hygienic, deterministic source expansion before semantic compilation.

Backend pragmas must preserve source provenance through expansion. A macro that introduces or propagates a backend pragma therefore needs an origin chain showing whether the directive came from the use site, macro definition, or generated syntax.

The backend-policy record should retain the effective directive's source/origin identity after expansion.

A macro must not make backend selection depend on filesystem state, network state, runtime load, or arbitrary host execution. Macro expansion and backend materialization remain deterministic compiler phases.

* Rejected Alternatives

** Nim punctuation

Rejected:

#+begin_example
{. backend: swi-prolog .}
#+end_example

The semantics of compiler directives are useful inspiration; the punctuation is foreign to StarLang's Lisp-family source model.

** =(:backend ...)= as an equivalent selector

Rejected as a second spelling. It makes compiler policy indistinguishable from ordinary declaration metadata and creates two equivalent forms whose precedence and transformation rules could diverge.

Ordinary metadata may contain a field named =:backend= in another data contract if that contract needs it, but such data is not the StarLang compiler backend directive.

** Host Common Lisp =declare= or =declaim=

Rejected as the direct =.star= source mechanism. StarLang is parsed by its closed reader; host Common Lisp declarations would couple the source language to host reader/compiler behavior and blur the implementation boundary.

Their scope semantics remain useful research precedent.

** Last-one-wins directives

Rejected because order-sensitive duplicate policy is easy to hide during refactoring or macro expansion. Duplicate backend pragmas in one scope are compile errors.

** Unconditional operation-overrides-session precedence

Rejected because an operation inside a stateful expert session may share mutable engine state. Lexical specificity chooses the requested policy only after the compiler proves the boundary is safe.

** Runtime engine failover

Rejected because changing from LISA to SWI-Prolog or from SWI-Prolog to N-Prolog after timeout/failure changes the materialized execution contract and invalidates deterministic replay.

** Approximate cross-engine translation

Rejected. A mechanically translatable program is not necessarily semantically equivalent. Exact profile compatibility and conformance evidence dominate convenience and performance.

* Implementation Implications

After approval and after the owning compiler packages are ready, implementation should:

1. add =pragma= to the closed StarLang grammar as a compiler-only directive form;
2. validate the =:backend= directive against exactly the four initial policies;
3. collect pragmas into lexical compiler environments after macro expansion;
4. retain directive source spans and macro origin chains;
5. reject duplicate and misplaced backend directives;
6. normalize project/module/actor/expert/reason policy inheritance;
7. mark state-sharing boundaries that forbid cross-backend child overrides;
8. derive semantic profiles before backend acceptance;
9. delegate concrete descriptor/capability truth to the =star-logic= runtime contracts researched in 021/022;
10. materialize a closed backend-policy evidence record;
11. include that record in plan hashing/replay identity;
12. expose a diagnostic/explain projection that answers why a backend was selected from the stored plan;
13. add conformance fixtures for precedence, incompatibility, unsafe stateful overrides, deterministic =:auto=, and no-runtime-switch behavior.

Do not implement backend selection by scanning raw property lists at runtime.

* Required Conformance Fixtures

At minimum:

1. project =:auto= + no source override selects one deterministic compatible backend;
2. module =:swi-prolog= overrides project =:auto=;
3. actor =:swi-prolog= overrides module =:auto= for actor-owned independent reason calls;
4. expert-system =:lisa= overrides actor/module defaults for the whole expert session when compatible;
5. reason =:swi-prolog= overrides an inherited default for an isolated reason operation;
6. reason =:lisa= + =:tabled-recursion= fails with =STAR.LOGIC.BACKEND-INCOMPATIBLE=;
7. expert-system =:swi-prolog= + =:production-agenda= fails unless the selected SWI descriptor truthfully claims that exact profile;
8. stateful LISA expert session + nested SWI reason sharing session state fails with =STAR.LOGIC.BACKEND-OVERRIDE-UNSAFE=;
9. child =:auto= cannot escape the same stateful-session restriction;
10. duplicate backend pragmas in one scope fail;
11. backend pragma after ordinary body forms fails as misplaced;
12. unknown policy fails before materialization;
13. =:auto= produces the same selected backend and why-selected evidence for identical compiler inputs;
14. =:auto= does not choose N-Prolog because a selected/preferred SWI worker is unavailable at runtime;
15. materialized replay never reruns backend selection;
16. pinning backend-neutral source to SWI preserves portability classification =:backend-neutral=;
17. an SWI-specific package under =:auto= filters incompatible backends before ranking.

* Acceptance Criteria

This research is ready for approval only when reviewers accept all of the following:

1. StarLang source backend selection has one universal spelling: =(pragma :backend <policy>)=.
2. The initial policy vocabulary is exactly =:auto=, =:lisa=, =:swi-prolog=, and =:n-prolog=.
3. =(:backend ...)= is not an equivalent compiler-selector syntax.
4. Project/compiler default, module/file, actor, expert-system, and reason scopes have deterministic inheritance.
5. Precedence follows lexical specificity rather than an ambiguous actor-versus-expert fixed tier.
6. A more specific request is rejected when crossing a backend boundary would alter shared state semantics.
7. Explicit backend pins never bypass semantic-profile, package, proof, limit, isolation, or fact-mapping compatibility checks.
8. =:auto= selects once from explicit versioned capability data during compilation/plan materialization.
9. Runtime load, engine availability, timeout, and returned answers do not change engine type.
10. Materialized plans pin one exact backend/build/adapter contract.
11. The compiler retains sufficient immutable evidence to explain why the backend was selected without rerunning selection.
12. Portability uses =:backend-neutral=, =:portable-prolog=, =:swi-specific=, =:n-prolog-specific=, and =:lisa-specific= as distinct research categories.
13. Portability classification is independent from the requested or selected backend.
14. STAR-LANG-RESEARCH-022 remains runtime/adapter/capability authority.
15. This node becomes source backend-selection authority.
16. STAR-LANG-RESEARCH-023 remains =REVIEW= and is not otherwise approved or substantially redesigned by this work.

* Result

StarLang should adopt a compiler-owned, Lisp-native backend directive:

#+begin_src lisp
(pragma :backend :auto)
#+end_src

with the same form accepting =:lisa=, =:swi-prolog=, and =:n-prolog=.

The directive participates in deterministic lexical policy inheritance from project/module through actor or expert-system owners down to individual reason operations. More-specific policy is not absolute authority: stateful semantic boundaries can reject an otherwise higher-precedence override.

Backend compatibility is checked against exact semantic requirements before selection. =:auto= performs deterministic capability-based selection once, records the exact choice and elimination evidence, and freezes the backend into the executable plan. Runtime failure does not reopen selection.

The result is one coherent source-language mechanism without Nim punctuation, without duplicate metadata syntax, and without giving engine selection permission to change program meaning.

* Footnotes and Glossary

- *Backend directive* — Compiler-only StarLang source form =(pragma :backend ...)= that contributes backend policy to a lexical compilation scope and is not executed at runtime.
- *Backend policy* — Requested selection mode or explicit engine pin before concrete materialization.
- *Backend descriptor* — Versioned adapter-owned record of exact semantic profiles, capabilities, limits, isolation properties, and build identity; runtime authority remains STAR-LANG-RESEARCH-022.
- *Lexical specificity* — Rule that the nearest enclosing valid policy request is considered before an outer default, subject to semantic-boundary safety.
- *Materialized plan* — Immutable executable plan whose backend, adapter/build identities, packages, mappings, limits, and selection evidence have been resolved.
- *Semantic profile* — Versioned contract defining observable inference behavior independently from native engine APIs.
- *Stateful expert session* — Expert-system execution whose working memory, agenda, tables, questions, uncertainty state, or justification state persists across operations.
- *Why-selected evidence* — Immutable compiler record of the policy chain, semantic requirements, candidate filtering, selection-policy identity, and exact selected backend sufficient to explain the result without rerunning selection.
- *Portability category* — Compiler/package classification describing which semantic contracts a program relies on; independent from which compatible backend is requested or selected.
