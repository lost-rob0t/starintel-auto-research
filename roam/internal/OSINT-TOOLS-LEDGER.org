* Purpose

Track every retained OSINT tool encountered during StarIntel feature research before research conclusions are promoted into ARARD/ARADR documents.

This ledger is tool-centric for research traceability. Architecture decisions remain domain-server-centric. Provider names mentioned inside a tool's feature surface do not automatically become separate StarIntel components.

For every retained tool record:

- deeply enumerate the actual feature surface
- identify the smallest reusable capability set rather than cloning the product
- map those capabilities into an existing or proposed OSINT domain-server cluster
- prefer implementation in StarLang
- if StarLang cannot express a required primitive, record the missing language/runtime capability so StarLang can be extended
- use Common Lisp when the capability genuinely belongs below the StarLang surface or needs a Lisp library/adapter
- use Python only when StarLang plus Common Lisp cannot reasonably implement or wrap the required dependency
- preserve provenance, confidence, failure states, rate limits, and partial results
- do not create one actor per upstream feature or provider

* Implementation Preference

1. StarLang
2. Extend StarLang where the required semantic/runtime primitive is missing
3. Common Lisp library or adapter
4. Python only as a last-resort external process boundary

* Domain-Server Rule

Tools do not define architecture boundaries. Related capabilities are grouped into coherent domain servers. Providers and algorithms live behind capability contracts inside those servers.

** RESEARCHING Maigret

- Repository :: https://github.com/soxoj/maigret
- Primary cluster :: identity intelligence
- Domain server :: Identity Domain Server
- Research issue :: #160
- Architectural decision hypothesis :: use as the strongest reference for registry-driven username enumeration and recursive identity pivots; do not embed the Python package by default

*** Deep feature surface

**** Platform registry

- supports 3,000+ sites
- ranked default scan over a high-value subset with full-scan option
- tags for categories and countries
- remote site-database refresh with local fallback
- custom/extensible site definitions
- request URL templates and site-specific existence logic

**** Enumeration

- username-only starting point
- concurrent checks across many sites
- account-existence classification
- support for ordinary web, Tor, and I2P targets
- domain checking in addition to username checking
- handling for blocks, censorship, CAPTCHA, 403s, and timeouts
- proxy-oriented operating model

**** Profile extraction

- fetch profile pages and site APIs after a hit
- extract account-owner metadata
- extract linked accounts and identifiers
- keyword matching in discovered pages
- derive new usernames/IDs from findings

**** Recursive investigation

- recursively search newly discovered usernames and identifiers
- create a graph of pivots and discovered accounts
- prevent the initial enumeration from being the terminal result

**** Scope and ranking

- site ranking by traffic/popularity
- category/country tag filters
- run all sites or bounded top-site subsets
- multiple usernames per invocation

**** Reports and machine output

- HTML report
- PDF report
- XMind report
- NDJSON / simple JSON
- CSV
- text
- interactive D3 graph
- Neo4j Cypher export with idempotent re-import behavior

**** Embedding and UX

- CLI
- Python library API
- web interface
- graph browsing
- optional AI-generated investigation summary

*** What StarIntel needs

- one versioned platform-probe registry
- one typed =identity.enumerateAccounts= capability with strategy fields rather than Maigret-specific code paths
- recursive identity pivots as bounded StarLang workflow semantics
- account metadata extraction as a follow-up capability, not mixed into the existence test contract
- tags/ranking to let the planner choose fast, regional, category-specific, or exhaustive sweeps
- explicit blocked/unknown outcomes rather than silently treating network defenses as not-found
- graph relations with per-probe provenance

*** StarLang implications

- registry-driven dynamic fan-out
- bounded recursion with visited-set/cycle control
- per-probe deadlines
- proxy/adapter selection metadata
- typed =found/notFound/blocked/unknown/partial= result states
- post-hit pipeline activation

** RESEARCHING Holehe

- Repository :: https://github.com/megadose/holehe
- Primary cluster :: identity intelligence
- Domain server :: Identity Domain Server
- Research issue :: #161
- Architectural decision hypothesis :: copy the account-existence technique family, not the Python module layout

*** Deep feature surface

**** Service probing

- checks whether an email is registered on 120+ services
- uses multiple public account flows depending on provider: registration, login, password recovery, or another provider-specific check
- aims to avoid triggering a notification to the target address
- each service is its own provider-specific probe module

**** Result model

- service name
- explicit rate-limit flag
- boolean existence signal
- partially obfuscated recovery email when exposed
- partially obfuscated recovery phone number when exposed
- provider-specific extra fields

**** Execution model

- asynchronous networking
- reusable HTTP client
- embeddable module functions as well as CLI
- provider table documents the probe method and known frequent rate-limit behavior

**** Provider drift risk

- techniques depend on public login/register/recovery flows
- provider endpoints and response semantics can change independently
- rate limits are service-specific
- some outcomes expose only partial recovery hints

*** What StarIntel needs

- =identity.emailAccountPresence= as a provider-registry strategy under =identity.enrichEmail=
- provider probe type =register/login/recovery/other=
- explicit =exists/notExists/ambiguous/rateLimited/blocked/error= outcome
- recovery hints stored as observations with provenance, never promoted directly to confirmed identity
- health/drift monitoring because these probes are unusually fragile
- do not reproduce modules whose workflow would notify or modify the target account

*** StarLang implications

- provider-specific request/response strategy declarations
- secret-safe evidence capture/redaction
- rate-limit state
- policy flag forbidding side-effectful probes
- health tests for provider drift

- Primary cluster :: Google identity and public asset pivots
- Domain server :: Identity Domain Server, with cross-domain geolocation/asset calls
- Research issue :: #161
- Architectural decision hypothesis :: reproduce/publicly wrap individual Google pivots behind typed capabilities; do not make GHunt itself the domain boundary

*** Deep feature surface

**** Authentication/session support

- authenticated Google-session workflow
- browser companion for login/cookie acquisition
- listener mode
- base64 cookie import
- manual cookie entry
- session state required for some Google surfaces

**** Identity modules

- email-address lookup
- Gaia ID lookup
- conversion/pivot between Google identity identifiers where available
- structured JSON export

**** Google Drive investigation

- inspect public/shared Drive file or folder targets
- treat Drive identifiers as investigation pivots

**** Geolocation

- BSSID geolocation capability
- outputs suitable for structured JSON processing

**** Digital Asset Links discovery

- =spiderdal= mode for discovering assets using Google's Digital Asset Links ecosystem
- links web/app assets rather than treating identity lookup as the only Google capability

**** Integration

- CLI module dispatch
- fully asynchronous implementation
- Python library embedding
- JSON output

*** What StarIntel needs

- typed Google identity provider capabilities behind =identity.findPublicProfiles= / =identity.enrichEmail=

** RESEARCHING IntelOwl

- Repository :: https://github.com/intelowlproject/IntelOwl
- Primary cluster :: analysis orchestration and threat enrichment
- Domain server :: Investigation/Analysis Domain Server with source-specific calls to other domains
- Research issue :: #164
- Architectural decision hypothesis :: use IntelOwl as a reference for artifact/job/playbook/pivot lifecycle, not as a dependency

*** Deep feature surface

**** Artifact model

- files and observables are reusable artifacts
- the same artifact can be analyzed multiple times
- analysis is a job/request rather than mutation of the artifact itself

**** Plugin classes

- analyzers retrieve external intelligence or run local analysis tools
- connectors export results to external platforms
- pivots trigger/chains follow-up analysis
- visualizers present analyzer/playbook-specific results
- ingestors automatically turn incoming streams into jobs
- playbooks package repeatable combinations of plugins
- data models normalize heterogeneous analyzer output
- user events attach analyst evaluation/context

**** Analysis coverage

- IP/domain/URL/hash observable enrichment
- file analysis
- Office/RTF/PDF metadata/static analysis
- PE/ELF/APK analysis
- strings/deobfuscation
- YARA/ClamAV
- emulation/capability extraction
- JavaScript analysis
- Android analysis
- SPF/DMARC validation
- PCAP analysis
- honeyclients/browser analysis
- scanners
- numerous external threat-intelligence services

**** Playbooks and pivots

- repeatable shared analysis sequences
- predefined playbooks for free analyzers, static analysis, URL/IP reputation, DNS, and operational response flows
- pivots connect analyses instead of forcing operators to manually re-enter results

**** Ingestors and automation

- continuous/periodic IOC ingestion
- each ingested item can create a job through an attached playbook
- automation runs under service/robot identities
- permissions/config ownership matter for automated runs

**** Investigation/analyst layer

- investigations group findings
- user events capture analyst judgments
- GUI dashboards and visualizers
- collaboration around findings

**** Integration

- REST API
- official client libraries
- connectors to MISP/OpenCTI and other destinations
- scale-out architecture

*** What StarIntel needs

Standardize shared semantics across domain servers:

- target/artifact identity
- immutable or append-only analysis jobs
- declarative playbooks
- pivots / result bindings
- capability selection by input type
- analyst assessment documents
- service identities for automated ingestion
- visualizer declarations for result types
- normalized result envelope without erasing source-native evidence

Do not centralize every analyzer in one server. Investigation/Analysis coordinates capabilities owned by other domain servers.

*** StarLang implications

- first-class playbook/job state
- typed result bindings and pivots
- service identity/capability permissions
- scheduled/stream ingestor triggers
- visualizer metadata in capability manifests
- reusable artifact references and historical analyses
