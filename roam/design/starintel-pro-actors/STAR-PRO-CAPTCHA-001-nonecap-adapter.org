#+title: STAR-PRO-CAPTCHA-001 NoneCap hCaptcha Adapter
#+description: Exact-capability StarIntel Pro Actor design for NoneCap standard, invisible, and Enterprise hCaptcha operations with runtime contract registration and no static unverified capability claims.
#+status: REVIEW
#+filetags: :starintel:design:starintel-pro-actors:captcha:hcaptcha:nonecap:adapter:uml:

* Decision

Implement =NoneCapAdapterActor= as a narrow provider adapter behind [[id:star-captcha-000-broker-router][STAR-CAPTCHA-000]]. It accepts only authenticated broker messages. It has no public solve route, performs no target authorization widening, and never registers reCAPTCHA, Turnstile, FunCaptcha, or other reserved task names.

The actor may register standard, invisible, and Enterprise hCaptcha capabilities independently at runtime only after configuration, official-contract validation, fixture validation, and operator policy establish the declared state.

* Provider Operations

| Broker operation | NoneCap operation |
|------------------+-------------------|
| submit exact solve | =POST /v1/solves?wait=N= |
| poll exact solve | =GET /v1/solves/{id}?wait=N= |
| cancel | =DELETE /v1/solves/{id}= |
| account/balance | =GET /v1/me= |
| report verified outcome | =POST /v1/feedback= under operator policy |
| health snapshot | account probe, recent contract state, and local circuit state |

The configured default base uniform resource locator is =https://api.nonecap.com=. It is deployment configuration, never request-controlled input.

* Request Mapping

| Normalized field | NoneCap field or behavior |
|------------------+---------------------------|
| standard hCaptcha | =type: hcaptcha= with standard context fixture |
| invisible hCaptcha | =type: hcaptcha= with separately validated invisible context |
| Enterprise hCaptcha | =type: hcaptcha_enterprise= |

Reject missing required fields and any issuer, family, variant, version, result kind, mobile, cookie, browser-session, network, proxy, or user-agent requirement not satisfied by the exact registered capability.

* Result Validation

A solved response must contain the exact provider solve identifier, solved state, solution token, and billing/timing fields required by the fixture. Unknown additive fields may be ignored. Missing required fields or an unexpected result kind moves only the affected capability to =invalidContract=.

The token is written to the ephemeral secret store with result kind, binding, expiry, request ID, attempt ID, and authorized source-reader metadata. The actor returns only =resultRef= and non-sensitive provider/job/cost/timing metadata.

* Adapter Sequence

#+begin_src plantuml
@startuml
participant "CaptchaRunActor" as Run
participant "NoneCapAdapterActor" as Adapter
participant "EphemeralSecretStoreActor" as Secrets
participant "NoneCap API" as API

Run -> Adapter : captchaProviderSubmit(exact capability, challengeRef)
Adapter -> Adapter : verify runtime registration and deadline
Adapter -> Secrets : read bounded challenge, proxy, and credential refs
Adapter -> API : POST /v1/solves?wait=N
alt solve id returned
  API --> Adapter : pending/solving/terminal + id
  loop while pending and before deadline
    Adapter -> API : GET /v1/solves/{id}?wait=N
    API --> Adapter : state + solution/error + charge metadata
  end
  alt solved and exact result valid
    Adapter -> Secrets : store token with one-read lease
    Adapter --> Run : captchaProviderSucceeded(resultRef)
  else failed/cancelled/expired/invalid contract
    Adapter --> Run : captchaProviderFailed(normalized failure)
  end
else ambiguous create without solve id
  Adapter --> Run : ambiguousSubmission(chargePossible)
end
@enduml
#+end_src

* Actor State

The actor owns:

- immutable configured base URL;
- provider credential reference;
- configured maximum concurrency;
- runtime capability records and fixture fingerprints;
- active attempts keyed by =attemptId=;
- provider solve identifiers;
- cancellation state;
- polling deadlines;
- circuit and health state;
- redacted latency, result, error, and billing counters.

It owns no durable provider key, proxy credential, Enterprise data, cookie, or result token.

* Idempotency and Ambiguous Create

The adapter journals =attemptId= before the provider request and records the solve identifier immediately after a successful create response. Duplicate local or RabbitMQ deliveries attach to the same attempt or replay its terminal normalized result.

NoneCap does not document a create idempotency key. A transport failure without a solve identifier enters =ambiguousSubmission=. The adapter never recreates the task automatically. It reports =chargePossible= according to observed evidence.

* Cancellation, Feedback, and Shutdown

- Cancellation calls the documented delete operation for an active solve.
- A conflict or already-terminal response triggers one result retrieval and normalized terminal report.
- Duplicate cancellation is idempotent.
- Feedback is sent only when target policy and operator policy allow it and only after downstream verification.
- Shutdown stops new submissions, drains or cancels active solves until a bounded deadline, deletes unconsumed result leases, flushes redacted metadata, and reports unresolved provider identifiers.

* Error Normalization

| Provider condition | Normalized failure |
|--------------------+--------------------|
| invalid request or validation | =providerRejectedRequest=, not retryable |
| unauthorized | =providerAuthenticationFailed=; disable shared credential path |
| insufficient credits | =providerInsufficientBalance= |
| locked or forbidden | =providerDisabled= |
| unknown solve | =providerRejectedRequest= unless retention expiry is proven |
| cancellation conflict | retrieve actual state once |
| concurrency or rate limit | =providerConcurrencyLimited= |
| provider timeout or service error | =providerUnavailable= with bounded retry only when create is unambiguous |
| required result missing or wrong type | =contractDrift= and exact capability =invalidContract= |

Every failure includes =retryable=, =chargePossible=, and a safe redacted provider code.

* Contract Drift and Runtime Registration

At actor start:

1. load configured candidate capabilities;
2. validate configuration and credential reference presence without exposing the credential;
3. load current request/result fixture fingerprints;
4. register each capability with its exact state;
5. omit =unsupported= capabilities from eligible routing while retaining them in audit metadata;
6. update only the affected capability after drift;
7. emit a redacted provider-health/capability event.

A shared authentication or transport outage may mark all capabilities =disabled=. A standard fixture failure does not disable invisible or Enterprise unless the shared failure actually affects them.

The manifest declares actor identity, accepted and produced message types, provider host allowlist, secret classes, implementation entry point, and runtime registration support. It does not advertise unverified active capabilities.

* Security and Secret Handling

Never log, persist, trace, fixture, publish, or place in ordinary actor/RabbitMQ messages:

- bearer key;
- solution token;
- proxy credential;
- Enterprise data;
- cookie or session material;
- authorization header;
- full request or response body containing sensitive fields.

Sanitized fixture values use explicit placeholders. Provider records and cost metadata are redacted before durable storage.

* Quota, Billing, and Health

The adapter exposes configured concurrency, active count, recent exact-capability success/failure, downstream acceptance, circuit state, balance evidence, and provider latency. It does not infer concurrency from marketing.

Budget is reserved before submission. Multi-round hCaptcha costs are reconciled from provider evidence. Cost telemetry distinguishes provider completion from downstream accepted results.

* Tests and Bounded Canaries

- exact standard, invisible, and Enterprise request/result fixtures;
- forbidden capability and context widening;
- every documented state and relevant HTTP condition;
- long-poll deadline calculation;
- duplicate local and RabbitMQ delivery;
- ambiguous create without solve identifier;
- cancellation races and duplicate cancellation;
- account/balance and feedback fixtures;
- capability-local drift and shared outage behavior;
- static manifest contains no active unverified capabilities;
- bearer key, token, proxy, Enterprise data, request, trace, and error redaction;
- shutdown with active solves;
- no paid provider in continuous integration;
- one opt-in, credential-gated, strict-budget canary per capability on an operator-owned system.
