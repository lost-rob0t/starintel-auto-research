* Scope

Re-examine operation and phase semantics as canonical JSON-LD under the ontology foundation [[https://github.com/lost-rob0t/starintel-auto-research/issues/72][#72]] and its gate [[https://github.com/lost-rob0t/starintel-auto-research/issues/219][#219]], so that agent-executable operations, phases, dependencies, target scope, datasets, capabilities, assignments, completion, evidence, and post-actions carry the same semantics in every language without per-language source edits.

This node records the first pass: the 0.9.1 inventory, proposed term positions, the constraint split, and open questions. It does not block StarIntel v0.9, does not make any programming language the ontology authority, does not collapse =target= and =investigation-target=, and does not confuse control-plane roles with real-world entity classes. Foundation positions come from [[file:STAR-RESEARCH-007-starintel-ontology-foundations.org][STAR-RESEARCH-007]] and [[file:../ardr-issues/ARDR-ISSUE-072-starintel-ontology-foundation.org][ARDR-ISSUE-072]]; gate transaction is [[file:../ardr-issues/ARDR-ISSUE-219-operation-ontology-reexamination.org][ARDR-ISSUE-219]].

* Findings

** Operation 0.9.1 inventory

The canonical operation dtype carries 12 data fields: =mission=, =objectives=, =status= (8 states), =in_scope=, =out_of_scope=, =target_policy=, =targets= (roles primary, supporting, derived, excluded), =phases= (at least one, forming a DAG), =datasets=, =capability_gaps=, =assignments=, and =post_actions=. Enum totals: 56 terms across 8 vocabularies — operation status (8), phase state (9), dataset role (6), dataset access (4), capability category (10), capability gap status (7), assignment status (6), post-action status (6). Phase subfields: =phase_id=, =title=, =objective=, =state= (9 states), =depends_on=, =entry_conditions=, =exit_conditions= (CONDITION), phase-local scope, =target_policy=, =target_ids=, =dataset_binding_ids=, =required_capability_ids=, =deliverable_ids=, =completion_evidence=. Dataset bindings carry =binding_id=, =dataset=, =role= (6), =access= (4), =phases=, =purpose=. Capability gaps carry =capability_id=, =category= (10), =description=, =blocking=, =status= (7), =required_by=, =capability_ref=, =resolution_ref=, =owner=. Assignments carry =assignment_id=, =agent_id=, =actor_id=, =phase_ids=, =role=, =status= (6). Post-actions carry =action_id=, =action_type= (free-form), =condition= (CONDITION), =target_ids=, =dataset_binding_ids=, =status= (6), =config=.

** Proposed positions (Proposed, pending operator research approval)

1. *Operation class.* Both ontology class and control-plane profile: a StarIntel-native control-plane Activity/Plan hybrid (star-investigation or star-runtime module; placement is a gate decision), with the schema.org =Action= mapping kept as a transitional drift-guarded =close= mapping and PROV-O =Activity=/=Plan= as structural mappings.
2. *Link model.* Operation =has-phase= Phase (phase_id-keyed named nodes, not a separate dtype in the first slice); =binds= DatasetBinding (role + access); =requires= Capability with blocking gaps hooking the R&D loop via =resolution_ref=; =assigns= Agent/Actor control-plane pairs; =references= Target/InvestigationTarget through roles only, never Entity subclasses; deliverables and =completion_evidence= are Evidence/Document records; =post_actions= are condition-gated follow-up Plans.
3. *PROV reuse matrix.* =prov:Plan=, =prov:Activity=, =prov:used=, =prov:wasGeneratedBy=, =prov:wasAssociatedWith=, and dependency edges are structural mappings; lifecycle states remain StarIntel-native SKOS-style versioned terms with close =schema:ActionStatus= mappings only where they exist. Mapping strengths are recorded per the foundation vocabulary (exact, close, broader, narrower, structural, lossy, unsupported).
4. *Versioning.* Extend the additive expansion-registry pattern (immutable base + versioned expansion + content hash) to version-pinned JSON-LD contexts; 56 enum terms become versioned registry entries with deprecation and migration rules; custom operation ontologies refine via separate pinned contexts with zero per-language edits.
5. *Constraint split.* JSON Schema keeps shapes, required fields, enum membership, and =additionalProperties: false=; cross-reference integrity, DAG acyclicity, scope precedence, and evidence-gated completion become shared Prolog-projectable semantic rules replacing per-language Python-only reimplementations.

* Open Questions

1. What is the canonical =starintel:= context namespace IRI and term-casing convention for the operation context?
2. Does Phase stay an embedded =@id=-addressable node in the first slice or become an independent dtype document, and how does =phase_id= identity survive server revisions?
3. Which of the 8 operation states and 9 phase states earn close =schema:ActionStatus= mappings, and which remain unsupported/native-only?
4. Is =target_policy= a closed vocabulary term, free text, or a policy record, and how does it compose with =excluded= targets?
5. How do assignment =agent_id= and =actor_id= separate control-plane actors from real-world agents (and from =prov:Agent=) without collapsing the classes?
6. What is the authoritative semantics of each dataset role (6) by access (4) pair, and is access an authorization boundary or a provenance qualifier?
7. What closes a capability gap: which evidence proves resolution through =resolution_ref=, and which gap status transitions are legal?
8. Should post-action =action_type= remain free-form with registry-refused unknown types, or become an open enumeration with registered extensions?
9. What shared CONDITION syntax do =entry_conditions=, =exit_conditions=, and post-action =condition= use so they project to Prolog without per-language parsers?
10. Are deliverables and =completion_evidence= star-assertion Evidence records or plain Document references, and who asserts them?
11. Where do version-pinned context content hashes live, and what is the verification procedure for the immutable-base + versioned-expansion pattern?
12. Which of the twelve #219 decisions are ontology semantics versus control-plane profile, and which approval rows do they consume?
13. Which representative operation+phase graph (DAG branches, blocked phase, scope override, gap-blocked completion, post-action) anchors the conformance fixtures?
14. Should the server persist phases embedded in the operation document or as child phase documents, per CouchDB revision and replication behavior?

** Proposed answers (pass 2 — Proposed, pending operator research approval)

1. *Namespace and casing.* The namespace authority is =starintel.actor= (operator-chosen); the canonical context IRI is served under the spec host alongside the schema =@id= =https://spec.starintel.actor/schema/starintel-doc-v0.9.0.json=: base namespace =https://spec.starintel.actor/ns/starintel/operation#,= versioned context document =https://spec.starintel.actor/context/starintel-operation-v0.9.1.jsonld= (content-hash pinned; the operator has offered to stand up the web box at =spec.starintel.actor= to serve immutable contexts). The =starintel:= scheme remains the *identifier* scheme used inside documents (=starintel:operation:<id>=, =starintel:phase:<operation-id>/<phase_id>=) and is declared in the context as a prefix for =https://spec.starintel.actor/id/=. Casing: PascalCase for classes (=Operation=, =Phase=, =DatasetBinding=, =CapabilityGap=, =Assignment=, =PostAction=), lowerCamelCase for properties (=operationStatus=, =dependsOnPhase=), matching the mapping skeleton in [[file:../ardr-issues/ARDR-ISSUE-219-operation-ontology-reexamination.org][ARDR-ISSUE-219]].

   *Multi-consumer implication (end users may redefine and ship their own specs).* StarIntel has multiple consumers beyond the operator (star-cl, starintel-server, gpt-auto-dig, emacs client, actors, plus the conformance-matrix runtimes python/js/cl/nim). Two rules follow. First, =starintel.actor= is the *publication host*, never the semantic authority: every consumer resolves terms by *content hash* (the lock pattern: =schema/starintel-schema.lock.json= pins canonical commit + =expansion_content_hash=; contexts get the same treatment per answer 11), so a domain outage, ownership transfer, or policy change cannot silently change meaning for any consumer. Consumers are never required to fetch live from the domain: pins in their own locks suffice, mirrors (including a GitHub Pages mirror of =spec.starintel.actor=) are legitimate, and domain continuity is a recorded migration concern (a domain move is a content-preserving, hash-preserving lossless rebind under the #72 migration rule — to be avoided by keeping publication stable). Second — stronger than extension — end users must be able to *redefine* base semantics and ship their own specs. The context model therefore carries an explicit, governed override layer instead of a closed base: resolution order is =end-user override context= → =registered expansion context= → =base canonical context=, with the base authoritative for every term an override does not touch. Overrides are first-class artifacts under the same discipline as everything else: version-pinned, content-hashed, carrying a declared redefinition record naming the redefined terms, the base version they pin against, and a mapping-strength label per the #72 strength vocabulary for each override. They load through the same registry machinery so runtimes consume them with zero per-language source changes (the server#151 creatable/loadable/extensible/versionable requirement); an override that does not declare its base commit + content hash is not loadable, so silent divergence from the base is structurally impossible; runtimes reject unpinned overrides fail-closed. Redefined =starintel:*= terms are recorded as declared conflicts with the pinned base version, keeping provenance of who redefined what.
2. *Phase addressing.* Embedded =@id=-addressable node in the first slice per issue server#151's non-goal (=phase= stays out of the dtype registry). Semantic identity is =phase_id= scoped by operation identity, never the CouchDB revision: =@id= =starintel:phase:<operation-id>/<phase_id>= survives every server revision. If phases later become independent documents, the migration is =@id= rebinding from fragment-scoped to absolute IRIs with =phase_id= unchanged — the lossless path #72 requires.
3. *schema:ActionStatus mappings.* schema.org defines only =PotentialActionStatus=, =ActiveActionStatus=, =CompletedActionStatus=, =FailedActionStatus=. Proposed =close= mappings: operation =planned→PotentialActionStatus=, =active→ActiveActionStatus=, =completed→CompletedActionStatus=, =aborted→FailedActionStatus=; phase =planned= and =ready→PotentialActionStatus=, =active→ActiveActionStatus=, =completed→CompletedActionStatus=, =failed→FailedActionStatus=. Native-only (no analog, strength =unsupported=): operation =draft=, =blocked=, =suspended=, =archived=; phase =blocked=, =awaiting-review=, =skipped=, =aborted= (aborted and failed are distinguished: aborted is operator-initiated, failed is condition-initiated, so =aborted→FailedActionStatus= is only recorded for operations; phases keep =aborted= native-only).
4. *target_policy.* A structured policy record, not free text: the canonical subfields =allowed_dtypes=, =allowed_target_types=, =allowed_roles=, =selectors= become the =starintel:targetPolicy= node; =allowed_dtypes= and =allowed_target_types= reference the versioned dtype/type registries (never arbitrary strings); =selectors= remain structured selector records (kind + expression, sharing the CONDITION grammar, question 9). Composition with =excluded=: exclusion always wins with deny precedence — evaluation order is =excluded targets= → operation =out_of_scope= → phase policy → phase-local =in_scope=. The role set {primary, supporting, derived, excluded} is a closed structural vocabulary.
5. *agent_id vs actor_id.* =agent_id= names the control-plane executor (a star-runtime Actor instance that runs phases); =actor_id= names the accountable principal that is credited and reviewed. Neither is a real-world class: =prov:Agent= is a structural *export* mapping of the assignment edge only (=prov:wasAssociatedWith=); real-world =star-core= Person/Organization remain referenced by actor records, never by assignments. The ontology rule: an assignment asserts control-plane responsibility; any real-world identity resolution happens through the actor record's own links to =star-core= Person/Organization.
6. *Dataset role × access semantics.* =access= is a declared *authorization boundary* for the operation's runtime during the bound phases (an intent the server's existing lease/quota/ACL machinery enforces); =role= is the *provenance/purpose qualifier* recording why the dataset is bound. Actual access events are provenance assertions, never inferred from the binding. Proposed authoritative matrix (role → intended access ceiling): =collection→read=, =working→read-write=, =derived→append=, =publication→read=, =reference→read=, =archive→append= (write-once). A binding declaring access above its role's ceiling is a semantic rule violation (registry rule package, question 9's rule home).
7. *Capability gap closure.* =resolution_ref= must resolve to an existing, dtype-valid resolution record (R&D/design work, dataset, schema update, or actor provisioning) that itself asserts availability. =gapStatus= transition to =available= or =resolved= requires exactly that record; legal transitions (Proposed): =required→planned|missing=, =missing→planned=, =planned→in-progress=, =in-progress→available=, =available→resolved=, =waived= from any non-terminal state; =resolved= and =waived= are terminal; no backward transitions. The blocking completion gate (question: gap-blocked phases) reads only =blocking: true= and non-terminal status.
8. *action_type.* Open enumeration with registered extensions: the ten issue#151 action types become the base vocabulary, extensions are added through versioned expansion contexts (the registry pattern), and unknown types are registry-refused. Transitional tolerance for v0.9: the structural schema keeps =action_type= free-form (already canonical), the shared semantic rule records unregistered types; strict mode rejects them. This keeps v0.9 unblocked while giving the registry the authority.
9. *CONDITION syntax.* Structure, not text: =condition= records project to Prolog facts directly from structured fields (=kind=, =predicate=, =subject=, =object=, =expression=). =kind= becomes a closed versioned vocabulary (dataset-bound, phase-state, capability-available, target-in-scope, time-window, external-ref — proposed); =expression=, where needed, is a canonical JSON-serialized s-expression term, so every language consumes the structure with zero parsing. Free-text expressions are transitional-tolerant and rejected in strict mode.
10. *Deliverables and evidence.* =deliverable_ids= reference Document/Artifact records (=prov:Entity=, =prov:wasGeneratedBy= the phase — structural mapping); =completion_evidence= references star-assertion *Evidence* records — qualified assertions carrying asserted-by, observed/valid/recorded time, and confidence per #72 — asserted by the operator or assigned actor completing the phase. =evidence_resolves/2= requires the referenced assertion to exist, validate, and be non-retracted.
11. *Context hashes and verification.* Content hashes live in the server schema lock (=schema/starintel-schema.lock.json=, which already carries =expansion_content_hash=; extend with =context_content_hash=) and in the canonical repo manifest. Verification procedure = the existing checker pattern: =scripts/check-starintel-schema-lock.py= recomputes canonical content and fails closed on mismatch; conformance fixtures pin the context per release. =spec.starintel.actor= serves the immutable artifacts (operator-provided web box).
12. *Decision-to-approval mapping.* All twelve #219 decisions consume the Research conclusion row first. Ontology-semantics decisions (2 phase addressing, 3 identity/relations, 4 PROV boundary, 5 state vocabularies, 9 capability semantics, 10 post-actions, 11 constraint split, 12 versioning) additionally consume the Design row. Control-plane profile decisions (1 class/profile split, 6 dependency semantics, 7 scope precedence, 8 dataset surfaces) are profile-level and consume Research + Design only; no decision consumes the Implementation row before its design evidence exists.
13. *Representative fixture graph.* A "three-phase blocked-research" operation: phases A, B (parallel branch) converge on phase C; C is also blocked by a blocking capability gap; phase A carries an in-scope item that the operation's =out_of_scope= overrides; dataset bindings include one =working/read-write= and one =derived/append= pair; operation completion triggers a condition-gated =generate-report= post-action. This single graph exercises DAG convergence, blocking, scope precedence, gap closure, and post-actions — every predicate and every semantic rule at once.
14. *Phase persistence.* Embedded in the operation document for the first slice: the operation document is the unit of CouchDB revisioning/replication, phases carry no independent ACL surface yet, and =phase_id= (question 2) preserves identity across revisions. Child phase documents are the recorded follow-up, justified when phases need independent ACLs or lifecycle; migration rebinds =@id= fragment-scoped to absolute without touching =phase_id=.

* Footnotes and Glossary

- *Operation re-examination gate* :: The issue 219 acceptance test: the nine Prolog predicates must project from canonical JSON-LD without bespoke per-language semantics.
- *Qualified assertion* :: A fact-like record carrying provenance, evidence, temporal context, confidence, and assertion status, per the #72 foundation.
- *DatasetBinding* :: The role- and access-qualified binding of a dataset to an operation, referenced by phases and post-actions through =binding_id=.
- *Capability gap* :: A recorded missing capability with a blocking flag and a =resolution_ref= that hooks the gap into the R&D loop.
- *CONDITION* :: The canonical condition term used by =exit_conditions= and post-action =condition= fields; its shared projectable syntax is an open question.
- *Expansion-registry pattern* :: The repository's pin-and-extend precedent: immutable base plus versioned expansion plus content hash, applied additively since v0.9.
- *Constraint split* :: The division of validation labor: structural rules in JSON Schema, cross-document semantic rules in shared Prolog-projectable packages.
