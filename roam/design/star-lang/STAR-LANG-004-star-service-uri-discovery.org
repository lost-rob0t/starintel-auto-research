#+title: STAR-LANG-004 STAR Service URI Discovery and Dispatch
#+description: Define transport-neutral star:// service identity, manifest declaration, runtime discovery, and dispatch semantics for StarLang actors.
#+status: APPROVED

* Decision

StarLang SHALL support canonical actor/service identities of the form:

#+begin_example
star://domain:address:actor-name
#+end_example

Examples:

#+begin_example
star://quasar:localhost:user-hunt
star://bbp:localhost:nmap
#+end_example

The URI names a logical STAR actor/service. It does not select HTTP, RabbitMQ,
Sento remoting, ZeroMQ, or any other transport.

The language/runtime split is:

#+begin_example
StarLang source / portable manifest
        |
        v
canonical STAR service URI
        |
        v
runtime directory / registry resolution
        |
        v
actor descriptor or actor reference
        |
        v
transport/runtime-specific dispatch
#+end_example

* Research audit

This design reuses existing StarLang research rather than reopening settled
runtime questions.

- [[file:../../research/star-lang/STAR-LANG-RESEARCH-011-deterministic-dispatcher.org][STAR-LANG-RESEARCH-011 Deterministic Dispatcher]] already defines standalone dispatch.
- [[file:../../research/star-lang/STAR-LANG-RESEARCH-012-transport-port-and-settlement.org][STAR-LANG-RESEARCH-012 Transport Port and Settlement]] already separates dispatch semantics from transport settlement.
- [[file:../../research/star-lang/STAR-LANG-RESEARCH-013-cl-gserver-runtime-facade.org][STAR-LANG-RESEARCH-013 Optional cl-gserver Runtime Adapter]] already defines optional runtime topology discovery and liveness snapshots.
- [[file:../../research/star-lang/STAR-LANG-RESEARCH-014-bbp-tool-domain-remoting.org][STAR-LANG-RESEARCH-014 BBP Tool Domain Remoting]] already proves cross-domain actor routing.
- [[file:../../research/star-lang/STAR-LANG-RESEARCH-015-runtime-endpoint-materialization.org][STAR-LANG-RESEARCH-015 Runtime Endpoint Materialization]] already establishes that deployment coordinates are runtime material, not language identity.
- [[file:STAR-LANG-002-durable-actor-runtime.org][STAR-LANG-002 Durable Actor Runtime]] already defines runtime actor references, capability ownership, and runtime portability boundaries.

Therefore the missing design surface is naming, manifest representation,
resolution, and dispatch integration.

* URI grammar

Initial grammar is intentionally strict:

#+begin_example
star-uri    = "star://" domain ":" address ":" actor-name
domain      = token
address     = token
actor-name  = token
token       = 1*( lower-alpha / digit / "-" / "_" / "." )
#+end_example

Initial implementation rules:

- scheme is exactly =star://=;
- domain, address, and actor-name are non-empty;
- canonical tokens are lowercase ASCII;
- colon is reserved as the component separator;
- no query string, fragment, credentials, or implicit default component exists in v1;
- IPv6 literals are not represented directly in v1 because colon is reserved;
- future URI revisions may add escaping or structured authorities without changing the v1 parser.

Canonicalization is identity preserving: valid input already has one canonical
string representation.

* Component semantics

** domain

A logical STAR application or actor namespace, for example =quasar= or =bbp=.
It is not necessarily a DNS domain and does not imply process ownership.

** address

A logical runtime location selector. =localhost= means the local host/runtime
scope. Other values may later identify configured runtime nodes. Address does
not itself encode a transport.

** actor-name

The stable logical actor/service name declared by the StarLang actor contract.
Examples include =user-hunt= and =nmap=.

* Manifest model

Actor manifests may declare an optional canonical service URI.

#+begin_src lisp
(actor user-hunt
  (:runtime native
   :service-uri "star://quasar:localhost:user-hunt"
   :accepts (username-search)
   :produces (username-search-result)
   :handler user-hunt-handler
   :restart permanent
   :mailbox (bounded 256)))
#+end_src

The compiled actor IR and portable manifest record =:service-uri= as data.
The manifest does not contain a live Sento actor cell, socket, queue, or host
object.

A service URI declared on an actor MUST have an actor-name component equal to
the actor contract name. This prevents one manifest entry from claiming another
actor's logical identity.

* Static manifest versus runtime registration

These are distinct concepts.

Manifest declaration:

#+begin_example
star://quasar:localhost:user-hunt
  actor = user-hunt
  capabilities = username-search
#+end_example

Runtime observation:

#+begin_example
star://quasar:localhost:user-hunt
  runtime = cl-gserver
  alive = true
  ref = runtime-specific reference
#+end_example

The manifest answers what service exists. The runtime directory answers which
service instance is currently reachable.

* Runtime directory extension

The existing optional runtime-directory port remains the discovery boundary.
Directory entries MAY include:

#+begin_src lisp
(:name "user-hunt"
 :service-uri "star://quasar:localhost:user-hunt"
 :domain "quasar"
 :address "localhost"
 :runtime :cl-gserver
 :alive t
 :capabilities ("username-search")
 :ref <opaque-runtime-reference>)
#+end_src

The generic StarLang layer validates portable metadata but treats =:ref= as an
opaque runtime value. Final extracted packages may split portable descriptor
fields from implementation-private references.

No second competing registry is required for the first implementation. A
concrete Sento/cl-gserver adapter may source the directory snapshot from
=all-actors=, =find-actors=, and running state. Other registry backends can later
implement the same runtime-directory port.

* Resolution

Resolution of a canonical STAR URI is exact.

#+begin_example
parse URI
  -> validate canonical components
  -> obtain runtime-directory snapshot
  -> find exact :service-uri match
  -> require alive != nil
  -> return normalized runtime entry
#+end_example

If a legacy directory entry lacks =:service-uri=, no implicit cross-domain
mapping is performed. Compatibility mapping may be added only as an explicit
adapter policy.

Typed failures distinguish:

- malformed service URI;
- service not registered;
- service registered but stopped;
- duplicate service registrations;
- manifest/service actor-name mismatch.

* Deterministic standalone dispatch

Standalone deterministic execution remains valid without a runtime directory.
A command may target either the actor name or the actor's declared STAR service
URI.

For a STAR URI target, deterministic dispatch performs manifest-only resolution:

#+begin_example
command :actor = star://quasar:localhost:user-hunt
  -> parse URI
  -> find manifest actor whose :service-uri exactly matches
  -> dispatch through the already registered deterministic handler
#+end_example

It does not pretend to perform network discovery. This gives deterministic tests
the same logical addressing model without requiring cl-gserver.

* Runtime dispatch

Runtime-backed execution may use the directory before selecting a concrete
runtime transport.

#+begin_example
star://bbp:localhost:nmap
  -> runtime-directory resolve
  -> runtime descriptor
  -> selected runtime adapter
  -> tell / dispatch / remote transport
#+end_example

The STAR URI remains unchanged if the implementation moves from same-process
Sento to another local process or future remote transport.

* Wire semantics

Existing message envelopes keep =:actor= as a string. A canonical =star://=
service URI is therefore a valid actor destination without introducing a second
recipient field in protocol v1.

The sender/recipient logical identity should remain the STAR URI at system
boundaries. Runtime adapters may internally map the URI to an actor name or
opaque reference.

* Capabilities

Capabilities remain manifest metadata, not URI syntax. Do not add capability
selectors to the URI.

Future discovery may support:

#+begin_src lisp
(find-services directory :domain "quasar" :capability "username-search")
#+end_src

and then return one or more canonical STAR URIs.

* Relationship to runtime endpoint materialization

=STAR-LANG-RESEARCH-015= uses runtime-neutral Sento endpoint templates such as
=sento://dynamic/user/bbp-domain=. STAR service identity is a higher layer.

Example:

#+begin_example
logical identity:
  star://bbp:localhost:nmap

resolved runtime descriptor:
  runtime = sento
  endpoint = sento://worker.internal:4912/user/nmap
#+end_example

The compiled STAR URI stays stable while runtime coordinates change.

* API design

Prototype Common Lisp API:

#+begin_src lisp
(parse-star-service-uri "star://quasar:localhost:user-hunt")
(star-service-uri-string uri)
(resolve-star-service-uri directory context uri)
#+end_src

The URI object exposes domain, address, and actor-name accessors.

The first implementation deliberately does not add global mutable registry
state. Discovery is injected through the existing runtime-directory port.

* Initial implementation slice

Implement in =lost-rob0t/star-lang= prototype ownership:

1. strict STAR service URI parser and canonical formatter;
2. optional =:service-uri= actor contract field;
3. portable manifest emission of service identity;
4. runtime-directory validation for service metadata;
5. exact URI resolution over runtime-directory snapshots;
6. deterministic dispatcher routing to manifest-declared service URIs;
7. tests covering Quasar UserHunt and BBP nmap examples;
8. no transport-specific code in the URI module.

* Deferred work

Not part of the first implementation:

- query parameters or URI version selectors;
- IPv6 authority encoding;
- distributed registry consensus;
- DNS-SD, Consul, Kubernetes, or mDNS discovery;
- global mutable process registry;
- automatic cross-domain trust;
- remote authentication or mTLS policy;
- Quasar registry UI;
- starintel-server gateway implementation.

Those belong to later service-discovery and server-dispatch work.

* Acceptance

The slice is conformant when:

1. both example URIs parse and round-trip canonically;
2. malformed/noncanonical URIs fail with stable typed conditions;
3. an actor manifest may declare exactly one service URI;
4. actor-name mismatch is rejected;
5. the portable manifest retains the URI without runtime objects;
6. runtime-directory resolution returns the exact live entry;
7. stopped and missing entries are distinguishable;
8. deterministic dispatch can address a handler through the declared URI;
9. actor-name dispatch remains backward compatible;
10. all existing prototype tests remain green.
