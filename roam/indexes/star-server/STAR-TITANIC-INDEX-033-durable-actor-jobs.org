* Purpose

This stack revives the 2023 StarIntel =Titanic= concept as a modern durable actor-job protocol while preserving the project's already-approved ZeroMQ boundary for language-independent and cross-process actors.

The historical design was already recognizably descended from ZeroMQ's Titanic Service Protocol: persistent asynchronous request submission, worker dispatch, retained results, and later client retrieval. The recovered diagram also separated the broker, Titanic persistence, and the router socket. The modern design keeps those responsibilities separate.

Sento remains the local actor runtime. Star Router remains the client/application routing layer. ZeroMQ is the canonical cross-language actor-job transport. Titanic owns durable job meaning and persistence. RabbitMQ remains the existing broker for document/event traffic and may be used as an adapter or internal scheduling aid without becoming the public worker protocol.

* V1 Required Semantics

1. stable =job_id= and idempotency scope;
2. durable admission before submit acknowledgement;
3. durable job/attempt journal;
4. capability registration and worker capacity over ZeroMQ;
5. ROUTER/DEALER dispatch to heterogeneous workers;
6. at-least-once logical execution with explicit terminal outcomes;
7. typed terminal results and disconnected result lookup;
8. bounded retry with backoff and dead-lettering;
9. cooperative cancellation and absolute deadlines;
10. target lease/fencing integration where manifests require exclusive authority;
11. deterministic fake/model contract tests before transport implementation promotion;
12. byte-level interoperability tests across Common Lisp, Nim, Python, and JavaScript/TypeScript.

* Explicit Non-Goals

- replacing Sento local actor mailboxes;
- forcing every actor language to implement AMQP or NATS;
- making RabbitMQ delivery tags stable actor-protocol identity;
- introducing JetStream as a planned StarIntel transport without a new explicit requirement;
- promising exactly-once execution;
- putting every high-frequency local actor message through durable storage;
- exposing LMDB or another journal backend through the worker protocol;
- introducing Temporal or Kafka merely to implement a job queue.

* Suggested Next Design Pass

After review, create a design node covering only the v1 seam:

- =star.titanic/1= durable job envelope;
- ZeroMQ worker envelope and ROUTER/DEALER framing;
- Common Lisp transport implementation using the approved SENTO-ZMQ strategy;
- Nim, Python, and JavaScript conformance peers;
- =job-store= interface plus deterministic fake;
- LMDB versus SQLite/local-store spike for the first embedded journal;
- one capability-class worker pilot;
- result/status/cancel/close API;
- contract tests from STAR-RESEARCH-036 and STAR-RESEARCH-037.

Do not start by generalizing every actor or backend.
