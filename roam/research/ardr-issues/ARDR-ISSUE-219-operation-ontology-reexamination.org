* Research Seed

Express agent-executable operations, phases, phase dependencies, target scope, datasets, capabilities, assignments, completion, evidence, and post-actions in canonical JSON-LD so that every language consumes the same semantics without per-language source edits. The gate accepts the re-examination when the nine Prolog predicates =currentPhase=, =phaseRunnable=, =phaseBlockedBy=, =validTarget=, =allowedDataset=, =phaseComplete=, =nextPhase=, =operationComplete=, and =capabilityMissing= can be projected from canonical JSON-LD without bespoke per-language semantics.

The gate requires twelve recorded decisions and eight deliverables. Non-goals: do not block StarIntel v0.9; do not make any programming language the ontology authority; do not collapse =target= and =investigation-target=; do not confuse control-plane roles with real-world entity classes.

*** Gate question positions (Proposed, pending operator research approval)

**** Q1: Operation as ontology class, control-plane profile, or both

Proposed: both. Operation is a StarIntel-native control-plane class — an Activity/Plan hybrid — placed in the =star-investigation= or =star-runtime= module (module placement is one of the twelve gate decisions) and exposed as a control-plane profile over the qualified assertion model. The schema.org =Action= mapping recorded in =DTYPE_SCHEMA_ORG_TYPES= is a transitional, drift-guarded =close= mapping enforced by server and canonical tests, not a schema-enforced class boundary. PROV-O =Activity= and =Plan= provide structural mappings. Operation and Phase are not yet in any #72 module; this transaction tracks their admission.

**** Q2: Link model across Operation, Phase, Target, Dataset, Capability, agents, deliverables, evidence

Proposed link model (role-qualified references, never Entity subclasses):

- Operation =has-phase= Phase. Phases are independently addressable named nodes keyed by =phase_id= (for example =starintel:phase:<phase_id>=) but are not a separate dtype in the first slice.
- Operation =binds= DatasetBinding with =role= and =access=; bindings are what phases and post-actions reference.
- Operation =requires= Capability; blocking capability gaps hook the R&D loop through =resolution_ref=.
- Operation =assigns= Agent/Actor pairs; assignment is a control-plane relation and must not reclassify the assignee as a real-world Agent class.
- Operation and Phase =reference= Target/InvestigationTarget through roles only, preserving the #72 rule that Target is a workflow designation, not an Entity subclass, and preserving the target/investigation-target distinction.
- Deliverables and =completion_evidence= are Evidence/Document records linked to phases.
- =post_actions= are condition-gated follow-up Plans emitted on completion or failure conditions.

**** Q3: PROV-O reuse versus StarIntel-native terms

Proposed reuse matrix:

| Operation concern | PROV-O term | Reuse verdict |
|---+---+---|
| operation as plan | =prov:Plan= | structural mapping |
| phase execution | =prov:Activity= | structural mapping |
| operation execution | =prov:Activity= | structural mapping |
| dataset binding as input | =prov:used= | structural mapping |
| deliverables and evidence | =prov:Entity=, =prov:wasGeneratedBy= | structural mapping |
| assignment of agents | =prov:wasAssociatedWith= | structural mapping |
| phase dependency | =prov:wasInformedBy= | broader; native =dependsOnPhase= preferred |
| lifecycle states (8 op, 9 phase) | none | StarIntel-native, SKOS-style versioned terms |
| scope, target roles, post-action conditions | none | StarIntel-native; lossy or unsupported in PROV-O |

Lifecycle states stay StarIntel-native versioned terms with =close= mappings to schema.org =ActionStatus= only where a state genuinely corresponds; all mapping strengths follow the #72 strength vocabulary (exact, close, broader, narrower, structural, lossy, unsupported).

**** Q4: Versioning of state vocabularies and custom operation ontologies

Proposed: extend the repository's additive expansion-registry pattern — immutable base plus versioned expansion plus content hash — to version-pinned JSON-LD contexts. The 56 enum terms become versioned registry entries carrying definition, ontology version introduced, deprecation rule, and migration rule, mirroring the #72 predicate-registry record. Custom operation ontologies refine semantics through separate pinned expansion contexts rather than editing the base context, so no per-language source change is required when a vocabulary evolves. Unpinned contexts are rejected because contexts can conceal semantic changes.

**** Q5: Constraint split between ontology semantics and structural validation

Proposed split. JSON Schema retains document shapes: required fields, field types, enum membership (the 56 terms), and =additionalProperties: false=. Cross-document semantics move to shared, Prolog-projectable rules replacing the per-language Python-only reimplementation in =operation_spec.py= lines 282-376:

- unique identifiers across all id-bearing collections;
- all cross-references resolve (=target_ids=, =dataset_binding_ids=, =required_capability_ids=, =deliverable_ids=, =depends_on=, =phase_ids=, =required_by=);
- phase DAG is acyclic with no self-dependencies;
- operation =out_of_scope= overrides phase =in_scope=;
- a completed phase requires =completion_evidence=;
- operation =completed= implies every phase =completed= or =skipped=.

See STAR-RESEARCH-064 for the full constraint-split inventory and the Prolog projection sketches for the nine acceptance predicates.

*** Nine-predicate Prolog projection sketches

Project canonical operation JSON-LD into facts, then define the acceptance predicates over the shared semantic rules. Facts and helpers (for example =phase_before/3= over the DAG, =entry_conditions_held/2=, =access_grants/3=, =evidence_resolves/2=, =phase_terminal/2= where terminal means completed or skipped) are the Prolog-projectable semantics; no per-language reimplementation is permitted. Sketches only — normative rules pending research approval:

#+begin_src prolog
current_phase(Op, Phase) :-
    phase(Op, Phase),
    phase_state(Op, Phase, State),
    State \= completed, State \= skipped,
    \+ (phase(Op, Earlier), Earlier \= Phase, phase_before(Op, Earlier, Phase)).

phase_blocked_by(Op, Phase, Dependency) :-
    depends_on(Op, Phase, Dependency),
    phase_state(Op, Dependency, State),
    State \= completed, State \= skipped.

phase_runnable(Op, Phase) :-
    phase(Op, Phase),
    \+ phase_blocked_by(Op, Phase, _),
    entry_conditions_held(Op, Phase).

valid_target(Op, Phase, Target) :-
    target_role(Op, Target, Role),
    Role \= excluded,
    \+ out_of_scope(Op, Target),
    target_policy_holds(Op, Phase, Target).

allowed_dataset(Op, Phase, Binding, Access) :-
    phase_binding(Op, Phase, Binding),
    binding_access(Op, Binding, Access),
    access_grants(Op, Access, Binding).

phase_complete(Op, Phase) :-
    phase_state(Op, Phase, completed),
    phase_evidence(Op, Phase, Evidence),
    evidence_resolves(Op, Evidence).

next_phase(Op, Current, Next) :-
    phase_state(Op, Current, completed),
    depends_on(Op, Next, Current),
    phase_runnable(Op, Next),
    Next \= Current.

operation_complete(Op) :-
    \+ (phase(Op, Phase), \+ phase_terminal(Op, Phase)).

capability_missing(Op, Capability) :-
    gap(Op, Capability),
    gap_blocking(Op, Capability, true),
    gap_status(Op, Capability, GapStatus),
    \+ member(GapStatus, [available, resolved, waived]).
#+end_src

The =capability_missing= closure filters the canonical 7-state gap-status vocabulary (=required, missing, planned, in-progress, available, resolved, waived=): only gaps whose resolution has not landed remain missing. Signature order follows issue server#151's predicate list; refining =valid_target=, =allowed_dataset=, and =next_phase= to their issue arities is part of the normative pass.

* Footnotes and Glossary

- *Operation re-examination gate* :: The issue 219 acceptance test: the nine Prolog predicates must project from canonical JSON-LD without bespoke per-language semantics.
- *Control-plane profile* :: An ontology view describing StarIntel's own execution control objects (operations, phases, assignments) without promoting them to real-world entity classes.
- *DatasetBinding* :: The role- and access-qualified binding of a dataset to an operation, referenced by phases and post-actions through =binding_id=.
- *Capability gap* :: A recorded missing capability with a blocking flag and a =resolution_ref= that hooks the gap into the R&D loop.
- *CONDITION* :: The canonical condition term used by =exit_conditions= and post-action =condition= fields; its shared projectable syntax is an open gate question.
- *Expansion-registry pattern* :: The repository's established pin-and-extend precedent: immutable base plus versioned expansion plus content hash, applied additively since v0.9.
- *Issue transaction* :: The durable Org record pairing one research issue with its passes and canonical research outputs.
