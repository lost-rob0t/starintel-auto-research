* Normative Status

This document defines the StarIntel-specific verification design that consumes Star-Lang specifications and runtime contracts.

The words MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, and MAY are normative.

The design does *not* create a second dispatcher, actor runtime, message lifecycle, persistence stack, or proof database.

The one-authority rule applies:

- =star-lang= owns reusable Star-Lang verification semantics and certificate formats;
- =starintel-server= owns StarIntel domain-specific ingest policy and domain invariants;
- the existing actor runtime owns actor execution;
- the existing transport adapter owns broker settlement;
- the existing artifact/provenance layer owns retained verification artifacts.

A verification component observes or checks those authorities. It MUST NOT duplicate them.

* Required Guarantees

The first StarIntel verification profile SHALL expose four independently testable guarantees.

** G1 — Document conformance

A document accepted into a verified domain dataset MUST have passed:

- bounded canonical decoding;
- exact schema lookup in the pinned specification bundle;
- field/type validation;
- relation predicate validation where applicable;
- StarIntel dataset/case/provenance rules;
- domain-specific invariant checks; and
- canonical subject hashing.

This guarantee means the document is valid under the declared StarIntel contract. It does not mean the real-world claim is true.

** G2 — Actor protocol conformance

A StarIntel actor MUST receive only messages accepted by its pinned actor manifest and MUST emit only replies/events allowed by that manifest.

Protocol verification MUST happen before handler invocation for input and before publication for output.

** G3 — Poison termination

A delivery classified as terminal poison MUST leave the active processing path exactly once and MUST NOT be automatically requeued into that path under the same verification context.

It may be dead-lettered, quarantined, or discarded by explicit policy, but the terminal disposition must be recorded.

** G4 — Protocol deadlock/livelock control

StarIntel MUST structurally prevent blocking actor-to-actor request cycles at the Star-Lang level and MUST verify the declared topology for remaining blocking dependencies and protocol progress.

The guarantee is scoped to declared Star-Lang actor, mailbox, request, timeout, cancellation, retry, supervision, and port semantics. Arbitrary unmodeled Common Lisp or foreign-library locking is outside the claim.

* Canonical Verification Certificate

All verification results use one portable artifact envelope.

#+begin_src json
{
  "schema": "star.verify.certificate/1",
  "certificateId": "verify_01",
  "class": "checked-conformance",
  "claim": "star.document.valid-for-domain",
  "subjectType": "org.starintel/core@1/person",
  "subjectHash": "sha256:...",
  "specificationDigest": "sha256:...",
  "planDigest": "sha256:...",
  "verifier": "star.document.verify/1",
  "verifierVersion": "1.0.0",
  "assumptions": [],
  "bounds": {},
  "evidence": ["sha256:..."],
  "result": "valid"
}
#+end_src

Required classes:

- =evidence=;
- =checked-conformance=;
- =lifecycle-verified=;
- =model-checked=;
- =solver-certificate=;
- =theorem-artifact=.

A certificate MUST state a specific claim. Generic fields such as =proved: true= are forbidden.

The certificate semantic identity includes the claim, subject hash, specification/plan digest, verifier identity/version, assumptions, bounds, evidence hashes, and result.

Wall-clock storage metadata MAY be attached outside the semantic identity.

* Document Verification Contract

The reusable document verifier accepts only immutable data:

#+begin_example
verify-document(
  canonical-document,
  schema-id,
  locked-specification-graph,
  domain-validation-profile)
    -> valid certificate | structured violations
#+end_example

Required generic checks:

1. canonical parse succeeded within configured bounds;
2. schema identity is exact and exists in the locked graph;
3. no implicit schema version fallback occurred;
4. required and optional field rules hold;
5. scalar and collection bounds hold;
6. closed schemas reject undeclared fields;
7. canonical field naming rules hold;
8. relation documents use =source=, =predicate=, and =destination=;
9. predicate source/destination schema contracts hold;
10. canonical serialization produces the claimed subject hash.

StarIntel domain validation then checks policy that is intentionally not generic Star-Lang semantics, for example:

- required provenance for persisted investigative records;
- dataset/case boundary;
- source-document references;
- immutable source-document identity;
- domain-specific cross-field constraints;
- target or investigation policy;
- any approved ontology invariant.

Failure returns a closed machine-readable violation set. Host-language stack traces are diagnostics, not protocol errors.

* Actor Manifest Contract

Every deployable actor authority has one immutable protocol manifest.

Required fields:

#+begin_example
actorId
actorGenerationPolicy
starVersion
specificationDigest
acceptedCommands
acceptedEvents
emittedReplies
emittedEvents
requiredCapabilities
idempotencyPolicy
deadlinePolicy
cancellationPolicy
blockingPortDeclarations
protocolFixtureDigest
adapterVersion
#+end_example

A native actor and an external actor use the same semantic manifest.

Generated Python/TypeScript bindings MAY expose the types, but the StarIntel runtime does not trust generated client code to self-validate.

** Input rule

Before enqueue/handler invocation:

#+begin_example
envelope valid
AND route resolves exactly one actor authority
AND messageType belongs to actor.acceptedCommands/events
AND payload validates against the pinned specification digest
AND capability/case policy passes
#+end_example

Otherwise the handler is not invoked.

** Output rule

Before transport publication:

#+begin_example
reply/event kind valid
AND causation/correlation valid
AND output messageType is declared by actor manifest
AND payload validates
#+end_example

An invalid actor output is an actor/runtime fault. It is not converted into a successful reply.

* Ingest State Machine

The authoritative StarIntel ingest operation uses the following semantic states:

#+begin_example
received
  -> envelope-validated
  -> route-validated
  -> payload-validated
  -> domain-validated
  -> dedupe-checked
  -> persisted
  -> indexed
  -> completed
#+end_example

Terminal alternatives:

#+begin_example
received/... -> quarantined-poison
received/... -> terminal-rejected
received/... -> cancelled
received/... -> deadline-exceeded
#+end_example

Retryable alternatives:

#+begin_example
... -> retryable-infrastructure-failure -> scheduled-redelivery
... -> publication-recovery
#+end_example

The distinction between poison and infrastructure failure is mandatory.

* Poison Classification

Terminal poison codes include at minimum:

- =star.poison.malformed-envelope=;
- =star.poison.unsupported-version=;
- =star.poison.unknown-route=;
- =star.poison.actor-message-mismatch=;
- =star.poison.invalid-document=;
- =star.poison.invalid-relation=;
- =star.poison.domain-invariant=;
- =star.poison.case-boundary=;
- =star.poison.capability-denied=.

Retryable infrastructure codes are separate, including storage unavailable, transport publication unavailable, temporary backend unavailable, and lease contention when policy allows retry.

A deterministic validation failure MUST NOT be relabeled retryable merely because the caller asks for another attempt.

* Poison Terminal Disposition

The transport-neutral invariant is:

#+begin_example
terminal-poison -> terminal-settlement
#+end_example

Allowed terminal settlements:

1. =reject-with-dead-letter=;
2. =reject-and-discard= under explicit policy;
3. =quarantine-then-ack= for transports without native dead-letter support.

Forbidden transition:

#+begin_example
terminal-poison -> requeue-original-active-path
#+end_example

The quarantine destination MUST NOT automatically route to the originating active ingest queue.

If the quarantine persistence path itself is unavailable, the consumer SHOULD stop or apply bounded infrastructure recovery rather than convert the poison delivery into an unbounded active-queue loop.

* Poison Disposition Artifact

A terminal poison event records:

The artifact need not duplicate sensitive payload bytes.

* Split-Phase Ask Semantics

StarIntel MUST NOT implement Star-Lang actor asks as synchronous waits that occupy the actor's only mailbox execution slot.

The semantic form is:

#+begin_example
handler receives command
  -> send request to actor B
  -> record continuation + deadline
  -> return control to mailbox
  -> later receive reply/error/cancel/deadline event
  -> resume continuation
#+end_example

This is the default compiled behavior for Star-Lang =ask=.

An adapter may internally use futures/promises, but observable semantics must remain split-phase.

A direct host-language blocking call from inside an actor handler is outside the verified actor protocol unless declared as a blocking port.

* Blocking Port Declarations

Every potentially blocking non-actor dependency used by a verified actor must be declared in the plan/manifest.

Example:

#+begin_src lisp
(:blockingPort
 :name "couchdb-write"
 :class "storage"
 :maximumWaitMs 5000
 :holdsActorMailbox nil
 :resourceScope "dataset")
#+end_src

Required fields:

- stable port identity;
- blocking class;
- finite maximum wait/deadline;
- whether actor mailbox progress is held;
- resource scope/lock scope if any;
- cancellation behavior.

Production verification rejects =maximumWait=infinity= for inter-authority waits.

* Static Wait-For Verification

Build/promotion verification constructs a directed graph containing all hard waits that can simultaneously hold progress.

Nodes may include:

- actor authorities;
- domain servers;
- storage transaction scopes;
- foreign-runtime leases;
- explicitly modeled external services.

Edges are created only for blocking waits. Asynchronous messages do not create wait edges.

A simple hard cycle is rejected:

#+begin_example
A waits B
B waits C
C waits A
#+end_example

If a design needs a state-dependent cycle that is safe because edges cannot coexist, it must be proven by the protocol model instead of waived informally.

* Protocol Model Checking

The compiler/deployment planner should emit a finite verification model from the immutable plan.

The model includes:

- actor states relevant to request progress;
- bounded mailbox contents by message class;
- correlation/request states;
- split-phase asks;
- replies/errors;
- cancellation;
- deadlines;
- bounded retry policy;
- poison terminal settlement;
- stop/restart behavior relevant to an in-flight request;
- declared blocking ports.

Required properties:

1. no unexpected message transition;
2. no reachable permanent actor wait cycle;
3. terminal poison never returns to active processing;
4. retry budget never increases unexpectedly;
5. every accepted command reaches terminal, explicit deferred, or bounded retry state under declared fairness assumptions;
6. cancellation cannot strand a permanently held request when the target remains reachable;
7. restart does not create two simultaneous authorities for the same actor generation;
8. message correlation/causation remains well formed.

A model-check artifact MUST record:

- plan digest;
- model generator version;
- model source hash;
- actor count/topology;
- mailbox abstraction bound;
- retry bound;
- data-domain abstraction;
- fairness assumptions;
- checker/version;
- result;
- counterexample hash when failed.

A bounded model result is labeled =model-checked=. It is never labeled an unrestricted theorem.

* Deadlock-Freedom Promotion Gate

A verified StarIntel ingest topology may be promoted only when:

1. all Star-Lang actor asks use split-phase semantics;
2. every blocking port is declared with finite deadline;
3. static hard wait-for graph is acyclic;
4. protocol model passes configured deadlock/livelock properties;
5. all actor manifests bind exact specification digests;
6. negative protocol fixtures demonstrate mismatched messages are rejected before handler invocation.

An unmodeled blocking primitive in the Star-Lang execution path invalidates the deadlock certificate until modeled or removed.

* Domain Ingest Concurrency Rules

To keep the proof surface tractable:

- a domain server owns its bounded domain state and indexes;
- one document ingest operation may use one local storage transaction boundary;
- a domain ingest transaction MUST NOT hold a local storage lock while synchronously waiting on another actor/domain server;
- cross-domain changes use messages/outbox semantics, not distributed lock chains;
- actor-to-actor coordination is asynchronous and correlation-based;
- all external waits have deadlines;
- retries preserve idempotency keys;
- terminal outcomes are journaled before the transport input is finally settled when required by the existing lifecycle design.

* Idempotency and Crash Recovery

Verification does not replace the lifecycle/outbox design.

The sequence remains:

#+begin_example
receive
 -> verify
 -> execute/persist
 -> retain deterministic outcome
 -> retain required publication cursor
 -> publish outcomes
 -> settle input
#+end_example

On redelivery after a crash:

- a terminal idempotency record suppresses duplicate domain mutation;
- retained publication state resumes output publication;
- a terminal poison disposition suppresses reclassification into active work;
- certificates are referenced by stable subject/event hashes and may be reused only when every semantic input digest matches.

* Supervision Rules

Actor crashes are not automatically poison messages.

A supervisor MAY restart an actor according to its declared restart policy. The delivery remains governed by the lifecycle retry/idempotency rules.

A message becomes terminal poison only when a deterministic verifier/policy says the message cannot be processed under the pinned contract.

Restart intensity must be bounded. Repeated actor crashes caused by the same payload may trigger a circuit-breaker or operator review, but payload-triggered crash classification is not inferred solely from the crash count without a deterministic validation rule.

* Verification Artifact Storage

Verification artifacts use the existing =star-artifact= authority.

The ingest/document row stores only stable references where appropriate:

#+begin_example
verificationCertificateHash
poisonDispositionHash
modelCertificateHash
#+end_example

This avoids creating a parallel proof database.

Artifacts inherit StarIntel access-control, provenance, retention, and dataset/case policies.

* Runtime API Surface

The minimal reusable verification protocol should resemble:

#+begin_src lisp
(verify-document document schema spec-graph &key profile)
(verify-envelope envelope protocol-manifest)
(verify-actor-input actor-manifest envelope)
(verify-actor-output actor-manifest envelope)
(verify-lifecycle-transition prior event next)
(classify-poison delivery verification-failure policy)
(verify-wait-graph topology)
(verify-certificate certificate)
#+end_src

These are semantic operations. Their final Common Lisp package/function names may differ, but there must be one authoritative implementation for each behavior.

* StarIntel Domain Ingest Example

A people domain receives:

#+begin_src lisp
(command "starintel.people/ingest@1"
  :payload person-document
  :actor "people-domain")
#+end_src

Required flow:

1. envelope verifies against =star.protocol=;
2. =people-domain= manifest accepts =starintel.people/ingest@1=;
3. payload declares a pinned Person schema;
4. generic document verifier checks schema and canonical hash;
5. StarIntel domain verifier checks provenance/dataset invariants;
6. idempotency scope is checked;
7. domain server persists the document;
8. indexes are updated through the domain authority;
9. document verification certificate is attached by hash;
10. typed reply and completion acknowledgement are validated;
11. lifecycle output publishes;
12. transport input settles.

If step 4 deterministically fails, steps 6-9 never run. The delivery receives terminal poison disposition and leaves the active queue.

If persistence in step 7 is temporarily unavailable, the message is not poison; normal retry/backoff rules apply.

* Required Negative Tests

The conformance suite MUST include failures, not only happy-path certificates.

1. malformed envelope cannot reach an actor handler;
2. actor A cannot receive a command declared only for actor B;
3. valid JSON with wrong Star-Lang message type is rejected;
4. document with unknown schema version is rejected;
5. relation with invalid predicate endpoints is rejected;
6. domain-invariant violation is terminal poison;
7. terminal poison is never requeued to the originating active queue;
8. quarantine route bound back to the active route fails deployment validation;
9. actor output with undeclared reply type fails before publish;
10. synchronous A->B->A blocking wait fails static verification;
11. split-phase A->B->A request flow does not create a hard wait-cycle edge;
12. =infinity= blocking deadline fails production verification;
13. bounded retry exhaustion reaches terminal state;
14. duplicate command does not repeat persistence side effects;
15. restart preserves generation and correlation semantics;
16. model-check failure emits a counterexample artifact and blocks promotion;
17. certificate subject hash mismatch invalidates the certificate;
18. certificate against the wrong specification digest invalidates the certificate.

* Acceptance Criteria

This design is implementable when all of the following are true:

1. one canonical =star.verify.certificate/1= schema exists;
2. document verification is deterministic over document bytes + spec digest + profile;
3. actor manifests explicitly enumerate accepted/emitted message contracts;
4. dispatcher checks actor input contracts before invocation;
5. actor outputs are checked before publication;
6. terminal poison has a one-way disposition;
7. active and quarantine routing cannot form an automatic cycle;
8. infrastructure failures remain distinct from poison;
9. Star-Lang asks are split-phase;
10. hard blocking waits are explicit and finite;
11. build-time wait graph rejects simple hard cycles;
12. deployment can emit a bounded protocol model;
13. model-check results include bounds/assumptions;
14. no new dispatcher/runtime/lifecycle authority is introduced;
15. verification artifacts use existing artifact/provenance ownership;
16. end-to-end tests prove a domain ingest server accepts valid documents, rejects invalid ones, removes poison, and does not block its mailbox on actor asks.

* Implementation Slices

The recommended dependency order is:

** Slice 1 — Certificate and claim vocabulary

Freeze =star.verify.certificate/1=, claim identifiers, result classes, and hash identity rules. No runtime behavior changes.

** Slice 2 — Pure document and actor manifest checkers

Extract/reuse existing schema and actor-message validation so one implementation owns each check. Add certificate emission as a caller-side wrapper, not a duplicate validator.

** Slice 3 — Poison classification and terminal disposition contract

Define the deterministic poison classification boundary and adapt the existing transport =reject= settlement to persist/emit terminal disposition evidence.

** Slice 4 — Split-phase ask

Make the runtime-facing Star-Lang =ask= contract release mailbox execution while awaiting reply/error/deadline/cancel. Remove or quarantine any synchronous actor-wait path from verified Star-Lang execution.

** Slice 5 — Static wait graph

Compile declared blocking dependencies and reject hard cycles/infinite waits.

** Slice 6 — Model generator and promotion gate

Generate the bounded protocol model from the immutable plan and run the selected model checker in CI/promotion, recording a =model-checked= certificate.

** Slice 7 — StarIntel domain ingest integration

Wire the generic verification layer into one StarIntel domain ingest server end to end, then expand domain by domain without creating a second ingest framework.

After every slice, exactly one implementation owns the behavior.

* Non-Goals

This design does not:

- prove that OSINT claims are factually true;
- prove arbitrary Common Lisp or foreign code cannot deadlock;
- introduce a replacement actor runtime;
- introduce a replacement dispatcher;
- introduce a second retry or acknowledgement lifecycle;
- require theorem proving for ordinary document ingest;
- require runtime TLA+ or SMT calls on every message;
- promise distributed exactly-once execution;
- require one actor per document;
- replace StarIntel provenance, corroboration, or analytical confidence models.

* Decision

StarIntel should make verification a first-class property of the existing Star-Lang actor/domain-ingest path.

The practical architecture is:

- verify every document against an immutable specification and StarIntel domain profile;
- verify every actor input/output against its pinned message manifest;
- terminate deterministic poison with a one-way quarantine/dead-letter disposition;
- compile actor requests as split-phase operations so mailbox progress is not held by actor-to-actor waits;
- reject undeclared or cyclic blocking dependencies before deployment;
- model-check the finite declared topology for deadlock/livelock properties;
- attach immutable, precisely scoped verification certificates by hash.

This gives StarIntel useful proof-carrying behavior without pretending that explanation traces, schema checks, or bounded model checks are stronger than they are.

* Footnotes and Glossary

- *Proof-carrying ingest* — An ingest path in which accepted or rejected subjects carry immutable, precisely scoped verification evidence by hash.
- *Terminal poison* — A deterministic validation failure whose original delivery is permanently removed from the active processing path by reject/dead-letter/quarantine policy.
- *Split-phase ask* — A Star-Lang actor request that releases the mailbox while waiting and resumes through a reply/error/deadline/cancel continuation.
- *Wait-for graph* — A directed graph whose edges represent hard blocking dependencies that can hold progress simultaneously.
- *Protocol deadlock freedom* — Absence of reachable permanent wait cycles in the declared Star-Lang actor/port abstraction under recorded messaging, timeout, retry, cancellation, and fairness assumptions.
