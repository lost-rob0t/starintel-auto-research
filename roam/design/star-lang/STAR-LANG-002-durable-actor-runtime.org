* REVIEW Objective

Create a reusable StarLang runtime in Common Lisp that can execute the Franklin County actor design and later support other StarIntel domains without embedding Franklin-specific policy.

The runtime must make the safe and correct behavior declarative:

- bounded mailboxes
- explicit overload policy
- supervision strategies
- durable jobs and replay
- immutable revisions
- authority ownership
- lease fencing
- capabilities
- raw artifact commit and durable evidence delivery
- cancellation
- readiness and degradation
- deterministic testing

* REVIEW Repository Boundary

Create a dedicated repository, provisionally =lost-rob0t/star-lang=.

The repository should contain the language, normalized IR, compiler, runtime, reusable ports, conformance suite, examples, and release tooling.

It should not contain:

- Franklin source profiles
- Ohio applicability policy
- county-specific adapters
- StarIntel server configuration
- public website code
- investigation datasets

* REVIEW Compiler Pipeline

1. Parse StarLang source into lossless syntax objects.
2. Resolve imports, packages, schema names, actor names, and authority ownership.
3. Lower to normalized, versioned IR.
4. Validate boundedness, capabilities, dispatcher rules, message revisions, authority writes, and durable-delivery obligations.
5. Compute deterministic manifest and policy hashes.
6. Generate portable Common Lisp forms and ASDF systems.
7. Generate canonical JSON or binary wire bindings where declared.
8. Generate deterministic fake-runtime fixtures.
9. Generate topology, message, capability, dependency, and recovery documentation.
10. Reject builds that contain unbounded external work, ambiguous canonical writers, or artifact workflows without durable downstream delivery.

* REVIEW Normalized IR

The IR must represent:

- domain
- actor, authority, pool, router, port, and workflow declarations
- parent-child supervision
- dispatcher and execution class
- mailbox capacity and overflow policy
- restart strategy and intensity
- state durability class
- owned record types
- accepted and emitted message schemas
- exact schema versions
- capability grants
- source or host scopes where static
- timeout and resource bounds
- cancellation behavior
- readiness dependencies
- health metrics
- adapter and port bindings
- artifact commit, delivery-intent, outbox, acknowledgement, and recovery policy
- implementation constraints
- generated test obligations

IR objects are immutable and content-addressed. A deployment binds an exact IR graph hash.

* REVIEW Static Rejections

The compiler must reject:

- actor without mailbox capacity
- worker without time and resource bounds
- canonical record type with zero or multiple authorities
- network call on control dispatcher
- process execution without process capability
- credential access without named credential capability
- adapter canonical write access
- durable workflow without idempotency key definition
- retry without attempt identity
- lease-bound result without fencing token
- checkpoint without job and attempt revision
- supervisor child without restart classification
- readiness dependency cycle
- wire message with unversioned schema
- mutable manifest or policy reference
- retrieved content used to grant capabilities
- browser or OCR worker with ledger access
- durable artifact commit without a declared delivery-intent or transactional downstream release
- attempt success before its artifact delivery intent is durably recorded
- checkpoint that references an artifact whose required retrieval event or downstream work is neither acknowledged nor explicitly pending

* REVIEW Runtime Systems

** =star-actor-protocol=

Defines IDs, revisions, message envelopes, commands, events, results, checkpoints, lifecycle events, typed failures, cancellation, and wire compatibility.

** =star-sento-compat=

Provides the implementation-neutral actor API over Sento/cl-gserver:

- spawn
- stop
- ask
- tell
- watch
- unwatch
- link
- resolve
- dispatcher selection
- mailbox metrics
- lifecycle hooks

No generated application code calls private Sento APIs directly.

** =star-mailbox=

Required policies:

- =reject=
- =backpressure=
- =drop-newest=
- =drop-oldest=
- =coalesce-by-key=
- =spill-to-durable-journal=
- =quarantine=

Dropping is forbidden for commands that mutate durable state unless the command is represented durably elsewhere and the policy is explicitly declared.

** =star-supervisor=

Strategies:

- one-for-one
- one-for-all
- rest-for-one
- temporary child
- transient child
- permanent child

Owns restart windows, delay and jitter, child generations, startup order, readiness, degradation, terminal stop, and lifecycle events.

** =star-journal=

Storage-neutral interface:

- append event
- create job revision
- claim job
- renew claim
- complete attempt
- append checkpoint
- create evidence-delivery intent
- claim evidence-delivery intent
- acknowledge delivery step
- replay pending delivery intents
- materialize state
- replay range
- compare state hash
- quarantine entry
- compact under policy

Initial backends:

- in-memory deterministic test backend
- SQLite backend
- StarIntel/CouchDB outbox backend after integration tests

** =star-lease=

Owns lease scopes, generations, fencing tokens, expiry, renewals, rate windows, concurrency, circuit breakers, and stale-result rejection.

** =star-capability=

Capabilities are immutable manifest entries and runtime handles. Core capabilities:

- clock
- random
- network read
- DNS read
- TLS metadata read
- artifact stage
- artifact commit
- journal append
- canonical proposal
- authority write
- process execute
- filesystem read/write under declared roots
- credential read by named identifier

Authority-write handles are never issued to adapters.

** =star-artifact=

Artifact lifecycle:

1. allocate staging reference
2. stream bytes while enforcing limits
3. compute hashes
4. extract bounded metadata
5. atomically commit immutable artifact bytes and metadata
6. create or confirm an idempotent evidence-delivery intent keyed by artifact hash, job revision, and attempt revision
7. emit the immutable artifact reference
8. deliver the required retrieval event and downstream work from the intent
9. acknowledge each delivery step idempotently
10. mark the intent complete only after all required steps are durable

If the artifact store and journal share a transactional boundary, steps 5 and 6 commit together. If they do not, the backend must use a durable outbox protocol plus startup and periodic orphan-artifact recovery. A committed artifact without a complete intent is never silently ignored: recovery creates or republishes the intent, or records an explicit quarantine decision.

An attempt cannot report terminal success until the evidence-delivery intent is durable. Runtime readiness remains degraded while committed artifacts are unaccounted for or while required delivery intents cannot be replayed safely.

** =star-adapter-sdk=

Adapters are pure bounded attempts from the runtime's perspective. They receive immutable job/attempt context and capability handles, and return typed results.

** =star-http-port=

Wraps HTTP, URI, TLS, redirect, timeout, streaming, content decoding, and connection-pool behavior.

** =star-process-port=

Uses versioned framed messages over stdin/stdout or local sockets. Owns process groups, CPU/memory/time ceilings where available, cancellation, environment, working directories, stderr, and exit classification.

** =star-health=

Exports structured health events and snapshots without exposing credentials or raw protected content. Health includes pending and oldest evidence-delivery intent, orphan-artifact scan results, replay failures, and quarantine counts.

* REVIEW Actor Reference

A runtime actor reference contains:

#+begin_src lisp
(defstruct star-actor-reference
  domain-id
  logical-path
  node-id
  generation
  protocol-revision
  capability-set-hash)
#+end_src

Messages sent to a superseded generation fail with a typed stale-reference result. They are never silently redirected to a new generation unless a declared logical router performs that action.

* REVIEW Durable Job and Attempt Split

A job identifies logical work and immutable bindings. An attempt identifies one execution under one lease.

#+begin_src lisp
(defstruct star-job-revision
  job-id
  revision
  workflow-id
  domain-revision
  policy-snapshot-revision
  manifest-revisions
  input-revisions
  bounds
  cancellation-id
  idempotency-key)

(defstruct star-attempt
  attempt-id
  job-id
  job-revision
  worker-reference
  adapter-manifest-revision
  lease-id
  lease-generation
  fencing-token
  started-at
  deadline)

(defstruct star-evidence-delivery-intent
  intent-id
  artifact-reference
  artifact-hash
  job-id
  job-revision
  attempt-id
  fencing-token
  required-delivery-steps
  acknowledged-delivery-steps
  state
  created-at
  updated-at)
#+end_src

A retry never mutates the prior attempt. Evidence delivery is idempotent by intent and delivery-step key; retrying delivery does not create a new artifact or authority revision.

* REVIEW Authority Model

An authority is a serialized canonical writer for one or more revisioned record types.

The compiler verifies exclusive ownership. Runtime writes require:

- authority generation
- record logical ID
- expected prior revision or explicit create
- proposed revision hash
- idempotency key
- policy and schema revisions
- supporting event or artifact references where required

Conflicts produce typed results and are resolved through new proposals, not last-writer-wins mutation.

* REVIEW Deterministic Runtime

The conformance runtime supplies:

- virtual clock
- seeded random source
- deterministic dispatcher
- fake network
- fake process port
- in-memory journal
- in-memory artifact store
- programmable failures
- crash points before and after artifact and delivery-intent commits
- lease expiry control
- message reordering and duplication
- orphan-artifact injection
- delivery-intent replay and acknowledgement control
- state-hash snapshots

Every production backend must pass the same semantic suite.

* REVIEW Fault Model

Typed runtime failures include:

- schema unsupported
- capability denied
- mailbox full
- actor stale generation
- actor unavailable
- deadline exceeded
- cancelled
- lease unavailable
- lease expired
- stale fencing token
- journal conflict
- artifact staging failed
- artifact commit failed
- evidence delivery intent failed
- evidence delivery incomplete
- orphan artifact detected
- delivery replay failed
- process crashed
- process protocol invalid
- network timeout
- TLS failure
- parse unsupported
- parse malformed
- result truncated
- checkpoint invalid
- authority conflict
- readiness blocked
- restart budget exhausted

Unknown implementation conditions are converted to =runtime-unclassified= with bounded diagnostics and quarantined until classified.

* REVIEW Portability

Initial production baseline: SBCL on Linux.

The runtime keeps portability boundaries at:

- threads
- monotonic time
- process control
- filesystem atomic operations
- sockets/TLS
- memory/resource measurement
- implementation-specific condition details

A feature is portable only after CI passes on that implementation. Source-level portability without runtime evidence is not sufficient.

* REVIEW Release Units

Each reusable ASDF system has independent semantic versioning. The umbrella =starlang-runtime= release pins compatible versions and publishes one runtime manifest.

Generated Franklin deployments bind:

- StarLang compiler version
- normalized IR version
- runtime umbrella version
- every component ASDF version
- source commit hashes
- implementation and build identifiers
- conformance suite version

* REVIEW Compatibility Policy

- Message schemas are versioned independently from library versions.
- Readers may support multiple prior revisions.
- Writers emit one configured revision.
- Incompatible schema changes require a new schema name or major revision.
- Journal migrations are explicit and replay-tested.
- Evidence-delivery intent schema migrations preserve pending acknowledgements and idempotency keys.
- Actor logical paths remain stable while generations change.
- Runtime upgrades use shadow replay before authority promotion.

* REVIEW Security and Capability Boundary

The runtime is capability-scoped by construction, not by naming convention.

- Network adapters receive scoped network handles.
- Browser workers receive process and restricted network manifests.
- Parsers receive artifact-read handles but no network.
- Normalizers receive artifact and retrieval references but no credentials.
- Review actors receive candidate and evidence references but no mutation handle except review authority proposals.
- Retrieved code, HTML, scripts, documents, and prompts cannot grant capabilities.
- Outbox replay workers receive only the exact delivery capabilities declared by the intent; they cannot expand scope from artifact content.

* REVIEW Observability

Required structured metrics:

- actor generation
- mailbox depth and oldest message age
- rejection/backpressure/drop counts
- durable ready/running/retry/quarantine job counts
- lease utilization and wait time
- restart counts and budgets
- run and attempt latency
- artifact stage/commit lag
- pending evidence-delivery intent count and oldest age
- orphan-artifact count and recovery outcome
- delivery replay and acknowledgement latency
- normalization and review lag
- replay duration
- state-hash divergence
- typed failure counts
- process worker resource use

Metrics are not canonical state and cannot substitute for durable events.

* REVIEW Conformance Gates

1. Duplicate delivery does not duplicate authority state.
2. Crash after journal append replays correctly.
3. Crash after artifact commit but before intent acknowledgement recreates or republishes the delivery intent.
4. Crash after retrieval-event delivery but before normalization release resumes only the missing step.
5. No terminally successful attempt has a missing or non-durable evidence-delivery intent.
6. Orphan-artifact recovery accounts for every committed artifact by completed intent or explicit quarantine.
7. Expired attempts cannot commit through stale fencing tokens.
8. Mailbox overflow follows declared policy.
9. Rest-for-one restarts only the required suffix.
10. Generation-stale references fail explicitly.
11. Cancellation reaches all descendants.
12. Replay produces the same state hash.
13. Shadow runtime replay matches the current runtime before upgrade.
14. Capability-invalid StarLang source fails compilation.
15. Unbounded actor or adapter source fails compilation.
16. Process worker cannot obtain authority-write capability.
17. Unsupported wire revision fails without partial interpretation.
18. Every accepted artifact and record resolves to exact runtime and manifest revisions.

* REVIEW Blockers

- =STAR-RESEARCH-PIPELINE-004= must define the parent revisioned protocol.

* REVIEW Decision

Approve StarLang as the authored actor language and Common Lisp as the host runtime.

Implement the durable actor runtime as independently reusable Common Lisp systems. Treat the Franklin County deployment as the first complete conformance application, not as the place to hide generic runtime logic.
