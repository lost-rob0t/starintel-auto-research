* Research Question

What should =starintel-discord-tool= become if it is used as an operator and trusted-collaborator interface to StarIntel, while preserving StarIntel's existing actor, document, provenance, authorization, and RabbitMQ boundaries?

The requested feature set is:

- implement the Discord edge as a Python bot;
- search the StarIntel database through a gserver-backed interface;
- interact with =starintel-gpt-auto-dig=;
- submit documents through Discord for whitelisted users;
- work in private direct messages;
- allow specially trusted users to add investigation targets;
- notify the submitting user when new documents related to their submission appear;
- configure a Discord channel to receive selected RabbitMQ traffic.

* Verified Current State

** =starintel-discord-tool= is effectively an interface stub

The repository currently contains a minimal README and Nim package metadata. Its README describes the bot as an operations-management interface and lists unimplemented command ideas including =/createOperation=, =/deleteOperation=, =/newDataset=, =/operationAddDataset=, =createTarget=, =/deleteTarget=, =/jobs=, =/search=, and =/debug=.

There is no existing production bot architecture to preserve. This is a favorable point to define the trust boundary before commands become coupled directly to storage or broker internals.

The operator has now selected Python for the bot implementation. The existing Nim metadata is therefore historical repository state rather than the intended runtime. The implementation pass should replace or retire the Nim edge scaffolding instead of treating it as a second supported bot implementation.

** Auto-Dig is Git-backed and CLI-oriented

The current Auto-Dig repository defines canonical normalized documents under =db/<dtype>/<_id>.ndjson= and packet-oriented output under =digs/<target>/<run>/starintel-documents.jsonl=. Its documented command surface includes typed schema inspection, search, recursive target selection, corpus validation, and canonical import/write paths.

The repository instructions explicitly forbid ad hoc normalized DB writes. Therefore a Discord process should not edit Auto-Dig files itself. A Discord-triggered Auto-Dig integration needs a supervised adapter that invokes the repository's canonical commands and returns typed job state.

** The current starintel-server HTTP surface is not an Internet-facing Discord API

The current HTTP API documentation says the API has no authentication or authorization and must not be exposed directly to an untrusted network. It includes document publication, target publication, document retrieval, full-text search, and view routes.

This makes the existing API useful as evidence that the underlying operations exist, but not an acceptable direct trust boundary for Discord. The Discord integration should terminate at an authenticated, capability-checked bridge that dispatches typed messages to StarIntel gservers.

** The approved StarIntel direction already supports a bridge gserver

The approved composable-gserver design defines one managed actor system per StarIntel server process, supervised domain/service subtrees, typed ingress, shared service components, actor manifests, dataset manifests, scoped event buses, lifecycle policy, and optional remoting/ZeroMQ adapters. A Discord operations bridge fits this model as a shared service or SOCMINT-adjacent edge bridge without making Discord itself authoritative.

* External Platform Findings

** Python and =discord.py= fit the selected edge role

The =discord.py= documentation describes an asynchronous Discord API wrapper with application-command support and rate-limit handling. Its interaction API exposes slash/context commands through =discord.app_commands= and includes guild/user installation and command-context controls. Python's standard =asyncio= runtime provides cancellation, timeouts, and structured task groups suitable for a long-lived network edge.

This makes a Python edge a strong fit for the selected boundary: Discord protocol handling, command registration, attachment streaming, bridge request/reply, notification delivery, and rate-limit behavior can remain asynchronous without moving StarIntel policy into the bot.

Implementation guidance:

- use =discord.py= application commands as the primary command surface;
- use =asyncio= for lifecycle, cancellation, deadlines, and supervised background tasks;
- keep blocking filesystem or subprocess work out of the Gateway event loop;
- pin the Python interpreter and dependencies in the repository's actual reproducible environment rather than relying on system Python;
- keep command handlers thin: parse Discord input, create typed bridge requests, await typed results, and render already-authorized output;
- do not add a direct CouchDB client, generic shell runner, or unrestricted RabbitMQ client to the Discord edge merely because Python libraries make those integrations easy.

The research does not require a second Nim implementation. One Python edge reduces duplicate protocol/security surfaces.

** Discord interactions support the required command surfaces

Discord application commands can be received through HTTP interactions or the Gateway. Commands can be global or guild-scoped. Current command contexts include guild, bot direct-message, and private-channel contexts, with installation context controlling availability.

This supports a model where:

- read-only commands are available in authorized guild channels and DMs;
- mutation commands are visible only where intended and still re-authorized server-side;
- a private DM can be the default surface for sensitive receipts and search detail;
- message context commands can later provide a convenient =Submit to StarIntel= action for a Discord message.

Discord-side command permissions can constrain users, roles, and channels, but these should be treated as user-interface policy rather than the authoritative StarIntel authorization database. StarIntel must repeat authorization on every request.

** Passive message reading has additional privilege implications

Discord's message resource documentation states that message content, embeds, attachments, and components can be absent unless the application has the required Message Content privileged intent. A command-driven interface avoids needing broad passive content access for most features.

Recommendation: use application-command interactions for normal operations and require an explicit, separately approved listener mode before ingesting arbitrary guild message content.

** Discord can send results into guild or DM channels

The Discord message API supports sending messages to guild text channels or direct-message channels. Sensitive output still requires StarIntel-side redaction and output policy; Discord transport capability is not permission to disclose the underlying document.

** RabbitMQ favors long-lived bounded consumers

RabbitMQ documents consumers as long-lived subscriptions to queues. Manual acknowledgements allow a consumer to acknowledge only after processing, and prefetch bounds in-flight deliveries. Topic exchanges route by dotted routing-key patterns using =*= and =#= wildcards.

This maps well to a persistent StarIntel-managed Discord channel projection, but not to allowing arbitrary Discord users to type raw AMQP topology commands. The binding must be validated against an operator-approved manifest.

* Authorization Model

Use a StarIntel-owned principal record keyed by immutable Discord snowflake identifiers. Discord roles may contribute claims, but the StarIntel record is authoritative.

Proposed capabilities:

#+begin_example
star.read
star.document.read
star.document.submit
star.watch.manage
star.target.read
star.target.create
star.autodig.read
star.autodig.start
star.rabbit.read
star.rabbit.bind
star.admin
#+end_example

Important separation:

- =star.document.submit= does not imply =star.target.create=;
- =star.autodig.read= does not imply =star.autodig.start=;
- =star.rabbit.read= does not imply arbitrary exchange/queue declaration;
- guild membership does not imply any StarIntel capability;
- DM access does not bypass capability checks;
- channel configuration cannot increase a user's capabilities.

A request is authorized against the tuple =principal + capability + resource + context=. Context can include guild ID, Discord channel ID, DM, dataset, target, operation, and requested result sensitivity.

* Document Submission Research

The strongest design is not "upload JSON and trust it." Discord input is untrusted source material.

Recommended flow:

1. create a durable submission receipt using the Discord interaction/message ID as part of the idempotency key;
2. fetch the attachment or message snapshot into a bounded quarantine area;
3. record source URL, Discord guild/channel/message/user IDs, observed timestamp, filename, media type, byte length, and cryptographic hash;
4. reject unsupported size/type or malformed content before canonical ingest;
5. parse the source into a candidate StarIntel document or source artifact;
6. validate against the authoritative StarIntel document contract;
7. persist through the authoritative StarIntel ingest path;
8. emit a durable =submission.accepted= or terminal failure record;
9. create a subscription keyed to the produced document, target, dataset, or lineage when the user requested updates;
10. DM or reply with the receipt and later lifecycle notifications.

Raw Discord content must remain distinguishable from claims derived from it. The ingest path should retain provenance rather than treating the submitting user as proof that a claim is true.

* Notification Research

"Update the user of new documents" should be an explicit durable subscription, not a best-effort callback hidden inside document submission.

Useful subscription selectors:

- exact document ID;
- target ID;
- dataset ID;
- operation/investigation ID;
- source-lineage ID;
- relation endpoint ID;
- Auto-Dig job ID;
- query/watch expression compiled into an approved bounded selector.

Delivery policy should support:

- DM by default for user-specific submissions;
- optional configured guild channel for team-visible watches;
- coalescing bursts into a digest;
- deduplication by event/document ID;
- retry with a terminal undeliverable state;
- rate-limit-aware backoff;
- no disclosure when the user loses access after the subscription was created.

The final access check must happen at delivery time, not only at subscription creation time.

* Auto-Dig Integration Research

Auto-Dig is currently repository/CLI-centric, so the Discord feature should target a job protocol rather than shell access.

A typed request should include at least:

#+begin_example
request-id
principal-id
target-id or bounded query
requested-mode
budget profile
source constraints
maximum recursion depth
maximum produced documents
deadline
notification policy
#+end_example

The adapter owns:

- a pinned Auto-Dig checkout/revision;
- invocation of canonical scripts only;
- one isolated worktree or workspace per job;
- stdout/stderr capture with secret filtering;
- cancellation and deadline enforcement;
- validation before any publication/import;
- terminal job state;
- resulting document IDs and packet paths;
- optional branch/PR publication when the configured workflow permits it.

Discord never receives a generic shell command and never supplies arbitrary script names or filesystem paths.

* RabbitMQ-to-Discord Research

The requested "set a channel to listen on RabbitMQ" feature is feasible, but it should be modeled as an event projection profile.

Example operator-approved profiles:

#+begin_example
documents.created.#
targets.status.#
autodig.jobs.#
actors.health.#
operations.alerts.#
#+end_example

The exact routing keys must come from the deployed StarIntel event contract; the strings above are illustrative until verified against the current runtime.

A profile should specify:

- source exchange;
- allowed routing-key pattern;
- target Discord guild/channel;
- formatter;
- redaction class;
- maximum messages per interval;
- burst-coalescing policy;
- acknowledgement mode;
- retry/dead-letter behavior;
- principal who created the binding;
- expiration or persistent flag;
- audit ID.

Use a long-lived consumer with bounded prefetch and manual acknowledgement. Ack only after the event is either delivered to Discord or durably recorded for retry. Repeated poison messages should terminate in a dead-letter/failure record rather than loop forever.

* Private DM Model

Private DMs are a useful operator surface, but privacy is contextual rather than absolute.

Recommended behavior:

- global/user-install-compatible read commands can operate in DMs where Discord supports the configured command context;
- DM responses can show more detail than a public channel only if the StarIntel disclosure policy permits it;
- mutation commands in DMs still require the same capability checks as guild commands;
- guild-specific resources remain scoped to the resource the principal is authorized to access;
- the bot never treats "this is a DM" as sufficient authorization;
- sensitive result sets should default to summaries plus stable IDs rather than dumping full raw documents.

* Threats and Failure Modes

** Discord account compromise

An allowlisted Discord account can be compromised. Mitigations: narrow capabilities, mutation confirmation for high-impact actions, short-lived elevated grants, audit records, rate limits, and easy revocation.

** Prompt injection and adversarial documents

Submitted messages and files are evidence, not instructions. Do not concatenate raw user content into an agent system prompt with authority. Any later LLM analysis must receive the content as untrusted source material inside a capability- and budget-constrained job.

** Duplicate interactions and retries

Discord and internal transports can retry. Every mutation requires an idempotency key and a durable result record so repeated delivery cannot create duplicate targets, duplicate documents, or duplicate Auto-Dig runs.

** Disclosure through notifications

A subscription created while access was valid may outlive that access. Re-authorize before every delivery and redact by current policy.

** RabbitMQ event floods

A broad topic binding can overwhelm a Discord channel. Require bounded routing profiles, prefetch, coalescing, per-binding quotas, and a circuit breaker.

** Direct exposure of starintel-server

The current unauthenticated HTTP API must not be exposed to Discord or the Internet as the bot backend. Add a proper authenticated bridge or trusted local adapter first.

** Python event-loop starvation

A Python Discord bot can become unresponsive if command handlers perform blocking I/O or CPU-heavy parsing on the event loop. Keep handlers thin, enforce deadlines, isolate blocking work, and keep document parsing/Auto-Dig execution behind the StarIntel bridge rather than inside the bot process.

* Recommended Architecture Conclusion

Implement =starintel-discord-tool= as a thin Python Discord edge using =discord.py=. This is now a selected implementation constraint, not an open language choice. Retire the current Nim edge scaffolding during implementation unless a separately approved compatibility requirement appears later.

Put authoritative behavior in a new =discord-ops-bridge= gserver under =starintel-server=. That gserver owns principal mapping, capability checks, typed request validation, idempotency, audit, search dispatch, document-ingest coordination, target mutation, Auto-Dig jobs, subscriptions, RabbitMQ projections, and output policy.

The Python edge process should know Discord protocol details and render responses; it should not own StarIntel authorization rules, canonical documents, raw CouchDB credentials, arbitrary RabbitMQ credentials, or Auto-Dig repository mutation logic.

The Python edge should use =discord.py= application commands and =asyncio= lifecycle primitives, with a separately testable typed StarIntel bridge client. This keeps Discord-specific code small and lets other future clients reuse the same StarIntel contract without duplicating policy.

* Unresolved Questions Before Implementation

1. What is the current canonical authenticated Star Router/remoting protocol that should carry edge-to-gserver requests? If none is production-ready, define a minimal authenticated loopback/Unix-socket bridge rather than exposing the current HTTP API.
2. Which RabbitMQ exchanges and routing keys are canonical in the deployed fourth-generation server? Do not freeze illustrative names into manifests until verified.
3. Which StarIntel document spec version will =starintel-server= accept when the Discord implementation begins? The current server API documentation and Auto-Dig repository are not yet presented as one fully aligned ingest contract.
4. Should submitted Discord files be stored as first-class source artifacts in StarIntel object storage, in Auto-Dig Git evidence, or both under a lineage record?
5. Which target types may trusted collaborators create, and which require operator confirmation?
6. Should Auto-Dig jobs publish branches/PRs automatically, or only produce local validated results pending operator action?
7. Which document classes are safe to return in guild channels versus DM-only versus never through Discord?
8. Which exact CPython and =discord.py= versions should the implementation repository pin after its current packaging/Nix state is reconciled? The language/library family is selected; exact versions remain an implementation-time pin.

* Footnotes and Glossary

[fn:gserver] A supervised actor-style StarIntel service that owns state and handles typed messages behind a stable capability boundary.

[fn:principal] A StarIntel identity record representing the authenticated Discord user independently of mutable display names.

[fn:capability] An explicit permission to perform one class of action against a bounded resource; capabilities are deny-by-default.

[fn:idempotency] A property ensuring repeated delivery of the same logical request produces one durable effect rather than duplicates.

[fn:projection] A bounded consumer that transforms internal events into a non-authoritative external view such as Discord notifications.

[fn:quarantine] Temporary bounded storage for untrusted files before parsing, validation, and canonical persistence.

[fn:discord-py] The asynchronous Python Discord API wrapper selected for the edge implementation; it handles Discord protocol mechanics but is not an authorization authority for StarIntel.

[fn:asyncio] Python's standard asynchronous I/O runtime used for tasks, cancellation, timeouts, and long-lived network concurrency in the Discord edge.
