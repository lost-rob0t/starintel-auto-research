* Scope

This node evaluates NoneCap as a narrow hCaptcha provider behind [[id:star-captcha-000-broker-router][STAR-CAPTCHA-000]]. It does not define the global challenge taxonomy, and it does not treat reserved future task names as active capabilities.

Current official documentation exposes active =hcaptcha= and =hcaptcha_enterprise= solve types. Standard and invisible behavior must be separated by fixture and context even when they share a request operation. Enterprise requires its own mapping and evidence. reCAPTCHA, Turnstile, FunCaptcha, and other reserved names remain =unsupported= until an active official contract and fixture exist.

* Provider Interaction Sequence

participant "NoneCapAdapterActor" as Adapter
participant "EphemeralSecretStoreActor" as Secrets
participant "NoneCap v1 API" as API

Run -> Adapter : captchaProviderSubmit(exact hCaptcha capability, challengeRef)
Adapter -> Secrets : read bounded challenge and credential refs
Adapter -> API : POST /v1/solves?wait=N
alt create returns solve identifier
  API --> Adapter : pending/solving/terminal + id
  loop bounded by deadline while non-terminal
    Adapter -> API : GET /v1/solves/{id}?wait=N
    API --> Adapter : state + timing + charge metadata
  end
  alt solved and result contract valid
    Adapter -> Secrets : write token with expiry and one-read lease
    Adapter --> Run : captchaProviderSucceeded(resultRef)
  else failed/cancelled/expired/invalid result
    Adapter --> Run : captchaProviderFailed(normalized error)
  end
else ambiguous transport outcome without identifier
  Adapter --> Run : ambiguousSubmission(chargePossible)
end
@enduml

* Cancellation, Feedback, and Shutdown

- Cancellation uses the documented delete operation and records whether the solve was already terminal.
- Duplicate cancellation is idempotent at the adapter boundary.
- A cancelled solve is documented as not charged; a cancellation request racing a terminal completion must preserve the provider's terminal result and charge metadata.
- Feedback is sent only under explicit operator policy and never includes local secrets beyond the provider's documented job reference and accepted feedback contract.
- Batch feedback supports up to 500 items and returns per-item status; one invalid item must not be interpreted as whole-batch failure.
- Shutdown stops new submissions, polls or cancels active solves until a bounded deadline, expires local result leases, and records unresolved provider identifiers.

* Billing, Concurrency, and Budget

The adapter records provider-reported charge only after terminal resolution and reports cost in redacted normalized metadata. Failed, cancelled, and expired solves are documented as not charged. Concurrency must come from configured account limits and observed provider responses; the current public contract documents a default cap of five but runtime policy must not assume that every account has that value.

The broker reserves budget before submission. Fallback to another provider requires a new attempt, remaining budget, exact capability, disclosure permission, and a non-ambiguous prior terminal state.

* Security, Retention, and Disclosure

Never place provider keys, solution tokens, proxy credentials, Enterprise data, cookie bundles, page data, authorization headers, or full provider response bodies in actor messages, RabbitMQ messages, fixtures, documents, durable events, or generated pages.

The provider receives at least the target page URL, site key, task context, timing, and account identity. Public API documentation states that solve records are retained for thirty days before purge. That disclosure and retention require explicit operator acceptance.

Feedback context is free-form and can be read by a human when support is involved. Therefore StarIntel must not forward raw target response bodies, private page content, proxy credentials, authenticated identifiers, or other unnecessary source material in feedback context.

Credential logs use placeholders such as =Authorization: Bearer <redacted>=. Returned tokens remain in the ephemeral secret store and are read once by the authorized source runtime.

* Error Contract

Normalize provider transport, authentication, balance, invalid request, unsolvable, cancellation, timeout, expiry, concurrency, sitekey rate limit, and service failure into broker failure types. Preserve the provider code only when safe. Every failure records =retryable= and =chargePossible=.

No blind create retry is permitted after an ambiguous transport outcome.

* Contract Drift

- A failing standard fixture changes only the standard capability state.
- A failing invisible fixture changes only the invisible capability state.
- A failing Enterprise fixture changes only the Enterprise capability state.
- Shared authentication or transport failure may disable all NoneCap capabilities while the dependency is unavailable.
- Reserved future task names remain =unsupported= until current official docs and fixtures establish an active contract.
- Account concurrency and sitekey rate-limit behavior are runtime evidence and may tighten scheduling without changing the request/result schema.

* Required Fixtures and Tests

- standard request and solved result;
- invisible request and result;
- Enterprise request with required =rqdata= and result;
- pending and solving polls;
- failed, cancelled, and expired states;
- cancellation conflict after terminal completion;
- every relevant HTTP and provider error, including concurrency and sitekey rate limiting;
- account and balance response;
- batch and single-solve feedback request/response shapes;
- duplicate RabbitMQ delivery;
- ambiguous create without provider ID;
- cancellation race and already-terminal cancellation;
- polling deadline and shutdown with active work;
- billing reconciliation and budget exhaustion;
- provider key, token, proxy, Enterprise context, free-form feedback context, and response redaction;
- reserved task names never registered;
- no paid provider in continuous integration;
- opt-in bounded live canary against an operator-owned system only.

* Decision

Retain NoneCap as a narrow hCaptcha adapter candidate. Enable standard, invisible, and Enterprise capabilities independently only after their exact contract fixtures, security review, operator policy, and bounded canary requirements are satisfied.

* Footnotes and Glossary

- *Ambiguous submission* — A create request whose provider-side outcome is unknown, making an automatic retry potentially duplicate and billable.
- *Bearer authentication* — Authentication by possession of a secret token in the HTTP authorization header.
- *Capability-local drift* — A contract failure that changes only the affected exact capability rather than globally rejecting a provider.
- *Round* — One provider-counted hCaptcha challenge stage; one logical solve may contain multiple rounds.
