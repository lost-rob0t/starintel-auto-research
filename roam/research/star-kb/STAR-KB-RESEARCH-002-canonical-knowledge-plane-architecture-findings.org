* Verified Facts

The current =lost-rob0t/prolog-query-server= already provides CouchDB-persisted =prolog_fact= and =prolog_rule= documents, multiple named KBs, safe JSON term/goal representation, bounded backward-chaining inference, synchronous query/explain endpoints, async jobs, query IDs, immutable releases, active-release manifests, explicit release pinning, revision-aware writes, static release analysis, proof/source information, incremental =_changes= synchronization, safe builtins, auth, resource budgets, and fail-closed handling of unresolved knowledge conflicts.

Persisted facts are ground. Rules are represented as a structured =head= plus ordered =body=. Variables are JSON objects such as ={ "var":"X" }=; compounds use ={ "functor":"point", "args":[...] }=; explicit atoms can be distinguished from strings. The safe builtin surface includes equality/disequality, =calc/2=, numeric comparisons, type checks, and a restricted arithmetic-expression vocabulary.

The current PQS query path holds a per-KB mutex across release resolution, refresh/sync, and query execution, so high-concurrency same-KB workloads may serialize.

The new =lost-rob0t/star-kb= repository exists and currently contains the RAGE research/design/implementation control-plane skeleton. Product knowledge/compiler code is not yet implemented.

* Inference

The verified runtime makes a second Prolog query server unnecessary. =star-kb= should own the reusable human/agent-authored knowledge source, source records, module/bundle composition, deterministic build identities, fixtures, and publication tooling, while PQS+CouchDB remain the executable runtime.

Readable Prolog should be accepted only through a restricted source profile. SWI-Prolog should parse terms as data; a validator then rejects executable/general-purpose constructs and compiles accepted clauses into the PQS safe JSON AST. Source files are not consulted or executed.

Git should remain the authority for reviewed reusable source knowledge. CouchDB should remain the authority for executable PQS releases and active-release manifests. StarIntel document/artifact stores should remain the authority for run-specific observations, scraper evidence, and learned-model outputs. Promotion from observation to reusable knowledge is explicit rather than automatic.

Because the existing runtime selects one =(kb, release)= pair, V0.1 should resolve source-module dependencies at build time and flatten one consumer-facing bundle into one immutable PQS release. Runtime multi-KB imports can wait for measurements showing that duplication is a real problem.

PQS strict analysis should be mandatory during normal =star-kb= activation. Query and proof metadata should be preserved so derived StarIntel outputs can be traced through actor/version -> PQS query ID -> KB/release -> runtime source document -> =star-kb= clause/module/source record.

Dialect enrichment remains a strong first consumer after the generic pipeline. Its evidence model must keep linguistic features, contextual geographic clues, named-place clues, and learned-model evidence separate.

* Contradictions

No fatal contradiction was found, but the research identified design tensions:

- Prolog is desired as the human knowledge language while PQS intentionally rejects raw executable Prolog at runtime. The design must bridge this with parse-only restricted source compilation.
- A large shared corpus is desired while PQS queries one named KB/release. V0.1 can build bundles by dependency closure and accept duplicated shared facts until scale measurements justify runtime imports.
- Reproducible semantic releases are desired while Git commits/timestamps change even when knowledge does not. Semantic content identity must be separated from non-semantic build provenance.
- Large future actor throughput is desired while current same-KB PQS queries serialize under a per-KB lock. This needs benchmarking before production scale, not speculative runtime redesign in the bootstrap slice.
- A continuously growing intelligence corpus is desired while raw observations can grow far faster than a reviewable Git KB. Observations must stay outside canonical source unless explicitly promoted.

* Unresolved Questions

- Practical bundle/document/byte ceilings against current PQS resource limits.
- Same-KB throughput before the current mutex becomes a bottleneck.
- Whether large actor evidence eventually requires query-scoped ephemeral facts rather than goal arguments.
- Whether probabilistic dialect inference later belongs in safe PQS builtins, cplint, or a separate model/fusion service.
- Whether native multi-KB runtime imports become worthwhile after corpus growth.
- First-party dialect survey consent, retention, deletion, and publication policy.
- Future release signing/attestation beyond deterministic content hashes.

* Research Conclusion

The next artifact must be a real implementation-ready design in =lost-rob0t/star-kb=. It must specify exact source grammar, repository layout, manifest schemas, clause/release identity algorithms, compiler modules, CLI behavior, staging/activation state machine, provenance fields, test matrix, failure semantics, and bounded V0.1 scope. It must remain under =roam/design/= until explicit operator approval.

That deep design is being reviewed separately in =lost-rob0t/star-kb= PR #2. No implementation authorization is implied by this research note.

* Footnotes and Glossary

- *PQS*: =prolog-query-server=, the existing SWI-Prolog/CouchDB expert-system runtime.
- *KB*: knowledge base, a named set of facts and rules.
- *AST*: structured representation of parsed code. PQS consumes safe JSON AST data rather than raw executable source text.
- *Ground fact*: a fact containing no variables.
- *Meta-interpreter*: a Prolog program that interprets a restricted stored-rule representation rather than directly executing arbitrary stored Prolog.
- *Bundle*: a consumer-facing package formed from a module dependency closure and, in V0.1, published as one PQS KB release.
- *Release*: immutable version of one runtime KB selected by an active-release manifest.
- *Manifest*: metadata record describing composition/version state rather than logical facts themselves.
- *Provenance*: where knowledge/results came from and which exact versions participated.
- *Observation*: case/run-specific evidence, not automatically reusable canonical knowledge.
- *Strict activation*: release cutover with PQS static analysis required to succeed.
- *Per-KB mutex*: a lock protecting one KB's runtime state; in the current path it also serializes same-KB query execution while held.
