* Research Question

How should StarLang gain the ergonomic benefits of source-local compiler directives—optimization choices, warnings, backend selection and tuning, verification requests, resource defaults, and developer artifacts—without importing Nim punctuation, exposing Common Lisp evaluation, creating an arbitrary option bag, or allowing source code to grant itself deployment authority?

The desired language remains unmistakably Lisp-like:

#+begin_src lisp
(pragma :optimize :speed)
(pragma :warnings :strict)
(pragma :backend :swi-prolog)
#+end_src

The following is explicitly not StarLang syntax:

#+begin_example
{. optimize: speed .}
#+end_example

* Executive Decision

Adopt one regular source form:

#+begin_src lisp
(pragma <name> <value> ...)
#+end_src

V1 should use repeated =pragma= forms as the canonical spelling. Each pragma name is registered in a compiler-owned typed option registry that defines:

- exact value schema and arity;
- typed category;
- legal scopes;
- inheritance/resolution rule;
- deployment authority rule;
- backend association when namespaced;
- reproducibility class;
- conflict/dependency rules;
- stable diagnostics and documentation key.

A pragma is compiler-interpreted StarLang data. It is not executable Common Lisp, not an arbitrary StarLang expression, not a macro invocation, and not a runtime capability grant.

The normalized resolution pipeline is:

#+begin_example
compiler defaults
       ↓
project configuration
       ↓
module pragmas
       ↓
declaration pragmas
       ↓
operation pragmas
       ↓
deployment restrictions
       ↓
validated compiler policy
#+end_example

Source may select or tighten policy within the registered rules. It can never grant authority forbidden by deployment configuration.

* Research Basis

** StarLang compiler boundary

The current =lost-rob0t/star-lang= prototype uses dedicated StarLang syntax objects and carries source spans, origin frames, expansion traces, parser limits, and structured compiler errors. That is the correct substrate for pragmas: each directive can remain ordinary closed StarLang syntax with exact source provenance, then normalize into compiler-owned option data.

Current source evidence reviewed 2026-08-15:

- [[https://github.com/lost-rob0t/star-lang/blob/main/prototype/core-surface-prototype.lisp][StarLang core surface prototype]]
- [[https://github.com/lost-rob0t/star-lang/blob/main/prototype/compiler-ir-prototype.lisp][StarLang compiler IR prototype]]

A pragma must never be handed to the Common Lisp reader or evaluator merely because the compiler is implemented in Common Lisp.

** Common Lisp declaration precedent

Common Lisp declarations are useful design evidence rather than StarLang semantics. The HyperSpec defines declarations as information for program processors; a declaration specifier is list-shaped data whose identifier determines how the rest is interpreted; =declare= expressions are not evaluated; declarations have explicit scope; and =optimize= is a standard compiler declaration.

Useful lessons for StarLang:

- compiler metadata can look like ordinary Lisp data;
- compiler metadata can be legal only in defined contexts;
- local scope does not require a punctuation sublanguage;
- compiler advice can be distinct from executable code.

StarLang should not inherit Common Lisp's implementation-defined declaration extension behavior. StarLang needs a closed, typed registry for reproducible compilation.

Sources reviewed 2026-08-15:

- [[https://www.lispworks.com/documentation/HyperSpec/Body/03_c.htm][Common Lisp HyperSpec 3.3 Declarations]]
- [[https://www.lispworks.com/documentation/HyperSpec/Body/03_cb.htm][Common Lisp HyperSpec 3.3.2 Declaration Specifiers]]
- [[https://www.lispworks.com/documentation/HyperSpec/Body/s_declar.htm][Common Lisp HyperSpec DECLARE]]
- [[https://www.lispworks.com/documentation/HyperSpec/Body/03_cd.htm][Common Lisp HyperSpec Declaration Scope]]
- [[https://www.lispworks.com/documentation/HyperSpec/Body/d_optimi.htm][Common Lisp HyperSpec OPTIMIZE]]

** Nim pragma precedent

The Nim manual describes pragmas as compiler information/commands processed during semantic checking. It documents compilation-option pragmas and push/pop for temporary scoped overrides, plus user-defined/custom pragmas.

StarLang should borrow the ergonomic concepts:

- source-local compiler metadata;
- typed values;
- scoped effect;
- nearby tuning/annotations;
- static diagnostics.

StarLang should reject for ordinary source:

- Nim ={. ... .}= punctuation;
- arbitrary source-defined pragma semantics;
- compiler/linker escape hatches;
- ambient compile-time I/O or process execution.

Sources reviewed 2026-08-15:

- [[https://nim-lang.org/docs/manual.html#pragmas][Nim Manual — Pragmas]]
- [[https://nim-lang.org/docs/manual.html#pragmas-compilation-option-pragmas][Nim Manual — Compilation option pragmas]]
- [[https://nim-lang.org/docs/manual.html#pragmas-push-and-pop-pragmas][Nim Manual — Push and pop pragmas]]
- [[https://nim-lang.org/docs/manual.html#user-defined-pragmas][Nim Manual — User-defined pragmas]]
- [[https://nim-lang.org/docs/nimc.html][Nim Compiler User Guide]]

* Canonical Grammar

Conceptual grammar:

#+begin_example
pragma-form        ::= (pragma pragma-name pragma-argument*)
pragma-name        ::= keyword | namespaced-keyword
namespaced-keyword ::= :backend-namespace/option-name
pragma-argument    ::= typed-literal | typed-literal-list
#+end_example

A registered value schema may accept only closed StarLang literals such as:

- booleans;
- bounded integers;
- strings where explicitly allowed;
- closed keyword enums;
- typed lists of those literals.

Arbitrary expressions are not pragma values.

Valid:

#+begin_src lisp
(pragma :optimize :speed)
(pragma :warnings :strict)
(pragma :debug-info :full)
(pragma :backend :swi-prolog)
(pragma :inference-limit 500000)
(pragma :emit-bindings (:python :typescript))
#+end_src

Invalid:

#+begin_src lisp
(pragma :memory-limit (calculate-limit environment))
(pragma :backend (load "engine.lisp"))
#+end_src

* Typed Option Registry

A compiler descriptor is conceptually equivalent to:

#+begin_src lisp
(pragma-descriptor
  :name :inference-limit
  :category :resource-policy
  :value-schema (:integer :minimum 1)
  :legal-scopes (:project :module :declaration :operation)
  :resolution :replace-nearest
  :reproducibility :runtime-policy
  :authority :deployment-bounded
  :backend nil)
#+end_src

This is conceptual compiler data, not user-facing StarLang source.

Unknown options never dynamically create descriptors.

* Typed Pragma Categories

The registry should expose typed classes rather than one arbitrary option bag.

** Compiler behavior

Candidates:

#+begin_src lisp
(pragma :optimize :speed)
(pragma :warnings :strict)
(pragma :debug-info :full)
(pragma :warnings-as-errors t)
#+end_src

Recommended initial classification:

| Pragma | Candidate values | Category | Reproducibility |
|--------+------------------+----------+-----------------|
| =:optimize= | =:none :speed :space :balanced= | compiler behavior | =:code-generation= |
| =:warnings= | =:default :strict :quiet= | compiler behavior | =:diagnostic-only= |
| =:debug-info= | =:none :line :full= | compiler behavior | =:code-generation= |
| =:warnings-as-errors= | boolean | compiler/verification behavior | =:diagnostic-only= |

=:warnings :quiet= can reduce warnings but must never suppress required semantic or safety errors.

The candidate =:source-map= duplicates the clearer developer-output name =:emit-source-map=. V1 should keep one canonical control, =:emit-source-map=, rather than two aliases for the same artifact.

** Logic backend

Backend-selection authority is the separate STAR-LANG-RESEARCH-026 node. Its canonical values remain:

#+begin_src lisp
(pragma :backend :auto)
(pragma :backend :lisa)
(pragma :backend :swi-prolog)
(pragma :backend :n-prolog)
#+end_src

This node owns only the general pragma mechanism around =:backend=: typing, scope representation, normalization, diagnostics, explanation, and identity participation. It does not redefine =:auto=, backend IDs, semantic compatibility, state-boundary safety, or why-selected evidence from STAR-LANG-RESEARCH-026/022.

Generic semantic requirements should remain backend-neutral, for example conceptually:

#+begin_src lisp
(pragma :logic-profile :tabled)
#+end_src

An explicit backend pin never bypasses the semantic requirement.

** Verification pragmas

Candidates:

#+begin_src lisp
(pragma :verify-documents t)
(pragma :verify-messages t)
(pragma :deadlock-check :required)
(pragma :model-check :bounded)
(pragma :warnings-as-errors t)
#+end_src

Safety-sensitive options require a floor/constraint model, not simple last-write-wins.

Recommended rules:

| Pragma | Source role | Deployment interaction |
|--------+-------------+------------------------|
| =:verify-documents= | request verification | source may enable; cannot disable mandatory floor |
| =:verify-messages= | request verification | source may enable; cannot disable mandatory floor |
| =:deadlock-check= | request verification level | cannot fall below deployment/compiler requirement |
| =:model-check= | request model-check mode | may request stronger supported mode; deployment may require a floor |
| =:warnings-as-errors= | build acceptance policy | replace-nearest unless project policy requires strict diagnostics |

If deployment requires message verification, this is a compiler policy error:

#+begin_src lisp
(pragma :verify-messages nil)
#+end_src

Reject the attempted relaxation rather than silently clamping it. The diagnostic should show the source request and the policy authority that forbids it.

Mandatory semantic/safety checks are never disableable by ordinary source pragmas.

** Resource policy

Candidates:

#+begin_src lisp
(pragma :timeout-ms 10000)
(pragma :memory-limit 268435456)
(pragma :mailbox-limit 4096)
(pragma :retry-limit 3)
(pragma :inference-limit 500000)
(pragma :answer-limit 250)
#+end_src

These are =:resource-policy= category options and normally =:runtime-policy= for reproducibility because they can change timeout, backpressure, retry, answer enumeration, and terminal behavior.

Recommended authority behavior:

| Option | Source meaning | Deployment authority |
|--------+----------------+----------------------|
| =:timeout-ms= | requested/default wall-time bound | may impose lower maximum or required boundedness |
| =:memory-limit= | requested/default memory bound | may impose lower maximum |
| =:mailbox-limit= | requested actor/mailbox bound | may impose allowed range/maximum |
| =:retry-limit= | requested retry bound | may impose maximum and idempotency requirements |
| =:inference-limit= | requested logic inference bound | may impose maximum/minimum-required boundedness |
| =:answer-limit= | requested answer bound | may impose maximum |

A source limit is not permission to consume that amount if deployment grants less.

** Developer output

Candidates:

#+begin_src lisp
(pragma :emit-ir t)
(pragma :emit-manifest t)
(pragma :emit-source-map t)
(pragma :emit-bindings (:python :typescript))
#+end_src

Recommended classification:

| Option | Reproducibility | Identity effect |
|--------+-----------------+-----------------|
| =:emit-ir= | =:code-generation= | generated artifact set/build receipt |
| =:emit-manifest= | =:code-generation= | generated artifact set |
| =:emit-source-map= | =:code-generation= | generated artifact set |
| =:emit-bindings= | =:code-generation= | generated binding artifact identity |
| =:pretty-diagnostics= | =:diagnostic-only= | no executable/run-plan identity effect |
| =:trace= | implementation-dependent until proven | runtime-policy if tracing changes runtime contract |

Do not classify tracing as diagnostic-only until the implementation proves that tracing cannot alter persistence, buffering, timing guarantees, or runtime outcomes relevant to the contract.

* Logic Backend and Namespaced Pragmas

Use flat namespaced keyword names while preserving the same grammar:

#+begin_src lisp
(pragma :swi/tabling :incremental)
(pragma :swi/inference-limit 500000)

(pragma :lisa/agenda-strategy :salience)
(pragma :lisa/working-memory-limit 100000)

(pragma :n-prolog/compatibility :portable)
#+end_src

The slash is part of a compiler-recognized pragma key. It is not Common Lisp package syntax and does not expose host package interning.

** Flat namespace versus nested form

Prefer:

#+begin_src lisp
(pragma :swi/tabling :incremental)
(pragma :swi/inference-limit 500000)
#+end_src

Reject for V1:

#+begin_src lisp
(pragma :swi
  (:tabling :incremental)
  (:inference-limit 500000))
#+end_src

Flat namespaced keys win because they preserve one grammar, one registry key per option, independent source spans, direct duplicate detection, direct hashing, direct =--explain-options= paths, and precise deprecation/diagnostics.

** Static backend checking

A backend-specific source pragma requires a compatible resolved explicit backend pin.

Valid:

#+begin_src lisp
(reason ownership-path
  (pragma :backend :swi-prolog)
  (pragma :logic-profile :tabled)
  (pragma :swi/tabling :incremental)
  (pragma :swi/inference-limit 500000)
  ...)
#+end_src

Invalid:

#+begin_src lisp
(reason ownership-path
  (pragma :backend :lisa)
  (pragma :swi/tabling :incremental)
  ...)
#+end_src

Required result: compiler error, never silent ignore.

Also reject in V1:

#+begin_src lisp
(reason ownership-path
  (pragma :backend :auto)
  (pragma :swi/tabling :incremental)
  ...)
#+end_src

Reason: backend-specific tuning under =:auto= creates an implicit/circular selection constraint. Generic semantic requirements drive =:auto=; backend-specific tuning requires the author to pin that backend explicitly. This does not change STAR-LANG-RESEARCH-026's =:auto= semantics.

* Scope Model

General pragma scopes are:

1. project;
2. module;
3. declaration;
4. operation.

Project options live in project configuration rather than free-floating source before a module.

Module example:

#+begin_src lisp
(module ownership-analysis
  (pragma :optimize :speed)
  (pragma :warnings :strict)
  ...)
#+end_src

Declaration example:

#+begin_src lisp
(actor crawler
  (pragma :mailbox-limit 4096)
  (pragma :retry-limit 3)
  ...)
#+end_src

An =expert-system= is a declaration scope for this general option model. Its backend state-boundary semantics remain under STAR-LANG-RESEARCH-026/023.

Operation example:

#+begin_src lisp
(reason ownership-path
  (pragma :backend :swi-prolog)
  (pragma :inference-limit 500000)
  ...)
#+end_src

Every descriptor declares its legal scopes. A pragma in an illegal scope is an error rather than being ignored or hoisted.

* Inheritance and Precedence

For ordinary =:replace-nearest= options:

#+begin_example
compiler default
    ↓
project value
    ↓
module value
    ↓
declaration value
    ↓
operation value
#+end_example

The nearest legal source value wins before deployment constraints are applied.

Absence means inherit. Absence is not semantically identical to writing an explicit value that happens to equal the current default because provenance/explanation must distinguish them.

Backend-specific lexical details and state-boundary override safety remain governed by STAR-LANG-RESEARCH-026. The general pragma pipeline must not flatten those rules into unsafe last-write-wins behavior.

* Typed Resolution Operators

Not every option can use ordinary replacement. Initial registry resolution operators should include:

- =:replace-nearest= — nearest legal source value replaces inherited source value;
- =:minimum-floor= — resolved value may not fall below required safety/verification level;
- =:maximum-ceiling= — requested resource value may not exceed deployment maximum;
- =:set-union= — only where accumulating independent output targets is intentional;
- =:intersection= — request and deployment allowance must overlap;
- =:exact-match= — deployment requires one exact value.

The compiler registry selects the rule. Source syntax cannot choose its own merge semantics.

* Duplicate Pragmas

Two occurrences of the same canonical option in the same scope are a hard error, even when values are identical.

#+begin_src lisp
(module example
  (pragma :optimize :speed)
  (pragma :optimize :speed)
  ...)
#+end_src

Reason: duplicate directives usually indicate generated-source, copy/paste, or ordering mistakes. Same-scope last-one-wins is rejected.

A narrower scope overriding a broader scope is not a duplicate.

* =with-pragmas= Research

Candidate:

#+begin_src lisp
(with-pragmas
    ((:optimize :speed)
     (:warnings :strict))
  ...)
#+end_src

V1 recommendation: reject/defer.

Module/declaration/operation scopes already cover the useful ownership boundaries. An arbitrary lexical block would need new rules for declaration ownership, macro expansion, runtime-plan boundaries, and resource policies without a demonstrated requirement.

If future evidence requires arbitrary lexical configuration blocks, research them as a general language construct rather than adding pragma-specific push/pop state.

* =pragmas= Bundle Research

Candidate:

#+begin_src lisp
(pragmas
  (:optimize :speed)
  (:warnings :strict)
  (:trace :messages))
#+end_src

V1 recommendation: reject as canonical syntax.

Prefer:

#+begin_src lisp
(pragma :optimize :speed)
(pragma :warnings :strict)
(pragma :trace :messages)
#+end_src

Repeated forms preserve one syntax shape and one syntax object/source span per directive. A formatter may visually group adjacent pragmas without changing the language.

* Resolution Pipeline

Use exactly one normalized pipeline:

#+begin_example
compiler defaults
       ↓
project configuration
       ↓
module pragmas
       ↓
declaration pragmas
       ↓
operation pragmas
       ↓
deployment restrictions
       ↓
validated compiler policy
#+end_example

Each contribution retains provenance. Conceptually:

#+begin_src lisp
(resolved-option
  :name :backend
  :value :swi-prolog
  :category :logic-backend
  :reproducibility :semantic
  :source-layer :module
  :source-span <span>
  :resolution :replace-nearest
  :deployment-status :allowed)
#+end_src

The compiler retains both final values and the trace explaining how they were resolved.

* Safety and Authority Boundary

Deployment policy may:

- forbid a backend;
- require verification;
- enforce resource maxima/minima;
- require boundedness;
- deny runtime capabilities;
- restrict generated artifact targets;
- require isolation/proof profiles.

Source cannot reverse those decisions.

This should not be a capability grant:

#+begin_src lisp
(pragma :network :allow)
#+end_src

If its purpose is to grant runtime network authority, =:network= should not be a pragma. A component may declare a network *requirement* through StarLang's capability/effect model; deployment authorizes or denies it separately.

Compiler tuning and runtime capability authority are distinct concepts.

* Project, CLI, and Deployment Interaction

** Project configuration

Project configuration uses the same typed registry and normalized option schemas but is a distinct outer layer.

The exact project file syntax is not fixed here. It must be declarative data, not executable Common Lisp; name only registered options; retain provenance; validate project scope; and participate in explanation and relevant identity digests.

** CLI explanation

Required conceptual facility:

#+begin_example
starlang compile foo.star --explain-options
#+end_example

Exact CLI spelling is not predetermined, but the facility should explain rather than invent policy.

A future CLI may select project/deployment profiles. Dedicated flags must normalize into an existing typed project or deployment input rather than becoming a generic highest-precedence layer above deployment restrictions.

Reject a generic escape hatch such as:

#+begin_example
starlang compile foo.star --set-anything :verify-messages=nil
#+end_example

* Option Explanation Facility

Conceptual output:

#+begin_example
:backend
  compiler default: :auto
  project default:  :auto
  module pragma:    :swi-prolog  ownership.star:3:3
  declaration:      <none>
  operation:        <none>
  deployment:       allowed [:swi-prolog :lisa]
  final:            :swi-prolog

:optimize
  compiler default: :balanced
  project:          :speed
  module:           <none>
  actor pragma:     :debug
  final:            :debug

:deadlock-check
  compiler default: :advisory
  source request:   :off       ownership.star:21:5
  deployment floor: :required
  final:            rejected
  diagnostic:       STAR-PRAGMA-006
#+end_example

The explanation should include option name, every contributing layer, source spans, resolution rule, deployment constraint, final/rejected value, reproducibility class, backend namespace requirement, and stable diagnostic code.

A versioned machine-readable form should eventually mirror this data for IDE/build tooling.

* Unknown Pragma Behavior

Unknown pragmas are hard errors.

#+begin_src lisp
(pragma :optmize :speed)
#+end_src

Conceptual diagnostic:

#+begin_example
error STAR-PRAGMA-001: unknown pragma :optmize
suggestion: :optimize
#+end_example

The compiler may suggest a spelling but must never guess and continue.

Unknown namespaced backend options are likewise errors. Ordinary source cannot define a new pragma name to silence them.

* Diagnostics

Recommended diagnostic families:

| Code | Meaning |
|------+---------|
| =STAR-PRAGMA-001= | unknown pragma name |
| =STAR-PRAGMA-002= | wrong arity or value type/range |
| =STAR-PRAGMA-003= | pragma illegal in current scope |
| =STAR-PRAGMA-004= | duplicate same-scope pragma |
| =STAR-PRAGMA-005= | backend namespace mismatch or forbidden backend-specific =:auto= tuning |
| =STAR-PRAGMA-006= | attempted relaxation below mandatory safety/verification floor |
| =STAR-PRAGMA-007= | deployment policy rejects requested value |
| =STAR-PRAGMA-008= | resolved option conflict |
| =STAR-PRAGMA-009= | macro-generated pragma forbidden |
| =STAR-PRAGMA-010= | deprecated pragma/replacement required |

Diagnostics should carry StarLang syntax span/origin data.

* Macro Interaction

STAR-LANG-RESEARCH-020 keeps macros inside the closed StarLang compiler rather than exposing host execution. Pragmas should have a stronger visibility rule in V1:

1. closed reader produces syntax objects;
2. direct authored pragmas are collected/validated for recognized enclosing scopes;
3. the resulting compile environment is available to later compiler phases;
4. general macro output containing new =pragma= forms is rejected with =STAR-PRAGMA-009=;
5. semantic compilation consumes normalized option data, not raw pragma syntax.

This prevents a macro library from secretly changing verification, backend, optimization, or resource policy.

Common Lisp provides useful precedent here: =declare= expressions must occur explicitly in permitted positions rather than being created by ordinary macro expansion.

Trusted compiler extensions, if eventually supported, are a separate privileged mechanism and may have a reviewed API for contributing option descriptors. Ordinary =.star= macros do not receive that privilege.

* Reproducibility Model

Every descriptor declares one primary class:

#+begin_example
:semantic
:code-generation
:runtime-policy
:diagnostic-only
#+end_example

** =:semantic=

Changes program meaning or required semantic interpretation.

Examples:

- =:backend= policy/concrete selection where engine semantics matter;
- =:logic-profile=;
- verification semantics that determine accepted data/messages.

These participate in semantic artifact and executable run-plan identity.

** =:code-generation=

Changes emitted artifacts without necessarily changing source meaning.

Examples:

- =:optimize=;
- =:debug-info=;
- =:emit-ir=;
- =:emit-manifest=;
- =:emit-source-map=;
- =:emit-bindings=.

These participate in build artifact identity when they alter emitted bytes or artifact sets.

** =:runtime-policy=

Changes bounded execution or operational outcomes.

Examples:

- =:timeout-ms=;
- =:memory-limit=;
- =:mailbox-limit=;
- =:retry-limit=;
- =:inference-limit=;
- =:answer-limit=.

These participate in run-plan identity because they can change terminal outcomes even with identical logical source.

** =:diagnostic-only=

Changes developer-facing diagnostics without changing executable/run-plan behavior.

Examples:

#+begin_src lisp
(pragma :pretty-diagnostics t)
(pragma :warnings :strict)
#+end_src

Diagnostic-only values are excluded from executable/run-plan identity but should be recordable in a build receipt. =:warnings-as-errors= likewise affects build acceptance and should be recorded even if the successful executable's runtime identity is unchanged.

* Artifact and Run-Plan Identity

A build should retain at least:

1. semantic-option digest;
2. code-generation-option digest;
3. runtime-policy digest;
4. diagnostic/build receipt.

Logic run-plan identity continues to include the concrete backend/build/adapter/package/mapping/proof evidence required by STAR-LANG-RESEARCH-022 and STAR-LANG-RESEARCH-026.

Changing:

#+begin_src lisp
(pragma :pretty-diagnostics t)
#+end_src

should not invalidate an otherwise identical executable/run-plan cache.

Changing:

#+begin_src lisp
(pragma :backend :swi-prolog)
#+end_src

or:

#+begin_src lisp
(pragma :inference-limit 500000)
#+end_src

must invalidate identities that depend on those semantic/runtime-policy values.

* No Compile-Time Escape Hatches

Ordinary StarLang pragmas must never provide equivalents of:

#+begin_src lisp
(eval ...)
(load ...)
(shell ...)
(require-native-library ...)
#+end_src

They also must not provide unrestricted compile-time filesystem access, network access, process execution, environment reads, host package lookup/interning, arbitrary Common Lisp calls, arbitrary compiler/linker flags, native-library loading, or engine-native source evaluation.

Pragma arguments are closed typed literals only.

This does not sandbox ordinary StarLang runtime capabilities out of existence. Actors/adapters remain able to perform authorized filesystem, network, process, scraping, database, and other runtime effects through declared capabilities and deployment policy. The restriction is specifically against using compiler pragmas as an ambient compile-time escape hatch.

* Trusted Compiler Extensions

If trusted compiler extensions are introduced later, they must be a distinct privileged mechanism, for example a reviewed digest-locked compiler plugin installed by the operator.

Such an extension should have an explicit ID/version/digest, deterministic behavior contract, declared compile-time capabilities, registered option descriptors, inclusion in compiler/build identity, and security review.

Ordinary source cannot establish trust through a pragma.

* Rejected Designs

** Nim punctuation

Rejected:

#+begin_example
{. optimize: speed .}
{. backend: swi-prolog .}
#+end_example

Reason: StarLang is Lisp-family source and can represent compiler data directly with lists.

** Arbitrary property-list option bag

Rejected:

#+begin_src lisp
(actor crawler
  (:options
   :optimize :speed
   :backend :swi-prolog
   :anything-at-all 42)
  ...)
#+end_src

Reason: it obscures option typing, scope, provenance, duplicate handling, diagnostics, and authority.

** Bundled =pragmas= form

Rejected for V1 because it adds a second entry grammar and weakens per-option source precision without a demonstrated benefit.

** =with-pragmas= blocks

Rejected/deferred for V1 because module/declaration/operation boundaries already provide useful scope and arbitrary expression-local policy creates substantial semantic complexity.

** Nested backend tuning

Rejected:

#+begin_src lisp
(pragma :swi
  (:tabling :incremental)
  (:inference-limit 500000))
#+end_src

Flat namespaced keys preserve the uniform grammar.

** Silent unknown pragmas

Rejected. Unsupported or misspelled options are errors.

** Same-scope last-one-wins

Rejected. Duplicate canonical option names within one scope are errors.

** Backend-specific tuning under =:auto=

Rejected in V1. Generic requirements drive =:auto=; engine-specific tuning requires an explicit matching pin.

** Source-defined arbitrary pragmas

Rejected for ordinary StarLang source. Trusted compiler extensions are privileged installed components.

** Generic CLI override above deployment policy

Rejected. CLI inputs normalize into typed project/deployment inputs and cannot bypass deployment restrictions.

** Compile-time effect pragmas

Rejected:

#+begin_src lisp
(pragma :shell "generate.sh")
(pragma :load "plugin.lisp")
(pragma :fetch "https://example.test/compiler-extension")
#+end_src

Compilation should remain deterministic interpretation of source/configuration rather than ambient-authority execution.

* Footnotes and Glossary

- *Pragma* — Closed StarLang source data that requests a registered compiler option; it is interpreted by the compiler and is not executable host code.
- *Pragma descriptor* — Compiler-owned typed metadata defining one option's schema, legal scopes, resolution rule, authority model, reproducibility class, and diagnostics.
- *Source option environment* — Normalized inherited map of project/module/declaration/operation option contributions before deployment constraints.
- *Deployment restriction* — Operator-controlled constraint that can deny or narrow source requests and cannot be overridden by ordinary source.
- *Reproducibility class* — =:semantic=, =:code-generation=, =:runtime-policy=, or =:diagnostic-only= classification used to determine identity/cache effects.
- *Namespaced pragma* — Compiler-registered backend-specific option such as =:swi/tabling=; the slash is part of the option key, not a Common Lisp package escape.
- *Safety floor* — Minimum verification or semantic requirement that lower-precedence source cannot weaken.
- *Resource ceiling* — Maximum runtime resource allowance imposed by deployment policy.
- *Materialized run plan* — Immutable executable plan after backend selection, deployment validation, and runtime-policy resolution.
