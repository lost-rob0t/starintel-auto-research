* Research Question

Which transport should heterogeneous StarIntel actors speak, and which persistence or broker systems should back the modern Titanic durable job protocol?

This is deliberately split into two questions. Transport and durability are not the same layer.

* Correction Notice

The initial version of this node over-weighted RabbitMQ's existing deployment and broker semantics, and called NATS JetStream the strongest future adapter. That ranking was incomplete because it did not treat StarIntel's multi-language actor boundary and the already-approved ZeroMQ architecture as first-class constraints.

[[id:starintel-star-server-research-037][STAR-RESEARCH-037 Titanic Polyglot ZeroMQ Transport Correction]] records the correction in detail.

The corrected conclusion is:

- ZeroMQ / ZMTP is the canonical cross-language Titanic worker transport;
- Titanic owns durable job state and result retention above the transport;
- RabbitMQ remains an existing broker, document/event path, and optional adapter/internal scheduling aid;
- NATS JetStream is useful comparative research but is not a planned StarIntel transport;
- LMDB remains a candidate embedded Titanic journal backend rather than a worker-facing protocol.

* Evaluation Criteria

The system must be judged against StarIntel's actual architecture:

- Common Lisp, Nim, Python, and JavaScript/TypeScript actors;
- future actors in additional languages without redesigning the wire contract;
- process and host boundaries;
- durable disconnected job submission and result retrieval;
- at-least-once logical execution;
- explicit acknowledgement after required side effects;
- competing workers and horizontal scaling;
- capability routing;
- worker readiness and backpressure;
- bounded retry and terminal failure;
- cancellation and deadlines;
- idempotency and fencing;
- local-first deployment;
- compatibility with existing Sento, Star Router, RabbitMQ, CouchDB, and Star-Lang work;
- no requirement that every language have a high-quality client library for one specific broker.

* ZeroMQ / ZMTP

** Why it fits the worker boundary

ZeroMQ is a brokerless messaging library and ZMTP is its interoperable wire protocol. The ZeroMQ ecosystem has bindings or implementations in many languages, while the native =libzmq= API provides a C-callable fallback for languages where a high-level binding is missing or weak.

That matters directly for StarIntel:

- Common Lisp can use the already-researched PZMQ path or a narrow maintained CFFI binding;
- Nim has direct C foreign-function interoperability, so a narrow =libzmq= binding is feasible without depending on a broker-specific Nim client;
- Python has mature PyZMQ;
- JavaScript/TypeScript has a maintained Node.js ZeroMQ binding;
- future languages can target ZMTP or the C API without changing =star.titanic/1=.

The approved StarIntel ADR already selected ZeroMQ at boundaries requiring language independence, process separation, routing identity, mobility, or failure containment.

** Socket pattern

Use ROUTER/DEALER for Titanic worker traffic.

ROUTER owns worker routing identities and can dispatch to a selected ready worker. DEALER allows asynchronous receive/send behavior without REQ/REP lockstep.

Do not use PUB/SUB for required job completion. Do not use PUSH/PULL when the protocol needs addressed cancellation, result correlation, or worker identity.

** ZeroMQ is not durable

ZeroMQ's queues are memory-backed transport state, not a durable job ledger.

That is not a blocker. Titanic itself supplies the durability layer:

1. persist admission;
2. acknowledge =job_id=;
3. dispatch an attempt over ZeroMQ;
4. persist state transitions;
5. receive result/error;
6. persist terminal outcome;
7. serve disconnected result lookup.

The architecture therefore preserves ZeroMQ's simple polyglot transport without pretending its socket queues are durable storage.

* RabbitMQ

RabbitMQ remains a major StarIntel component.

The current server already has:

- durable topic exchanges;
- document ingest/new/update routes;
- explicit ACK/NACK settlement;
- dead-letter queue support;
- worker-local connections;
- prefetch/backpressure;
- target routing;
- document recursion.

Those capabilities remain useful.

The correction is architectural: RabbitMQ should not define the public Titanic worker protocol merely because it is already present.

Use RabbitMQ for:

- current document/event traffic;
- a bridge feeding jobs into Titanic;
- durable downstream StarIntel document output;
- optional internal scheduler experiments where broker semantics help;
- integration with legacy/existing actors already written for AMQP.

Do not put AMQP delivery tags, exchange names, routing keys, channel state, or queue arguments in the stable Titanic actor envelope.

* NATS JetStream

JetStream is the persistence/stateful-consumer subsystem inside NATS.

It adds:

- persisted streams;
- durable consumers;
- explicit acknowledgement;
- redelivery;
- work-queue retention;
- delivery limits;
- backoff;
- pull-based consumption and flow control.

Mechanically, those features resemble a durable job queue and therefore make JetStream useful comparative research.

However, adopting it would add a new distributed broker beside RabbitMQ and would not improve StarIntel's weakest language boundary. The official NATS maintained client list includes Go, Java, .NET, Rust, JavaScript, Python, and C, among others, but Common Lisp and Nim are not first-class maintained entries.

Because StarIntel already approved ZeroMQ specifically for language/process boundaries, JetStream should not be carried forward as a planned future Titanic adapter by default.

Reopen that decision only if a concrete later requirement calls for NATS independently of Titanic.

* LMDB

LMDB appeared directly behind Titanic in the recovered 2023 diagram.

That remains technically plausible because only the Titanic coordinator needs to access the journal. Worker languages do not need LMDB support.

Candidate uses:

- job state record;
- attempt record;
- idempotency receipt;
- worker/capability snapshot cache;
- retained result index;
- dead-letter and replay metadata;
- local single-node durable queue index.

Required evaluation:

- crash recovery after committed and uncommitted transitions;
- single-writer behavior under concurrent job admission;
- read scaling;
- transaction size and result retention;
- compaction/growth behavior;
- process restart and file corruption handling;
- deterministic export/replay;
- backup/restore;
- migration/versioning.

LMDB must not become a second hidden distributed authority. It is appropriate as a local Titanic-owned journal backend.

* SQLite

SQLite should be the comparison baseline for an embedded journal even if LMDB wins.

It provides transactions, a familiar inspection path, schema migration tooling, and straightforward state-machine constraints. LMDB provides a different performance/concurrency model.

Benchmark both with the actual Titanic state transitions instead of deciding from generic database throughput numbers.

* Kafka

Kafka is a durable partitioned event log. It is excellent for replay, high-throughput streams, ordering within partitions, and independent consumer groups.

Titanic's core problem is narrower:

- submit one logical job;
- durably retain its state;
- choose one capable actor worker;
- retry or terminate;
- retrieve one result later.

Kafka can model that, but it adds partition/offset semantics that do not improve the polyglot worker boundary and are unnecessary for v1.

Keep Kafka as a possible future event-stream/export backend, not Titanic v1.

* Temporal

Temporal is a durable workflow platform, not merely a message transport.

It is useful when the central problem becomes long-running multi-step orchestration with durable histories, timers, and activity retries.

Adding it for Titanic would create another execution model beside Sento, Star-Lang, Star Router, ZeroMQ, and StarIntel's own job state.

Do not add it for v1.

* Stable Titanic Boundary

The public durable API should expose semantics such as:

#+begin_example
submit(job) -> accepted(job-id) | rejected | unknown-outcome
status(job-id) -> state
result(job-id) -> result | pending | failed | cancelled | unknown
cancel(job-id) -> requested | terminal-state
close(job-id) -> retention-released
replay(dead-letter-id) -> new-attempt-lineage
#+end_example

The worker transport should expose versioned operations such as:

#+begin_example
HELLO
READY
JOB
ACCEPTED
HEARTBEAT
RESULT
ERROR
CANCEL
CANCELLED
#+end_example

Transport-specific identifiers stay outside the stable durable envelope.

* Required Language Interoperability Tests

Before promotion to implementation, prove at least:

1. Common Lisp ROUTER <-> Python DEALER;
2. Python ROUTER <-> Common Lisp DEALER;
3. Common Lisp ROUTER <-> Nim DEALER;
4. Nim ROUTER <-> Common Lisp DEALER;
5. Common Lisp ROUTER <-> JavaScript DEALER;
6. mixed Common Lisp/Nim/Python/JavaScript workers in one capability pool;
7. binary multipart frame equality;
8. canonical control/header decoding equality;
9. identical unknown-version rejection;
10. disconnect/reconnect without cross-language state disagreement;
11. cancellation and stale-attempt handling across different worker languages;
12. CURVE/ZAP interoperability when secure remote transport is enabled.

* Recommendation

**Titanic v1 should be a durable job coordinator and journal using ZeroMQ ROUTER/DEALER as the canonical polyglot worker transport.**

Keep RabbitMQ integrated as the existing StarIntel broker and bridge for documents/events. Evaluate LMDB and SQLite as first embedded journal backends. Do not introduce JetStream, Kafka, or Temporal merely to obtain queue semantics StarIntel can already provide while preserving its approved language-independent ZeroMQ boundary.

This ranking is the corrected decision and supersedes the earlier RabbitMQ-primary/JetStream-secondary ranking.
