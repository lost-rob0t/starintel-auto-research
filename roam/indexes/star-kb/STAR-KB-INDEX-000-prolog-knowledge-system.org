* Scope

This index tracks the shared symbolic knowledge system across its proper repository boundaries. The ARADR control plane is =lost-rob0t/starintel-auto-research=. The product implementation repository is =lost-rob0t/star-kb=. Runtime execution may occur through =lost-rob0t/prolog-query-server=, direct/native Prolog actors, or StarLang logic actors using the StarLang logic protocol/IR. PQS is therefore an important runtime and publication target, not the exclusive semantic authority for reusable rules.

Git remains the authority for reviewed reusable source knowledge. PQS/CouchDB remains authoritative for PQS runtime releases, but not for the meaning of every reusable =star-kb= rule. Direct actor/session observations or fact deltas do not automatically become canonical shared knowledge.

* Operational Follow-up Research Gate

[[id:star-kb-design-001-canonical-knowledge-authoring-query-plane][STAR-KB-RESEARCH-002]] now resolves its previous seven operational questions with the following preferred dispositions:

- normal production activation should preserve roughly 25% headroom beneath active PQS hard ceilings; with current defaults this implies soft thresholds near 7,500 documents, 12 MiB per loaded KB/release, 192 KiB per document, and 1.5 MiB per request;
- same-KB throughput has no fixed QPS answer: treat the serialized path as a queue and regard sustained mutex utilization near or above 70% as the practical pressure point, then route suitable actor-private work to direct/local logic or parallel immutable workers;
- large relational/reused actor evidence should eventually use bounded query/session-local *ground-data* fact overlays rather than mutating canonical packages or forcing everything through giant goal arguments;
- the first probabilistic escalation should be a separate calibrated model/fusion component; general probabilistic programming should not be inserted into the safe PQS builtin surface, while cplint/ProbLog remain sandboxed benchmark candidates if needed;
- runtime multi-KB imports remain deferred until duplicated shared modules measurably harm memory, reload time, or release churn; any future imports must be immutable digest-pinned dependencies, never floating active releases;
- a first-party dialect corpus should use purpose-separated consent, coarse/age-banded exposure history, finite raw retention, deletion while controlled, and aggregate/derived publication by default instead of raw participant material;
- deterministic content hashes remain package/release identity, while future production trust should use detached signed attestations over exact source, compiler, mapping, dependency, test, provenance, semantic-profile, and runtime evidence.

The operational follow-up remains =PENDING= operator review. Numeric thresholds are defaults/headroom policy to be validated against benchmarks, not evidence that current production hardware has already been measured.

* Portable Rule-Reuse Research Gate

[[id:star-kb-research-004-portable-rule-reuse-across-logic-actors][STAR-KB-RESEARCH-004]] changes an important assumption: a =star-kb= rule must not become reusable only by being translated into PQS documents and then queried over HTTP.

Current StarLang source materially supports this direction. =star-logic-protocol= already models backend identities for SWI-Prolog, LISA, and N-Prolog, selects backends by semantic profile/capabilities/limits, and opens logic sessions using package identity. =star-logic-ir= carries digest-locked package/version and independent mapping identity. This provides an existing cross-backend join point for future =star-kb= packages instead of requiring a second actor-logic abstraction.

The current SWI adapter is not yet a complete rule/query backend: it deliberately implements worker identity, MQI transport, trusted bootstrap, health, and lifecycle but does not yet expose portable query operations or fact mutation. That is an implementation gap to be handled only after design approval, not evidence against the portability model.

The research-supported property is:

#+begin_src text
author/version one logical package
        -> materialize for PQS
        -> materialize for direct Prolog actor
        -> materialize for StarLang logic backend
        -> prove semantic parity for every claimed compatible backend
#+end_src

The canonical package cannot silently rely on engine-specific semantics while claiming portability. StarLang's existing semantic-profile and capability model is the natural place to express backend compatibility; exact =star-kb= source/mapping schemas remain design work.

* Current Dialect Research Gate

[[id:star-kb-research-003-dialect-enrichment-corpus-inference-evidence][STAR-KB-RESEARCH-003]] answers the prior conceptual dialect questions while retaining the research-only gate. The research-supported first inference baseline is *weighted/salient evidence* rather than equal counting.

The current evidence decomposition is:

#+begin_src text
regional association
  * feature salience
  * source reliability
  * exposure relevance
  - redundancy/conflict penalties
#+end_src

Salience should be learned from corpus distributions where possible rather than assigned because a feature merely appears regional. A weighted score is not automatically a calibrated probability. Weak or conflicting evidence must be allowed to abstain.

The portability requirement does not change that evidence model. It means the same reviewed dialect association/salience/reliability rules should be reusable whether a dialect actor uses PQS, a direct Prolog worker, or a StarLang logic backend.

The dialect research conclusion remains =PENDING= operator review. No dialect actor design, corpus schema, frozen scoring formula, API contract, numeric weights, confidence thresholds, or implementation contract is authorized by this node.

* Remaining Empirical and Permission Checks

The remaining work is measurement, permission, or cross-runtime compatibility evidence rather than conceptual ambiguity:

- benchmark PQS load time, RSS, inference latency, proof size, and concurrent same-KB throughput at realistic clause shapes and the new soft-headroom points;
- learn feature salience, signed regional association, redundancy penalties, and abstention thresholds from first-party or otherwise compatible corpora;
- calibrate weighted scores and measure selective accuracy/risk versus coverage on speaker-disjoint, geographic-holdout, source/domain-holdout, and time-holdout data;
- establish per-source rights before promoting non-first-party source material or derived values into unrestricted =star-kb= packages;
- measure the amount of independent salient evidence needed before text or speech inference stops abstaining;
- identify the smallest useful semantic profile shared by PQS and direct SWI-Prolog execution;
- prove equivalent fixture answers across every runtime that claims compatibility with a portable =star-kb= package;
- benchmark when ephemeral fact overlays outperform goal arguments for actor workloads;
- measure duplicated-module memory/reload cost before implementing runtime multi-KB imports;
- review the first-party collection/retention policy against applicable deployment requirements before launch;
- prototype detached attestation verification before making signatures a production activation requirement.

These are validation gates for later design/implementation, not permission to start implementation now.

* Existing Design Decision Under Review

STAR-KB-001 V0.1 currently proposes restricted readable Prolog as knowledge source, deterministic compilation to PQS safe JSON AST, bundle dependency closure, immutable PQS releases, staging/analyze/query/explain/activation checks, and rollback.

That design remains pending and has not been approved. The operational answers in STAR-KB-RESEARCH-002 plus STAR-KB-RESEARCH-003/004 must now be reconciled before approval: the design should preserve runtime headroom, leave room for ephemeral actor facts, keep probabilistic/model fusion outside the safe PQS core by default, defer multi-KB imports until measured, carry first-party corpus policy as a separate later consumer gate, support detached attestation later, and ensure canonical reusable semantics are not PQS-only.

* Deferred Research/Design Questions

Remaining later questions are implementation-scale or post-baseline choices rather than permission to implement now:

- exact portable core semantics and backend-specific extension policy;
- mapping from =star-kb= package identity into StarLang =package-id/package-digest/mapping-id/mapping-digest=;
- direct Prolog actor package-loading and trust boundary;
- cross-runtime conformance fixture and proof-equivalence requirements;
- safe tabling if measured workloads require it;
- exact query/session ephemeral-fact wire format if measurements justify it;
- exact native multi-KB/runtime import mechanism if duplication becomes material;
- local/direct versus PQS execution-selection policy;
- exact signing key management / threshold policy after detached attestation prototype;
- probabilistic/neural-symbolic integration only if weighted-salience benchmark evidence justifies the complexity.

None of these are permission for an implementation agent to expand V0.1 scope or start the dialect actor.

* Footnotes and Glossary

- *ARADR control plane* :: The research/design/implementation-state documents recording what was researched, what is awaiting approval, and what implementation is active. Here it lives in =starintel-auto-research=.
- *PQS* :: =prolog-query-server=.
- *KB* :: Knowledge base, a named collection of facts and rules.
- *Logic package* :: A versioned/digest-identified reusable unit of logical semantics that can be materialized for one or more eligible execution backends.
- *Materialization* :: Translation/loading of the same logical package into a concrete runtime representation without silently changing intended semantics.
- *Semantic profile* :: A named behavioral contract a logic backend declares it can execute; current StarLang backend selection uses semantic profiles and capabilities.
- *Backend mapping* :: Independently identified/versioned mapping from portable logical package semantics onto one concrete backend.
- *Semantic parity* :: Evidence that one package has equivalent defined behavior across the runtimes claimed to support it.
- *Bundle* :: Consumer-facing package of source modules plus transitive dependencies; the existing V0.1 design proposes publishing one bundle as one PQS release, but portability research now requires that PQS not be the only materialization.
- *Release* :: Immutable version of one runtime knowledge materialization, such as a PQS KB release.
- *Canonical knowledge* :: Reviewed reusable facts/rules, distinct from one investigation's observations.
- *Weight* :: Numeric evidence importance/reliability used in scoring; it is not automatically a probability.
- *Salience* :: How discriminative a feature is across candidate dialect regions or varieties.
- *Evidence mass* :: The amount of sufficiently independent weighted salient evidence available for a candidate, distinct from raw token count or audio duration.
- *Ephemeral fact overlay* :: Bounded query/session-local ground data supplied to a logic runtime without mutating the immutable package/release.
- *Attestation* :: Detached signed evidence describing who/what built or approved an exact content digest and under which build/test/provenance conditions.
- *Abstention* :: Returning insufficient evidence rather than forcing a region when evidence is weak, sparse, or conflicting.
- *Dialect enrichment* :: Analysis that attaches evidence-backed regional-language features or candidates to an input while preserving uncertainty; it is not synonymous with exact geolocation.
- *Implementation slot* :: The one active approved design copy under =roam/implement/<project>/= used to track actual implementation work.
