* Research Question

What remains to satisfy authenticated target-lease HTTP and execution enforcement now that the backend-neutral lease protocol and Valkey adapter are implemented and hardened?

* 2026-08-29 Current-State Refresh

The original research correctly separated HTTP/application authority from storage authority, but it predates substantial implementation in =starintel-server=. Current source still contains the backend-neutral lease protocol, Valkey adapter, contract tests, and real-Valkey integration tests. Recent lease-store history records cluster-safe listing, corrupt-record fail-closed behavior, and green contract/integration evidence. Issue 32 must not redesign lease storage or reimplement fencing-token allocation.

Repository search on the current server baseline finds the lease protocol/store implementation but no implemented =target-leases= HTTP route/application-service surface. The open server #32 therefore remains a real integration gap rather than stale bookkeeping.

#+begin_example
HTTP or embedded caller
  -> authenticated service-call context
  -> target-lease application service
  -> existing lease-store protocol
  -> existing Valkey adapter

Target dispatch
  -> locking policy
  -> lease authority validation/acquisition
  -> immutable execution authority
  -> local/Rabbit delivery
  -> fenced side-effect boundary
#+end_example

The storage protocol remains authoritative for acquire/renew/release/revoke/get/list outcomes. HTTP code translates those typed outcomes; it does not inspect Valkey keys or scripts.

* Concrete Remaining Gaps

** Thin authenticated application service

Issue #32 still needs one service layer shared by HTTP and embedded callers. Every mutating/inspection operation receives explicit principal, capability/scope, correlation identity, idempotency identity where applicable, and one propagated deadline. Process-local invocation does not bypass authorization.

** HTTP projection

Expose versioned lease operations as adapters over that service. Preserve stable distinctions for conflict, stale fence/precondition, hidden/not-found, authorization denial, overload, backend unavailable, known timeout, and uncertain mutation outcome. Problem responses must not leak backend keys, credentials, stack traces, or another owner's private metadata.

** Dispatch authority

A target requiring locking must not reach local actor or Rabbit publication without an active authority matching the canonical target. User-supplied JSON cannot manufacture the authoritative lease envelope.

** Stale-fence enforcement

The most important remaining proof is downstream, not HTTP routing: generation N may continue computing after lease loss, but once generation N+1 exists, N cannot make an authoritative side effect. Persistence/publication/settlement boundaries must consume the fenced execution authority rather than trusting actor liveness.

** Recovery and races

Server #33 remains the dedicated expiry/crash/race matrix. #32 should expose enough typed authority and integration seams for #33 to prove renew-vs-expiry, reacquire, stale completion, and restart behavior without duplicating the race harness inside HTTP tests.

* v0.9 / StarLang Reconciliation

This refresh does not introduce StarLang syntax. Lease acquisition and fencing are host service/runtime authority. StarLang-defined actors may receive typed execution authority and declare that a capability requires locking, but they cannot mint fencing tokens, bypass the lease service, or reinterpret backend state.

The StarIntel v0.9 document boundary remains unchanged: accepted documents/results still pass canonical validation/persistence rules. A lease token is execution authority metadata, not a replacement for document provenance, authorization, or schema validation.

* Design Consequences

The existing STAR-SERVER-032 design remains directionally correct but must be narrowed around the implemented backend reality:

1. reuse =source/leases/protocol.lisp= rather than designing another lease algebra;
2. reuse the Valkey adapter and existing contract/integration tests;
3. implement service-context authorization before route/backend access;
4. make HTTP and embedded callers project the same service result;
5. carry immutable execution authority into target delivery;
6. enforce fencing at side-effect acceptance;
7. leave exhaustive crash/race validation to #33 while providing the required seams.

* Adversarial Review

Rejected:

- HTTP routes calling Valkey directly;
- a second lease protocol because the existing backend contract is already implemented;
- treating successful authentication as =targets:lease= authorization;
- trusting lease/fence fields copied from caller-controlled target JSON;
- checking a fence only at dispatch time and not again when effects become authoritative;
- ACKing stale Rabbit work as successful output before fenced effects are rejected;
- using actor/process liveness as proof that a lease is still current;
- letting embedded Common Lisp callers bypass the same authorization contract;
- folding #33's complete chaos/race matrix into the first HTTP implementation slice;
- adding StarLang or Prolog authority for host-level lease mutation.

* Proposed Implementation Handoff

Owning repository: =lost-rob0t/starintel-server=, issue #32.

Dependency order:

1. pure target-lease application-service result/context contract over a fake existing lease-store protocol;
2. authorization/scope + idempotency/deadline behavior with zero HTTP dependency;
3. versioned HTTP adapter and problem/success projection;
4. target-dispatch authority envelope for required-lock targets;
5. one fenced side-effect acceptance seam proving stale generation rejection;
6. Rabbit/local equivalence fixtures;
7. hand the expanded expiry/crash/race matrix to #33.

Mandatory first RED: a fake lease store that records invocation plus an unauthorized service-call context. Untouched current server must fail because no target-lease application service exists; GREEN must return typed authorization denial and prove the store was invoked zero times. A sibling fixture must prove an authorized embedded caller and HTTP projection consume the same service result algebra rather than separate lease logic.

Implementation authorization remains =PENDING / AWAITING_OPERATOR_APPROVAL=.
