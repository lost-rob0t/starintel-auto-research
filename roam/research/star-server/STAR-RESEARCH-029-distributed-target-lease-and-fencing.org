* Research Question

What exact semantics must StarIntel[fn:starintel] guarantee when multiple HTTP clients, service instances, recurring timers, local actors, and RabbitMQ[fn:rabbitmq] consumers may attempt to execute the same target concurrently?

The answer must remain correct when messages are duplicated, processes pause, responses are lost, leases expire, a former owner resumes, the key-value backend fails over, and downstream storage receives writes from both an old and a new worker.

* Repository Findings

The current target actor routes a target immediately to a registered local actor or publishes it to RabbitMQ. Recurring targets are scheduled by a process-local wheel timer. There is no ownership claim before dispatch, no lease identity in the target envelope, and no fencing check before publishing or persistence.

That means two server instances can independently load and schedule the same recurring target. RabbitMQ redelivery can also cause the same logical target work to execute again. Explicit RabbitMQ acknowledgement prevents silent message loss, but acknowledgement alone does not establish exclusive target ownership.

The current runtime uses process-global actor, timer, producer, CouchDB, and HTTP objects. A target lease therefore cannot be treated as a field local to one actor. It must be carried through the execution envelope and verified at every side-effect boundary.

* Core Findings

** A lease grants temporary authority, not permanent ownership

A lease[fn:lease] is a time-bounded authority record. It lets another worker acquire the same resource after the prior owner fails or stops renewing. The classic lease model depends on an explicit time authority and bounded assumptions about expiration.[fn:gray-leases]

The lease record answers: “Who may attempt work now?” It does not by itself prevent a paused or partitioned old worker from resuming later.

** Fencing prevents stale work from committing

A fencing token[fn:fencing-token] is a monotonically increasing integer issued on every successful acquisition. The newly acquired token must be larger than every token previously issued for the same canonical target key.

Every authoritative write must compare the supplied token with the highest token already accepted for that protected resource. A lower token is rejected even when the old worker still has a valid-looking lease identifier.

The central rule is:

#+begin_example
accept write only when incoming fencing token >= stored accepted fencing token
then atomically store the incoming token with the write
#+end_example

For operations that must be unique per generation, equality with the active token may be required. For monotonic document updates, greater-than-or-equal can be correct when the write itself atomically advances the accepted token.

** Fencing must be enforced outside the lease store

The lease store issues fencing tokens. It cannot stop stale code from writing directly to CouchDB, publishing RabbitMQ results, acknowledging work, updating job state, writing graph edges, saving attachments, or invoking another external service.

The application architecture must therefore place fencing gates at every side-effect boundary[fn:side-effect-boundary]. A direct backend call that bypasses the gate is a correctness bug.

** A lease identifier and fencing token solve different problems

A random lease identifier proves which acquisition a renew or release request refers to. It prevents a caller from deleting a newer lease merely by knowing the target key.

The fencing token orders acquisitions. It prevents delayed work from an older acquisition from committing after a newer acquisition exists.

Both values are required.

** RabbitMQ delivery is not ownership

RabbitMQ may redeliver a message after connection loss or a consumer crash. A consumer can receive a target envelope after the envelope's lease expired or after another owner acquired a larger token.

The consumer must validate the execution authority before beginning expensive work and must validate again immediately before each authoritative side effect. A successful validation at dispatch time is not sufficient for a long-running actor.

** Recurring timers require lease acquisition per run

A process-local timer may wake on multiple server instances. The timer callback should create or reference a run identifier and request a lease. Only the successful owner dispatches the target.

The timer itself is not the owner. It is merely an acquisition trigger. A recurring schedule can therefore exist redundantly on every service instance without causing duplicate accepted results.

** Renew-after is guidance, expiry is authority

The server should return both =expires_at= and =renew_after=. =renew_after= is an earlier recommended renewal point calculated from policy, expected network delay, and jitter. It is not a second expiration timestamp.

A worker that misses =renew_after= may continue only while its lease remains active and its local execution policy permits. A worker that reaches uncertainty about renewal must stop side effects until ownership is re-established.

** Lost responses create uncertain ownership

An acquire or renew operation may commit and lose its response. The request identifier must recover the original result. The client must retry with the same identifier rather than issue a second logical request.

When the service cannot determine whether a mutation committed before the request deadline, it must return an explicit unknown-outcome result. The actor pauses work and resolves ownership through request replay or a strong lease read.

* Canonical Lease Identity

The lease key must use canonical identifiers already validated by StarIntel document contracts:

- tenant or program security boundary;
- dataset when target identity is dataset-scoped;
- normalized actor or workflow name;
- operation class when one target may permit independent classes of work;
- normalized target identity.

Do not lock on raw URL spelling, raw username casing, unnormalized phone numbers, aliases, display names, JSON serialization, or caller-created backend keys.

A target-normalization service should produce the canonical target identity before authorization and acquisition. The same identity must appear in the target record, lease key, execution envelope, audit event, and fencing gate.

* Lease Record Findings

A logical active lease contains:

#+begin_src json
{
  "schema": "starintel.target-lease/1",
  "canonical_key": "opaque-canonical-key",
  "lease_id": "lease_01",
  "owner": {
    "principal_id": "principal_01",
    "service_instance_id": "server_01",
    "actor_instance_id": "actor_01"
  },
  "fencing_token": 42,
  "state": "active",
  "acquired_at": "2026-08-06T12:00:00Z",
  "renewed_at": "2026-08-06T12:00:20Z",
  "expires_at": "2026-08-06T12:00:40Z",
  "maximum_expires_at": "2026-08-06T12:10:00Z",
  "execution_id": "run_01",
  "trace_id": "trace_01",
  "metadata": {}
}
#+end_src

The active backend record may disappear on expiration. Historical states such as released, expired, and revoked belong in an append-only audit or execution journal rather than requiring permanent lock keys.

The fencing counter must survive release and expiration. A restored or replaced backend must never issue a token lower than one previously accepted by downstream storage.

* State Machine Findings

The application-level state machine is:

#+begin_example
ABSENT
  -> ACTIVE
ACTIVE
  -> ACTIVE-RENEWED
  -> RELEASED
  -> REVOKED
  -> EXPIRED
RELEASED | REVOKED | EXPIRED
  -> ACTIVE with a strictly larger fencing token
#+end_example

The persisted lease-store key may encode only the current active record. The service and audit layers still expose the logical transition that occurred.

Allowed operation outcomes:

| Operation | Current state | Matching owner and token | Outcome |
|-----------+---------------+--------------------------+---------|
| acquire | absent or expired | not applicable | acquire with next token |
| acquire | active | not applicable | conflict |
| acquire replay | any | same request fingerprint | original result |
| renew | active | yes | extend expiry, same token |
| renew | active newer generation | no | stale token |
| renew | expired | formerly matched | expired |
| release | active | yes | delete active record, preserve fence |
| release | active newer generation | no | stale token or not owner |
| revoke | active | administrator policy satisfied | delete active record, preserve fence |

* Split-Brain Findings

Valkey[fn:valkey] uses asynchronous replication by default. =WAIT= and =WAITAOF= improve data safety but do not make failover strongly consistent. A failover can therefore lose an acknowledged lease or fencing-counter update under documented failure windows.[fn:valkey-replication][fn:valkey-wait][fn:valkey-waitaof]

Issue 31 nevertheless selects Valkey as the initial deployable backend. The system must state the operational consequence directly:

- Valkey lease state is suitable only when downstream fencing tokens are persisted in an authoritative system that does not roll back below previously accepted generations;
- a Valkey failover that loses the latest fence value can create token reuse unless recovery advances the counter beyond the highest downstream token;
- strict deployments must configure persistence, replica acknowledgement, minimum replicas, restart behavior, and recovery procedures;
- a later strongly consistent adapter may reduce these operational assumptions without changing target or HTTP code.

The initial Valkey design should use one cluster hash tag per canonical lease key so the active lease, fence counter, and request receipt participate in one atomic script on one slot.[fn:valkey-cluster]

* Target Execution Envelope

Every dispatched target that requires locking must carry an immutable authority block:

#+begin_src json
{
  "target": { "...": "canonical target document or reference" },
  "execution": {
    "execution_id": "run_01",
    "lease_id": "lease_01",
    "canonical_target_key": "opaque-key",
    "fencing_token": 42,
    "lease_expires_at": "2026-08-06T12:00:40Z",
    "owner_service_instance_id": "server_01",
    "request_id": "request_01",
    "trace_id": "trace_01"
  }
}
#+end_src

The envelope is evidence of claimed authority, not final proof. Consumers must validate it against the lease service or against a trustworthy downstream fencing gate before mutation.

* Fencing Enforcement Matrix

| Boundary | Required check |
|----------+----------------|
| Target dispatch | active matching lease exists when manifest requires locking |
| Local actor start | envelope shape and canonical key match target |
| RabbitMQ consumer start | lease is active or policy permits read-only prework |
| CouchDB create/update/delete | compare and persist accepted fencing generation |
| Event or job status update | reject lower generation |
| Result publication | include generation and reject stale generation before publish |
| RabbitMQ acknowledgement | acknowledge accepted completion only after side effects pass fencing |
| Attachment/object storage | generation-bound commit marker or metadata check |
| External irreversible action | revalidate immediately before action; use provider idempotency where available |

Read-only computation may continue after lease loss only when it cannot trigger further side effects and its result is discarded unless a current fencing gate accepts it.

* Lease-Loss Propagation

Actors need an explicit =lease-lost= control message containing the execution identifier, lease identifier, last known token, reason, and detection time.

Possible reasons:

- expired;
- renewal rejected;
- stale token;
- revoked;
- backend unavailable beyond policy;
- unknown renewal outcome;
- runtime draining.

On lease loss an actor must:

1. stop scheduling new side effects;
2. cancel or isolate in-flight external calls when possible;
3. mark uncommitted output as stale;
4. avoid acknowledging success;
5. emit a bounded audit event;
6. terminate or enter a read-only cleanup state.

* Contract-Test Findings

The semantic contract suite must include:

1. one active owner under concurrent acquisition;
2. strictly increasing fencing tokens after release, expiry, revoke, restart, and recovery;
3. stale renew cannot extend a newer lease;
4. stale release cannot delete a newer lease;
5. duplicate acquire with the same request identifier returns the original result;
6. one recurring target scheduled on multiple instances produces one accepted execution;
7. RabbitMQ redelivery does not create a second accepted side effect;
8. a worker paused beyond expiry cannot commit after reacquisition;
9. lease loss reaches the actor before another side effect is accepted;
10. every persistence and result-publication path rejects a lower token;
11. restore procedures cannot silently lower the effective fence generation;
12. target execution without a required lease is rejected before dispatch.

* Decision

Define target leases as time-bounded execution authority paired with a durable monotonic fencing token. Acquire per execution run, carry the lease identity and token through every target envelope, and enforce the token at every authoritative side-effect boundary.

Valkey is the initial backend because issue 31 selects it, but its asynchronous failover limitations must be explicit. Correctness after failover depends on downstream fencing persistence and recovery that prevents fencing-token reuse.

* Footnotes and Glossary

[fn:starintel] StarIntel: A local-first intelligence platform that collects, validates, connects, searches, analyzes, and exports structured documents through actor-based services.

[fn:rabbitmq] RabbitMQ: A message broker used by StarIntel to deliver documents and target work between processes.

[fn:lease] Lease: A temporary grant of authority that expires unless renewed.

[fn:fencing-token] Fencing token: A monotonically increasing number attached to one lease generation. Downstream systems reject lower numbers from stale workers.

[fn:side-effect-boundary] Side-effect boundary: A point where software changes durable state, publishes externally visible data, acknowledges work, or invokes an irreversible external action.

[fn:valkey] Valkey: An open-source in-memory key-value server compatible with the Redis protocol and selected by issue 31 as the initial StarIntel lease backend.

[fn:gray-leases] Cary G. Gray and David R. Cheriton, “Leases: An Efficient Fault-Tolerant Mechanism for Distributed File Cache Consistency,” 1989. [[https://carlstrom.com/stanford/quals/mirror/www-db.stanford.edu/~daswani/quals/Gray89%20-%20Leases.htm][paper mirror]].

[fn:valkey-wait] Valkey, “WAIT.” Documents replica acknowledgement and its failover limitations. [[https://valkey.io/commands/wait/][official documentation]].

[fn:valkey-waitaof] Valkey, “WAITAOF.” Documents local and replica append-only-file fsync acknowledgement and states that it still does not make Valkey strongly consistent. [[https://valkey.io/commands/waitaof/][official documentation]].
