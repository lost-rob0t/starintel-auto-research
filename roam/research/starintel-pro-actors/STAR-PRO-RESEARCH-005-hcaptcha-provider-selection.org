* Question

How should StarIntel select a solver when source actors can encounter open-world CAPTCHA and adjacent browser, device, behavioral, proof-of-work, Web Application Firewall, media, puzzle, custom, and unknown challenges?

* Decision

Do not select one global CAPTCHA provider. Select a solver in two phases:

1. *hard eligibility*: reject every actor that fails one exact requirement;
2. *ranking*: order only eligible actors using the required deterministic sequence.

A provider name alone is never enough. A narrow provider may be the reference implementation for one exact capability and irrelevant to another.

* Phase 1: Hard Eligibility

A solver is eligible only when all applicable predicates pass:

- authenticated requester;
- =captcha:solve= authorization;
- target policy;
- approved purpose;
- provider allowlist;
- issuer;
- challenge family;
- challenge variant;
- integration version;
- required normalized fields;
- required result kind;
- source-session binding;
- network identity or proxy binding;
- cookie requirements;
- user-agent requirements;
- mobile or application-runtime requirements;
- execution class;
- disclosure class;
- provider contract state;
- fixture freshness threshold;
- provider health and circuit state;
- available concurrency;
- deadline feasibility;
- reserved budget.

There is no wildcard that widens reCAPTCHA v2 into v3, hCaptcha standard into Enterprise, Turnstile into Cloudflare Challenge Platform, token into assessment/cookie/coordinates/selections, proxyless into same-network, remote provider into same-session browser execution, automated provider into human-worker disclosure, or unknown into a known issuer.

* Phase 2: Required Ranking Order

Rank eligible actors in this exact order:

1. operator pin;
2. contract confidence;
3. fixture freshness;
4. source-context fidelity;
5. exact-capability downstream acceptance rate;
6. provider health;
7. available concurrency;
8. deadline fit;
9. cost per accepted result;
10. operator preference.

An operator pin chooses only among hard-eligible actors. It cannot override authorization, context, disclosure, contract state, health, deadline, or budget.

Cost is intentionally late. It cannot override authorization, source-context fidelity, disclosure, exact capability, or contract validity. Cost uses downstream accepted results, not provider-completed tasks.

* Execution and Disclosure Classes

| Class | Example | Hard policy implication |
|-------+---------+-------------------------|
| =localAutomated= | local browser, optical-character-recognition, image, or audio actor | preferred when exact capability and resources permit |
| =remoteAutomated= | automated token or recognition provider | approved challenge context leaves local boundary |
| =humanAssistedVendor= | worker-backed task provider | explicit human-worker disclosure approval required |
| =manualOperator= | local review queue | operator availability, bounded artifact, retention, and audit policy required |
| =customFirstParty= | owned test-system solver, test key, or organization-defined challenge | bound to named target policy and schema |

Unknown execution or disclosure class is ineligible.

* Capability State Eligibility

| State | Default selection behavior |
|-------+----------------------------|
| =verified= | eligible when every other hard requirement passes |
| =experimental= | eligible only under explicit experimental policy and bounded use |
| =degraded= | eligible only when the known limitation does not violate this request |
| =invalidContract= | ineligible |
| =disabled= | ineligible |
| =unsupported= | ineligible |

Contract drift is exact-capability-local unless a shared credential, transport, account, provider, or security failure affects every task.

* Source-Context Fidelity

Context fidelity measures whether the solver can preserve the exact source requirements:

- same browser session;
- same cookie state;
- same network identity;
- same user agent;
- mobile application binding;
- Enterprise challenge data;
- bounded page data;
- target-specific action and challenge instance.

A local browser actor normally outranks a remote provider for same-session work after both pass hard eligibility. A lower-cost provider with weaker fidelity does not replace an exact source-context match.

* Acceptance Metrics

Metrics are segmented by exact capability, source-runtime class, and target-policy class:

- provider task completion;
- downstream =accepted=;
- downstream =rejected=;
- =expired=, =replaced=, and =inconclusive=;
- p50 and p95 latency;
- provider and contract errors;
- ambiguous-charge rate;
- cancellation success;
- cost per accepted result;
- result expiry before application;
- redaction conformance.

Provider completion never counts as target acceptance. A broad provider's poor result for one exact task changes that task's rank or state, not unrelated capabilities.

* Deterministic Tie-Breaking

After all ten ranking dimensions, use a stable configured actor priority followed by stable actor ID. Do not use random selection unless an explicit experiment or load-balancing policy is separately approved and journaled.

The chosen capability record, ranking inputs, rejected candidates, and reasons are recorded in redacted attempt metadata.

* Fallback

Fallback is disabled by default. When explicitly enabled:

- the next actor independently passes all hard eligibility checks;
- the prior attempt is terminal or safely cancelled;
- an ambiguous create is never treated as a safe fallback trigger;
- a new attempt ID and budget reservation are created;
- disclosure count and total cost remain within policy;
- deadline still permits the attempt;
- result binding remains compatible;
- every attempt remains visible in redacted telemetry.

The source actor receives only an authorized final result reference and the complete terminal orchestration outcome.

* Speculative Execution

Speculative concurrent attempts are a separate gate and are never implied by fallback. Policy must define:

- allowed exact capabilities;
- maximum concurrent solver count;
- total cost ceiling;
- disclosure authorization for every solver;
- deterministic winner selection;
- loser cancellation;
- late-result deletion;
- ambiguous provider-task handling;
- telemetry and rollback.

- positive and negative hard-match matrix;
- unknown and custom challenge behavior;

- policy, purpose, disclosure, allowlist, budget, health, concurrency, and deadline denials;
- all six capability states;
- exact ten-stage ranking order;
- operator pin eligibility restrictions;
- fixture freshness and context-fidelity precedence;

* Footnotes and Glossary

- *Hard eligibility* — All-or-nothing exact predicates that must pass before ranking.
- *Source-context fidelity* — Degree to which a solver preserves the source session, network, cookies, user agent, mobile runtime, challenge instance, and application binding.
- *Cost per accepted result* — Total capability-specific spend divided by results verified as accepted downstream.
- *Operator pin* — Explicit instruction to prefer one actor only when it remains hard-eligible.
- *Speculative execution* — Concurrent attempts before a prior attempt becomes fallback-eligible.
