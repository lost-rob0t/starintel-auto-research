* APPROVED Objective

Build reusable Common Lisp Model Context Protocol[fn:mcp] and large-language-model tooling libraries first. Then build and conformance-test the full authoritative =starintel-mcp=. Only after that may =starintel-meta-mcp= integrate StarIntel as one of its providers.

The Meta MCP[fn:meta-mcp] is a deterministic information execution plane. It accepts bounded retrieval operations, resolves permitted semantic capabilities to providers, executes a plan, normalizes and fuses results, and returns attributable output.

It is not the StarIntel platform API and it is not an autonomous research agent.

The approved layering is:

#+begin_example
reusable Common Lisp MCP/LLM libraries
        |
        +--> full StarIntel MCP
        |       |
        |       v
        |    StarIntel
        |
        +--> Meta MCP
                search / fetch
                   |
                   +--> full StarIntel MCP
                   +--> SearXNG
                   |      +--> configured web engines
                   |      +--> local YaCy search index
                   +--> external MCP search/fetch providers

future StarIntel A2A Agent
        +--> Meta MCP
        +--> full StarIntel MCP
#+end_example

The intended public search service name may be =search.starintel.actor=, but host placement, network topology, private addresses, credentials, reverse-proxy layout, and deployment routing are outside this public design and belong to downstream infrastructure RAGE work.

* APPROVED Invariants

1. Reusable library systems are implemented before application-specific MCP composition.
2. The full =starintel-mcp= is implemented and its read/search contract passes conformance before Meta MCP may integrate StarIntel.
3. The final =starintel-meta-mcp= package contains tool definitions, composition, configuration, and StarIntel-specific Meta policy only; generic MCP protocol/client/server behavior belongs in reusable ASDF systems.
4. The client-visible Meta surface stays small and semantic. Provider-specific upstream tool names are not mechanically re-exported.
5. Meta exposes exactly the retrieval primitives =search= and =fetch= in this design.
6. Crawl is not part of Meta MCP, is not an implementation phase of PIPELINE-005, and is not required for approval or completion of this design.
7. =research= is not a Meta MCP tool. Iterative research belongs to the future StarIntel Agent exposed through Agent2Agent[fn:a2a].
8. The full StarIntel MCP is the authoritative model-facing interface for StarIntel capabilities, authorization, resource scope, and mutation.
9. Meta never reads or writes CouchDB, Clouseau, internal queues, or other StarIntel persistence internals directly.
10. Search scope is an authority ceiling. A planner cannot invoke a provider outside the caller-selected and authorized information universe.
11. Provider selection is deterministic and capability-based in the first implementation.
12. Adapter identity and physical provider/origin identity are separate so duplicate access paths do not create false corroboration.
13. Search and fetch never silently promote retrieved content into canonical StarIntel data.
14. Partial provider failure is represented explicitly and does not automatically fail a federated request when useful results remain.
15. Raw fetched content and upstream MCP output are untrusted data and cannot expand capabilities.
16. Every output that influences ranking, evidence, or later StarIntel work retains provenance sufficient to reconstruct its retrieval path.
17. The Meta MCP's StarIntel provider adapter talks only to the conformance-tested full StarIntel MCP contract defined by PIPELINE-006.

* APPROVED Reusable Library Systems

System names are semantic boundaries and may be renamed during monorepo reconciliation. The boundaries are normative; exact package names are not.

** =cl-mcp-core=

Owns protocol version negotiation, JSON-RPC[fn:json-rpc] message types, MCP request/result/error/notification/capability types, protocol serialization boundaries, typed protocol conditions, and version-specific conformance fixtures.

It performs no StarIntel routing and no provider-specific search behavior.

** =cl-mcp-transport=

Owns implementation-neutral transport interfaces and shared request metadata. Concrete systems may include =cl-mcp-transport-stdio= and =cl-mcp-transport-http=.

Remote HTTP support must implement the pinned MCP transport requirements, including Origin validation, bounded request handling, authentication integration points, cancellation, and explicit response lifetimes.

** =cl-mcp-client=

Owns initialization/discovery, tool/resource/prompt discovery, request dispatch and correlation, timeouts, cancellation, upstream authentication hooks, typed remote errors, and reconnect/retry policy boundaries.

It must be usable independently of StarIntel.

** =cl-mcp-server=

Owns server capability advertisement/discovery, declarative tool and resource registration, JSON Schema[fn:json-schema] input/output contracts, request validation, dispatch, structured errors, transport-neutral lifecycle, and authorization hook points.

It must support applications other than StarIntel.

** =cl-tool-capability=

Owns semantic capability and provider registration independent of MCP transport.

A provider descriptor contains at least adapter identity, physical origin, semantic capabilities, result kinds, authority class, cost class, freshness, and runtime health. Durable public descriptors contain no secrets.

Example:

#+begin_src lisp
(:provider
 (:id :brave-mcp)
 (:adapter-kind :mcp)
 (:physical-origin :brave)
 (:capabilities (:web-search :news-search :image-search :place-search :fetch))
 (:result-kinds (:web :news :image :place))
 (:authority-class :external-network)
 (:cost-class :metered)
 (:freshness :live)
 (:health :unknown)))
#+end_src

** =cl-exec-plan=

Owns a deterministic execution-plan[fn:execution-plan] abstract syntax tree and executor contract.

Initial node kinds:

#+begin_example
call
parallel
fallback
race
limit
merge
normalize
dedupe
rank
#+end_example

A plan is data. Provider code does not recursively invoke arbitrary providers outside the compiled plan.

The executor supports per-call and whole-plan deadlines, cancellation propagation, bounded concurrency, partial-result collection, typed provider failure, deterministic merge order where required, tracing, and correlation identifiers.

The first planner is ordinary Common Lisp code. Prolog, Prolog-RLM, and model-driven routing are not part of this design.

** =cl-search-model=

Owns one normalized retrieval model shared by HTTP and MCP providers.

A normalized result contains at least a request-local identifier, kind, title, snippet, locator or opaque source reference, source timestamp when known, score when applicable, content hash when available, and one or more provenance records.

A provenance record separates the adapter from the physical provider/origin so two adapters to the same provider cannot be interpreted as independent evidence.

** =cl-search-fusion=

Owns canonical locator normalization, content-hash-assisted duplicate detection, physical-provider/origin deduplication, result clustering, deterministic tie-breaking, preservation of all contributing provenance edges, and a benchmarked fusion strategy such as Reciprocal Rank Fusion[fn:rrf].

Fusion must never interpret two adapters to the same physical provider as two independent confirmations.

** =cl-search-provider=

Defines the provider protocol consumed by the Meta planner and executor:

#+begin_example
provider-capabilities
provider-health
provider-search
provider-fetch
provider-cancel    ; optional
#+end_example

There is intentionally no provider-crawl operation in PIPELINE-005.

** SearXNG adapter

The reusable SearXNG adapter provides broad metasearch and normalized result conversion. The local YaCy index may be searched through SearXNG's YaCy engine. PIPELINE-005 does not define direct YaCy crawl/index control.

** Generic upstream MCP provider adapter

A reusable MCP provider maps discovered upstream tools onto reviewed semantic capabilities. The adapter does not infer authority solely from upstream names or descriptions.

Dynamic tool discovery updates runtime availability, while reviewed semantic mappings determine which upstream tools may satisfy =search= or =fetch= plans.

** Full =starintel-mcp= dependency

PIPELINE-006 owns the full StarIntel MCP contract. It defines StarIntel resources, StarIntel query/mutation tools, service-port boundaries, authorization-aware discovery, and conformance tests.

Meta does not implement those semantics.

** =starintel-mcp-client-adapter=

This adapter uses the generic MCP client and search-provider contracts to access the conformance-tested full StarIntel MCP.

It owns no StarIntel database access. It maps only authorized StarIntel MCP read/search capabilities into Meta retrieval capabilities such as intelligence search and resource fetch.

** Final =starintel-meta-mcp= package

The final package owns only public Meta tool schemas, StarIntel-specific scope and result-kind vocabulary, provider composition/configuration, deterministic planner policy, authorization/scope projection into eligible capabilities, service startup, and health aggregation.

It consumes the generic systems above and the full StarIntel MCP through the client adapter.

* APPROVED Meta Tool Contract

** =search=

Initial semantic shape:

#+begin_src lisp
(:search
 (:query "required string")
 (:scope :auto)
 (:type :auto)
 (:filters ())
 (:limit 20))
#+end_src

Initial scope vocabulary:

| Scope | Meaning |
|-------+---------|
| =auto= | Planner may choose any caller-authorized information universe required by deterministic request classification |
| =web= | Public/external web retrieval only; private StarIntel data is ineligible |
| =archive= | Search retained/indexed web material through approved search providers, including the local YaCy-backed SearXNG path |
| =intel= | Authorized full StarIntel MCP retrieval only; public web providers are ineligible |
| =all= | Union of caller-authorized web, archive, and intelligence universes |

Initial result types may include =auto=, =web=, =news=, =images=, =places=, =documents=, =entities=, and =relations=. Unsupported scope/type combinations fail deterministically rather than silently broadening scope.

=scope= constrains the legal capability set before provider selection. It is not a post-search filter.

** =fetch=

=fetch= retrieves a known result reference or locator through the best eligible retrieval path while preserving provenance.

Resolution may use an authorized StarIntel MCP resource, a retained/indexed copy surfaced by an approved provider, an upstream extraction/fetch MCP capability, or bounded live HTTP retrieval through an approved provider.

The caller can request a stricter scope; resolution cannot broaden it.

* APPROVED Planner and Execution

The planner receives:

#+begin_example
normalized operation
+ requested scope
+ caller authority projection
+ desired result kind
+ filters
+ provider capability registry
+ provider health
+ explicit cost/latency policy
= execution plan
#+end_example

The first implementation uses deterministic rules and fixtures.

Example:

#+begin_src lisp
(:plan
 (:parallel
   (:call :searxng :search ...)
   (:call :starintel-mcp :search ...))
 (:normalize)
 (:dedupe :physical-origin :locator :content-hash)
 (:rank :rrf)
 (:limit 20))
#+end_src

This is execution planning, not autonomous research. A plan does not generate new questions, reinterpret task goals, or decide when an investigation is complete.

* APPROVED Provider Selection and Duplicate Origins

Adapter identity and physical origin are independent fields.

Examples:

| Adapter path | Physical origin | Normal interpretation |
|--------------+-----------------+-----------------------|
| SearXNG -> Brave engine | Brave | one Brave source family |
| Brave MCP | Brave | same source family, richer capability path |
| SearXNG -> non-Brave engine | corresponding upstream engine | independent only if origin differs |
| SearXNG -> local YaCy | local YaCy index | retained/indexed web source family |
| full StarIntel MCP | StarIntel | authorized private intelligence source family |

The planner prefers one route to a physical provider for one ordinary search. Multiple adapters to the same physical origin are used only when explicit fallback, comparison, or capability requirements justify them.

* APPROVED Authority and Service Boundary

The Meta service is a potential confused deputy[fn:confused-deputy] and therefore must not hold unrestricted StarIntel authority on behalf of narrower callers.

Required properties:

1. Caller authentication terminates at a reviewed boundary.
2. The normalized request contains an immutable authority projection with correlation identity.
3. Scope compilation intersects requested scope with caller grants; it never unions new authority.
4. StarIntel operations are sent through the full StarIntel MCP.
5. The full StarIntel MCP performs the authoritative capability/resource decision.
6. Meta does not derive access from route strings, provider names, dataset text, or client-supplied claims alone.
7. Credentials and secret verifier material are never included in normalized results, provenance, public logs, or published plans.
8. The StarIntel MCP read/search surface must pass PIPELINE-006 conformance before Meta integration is considered complete.

The exact token exchange, service identity, credential location, and deployment topology are private implementation/topology concerns.

* APPROVED Failure Semantics

Provider outcomes are typed, including success, partial-success, timeout, rate-limited, auth-denied, unavailable, invalid-result, cancelled, and policy-denied.

A federated search may return =partial-success= when at least one eligible provider produced usable results and no invariant requires all providers. The response identifies degraded provider classes without exposing secrets or private topology.

Fallbacks are bounded and specified by the plan. Providers cannot trigger unbounded recursive retries.

* APPROVED Agent Boundary

The future StarIntel Agent is a separate Agent2Agent service.

Its semantic responsibility is:

#+begin_example
research goal
  -> decide questions and subquestions
  -> search/fetch through Meta MCP
  -> inspect and act on authorized StarIntel state through full StarIntel MCP
  -> identify evidence gaps
  -> iterate within task budget
  -> produce research artifacts
#+end_example

The A2A agent owns iterative reasoning, gap analysis, branch selection, stopping criteria, and research artifacts. Meta MCP remains a bounded information execution plane.

The agent may have additional StarIntel abilities only through the full StarIntel MCP and its normal authorization model.

* APPROVED Monorepo Rule

Implementation lives in one Common Lisp MCP/LLM-tooling monorepo with independent ASDF systems.

Repository layout is non-normative until the target monorepo is selected, but dependency direction is normative:

#+begin_example
protocol/types
   ^
transports   client   server
   ^          ^        ^
   +----------+--------+
              ^
        shared MCP tooling
         /           \
        /             \
full starintel-mcp   search execution/fusion/provider adapters
        \             /
         \           /
          starintel-meta-mcp
#+end_example

No generic lower-level library may depend on =starintel-mcp= or =starintel-meta-mcp=.

* APPROVED Phased Implementation

** Phase 0 — conformance fixtures

- pin the targeted MCP protocol revision
- define protocol/client/server compatibility fixtures
- define normalized result/provenance fixtures
- define execution-plan and cancellation fixtures
- define provider-origin deduplication fixtures
- define fake providers; continuous integration makes no paid provider calls

** Phase 1 — reusable MCP and execution libraries

- implement MCP core/types
- implement STDIO and Streamable HTTP transports
- implement reusable MCP client/server
- implement capability registry
- implement execution-plan AST/executor
- implement search result/provenance and fusion libraries
- prove these systems with non-StarIntel example applications/tests

** Phase 2 — full StarIntel MCP

Execute [[file:STAR-RESEARCH-PIPELINE-006-starintel-mcp-authoritative-platform-interface.org][PIPELINE-006]]. At minimum:

- implement the typed StarIntel service-port/client boundary
- implement the full =starintel-mcp= package on reusable MCP server libraries
- expose authorization-aware StarIntel resource/tool discovery
- implement and test the read-only identity/document/search/view surface
- prove StarIntel resource reads reauthorize independently
- prove unavailable/stubbed StarIntel capabilities stay out of discovery
- publish conformance fixtures suitable for Meta integration

Meta must not use a direct HTTP/CouchDB/Clouseau shortcut while this phase is incomplete.

** Phase 3 — search providers and Meta MCP

- implement SearXNG adapter
- implement generic upstream MCP provider adapter
- implement reviewed capability mappings for initial external search/fetch MCPs
- implement the StarIntel MCP retrieval adapter against PIPELINE-006's conformance-tested interface
- ship Meta =search= and =fetch=
- validate =scope=intel= and =scope=all= through the full StarIntel MCP, not legacy StarIntel routes

** Phase 4 — future A2A agent

- implement reusable A2A protocol/client/server support as separate libraries if needed
- implement StarIntel Agent as a consumer of Meta MCP plus full StarIntel MCP
- place autonomous =research= behavior here, not in Meta MCP

There is no crawl phase in PIPELINE-005.

* APPROVED Acceptance Criteria

1. Every reusable ASDF boundary has a declared API and dependency direction.
2. MCP client and server conformance fixtures cover the pinned protocol revision and transport behavior.
3. A non-StarIntel demo proves the MCP libraries are reusable outside StarIntel packages.
4. PIPELINE-006 defines the full StarIntel MCP and its read/search conformance suite.
5. The full StarIntel MCP read/search surface is green before Meta's StarIntel provider is accepted.
6. Fake SearXNG, upstream MCP, and full StarIntel MCP providers can execute one normalized Meta plan without network access.
7. Provider-origin fixtures prove Brave-through-SearXNG plus Brave-through-MCP is not counted as independent corroboration.
8. =scope=intel= can never generate a public-web provider call in deterministic plan tests.
9. =scope=web= can never generate a private StarIntel MCP call.
10. A degraded provider returns partial results without hiding the degradation.
11. Meta search and fetch never mutate StarIntel.
12. The full StarIntel MCP remains the only Meta path to private StarIntel capabilities.
13. No Prolog-RLM or model planner is required to pass the initial conformance suite.
14. No infrastructure topology, secret, private address, or production credential is encoded in public libraries or public research docs.
15. Downstream infrastructure RAGE receives implementation/topology requirements only after the approved public architecture handoff.
16. No crawl tool, crawl adapter, crawl task, or crawl implementation phase is required or exposed by =starintel-meta-mcp=.
17. No direct StarIntel HTTP route, CouchDB, Clouseau, or queue adapter may masquerade as the Meta StarIntel provider while PIPELINE-006 exists.

* Footnotes and Glossary

[fn:mcp] Model Context Protocol, or MCP: A protocol for exposing model-controlled tools, resources, prompts, and related capabilities through standardized client/server messages.

[fn:meta-mcp] Meta MCP: The StarIntel execution-plane service that composes multiple retrieval providers behind a small semantic MCP tool surface.

[fn:a2a] Agent2Agent, or A2A: A protocol for interoperable remote agents that discover skills and exchange tasks, messages, status, and artifacts.

[fn:json-rpc] JSON-RPC: The request/response message format underlying MCP protocol messages.

[fn:json-schema] JSON Schema: A machine-readable schema language used to validate structured tool inputs and outputs.

[fn:execution-plan] Execution plan: A bounded data structure describing which providers to call, how calls compose, and how their outcomes are normalized and fused.

[fn:rrf] Reciprocal Rank Fusion, or RRF: A ranking method that combines ordered result lists by adding reciprocal functions of each result's rank.

[fn:confused-deputy] Confused deputy: A security failure where a service with broad authority is tricked into using that authority for a caller who lacks it.
