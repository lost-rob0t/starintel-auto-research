* Scope

NopeCHA exposes two materially different service surfaces:

1. the Token API, which returns issuer verification tokens for exact supported integrations; and
2. the Recognition API, which returns text, classifications, coordinates, selections, or provider-specific answers.

The surfaces require separate capability registrations, request mappers, result validators, budgets, fixtures, error contracts, and disclosure policies. Browser-extension marketing is not a server API contract and does not become a runtime capability without an official API operation and fixture.

* Token API Capabilities

Current official Token API material advertises hCaptcha, reCAPTCHA v2, reCAPTCHA v3, and Cloudflare Turnstile operations. Each integration remains independent.

| Exact capability | Required source fields | Result | Current state |
|------------------+------------------------+--------+---------------|
| hCaptcha standard | page URL, site key, documented token context | =token= | =experimental= until fixture passes |
| hCaptcha Enterprise | page URL, site key, exact Enterprise data and provider fields; source-consistent proxy strongly preferred by current provider guidance | =token= | =experimental= until fixture passes |
| reCAPTCHA v2 checkbox | page URL, site key, exact v2 integration context | =token= | =experimental= until fixture passes |
| reCAPTCHA v2 invisible | page URL, site key, invisible/action context | =token= | =experimental= until separate fixture passes |
| reCAPTCHA Enterprise checkbox/invisible | exact Enterprise fields and integration type | =token= | =experimental= until separate fixture passes |
| reCAPTCHA v3 score | page URL, site key, action; current provider docs do not allow the caller to demand an arbitrary minimum score | =token= plus provider score behavior | =experimental= until fixture passes |
| Cloudflare Turnstile managed | page URL, site key, action/challenge data when required | =token= | =experimental= until fixture passes |
| Other Turnstile modes | exact documented mode and fields | =token= | =unsupported= unless current operation and fixture exist |

Support for one integration does not widen to another version, variant, Enterprise mode, result kind, browser binding, network binding, or mobile flow.

Current hCaptcha documentation states that the Token API covers Publisher, Pro, and Enterprise. It also says Enterprise use should generally preserve the same proxy/IP between provider solve and downstream token submission because sites may bind acceptance to network identity. That makes network fidelity a hard capability field for Enterprise-sensitive targets rather than a late ranking hint.

* Recognition API Capabilities

Recognition returns challenge answers, not trusted issuer tokens.

| Challenge family | Required input | Normalized result kind | Current state |
|------------------+----------------+------------------------+---------------|
| Distorted text | bounded image artifact | =textAnswer= | =experimental= until fixture passes |
| Grid/object selection | bounded image plus exact prompt/task format | =selectionSet= or =coordinates= | =experimental= until fixture passes |
| Coordinate/bounding/draw task | bounded image and task instructions | =coordinates= or =interactionPlan= | =experimental= until fixture passes |
| Slider/rotation/puzzle | bounded challenge media and exact task context | =interactionPlan= or =customTypedResult= | =experimental= until fixture passes |
| Arkose image subchallenge | exact supported recognition task | typed recognition result | =experimental= until fixture passes |
| AWS WAF image/puzzle subchallenge | exact supported recognition task | typed recognition result | =experimental= until fixture passes |
| GeeTest v3/v4 subchallenge | version-specific media and fields | typed recognition result | =experimental= until version fixture passes |
| hCaptcha image subchallenge | bounded challenge image/prompt | selection or coordinate result | =experimental= until fixture passes |

Recognition completion does not prove issuer or target acceptance. The source runtime applies the answer and returns downstream verification.

Current hCaptcha Token documentation explicitly excludes at least one challenge interaction shape that requires drawing a box around an object. That exclusion must not be hidden by the broader “all versions” language: exact interaction-type support remains fixture-driven.

* Request and Result Fields

Every capability record captures:

- exact official operation and retrieval date;
- exact task type;
- required and optional request fields;
- required result fields;
- result kind;
- proxy and cookie formats;
- user-agent requirements;
- browser-session and same-network requirements;
- mobile requirements;
- credential location;
- polling or synchronous delivery;
- cancellation and idempotency support;
- ambiguous-create behavior;
- per-capability credit cost;
- error codes;
- fixtures and unsupported variants.

A general supported-CAPTCHA catalog is discovery evidence, not enough to activate a runtime capability.

* Proxy, Cookie, Session, and Network Context

Some token and Enterprise flows may require a source-consistent proxy, cookies, user agent, challenge data, or other session context. Therefore:

- proxy credentials and cookie bundles remain behind ephemeral references;
- target policy explicitly permits each disclosure;
- the capability declares whether the provider must use the same network identity;
- hCaptcha Enterprise is treated as same-network-sensitive when current provider guidance or target evidence requires matching solve/submission IP;
- the capability declares whether result application requires the same browser session;
- authenticated cookie material is never stored in documents or ordinary actor messages;
- the broker prefers a local browser solver when an external provider cannot preserve exact context fidelity.

* Quota and Billing

Official NopeCHA pages describe credit costs and refill behavior, but public pages currently contradict one another for hCaptcha token cost: the dedicated hCaptcha Token page reports one cost while the general overview reports another. Therefore pricing is explicitly =drift-prone= evidence.

The runtime must not compile a fixed NopeCHA credit price into actor code. Store the observed or configured cost with the exact capability contract, retrieval timestamp, source URL, and fixture/canary evidence. If official sources disagree, mark the cost field =contradictory= and use an operator-configured budget ceiling until account-side billing evidence resolves it.

The adapter reserves configured credits before submission and reconciles only from provider evidence. A local cancellation does not imply provider credit recovery. Refill capacity is subscription capacity, not a free budget override.

* Polling, Cancellation, and Ambiguous Submission

Token jobs are polled with bounded backoff until terminal state or deadline. The researched token contract does not establish provider-side cancellation, so local cancellation stops polling, deletes local result material, and reports that cost may still be incurred.

After an ambiguous token create, recover only through a provider-supported identifier or lookup contract. Never blindly submit another billable job.

Recognition delivery and cancellation are declared per capability. A synchronous recognition timeout is not silently retried when the provider may have consumed credits.

* Security and Disclosure

Never persist or publish:

- subscription keys;
- request URLs containing keys;
- proxy credentials;
- cookie bundles;
- authenticated session material;
- challenge images or audio containing private target data unless explicitly approved and retained according to policy;
- provider tokens;
- text answers;
- coordinates;
- selections;
- interaction plans;
- full provider bodies or authorization headers.

Use placeholders such as =key=<redacted>=. Result values remain in the ephemeral secret store and leave it only through a bounded authorized read in the source runtime.

* Error Contract and Drift

Normalize authentication, quota, invalid request, unsupported task, pending, unsolvable, timeout, service failure, malformed result, and internal adapter errors. Every failure carries =retryable= and =chargePossible=.

Drift is localized:

- one Token capability may become =invalidContract= without disabling other token families;
- Token API drift does not automatically disable Recognition API capabilities;
- Recognition result-schema drift affects only the exact task;
- shared credential or provider outage may temporarily mark all NopeCHA capabilities =disabled=;
- browser-extension changes do not alter server API capability state;
- contradictory public pricing changes only the capability's cost-confidence state and budget policy, not its request/result contract.

* Required Fixtures and Tests

- hCaptcha standard and Enterprise token requests/results;
- hCaptcha Enterprise same-network/proxy-binding acceptance fixture;
- explicit unsupported interaction fixture for box-drawing challenge behavior;
- reCAPTCHA v2 checkbox, v2 invisible, Enterprise, and v3 score fixtures;
- Turnstile mode-specific fixtures;
- text, grid, coordinate, bounding, puzzle, Arkose, AWS WAF, GeeTest, and hCaptcha-recognition fixtures;
- typed result validation and forbidden result-kind widening;
- pending-job polling and deadline behavior;
- ambiguous create and duplicate RabbitMQ delivery;
- per-capability credit cost and refill-window behavior;
- official-price contradiction detection and operator-budget fallback;
- local cancellation with possible charge;
- proxy, cookie, session, key, challenge, and result redaction;
- capability-local drift;
- source-runtime downstream acceptance, rejection, replacement, expiration, and inconclusive outcomes;
- no paid provider in continuous integration;
- capability-specific opt-in canaries on operator-owned systems only.

* Decision

Retain NopeCHA as a broad secondary provider candidate with separate Token and Recognition actor surfaces. Activate each exact capability only after its official contract, fixture, cost, redaction, context, and operator-policy requirements pass.

* Footnotes and Glossary

- *Recognition result* — Text, coordinates, selections, or an interaction description that the source runtime must apply; it is not an issuer token.
- *Token result* — An issuer-specific verification token produced by an exact provider operation and later applied and verified by the source runtime.
- *Query credential exposure* — Risk that a secret in a URL query is captured by logs, traces, analytics, or error reports.
- *Capability-local drift* — A request or result contract failure isolated to the exact task and API surface.
- *Cost-confidence state* — Confidence that the runtime budget model matches current provider billing; it can drift independently from request/result capability validity.
