Owning implementation issue: [[https://github.com/lost-rob0t/starintel-server/issues/38][starintel-server #38]].

The complete open Auto-Research, StarIntel Server, and StarLang backlogs were enumerated before selection, and recently closed Auto-Research/Server work was checked for follow-up obligations. Server #34-#37 are P0 runtime prerequisites with current canonical research/design. #38 is the next open P0 in dependency order whose old issue text contains both repaired defects and an uncovered residual config/security problem.

This is not generic container/config research. It owns the concrete StarIntel Server deployment boundary.

* Contradiction: much of #38 is already repaired

The original #38 description is stale in several material respects. Current master already:

- builds StarIntel Server as a Nix =dockerTools.buildLayeredImage= carrying the application closure instead of copying a Nix wrapper into an unrelated Debian image;
- uses Compose service DNS names for CouchDB/Rabbit/Valkey;
- declares Valkey and dependency health conditions;
- supplies Compose secret files rather than checked-in default credential values;
- defaults host service publication to loopback bindings;
- runs the server entrypoint under uid/gid 65532 through =su-exec=;
- has a stack test which loads the Nix-produced images and boots/probes the authenticated Compose stack.

Research MUST preserve these fixes. Rewriting the OCI image or Compose topology is not the remaining P0.

* Residual Finding: ordinary configuration is still executable Lisp

Current entrypoint selects =STAR_SERVER_INIT_FILE=, defaulting to =/etc/starintel/init.lisp=, then executes:

#+begin_example
/bin/star-server start -i "$STAR_SERVER_INIT_FILE"
#+end_example

The default init file is executable Common Lisp. It mutates global specials using environment variables and =environment-secret= helpers. This means the default ordinary configuration path and the trusted code-extension path are the same mechanism.

This is too much authority for routine deployment data. A typo/misconfiguration and an intentionally executable extension are not distinguishable by type or policy.

Requirement: normal deployment settings must have a data-only, validated representation. If executable Lisp startup extensions remain supported, they are an explicit trusted extension mechanism, separate from ordinary config, with an opt-in boundary visible in diagnostics.

* Residual Finding: secret resolution is duplicated across entrypoint and Lisp

The shell entrypoint resolves =COUCHDB_PASSWORD=, =RABBITMQ_PASSWORD=, =STAR_AUTH_PEPPER=, and =STAR_AUTH_BOOTSTRAP_SECRET= from =*_FILE= and exports plaintext process environment values. The Lisp init subsequently supports =environment-secret VALUE VALUE_FILE= again.

This works for server startup, but the split semantics already produced an operational regression recorded by closed server #112: direct local administration initially did not inherit the same Compose =*_FILE= behavior.

Requirement: secret-reference resolution is one application-level contract reused by server startup and administration. Container wrappers may mount/point at secret files, but must not be the only place the semantic exists.

Secret values must never enter normalized config snapshots, diagnostics, logs, issue fixtures, or generated artifacts.

* Residual Finding: config completeness must be proven by observed behavior

#38 still names settings whose existence alone is insufficient: HTTP base path, scheme/TLS certificate/key, service ports, Rabbit/CouchDB parameters, thread budgets and limits.

Requirement: a declared supported setting must map through one typed normal form into the actual runtime owner and have an observed behavior/contract test. Unknown settings fail validation instead of being silently accepted as dead configuration.

Thread/concurrency settings must feed the existing #34/#35 budget authority; queue/admission limits feed #36; lifecycle/readiness settings integrate with #37. #38 must not create competing runtime authorities.

* Research Decision

Preserve current packaging and define one typed Common Lisp deployment-configuration boundary with these properties:

1. ordinary settings are parsed as data, not evaluated code;
2. schema is closed/versioned and unknown keys fail;
3. normalization is deterministic and validates type/range/cross-field constraints before long-lived startup;
4. secrets are represented as opaque secret references/resolvers and are not serialized back into config diagnostics;
5. environment variables and =*_FILE= are input adapters to the same schema, not separate semantics;
6. an optional trusted Lisp init/extension hook is explicitly distinct from normal config and never required for basic deployment;
7. production profile rejects known unsafe bootstrap/default-secret states;
8. current Nix OCI and Compose layout remain supported;
9. runtime ownership stays with existing Common Lisp components and P0 authorities;
10. no new StarLang syntax is justified for host-process deployment configuration.

* Proposed Config Normal Form

The exact Lisp representation is an implementation choice, but the logical object is closed and typed:

#+begin_example
DeploymentConfig {
  schemaVersion
  profile
  couchdb { host, port, scheme, database, authDatabase, user, passwordRef }
  rabbit { host, port, user, passwordRef, vhost }
  valkey { host, port, passwordRef? }
  http { listenAddress, port, basePath, tlsMode, certificateRef?, keyRef?, allowedOrigins }
  auth { mode, pepperRef, bootstrapSecretRef?, devBypass, timeoutLimits... }
  runtime { processThreadLimitRef/config values approved by #34, shutdown deadline values from #37 }
}
#+end_example

This does not make the config object the authority for thread/lifecycle semantics. It initializes the canonical authorities defined by their owning designs.

* Configuration Precedence

Use one deterministic precedence rule documented and tested. Recommended first contract:

1. compiled safe defaults;
2. optional data config file;
3. explicit environment overrides;
4. secret references resolve only at the consuming boundary.

A plaintext environment secret may remain compatibility input where already supported, but =*_FILE=/runtime-secret references are preferred. If both VALUE and VALUE_FILE are supplied, reject ambiguity unless an existing compatibility rule is explicitly preserved and tested.

* Trusted Extension Boundary

An executable Lisp init file is code authority, not config data.

If retained:

- it is opt-in and named as a trusted extension/hook rather than the default config mechanism;
- it executes after validated base configuration is established but before affected long-lived components start;
- production diagnostics state that trusted extension code is enabled without exposing its content/secrets;
- extension code cannot convert invalid base config into silently valid config without an explicit revalidation boundary;
- ordinary Compose/Nix deployments require no executable init.

* StarLang Classification

No StarLang extension is justified. Deployment config concerns host ports, TLS files, broker/database credentials, OS/runtime capacity, and process startup. These remain Common Lisp/runtime adapter concerns. StarLang actors/domain servers consume the resulting authorized runtime capabilities; they do not gain host secret/config authority.

* Adversarial Findings

Rejected:

1. rewrite current Nix OCI/Compose packaging -- repaired and regression-prone;
2. keep executable Lisp as the only/default config format -- unnecessary code authority for data;
3. invent a general-purpose configuration DSL -- a small typed schema is enough;
4. make shell entrypoint the canonical secret resolver -- breaks direct CLI/admin and non-container launches;
5. materialize secret contents in normalized config/status output -- leakage risk;
6. silently prefer VALUE over VALUE_FILE or vice versa -- hides ambiguous operator intent;
7. let #38 own a second thread/lifecycle/admission model -- #34-#37 are authority;
8. add StarLang syntax for host deployment controls -- wrong ownership;
9. remove trusted Lisp extension support without compatibility inventory -- unnecessary breakage;
10. claim old #38 Docker/Compose defects remain current after source proves otherwise.

* RED-First Handoff Targets

First proposed implementation slice is pure parsing/normalization, before network/thread startup.

Mandatory REDs:

- valid minimal data config cannot currently produce a closed normalized deployment-config object;
- unknown key is rejected;
- invalid port/range/type is rejected before startup;
- VALUE and VALUE_FILE ambiguity follows one explicit tested rule (prefer rejection for the new contract);
- unreadable/empty required secret file yields typed config/secret error with no secret content;
- normalized diagnostic/snapshot contains secret refs/status only, never secret values;
- equivalent input normalizes deterministically;
- config with executable Lisp form is data/rejected, never evaluated.

Follow-on REDs:

- direct =star-server admin= and normal server startup resolve the same =*_FILE= contract;
- HTTP base path/TLS settings alter observed route/listener behavior;
- production profile rejects dev bypass/missing required secret state;
- enabling trusted init is explicit and base config is revalidated before long-lived startup;
- existing Nix image + authenticated Compose stack remains green.

* Unresolved Questions

- Exact compatibility period for =STAR_SERVER_INIT_FILE= requires caller/deployment inventory before deprecation or default change.
- Exact data syntax (EDN-like plist, JSON, TOML, etc.) should follow existing server dependency/style constraints; architecture requires typed data, not a specific parser.
- Some TLS termination may live at an outer proxy in production; server TLS fields should only remain canonical if the server itself supports/owns that deployment mode.

* Footnotes and Glossary

- *Data-only config* :: Configuration parsed into a closed typed object without evaluating host-language code.
- *Trusted extension* :: Explicit operator-authorized executable Lisp startup hook, separate from ordinary configuration.
- *Secret reference* :: Runtime locator/handle whose secret value is resolved only at the consuming boundary and is never serialized into ordinary configuration diagnostics.
