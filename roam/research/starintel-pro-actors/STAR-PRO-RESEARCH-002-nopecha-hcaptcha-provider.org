* Scope

This note evaluates both NopeCHA service surfaces behind the provider-neutral StarIntel broker:

- the *Token API*, which returns issuer verification tokens; and
- the *Recognition API*, which returns text, classifications, coordinates, or challenge answers.[fn:recognition]

The previous hCaptcha-only scope was incomplete. The two surfaces must register separate capabilities, budgets, result kinds, and disclosure rules.

* Current Advertised Coverage

NopeCHA currently advertises these families in its supported-CAPTCHA catalog.

| Service surface | Advertised families | Typical result kind |
|-----------------|---------------------+---------------------|
| Token API | hCaptcha, reCAPTCHA v2, reCAPTCHA v3, Cloudflare Turnstile | token |
| Recognition API | Arkose FunCaptcha, AWS WAF CAPTCHA, GeeTest, hCaptcha, Lemin, reCAPTCHA, text CAPTCHA | text, coordinates, selection, or provider-specific answer |
| Browser extension | broader interactive automation | browser-bound result; not a server adapter contract by itself |

A marketing or extension claim is not enough to register a server capability. Each runtime capability requires a current request/result fixture from the corresponding official API page.

* Token Contract

The token service uses =POST https://api.nopecha.com/token/= and a retrieval request containing the subscription key and provider job identifier. The key may appear in the create body or retrieval query. Request-body and request-target logging must be disabled and sanitized.[fn:url]

Current documented token types include:

- =hcaptcha= with optional Enterprise data;
- =recaptcha2= including Enterprise variants;
- =recaptcha3= with action and minimum-score context;
- =turnstile= with optional action and challenge data.

The hCaptcha page documents five credits per request, while the general overview has published a different value. The adapter therefore requires an operator-configured or contract-probed credit cost per capability rather than one global hard-coded value.

* Recognition Contract

Recognition tasks return challenge answers rather than issuer tokens. They must use distinct normalized result kinds:

| Recognition family | Normalized result kind |
|--------------------+------------------------|
| Distorted text | =textAnswer= |
| Grid or object selection | =selectionSet= or =coordinates= |
| Bounding or drawing task | =coordinates= or =interactionPlan= |
| Slider/rotate/puzzle | =interactionPlan= or provider-specific typed result |
| Provider image subchallenge | capability-specific typed result |

Recognition output must never be mislabeled as a trusted token. The source actor applies it through its own browser/session flow and reports whether the issuer accepted it.

The actual runtime list is populated only by fixtures that pass. A token capability never implies recognition, and recognition never implies token generation.

* Proxy, Cookie, and Session Context

Some token and Enterprise flows may require the solve network identity to match the source actor's submission identity. Cookies may contain authenticated session material.[fn:session]

Therefore:

- proxy and cookie values are represented only by ephemeral references;
- target policy explicitly permits each context kind;
- a capability registration declares same-network and same-session requirements;
- the broker prefers a local browser actor when remote provider context cannot preserve required binding;
- no provider URL, log, trace, or error may contain the subscription key.

* Quota Accounting

Credits refill every twenty-three hours and unused capacity does not accumulate. The adapter maintains a per-capability quota ledger because token and recognition operations consume different amounts.

Before submission, reserve the configured amount. On completion, reconcile against provider evidence where available. Do not release a reservation unless the contract proves no charge occurred. A refill is paid subscription capacity, not free budget.

* Polling and Cancellation

A token create returns a job identifier. The documented incomplete-job response remains pending and is polled with bounded backoff. The researched token contract does not document provider-side cancellation. Local cancellation stops polling and deletes local secret material, but may still consume credits.

Recognition operations may be synchronous or asynchronous by endpoint. Each capability adapter declares its delivery model explicitly.

* Risks

- Credit documentation can disagree across official pages.
- Retrieval authentication in a query creates log-exposure risk.
- Token and recognition coverage can drift independently.
- Cookies and proxy context increase disclosure.
- Recognition can solve a subchallenge without producing a server-accepted token.
- Browser-extension capability is not automatically equivalent to a stable server API.

* StarIntel Decision

Approve NopeCHA as a broad secondary provider candidate, not as one undifferentiated adapter capability. Implement separate token and recognition ports inside one supervised provider actor or two sibling actors. Enable each capability only after its own contract fixture, redaction test, cost configuration, and operator policy pass.

* Test Requirements

- Per-capability fixture registration and drift disablement.
- hCaptcha, reCAPTCHA v2/v3, and Turnstile token mocks.
- Arkose, AWS WAF, GeeTest, hCaptcha-recognition, and text mocks.
- Pending-job behavior and bounded polling.
- Recognition result-kind validation.
- Per-capability quota and refill-window tests.
- Local cancellation without provider cancellation support.
- Proxy, cookie, key, challenge, and result redaction.
- Capability-specific opt-in canaries only.

* Footnotes and Glossary

[fn:recognition] Recognition API: A service that interprets challenge media and returns answers, labels, selections, or coordinates rather than a completed issuer token.

[fn:url] Uniform resource locator: A network address whose query component can accidentally expose credentials when recorded.

[fn:session] Session material: Cookies or related values that associate requests with an authenticated or previously established browser session.
