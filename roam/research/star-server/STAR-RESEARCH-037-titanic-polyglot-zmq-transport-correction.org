#+title: STAR-RESEARCH-037 Titanic Polyglot ZeroMQ Transport Correction
#+description: Correct the initial Titanic backend comparison by making StarIntel's multi-language actor boundary and the already-approved ZeroMQ architecture first-class constraints.
#+status: REVIEW
#+last_modified: [2026-08-08 Sat]
#+filetags: :starintel:star-server:titanic:zeromq:polyglot:actors:transport:correction:research:org-roam:

* Purpose

The first Titanic research pass over-weighted broker-side durability and the fact that RabbitMQ is already deployed in =starintel-server=. It under-weighted a harder StarIntel requirement: external actor workers must remain language-independent, and the project already has an approved ZeroMQ transport decision for process and language boundaries.

This node corrects that mistake before the research stack is approved or promoted into implementation design.

* Existing Approved Constraint

[[file:../../design/star-server/STAR-ADR-001-domain-gserver-zmq-approval.org][STAR-ADR-001 Domain GServer and ZeroMQ Approval]] explicitly approves ZeroMQ at boundaries requiring process separation, language independence, routing identity, mobility, or failure containment.

[[file:../../design/cl-gserver/SENTO-ZMQ-000-zero-mq-transport-runtime.org][SENTO-ZMQ-000 ZeroMQ Transport Runtime]] already defines ROUTER/DEALER as the addressed asynchronous cross-process command path.

[[file:../cl-gserver/SENTO-000-zeromq-transport-analysis.org][SENTO-000 ZeroMQ Transport Analysis]] already defines the supervised reactor, socket ownership, multipart envelope, overload behavior, monitoring, CURVE/ZAP security, and cross-language test strategy.

Titanic is exactly such a boundary. A durable actor-job system whose workers may be implemented in Common Lisp, Nim, Python, JavaScript, or additional languages must not force every worker implementation to adopt an AMQP- or NATS-specific client stack when the approved architecture already provides a language-neutral ZeroMQ boundary.

* Polyglot Requirement

The maintained StarIntel ecosystem already spans at least:

- Common Lisp;
- Nim;
- Python;
- JavaScript/TypeScript.

The transport decision must therefore be evaluated against the weakest language integration, not merely against the strongest broker feature set.

A suitable worker wire protocol should have:

- one stable binary framing model;
- implementations or a practical foreign-function path in every maintained language;
- no broker-specific delivery tag, offset, sequence number, or client object in the actor contract;
- equivalent conformance fixtures across languages;
- routing identities that survive heterogeneous implementations;
- a protocol that can be implemented directly over a stable C ABI when a high-level client library is weak or absent.

* Language Coverage Finding

ZeroMQ has the strongest fit for this specific StarIntel constraint because its native =libzmq= API is a stable C-callable boundary and its ZMTP wire protocol is shared across implementations and bindings.

For the current language set:

| Language | ZeroMQ path | StarIntel implication |
|----------+-------------+----------------------|
| Common Lisp | audited PZMQ or a narrow maintained CFFI binding to =libzmq= | already researched and approved as the StarIntel ZMQ strategy |
| Nim | direct C FFI to =libzmq= is practical even if a community wrapper is unsuitable | no dependency on a broker-specific Nim client implementation |
| Python | mature PyZMQ implementation | useful reference peer and conformance oracle |
| JavaScript/TypeScript | maintained Node.js ZeroMQ binding exists | can participate in the same ZMTP topology |
| Future C-compatible languages | direct or generated binding to the C API | keeps the core boundary broadly portable |

The Common Lisp binding remains subject to the existing PZMQ adopt/fork/replace audit. The important point is that the architecture does not depend on finding a first-class broker client for every language: a narrow =libzmq= binding is always a viable fallback.

* NATS JetStream Correction

JetStream is NATS's persistence and stateful-consumer layer. It provides durable streams, acknowledgements, redelivery, work-queue retention, and pull consumers.

Those mechanics are interesting as comparative distributed-systems research, but JetStream should not be presented as StarIntel's likely next actor transport.

The official NATS client list has first-class maintained clients for languages such as Go, Java, .NET, Rust, JavaScript, Python, and C. Common Lisp and Nim are not in that first-class maintained list.

That is enough to downgrade JetStream from “future adapter worth targeting” to “comparative reference only” for Titanic. StarIntel should not create a new distributed transport dependency whose language coverage is weaker than the already-approved ZeroMQ path.

* RabbitMQ Correction

RabbitMQ remains useful and already deployed. It should not automatically become the universal worker protocol.

The clean separation is:

#+begin_example
existing StarIntel documents/events
          |
          v
      RabbitMQ
          |
          v
  Titanic admission/gateway
  durable job journal
          |
          v
  ZeroMQ ROUTER/DEALER
      /      |      \
     /       |       \
    v        v        v
 Common    Nim      Python/JS
 Lisp      actor      actors
 worker
#+end_example

RabbitMQ may carry existing document and event traffic into or out of Titanic. It may also be used internally as one scheduling backend if that proves useful.

External Titanic workers should speak the stable Titanic-over-ZeroMQ protocol, not RabbitMQ's AMQP details.

This preserves compatibility with the deployed server while avoiding a transport lock-in at every actor implementation.

* Recovered 2023 Architecture

The recovered devlog diagram is now more important, not less.

It showed approximately:

#+begin_example
actors -> Broker <-> Titanic <-> LMDB
                         |
                    router socket
                    /           \
             subfinder       database
#+end_example

That topology already separated:

- the broker/event side;
- Titanic persistence;
- a router socket;
- heterogeneous workers.

The modern design should preserve that separation instead of collapsing Titanic into “RabbitMQ plus a job table.”

* Modern Titanic Boundary

Titanic owns durable job semantics:

- stable =job_id=;
- idempotent admission;
- durable job journal;
- queued, dispatched, running, retrying, cancelled, failed, completed, and retained-result states;
- attempt identity and bounded retry policy;
- disconnected status/result lookup;
- cancellation and deadlines;
- correlation, causation, trace, and provenance;
- lease/fencing metadata for protected side effects;
- dead-letter and audited replay lineage.

ZeroMQ owns the cross-language worker transport:

- ROUTER/DEALER routing identities;
- asynchronous command/reply framing;
- worker readiness and heartbeats;
- explicit capability registration;
- bounded high-water marks and overload errors;
- binary-safe multipart frames;
- CURVE/ZAP when remote encrypted/authenticated transport is required.

The persistence backend is a separate decision.

* Persistence Backend

The original diagram used LMDB. That remains a credible local-first backend because Titanic itself, rather than every actor language, owns the database integration.

Do not couple the public actor protocol to LMDB APIs.

The persistence interface should support at minimum:

#+begin_example
put-job
get-job
compare-and-transition
append-attempt
put-result
get-result
claim-dispatch
renew-dispatch
release-dispatch
record-idempotency-outcome
record-dead-letter
record-replay
#+end_example

LMDB can be evaluated as the first embedded implementation against SQLite and the existing StarIntel storage stack. The decisive tests are crash recovery, atomic state transition, concurrent readers/writer behavior, result-retention cost, and deterministic replay—not whether a worker language has an LMDB library.

* Worker Protocol Shape

The historical TSP =request/reply/close= model should be retained but extended for actor jobs.

Suggested protocol operations:

- =HELLO= / capability registration;
- =READY= / worker capacity advertisement;
- =JOB= / dispatch one durable job attempt;
- =ACCEPTED= / worker accepted execution responsibility;
- =HEARTBEAT= / liveness and lease-renewal signal;
- =RESULT= / successful typed result;
- =ERROR= / structured retryable or terminal failure;
- =CANCEL= / cooperative cancellation request;
- =CANCELLED= / cancellation terminal state;
- =STATUS= / disconnected state lookup;
- =FETCH= / retained result retrieval;
- =CLOSE= / caller no longer requires retained result.

All stable fields belong to a versioned Titanic envelope. ZMQ routing identity remains transport metadata outside the durable actor message.

* Reliability Rule

ZeroMQ alone is not durable. That is not a reason to reject it for Titanic; it is the reason Titanic exists.

The reliable sequence is:

1. validate submission;
2. durably record job admission;
3. acknowledge the submitter with stable =job_id=;
4. dispatch an attempt over ZeroMQ when a capable worker is available;
5. persist attempt state before/around externally visible transitions according to the state-machine contract;
6. require idempotent/fenced side effects;
7. durably record the terminal result before exposing completion;
8. allow disconnected retrieval until retention/close policy removes the result.

A process crash between any two steps must recover from the journal without inventing a second logical job.

* Revised Transport Ranking

| System | Role after correction | Reason |
|--------+-----------------------+--------|
| ZeroMQ / ZMTP | PRIMARY actor-worker transport | approved StarIntel language/process boundary; broad bindings plus stable C ABI; matches recovered router-socket design |
| Titanic job journal | PRIMARY durability authority for job lifecycle | separates durability from transport and enables disconnected request/result semantics |
| RabbitMQ | EXISTING broker/adapter and optional internal scheduling aid | already deployed for documents/events; should not leak AMQP into every actor |
| LMDB | CANDIDATE first embedded Titanic journal backend | historically intended, local-first, private to Titanic service |
| NATS JetStream | COMPARATIVE REFERENCE ONLY | good queue semantics, but adds another broker and weaker fit for Common Lisp/Nim integration |
| Kafka | NON-V1 | log/stream first, not necessary for actor jobs |
| Temporal | NON-V1 | separate workflow runtime/control plane |

* Conformance Matrix Required Before Design Promotion

Titanic-over-ZeroMQ must be tested with the same byte-level fixtures across all maintained languages.

Minimum matrix:

1. Common Lisp ROUTER <-> Python DEALER;
2. Python ROUTER <-> Common Lisp DEALER;
3. Common Lisp ROUTER <-> Nim DEALER;
4. Nim ROUTER <-> Common Lisp DEALER;
5. JavaScript DEALER <-> Common Lisp ROUTER;
6. mixed workers consuming the same capability class;
7. multipart binary payload equality;
8. canonical JSON/header equality when JSON payloads are used;
9. disconnect/reconnect with stable worker identity policy;
10. worker crash after =ACCEPTED= but before =RESULT=;
11. Titanic crash after durable admission but before dispatch;
12. Titanic crash after result receipt but before client retrieval;
13. duplicate =RESULT= from a retried/stale attempt;
14. cancellation while a worker is disconnected;
15. deadline expiration during execution;
16. high-water saturation and bounded overload;
17. stale fencing token rejection at downstream side effects;
18. CURVE/ZAP interoperability for remote workers when enabled.

* Decision

Correct the Titanic research stack as follows:

- ZeroMQ is the canonical cross-language actor-job transport.
- Titanic provides the persistence and durable job state machine above ZeroMQ.
- RabbitMQ remains an existing StarIntel broker and adapter, not the universal actor-facing Titanic protocol.
- JetStream is not a planned StarIntel transport; keep it only as comparative research unless a future explicit requirement reopens that decision.
- Preserve the 2023 separation of broker, Titanic persistence, and router-socket workers.
- Reuse the already-approved SENTO-ZMQ runtime rather than inventing a second transport architecture.

This correction supersedes any statement in STAR-RESEARCH-035 or the Titanic index that calls RabbitMQ the canonical Titanic worker backend or JetStream the preferred future adapter.
