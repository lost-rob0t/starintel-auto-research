* Plain-English Version

The short version is this:

1. Put the reusable Prolog knowledge we want to build in one Git repository called =star-kb=[fn:star-kb].
2. Humans and agents edit readable Prolog facts and rules there.[fn:fact][fn:rule]
3. Do *not* execute those source files directly in production. A build tool reads them as data, rejects dangerous/general-purpose Prolog features, and converts the accepted clauses into the safe JSON format already understood by =prolog-query-server=.[fn:restricted-prolog][fn:ast][fn:pqs]
4. =prolog-query-server= stores the executable copy in CouchDB and does the actual reasoning.[fn:couchdb][fn:inference]
5. Actors ask the query server questions over HTTP. They do not each start their own copy of SWI-Prolog.[fn:actor][fn:http]
6. Knowledge is published in immutable releases so an actor never sees half of a rule-set update.[fn:release][fn:immutable]
7. Normal StarIntel observations remain normal StarIntel data. Seeing something once does not magically promote it into shared world knowledge.[fn:observation][fn:canonical]
8. Dialect enrichment is the first real consumer. Later the same system can hold geography, organization, identity, infrastructure, social-platform, and other expert knowledge.

If this design is approved, the first implementation is *not* the dialect actor. The first implementation is a tiny end-to-end =star.core.test= knowledge bundle that proves authoring -> compile -> stage -> validate -> query -> explain -> activate -> rollback.[fn:bundle][fn:stage][fn:rollback]

* Decision

Pending operator approval, use the existing =lost-rob0t/prolog-query-server= as the shared StarIntel knowledge runtime[fn:runtime]. Create a separate =star-kb= repository as the reviewed source for reusable knowledge.

Do not build a second Prolog server. Do not embed a private SWI-Prolog process in every actor. Do not use Git as the live query database.

#+begin_src text
          readable source knowledge
                  star-kb
                     |
              parse + validate
                     |
              compile to safe AST
                     |
                     v
       prolog-query-server + CouchDB
       releases / queries / proofs
                     ^
                     |
        +------------+-------------+
        |            |             |
   Lisp actors   prolog-rlm   later StarLang
        |
        v

#+end_src

The important split is *source versus runtime versus observations*:

- =star-kb= says what reusable facts/rules we intentionally maintain.
- =prolog-query-server= executes a compiled version of those facts/rules.
- StarIntel stores what actors actually observed during investigations or enrichment runs.

* Second ARADR Review Findings

** Finding 1: =prolog-query-server= already owns more of this problem than the first draft assumed

The current server already supports named knowledge bases, CouchDB-persisted facts and rules, safe structured query terms, bounded inference, immutable releases, active-release manifests, proof trees, revision-aware knowledge writes, incremental =_changes= synchronization, conflict detection, safe builtins, resource limits, authentication, and static release analysis.[fn:manifest][fn:proof-tree][fn:changes][fn:builtin]

Therefore =star-kb= should be mostly an *authoring/build/publishing repository*. Reimplementing release logic, synchronization, proof construction, or inference in =star-kb= would be duplication.

** Finding 2: strict activation must be mandatory for =star-kb= releases

The query server supports static analysis before activation, but its =strict= activation option defaults to =false= for backward compatibility.

The =star-kb= publisher must *always* activate generated releases with =strict: true=.[fn:strict-activation]

That means malformed arities, unsafe negative recursion, and other structural errors caught by the analyzer block the release before it becomes the default knowledge seen by actors.[fn:arity][fn:negation-cycle]

The publisher may not silently fall back to non-strict activation just to get a release out.

** Finding 3: do not write a second Prolog parser

The first draft said =star-kb= needed a restricted Prolog compiler but did not say how to parse source.

Use SWI-Prolog's term reader as a *parse-only build tool*.[fn:read-term]

The compiler should read one Prolog term at a time with source positions, variable names, and syntax errors enabled, then inspect the returned term as data. It must not =consult= the file and must not execute directives, term expansion, initialization hooks, or source goals.[fn:consult][fn:directive]

In plain English: let Prolog understand Prolog syntax, but never give the source permission to run.

This avoids implementing a fragile second parser while preserving the query server's rule that production knowledge is executed only through its safe fact/rule representation.

** Finding 4: source modules are not SWI runtime modules

A =star-kb= module[fn:module] is an organizational unit in the source repository. It groups related facts/rules and declares dependencies.

It is *not* a request to use SWI-Prolog's runtime module/import system. SWI modules have their own loading, import, operator, and meta-predicate behavior. V0.1 does not need that complexity.

The build tool resolves source-module dependencies itself and emits one flat, safe query-server knowledge base for each actor-facing bundle.

** Finding 5: the query server already returns useful query provenance

Synchronous query execution already creates a =query_id=. Query results include the query ID, knowledge-base name, resolved release, result count, solutions, the actual resource budget used, limit-hit indicators, proof usage, and refresh/synchronization data.[fn:query-id][fn:budget]

The actor should record these real values rather than inventing another parallel query identity format.

For an explained query, proof nodes can identify exact CouchDB source document IDs and revisions. Generated knowledge documents therefore need enough source metadata to map those runtime IDs back to =star-kb= modules, clauses, source citations, and commits.

** Finding 6: synchronous actor queries should be the default

The query server also has asynchronous job support and cancellation.[fn:async]

That is useful for genuinely long inference jobs, but it should not complicate the first actor client. The generic Common Lisp client starts with synchronous bounded query/explain calls. Add async behavior only when measured actor workloads actually exceed the synchronous deadline budget.

** Finding 7: bundle flattening is still the right V0.1 tradeoff

The query API selects one =(kb, release)= pair.[fn:kb-release]

Instead of immediately adding cross-KB imports/joins, the publisher computes the dependency closure of a bundle and materializes that whole closure as one immutable runtime KB release.[fn:dependency-closure]

This duplicates some shared facts between bundles, but it keeps querying, release switching, rollback, proofs, and conflict behavior simple. Measure storage/runtime cost before changing it.

** Finding 8: first-party raw survey responses do not belong in =star-kb=

A person answering a dialect survey is an observation/data record, not automatically reusable canonical knowledge.

Raw respondent answers belong in an appropriate StarIntel dataset or research store with the required consent/retention policy. Aggregated or researched linguistic conclusions can later be reviewed and promoted into =star-kb= as reusable facts/rules with provenance.

This prevents training/test data, personal responses, and reusable language knowledge from being mixed into one repository.

** Finding 9: dialect scoring needs an explicit mathematical contract

The first dialect release may use deterministic weighted evidence, but =Score= must say exactly what it means. A weighted score is not automatically a probability.[fn:calibration]

The first fixture suite must prove that recursive list/feature scoring is expressible using the safe runtime rule representation and builtin set before we promise a particular scoring API.

If that becomes awkward, research a narrowly safe scoring builtin or a separate probabilistic-logic layer. Do not weaken the raw-code boundary merely to make scoring convenient.

* Repository Ownership

** =star-kb=

Owns:

- readable canonical source facts and rules;
- source modules and bundle manifests;
- citations, licenses, and source records;
- deterministic clause identities;
- the restricted source-Prolog validation rules;
- fixtures with expected inference results;
- deterministic compilation to query-server fact/rule JSON;
- release build metadata and content hashes;
- publishing commands that stage, analyze, test, activate, diff, and roll back releases.

Does not own:

- the live SWI-Prolog HTTP runtime;
- CouchDB replication or =_changes= handling;
- actor-local observations;
- raw large training corpora;
- secret/private evidence;
- StarLang runtime behavior;
- neural-model training.

** =prolog-query-server=

Owns the live knowledge database and inference behavior:

- persisted =prolog_fact= / =prolog_rule= documents;
- named KBs and releases;
- active-release manifests;
- safe query JSON decoding;
- bounded meta-interpreted inference;[fn:meta-interpreter]
- proof/explanation trees;
- static release analysis;
- safe builtins;
- resource limits and query IDs;
- incremental CouchDB synchronization;
- fail-closed conflict behavior;[fn:fail-closed]
- read/write authentication and runtime metrics.

The native CouchDB =language: "prolog"= map/reduce query server is a different thing: it helps CouchDB build views over individual documents. Actors should use the HTTP expert-system API for recursive reasoning.[fn:couchdb-query-server]

** =starintel-server=

Owns:

- the generic Common Lisp client for =prolog-query-server=;
- actor lifecycle and routing;
- production enrichment actors;
- StarIntel observation/derived-document persistence;
- actor-level retries, deadlines, idempotency, and operational events.[fn:idempotent]

It must not carry its own copy of the canonical knowledge corpus.

** =star-lang=

Later owns declarative orchestration through a generic HTTP/process/RPC adapter.[fn:adapter][fn:rpc]

Core StarLang does not gain special Prolog syntax. It sends the same structured query contract that the Lisp client sends.

** =prolog-rlm=

May query the shared knowledge runtime as another client. It is not the canonical knowledge repository and is not a dependency of ordinary StarIntel actor inference.[fn:rlm]

* Restricted Source-Prolog

=star-kb= source should look like Prolog because Prolog is the knowledge language we want to maintain.

Example:

#+begin_src prolog
regional_term(pop, inland_north).

supports_region(Features, Region, Score) :-
    dialect_feature_score(Features, Region, Score),
    gte(Score, 0.0).
#+end_src

The source reader parses these clauses but never executes them.

Allowed V0.1 constructs:

- ground facts;[fn:ground]
- normal variables in rule heads/bodies;
- compound terms and lists that the query server can represent;
- conjunctions of approved user predicates;
- builtins already whitelisted by =prolog-query-server=;
- negation only when static analysis accepts the dependency structure.[fn:naf]

Rejected V0.1 constructs:

- initialization or other executable directives;
- =consult/1=, =use_module/1=, file includes, or network-loaded source;
- =call/N= and constructed meta-calls;
- =assert*=, =retract*=, =abolish*=;
- shell/process/filesystem/environment/socket/HTTP-client/database/foreign calls;
- term expansion and compile-time hooks;
- unapproved operators or callable functors;
- any clause that cannot be represented in the query server's safe AST.

* Source Reader and Compiler

The compiler pipeline should be:

#+begin_src text
.pl source bytes
   |
   v
SWI read_term/3-style parse only
   |
   v
term + variable names + source positions
   |
   v
restricted-profile validator
   |
   v
normalized clause AST
   |
   v
safe query-server JSON fact/rule document
#+end_src

The build process must never call the parsed clause as a goal.

Source positions should be retained where practical so validation errors can say something useful such as:

#+begin_src text
modules/dialect/en-us/scoring.pl:81:5
rejected call/2: meta-calls are outside star-kb source profile v1
#+end_src

* Modules and Bundles

A *module* is a reusable source chunk. A *bundle* is the deployable thing an actor asks for.

Example module manifest:

#+begin_src json
{
  "name": "dialect.en-us.lexical",
  "version": "0.1.0",
  "provides": ["dialect_lexical_evidence/4"],
  "requires": ["core.provenance", "geography.us"],
  "sources": ["src-us-dialect-001"]
}
#+end_src

Example bundle:

#+begin_src json
{
  "name": "star.dialect.en-us",
  "version": "0.1.0",
  "modules": [
    "core.provenance",
    "core.confidence",
    "geography.core",
    "geography.us",
    "dialect.core",
    "dialect.en-us.lexical",
    "dialect.en-us.syntax",
    "dialect.en-us.scoring"
  ],
  "exports": ["dialect_candidate/3", "dialect_evidence/4"]
}
#+end_src

The publisher resolves all transitive dependencies and compiles the result into one PQS KB release.

Build dependency cycles are rejected. Logical recursion inside the rule graph can still be valid; those are different problems.[fn:recursion]

* Clause Identity and Provenance

Every compiled fact/rule gets a deterministic CouchDB document ID.[fn:deterministic]

The identity should depend on stable normalized inputs such as:

#+begin_src text
source profile version
module name
normalized clause AST
source record IDs
source repository commit
#+end_src

Generated runtime documents should carry non-executable metadata such as:

#+begin_src json
{
  "originModule": "dialect.en-us.lexical",
  "originPath": "modules/dialect/en-us/lexical.pl",
  "originClause": "sha256:...",
  "sourceCommit": "...",
  "sourceRecords": ["src-us-dialect-001"],
  "licenseRefs": ["license-star-owned"],
  "generatedBy": "star-kb-compiler/0.1.0"
}
#+end_src

This is how a proof pointing at CouchDB document =X= can eventually be traced back to the exact source clause and source evidence that generated =X=.[fn:provenance]

* Source Records and Licensing

A source record should include, when applicable:

#+begin_src text
sourceId
kind
canonicalURL
retrievedAt
title / authority
license
licenseURL
allowedUses
collectionMethod
sourceVersion or contentHash
notes
#+end_src

Licensing is not just a README note. The bundle validator must be able to reject a production bundle when its source-license policy is incompatible with the intended release.

For dialect research, Harvard/MyDialect-derived data remain benchmark/research material unless the exact downstream use is compatible with their stated license. The long-term production corpus should favor StarIntel-controlled or otherwise suitably licensed facts and research conclusions.

* Publication Lifecycle

No Git commit automatically becomes live knowledge.

#+begin_src text
edit source
   |
parse without executing
   |
validate restricted source
   |
compile deterministic runtime documents
   |
run fixtures
   |
stage new immutable PQS release
   |
POST /v1/analyze
   |
pinned /v1/query + /v1/explain tests
   |
review release diff
   |
POST /v1/releases/activate with strict:true and current _rev
   |
observe active release
#+end_src

The =strict:true= requirement is normative.

If activation fails, the currently active release stays active. If the new release later proves bad, rollback means activating a previously known-good immutable release using the current manifest revision.

* Actor Query Contract

Actors talk to the HTTP expert-system API rather than CouchDB directly.

Conceptual Common Lisp API:

#+begin_src lisp
(query-kb client
          :kb "star.dialect.en-us"
          :release release
          :goal goal
          :max-depth 32
          :max-solutions 20
          :timeout-ms 500
          :refresh t)

(explain-kb client
            :kb "star.dialect.en-us"
            :release release
            :goal goal)
#+end_src

The client owns transport concerns only:

- server URL and TLS;
- bearer-token retrieval;
- JSON encoding/decoding;
- deadlines;
- bounded safe retries;
- typed error mapping;
- secret redaction;
- actor/request correlation.

The client does *not* implement Prolog inference or CouchDB synchronization.

Raw Prolog query strings are not the normal actor API. Actors send the existing structured goal representation.

* Query Provenance

The query server already supplies a useful base provenance envelope.

For each synchronous result, preserve where relevant:

#+begin_src text
query_id
kb
release
count
budget
limit_hits
proof_usage
refresh/sync information
#+end_src

For explained results, preserve or reference proof source IDs/revisions when the derivation needs auditability.

A derived StarIntel document can additionally record the actor version and =star-kb= bundle/source commit that correspond to the runtime release.

Conceptual extension:

#+begin_src json
{
  "knowledgeInference": {
    "server": "prolog-query-server",
    "queryId": "...",
    "kb": "star.dialect.en-us",
    "release": "2026-09-10-a",
    "bundleVersion": "0.1.0",
    "sourceCommit": "...",
    "proofSourceIds": ["..."],
    "actor": "dialect-enricher",
    "actorVersion": "0.1.0"
  }
}
#+end_src

Never store tokens or raw Authorization headers in provenance.

* Canonical Knowledge Versus Observations

Keep these classes separate:

| Thing | Where it belongs | Example |
|-------+------------------+---------|
| reusable fact | =star-kb= -> compiled PQS release | a county is contained in a state |
| reusable rule | =star-kb= -> compiled PQS release | a relation implies another relation under documented conditions |
| run observation | StarIntel evidence/document store | actor saw token =pop= in document X |
| learned-model score | StarIntel evidence/document store | model M assigned region R score 0.71 |
| promoted knowledge | reviewed future =star-kb= release | aggregated/researched conclusion accepted as reusable knowledge |

There is no automatic observation -> canonical knowledge feedback loop.

* Passing Per-Document Evidence Into a Query

V0.1 should avoid temporary runtime writes just to ask a question.

The actor passes a bounded evidence value in the query goal:

#+begin_src json
{
  "predicate": "dialect_candidate",
  "args": [
    [
      {"functor": "lexical", "args": ["pop"]},
      {"functor": "lexical", "args": ["drinking_fountain"]}
    ],
    {"var": "Region"},
    {"var": "Score"}
  ]
}
#+end_src

If real workloads prove that bounded goal arguments are insufficient, research a query-scoped temporary evidence context later.[fn:ephemeral]

* First Reference Consumer: Dialect Enrichment

The first real bundle is =star.dialect.en-us=.

Initial knowledge areas:

#+begin_src text
core provenance
core confidence
US geographic hierarchy
dialect regions
dialect lexical features
dialect syntactic features
deterministic scoring rules
#+end_src

The actor returns *candidate regions with evidence*, not a claim that somebody's exact physical location has been discovered.

Evidence classes stay separate:

#+begin_src text
linguistic evidence
  "pop", "y'all", syntactic constructions, etc.

contextual geographic evidence
  a regional brand or institution mention

named geographic evidence
  explicit city/place/road/business mention

learned-model evidence
  versioned neural-model score
#+end_src

A regional brand mention is not automatically a dialect feature.

The first scoring implementation must define its units. If it is a weighted evidence score, call it that. Only call a number a probability after held-out evaluation shows that the probabilities are calibrated.

* Learned Models

Deep learning remains a third evidence path, especially for free-form text and later audio.[fn:deep-learning]

#+begin_src text
input text/audio
    |
    +--> deterministic feature extraction --> observations ----+
    |                                                         |
    +--> learned model ---------------------> model scores -----+--> Prolog reasoning/fusion
                                                              |
                                                    canonical KB rules
#+end_src

A model result must include model identity/version, input reference, score semantics, and evaluation/calibration version.

Model output does not automatically become a canonical fact.

* Probabilistic Logic and Tabling

Do not add =cplint= or arbitrary table declarations to the production query server in V0.1.[fn:cplint][fn:tabling]

They are legitimate future research candidates, but the shared knowledge/release/proof architecture should be validated first. If measured workloads show a need, do a separate pass that preserves the current safe execution boundary.

* StarLang Boundary

StarLang stays unaware of Prolog syntax.

A later StarLang actor can invoke a generic capability such as:

#+begin_src text
knowledge.query
  transport: http
  requestContract: pqs.query.v1
#+end_src

The StarLang compiler/runtime does not =consult= =.pl= files or implement Prolog semantics. It sends the same structured network request as the Lisp client.

* Failure Semantics

The client must distinguish at least:

#+begin_src text
knowledge_not_found
release_not_found
invalid_goal
invalid_release
release_conflict
knowledge_conflict
analysis_rejected
query_timeout
resource_limit
unauthorized
forbidden
server_unavailable
no_solutions
successful_solutions
#+end_src

=No solutions= means Prolog could not prove the requested goal under the selected KB/release. It is not a network failure.

A timeout also does not mean no solution exists; it means the computation did not finish inside its budget.

* Security Rules

1. Actors normally receive read-only query credentials.
2. Publishing credentials are separate and write-capable.
3. Production non-loopback traffic uses TLS.[fn:tls]
4. Source =.pl= is parsed but never directly executed by the compiler/runtime.
5. Actor messages, scraped documents, model output, and targets can never supply executable Prolog source.
6. Query depth, inference steps, solution count, request size, loaded-KB size, proof size, and execution time remain bounded.
7. Unresolved CouchDB knowledge conflicts fail closed.
8. Release activation uses revision checks and =strict:true=.
9. Logs and metrics redact credentials and avoid dumping private evidence bodies.
10. Source provenance and licensing are validation inputs, not optional decoration.

* Tests

** =star-kb=

- parse legal source without executing it;
- reject every forbidden construct;
- preserve variable identity and useful source positions;
- deterministic normalization and JSON output;
- deterministic document IDs;
- module dependency closure;
- build dependency-cycle rejection;
- source/license validation;
- stable bundle content hashes;
- expected fixture inferences;
- identical inputs produce identical release payloads.

** =prolog-query-server= integration

- stage generated release;
- =/v1/analyze= accepts valid release and rejects invalid fixture release;
- publisher always activates with =strict:true=;
- pinned query and explain work before activation;
- active cutover is atomic;
- old release remains queryable;
- rollback works;
- proof IDs/revisions map to generated documents;
- manifest revision conflict blocks activation;
- unresolved CouchDB conflicts still block inference.

** Common Lisp client

- exact request/response fixtures;
- sync query and explain;
- release pinning;
- query ID/budget/limit metadata extraction;
- no-solutions versus errors;
- timeout and resource-limit mapping;
- auth and redaction;
- live test stack integration.

** Dialect actor

- lexical/syntax fixtures produce expected ranking;
- unknown features do not fabricate evidence;
- conflicting evidence preserves alternatives;
- contextual and named-place evidence remain separate from linguistic evidence;
- exact KB/release/query ID are recorded;
- duplicate delivery is idempotent;
- held-out learned-model evaluation splits by respondent rather than by post.

* Implementation Order

After explicit approval:

1. Create =star-kb= with repository policy and tests.
2. Define the restricted source-Prolog profile.
3. Implement a parse-only SWI term reader plus validator and safe-AST compiler.
4. Define module, bundle, source, and generated-release manifests.
5. Compile a tiny =star.core.test= bundle.
6. Stage it in a test =prolog-query-server= deployment.
7. Run static analysis, pinned query, explain, and release-diff checks.
8. Activate it using =strict:true= and the current manifest =_rev=.[fn:rev]
9. Prove rollback and conflict behavior.
10. Add the generic Common Lisp query client.
11. Build =star.dialect.en-us=.
12. Add =dialect-enricher=.
13. Start first-party dialect corpus collection/research.
14. Benchmark deep-learning/probabilistic extensions from measured gaps.
15. Add the StarLang adapter after the query contract stabilizes.

Do not skip directly to hard-coding dialect facts inside the actor.

* Explicit Non-Goals for V0.1

- arbitrary remote Prolog execution;
- a second Prolog query server;
- Git as the live database;
- automatic promotion of observations/model outputs into shared knowledge;
- cross-KB runtime imports/joins;
- arbitrary SWI module loading;
- production =cplint= execution;
- arbitrary tabling directives;
- Prolog syntax embedded into StarLang;
- model training inside the query server;
- claiming exact personal geolocation from dialect evidence.

* Acceptance Criteria

Implementation is complete only when:

1. A =star-kb= source bundle compiles deterministically into safe PQS documents.
2. The source compiler parses but never executes source =.pl=.
3. A generated release can be staged, strictly analyzed, queried, explained, activated, pinned, and rolled back.
4. Publication cannot activate with =strict:false= through the normal =star-kb= tooling.
5. Source provenance/license metadata survive compilation into inspectable runtime documents.
6. Proof source IDs/revisions map back to deterministic source-clause records.
7. A generic Common Lisp client queries a live test server with bounded deadlines and typed errors.
8. The dialect actor uses that generic client instead of its own Prolog runtime.
9. Dialect output separates linguistic/contextual/named-geo/model evidence.
10. Derived output records exact KB release and query provenance.
11. Existing query-server and StarIntel tests remain green.
12. A new operator can reproduce the release from documented source without hidden state.

* Footnotes and Glossary

This section is intentionally verbose. It exists so the rest of the design can use precise technical terms without requiring the reader to already know Prolog, CouchDB, distributed-systems, or machine-learning jargon.

[fn:adapter] *Adapter*: code that translates between two interfaces. Here it means the thin code that turns a StarIntel/StarLang request into the HTTP JSON expected by =prolog-query-server= and turns the response back into StarIntel data.

[fn:actor] *Actor*: a long-lived component that receives messages and handles them one at a time according to its behavior. In StarIntel, actors perform work such as enrichment, routing, scraping, or persistence and can send messages/documents to other actors.

[fn:arity] *Arity*: the number of arguments a Prolog predicate takes. =parent/2= has arity 2; =dialect_candidate/3= has arity 3. Accidentally using the same predicate name with incompatible arities is usually a bug and the query-server analyzer can flag it.

[fn:ast] *AST (Abstract Syntax Tree)*: a structured data representation of code after parsing. Instead of shipping the text =human(socrates).=, the runtime can store data describing predicate =human= with one argument =socrates=. The query server uses JSON-shaped AST data so it never needs to execute arbitrary source text from HTTP/CouchDB.

[fn:async] *Asynchronous query*: a query submitted as a background job. The caller gets a job/query ID first and checks/cancels it later instead of holding one HTTP request open until inference completes.

[fn:budget] *Query budget*: hard limits on how much work one query may perform, such as timeout, recursion depth, solution count, inference steps, or proof size. Budgets prevent one pathological query from consuming unbounded CPU/RAM.

[fn:builtin] *Builtin*: a predicate implemented by the query runtime itself rather than stored as a user rule. Current safe examples include equality/disequality, arithmetic, numeric comparisons, and type checks. Only explicitly whitelisted builtins are executable.

[fn:bundle] *Bundle*: the thing an actor asks for conceptually: a named, versioned collection of source modules plus all their dependencies. In V0.1 a bundle is compiled into one query-server KB release.

[fn:calibration] *Calibration*: whether a model/score that says =0.70= is actually correct about 70 percent of the time for comparable cases. A number between 0 and 1 is not automatically a probability just because it looks like one.

[fn:canonical] *Canonical knowledge*: reusable knowledge intentionally accepted as part of the shared corpus. It is different from an observation made during one investigation. Canonical means "this is the maintained shared version," not "this can never be wrong."

[fn:changes] *=_changes= feed*: CouchDB's ordered-ish stream of document changes used for synchronization. Consumers may see some changes more than once, so applying a change must be safe to repeat.

[fn:clause] *Clause*: one Prolog fact or rule. =human(socrates).= is a fact clause. =mortal(X) :- human(X).= is a rule clause.

[fn:consult] *=consult=*: the normal Prolog action of loading a source file as executable program code. This design deliberately does *not* consult =star-kb= source during compilation; it parses source terms as data and validates them first.

[fn:couchdb] *CouchDB*: the document database used by the query server to durably store compiled knowledge documents and release manifests. It provides document IDs/revisions, replication, conflict semantics, Mango queries, and the =_changes= feed.

[fn:couchdb-query-server] *CouchDB query server*: CouchDB terminology for an external language runtime used while building map/reduce views. This repo also contains a Prolog implementation of that protocol. It is not the same thing as the HTTP expert-system API that actors use for recursive Prolog inference.

[fn:cplint] *=cplint=*: a SWI-Prolog package for probabilistic logic programming. It can represent uncertain rules probabilistically, but it is not part of V0.1 because introducing it safely into the current restricted runtime needs separate research/testing.

[fn:deep-learning] *Deep learning*: neural-network-based statistical learning. In this design a deep model may turn text/audio into a score or feature evidence, but that output remains versioned evidence that Prolog may reason over; it does not become canonical truth automatically.

[fn:dependency-closure] *Dependency closure*: start with the modules explicitly requested by a bundle, recursively include everything those modules require, and continue until no new dependencies remain. The complete resulting set is the closure.

[fn:deterministic] *Deterministic build/identity*: the same normalized source and version inputs produce the same output and identifiers. This makes diffs, reproducibility, caching, and audit possible.

[fn:directive] *Prolog directive*: a source term beginning with =:-= that asks the Prolog system to do something while loading/compiling, such as load a module or run initialization. V0.1 rejects executable directives rather than trusting them.

[fn:ephemeral] *Ephemeral/query-scoped context*: temporary facts/evidence that exist only for one query and disappear afterward. V0.1 avoids adding this runtime concept until bounded goal arguments are shown to be insufficient.

[fn:fact] *Fact*: a Prolog clause that states something directly and has no rule body, for example =located_in(columbus, ohio).= A fact is data the reasoning engine can match against.

[fn:fail-closed] *Fail closed*: when the system cannot establish a safe/correct state, it refuses to proceed rather than guessing. Example: an unresolved CouchDB conflict in executable knowledge blocks inference instead of silently choosing one version.

[fn:fixture] *Fixture*: small fixed test data checked into the repository so tests can repeatedly prove exact behavior without depending on changing live data.

[fn:ground] *Ground term/fact*: a Prolog term containing no variables. =human(socrates)= is ground; =human(X)= is not. Persisted facts in the current query server must be ground.

[fn:http] *HTTP*: the network protocol used by the query-server API. Actors send JSON requests to endpoints such as =/v1/query= and =/v1/explain=.

[fn:idempotent] *Idempotent*: safe to perform again without creating a second incorrect side effect. StarIntel uses at-least-once messaging, so an actor may see the same work twice and must avoid emitting duplicate logical results.

[fn:immutable] *Immutable release*: once activated, the knowledge documents in that release are not edited in place. Changes are staged as a new release. This makes old inferences reproducible and rollback straightforward.

[fn:inference] *Inference*: asking the Prolog engine what follows from the stored facts and rules. Example: if the KB says =human(socrates)= and =mortal(X) :- human(X)=, inference can prove =mortal(socrates)=.

[fn:kb] *KB (knowledge base)*: a named collection of facts and rules available to the inference engine.

[fn:kb-release] *=(kb, release)= pair*: the exact runtime knowledge set selected by a query. =kb= names the logical knowledge base; =release= selects one immutable version of it.

[fn:manifest] *Manifest*: a small metadata document describing what something is and/or which version is active. PQS uses a per-KB CouchDB manifest whose =active_release= field selects the default release.

[fn:meta-interpreter] *Meta-interpreter*: a Prolog program that interprets a restricted set of Prolog-like rules itself instead of giving stored data directly to arbitrary Prolog execution. PQS uses this boundary to control what persisted knowledge is allowed to do.

[fn:module] *Source module*: in this design, a reusable group of related =star-kb= facts/rules plus metadata about what it provides/requires. It is a build organization concept, not automatically a SWI-Prolog runtime module.

[fn:naf] *Negation as failure*: the common Prolog interpretation of =not P=: treat =P= as false when =P= cannot be proven. This differs from having explicit evidence that =P= is false and can behave badly in recursive negative cycles.

[fn:negation-cycle] *Negative/negation cycle*: a rule dependency loop where proving something ultimately depends negatively on itself. These can make semantics ambiguous; the current PQS release analyzer treats non-stratified negative recursion as an error.

[fn:observation] *Observation*: something an actor or collector saw in one particular document/run, such as "the text contained the word pop." It is evidence for a query but is not automatically shared reusable knowledge.

[fn:pqs] *PQS / =prolog-query-server=*: the existing repository/service that stores safe Prolog fact/rule documents in CouchDB and executes bounded expert-system queries over them.

[fn:predicate] *Predicate*: a named relation/function-like logical relation in Prolog, identified by name and arity, such as =located_in/2= or =dialect_candidate/3=.

[fn:proof-tree] *Proof tree*: a machine-readable explanation of how Prolog proved a result: which rule was used, which subgoals had to be proven, and which persisted fact/rule documents supplied those steps.

[fn:provenance] *Provenance*: where a piece of knowledge or result came from. Here that can include source URL, source record, source module/file/clause, Git commit, generated CouchDB document ID/revision, KB release, query ID, actor version, and proof path.

[fn:query-id] *Query ID*: a unique identifier generated by the query server for one inference request. It is useful for logs, metrics, async job status, and linking a derived StarIntel result to the exact query execution.

[fn:read-term] *=read_term/3=*: SWI-Prolog's parser-level predicate for reading one Prolog term and returning it as a Prolog data structure. Options can also return variable names and source positions. Reading a term is not the same as consulting/executing the file.

[fn:recursion] *Recursion*: a rule eventually calls itself, directly or through other rules. Positive recursion can be legitimate; uncontrolled recursion still needs depth/step limits. A source-module dependency cycle is a different build-graph problem.

[fn:release] *Knowledge release*: an immutable version of one runtime KB. New facts/rules are staged under a new release ID, tested, and then selected as active with one manifest update.

[fn:rev] *=_rev=*: CouchDB's revision token for a document. Writers include the current revision when updating so two publishers cannot silently overwrite each other's change. A stale revision produces a conflict instead.

[fn:rlm] *RLM*: here, =prolog-rlm=, the separate reasoning/agent runtime. It may use the shared knowledge service as a client but does not own the canonical StarIntel KB.

[fn:rollback] *Rollback*: returning the default runtime to a previous known-good release. Because old releases are immutable, rollback is mainly a manifest switch rather than reconstructing old files by hand.

[fn:rpc] *RPC (Remote Procedure Call)*: a generic way for one process to ask another process to perform an operation. HTTP+JSON is the concrete RPC-like transport proposed here.

[fn:rule] *Rule*: a Prolog clause saying a conclusion is true when its body can be proven, for example =mortal(X) :- human(X).= Rules are the reusable reasoning logic layered over facts.

[fn:runtime] *Runtime*: the live software actually executing queries. In this design that is PQS/SWI-Prolog plus CouchDB, not the Git repository containing human-edited source.

[fn:stage] *Stage a release*: write a new release's generated fact/rule documents to CouchDB without making that release the default yet. Staging allows validation and pinned test queries before cutover.

[fn:star-kb] *=star-kb=*: proposed repository containing the human/agent-maintained reusable knowledge source, manifests, source records, fixtures, and publishing tooling.

[fn:strict-activation] *Strict activation*: PQS activation with =strict:true=. PQS runs its static analyzer while holding the KB synchronization boundary and refuses to activate releases containing structural errors.

[fn:tabling] *Tabling*: Prolog memoization of subgoal answers. It can improve recursive-query performance and termination, but allowing arbitrary table declarations from persisted knowledge would expand the runtime capability surface, so it is deferred.

[fn:tls] *TLS*: encryption/authentication used by HTTPS. It prevents bearer tokens and query data from being sent as readable plaintext across an untrusted network.

[fn:restricted-prolog] *Restricted Prolog/source profile*: the deliberately small subset of Prolog syntax =star-kb= accepts for reusable facts/rules. It excludes general code execution, I/O, dynamic database mutation, arbitrary meta-calls, and similar capabilities.
