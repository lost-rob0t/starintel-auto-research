* Decision

StarLang SHALL migrate from =star-lang.core-surface.prototype= into final ASDF
systems by semantic ownership, not by copying current prototype files verbatim.

The migration SHALL preserve exactly one authoritative implementation of each
moved concept.

Final systems MUST NOT depend on =starlang-prototype= or the prototype core
package. During migration, the dependency direction is final systems inward,
with =starlang-prototype= acting only as a strictly temporary compatibility and
end-to-end aggregate. It is a deletion target, not a permanent product layer.

* Layer model

The final architecture has four logical layers.

** Portable protocol/data layer

Includes:

- =star-actor-protocol=;
- =star-canonical-json=;
- portable mailbox/lease/journal value contracts where applicable.

This layer contains no parser state, live actor references, sockets, queues, or
runtime-specific transport objects.

** Compiler layer

=starlang-compiler= owns source syntax, provenance, parsing, expansion,
source-aware diagnostics, semantic lowering, and compilation into portable
protocol/IR objects.

Compiler may depend on portable protocol/data systems. Portable systems MUST NOT
depend on compiler.

** Runtime layer

=starlang-runtime= coordinates live actors, directory/liveness, deterministic
execution, domain servers, durable journal/lease/mailbox state, and injected
effect/transport ports.

Runtime depends on portable protocol/data systems and runtime port interfaces.
It MUST NOT depend on compiler parser/syntax internals for normal execution of
already compiled artifacts.

** Adapter layer

=star-adapter-sdk= defines portable runtime effect/transport interfaces.
Concrete adapters such as HTTP/process/Sento implementations depend on those
interfaces and are selected by deployment/runtime composition.

Portable compiler and actor protocol systems MUST NOT depend on concrete
adapters.

* Condition model

A single compiler-oriented error hierarchy SHALL NOT be the hidden dependency
between every final system.

Each final subsystem owns narrow condition classes appropriate to its API.

Examples:

#+begin_example
star-actor-protocol-error
  invalid-star-service-uri-error
  invalid-wire-envelope-error

star-journal-error
star-lease-error
star-runtime-error
#+end_example

=starlang-compiler= owns source-aware compiler conditions with spans/origins.
When compiler lowering invokes a final subsystem and receives a protocol/runtime
validation condition, the compiler may wrap or translate that failure while
attaching the current source context.

This keeps source diagnostics precise without forcing runtime/protocol packages
to import syntax objects.

* One-authority migration rule

For every moved symbol or behavior:

1. implement it in the final package;
2. add direct final-system tests;
3. change prototype callers to import/call the final implementation;
4. delete the prototype definition once all tracked callers use the final owner;
5. keep a thin compatibility wrapper only when a specific still-supported caller requires it;
6. forbid independent logic, state machines, parsing, policy, or serialization in that wrapper;
7. prove existing aggregate tests still pass;
8. remove the wrapper as soon as its last tracked caller is migrated.

A slice is not complete if both prototype and final packages contain independent
copies of the same parser, validator, state machine, serializer, resolver, or
runtime behavior.

* First extraction slice: shared STAR URI value model

The original package-extraction draft treated =star-actor-protocol= as the owner
of a StarLang-specific =domain:address:actor-name= URI model. That ownership is
superseded by STAR-LANG-004 and STAR-SERVER-041.

The first URI extraction slice SHALL instead consume the shared RFC 3986 STAR URI
value model and conformance fixtures. StarLang SHALL NOT create or retain a
second canonical URI parser.

The final StarLang-facing protocol layer owns only StarLang projection and
validation rules such as:

- actor and service declarations may carry canonical STAR resource URIs;
- actor resources require resource kind =actor=;
- service resources require resource kind =service=;
- duplicate canonical resource claims inside one manifest are invalid;
- portable manifests contain canonical STAR identity, never live runtime references;
- runtime adapters map canonical identity to local/runtime routing material.

The reusable shared URI boundary owns:

- RFC 3986 parsing and canonicalization;
- authority representation;
- path segments;
- resource-kind/resource-path extraction;
- percent-encoding normalization;
- legacy compatibility parsing and explicit migration targeting.

New final systems MUST NOT depend on legacy tuple accessors as canonical identity.
Legacy tuple input may exist only in an explicit compatibility module until its
callers are migrated.

* Service URI compatibility strategy

Legacy input such as:

#+begin_example
star://domain:address:actor-name
#+end_example

is compatibility input only. New manifests MUST emit hierarchical canonical
identities such as:

#+begin_example
star://gserver.starintel.actor/actor/user-hunt
star://bbpd.starintel.actor/service/recon
#+end_example

There is no universal inferred rewrite from the legacy tuple to a new authority
and resource path. Migration requires an explicit canonical target or
application-owned mapping, per STAR-LANG-004 / STAR-SERVER-041.

Any compatibility definitions still exported from the prototype SHALL delegate
to the shared URI implementation and MUST NOT construct a second URI data model.

* Subsequent extraction order

After shared STAR URI consumption is green:

1. move portable lifecycle/wire envelope data and validation into
   =star-actor-protocol=;
2. split syntax-aware actor lowering into =starlang-compiler=;
3. move deterministic JSON ownership into =star-canonical-json=;
4. move journal port/replay ownership into =star-journal=;
5. move lease policy/state into =star-lease=;
6. move mailbox policy into =star-mailbox=;
7. move runtime directory/service resolution/dispatch coordination into
   =starlang-runtime=;
8. move remaining parser/expander/compiler IR ownership into
   =starlang-compiler=;
9. migrate concrete transport/process/HTTP behavior behind final adapter ports;
10. migrate all product CLI/API entry points off =starlang-prototype=;
11. remove compatibility wrappers whose callers are gone;
12. delete =prototype/= when the repository-wide completion audit proves no
    remaining product, test, build, Nix, ASDF, CLI, fixture, or documentation
    dependency requires it.

Each step may be its own implementation PR if that keeps the dependency change
reviewable in the StarLang implementation repository.

* ASDF requirements

Every extracted final system SHALL:

- have explicit =:depends-on= declarations;
- load successfully in a fresh SBCL process;
- have a real test system invoked by =asdf:test-system=;
- avoid loading =starlang-prototype= transitively;
- avoid filesystem =load= calls into =prototype/=;
- expose only documented public symbols from its package;
- keep implementation-private helpers unexported.

The CI target-system loop SHALL continue loading each final system independently.
As systems gain real implementation, tests should be added to the top-level CI
contract rather than relying only on aggregate prototype tests.

* Nix requirements

Nix validation SHALL prove:

- each touched final system is discoverable under =CL_SOURCE_REGISTRY=;
- required Common Lisp dependencies are explicitly present in the SBCL closure;
- final systems do not work only because =starlang-prototype= happened to load
  first;
- product commands and tests run without adding =prototype/= to the source registry
  once their final-system port is complete.

* Source diagnostic preservation

Moving protocol validation out of the compiler must not degrade source errors.

For each compiler call site that invokes an extracted validator:

#+begin_example
with compiler source context
  -> call final protocol validator
  -> if protocol condition:
       attach current syntax span/origin
       re-signal stable compiler-facing error
#+end_example

Tests SHALL compare error phase, source path, line/column/span, and origin chain
for migrated compiler diagnostics.

* Frozen compatibility surfaces

The following remain stable unless a separate compatibility decision changes
them:

- canonical manifest fixture bytes and hashes where not superseded by an approved protocol migration;
- RFC-based canonical STAR URI semantics from STAR-LANG-004 / STAR-SERVER-041;
- wire protocol version and field spelling;
- explicitly retained actor-name dispatch compatibility;
- deterministic lifecycle outcome semantics;
- source span/import-origin diagnostics.

Legacy =star://domain:address:actor-name= strings are NOT a frozen canonical
surface. They are compatibility inputs scheduled for retirement.

* Prototype Retirement Is a Completion Requirement

Prototype retirement is part of this design, not optional cleanup.

The implementation SHALL repeatedly remove prototype ownership during migration:

- no new feature is implemented only in =prototype/=;
- every completed slice deletes its duplicate prototype implementation;
- final tests replace prototype-only tests where the behavior has moved;
- final fixtures replace prototype-owned fixture authority;
- the installed CLI must execute final systems directly;
- Nix/ASDF release closures must not require =starlang-prototype=;
- documentation and examples must stop teaching prototype packages once final
  equivalents exist;
- compatibility forwarding is allowed only for an identified caller and is
  removed when that caller migrates;
- the repository-wide final audit must search source, tests, ASDF, Nix,
  workflows, scripts, fixtures, examples, and docs for prototype dependencies;
- if the audit proves the port complete, =prototype/= SHALL be deleted in the
  same implementation effort rather than left behind "just in case".

A dedicated lost-rob0t/star-lang issue tracks this proof-and-delete gate.

* Acceptance: first shared URI slice

The first extraction slice is complete when:

1. final StarLang systems consume the shared RFC-based STAR URI implementation;
2. URI conformance uses STAR-SERVER-041 shared fixtures;
3. new manifests emit hierarchical canonical actor/service resource URIs;
4. legacy tuple input is confined to an explicit compatibility boundary;
5. explicit migration mappings are required for legacy tuple conversion;
6. no independent canonical URI parser remains under =prototype/=;
7. final protocol/compiler systems do not depend on =starlang-prototype=;
8. compiler call sites retain source-aware error behavior where applicable;
9. CI independently loads/tests the final URI consumer systems;
10. Nix remains green.

* Acceptance: overall migration

The package-extraction work item is complete only when:

- all product behavior is owned by final ASDF systems;
- no final system imports =star-lang.core-surface.prototype=;
- no final system, product CLI, release closure, or normal test suite loads =starlang-prototype=;
- compiler/runtime dependency direction is acyclic;
- final systems have independent tests;
- approved compatibility fixtures remain green;
- full CI and Nix validation pass from clean environments;
- a repository-wide search finds no required runtime dependency on =prototype/=;
- any remaining references are historical documentation explicitly marked as historical;
- =prototype/= is deleted once those conditions are proven.

* Footnotes and Glossary

- *Final system* — Intended product ASDF system such as =star-actor-protocol= or =starlang-runtime=, as opposed to the transitional prototype aggregate.
- *One-authority rule* — Migration invariant requiring one implementation to own a behavior after each completed extraction slice.
- *Portable protocol layer* — Runtime-neutral data/validation used by compiler and runtime without depending on either layer's internal state.
- *Source-aware condition* — Compiler diagnostic enriched with source span, origin chain, phase, and syntax context.
- *Semantic extraction* — Moving behavior according to architectural ownership, including splitting historically mixed files when necessary.
- *Prototype retirement* — Verified deletion of the transitional =prototype/= tree after final-system ownership and all required call paths are proven complete.
