* Decision Summary

The strict-JSON defect remains live, but the implementation context has changed substantially since the original research transaction. Current =starintel-server/master= already centralizes caller-controlled JSON parsing in =source/frontends/http-boundary-core.lisp=. The boundary enforces media type, a 1 MiB body limit, client-safe =malformed_json= errors, and then performs a YASON parse before converting the same text with JSOWN for the service's existing representation.

That refactor did not close the defect. YASON's current object and array parsing loops consume a comma and then allow the immediately following closing delimiter on the next loop iteration. Therefore YASON cannot serve as StarIntel's strict RFC 8259 syntax authority for trailing commas. YASON does, however, explicitly detect duplicate keys in one object and signals its =duplicate-key= condition.

The server already depends on =com.inuoe.jzon=. Jzon exposes RFC-8259-oriented parsing with explicit =:allow-comments=, =:allow-trailing-comma=, =:allow-multiple-content=, =:max-depth=, and =:max-string-length= controls; it accepts UTF-8 octet vectors directly and provides a SAX-like event parser. This makes a bounded strict boundary possible without adding another external runtime or replacing the rest of StarIntel's HTTP stack.

Research is therefore sufficient for a bounded design. Implementation authorization remains operator-only.

* Evidence

** The defect is a parser-boundary defect, not a document-schema defect

PR #126 proves =parse-json-octets= accepts an object ending in =,}= where the expected result is HTTP 400 / =malformed_json=. The failure occurs before any need to change StarIntel document semantics. The test must remain a syntax-boundary test.

** YASON cannot be the strict trailing-comma authority

Upstream YASON source parses objects by consuming a comma after a member and then beginning the loop again. At loop start, a closing brace terminates the object. Consequently ={"x":1,}= is structurally accepted. Its array loop has the same shape around closing brackets.

YASON does provide a useful property absent from many map-building parsers: before inserting a member it tracks keys in a hash table and signals =duplicate-key= if a name already exists in that object.

** Jzon is already in the server dependency graph

=current starintel-gserver.asd= depends on =com.inuoe.jzon= as well as YASON and JSOWN. This research therefore does not need to propose a new JSON library merely to obtain strict syntax.

Jzon's public parser explicitly controls comments, trailing commas, multiple top-level content, maximum nesting depth, and maximum string length. Its documented default data model preserves JSON false and null distinctly (=nil= versus =null=), arrays as vectors, and objects as =equal= hash tables. The streaming API exposes =:object-key= events, which is sufficient to implement deterministic duplicate-key rejection without reparsing malformed JSON through a permissive parser.

** Current route ownership is already mostly centralized

The canonical document, target compatibility, and bulk routes in =http-boundary-routes.lisp= call =parse-json-request=, which delegates to =parse-json-octets=. Other HTTP modules must still be checked during implementation for direct parser calls, but the correct architectural owner already exists: the shared HTTP boundary, not per-route patches.

* StarIntel Requirements

1. There is one caller-controlled =application/json= syntax authority before schema validation, authorization-dependent mutation, actor dispatch, outbox publication, Rabbit work, target authority, or persistence.
2. The syntax contract is RFC 8259 strict by default: comments, trailing commas, and multiple top-level values are rejected.
3. Duplicate member names are rejected deterministically at the syntax boundary. Do not let authority-sensitive values depend on parser-specific first/last-wins behavior.
4. Parse directly from the already-bounded octet body where possible; do not create an unbounded preprocessing copy.
5. Apply explicit nesting and string-length limits in addition to the existing body-byte limit. Numeric/resource behavior must be covered by the hostile corpus rather than silently delegated to implementation defaults.
6. Parser failures become the existing HTTP 400 / =malformed_json= envelope with the request correlation ID; internal parser condition text is not exposed.
7. Valid canonical request bodies retain the current JSOWN-facing service representation until a separately justified representation migration is designed.
8. All body-bearing HTTP routes must converge on the common boundary. A route-local =jsown:parse=, =yason:parse=, or =jzon:parse= on caller bytes is a contract violation unless it is the boundary implementation itself.
9. Rejection must be proven side-effect-free for document/outbox writes, Rabbit publication, user/credential mutation, target/lease authority, and actor/task submission.
10. No StarLang change is required. This is a Common Lisp HTTP adapter boundary below domain behavior.

* Hostile Corpus Required by Design

The design must cover at least valid canonical JSON plus:

- object and array trailing commas;
- comments;
- duplicate object keys, including nested duplicates;
- multiple top-level values / trailing tokens;
- malformed and truncated strings/escapes;
- invalid UTF-8;
- malformed numbers and non-JSON numeric extensions;
- maximum-depth overflow;
- maximum-string-length overflow;
- empty body and wrong top-level shape where route contracts require an object or array.

Each negative case must establish both the typed client result and that the downstream side-effect spy was not invoked.

* Design Direction

The preferred bounded direction is to make Jzon the single strict lexer/parser authority over the bounded request octets, with all permissive extensions explicitly disabled and limits explicitly supplied. Duplicate-key rejection should be implemented while consuming Jzon's streaming object-key events, so the strict parser remains the only syntax reader. The resulting JSON value can then be converted in-memory into the existing JSOWN representation rather than feeding the untrusted original bytes through JSOWN again.

A transitional triple parse (=Jzon + YASON + JSOWN=) is rejected as the architectural target. It multiplies parser semantics and work, and creates ambiguity about which parser defines correctness. YASON's duplicate detection is evidence for the required policy, not a reason to retain it in the final request path.

* Adversarial Questions for Design

- Does the Jzon event-state duplicate detector correctly scope key sets independently for nested objects?
- Can conversion preserve the distinction among =false=, =null=, empty array, and empty object expected by current JSOWN consumers?
- Are depth and string limits applied before materializing pathological structures?
- Does every body-bearing route reach this boundary exactly once?
- Can malformed input trigger any logging path that accidentally includes credentials or full bodies?
- Does the implementation preserve the existing 413-before-parse body limit and 415 media-type ordering?

* RED-First Handoff

The first implementation slice must start from the preserved #126 regression and add the smallest strict-parser contract matrix without modifying production parsing first.

Mandatory first RED:

#+begin_example
input: {"_id":"strict-json-red",}
content-type: application/json
expected: http-input-error status=400 code=malformed_json
observed untouched behavior: accepted / no http-input-error
#+end_example

The RED must fail for the expected permissive parser behavior, not a broken fixture or unavailable test harness.

* Unresolved Questions

- Exact =max-depth= and =max-string-length= values require compatibility/load evidence; design should specify deterministic configuration ownership but must not invent production numbers from thin air.
- The exact installed Jzon source revision is transitive in the current dependency closure rather than separately pinned in =qlfile.lock=. Implementation must capture the resolved closure/version before depending on version-specific condition classes or event details.
- A route audit must verify that auth/authorization/contract route modules do not retain independent direct body-parser seams outside =parse-json-request=.

* Footnotes and Glossary

- *HTTP boundary* :: The server adapter that validates and decodes caller-controlled HTTP input before application behavior.
- *Strict syntax authority* :: The single parser whose acceptance grammar defines valid =application/json= input for StarIntel.
- *Duplicate key* :: Repetition of the same object member name within one JSON object; rejected to avoid parser-dependent authority semantics.
- *Jzon* :: Common Lisp RFC-8259-oriented parser already in the StarIntel server dependency graph, with explicit strictness and resource-limit controls.
- *JSOWN representation* :: The existing internal JSON object/list representation consumed by substantial StarIntel application code; retained as a compatibility target for this bounded slice.
- *Lifecycle readiness* :: Machine/workflow conclusion that evidence is sufficient to produce a design; it is not operator implementation approval.
