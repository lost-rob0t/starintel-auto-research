* Research Question

How should StarIntel expose one small Model Context Protocol[fn:mcp] information-retrieval surface over self-hosted search, external search/fetch MCPs, retained local web search, and the full StarIntel service without creating a tool explosion, duplicating provider results, or placing autonomous research reasoning inside an MCP tool?

The implementation constraint is library-first Common Lisp[fn:common-lisp]: protocol, client, server, execution-plan, provider, result, provenance, and fusion behavior must live in reusable ASDF systems. The final StarIntel Meta MCP is a consumer package in the same monorepo.

* Assess

** MCP protocol direction

The current MCP direction supports a reusable client/server library boundary, Streamable HTTP transport, capability discovery, cancellation, and bounded tool execution.[fn:mcp-release][fn:mcp-http]

The Meta design does not need autonomous behavior inside an MCP tool. Search and fetch are bounded primitives that can be planned and executed deterministically.

** SearXNG and YaCy

SearXNG exposes an HTTP search API with JSON output when enabled. It has a native YaCy engine and supports local YaCy search, so the local YaCy index can participate in federated retrieval without making YaCy a second model-visible tool surface.[fn:searx-api][fn:searx-yacy]

The corrected design does not add direct crawl/index control to Meta MCP. YaCy is relevant here only as a retained local search source reachable through the approved search path.

** External search MCPs

The official Brave Search MCP exposes multiple search/fetch-oriented capability classes. Exa exposes a compact search/fetch-oriented surface, and Tavily demonstrates that upstream MCPs may expose broader capabilities than Meta should adopt.[fn:brave-mcp][fn:exa-mcp][fn:tavily-mcp]

The architectural conclusion is to compile semantic Meta requests onto reviewed provider capabilities instead of mirroring every upstream tool name into the client-visible surface.

** Common Lisp MCP ecosystem

Current Common Lisp MCP implementations are useful references but do not justify coupling StarIntel to one implementation without conformance testing.

- =40ants/mcp= provides server-side MCP infrastructure, transports, schema-backed tools, and OpenRPC foundations.[fn:40ants-mcp]
- =cl-ai-project/cl-mcp= demonstrates Common Lisp MCP server, transport, worker-isolation, test, and Nix patterns.[fn:cl-mcp]
- Common Lisp is not currently an official MCP SDK language, so StarIntel should treat protocol conformance as an explicit library responsibility rather than assuming an official SDK supplies it.[fn:mcp-sdks]

The proper implementation shape is reusable Common Lisp protocol/client/server and execution libraries first, with =starintel-meta-mcp= layered above them.

** Existing StarIntel boundary

The current StarIntel server already owns documents, search, persistence, authorization, and platform behavior. Meta must not learn CouchDB, Clouseau, or persistence internals directly. A full StarIntel MCP is the authoritative MCP boundary for StarIntel operations, authorization, and resource scope.

Meta consumes the StarIntel MCP like another capability provider.

* Design Finding

The approved client-visible Meta surface is:

#+begin_example
search(...)
fetch(...)
#+end_example

There is no =crawl(...)= tool in PIPELINE-005.

There is also no =research(...)= Meta tool. Research requires iterative reasoning, branch selection, gap analysis, evidence review, and stopping criteria. That belongs to a future StarIntel Agent exposed through Agent2Agent[fn:a2a].

The future agent can use both Meta MCP and the full StarIntel MCP:

#+begin_example
StarIntel A2A Agent
  -> Meta MCP: search / fetch
  -> StarIntel MCP: full authorized platform abilities
#+end_example

* Attack

** Tool explosion

Directly re-exporting every upstream MCP produces provider-coupled tool names, larger model context, and client-visible churn when providers change.

Countermeasure: expose semantic =search= and =fetch= tools and keep provider capabilities internal.

** False corroboration

Calling Brave through SearXNG and Brave MCP separately can return the same underlying source family twice. The same problem applies to any provider reachable through multiple adapters.

Countermeasure: normalized results distinguish adapter identity, physical provider/origin, source locator or document identity, retrieval time, and content hash. Fusion deduplicates provider origin before ranking or confidence interpretation.

** Confused deputy

If Meta receives broad StarIntel credentials and accepts a narrower caller request, it could accidentally act with more authority than the caller intended.

Countermeasure: the full StarIntel MCP remains authoritative for capability and dataset/resource scope. Meta propagates or exchanges caller authority rather than interpreting =scope=intel= as unrestricted service authority.

** God-service drift

Once Meta can call StarIntel MCP, there is pressure to expose mutations and platform actions through Meta.

Countermeasure: Meta remains an information execution plane. Full StarIntel actions stay on StarIntel MCP. The future A2A agent may compose both services when an autonomous task legitimately needs them.

** Scope creep into crawling

Adding crawl to Meta would turn a small retrieval facade into a larger acquisition/index-control service and introduce additional retention, task, network-policy, and ingest-boundary questions before the core search/fetch plane is proven.

Countermeasure: crawl is removed from PIPELINE-005 entirely. Any future crawling capability would require a new research/design track rather than silently expanding this approved Meta contract.

** Library fragmentation

Implementing protocol parsing, provider adapters, result normalization, and ranking directly inside =starintel-meta-mcp= would make the final package unusable as general Common Lisp LLM tooling.

Countermeasure: stable semantic boundaries become reusable ASDF systems first; the application package wires them together.

* Recommendation

The approved recommendation is:

1. Build reusable Common Lisp libraries for MCP protocol/types, MCP client, MCP server, capability/provider registration, execution-plan representation and execution, normalized search results/provenance, fusion/deduplication, HTTP provider adapters, and MCP-provider adapters.
2. Keep provider selection deterministic and capability-based initially. Do not introduce Prolog-RLM or an LLM planner into the execution plane without later evidence that ordinary code is insufficient.
3. Treat SearXNG as the broad metasearch front end and include the local YaCy index through SearXNG where appropriate.
4. Treat Brave, Exa, Tavily, and future MCPs as capability providers, but adopt only reviewed search/fetch capabilities. Track physical provider identity independently from adapter identity.
5. Build the full StarIntel MCP as the authoritative platform interface; Meta calls it rather than bypassing it.
6. Meta exposes =search= and =fetch= only.
7. Do not implement crawl as part of this Meta MCP design or roadmap.
8. Reserve =research= for the future StarIntel A2A agent, which composes Meta MCP and StarIntel MCP and returns research outputs as A2A Artifacts.
9. Keep infrastructure placement, network topology, credentials, and deployment-specific routing out of public design material. Those details belong in downstream infrastructure RAGE work.

* Decision

Research decision: DONE and approved. =STAR-RESEARCH-PIPELINE-005 StarIntel Meta MCP Execution Plane= is approved with the operator correction that Meta is search/fetch-only and contains no crawl tool or crawl implementation phase.

The library-first rule remains mandatory: the final Meta MCP package contains composition and configuration only; reusable MCP and LLM-tooling semantics live in separate Common Lisp ASDF systems in the same monorepo.

* Footnotes and Glossary

[fn:mcp] Model Context Protocol, or MCP: A protocol for exposing model-controlled tools, resources, and related capabilities through standardized client/server messages.

[fn:common-lisp] Common Lisp: The approved implementation language for the reusable StarIntel runtime libraries in this design track.

[fn:a2a] Agent2Agent, or A2A: An open protocol for interoperable remote agents that discover skills and exchange tasks, messages, status, and artifacts.

[fn:mcp-release] MCP release material: Current release documentation used to validate protocol direction and capability boundaries.

[fn:mcp-http] Streamable HTTP: The MCP remote transport using an HTTP endpoint with request-scoped responses.

[fn:searx-api] SearXNG Search API: The HTTP search interface that can return machine-readable results when enabled by server configuration.

[fn:searx-yacy] SearXNG YaCy engine: The SearXNG backend adapter supporting local YaCy search.

[fn:brave-mcp] Brave Search MCP: Brave's official MCP server exposing several Brave Search API capability classes.

[fn:exa-mcp] Exa MCP: Exa's MCP server exposing web search and fetch capabilities.

[fn:tavily-mcp] Tavily MCP: Tavily's MCP server whose broader tool surface demonstrates why Meta should import reviewed capabilities rather than mirror every upstream tool.

[fn:40ants-mcp] 40ANTS MCP: A Common Lisp MCP framework using OpenRPC with server transports and tool registration.

[fn:cl-mcp] cl-ai-project/cl-mcp: A Common Lisp MCP development server demonstrating multiple transports and isolated SBCL workers.

[fn:mcp-sdks] MCP SDK list: The official MCP SDK list used to check whether Common Lisp has an official SDK.
