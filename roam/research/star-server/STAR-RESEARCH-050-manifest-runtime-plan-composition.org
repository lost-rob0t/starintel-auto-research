* Current-Source Findings

** StarIntel server composition is still largely imperative

Current server source contains process-global composition state such as =*actors-start-hook*=, =*document-patterns*=, =*ingest-workers*=, =*sys*=, =*actor-index-agent*=, producer/CouchDB/target globals, and hard-coded actor startup order. =define-actor= adds startup functions to a global hook; =register-actor= mutates a global actor-name -> actor-ref index; =start-actors= explicitly creates the actor system and then starts producer, CouchDB, actor-index, target timer/actor, and registered hooks.

This confirms #43's core defect: runtime topology is not compiled from one validated deterministic plan before side effects.

** StarLang already owns actor/domain semantic declarations

Current StarLang domain-server compiler code already normalizes and emits manifest entries containing:

- stable domain-server name;
- keyed authority/key type;
- owned document types;
- accepted message types;
- declared tools;
- restart policy;
- mailbox policy;
- dispatcher identity;
- capabilities.

That means the old #43 idea of independently defining accepted/produced types, capabilities, restart/mailbox, and dispatcher semantics again in a server-local Actor Manifest would create two authorities for the same contract.

StarLang remains the semantic declaration layer. StarIntel server must consume a compiled/locked StarLang actor/domain manifest and add only host-runtime binding and deployment facts that the language cannot safely own.

** Existing STAR-MANIFEST-001 is directionally useful but stale

The draft correctly separates Actor Manifest and Dataset Manifest and correctly prohibits actor manifests from enumerating document instances. It also distinguishes dataset membership/storage/flows from executable actor behavior.

However, its Actor Manifest currently includes broad implementation/runtime and behavior fields such as =accepts=, =produces=, =capabilities=, =mailboxPolicy=, =restartPolicy=, implementation locators, and runtime selectors as if this document were the primary semantic authority. That predates the now-concrete StarLang domain-server manifest/compiler path.

The draft therefore needs to be reframed as a composition envelope that references immutable compiled semantic artifacts instead of restating them.

** Dataset manifests are a different kind of authority

A dataset manifest describes a dataset instance/catalog and its bindings: identity, accepted document/schema set, storage, indexes/materializations, lineage/governance, and the selected component/flow bindings for that dataset.

Dataset manifests may choose among already-declared compatible components and flows, but they must not redefine actor message/capability semantics or embed an executable workflow. Executable orchestration belongs to StarLang declarations/compiled plans; runtime execution belongs to the server component/lifecycle layer.

* Research Decision

Keep =STAR-MANIFEST-001= as the canonical design owner, but split the manifest system into three explicit layers.

** Layer 1 — StarLang semantic program manifest

Authoritative for language/domain meaning:

- actor/domain-server identity and semantic version;
- accepted/produced message and document types;
- owned schemas/domain key semantics;
- declared capabilities/tools;
- semantic restart/mailbox constraints;
- declared dispatcher/resource profile where the StarLang contract supports it;
- semantic artifact digest and transitive specification lock identity.

This layer is produced by the closed StarLang compiler. StarIntel does not hand-author a second copy.

** Layer 2 — StarIntel actor deployment binding

A StarIntel Actor Manifest becomes a host composition/deployment envelope referencing one immutable StarLang semantic artifact (or an explicitly legacy built-in compatibility actor during migration).

It may define only deployment/runtime facts such as:

- stable component instance ID and deployment version;
- =programManifestRef= plus artifact/semantic digest;
- implementation adapter kind/reference for trusted installed code;
- runtime component dependencies;
- requested workload/dispatcher class and bounded routee cardinality constraints;
- concrete mailbox capacity/admission profile within declared semantic constraints;
- local/Rabbit/remote ingress binding references;
- authorization/lease/idempotency policy references;
- config and secret-reference schema bindings;
- readiness/health adapter reference from an allowlisted runtime adapter vocabulary;
- lifecycle ownership and operator-visible labels.

It must not redefine the StarLang artifact's accepted message types, capabilities, domain ownership, or semantic failure policy. Any override must be a validated *narrowing* explicitly allowed by the semantic contract; incompatible changes require a new StarLang artifact/version.

** Layer 3 — Dataset manifest

Dataset Manifest remains a data-only dataset-instance/catalog contract:

- dataset ID/version and tenant/owner identity;
- accepted schema/spec references and compatibility requirements;
- storage binding references, never raw credential values;
- validation/normalization policy refs;
- indexes/views/materializations/embedding configuration;
- component bindings by stable component ID/capability;
- flow bindings that select declared typed ports/routes without embedding executable code;
- provenance, retention, access, publication, lease, and research/analysis policy refs;
- migration/materialization lineage.

It cannot grant capabilities, bypass actor authorization, or make a component semantically accept a type its StarLang manifest rejects.

* Manifest Compilation Boundary

The server should compile the data-only deployment and dataset manifests plus locked StarLang semantic manifests into one pure =RuntimePlan= before long-lived side effects.

#+begin_example
locked StarLang semantic manifests
          +
actor deployment bindings
          +
dataset manifests
          +
runtime policy/config
          |
          v
pure validate / normalize / link
          |
          v
RuntimePlan
  components[]
  datasetBindings[]
  routes[]
  lifecycleGraph
  capabilityIndex
  threadDemand
  mailbox/admissionDemand
  storageBindings
  diagnostics
          |
          v
#34/#35/#36/#37 validation + grants
          |
          v
realize runtime
#+end_example

No thread, actor system, Rabbit connection, CouchDB connection, timer, HTTP listener, or tool process may be created before the plan passes semantic linking and the existing capacity/lifecycle validators.

* Cross-Authority Validation Rules

At minimum the compiler must reject:

1. actor deployment binding whose referenced semantic artifact/digest is missing or mismatched;
2. duplicate component instance IDs;
3. dataset binding to a component that does not advertise the required capability/type;
4. route whose message/document type is not accepted by the destination semantic manifest;
5. forbidden dependency cycle according to the #37 lifecycle graph rules;
6. unknown component/capability/schema references;
7. host deployment override that widens semantic capabilities, accepted types, or authority;
8. raw secret/credential literals where a secret reference is required;
9. dispatcher/routee demand that cannot receive a valid #34/#35 grant;
10. unbounded/invalid mailbox configuration contrary to #36;
11. duplicate or ambiguous route ownership without an explicit arbitration policy;
12. dataset storage or visibility policy incompatible with the selected operation/actor policy.

Validation produces typed diagnostics with manifest ID, source artifact/digest, field/path, and violated authority boundary.

* StarLang-First Boundary

No new server-private executable actor DSL is justified.

If #43 exposes missing semantic concepts, the order is:

1. add/extend the required closed StarLang declaration and normalized IR;
2. regenerate/consume the StarLang semantic manifest;
3. bind it through the StarIntel actor deployment manifest;
4. realize through Common Lisp adapters under =star.runtime=;
5. use external processes only for a capability whose adapter genuinely requires them.

This prevents init Lisp or manifest callback fields from becoming a shadow programming language.

* Relationship to Existing P0/P1 Runtime Work

- #34 owns total process-thread budget; manifests request demand, never grant threads.
- #35 owns aggregate Sento execution-lane accounting; actor bindings cannot self-authorize workers.
- #36 owns bounded mailbox/admission semantics.
- #37 owns component lifecycle graph/start-stop/reconnect ownership.
- #39/#40 establish side-effect-free core and explicit runtime/application contracts.
- #41 owns concrete adapter extraction/composition.
- #42 owns component handles/generation/readiness projection.
- #43 compiles declarative semantic + deployment + dataset inputs into a plan consumed by those authorities.

* Adversarial Review

Rejected:

1. *Server-local Actor Manifest duplicates StarLang* — creates semantic drift between accepted types/capabilities/restart/mailbox declarations.
2. *Actor Manifest contains arbitrary Lisp callbacks, function names, shell commands, or inline executable source* — turns inert runtime config into code execution.
3. *Dataset Manifest embeds a workflow engine* — duplicates StarLang orchestration and makes dataset state executable.
4. *Manifest worker/thread counts are authority* — bypasses #34/#35 capacity grants.
5. *Manifest capability declaration grants caller authority* — discovery/configuration is not authorization.
6. *Runtime silently patches incompatible semantic manifests* — incompatible meaning requires a new version/artifact.
7. *Raw Rabbit/CouchDB/Valkey topology and credentials become public capability metadata* — deployment topology remains private.
8. *Compile while starting components* — partial side effects make invalid topology non-atomic and hard to roll back.
9. *One generic manifest map for actors and datasets* — conflates executable component deployment with dataset/catalog governance.
10. *Legacy global hook/index is kept as a second authoritative route table after migration* — compatibility wrappers may delegate, but only one compiled plan may own topology.

* RED-First Targets

First RED is pure and deliberately avoids actors/network:

#+begin_example
semantic manifest: component email-enricher accepts EmailSeed
actor binding: component-id identity/email, semantic-digest sha256:A
dataset binding: route PersonDocument -> identity/email

compileRuntimePlan(...)
=> typed incompatible-route error
=> zero actor/thread/network construction callbacks
#+end_example

Untouched server must fail because no pure manifest linker/runtime-plan compiler exists.

Sibling REDs:

- actor binding references semantic digest A but resolved artifact is B -> reject before effects;
- deployment binding attempts to add undeclared capability -> reject widening;
- duplicate component IDs -> reject;
- unknown component dependency -> reject;
- lifecycle cycle -> reject through #37 graph validator;
- mailbox demand unbounded/invalid -> reject through #36 contract;
- thread/dispatcher demand exceeds grant -> reject through #34/#35 contract;
- two equivalent manifest input sets normalize to an equal deterministic RuntimePlan;
- manifest containing raw credential or arbitrary executable callback field -> reject.

* Unresolved Questions

- The exact stable wire name for the StarLang semantic artifact reference (=programManifestRef= versus =semanticManifestRef=) should align with the final StarLang manifest/lock format when #43 is implemented. The architecture requires an immutable digest-bound reference; naming does not block design.
- Existing =STAR-MANIFEST-001= calls for camelCase data fields while parts of the current v0.9 corpus use snake_case. Migration must remain explicit and versioned; this research does not rewrite historical document bytes.
- The current actor-manifest skill predates the StarLang semantic/runtime split and should be reconciled after the canonical design is accepted; it is operational guidance, not a competing contract.

* Footnotes and Glossary

- *Semantic manifest* :: Immutable compiler-produced StarLang description of an actor/domain server's typed behavior and declared capabilities.
- *Actor deployment binding* :: Data-only StarIntel record binding one semantic component artifact to concrete runtime composition, resource, lifecycle, and ingress policy.
- *Dataset manifest* :: Data-only description of one dataset's schema compatibility, storage, lineage, governance, and selected component/flow bindings.
- *RuntimePlan* :: Pure deterministic normalized topology produced before side effects and validated by existing lifecycle/capacity authorities.
- *Narrowing* :: A deployment restriction that reduces allowed behavior without adding capabilities/types/authority absent from the semantic contract.
