* Research Question

What StarLang syntax should make expert systems pleasant to author without exposing Common Lisp =EVAL=, native LISA macros, raw Prolog source, engine-specific handles, or ambiguous inference semantics?

The desired author experience should support:

- typed facts;
- reuse of existing StarIntel objects as fact-bearing values without an expert-only duplicate object model;
- named rules and goals;
- joins, existence, absence, comparisons, and deliberately named negation forms;
- checked derived conclusions with structured reasons;
- typed questions when information is missing;
- explicit =auto=, =lisa=, =swi-prolog=, or =n-prolog= backend policy;
- normalized explanation/proof requirements;
- optional named uncertainty algebra;
- actor-owned persistent expert sessions;
- complete compile-time lowering before runtime execution.

* Current Source Boundary

The live StarLang prototype uses a custom closed reader and first-class syntax/source-span objects. Untrusted =.star= input does not go through the Common Lisp reader. That is the correct foundation for expert-system sugar.

New expert forms should extend the closed parser and compiler phase model. They must not be implemented by reading LISA =defrule= forms, evaluating host Lisp, or concatenating user-controlled strings into Prolog goals.

The maintained LISA source remains valuable as semantic evidence because it demonstrates production-rule features such as salience, contexts, belief annotations, assertion/retraction/modification, agenda inspection, and forward-chaining execution. These concepts inform StarLang design; LISA syntax itself does not become the StarLang language contract.

LISA also provides a concrete object-backed fact path. Its =assert= macro detects a Common Lisp =standard-object= and sends that instance through =parse-and-insert-instance=; the public language layer also exposes =assert-instance=, =retract-instance=, and =mark-instance-as-changed=. This is primary-source evidence that the LISA backend can reason from object instances. It does not by itself prove that current StarIntel objects satisfy the desired StarLang identity, provenance, schema-version, mutation, and replay contracts; those remain part of the approval gate below.

* Design Principle: Describe Knowledge, Not Engine Instructions

The expert surface should answer:

1. what facts exist;
2. what conditions make a rule applicable;
3. what conclusion follows;
4. what information is missing;
5. which goal the expert wants to establish;
6. why a conclusion follows;
7. which uncertainty algebra combines evidence, if any;
8. which backend semantics are required.

It should not expose LISA network nodes, SWI modules/engine handles, N-Prolog process state, CLOS fact instances, native Prolog variables, sockets, process IDs, or implementation-specific memory structures.

* Typed Facts

Expert facts reuse StarLang schemas and may reuse existing StarIntel objects as fact-bearing values rather than creating a second expert-only type or object system.

#+begin_src lisp
(facts
  (transaction
    (id string :required)
    (amount decimal :required)
    (currency string :required)
    (country string :required)
    (customerConfirmed boolean :optional))

  (risk
    (transactionId string :required)
    (level riskLevel :required)))
#+end_src

Each fact type declares a role:

- =source= — projected from declared input data or supplied by an existing typed StarIntel object;
- =session= — mutable inside one expert session;
- =derived= — produced by inference and backed by justification;
- =questionAnswer= — generated from a typed question response.

This role model prevents a rule from rewriting canonical source data.

Schema reuse and object reuse are separate requirements. Reusing a StarLang schema avoids an expert-only type system. Reusing a StarIntel object additionally means the expert layer must not require the application to clone that object into an unrelated expert-only record merely to make it visible to inference.

A backend may require an internal representation change. For example, a Prolog adapter may need a relational projection. Such lowering is acceptable only when the StarLang runtime retains the stable source-object identity and the provenance/schema metadata needed to map conclusions and proofs back to the authoritative StarIntel object. Backend representation is an implementation detail; application-visible object duplication is not the language contract.

** LISA Object-Instance Evidence

The LISA language implementation retrieved on 2026-08-15 provides the reference capability for this requirement:

- =assert= branches when the supplied fact value is a Common Lisp =standard-object= and inserts the instance through =parse-and-insert-instance=;
- =assert-instance= inserts an existing instance directly;
- =retract-instance= retracts an instance;
- =mark-instance-as-changed= reports a changed CLOS instance/slot to the inference engine.

This demonstrates that object-backed facts are not hypothetical for the LISA backend. The StarLang research still has to establish exactly which StarIntel object families qualify, how schema compatibility is checked, how identity is represented in normalized IR, how changes are observed, and what replay/proof representation is portable.

** StarIntel Object Reuse Approval Gate

STAR-LANG-RESEARCH-023 remains =REVIEW= and MUST NOT be approved until the research demonstrates all of the following:

1. native StarLang schemas remain valid fact/type contracts;
2. at least one real existing StarIntel object family can enter an expert session without first being copied into a separate expert-only application object;
3. the runtime retains a stable mapping from every backend fact/projection to the authoritative StarIntel object identity;
4. relevant provenance, document/object ID, schema/version identity, relationship references, and verification/proof metadata remain available to inference or to normalized explanation/proof construction as required by the declared profile;
5. LISA is exercised as the reference object-backed backend using its existing instance path rather than a synthetic expert-only replacement object;
6. SWI-Prolog and N-Prolog research states explicitly whether they can satisfy the same semantic contract through identity-preserving relational projection, which metadata crosses the boundary, and which capabilities are backend-specific;
7. backend selection changes how inference executes, not which application object model the StarLang author is forced to use;
8. mutation and replay semantics are explicit: reasoning over an object must not create an untracked second mutable authority for canonical StarIntel state.

The exact future StarLang spelling for importing, binding, or projecting a StarIntel object is deliberately not fixed by this gate. That belongs to the design that follows approved research.

Conformance interpretation:

#+begin_example
FAIL: StarIntel Person -> copied expert-person object -> rules
PASS: StarIntel Person -> LISA object fact -> rules
PASS: StarIntel Person -> identity-preserving backend projection -> Prolog rules
#+end_example

The second =PASS= requires the projection to remain traceable to the same authoritative StarIntel object; merely copying fields into an anonymous tuple is insufficient when identity or provenance matters.

* Rule Form

#+begin_src lisp
(rule highValueForeignTransaction
  (:salience 80)
  (when
    (transaction
      (:bind ?tx)
      (id ?transactionId)
      (amount ?amount)
      (country ?country))
    (greaterThan ?amount 10000)
    (member ?country highRiskCountries))
  (then
    (conclude
      (risk
        (transactionId ?transactionId)
        (level high))
      (because highValueForeignTransaction))))
#+end_src

Semantics:

- rule names are stable package-local IDs;
- variables are lexical compiler bindings;
- fact patterns introduce typed bindings;
- conditions are declarative and effect-free;
- actions come from a closed expert action vocabulary;
- conclusions carry stable justification identity;
- salience is legal only under a profile that defines agenda ordering.

* Closed Rule Actions

Allowed initial actions:

- =conclude=;
- =assertSessionFact=;
- =retractSessionFact= when the package mutation profile permits it.

Question requests are generated through question declarations/triggers rather than arbitrary RHS host calls.

Disallowed by default:

- file I/O;
- HTTP;
- shell/process launch;
- database mutation;
- arbitrary actor send;
- arbitrary host function call;
- Common Lisp evaluation;
- arbitrary native-engine goal invocation.

External effects belong in ordinary StarLang actor/tool flows after inference emits a checked conclusion or event.

* Conditions

** Conjunction

#+begin_src lisp
(all
  (transaction (id ?id))
  (account (transactionId ?id) (status open)))
#+end_src

A plain sequence in =when= may lower to =all=.

** Disjunction

#+begin_src lisp
(any
  (countryEquals ?country "IR")
  (countryEquals ?country "KP"))
#+end_src

** Existence

#+begin_src lisp
(exists
  (priorAlert (customerId ?customerId)))
#+end_src

** Working-memory absence

#+begin_src lisp
(absent
  (customerConfirmation
    (transactionId ?transactionId)))
#+end_src

=absent= means no matching fact exists in the declared production/expert working-memory state at the current logical sequence. It is not automatically Prolog negation as failure.

** Negation as failure

#+begin_src lisp
(notProvable
  (knownSafeMerchant ?merchantId))
#+end_src

This is legal only under profiles that define the relevant closed-world/query semantics.

** Inequality

#+begin_src lisp
(different ?left ?right)
#+end_src

Inequality, absence, negation as failure, and explicit contradiction are separate semantic constructs. A bare overloaded =not= should be rejected in v1.

* Variable Model

Source variables may use =?name= for readability, but they are compiler bindings rather than native Prolog variables.

Rules:

1. variables must be introduced by a pattern, parameter, or explicit binder before use;
2. each binding has one static type;
3. bindings cannot escape a rule except through checked result fields;
4. nested shadowing is rejected in v1;
5. normalized IR assigns stable compiler binding IDs;
6. backend lowering privately maps binding IDs to LISA bindings or Prolog variables.

* Joins

Shared variables create relational joins naturally.

#+begin_src lisp
(rule suspiciousOwnerChain
  (when
    (organization (id ?orgId))
    (ownership
      (sourceId ?orgId)
      (targetId ?ownerId))
    (person
      (id ?ownerId)
      (riskLevel high)))
  (then
    (conclude
      (organizationRisk
        (organizationId ?orgId)
        (level high))
      (because suspiciousOwnerChain))))
#+end_src

The LISA lowering may derive join keys/indexes for RETE while SWI/N-Prolog lower to relational goals. Execution strategies differ, but the declared relation can remain portable when observable semantics match.

* Rule Metadata

Initial candidates:

#+begin_example
:salience
:group
:enabled
:explain
:tags
#+end_example

=:salience= has production-rule meaning and must not silently change Prolog goal ordering.

=:group= may map to deterministic production contexts/focus only after a StarLang semantic profile defines group scheduling.

=:enabled= is compile/deployment configuration by default. Runtime rule toggling requires a journaled session operation.

* Conclusions

=conclude= produces derived state rather than mutating source facts.

#+begin_src lisp
(conclude
  (risk
    (transactionId ?transactionId)
    (level high))
  (because highValueForeignTransaction)
  (:evidence ?tx))
#+end_src

Lowering records conclusion schema, normalized field expressions, rule ID, support binding IDs, explanation policy, uncertainty contribution if any, and stable conclusion identity.

A conclusion can be revoked when support disappears only under a profile that defines truth-maintained or incremental derivation semantics.

* Structured Reasons

Free-form text alone is insufficient provenance.

#+begin_src lisp
(because highValueForeignTransaction
  (:supports ?tx)
  (:code risk.highValueForeign)
  (:message "High-value transaction in a configured risk geography."))
#+end_src

Portable identity uses rule/code/support IDs. Human message text is presentation metadata and may change without altering logical identity.

* Goals

#+begin_src lisp
(goals
  (goal classifyRisk
    (risk
      (transactionId targetTransaction)
      (level ?level))
    (:answers many
     :required true
     :explain required)))
#+end_src

Goal metadata may define one/many answers, required/advisory status, answer schema, completion policy, proof requirement, and per-goal budget.

For Prolog a goal maps naturally to a named query. For LISA it can map to a target conclusion pattern plus run-until/quiescence policy. Portability requires normalized goal semantics rather than assuming those operational models are identical.

* Interactive Questions

Classic expert systems need a safe way to request missing information.

#+begin_src lisp
(questions
  (ask customerConfirmed
    (:returns boolean
     :scope session
     :cache once)
    (needs
      (transaction
        (id ?transactionId)
        (customerConfirmed missing)))
    (prompt
      "Did the customer confirm transaction {transactionId}?")))
#+end_src

Critical rule: an inference backend does not directly talk to a human, LLM, UI, or network service.

=ask= compiles into a typed =expert-question-request=. ExpertSessionActor publishes it through a configured question port. A UI, CLI, agent, operator, or test harness returns a checked =expert-question-answer=. The answer becomes a journaled session fact.

* Question IR

#+begin_src lisp
(defstruct expert-question-ir
  id
  trigger-condition
  parameter-bindings
  answer-type
  answer-schema
  prompt-template-id
  cache-policy
  maximum-attempts
  redaction-policy
  timeout-policy)
#+end_src

Prompt text is presentation data. Logical identity uses question ID, typed parameters, answer schema, and response value/status.

* Question Loop Prevention

Question request identity should include:

#+begin_example
(expert-session-id question-id normalized-parameters fact-generation)
#+end_example

Policies:

- =once= — one request for a parameter tuple per session;
- =perGeneration= — re-ask only after relevant fact generation changes;
- =untilAnswered= — bounded malformed/declined retries;
- =neverCache= — allowed only with explicit question budget.

The journal records requested, delivered, answered, declined, timed-out, cancelled, and superseded states.

* Expert Session State Machine

#+begin_example
CREATED
  -> MATERIALIZED
  -> READY
  -> RUNNING
       |-> WAITING-FOR-ANSWER -> RUNNING
       |-> QUIESCENT
       |-> GOAL-SATISFIED
       |-> BUDGET-EXHAUSTED
       |-> FAILED
       `-> CANCELLED
  -> CLOSED
#+end_example

A session is actor-owned. The backend cannot invent state transitions outside this protocol.

* Why and How

Convenience forms can query the normalized derivation graph instead of native engine tracers.

#+begin_src lisp
(explain
  (why
    (risk
      (transactionId "tx-123")
      (level high))))
#+end_src

#+begin_src lisp
(explain
  (how
    (goal classifyRisk)))
#+end_src

=why= returns supports of an existing conclusion. =how= returns the derivation path or bounded unsatisfied-goal diagnostics when the backend/package can produce them deterministically.

* Partial Matches and Missing Facts

Production engines can often report partially satisfied rules. This is useful for question planning but should remain a semantic capability rather than a LISA-private API.

Optional capability:

#+begin_example
expert.partial-match/1
#+end_example

Normalized result:

#+begin_src lisp
(defstruct expert-partial-match
  rule-id
  satisfied-condition-ids
  missing-condition-ids
  bound-parameters
  blockers)
#+end_src

Question declarations using explicit =needs= remain functional even when partial-match introspection is unavailable.

* Uncertainty

Uncertainty must be named at the expert-system level.

#+begin_src lisp
(expert-system diagnosis
  (:uncertainty dempsterShaferV1)
  ...)
#+end_src

Rule evidence should use semantic operations rather than blindly copying LISA's native =:belief= spelling:

#+begin_src lisp
(rule evidenceForHypothesis
  (:support 0.7)
  ...)

(rule evidenceAgainstHypothesis
  (:oppose 0.6)
  ...)
#+end_src

Initial algebras may include:

#+begin_example
boolean
certaintyFactorV1
dempsterShaferV1
#+end_example

Only =boolean= should be mandatory for all expert backends in v1. Other algebras require exact combination semantics, numeric precision rules, retraction behavior, proof representation, and conformance fixtures for every backend claiming support.

* Contradiction

Do not use last-write-wins for contradictory evidence.

A package declares how contradictions are treated:

- rejected as inconsistent input;
- represented as separate propositions;
- combined through uncertainty algebra;
- handled by explicit contradiction rules.

Derived conclusions should preserve contradiction state when applicable.

* Defaults and Defeasible Logic

Do not add a bare =default= construct in v1. Expert-system traditions assign incompatible meanings to defaults.

Potential future constructs need dedicated semantics such as =assumeIfUnknown= or explicitly prioritized =defeasibleRule=. Schema default values are data-shaping behavior, not inference defaults.

Until a non-monotonic reasoning research pass exists, defeasible/default logic stays outside the portable expert surface.

* Time

Rules do not read wall-clock time directly. Time is explicit input data or an injected logical-time fact/parameter.

#+begin_src lisp
(rule staleObservation
  (when
    (observation
      (id ?id)
      (observedAt ?observedAt))
    (logicalNow ?now)
    (olderThan ?observedAt ?now "P30D"))
  (then
    (conclude
      (stale (observationId ?id))
      (because staleObservation))))
#+end_src

Replay passes the same logical time unless a migration run intentionally changes the input plan.

* Aggregates

Aggregates are useful but should not enter the portable profile until duplicate, grouping, ordering, missing/null, numeric, and update semantics are frozen.

Future shape:

#+begin_src lisp
(aggregate count ?alert
  (where
    (alert (customerId ?customerId)))
  (as ?alertCount))
#+end_src

This is intentionally deferred from the minimal expert portability subset.

* LISA Lowering

A LISA package compiler may map:

- fact types to safe adapter-owned fact/template representations or, where the StarIntel object-reuse gate is satisfied, to LISA's existing object-instance path;
- existing StarIntel source objects without requiring a parallel expert-only application object;
- fact patterns to LISA conditional elements;
- shared compiler bindings to native rule bindings;
- =absent= to negative conditional elements where semantics match;
- =exists= to existential elements where semantics match;
- salience to LISA salience;
- group/context only when StarLang defines compatible scheduling semantics;
- =conclude= to adapter-owned derived-fact/justification operations;
- uncertainty to LISA belief hooks only for a conformance-proven algebra.

The adapter never splices arbitrary user forms into native =defrule= bodies. Object-backed conformance must additionally prove the mapping from a LISA instance/fact back to the authoritative StarIntel object identity and replay/provenance record.

* SWI-Prolog Lowering

A SWI package compiler maps compatible relational experts into named predicates/wrapper goals.

Potential mappings:

- fact types to typed module-scoped predicates or immutable snapshot predicates;
- StarIntel object-backed source facts to compiler-owned relational projections carrying stable source-object identity/provenance references;
- relational rules to generated clauses;
- goals to declared named query IDs;
- =notProvable= to negation as failure only under the declared profile;
- recursive relations to tabled predicates when required;
- questions to the external ExpertSessionActor question port;
- explanations to proof-carrying generated predicates or instrumented wrappers.

A package depending on production agenda order, salience, or retraction-driven activation must not be translated to plain Prolog clauses and called equivalent. A package depending on StarIntel object identity/provenance must likewise not be lowered to anonymous tuples that cannot be traced to their source objects.

* N-Prolog Lowering

Initial N-Prolog support targets =star.logic.portable-prolog/1= plus explicit N-Prolog-specific packages.

Restrictions:

- no tabled-query requirement;
- no SWI-specific directives/dictionaries/attributed-variable assumptions;
- no assumption that CLP(FD) implementation details match SWI;
- one query per worker initially;
- named wrappers only;
- bounded answer materialization;
- deterministic JSON/string-mode bootstrap;
- StarIntel object reuse requires the same stable identity/provenance projection contract as other Prolog lowering; unsupported metadata/capabilities must fail compatibility rather than disappear silently.

* Portable Expert Profiles

Avoid one misleading portable boolean.

** =star.expert.relational/1=

Candidate SWI/N-Prolog profile:

- immutable/source facts;
- pure fact patterns;
- conjunction/disjunction;
- equality/inequality/comparisons;
- bounded pure recursion not requiring backend-specific tabling;
- named goals;
- boolean conclusions;
- proof wrappers where implemented.

** =star.expert.production/1=

LISA-oriented profile:

- working memory;
- ordered fact deltas;
- agenda activations;
- salience;
- negative/existential conditions;
- assertion/retraction;
- quiescence;
- optional truth maintenance;
- rule-firing traces.

** =star.expert.consultation/1=

Higher-level interactive profile:

- typed questions;
- goals;
- conclusions;
- explanations;
- bounded interaction;
- explicit compatible relational or production implementation.

* Expert Lints

Non-fatal lints should cover:

- unreachable rule;
- no producer for required derived fact;
- conclusion never consumed/exported;
- question answer never used;
- impossible question trigger;
- recursive goals without a termination-capable profile;
- duplicate condition;
- low-selectivity Cartesian join;
- conclusion cycle;
- potential unbounded question loop;
- proof-required rule without proof path;
- uncertainty value outside algebra domain;
- backend-specific feature defeating declared portability;
- StarIntel object projection that drops provenance or stable source identity needed by the declared profile.

Heuristic performance warnings must never be mislabeled as proven semantic errors.

* Testing Strategy

** Parser

- all expert forms go through the closed reader;
- malformed syntax reports exact spans;
- unknown forms fail closed;
- no host reader/evaluation path exists.

** Binding/type analysis

- introduction/use rules;
- shared-variable joins;
- invalid shadowing;
- incompatible comparison types;
- action field typing.

** Semantics

- =absent= and =notProvable= stay distinct;
- source facts cannot be mutated;
- salience fails outside production profile;
- uncertainty algebra is explicit;
- question effects are typed/bounded;
- a real StarIntel object can be consumed through the LISA instance path without application-level expert-object duplication;
- identity/provenance required by the profile survives backend projection and maps conclusions/proofs back to the same authoritative object;
- lossy or anonymous projections fail compatibility when the package requires identity/provenance.

** Lowering

- fake backend receives stable normalized expert IR;
- LISA lowering contains no raw source splice;
- LISA object-backed fixture exercises =assert-instance= or the equivalent instance insertion path;
- SWI/N-Prolog call only named wrappers;
- SWI/N-Prolog object projections retain stable source-object identity/provenance references when the package requires them;
- backend artifacts are digest-stable for identical input.

** Runtime

- question request/answer/resume;
- conclusion/revocation;
- crash/restart on same pinned backend;
- budget exhaustion;
- cancellation;
- recorded replay;
- verify replay;
- explicit cross-backend migration.

* Canonical Expert Fixtures

Create small experts for:

1. animal classification — simple relational rules;
2. transaction risk — joins, thresholds, explanation;
3. equipment troubleshooting — typed questions/missing facts;
4. MYCIN-inspired synthetic uncertainty fixture without copying external prose/data;

6. streaming alerts — LISA production profile;

* Documentation Order

Teach users:

1. define facts;
2. write one boolean rule;
3. run with =backend auto=;
4. inspect conclusion/explanation;
5. add a goal;
6. add a typed question;
7. inspect backend selection;
8. pin LISA/SWI/N-Prolog;
9. understand semantic portability profiles;
10. add uncertainty only after boolean experts are clear.

Do not lead tutorials with native LISA or Prolog syntax. StarLang users learn the semantic surface first.

* Rejected Sugar

** Raw =(prolog "...")=

Rejected because it defeats static checking, named-query restrictions, source provenance, and replay identity.

** Raw LISA =(defrule ...)=

Rejected because it couples StarLang source to host Common Lisp/LISA internals and creates an execution escape hatch.

** Generic =(call predicate args...)=

Rejected as an inference primitive because it can become arbitrary executable goal invocation. Use declared named pure predicates/queries.

** Bare =not=

Rejected because absence, negation as failure, inequality, and contradiction differ semantically.

** Arbitrary rule RHS actor sends

Rejected. Inference emits conclusions/events; effects stay behind typed actor/tool boundaries.

** Implicit numeric uncertainty

Rejected because a weight has no cross-engine meaning without a named algebra.

** Mandatory expert-only object copies

Rejected as the StarLang semantic model. A backend may own an internal identity-preserving projection, but StarIntel applications must not be required to maintain a second expert-only copy of the same authoritative object merely to reason about it.

* Acceptance Criteria

1. Expert syntax is parsed only by the closed StarLang reader.
2. =expert-system= lowers completely into checked IR before runtime execution.
3. Normalized expert IR contains no raw Common Lisp/Prolog source, LISA objects, engine handles, or sockets.
4. Facts reuse StarLang schema/type contracts rather than defining an expert-only type system.
5. Research demonstrates at least one real existing StarIntel object family can participate in expert reasoning without a required expert-only application-object copy.
6. LISA proves the reference object-backed path using its existing instance support, with stable mapping back to the authoritative StarIntel object.
7. Backend projections preserve the stable source-object identity/provenance required by the declared profile, or compatibility fails explicitly.
8. Rule variables are lexical, typed, and source-traceable.
9. =absent=, =notProvable=, inequality, and contradiction remain distinct.
10. Derived conclusions are separate from source facts.
11. Questions are typed effect requests owned by ExpertSessionActor.
12. Explanation requirements normalize to the shared derivation graph.
13. Uncertainty names an explicit algebra; boolean reasoning works without uncertainty support.
14. Salience/group semantics cannot run under a backend/profile that cannot honor them.
15. Portability is declared by named semantic profile and proven by fixtures.
16. Backend pinning is optional in source but immutable after plan materialization.
17. Compiler diagnostics retain source spans/origin chains.
18. A complete expert is testable with a fake backend and no inference engine installed.

* Result

StarLang should gain a compact expert-system layer rather than an embedded native rule language. The layer declares typed facts, rules, goals, questions, conclusions, proofs, and optional uncertainty. It reuses StarLang schema contracts and must be able to reason over existing StarIntel objects without forcing a parallel expert-only application object model. It lowers through the closed compiler into engine-neutral expert/logic IR. LISA, SWI-Prolog, and N-Prolog are then implementation backends selected only when their advertised semantic profiles satisfy the package.

LISA's existing object-instance support makes direct object-backed reasoning a concrete reference capability. Prolog backends may require relational projection, but any claimed StarIntel-object support must retain the stable identity/provenance contract required by the package. Backend choice determines how inference executes; it must not silently redefine the application's object model.

The most valuable syntactic sugar is the sugar that makes correct semantics easy and ambiguous semantics hard: typed bindings, explicit negation forms, separated source/session/derived state, bounded question effects, structured explanations, capability-checked backend selection, and traceable reuse of authoritative StarIntel objects.

* Footnotes and Glossary

- *Expert system* — Declarative knowledge package containing schemas/facts, inference rules or queries, goals, and explanation behavior, optionally including interactive questions and uncertainty.
- *Syntactic sugar* — Source convenience syntax that expands into a smaller checked core and has no independent runtime semantics.
- *Conclusion* — Derived expert state with justification, distinct from canonical source data.
- *Question port* — Typed effect boundary through which an expert session requests missing information from a UI, agent, test harness, or operator.
- *Salience* — Production-rule activation priority; it has no automatic portable meaning in ordinary Prolog resolution.
- *Negation as failure* — Query semantics where inability to prove a goal is interpreted according to a declared closed-world profile; distinct from absence in working memory.
- *Uncertainty algebra* — Versioned formal rule for combining positive/negative evidence, such as certainty-factor or Dempster-Shafer semantics.
- *Partial match* — Information about a production rule whose conditions are only partly satisfied.
- *Backend lowering* — Trusted compiler step converting backend-neutral expert IR into an engine-specific artifact without exposing native syntax in StarLang source.
- *StarIntel object reuse* — Expert reasoning over an existing authoritative StarIntel object, either directly or through an identity-preserving backend projection, without requiring a second expert-only application object.
- *Identity-preserving projection* — Backend representation that carries enough stable source-object identity and provenance metadata to map facts, conclusions, and proofs back to the authoritative StarIntel object.
