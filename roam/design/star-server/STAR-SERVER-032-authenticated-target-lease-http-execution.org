* Decision

Do not redesign the implemented lease protocol or Valkey backend. Complete issue #32 by inserting one authenticated application-service boundary above the existing lease-store protocol, projecting that same result algebra through HTTP and embedded Common Lisp calls, and carrying server-created immutable lease authority into target execution and fenced side-effect acceptance.

#+begin_example
HTTP adapter                 embedded caller
     \                         /
      -> service-call context -> target-lease service
                                  -> existing lease-store protocol
                                  -> existing Valkey adapter

 target submission -> locking policy -> target-lease service
                   -> immutable execution authority
                   -> local actor / Rabbit delivery
                   -> fenced effect acceptance
#+end_example

* Ownership

** Existing lease-store stack

Owns atomic acquire, renew, release, revoke, get/list, fencing-token allocation, receipt/state serialization, backend deadlines/outcomes, and Valkey-specific implementation. HTTP and target code MUST NOT duplicate these semantics.

** Target-lease application service

Owns authorization and disclosure policy, canonical target binding, idempotency request binding, deadline propagation, conversion of store outcomes into service outcomes, and creation/validation of immutable execution authority.

** HTTP adapter

Owns bounded syntax/header parsing and service-result projection only. It does not call Valkey directly and does not make an independent lease decision.

** Target execution

Owns enforcement that a required-lock target cannot be dispatched without current authority. Local and Rabbit paths consume the same authority shape.

** Fenced effect boundary

Owns the final acceptance check that prevents stale generations from making authoritative persistence/publication/settlement effects.

* Service Contract

Every call receives a closed context containing at least principal identity/type, granted capabilities/scopes, correlation identity, absolute deadline, and request/idempotency identity where applicable.

Missing context is denial. In-process origin, package identity, localhost, or actor membership grants no implicit authority.

Service operations cover acquire, renew, release, revoke, inspect, and bounded list. Each operation checks authorization before store invocation when possible.

Service outcomes must distinguish at least:

- acquired / renewed / released / found / listed;
- conflict/held;
- stale fence/precondition;
- hidden/not-found;
- unauthorized/forbidden;
- invalid request;
- idempotency conflict;
- overloaded/rate-limited;
- backend unavailable;
- deadline exceeded with known no-commit;
- outcome unknown where replay of the same idempotency key is required.

* HTTP Projection

Use the current server API-version/capability work as the path authority during implementation. Do not create a parallel version convention solely for leases.

The adapter maps typed service outcomes into stable HTTP status/problem documents. It must preserve non-disclosure: another tenant/owner's hidden lease is indistinguishable from absence where policy requires it.

No problem document may contain Valkey keys/scripts/errors, credentials, raw target bodies, stack traces, or private owner metadata.

* Immutable Execution Authority

Caller-controlled target JSON never becomes lease authority.

For a target whose policy requires locking, the service constructs an immutable authority object from validated current lease state. Conceptually it carries:

#+begin_example
leaseId
canonicalTargetKey
fencingToken
ownerPrincipal
executionId
expiresAt / authority horizon
correlationId
#+end_example

The exact Common Lisp representation is implementation-owned. Actor and Rabbit envelopes carry the server-created value or its typed wire projection. Mutation by a downstream actor does not increase authority.

* Fenced Side-Effect Acceptance

Dispatch-time validation alone is insufficient. A stale worker can continue computing after expiry/reacquisition.

At least one authoritative side-effect seam must compare the submitted execution generation against current/highest accepted fencing state before committing the effect. The first implementation slice after dispatch integration should choose the narrowest real persistence/publication seam already used by target results.

Required proof:

#+begin_example
worker A owns fence N and stalls
worker B reacquires fence N+1
B effect is accepted
A later submits effect with N
A effect is rejected as stale and cannot become authoritative
#+end_example

Rabbit acknowledgement must not turn stale rejected output into a successful authoritative result. Settlement behavior follows the typed stale-work policy and bounded retry/dead-letter rules.

* #33 Boundary

Issue #32 supplies the service/authority/fencing seams. Issue #33 owns the exhaustive expiry, crash, restart, failover, timeout-after-commit, renew/release/reacquire race, and multi-process matrix.

Do not block the pure #32 service contract on the entire chaos harness, but do not mark the lease stack complete until #33 proves those failure modes.

* StarLang Boundary

No new StarLang syntax is required. A StarLang actor/domain server may declare that execution requires lease authority and may receive the typed authority through its runtime contract. It cannot mint tokens, call Valkey, or bypass host authorization/fencing.

* Dependency-Ordered Proposed Slices

All slices remain =AWAITING_OPERATOR_IMPLEMENTATION_APPROVAL=.

1. *Pure target-lease service context/result contract* over fake existing lease-store protocol.
2. *Authorization + idempotency + absolute deadline behavior* with zero HTTP dependency.
3. *HTTP adapter projection* using the current versioned API/capability boundary.
4. *Required-lock target dispatch authority* with server-created immutable envelope.
5. *One real fenced side-effect seam* proving N rejected after N+1.
6. *Local/Rabbit authority equivalence and settlement fixtures*.
7. *#33 integration handoff* for the complete race/recovery matrix.

* Mandatory RED-First Targets

** Slice 1

A fake lease store records every invocation. An unauthorized service context attempts acquire. Untouched current server must fail because no target-lease application service exists. GREEN returns typed authorization denial and store invocation count remains zero.

A sibling fixture requires an authorized embedded call to produce the same typed service result consumed by the future HTTP adapter.

** Slice 3

Given fixed service outcomes, HTTP projection fixtures prove conflict, stale, hidden/not-found, unauthorized, overload, unavailable, known timeout, and unknown mutation outcome remain distinct and redact backend/private data.

** Slice 4

A required-lock target without server-created authority must fail before local actor send or Rabbit publish. A caller-supplied fake fencing token must not satisfy the check.

** Slice 5

Generation N stalls; N+1 becomes current and commits; later N effect is rejected with zero authoritative mutation.

* Adversarial Review

Rejected:

- route handlers talking to Valkey scripts;
- a second lease result algebra;
- package/local-process trust as authorization;
- caller-provided lease fields as execution authority;
- fence check only at dispatch;
- actor liveness as lease-current proof;
- embedded callers bypassing authorization;
- separate local and Rabbit authority semantics;
- generic retry of unknown mutation outcome with a new idempotency key;
- collapsing hidden lease into a revealing conflict response;
- moving lease authority into StarLang or Prolog;
- claiming #32 completion before #33 validates the full failure matrix.

* Acceptance Criteria

- existing lease protocol/Valkey implementation remains the storage authority;
- HTTP and embedded calls share one authenticated service contract;
- unauthorized calls cannot touch the store;
- idempotency/deadline/unknown-outcome semantics are explicit and bounded;
- required-lock target cannot dispatch without current server-created authority;
- local and Rabbit execution carry equivalent immutable authority;
- stale generation cannot make an authoritative side effect after a newer fence exists;
- responses do not disclose backend/private authority data;
- #33 can exercise the resulting seams without bypassing them;
- no new StarLang syntax or second lease control plane is introduced.

* Footnotes and Glossary

[fn:fencing] Fencing rejects stale generations at the receiver of an authoritative side effect, even if the stale worker remains alive.
[fn:application-service] A thin application service applies caller authority and orchestration policy above the already implemented storage protocol.
[fn:unknown-outcome] A mutation outcome is unknown when the caller cannot prove whether the backend committed; safe recovery replays the same idempotency identity.
