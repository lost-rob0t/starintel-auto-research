* Research Question

Can =lost-rob0t/star-kb= serve as one reusable source of facts and rules for multiple execution styles rather than being coupled to =prolog-query-server=, specifically allowing direct Prolog actors and StarLang logic actors to reuse the same rule knowledge while preserving a strong trust boundary for logic that requires more power than PQS's current safe subset?

This is a research-only follow-up to [[id:star-kb-research-003-dialect-enrichment-corpus-inference-evidence][STAR-KB-RESEARCH-003]]. It records the operator's portability and sandbox/trust-label requirements. It does not freeze the final package schema, source grammar, compiler architecture, sandbox implementation, label spelling, import syntax, or actor API.

* Operator Requirements

- =star-kb= is the authority for reusable logical packages; PQS is one consumer/runtime, not the sole semantic owner.
- The same reviewed rules should be reusable by PQS-backed actors, direct/native Prolog actors, and StarLang logic actors where their declared semantic profile supports them.
- Logic that cannot be admitted to the safe shared-service subset should be visibly classified rather than silently accepted as ordinary safe logic.
- A sandbox/isolation path is preferred for approved logic that requires native or otherwise higher-risk Prolog capabilities.

                     star-kb package
                           |
             +-------------+-------------+
             |             |             |
             v             v             v
           PQS         native Prolog   StarLang logic
      safe interpreter     actor           actor
             |             |               |

* Verified Existing Runtime Evidence

** StarLang

Current =star-logic-protocol= already defines backend descriptors with semantic profiles, capabilities, isolation classes, hard limits, cooperative limits, build identity, and version. It defines =open-logic-session= with =package-id= and =package-digest= and generic fact-delta, operation, result, cancellation, status, and health boundaries.

Current =star-logic-ir= separates immutable logical package identity from backend materialization identity. It records =package-id=, =package-version=, =package-digest=, =mapping-id=, and =mapping-digest= and carries a semantic profile, backend policy, required capabilities, hard limits, required isolation, bindings, proof/answer policy, and budget. This is direct evidence that safety/isolation requirements can be represented independently from the package identity.

The current =star-logic-adapter-swi= provides a trusted process boundary, exact executable/build identity, authenticated MQI framing, a repository-owned bootstrap, process-isolated sessions, health, and orderly reaping. It deliberately does not expose arbitrary caller-controlled =consult/1=, raw goals, modules, files, or predicate indicators. Portable query/fact operations remain incomplete.

** prolog-query-server

PQS persists a restricted JSON AST, validates stored facts/rules, executes them through a bounded meta-interpreter, and does not expose arbitrary Prolog =call/1=. Its safe builtin registry is intentionally small: unification/disequality, bounded numeric calculation/comparison, and shape/type tests. This is already a strong safe-by-construction execution tier.

The evidence therefore does not support weakening the existing shared PQS interpreter merely to gain native Prolog power. A stronger capability should be a separate execution class with a separate isolation boundary.

* Research Finding: Safety and Portability Are Separate Axes

The operator's proposed "unsafe" label is useful, but one label should not collapse two different questions:

#+begin_src text
PORTABILITY                         EXECUTION TRUST
-----------                         ---------------
portable/core                       safe-by-construction
backend extension                   sandbox-required / privileged
native-only                         unsupported / prohibited in a given route
#+end_src

A rule may be backend-specific but harmless, such as a backend-specific tabling feature. A different rule may be syntactically common Prolog but dangerous in a shared service, such as dynamic code loading, file I/O, network access, shell execution, foreign calls, or unrestricted meta-calls.

Therefore later design should preserve two independent declarations: what semantic subset the package needs, and what execution isolation/trust class that subset requires. Exact field names remain design work.

* Research Finding: Fail Closed, Do Not Trust Self-Declared Safety

A package author may declare intent, but the runtime/compiler must verify whether a package actually fits the claimed safe subset. An arbitrary package must not become trusted merely because metadata says =safe=.

The research-supported trust behavior is:

- a package proven to use only the portable safe subset may execute through the normal PQS/shared-safe path;
- a package using an approved higher-risk capability is marked as requiring isolation and may execute only through an eligible sandboxed backend;
- a package using an unsupported or prohibited capability is rejected for that execution route;
- unclassified constructs fail closed rather than being treated as safe by default.

This is especially important for =consult/1= and related loading behavior: run-time input must never become arbitrary executable source in the trusted PQS process.

* Research Finding: Sandbox the Native-Power Path, Not the Canonical Knowledge

PQS's current restricted interpreter is already a logical sandbox in the sense that stored knowledge cannot reach arbitrary native Prolog operations. If later actors need approved native Prolog extensions, the research-supported direction is an external worker/process sandbox rather than consulting such rules directly into the shared PQS process.

A useful isolation boundary should be able to enforce, at minimum, no ambient credentials, no network unless explicitly granted, a read-only or narrowly scoped filesystem, CPU/time/memory/process limits, deterministic worker teardown/reaping, explicit executable/build identity, and capability-scoped access to any external effect. Exact Linux/container technology is deliberately left to design.

A sandbox does not make arbitrary logic trustworthy. It reduces blast radius. Static validation, package provenance, digest pinning, capability admission, and runtime limits still matter.

* Answers to the Previously Open Questions

** 1. Smallest useful semantic profile shared by PQS and direct SWI-Prolog

*Answer:* the smallest useful common profile is a *pure, bounded Horn-style rule subset* with ground facts; variables in rule/query terms; conjunction; unification and disequality; structured terms/lists; deterministic numeric calculation and comparisons; and bounded recursion/inference. For weighted/salient rules, the profile must also have a deterministic way to combine numeric evidence. The current PQS arithmetic builtins already cover scalar arithmetic/comparisons; whether summation is represented by recursive rules, a safe aggregate primitive, or materialized evidence remains design work.

The portable core should exclude arbitrary meta-call, dynamic source loading, I/O, shell/network access, foreign predicates, uncontrolled global mutation, and engine-specific control effects. Those features are not required for the weighted-salience dialect baseline.

** 2. Which constructs are portable core versus extensions?

*Answer:* classify by semantics, not by file extension or engine name.

Portable/core candidates are declarative facts and rules, ordinary terms, conjunction, bounded recursion, unification/disequality, deterministic safe arithmetic/comparison, and named query operations whose answer semantics are defined independently of one engine.

Backend extensions include features whose semantics are legitimate but not uniformly available, such as engine-specific tabling, constraint systems, indexing hints, specialized aggregates, or backend-native proof facilities. These require capability/profile negotiation and parity tests.

Sandbox-required/native-power constructs include dynamic consult/load, unrestricted meta-call, filesystem or network I/O, process/shell execution, foreign/native calls, mutable global code/state, and similar effects. A backend may refuse them entirely even when another backend permits them in a sandbox.

** 3. Mapping one star-kb package to StarLang package/mapping identity

*Answer:* the existing StarLang split is already appropriate. The =package-id/package-version/package-digest= should identify the canonical reviewed logical package and its semantics. The =mapping-id/mapping-digest= should identify the backend-specific materialization/translation used to load that package into PQS, SWI, or another backend. Backend build identity and required isolation are separate runtime evidence.

Therefore two actors can prove they used the *same rules* even if one used a PQS mapping and another used an SWI mapping. A changed backend translator changes the mapping digest without pretending that the canonical package changed.

** 4. Conformance fixture format for semantic parity

*Answer:* use backend-neutral competency fixtures tied to the package digest. Each fixture should identify the named operation/query, input bindings/fact delta, expected normalized answer set or multiset, expected success/failure/abstention behavior, and proof invariants when proofs are part of the profile. Ordering should be ignored unless ordering is explicitly part of the semantic contract.

Negative fixtures are equally important: unsupported capability, unsafe construct, malformed delta, resource exhaustion, and attempted package mutation should fail consistently. Backend-specific proof formatting may differ; parity should compare normalized semantic facts/proof claims rather than byte-identical trace text.

** 5. Trust boundary for direct Prolog actors

*Answer:* direct actors should never =consult/1= arbitrary run-time/user input. They should load only digest-pinned, validated =star-kb= package materializations through a trusted loader. Safe packages may run in the normal isolated logic worker. Packages requiring native-power capabilities must require a sandbox/isolation class and an explicit capability grant.

The sandbox path should fail closed when its required controls are unavailable. A package that needs prohibited capabilities should not run merely because the actor is local.

** 6. Which facts may be supplied as per-actor/session deltas?

*Answer:* actor/session deltas may contain ephemeral *data*, not new executable semantics. Good candidates are ground observations, actor-private facts, document features, model outputs, weights learned for that run, query context, and temporary entity relationships whose schema/predicate vocabulary is declared by the package.

A delta must not replace canonical rules, define new predicates/code, override reserved predicates, change package metadata, or silently persist into the reusable package. The package digest remains unchanged; the session/run should instead record a separate input/evidence digest or provenance identity. Durable reviewed rule/fact changes require a new canonical package version/release.

** 7. When should an actor use local execution versus PQS?

*Answer:* prefer PQS when centralized release selection, shared durable knowledge, consistent cross-actor state, server-side authorization, audit/proof provenance, or one authoritative runtime release is valuable. Prefer local/direct execution when latency, high per-actor throughput, offline operation, actor-private ephemeral evidence, or an approved backend-specific capability materially benefits the workload.

Higher-risk native Prolog logic should not be a reason to weaken the shared PQS process. It should use a sandboxed native worker/local backend or a future explicitly sandboxed PQS worker class. Backend choice must preserve the same package semantics and provenance.

** 8. Should LISA and N-Prolog be initial parity targets?

*Answer:* no. The first portability proof should target *PQS and native SWI-Prolog*, because both have concrete current runtime evidence and the SWI adapter foundation already exists. LISA and N-Prolog should remain later compatibility targets behind the same semantic-profile/capability model. The portable package/profile should avoid assumptions that unnecessarily block them later, but initial implementation should not require three or four engines to pass before the first useful actor exists.

* Implications for Weighted/Salient Dialect Rules

The weighted-salience findings in STAR-KB-RESEARCH-003 remain unchanged. The portable package should own reusable associations, salience semantics, reliability/exposure rules, redundancy handling, and named logical operations. Actor/session observations remain data inputs.

The safe portable subset is sufficient for the intended first dialect baseline: it does not need filesystem access, shell execution, arbitrary dynamic consult, foreign code, or network side effects. This makes dialect a good first parity case between PQS and native SWI execution.

* Remaining Empirical/Design Questions

The conceptual questions above are answered. Remaining work is now design or measurement:

- define the exact semantic-profile and safety/isolation vocabulary and how it is encoded without conflating portability with trust;
- decide the concrete sandbox implementation and prove its filesystem/network/credential/resource boundaries;
- decide whether weighted evidence summation needs a new safe aggregate primitive or is expressed within the portable rule subset;
- build PQS-versus-SWI parity fixtures and measure answer/proof equivalence, latency, startup cost, and failure semantics;
- define how package validators statically classify safe versus sandbox-required constructs and how unknown constructs fail closed;
- decide whether a future PQS sandbox-worker route is useful in addition to local StarLang/SWI worker isolation.

These are not permission to implement them in this research pass.

* Research Conclusion

The open portability questions are answered strongly enough to refine the research direction.

=star-kb= should author reusable logical packages independently from any one execution backend. PQS should remain the preferred shared *safe* execution path for the portable bounded subset. Direct Prolog and StarLang logic actors should be able to materialize the same package locally when that backend satisfies the package's semantic profile and capability requirements.

The operator's sandbox/unsafe idea is supported with one important refinement: *portability class and execution trust class should be separate*. Logic that cannot be proven to fit the shared safe subset must not silently enter the trusted PQS process. Approved native-power constructs may require a sandboxed worker plus explicit capability/isolation requirements; unsupported constructs remain rejected.

The research-supported property is therefore:

#+begin_src text
author rules once
  -> digest/version once
  -> classify required semantics + trust/isolation
  -> materialize to eligible runtimes
  -> execute safe subset in PQS or local safe workers
  -> execute approved native-power subset only in sandboxed workers
  -> prove semantic parity with shared fixtures
#+end_src

This research conclusion remains =PENDING= operator review. It does not authorize implementation changes in =lost-rob0t/star-kb=, =star-lang=, =prolog-query-server=, or StarIntel actors.

* Footnotes and Glossary

- *Logic package* :: A versioned/digest-identified reusable unit of logical facts, rules, named operations, and declared semantic requirements.
- *Materialization* :: Translating/loading one canonical logic package into the representation required by a concrete execution backend without changing its intended semantics.
- *Semantic profile* :: A named behavioral contract a logic backend declares it can execute; StarLang uses this during backend compatibility/selection.
- *Portability class* :: Whether logic belongs to the common portable subset or depends on a backend extension/native semantics.
- *Execution trust class* :: Whether the logic may execute in the normal safe path, requires an isolation/sandbox boundary and explicit capabilities, or is unsupported/prohibited for that route.
- *Sandbox-required* :: Logic that is not admitted to the shared safe subset and, if supported at all, must execute through an isolated worker with bounded capabilities/resources.
- *Backend mapping* :: Versioned logic/materialization code that maps a portable package/operation contract onto a concrete backend representation or operation surface.
- *PQS* :: =prolog-query-server=, the existing CouchDB-backed bounded expert-system service.
- *Direct Prolog actor* :: An actor whose logic executes against a local/native Prolog backend instead of requiring an HTTP query to PQS.
- *StarLang logic actor* :: A StarLang actor using the StarLang logic protocol/IR to execute a digest-identified logic package through an eligible backend.
- *Session delta* :: Ephemeral, schema-constrained run data supplied to a logic session without changing the canonical package identity.
- *Semantic parity* :: Evidence that the same logical package produces equivalent defined behavior across claimed compatible backend materializations.
