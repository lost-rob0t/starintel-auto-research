* Purpose

This stack revives the StarIntel =Titanic= concept as a durable actor-job protocol without turning transport research into an accidental architecture mandate.

Titanic means durable job identity and lifecycle semantics:

- durable admission;
- stable logical job identity;
- attempt/retry lineage;
- disconnected status/result lookup;
- cancellation and deadlines;
- idempotency and fencing;
- dead-letter/replay lineage;
- reconciliation across broker/store crash windows.

The first implementation uses infrastructure that StarIntel already operates plus the recovered local journal direction: RabbitMQ for brokered job delivery and LMDB for authoritative Titanic state.

Sento remains the local actor runtime. RabbitMQ moves durable cross-process work. Titanic owns job meaning. LMDB records authoritative v1 state. CouchDB is initially derived/queryable state and remains an alternate backend candidate behind the same =job-store= contract.

* V1 Required Semantics

1. stable =job_id= and idempotency scope;
2. durable admission before returning =accepted=;
3. durable job and attempt state;
4. capability routing through RabbitMQ without leaking AMQP details into =star.titanic/1=;
5. publisher confirms and unroutable-publication handling;
6. explicit ACK/NACK settlement;
7. at-least-once execution with duplicate-safe recovery;
8. typed terminal results and disconnected lookup;
9. bounded retry with backoff and dead-lettering;
10. cooperative cancellation and absolute deadlines;
11. target lease/fencing integration where manifests require exclusive authority;
12. deterministic fake/model contract tests before backend promotion;
13. crash-window reconciliation between LMDB and RabbitMQ;
14. backend contract tests reusable for LMDB, CouchDB, SQLite, and future stores.

A fake implementation supplies deterministic model tests.

LMDB, CouchDB, or another backend only passes when it satisfies the same semantic contract.

* CouchDB Boundary

CouchDB is not rejected.

The preferred first use is a projection from the authoritative LMDB journal for:

- dashboards and Quasar/API reads;
- status/result searching;
- dead-letter/replay operator tooling;
- analytics;
- replication/export;
- administrative inspection.

If CouchDB is later promoted to authoritative storage, follow [[id:starintel-star-server-research-038][STAR-RESEARCH-038]]:

- one authoritative aggregate document per logical job;
- =_rev= compare-and-swap for transitions;
- explicit Titanic audit records rather than Couch revision history;
- no assumption that =_bulk_docs= is atomic;
- no execution authority derived from replication conflict winner selection;
- Couch-specific crash/conflict/cluster contract tests.

* ZeroMQ Boundary

ZeroMQ remains useful transport research and may become an additional adapter when there is a concrete requirement such as:

- remote actor gateway;
- specialized low-latency pool;
- Sento process boundary;
- intentionally non-durable internal transport;
- polyglot interoperability experiment.

It is not a Titanic v1 promotion gate and Titanic does not require ROUTER/DEALER to function.

* Explicit Non-Goals

- replacing Sento local actor mailboxes;
- replacing RabbitMQ merely because another transport is interesting;
- forcing every actor language to expose AMQP details in the stable actor contract;
- requiring ZeroMQ for Titanic v1;
- making CouchDB replication winner semantics equal execution authority;
- treating CouchDB =_changes= or revision history as the durable Titanic audit log;
- claiming exactly-once execution;
- putting every high-frequency local actor message through Titanic persistence;
- introducing JetStream, Kafka, or Temporal without an independent requirement.

* Suggested Next Design Pass

Promote only the selected v1 seam:

- =star.titanic/1= durable envelope and validation fixtures;
- =job-store= protocol plus deterministic fake;
- LMDB =job-store= implementation;
- RabbitMQ transport adapter with confirms, mandatory routing, ACK/NACK, retry, and DLQ policy;
- atomic LMDB job/outbox/idempotency transitions;
- reconciler for journal/broker uncertain outcomes;
- one side-effect-light capability pilot;
- status/result/cancel/close API;
- optional CouchDB projection fed from deterministic outbox/events;
- contract tests from STAR-RESEARCH-036;
- CouchDB alternate-backend spike only after the LMDB baseline is measured.

Do not start by implementing ZeroMQ conformance or generalizing every backend.
