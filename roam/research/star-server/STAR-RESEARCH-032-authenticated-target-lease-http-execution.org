* Research Question

How should StarIntel[fn:starintel] expose authenticated target-lease operations through HTTP while ensuring that HTTP callers, embedded Common Lisp[fn:common-lisp] callers, local actors, RabbitMQ[fn:rabbitmq] workers, and persistence paths all use one authorization-aware lease service and one fencing contract?

* Repository Findings

The current authentication middleware creates an immutable request security context containing a principal, correlation identifier, and deadline. This is the right input shape for a lease application service.

The current deadline is derived from =X-Request-Timeout-Ms= and wall-clock universal time. Lease work needs an absolute monotonic deadline passed from middleware into the service so nested layers do not restart timeout budgets.

The principal contract already defines =targets:lease= and scoped actor principals. The lease routes should extend that contract rather than invent a parallel permission model.

The current HTTP error envelope is a custom =status/msg/code= object. New lease APIs need machine-readable errors with stable fields. RFC 9457 defines =application/problem+json= for this purpose.[fn:rfc9457]

Current target routing dispatches directly to a local actor or RabbitMQ and schedules recurring targets in a process-local timer. Issue 32 cannot be satisfied by adding routes alone. The target dispatch path, result publication path, persistence path, and RabbitMQ settlement path must all accept execution authority and reject stale fencing generations.

* Layering Finding

The correct stack is:

#+begin_example
HTTP route or embedded caller
  -> request/security context adapter
  -> target lease application service
  -> authorization decision
  -> issue-29 semantic state machine
  -> issue-30 backend-neutral lease store
  -> issue-31 Valkey adapter
#+end_example

Target execution uses the same application service:

#+begin_example
target submission
  -> manifest locking policy
  -> acquire or validate lease
  -> create immutable execution envelope
  -> dispatch local or RabbitMQ
  -> actor work
  -> fenced side-effect service
  -> settlement and release
#+end_example

HTTP routes MUST NOT call Valkey scripts or backend adapters directly. Embedded callers MUST NOT bypass authorization merely because they execute in-process.

* HTTP Resource Model

The issue lists operation-oriented endpoints. Preserve those paths for compatibility while treating the lease as a resource whose identity is the opaque lease identifier.

Recommended routes:

| Method | Path | Purpose |
|--------+------+---------|
| POST | =/v1/target-leases/acquire= | Acquire one canonical target lease |
| POST | =/v1/target-leases/:lease-id/renew= | Renew exact lease generation |
| DELETE | =/v1/target-leases/:lease-id= | Release exact lease generation |
| GET | =/v1/target-leases/:lease-id= | Inspect one lease when visible |
| GET | =/v1/target-leases= | Bounded filtered listing |
| POST | =/v1/target-leases/:lease-id/revoke= | Privileged revocation |

An acquire success should return =201 Created= with a =Location= header pointing to the lease resource. Replayed acquisition may return the same =201= body and location because the original resource is the result of the same logical request.

Renew returns =200=. Release returns =204= when no response body is required or =200= when returning a structured terminal result. The API should choose one stable behavior and test it.

* Request Contracts

** Acquire body

#+begin_src json
{
  "target": {
    "tenant_id": "tenant-main",
    "program_id": null,
    "dataset_id": "dataset-a",
    "actor_name": "collector",
    "workflow_id": null,
    "operation_class": "collect",
    "target_id": "target_01"
  },
  "ttl_ms": 30000,
  "maximum_lifetime_ms": 600000,
  "execution_id": "run_01",
  "trace_id": "trace_01",
  "metadata": {}
}
#+end_src

The server resolves and canonicalizes the target. Request fields do not create authority.

** Renew body

#+begin_src json
{
  "fencing_token": 42,
  "ttl_ms": 30000
}
#+end_src

The route lease identifier, authenticated owner binding, and submitted token identify the expected generation. The server may also require an explicit opaque lease version when the application service exposes one.

** Release and revoke

Release SHOULD require the fencing token through a body or an explicit conditional request field. Revocation requires a reason and may accept an expected token to avoid deleting a replacement generation.

DELETE request bodies are supported inconsistently by intermediaries. A dedicated release action route or an =If-Match=-style opaque lease version can avoid that ambiguity. Issue 32 lists DELETE, so the simplest stable contract is to carry the token in a required =X-StarIntel-Fencing-Token= header and keep the body empty.

* Idempotency Finding

Use the =Idempotency-Key= request header for acquire, renew, release, and revoke. The current IETF HTTPAPI draft defines it as a Structured Field string and states that the same key must not be reused with a different payload.[fn:idempotency-draft]

The service must bind the key to:

- authenticated principal;
- operation;
- route lease identifier when present;
- canonical request fingerprint;
- authorization scope;
- result receipt retention policy.

A matching replay returns the original result. A mismatched replay returns =422= or =409= with a stable =idempotency_key_reused= problem type. The design should select one; =422= is clearer because the request content and key combination is invalid independent of current lease ownership.

GET requests do not require idempotency receipts.

* Deadline Finding

Accept the existing bounded timeout header initially, but convert it at middleware entry to an absolute monotonic deadline. The service and adapter receive the same deadline.

The API must distinguish:

- =deadline_exceeded=: the operation is known not to have committed;
- =outcome_unknown=: the mutation may have committed and the caller must replay the same idempotency key.

A generic =504= is misleading for an uncertain committed mutation. Map known upstream timeout to =504=. Map unknown mutation outcome to =503= with =Retry-After: 0= or a bounded retry hint and an explicit instruction to replay the same key.

* Authorization Finding

Every route requires authentication.

Minimum capability:

- acquire, renew, release, inspect: =targets:lease=;
- listing: =targets:lease= plus explicit list permission or =targets:read= according to policy;
- revoke: administrator or separate =targets:lease:revoke= capability.

Authorization must bind:

- principal and credential identifiers;
- tenant and program;
- dataset;
- actor or workflow;
- operation class;
- canonical target;
- requested operation;
- lease owner for renew and release;
- correlation and decision identifiers.

An actor-scoped principal cannot inspect or mutate another actor's lease. An administrator is not exempt from tenant and reason requirements.

* Disclosure and 404 Policy

The API may return =404= instead of =403= when revealing lease existence would disclose another tenant, target, actor, or owner. This policy must be stable and applied after authentication.

A caller with permission to know the lease exists but not mutate it may receive =403=. A caller outside the visibility scope receives the same =404= shape as an absent lease.

Conflict responses must not expose another owner's private metadata. Safe fields may include:

- conflict type;
- canonical key fingerprint;
- expiry or retry-after when policy allows;
- owner class or caller-equality flag;
- correlation identifier.

* HTTP Status Findings

RFC 9110 defines =409 Conflict= for a request conflicting with current resource state and =412 Precondition Failed= for false request preconditions.[fn:rfc9110]

Recommended mapping:

| Lease outcome | HTTP status |
|---------------+-------------|
| acquired | 201 |
| replayed acquired | 201 |
| renewed | 200 |
| released | 204 or 200, selected consistently |
| found/listed | 200 |
| held by active owner | 409 |
| stale fencing token or opaque lease version | 412 |
| hidden or absent | 404 |
| unauthenticated | 401 |
| visible but unauthorized | 403 |
| malformed JSON or header | 400 |
| valid JSON with invalid lease fields | 422 |
| idempotency key reused with different request | 422 |
| rate or concurrency limit | 429 with =Retry-After= when known |
| backend unavailable, degraded, or unsafe recovery | 503 |
| known deadline expiration | 504 |
| uncertain mutation outcome | 503 with explicit replay instruction |

* Problem Details Finding

Use RFC 9457 problem details with =application/problem+json=.[fn:rfc9457]

Example:

#+begin_src json
{
  "type": "https://starintel.actor/problems/lease-conflict",
  "title": "Target lease is already held",
  "status": 409,
  "detail": "The canonical target operation currently has an active lease.",
  "instance": "urn:starintel:correlation:01...",
  "code": "lease_conflict",
  "correlation_id": "01...",
  "retry_after_ms": 8500
}
#+end_src

Problem documents must never contain backend keys, Valkey errors, credentials, full target documents, stack traces, or another owner's private metadata.

Owner fields are filtered by visibility policy. The public canonical target key may be an opaque stable encoding or fingerprint rather than the backend path.

* Embedded API Finding

The HTTP routes and embedded Common Lisp callers must invoke the same =target-lease-service= generic functions.

Embedded callers provide a =service-call-context= containing principal identity, scopes, correlation identifier, and deadline. Missing context denies. Package name, call stack, localhost origin, or process membership never grants authority.

The HTTP layer only:

1. parses and bounds input;
2. obtains the authenticated context;
3. calls the application service;
4. maps service results to HTTP;
5. emits safe response data.

* Target Dispatch Enforcement

The target or actor manifest declares whether locking is =required=, =optional=, or =forbidden=.

When required, target submission must either:

- include an active lease owned by the authorized caller and matching the canonical target key; or
- ask the target lease service to acquire one as part of a higher-level dispatch operation.

A raw target document without execution authority is rejected before local actor delivery or RabbitMQ publication.

The dispatch service creates the immutable execution envelope defined by issue 29. Actor code receives the envelope, not a mutable lease field copied from user JSON.

* Side-Effect Enforcement

Every result-producing path must go through a fenced service:

- document persistence;
- event persistence;
- graph mutation;
- attachment commit;
- result publication;
- RabbitMQ success acknowledgement;
- external irreversible action.

The fenced service atomically checks or advances the highest accepted token. A stale actor receives a structured =stale-fence= result and cannot publish accepted output.

This is the core acceptance test for issue 32: an expired worker may continue computing, but its output cannot become authoritative after a newer lease exists.

* RabbitMQ and Redelivery Finding

The target execution envelope must be serialized as a versioned message. The RabbitMQ delivery properties should include bounded trace fields for routing and observability, while the authoritative lease data remains in the body.

On redelivery:

- identical execution and fencing token may resume idempotently;
- lower fencing token is terminal stale work and should not be requeued forever;
- backend unavailability may be requeued under bounded policy;
- malformed authority is dead-lettered;
- successful acknowledgement happens only after fenced effects commit.

* Rate Limiting and Overload

Rate-limit dimensions:

- principal;
- credential;
- tenant;
- actor;
- canonical target key;
- source address as a secondary abuse signal;
- global in-flight lease operations.

Rate-limit checks happen after cheap authentication parsing but before expensive backend work when possible. A denied request cannot become allowed because the rate limiter fails.

Use =429= for caller-specific limits and =503= for global capacity or backend health failures. Include =Retry-After= only when meaningful.

* Acceptance-Test Findings

The implementation must prove:

1. every route requires authentication;
2. =targets:lease= and exact scope are checked before backend access;
3. hidden resources return stable non-disclosing =404=;
4. acquire, renew, release, and revoke replay safely by idempotency key;
5. mismatched idempotency reuse is rejected;
6. stale tokens map to =412=;
7. held leases map to =409=;
8. rate and backend failures map to structured =429= and =503=;
9. HTTP and embedded calls return equivalent service results;
10. required-lock targets cannot dispatch without authority;
11. local and RabbitMQ execution carry immutable lease identity and token;
12. every side-effect boundary rejects stale fencing generations;
13. an expired actor cannot publish accepted output after reacquisition;
14. problem responses contain no secrets or backend internals;
15. deadline and uncertain-outcome behavior instruct safe replay.

* Decision

Implement versioned authenticated lease routes as thin adapters over one target lease application service. Use =Idempotency-Key=, one monotonic deadline, scoped =targets:lease= authorization, RFC 9457 problem responses, non-disclosing visibility policy, manifest-controlled dispatch enforcement, immutable target execution envelopes, and mandatory fencing at every side-effect boundary.
