* Normative Status

This document defines the backend-neutral lease-store[fn:lease-store] protocol beneath issue-29 target lease semantics and issue-32 HTTP and execution integration.

Issue 31 selects Valkey[fn:valkey] as the initial deployable adapter. This protocol MUST preserve that decision while keeping all target, actor, and HTTP code independent of Valkey packages.

The words MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, and MAY are normative.[fn:normative]

* Goals

The protocol MUST:

- expose =acquire-lease=, =renew-lease=, =release-lease=, =get-lease=, =list-leases=, =revoke-lease=, =backend-health=, and =close-lease-store=;
- require one absolute deadline and request identifier for every operation;
- return structured immutable outcomes instead of booleans;
- preserve atomic acquire, compare renew, compare delete, revoke, and fencing-counter increment;
- encode keys deterministically and safely for standalone and clustered Valkey;
- persist explicit serialization versions;
- make request replay idempotent;
- distinguish known deadline failure from unknown mutation outcome;
- own connections, scripts, retry state, metrics, audit hooks, and lifecycle under one runtime object;
- provide a deterministic memory backend for unit tests only;
- provide one contract suite for every backend;
- reject new work after close begins;
- prevent HTTP routes and target actors from importing backend-specific packages.

* Non-Goals

The protocol MUST NOT:

- authenticate users or decide target scope;
- accept caller-supplied backend keys, script text, prefixes, or queries;
- expose Valkey connections, script digests, cluster slots, credentials, or raw errors;
- make listings proof of current ownership;
- reset fencing state when active leases expire or release;
- claim strong consistency across Valkey failover;
- permit the memory backend in production.

* Canonical Encoding

The logical tuple is serialized deterministically and hashed with SHA-256.

The digest becomes:

- the public opaque key fingerprint;
- the Valkey cluster hash tag;
- the stable audit correlation for the logical lease key.

Valkey keys:

#+begin_example
starintel:{lease-v1:<digest>}:active
starintel:{lease-v1:<digest>}:fence
starintel:{lease-v1:<digest>}:request:<request-digest>
#+end_example

The text inside braces is identical for all keys touched by one mutation, forcing one Valkey Cluster hash slot.[fn:hash-tag]

Raw tenant, actor, target, request, or owner identifiers MUST NOT appear in Valkey key paths.

The codec exports:

#+begin_src lisp
(encode-lease-key lease-key)
(decode-lease-key octets)
(lease-key-digest lease-key)
(render-safe-lease-key lease-key)
#+end_src

Round-trip and collision tests are REQUIRED.

* Capability Profile

#+begin_src lisp

The Valkey adapter reports:

- atomic same-primary scripts;
- same-slot multi-key support when cluster key tags are valid;
- server TTL and time;
- optional =WAIT= and =WAITAOF= durability modes;
- asynchronous failover limitations;
- current topology and recovery state.

Startup fails when required script, TTL, cluster-slot, authentication, TLS, or lifecycle capabilities are unavailable.

* Acquire Semantics

Acquire MUST atomically:

1. read a request receipt;
2. replay a matching receipt;
3. reject mismatched request reuse;
4. reject a valid active lease as conflict;
5. increment the persistent fence counter;
6. create an opaque lease identifier;
7. write the active record with server-authoritative timestamps and TTL;
8. write the request receipt;
9. return the lease handle, server time, and TTL.

Exactly one concurrent acquisition may return =acquired= for one key on one authoritative primary.

* Renew Semantics

Renew compares:

- schema;
- canonical key;
- lease identifier;
- owner identity;
- fencing token;
- positive current TTL;
- maximum lifetime.

Success keeps the same token, updates renewal and expiry, sets TTL, writes the receipt, and returns a replacement handle.

* Release Semantics

Release compares the exact lease identifier, owner, and token, then deletes only the active key and writes the receipt.

The fence key remains.

* Revoke Semantics

Revoke optionally compares expected lease identifier and token, deletes the active key, preserves the fence, and writes the receipt.

Authorization and reason validation occur above this protocol.

* Get and List

=get-lease= uses the authoritative primary for ownership decisions. Replica reads are forbidden for current ownership.

=list-leases= is bounded, cursor-based, and diagnostic. A Valkey cluster listing may be eventually assembled from multiple slots and MUST report that consistency. It cannot authorize execution.

* Valkey Adapter

** Scripts

Use versioned Lua scripts or Valkey Functions[fn:valkey-functions]. Every accessed key is passed explicitly. Scripts are loaded at adapter startup and reloaded after =NOSCRIPT= or failover.

Scripts MUST:

- use only deterministic bounded operations;
- avoid unbounded scans and loops;
- validate serialization versions and field limits;
- return one stable versioned result tuple;
- never log or return secrets;
- never call blocking acknowledgement commands inside the script.

** Durability acknowledgement

After a successful mutating script, the same client connection MAY execute:

- =WAIT <replicas> <remaining-timeout>=;
- =WAITAOF <local> <replicas> <remaining-timeout>=.

The configured profile defines required thresholds.

Failure to meet the threshold returns =durability-degraded= or =outcome-unknown= according to whether the script result is known. =WAIT= and =WAITAOF= do not justify a strong-consistency claim.

** Topology

Supported profiles:

- standalone;
- Sentinel-managed primary and replicas;
- Valkey Cluster.

Cluster mode requires all mutation keys in one slot. The client handles =MOVED=, =ASK=, and transient =TRYAGAIN= within the original deadline.

** Recovery fencing floor

After failover, restore, or detected fence-state loss, the adapter enters =:recovery-required=.

A recovery component obtains the highest accepted downstream fencing token for each affected canonical key or namespace checkpoint. It sets the Valkey fence to at least that value before acquisition resumes.

When the highest accepted token cannot be established, acquisition remains disabled. Guessing is forbidden.

* Runtime Lifecycle

#+begin_src lisp
(defclass managed-lease-store (lease-store)
  ((state :initform :created :reader lease-store-state)
   (adapter :initarg :adapter :reader lease-store-adapter)
   (pool :initarg :pool :reader lease-store-pool)
   (clock :initarg :clock :reader lease-store-clock)
   (metrics-sink :initarg :metrics-sink :reader lease-store-metrics-sink)
   (audit-sink :initarg :audit-sink :reader lease-store-audit-sink)
   (retry-policy :initarg :retry-policy :reader lease-store-retry-policy)
   (capabilities :initarg :capabilities :reader lease-store-capabilities)))
#+end_src

Lifecycle:

#+begin_example
:created -> :opening -> :ready -> :draining -> :closed
                     \-> :failed
                     \-> :recovery-required
#+end_example

Only =:ready= accepts operations. Close changes state to =:draining= before waiting for in-flight work and closes resources exactly once.

* Retry Rules

Retries MUST:

- reuse the same request identifier and fingerprint;
- derive every delay and backend timeout from the original deadline;
- use bounded exponential backoff with jitter;
- stop on ownership, validation, closed, malformed-record, and recovery-required outcomes;
- return =outcome-unknown= when commit status cannot be resolved through receipt replay before the deadline.

The adapter never creates a replacement request identifier.

* Metrics

Metrics use low-cardinality labels only:

- operation;
- result kind;
- adapter;
- topology;
- durability mode;
- retryability.

Required metrics:

- operation count;
- latency;
- in-flight calls;
- script reloads;
- cluster redirections;
- unknown outcomes;
- durability shortfalls;
- recovery-required state;
- pool state;
- malformed records.

No tenant, actor, target, principal, lease, or request identifier appears as a metric label.

* Audit Hooks

Every operation emits bounded audit data containing operation, result, correlation and request identifiers, principal identifier when supplied, key fingerprint, safe lease identifier, fencing token, replay flag, topology, durability result, retries, and latency.

Audit failure does not change an already committed lease result. The runtime records sink failure separately.

* Deterministic Memory Backend

The memory backend uses:

- one explicit state object;
- an injected manual monotonic clock;
- deterministic ID generators supplied by tests;
- one mutex or serialized actor;
- no sleeping or wall clock;
- no global state.

It refuses production configuration. It proves semantic behavior, not Valkey failover safety.

* Contract Suite

Every adapter runs:

1. key encoding round-trip and collision tests;
2. record-version rejection;
3. one-winner concurrent acquire;
4. fencing monotonicity after release, expiry, and revoke;
5. exact renew and release;
6. stale renew and release rejection;
7. request replay and mismatched reuse;
8. known deadline and unknown-outcome behavior;
9. bounded list behavior;
10. backend unavailable mapping;
11. close racing with operations;
12. pool closure exactly once;
13. audit and metrics failure isolation;
14. no adapter dependency in HTTP or target systems.

Valkey additionally runs:

- 100 concurrent acquires against a real service;
- cluster same-slot validation;
- script reload;
- connection loss before and after commit;
- expiry and reacquisition;
- durability acknowledgement thresholds;
- failover and restore;
- recovery fence advancement;
- secret redaction.

1. Protocol objects, results, key codec, serializer, and deadlines.
2. Runtime lifecycle and hooks.
3. Deterministic memory backend and complete common suite.

* Footnotes and Glossary

[fn:lease-store] Lease store: The component that atomically records temporary ownership, expiration, request replay, and a monotonically increasing fencing generation.

[fn:valkey] Valkey: The key-value server selected by issue 31 as the initial deployable lease backend.

[fn:normative] Normative: A requirement that conforming implementations must follow.

[fn:monotonic-deadline] Monotonic deadline: One absolute operation limit measured by a clock that only moves forward.

[fn:hash-tag] Hash tag: The substring inside braces in a Valkey Cluster key that forces related keys into the same hash slot.

[fn:valkey-functions] Valkey Functions: Server-managed named program logic that can execute atomically as an alternative to sending raw EVAL scripts on every call.
