* Research Question

How should StarIntel redesign the public Auto-Dig[fn:auto-dig] and Auto-Research[fn:auto-research] surfaces so that Auto-Dig becomes a real corpus dashboard with charts and a complete dataset browser, while Auto-Research remains a readable research system, and both remain approachable to ordinary visitors and useful to analysts?

This packet is intentionally research and design only. It does not approve or implement the user-interface changes.

* User Requirements Captured

The required product direction is:

1. =https://auto-dig.starintel.actor/= becomes the primary dashboard index, not a catalog-style landing page.
2. The dashboard must contain real charts and corpus-wide metrics.
3. The dashboard must be visually strong enough to attract ordinary visitors without becoming decorative research software that frustrates analysts.
4. A dedicated datasets page must browse every generated topic dataset and every source dataset.
5. The Auto-Dig =Research= navigation item must open =https://auto-research.starintel.actor/=.
6. Auto-Research must contain a reciprocal =Auto-Dig= link to =https://auto-dig.starintel.actor/=.
7. The design must use the Impeccable[fn:impeccable] design language as a design-review and anti-pattern source.
8. The result must avoid generic AI-generated dashboard styling and must preserve evidence, provenance, filters, document drill-downs, source access, and graph access.
9. The design must include visual “eye candy,” but visual effects must be driven by real corpus state and may not replace the operational dashboard.

* Current Auto-Dig Findings

** Finding 1: the root already has the data needed for a dataset catalog, but it is not yet a corpus dashboard.

=scripts/starintel_site/builder.py= currently generates:

- the complete corpus download and manifest;
- =datasets.json= for source datasets;
- =topic-datasets.json= for merged topic datasets;
- one dashboard, graph, document browser, source inventory, and exports for each target;
- root counts for research targets, topic datasets, source datasets, and canonical records.

The root page then renders three large catalog sections: topic datasets, research targets, and source datasets. This is useful as an index but it is not the visual command center requested by the user.

** Finding 2: the per-target dashboard is a strong foundation and should not be discarded.

=scripts/starintel_site/dashboard.py= already computes reviewed/unreviewed counts, unique source counts, relation counts, most-connected nodes, relation predicates, recent research passes, document-type chips, graph launch behavior, and paginated document browsing.

The redesign should reuse these concepts at corpus scope and align per-target dashboards to the new global design system rather than create a second dashboard implementation.

** Finding 3: the root page should stop rendering every dataset as a primary dashboard element.

All topic and source datasets already have machine-readable indexes. The root does not need to print the complete catalog as a card wall. Move the complete catalog to =/datasets.html= and show only a small “active datasets” or “largest datasets” slice on the dashboard.

This reduces cognitive load[fn:cognitive-load] for casual visitors and gives analysts a dedicated dense browser instead of forcing both groups through one giant landing page.

** Finding 4: the current visual language contains several Impeccable anti-pattern signals.

The current Auto-Dig stylesheet uses Inter as the primary font, repeated rounded gradient cards, large radial-gradient backgrounds, and many three-column card grids. Impeccable explicitly warns against defaulting to Inter, card-everything layouts, and other common template patterns.

The redesign should keep the useful dark intelligence-workspace identity but replace the generic SaaS/card-wall look with stronger editorial hierarchy, data-dense sections, intentional typography, and fewer container boxes.

** Finding 5: Auto-Dig and Auto-Research should share a shell, not a page template.

Impeccable distinguishes =Operate= surfaces such as dashboards and tools from =Read= surfaces such as documentation and research. Auto-Dig is an Operate surface: users scan, filter, compare, drill down, and open data. Auto-Research is a Read surface: users read research nodes, follow links, search, and inspect a knowledge graph.

Therefore the sites should share brand tokens[fn:design-token], navigation structure, typography family, spacing rhythm, focus treatment, and cross-site switching, while keeping distinct page compositions.

* Dashboard Content Model

The root dashboard should contain the following first-class modules.

| Module | Default presentation | Data source | Casual-user value | Analyst value |
|--------+----------------------+-------------+-------------------+---------------|
| Documents added by day | Line/area chart with 30d, 90d, 1y, all toggles | =date_added= from canonical documents | Immediately shows whether the corpus is alive and growing | Reveals ingestion bursts, pauses, and research campaigns |
| Document type breakdown | Doughnut chart excluding =relation= | =dtype= counts | Explains what the corpus contains at a glance | Click segment to filter dataset/document browser |
| Relation type breakdown | Separate doughnut or ranked bar chart | relation predicate/type counts | Shows what kinds of connections dominate | Click relation type to drill into related records or graph filter |
| Top connected people | Ranked horizontal bars, default reviewed relations only | reviewed graph degree for =person= nodes | Gives an immediate “who matters in this corpus?” entry point | Displays degree, dataset count, relation mix, and direct entity link |
| Top findings | Ranked evidence-backed finding list | reviewed claim/analysis/research records using deterministic ranking | Surfaces the strongest interesting material without opening the graph | Exposes rank reason, evidence count, source count, review state, and document link |
| Total sources | Large KPI[fn:kpi] plus source-domain breakdown | normalized unique source URLs | Conveys evidence scale | Opens source inventory / domain distribution |
| Active datasets | Compact ranked list with sparklines | dataset counts and recent additions | Easy jump into recognizable subjects | Size, update rate, sources, and last update |
| Corpus totals | Records, people, organizations, relations, datasets | precomputed corpus aggregates | Gives scale instantly | Filter anchors and audit baseline |
| Latest activity | Timeline of newest reviewed documents / research passes | =date_added= and =date_updated= | Makes the site feel current | Direct path to recent ingest |

The dashboard must not make a chart for every available metric. The priority is a small number of high-information modules with strong hierarchy.

* Top Findings Ranking

“Top findings” must not be a vague model-generated popularity label.

The first implementation should rank only reviewed candidate documents. A deterministic score may combine:

1. explicit assessment/confidence when present;
2. number of attached evidence records;
3. number of unique source URLs;
4. reviewed relation degree to other canonical entities;
5. recency as a small tie-breaker, not the dominant signal.

The UI must display why a finding ranks. If the schema cannot safely identify a finding class, the initial implementation should use a narrower reviewed claim/analysis set rather than fabricate significance.

* Top Connected People

The default ranking should use reviewed person-to-entity relations only. The interface may provide an analyst toggle for all relations.

Each row should show:

- person name;
- reviewed connection count;
- number of datasets containing the person;
- small relation-type distribution;
- direct document or graph-focus action.

This preserves a normie-friendly ranking while avoiding the false precision of one unexplained “influence score.”

* Dedicated Dataset Browser

The dataset browser should consume a unified generated catalog rather than make the browser re-scan the corpus.

Recommended generated record:

#+begin_src json
{
  "kind": "topic|source",
  "id": "dataset-id",
  "title": "Dataset title",
  "record_count": 1234,
  "people_count": 300,
  "organization_count": 91,
  "relation_count": 4021,
  "source_count": 188,
  "source_dataset_count": 6,
  "source_target_count": 9,
  "added_30d": 84,
  "updated_through": "2026-08-08T...",
  "url": "dataset-foo/index.html",
  "download": "dataset-foo/downloads/starintel-documents.jsonl"
}
#+end_src

The page should support:

- instant search by dataset name and target;
- =All / Topic / Source= filter;
- sort by records, recently updated, recent growth, source count, and name;
- visual card mode as the default casual-user view;
- dense table mode for analysts;
- direct dataset dashboard and download actions;
- pagination or virtualized rendering[fn:virtualization] if catalog size grows enough to make full rendering expensive.

* Cross-Site Navigation Decision Basis

Auto-Dig should use a persistent top-level product shell such as:

#+begin_src text
StarIntel  |  Dashboard  Datasets  Research ↗
#+end_src

=Research= resolves to =https://auto-research.starintel.actor/=.

Auto-Research should add a reciprocal link:

#+begin_src text
StarIntel Research  |  Index  Search  Graph  Auto-Dig ↗
#+end_src

=Auto-Dig= resolves to =https://auto-dig.starintel.actor/=.

The same labels should remain available on mobile without hiding the cross-product switch behind ambiguous icons.

* Visual Direction Using Impeccable

** Operate mode for Auto-Dig

Auto-Dig should optimize for scanability, comparison, and action. Visual expression belongs in exact typography, chart composition, subtle motion, data-driven ambient elements, and high-quality interaction states rather than decorative panels.

** Read mode for Auto-Research

Auto-Research should optimize for comprehension, reading width, visible hierarchy, backlinks, citations, and movement through the research graph. The shared shell may become visually aligned with Auto-Dig, but research pages should not inherit dashboard density.

** Anti-slop rules

The implementation should:

- remove Inter as the default design choice and select a more intentional readable type system;
- avoid wrapping every metric or paragraph in a rounded gradient card;
- avoid generic purple-blue AI gradients;
- avoid decorative icon tiles above headings;
- avoid excessive glow, blur, or motion that competes with evidence;
- avoid low-contrast gray text on tinted surfaces;
- keep color tied to data classes, state, interaction, or hierarchy;
- use larger uninterrupted surfaces for charts and ranked data instead of nested cards.

** Proposed visual character

- deep tinted navy/ink background rather than pure black;
- crisp cyan/ice interaction color;
- amber/gold as a limited evidence/highlight color;
- restrained semantic colors for state and document classes;
- one display/heading family plus a highly readable interface family and monospace only where identifiers/data require it;
- strong grid alignment and editorial whitespace;
- thin dividers, chart axes, and section rules instead of boxes around every section.

* Eye Candy That Carries Information

The dashboard may include one restrained “corpus pulse” element derived from real data, for example:

- a compact animated sparkline behind the update-state header;
- a small relationship constellation whose node count and movement represent recent reviewed additions;
- subtle chart entrance transitions on first render only.

It must obey =prefers-reduced-motion=[fn:reduced-motion], stop after initial presentation, and never require WebGPU or graph-scale data merely to render the landing dashboard.

The full relationship graph remains a separate analyst workbench.

* Data and Performance Architecture

The browser should not load the complete JSONL corpus to compute dashboard charts.

Extend the Python static-site generator to emit a compact =dashboard-data.json= containing pre-aggregated values:

#+begin_src text
summary
  total_documents
  total_sources
  total_datasets
  total_people
  total_organizations
  total_relations
  updated_through

documents_by_day[]
document_types[]            # relation excluded
relation_types[]
top_connected_people[]
top_findings[]
active_datasets[]
latest_activity[]
#+end_src

The root =index.html= should load only this small projection[fn:projection] plus the chart runtime. The datasets page should load the generated dataset catalog, not the full corpus.

This preserves the current static deployment model and avoids creating a dashboard that becomes slower as the research database grows.

* Chart Renderer Recommendation

Use a small adapter boundary so the data contract does not depend on a chart library.

Preferred initial implementation: a locally vendored Chart.js[fn:chartjs] build because the requested line, doughnut, and horizontal-bar charts can be implemented with one browser library and no application framework. Do not load chart code from a public CDN[fn:cdn] at runtime.

Every canvas chart must have a semantic summary or table fallback so the information remains accessible and inspectable without relying only on pixels or color.

* Responsive and Accessibility Requirements

1. Dashboard modules must reflow from a wide editorial grid to one-column mobile sections.
2. Charts must resize without horizontal page overflow.
3. All chart meaning must have a text/table equivalent.
4. Color may not be the only encoding for review state or document type.
5. Keyboard focus must be visible on chart controls, dataset filters, rows, and navigation.
6. Motion must honor reduced-motion preferences.
7. Dataset table mode must remain usable with keyboard navigation and narrow screens.
8. Touch targets must remain large enough for mobile use.

* Footnotes and Glossary

[fn:auto-dig] Auto-Dig: The StarIntel static research and dataset site at =auto-dig.starintel.actor=, generated from canonical research documents and supporting graph, document, source, and download views.

[fn:auto-research] Auto-Research: The StarIntel Org-roam research and design publication at =auto-research.starintel.actor=.

[fn:impeccable] Impeccable: The design-guidance project by pbakaus used here as a source for interface modes, visual anti-patterns, hierarchy, accessibility, and frontend craft guidance.

[fn:org-roam] Org-roam: An Emacs Org-mode knowledge-management system that stores linked notes as a graph and supports backlinks and node search.

[fn:cognitive-load] Cognitive load: The amount of information a person must keep and process at once to understand or operate an interface.

[fn:design-token] Design token: A named reusable visual value such as a color, spacing unit, type size, border treatment, or motion duration shared across interfaces.

[fn:kpi] KPI: Key performance indicator; here, a compact high-priority measurement such as total records or unique sources.

[fn:virtualization] Virtualized rendering: Rendering only the visible portion of a long list or table instead of creating browser elements for every row at once.

[fn:reduced-motion] Reduced motion: An operating-system and browser accessibility preference that asks websites to minimize non-essential animation.

[fn:projection] Projection: A small derived view of canonical data created for a specific interface, such as dashboard aggregates, rather than a second source of truth.

[fn:chartjs] Chart.js: A browser charting library that renders common charts such as line, doughnut, and bar charts without requiring React or another application framework.

[fn:cdn] CDN: Content delivery network; a remote service that hosts static files. This design recommends local vendoring so the public dashboard does not depend on a third-party runtime fetch.
