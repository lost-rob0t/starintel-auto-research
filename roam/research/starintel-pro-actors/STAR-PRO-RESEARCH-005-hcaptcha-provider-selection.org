#+title: STAR-PRO-RESEARCH-005 Capability-Based CAPTCHA Solver Selection
#+description: Comparative selection policy for local, browser, manual, and paid solver actors across exact challenge issuer, family, variant, context, result, cost, and disclosure requirements.
#+status: REVIEW
#+filetags: :starintel:research:starintel-pro-actors:captcha:provider-selection:capabilities:uml:

* Question

How should StarIntel select a solver actor when source actors can encounter many CAPTCHA and anti-bot challenge families rather than only hCaptcha?

* Approval Table

| Approval area | Required reviewer | State | Evidence required |
|---------------+-------------------+-------+-------------------|
| Selection algorithm | StarIntel server maintainer | PENDING | Deterministic exact-match and ranking tests |
| Capability evidence | Pro-actors maintainer | PENDING | Current provider fixtures and drift handling |
| Disclosure policy | Security reviewer and operator | PENDING | Local, automated-vendor, human-assisted, and manual classes |
| Cost policy | Operator | PENDING | Per-capability budgets and fallback rules |
| Reference implementations | Repository maintainers | NOT STARTED | Fake, browser, recognition, and provider adapters green |

* Decision

Do not select one global CAPTCHA provider. Select a solver in two stages:

1. perform a hard exact-capability match against issuer, family, variant, integration version, required fields, context binding, result kind, and execution/disclosure class;
2. rank only eligible matches by verified contract state, health, concurrency, downstream acceptance, latency, cost, and operator preference.

A narrow provider can be the reference implementation for one capability. NoneCap remains the hCaptcha token reference. It is not the global reference for reCAPTCHA, Turnstile, WAF interstitials, image recognition, or puzzles.

* Reference Actors by Role

| Role | Reference choice | Reason |
|------+------------------+--------|
| Protocol and continuous integration | Fake solver actor | Deterministic, network-free coverage of every result kind |
| Source-facing orchestration | =CaptchaDetectActor= | Owns detect, solve, apply, and verify lifecycle |
| Same-session browser challenge | Isolated local browser actor | Preserves operator-owned browser and network context |
| Image/text/audio recognition | Local recognition actor first | Avoids third-party disclosure and produces typed answers |
| hCaptcha token | NoneCap adapter | Narrow explicit contract, long polling, cancellation, feedback |
| Broad automated token/recognition | NopeCHA adapter | Separate Token and Recognition surfaces |
| Broad asynchronous task provider | 2Captcha adapter | Large task catalog and multiple result kinds |
| Broad alternate provider | Anti-Captcha candidate | Strong current catalog for reCAPTCHA, Arkose, GeeTest, Turnstile, AWS WAF, ALTCHA, image, and custom tasks |
| Unknown or custom challenge | Manual-review actor when policy permits | Prevents false type coercion |

* Hard Match Fields

A candidate is eligible only when all required predicates pass:

- issuer;
- challenge family;
- variant and integration version where material;
- required result kind;
- required normalized fields;
- browser-session binding;
- network-identity or proxy binding;
- cookie and user-agent requirements;
- mobile or application-runtime requirements;
- target-policy provider allowlist;
- execution/disclosure class;
- contract confidence.

There is no wildcard that silently widens =reCAPTCHA v2= into =v3=, hCaptcha standard into Enterprise, standalone Turnstile into a Cloudflare Challenge page, or image recognition into a token capability.

* Ranking Model

After hard matching, rank in this order:

1. operator-pinned provider when healthy and eligible;
2. contract confidence and fixture freshness;
3. source-context fidelity;
4. downstream acceptance rate for the exact capability;
5. health and circuit state;
6. available concurrency;
7. deadline fit;
8. estimated cost per accepted result;
9. operator preference.

Cost is intentionally late. It cannot override authorization, context fidelity, disclosure policy, or contract validity.

* Execution and Disclosure Classes

| Class | Example | Policy implication |
|-------+---------+--------------------|
| =localAutomated= | Browser or recognition actor on operator infrastructure | Preferred when capability and resources permit |
| =remoteAutomated= | Automated token provider | Challenge metadata leaves local boundary |
| =humanAssistedVendor= | Worker-backed task provider | Explicit worker-disclosure approval required |
| =manualOperator= | Local operator review queue | Explicit operator availability and audit policy |
| =customFirstParty= | Owned test-system solver or test key adapter | Bound to named target policy |

Provider registration must declare one class. Unknown execution class is ineligible.

* Fallback

Automatic fallback is disabled by default. Each fallback can create another charge, disclose challenge data to another party, and invalidate session or network binding.

When explicitly enabled:

- fallback candidates must independently pass the full hard match;
- the previous attempt must be terminal or safely cancelled unless speculative execution is separately approved;
- provider disclosure count and total reserved cost remain within policy;
- the source actor receives only the final accepted result;
- all attempts remain visible in redacted telemetry.

* Speculative Execution

Concurrent attempts are a separate policy and are never implied by fallback. It requires:

- an explicit target-policy flag;
- a maximum concurrent provider count;
- a total cost ceiling;
- disclosure approval for every candidate;
- cancellation behavior for losing attempts;
- deterministic winner selection and late-result deletion.

* Acceptance Metrics

Metrics are segmented by exact capability and target-policy class:

- solve completion;
- downstream acceptance;
- p50 and p95 latency;[fn:percentile]
- provider and contract errors;
- ambiguous-charge rate;
- cancellation success;
- cost per accepted result;
- result expiry before application;
- source-actor verification outcome;
- secret-redaction conformance.

A broad provider with poor acceptance for one family loses only that capability unless failures indicate account or generic API health problems.

* Provider Selection Matrix

| Challenge example | Preferred first actor | Secondary candidates |
|-------------------+-----------------------+----------------------|
| hCaptcha token | NoneCap | NopeCHA; verified 2Captcha contract later |
| reCAPTCHA v2 token | local browser when session-bound | NopeCHA, 2Captcha, Anti-Captcha, other verified adapters |
| reCAPTCHA v3 score/token execution | local browser | verified token provider with action/score contract |
| Turnstile standalone | local browser | NopeCHA, 2Captcha, Anti-Captcha, other verified adapters |
| Cloudflare Challenge page | isolated browser actor | provider only with exact challenge-page context support |
| Arkose/GeeTest puzzle | browser or local recognition | 2Captcha, Anti-Captcha, NopeCHA Recognition, other verified adapters |
| AWS WAF interstitial | isolated browser actor | exact AWS WAF provider capability |
| Text/image CAPTCHA | local recognition | NopeCHA Recognition, 2Captcha, Anti-Captcha, manual review |
| Unknown/custom | custom first-party or manual review | no automatic coercion |

This table is a default policy seed, not a permanent provider ranking.

* Test Requirements

- Exact-match positive and negative matrix.
- Version, variant, result-kind, and context widening prohibited.
- Execution/disclosure class denial.
- Operator pin, health failure, concurrency, and budget behavior.
- Acceptance-rate ranking segmented by capability.
- Fallback and speculative execution separately gated.
- Late result deletion and loser cancellation.
- No provider selected for unknown execution class or stale fixture.
- Deterministic tie breaking.
