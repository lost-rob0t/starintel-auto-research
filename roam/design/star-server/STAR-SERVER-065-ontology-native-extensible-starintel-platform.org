* Decision Proposal

**Recommend a single ontology-native semantic model across StarIntel without replacing the existing canonical JSON document store or making every domain type a compiler enum.**

The whole platform must resolve, validate, preserve and query *meaning*, not merely store extra ontology files. Every document resolves its storage dtype to zero or more named semantic class URIs, and every meaningful cross-object fact is represented as a qualified, provenance-backed assertion. All clients and actors consume one immutable semantic bundle (including extension packages) and the same evidence and time interpretation.

The system remains *document-primary and ontology-native*, not RDF-store-primary:

#+begin_example
canonical StarLang semantic model + release locks
    + versioned, digest-pinned ontology/domain packages
    |
    +--> generated document validator / portable manifests / binding catalogs
    +--> generated stable JSON-LD context + RDF vocabulary projection
    +--> typed fact/constraint catalog for Star KB / Prolog
                         |
authorized ingest -> validate document + ontology semantics -> canonical JSON
                         |
            durable change/outbox + provenance
               /          |            \
       star-kb Prolog    star-geo     graph/search/RDF
       derived facts     PostGIS      query projections
               \          |            /
                  referenced assertions
                         |
       signals for independently governed workflow actors
#+end_example

No semantic/graph/geo/RDF projection may become a second mutable ground-truth store; every derived result can be rebuilt from immutable sources, active package locks and rule locks. No LLM is required for deterministic validation, ontology resolution, inference or workflow selection.

* Contract: Ontology-Native From Every Document

** Storage type is not semantic type

- =dtype= selects the canonical versioned persisted shape and validated base envelope.
- A semantic class URI identifies the thing, concept, event or activity the document represents; one object can have several qualified classes.
- A predicate URI identifies the stable meaning/direction of a relationship, attribute or observation.
- A *qualified assertion* links subject/predicate/object to observed/valid/recorded times, source records, confidence/review, evidence, rule/proof and dataset/named context.
- A class assignment itself may be sourced, disputed, inferred or time-qualified. A model's guess is not a fact by virtue of =@type=.

To bridge old and new objects, define a **generated dtype-to-ontology profile registry**, not manual assumptions in each SDK. Examples:

| Persisted dtype | Initial semantic profile | Important distinction |
|----------------+--------------------------+-----------------------|
| =entity= | generic =Entity= with declared ontology classes | broad resource without inventing new dtype |
| =person= / =org= / =user= | person/organization/online-account profiles | account is not automatically same as the human who operates it |
| =concept= | SKOS-like concept/vocabulary term | taxonomy labels are not automatically asserted entity facts |
| =relation= | qualified relation/assertion projection | never collapse claim/evidence/inference into an unqualified edge |
| =event= | real-world event/occurrence type(s) | broker/audit/workflow signal is not automatically a world event |
| =observation= / =claim= | sourced observation/proposition | uncertain claims do not become verified occurrences |
| =geo=, =location=, =route= and =geofence= | geometry/place/spatial object family | event at a location is an assertion, not an ID alias |
| =target= and =operation= | control-plane activity/plan profiles | remain separate from investigative subject and real-world event |

** Extension envelope decision to implement only after version approval

Add one structurally typed optional semantic profile to the *new* core version, available on any document dtype (proposed shape; NOT CURRENT 0.10.1 syntax):

#+begin_example
semantic:
  ontologyRefs: [{packageUri, version, digest}]
  classUris: [stable URI ...]
  propertyValues: [{predicateUri, typedValue, qualifiers?} ...]
  assertionRefs: [canonical assertion refs ...]
#+end_example

This is *illustrative*. Final typed member names, null semantics, cardinalities, reference types, index obligations and migration are decided by StarLang implementation conformance. Root document envelope remains flat =id= /=dataset= /=dtype= /=schemaVersion=; an optional typed semantic member does **not** sanction a second nested =data= envelope. Do not copy a loose JSON map with unchecked keywords into the trusted schema.

The core ontology module should be small: universal Entity/Event/Activity/Place/Concept/Document/Assertion/Source/Time/Role semantics and package resolution. Specialized communities, finance, cyber, governance, alert taxonomies and source-specific types belong in domain modules.

* Contract: Extensible Domain Packages

A domain owner authors a modular **data-only ontology package** referencing stable namespaced class and predicate URIs, with shapes and mappings, not executable arbitrary code.

Proposed registry/package API operations for later design verification (NOT current public APIs):

#+begin_example
ontology.verify(bundleId, digest)
ontology.resolveClass(classUri, lockedSnapshot)
ontology.resolvePredicate(predicateUri, lockedSnapshot)
ontology.validateDocument(document, lockedSnapshot)
ontology.validateAssertion(assertion, lockedSnapshot)
ontology.diff(baseDigest, proposedDigest)
ontology.planMigration(sourceLock, destinationLock)
#+end_example

The package manifest is proposed to contain:

| Member | Contract |
|--------+----------|
| =packageUri=, =version=, =digest= | Canonical identity and hash of deterministic bundle bytes |
| =imports[]= | Exact digest-locked dependency closure; cycles/conflicts rejected |
| =classes[]= | URI, parent classes, definitions, shapes, introduction/deprecation |
| =predicates[]= | URI, domain/range, qualifiers, inverse/symmetric/transitive rules where proven |
| =typedProperties[]= | datatype/units/cardinality/allowed references; no arbitrary executable validators |
| =mappings[]= | Exact/close/broader/narrower/lossy external crosswalks with explicit data loss |
| =factProjection= | Generated registry for generic Prolog facts and bounded named queries |
| =migration= | Classified additive/breaking conversions, reversible transforms or loss markers |
| =fixtures[]= | Immutable positive/negative/example and round-trip conformance records |
| =owner= / =visibility= | Package ownership and import permissions; not an authorization grant |

** Release/version invariant

- Normative StarIntel *core schema* or compiled core semantics change => **new core schemaVersion**. 0.10.1 bytes, release locks and fixtures remain untouched.
- A compatible additive release might be =0.11.0=, but exact semver classification is a release gate; if existing semantics must change incompatibly, use a major bump. Version numbers are never a substitute for migration.
- Custom domain packages change => bump their *package version*, recalculate digest and pin the new bundle in document/dataset semantic contexts. A package introducing new classes via an already-supported extensibility envelope does **not** require arbitrarily bumping the core schema; this does not violate the core-change version rule.
- Rule packs, workflow policies, named queries, graph projections and API/transport profiles have independent version/digest coordinates.
- Package activation is immutable and controlled by authorized registry publication, static validation and rollback. No client-supplied remote contexts, unsandboxed Prolog clauses or tenant modifications of built-in URIs.
- Unknown package or digest mismatch => typed quarantine/failure, never default-to-permissive or silent reinterpretation.

** Offline and cross-language conformance

CL, Kotlin, Java, Python, TS/JS, Nim, Go, Rust, Emacs Lisp and Prolog consumers of the existing release must resolve the *same* ontology definition, preserve unknown authorized extension fields and report the same invalid document/error category. New domain class installation must not require hand editing each language's class hierarchy.

Generate a versioned JSON-LD =@context= and RDF vocabulary projection from the exact locked semantic source. A round-trip must preserve assertion IDs, typed literals, time, evidence and named context. If an export format cannot express a qualifier, report loss; do not silently declare equivalence. RDF/SPARQL query service is an optional projection and may be powered independently, without replacing CouchDB.

* Domain: First-Class Communities Without One New Dtype Per Variant

Use the broad class vocabulary from [[https://github.com/lost-rob0t/starintel-auto-research/issues/252][#252]]; specialize only through domain packages.

A =Community= can be geographical, online, informal, event-based, topic-based, temporary, federated, or an overlapping collection. It may refer to an =Organization=, =Forum=, =Channel= or =ChatGroup= without being identical to that thing. The canonical =entity= is a valid storage profile; =community= as a dedicated dtype is a separate question requiring demonstrated storage-specific invariants and a new schema version.

The domain module must define machine-readable predicates for =subcommunityOf=, =hasPlatformSpace=, =partOf=, =locatedIn=, =hostedBy=, =moderatedBy=, =memberOf=, =claimedMemberOf=, =mentions= and =participatedIn= with distinct semantics. =memberOf= requires an attributed assertion, temporal interval and evidence; a role binding is not a permanent person's characteristic.

Negative examples:

- A commenter discussing a forum is not necessarily a forum member.
- A user following an account is not automatically an adherent of its ideas.
- Co-attendance at a meeting is not evidence of membership or affiliation.
- A city/neighborhood community can have a spatial catchment without containing a list of named humans.
- Expired/retracted memberships cannot appear as current and cannot be silently re-inferred on stale sources.

* Domain: Real-World Events as First-Class Knowledge

** Reuse =event=; distinguish reports and hypotheses

The 0.10.1 =event= dtype is the likely storage profile for a real-world event, with typed semantic classes in the new package. Different event taxonomies belong to domain vocabularies and must not be encoded as new core enums for every phenomenon. An event is *not* a broker message, target scheduling tick, detector alert, log entry or rule signal. Those remain runtime/control-plane records.

Minimum domain meaning:

- stable event candidate/identity plus independent source-report IDs;
- time of occurrence (=earliest/latest=, instant, interval, ongoing or unknown) distinct from when evidence was collected/ingested and a classifier ran;
- event stage =reported=, =hypothesized=, =contested=, =reviewed=, =confirmed= or =retracted= as qualified source/review assertions, not a single unqualified truth toggle;
- one or many geometries, place anchors, region/area/trajectory, with explicit accuracy and alternative hypotheses;
- role-qualified participants and organizations; alleged/claimed roles not treated as verified participation;
- parent/subevent, repeated-instance, correlated-event and duplicate-report links, with evidence for merges and reversible adjudication;
- source/licensing/provenance and event-specific ontology fields supplied by optional packages.

Event classification can change as facts arrive. The original media and reports remain unchanged, and the derived event projection is rebuilt or revised with causation/proof. For a virtual world event, geometry may be absent; do not invent a site.

* Domain: Better Geo as Semantic Relations Over Existing Geometry

Use =geo= (seven families), =location=, =address=, =route=, =geofence=, =encounter= and =map-layer= as already implemented schema *types*; reuse [[https://github.com/lost-rob0t/starintel-server/issues/237][geo #237]] to answer spatial queries. The key addition is **semantics**:

- =Place=, =Region=, =AdministrativeArea=, =Building=, =Venue=, =Route=, =Track=, =Coverage= etc. as ontology classes; locality hierarchy as time-qualified assertions rather than hard-coded U.S.-only administrative enums;
- geometry source distinctions =direct/anchored/derived= and transform chain, with accuracy, measured or inferred status, timezone and vertical datum where applicable;
- spatial predicates =inside=, =intersects=, =touches=, =near=, =coveredBy=, =routeThrough=, =observedAt= and =reportedInRegion= qualified by measurement method and temporal window;
- precise polygon/ring orientation/holes, coordinate order WGS84, antimeridian, invalid/self-intersecting geometries, CRS conversion and units checked by geospatial services;
- time-dependent location and competing location claims; an IP-geolocation or Wi-Fi sighting must never be promoted into the person's direct present location;
- spatial projection only: PostGIS/vector tiles/GeoJSON/GeoSPARQL/TAK and mobile map layers are derived, visibility-filtered and rebuildable, and never a canonical data editing surface.

The relevant historic =star-spec= geo draft supplies direct/anchored/derived projections and uncertainty principles; migrate useful statements into the version-bumped canonical source rather than retaining conflicting normative authorities.

* Rules, Signals, Workflow Fan-Out and Dataset Policy: Not Schema Authority

** All signal and workflow interpretation is outside core ontology

A Star KB Prolog expert *named and bounded query* may detect a tenant/domain-defined signal from source-backed facts. The domain/rule package owns a rule's label and criteria; the workflow policy owns eligible capabilities, review requirements, actor selection and destination dataset. **Neither a generic StarIntel =event= document nor a custom ontology term authorizes execution.**

#+begin_example
raw source records -> validate + canonical document/evidence ingest
  -> resolved ontology facts (star-kb projection)
  -> bounded named Prolog query + proof + rulePack lock
  -> candidate signal with source/evidence/time and reason
  -> authenticated policy evaluator / review decision
  -> StarIntel Target/Operation (durably accepted)
  -> supervisor / workflow actor / bounded fan-out
  -> actor outputs -> canonical validation + authorized dataset assignment
  -> change feed -> re-evaluation or truth-maintenance, subject to dedupe/stop rules
#+end_example

Example (deliberately *non-normative*): a public-safety domain rule produces an =example.publicSafety.reviewCandidate= signal based on synthetically defined evidence. A tenant-configured policy may open a human review and run source-corroboration actors. The core schema must NOT introduce =activeShooter=, a social-media keyword flag, an emergency dispatch command, default watchlists, or specific dataset routing. Detection does not equal confirmed event; commentary or praise alone is not a threat finding, membership claim or authorization for action.

** Required workflow invariants

- signal has stable idempotency identity, rule URI/version/digest, input assertion/evidence refs, observed/decision times, method, provenance and state;
- selected workflow is authorized by principal/tenant/purpose/capabilities *outside* ontology; dataset output is chosen by authorized policy, not an untrusted source field;
- positive ceilings for fan-out count, concurrency, recursion depth, total work, time, bytes, costs; explicit cancellation/leases/fencing and terminal partial/error states;
- no unbounded recursive rule → actor → rule feedback, no automatic public notification/high-consequence action on a single weak classifier hit;
- replay and changed source evidence can invalidate a derived signal, update an alert, or ask for review without deleting historical audit;
- no arbitrary external Prolog text, Prolog =call/1= or LLM-generated executable code through a generic public query endpoint; only signed/allowlisted named rule packages.

Link execution to existing [[https://github.com/lost-rob0t/starintel-server/issues/167][server playbook #167]], [[https://github.com/lost-rob0t/starintel-server/issues/129][webhook registry #129]], [[https://github.com/lost-rob0t/starintel-server/issues/302][alert evaluator #302]] and [[https://github.com/lost-rob0t/star-lang/issues/51][bounded fan-out #51]]. This design must not create a hidden second scheduler or actor registry.

* Contract: Entity-Agnostic Semantic Target Monitoring (Proposed; Not a Shipped API)

** Three different things: subject, watch intent and actor Target

A *subject* is a canonical document/identity reference or a separately qualified unresolved external identifier. It may refer to a Bluetooth device, lake, person, organization, document, event or anything supported by the ontology. Never assume all subjects are =person= or persist under =dtype=entity=.

A *watch profile* is independently versioned, rule-/policy-owned declarative monitoring intent: eligible semantic predicates, subject classes, directions, evidence/review states, time windows, requested actor capabilities, admission limits, observation frequency and intended purpose. Watch-profile authority lives in Star KB policy and Server scheduling configuration, *not* in a relation edge or as a new 0.10.1 core schema field.

A *Target* is a durable actor work/control-plane document accepted by StarIntel Server. Existing 0.10.1 =target= stores required =actor= and =target= strings, optional =targetType= and timing/state/attempt fields. Its string must be resolved, authorized and normalized by a versioned service boundary before it is treated as a canonical subject reference. Adding an authoritative typed =subjectRef= or changing =target= semantics would require a *new* StarLang core release with migration and conformance; this design does not do so.

** Separate discovery edges from monitor-eligible assertions

Existing =star-kb= [[https://github.com/starintel-labs/star-kb/blob/main/kb/core/star_reasoning.pl][=graph_edge/5=, =path/4= and =tool_neighbors/3=]] enumerate explicit =star_relation/9= claims and document =star_ref/3= paths (=references(Path)=), with =path/4= currently independent of predicate/direction. This is useful for exploratory graph walks. It is *not* a semantics- or authorization-filtered monitor query.

| Relation-like input | What it means | Monitoring treatment |
|---------------------+---------------+----------------------|
| =relation(source,predicate,destination)= | Explicit, potentially time-qualified semantic assertion | Consider only after ontology, evidence, policy and tenant resolution |
| =references(Path)= / =referenced_by(Path)= | Structural JSON/document reference | Discovery navigation only unless a separate named monitoring rule explicitly qualifies the *underlying* asserted semantics |
| =observedAt(Device,Place)= | Time/observer-qualified observation | May support device/place observation policy; never implies owner or identity |
| =mentions(Person,Event)= / =follows(Account,Account)= | Mention or platform interaction | Never convert into membership, adherence, participation or threat status |
| =candidateSameAs(A,B)= | Hypothesized identity link | Review/candidate only; not a canonical merge or unrestricted new watch |
| =related-to= | Unspecific association | Reject for rule-driven monitoring; optional derived UI convenience cannot create a canonical assertion |

Typed ontology metadata declares predicate URI, inverse semantics (if valid), domain/range, temporal meaning, evidence shape and version/digest. *Monitoring profile policy* independently declares whether an outbound/inbound predicate is relevant to a particular task. Neither schema typing nor =subPropertyOf= creates an automatic permission to traverse. =graph_edge(..., in)= is a direction of navigation, not proof that a semantically valid inverse assertion exists.

** Proposed named query and decision separation

#+begin_example
monitor.expandCandidates(authorizedContext, watchProfileLock,
                         subjectRefs, evidenceSnapshot, traversalBudget)
    -> candidateSet {
         candidates: [{subjectRef, predicatePath, evidenceRefs,
                       ruleProofRef, assertionStates, validInterval,
                       reasonCodes, requiredActorCapability}],
         skipped: [{subjectRef, reasonCode}],
         snapshotRevision, rulePackDigest, ontologyDigest,
         continuationOrTerminalState
       }
#+end_example

This is **illustrative**, not current 0.10.1 wire syntax, executable Prolog, or permission for clients to call arbitrary predicates. It is a bounded named tool contract over a deterministic immutable snapshot. The implementation may use tabled Prolog/Datalog and incremental invalidation for performance, but named external operations must not accept arbitrary Prolog goals.

1. Resolve each subject ID/identifier under tenant/dataset authorization and ontology/semantic bundle locks. Ambiguous matches stay proposals, never silently merge.
2. Select a *purpose-scoped* expansion profile. If no profile edge matches, retain the originating subject and return =no_eligible_relation=; never fall back to =related-to= or "all neighbors."
3. Traverse only reviewed, policy-eligible semantic assertions. Require predicate direction, domain/range, valid/observed time, evidence and statement status. Source copying is not independent corroboration; inferred/claimed status cannot be silently promoted.
4. Enforce positive limits on max hops, evaluated edges, visited nodes, output candidates, bytes, runtime and actor-work budget; stable ordering and cycle/duplicate suppression across the *whole watch batch*, not only per input Target.
5. Produce candidates with a proof path (predicate URIs, source direction, assertion/evidence IDs, temporal intersection, ontology+rule locks, confidence/review state) and explicit skip/review reason codes.
6. The authenticated Server policy evaluates *each candidate endpoint and requested actor capability*, including disclosure/dataset restrictions, before admission. Only after approval do existing Target/Operation actors perform durable idempotent scheduling; Prolog is pure decision output.
7. On source change, ontology/rule revision, revocation or evidence retraction, recompute dependent candidates and mark old proof conclusions stale. Preserve historical audit and enforce revocation on new work; active in-flight operations follow service-owned cancellation policy.
8. Prefer ingest/change-feed-driven invalidation plus scheduler-owned bounded freshness checks. =lastRunAt= and =nextRunAt= are durable scheduling concerns, not permanent mutable =last_check/1= facts in Star KB.

** Illustrative domain profiles, not platform defaults

| Watch purpose | Input subject | Eligible predicate example | Possible *candidate* action | Explicitly forbidden inference |
|---------------+---------------+----------------------------+-----------------------------+--------------------------------|
| Local wireless observation | Bluetooth device | =observedAt= qualified with sensor/time | Recheck authorized device observations | Correlating MAC/proximity with an identified person or owner |
| Watershed changes | Lake | =outflowsTo=, =withinWatershed= | Check related waterbody/region data | Expanding to residents/people by geographic proximity |
| Website uptime | Organization | =operates= | Check explicitly operated site | Treating linked accounts or employees as operators by implication |
| Public event update | Event | =heldAt=, =hostedBy= | Recheck venue schedule or organizer notice | Treating mere mentions as attendance or group membership |

=related-to= is not required: meaningful predicates already supply specific, qualified connections. Family/social networks may offer deliberately modeled relation families, but the monitor still selects concrete predicates, time windows and policy requirements.

** Authority, versioning, and implementation ownership

- [[https://github.com/lost-rob0t/starintel-auto-research/issues/252][Ontology #252]] / StarLang define *what each predicate means*. New core semantic/wire behavior requires new core schemaVersion (never patch 0.10.1); independently declared domain predicates use versioned/digest-locked extension bundles where the released envelope permits.
- [[https://github.com/starintel-labs/star-kb/issues/15][Star KB #15]] owns *which named, bounded policy queries derive candidates and decisions*, including admissibility, versioned watch profiles and proof. A rule-pack change bumps its own version/digest and invalidates affected derived projections, not the immutable StarIntel 0.10.1 schema.
- StarIntel Server owns *who may monitor whom/what and execute which work*: authorization, actor capability matching, Target creation, schedule/checkpoint, CAS/fencing, outbox/idempotency, budgets, cancellation and tenant-scoped dataset routing. Query candidates are not executable commands.
- Quasar/clients may visualize reviewed typed edges and explain rejected/accepted candidates; Quasar does not become the ontology, scheduler or ARADR authority. An external third-party ARADR integration can be designed separately.
- Legacy =star-kb:tool_path/4= continues to serve exploratory paths; a future separate allowlisted =monitor.expandCandidates= endpoint must not silently redefine =tool_path/4= semantics.

** Adversarial and RED-first semantic monitoring matrix

| ID | Input/attack | Required future assertion or observable outcome |
|----+--------------+--------------------------------------------------|
| MON-001 | Bluetooth device + sourced =observedAt= + =references(Path)= to collection record | Only purpose-allowed sourced observation can expand; structural reference does not |
| MON-002 | Lake linked by =outflowsTo=, organization by =operates= | Appropriate distinct profiles work without hard-coded =person= or one =dtype= per target class |
| MON-003 | =related-to=, =mentions=, =follows=, inferred/co-located device | No identity, ownership, membership or automatic monitoring promotion |
| MON-004 | Reverse edge, missing =inversePredicate= and ontology =subPropertyOf= | Do not invent inverse meaning or authorize child predicate by inheritance |
| MON-005 | Contradictory/retracted assertion and cross-tenant hidden endpoint | Skip, require review or deny; no leaked endpoint or stale positive watch |
| MON-006 | 1,000-degree hub, mutual cycle, 3-hop graph and duplicate input targets | Budgets and stable dedupe bound work, return continuation/terminal reason |
| MON-007 | Replayed candidate, concurrent schedulers and changed source before acceptance | At most one authorized durable Target action per idempotency identity; proof checked against fresh policy epochs |
| MON-008 | Existing valid 0.10.1 =target=, then proposed new typed subject constraint | Old reader remains valid; normative contract change only after explicit new StarLang release/version lock |
| MON-009 | Rule-pack or ontology lock changes while a watch is active | Old proof remains auditable; new evaluation uses pinned accepted version and revocation rules |
| MON-010 | Source profile asks to watch every person near a wireless device | Fail closed unless a separately valid, expressly authorized evidence-backed rule exists; proximity is not personal identity |

These tests are **proposed fixtures only**; no monitoring API or end-to-end proof is implemented by this ARADR edit. Operator research/design approval is still pending.

* Concrete Non-Normative Scenario

#+begin_example
Package: example.org/community-events@1.2.0 (digest locked)
  class: Community
  class: MeetupEvent extends WorldEvent
  predicate: hostedBy -> Community
  predicate: heldAt -> Place
  predicate: participantRole -> RoleAssignment

Canonical entity: "Synthetic neighborhood coding club"
  dtype=entity, semantic class=Community, evidence of existence

* Adversarial Review and Explicit Rejections

- **Reject a million fixed dtypes:** does not scale to user-defined communities/event classes and breaks portable bindings.
- **Reject ungoverned live ontology mutations:** changing domain/range, imports or class meaning invalidates downstream inference; require version, digest and migration.
- **Reject a second canonical triple store:** PostGIS/RDF/graph/Prolog each derive from canonical validated documents, subject to the same scopes.
- **Reject an inferred graph edge treated as a direct real-world fact:** every inferred edge needs provenance, time, proof, confidence/review and invalidation path.
- **Reject source-content-driven workflow execution:** untrusted text, custom event names or class declarations do not grant capabilities, select datasets or create privileged targets.
- **Reject blind high-consequence public-safety classification:** source sarcasm, debate, copied posts or topical support alone are not proof of imminent danger. Human review/authorization, independent corroboration and precise rule provenance belong to policy/evaluation services.
- **Reject map projection as identity oracle:** co-observation and spatial proximity alone do not prove affiliation, residence, ownership, movement or intent.
- **Reject unbounded event cascades:** budget, idempotency, parent causation and cancellation remain operational necessities even when a document is schema-valid.
- **Reject semantic version relabeling:** migrating old documents requires explicit verified mapping, not replacing =schemaVersion= values.

* Footnotes and Glossary

- *Ontology-native platform*: All persisted records participate in versioned typed semantic interpretation and evidence-aware inference, rather than ontology being a mere optional reference table.
- *Storage dtype*: Versioned wire/document profile, not necessarily a domain class.
- *Ontology module/package*: Versioned, integrity-locked namespaced data-only classes/predicates/shapes/constraints and mappings.
- *Semantic projection*: Derived and rebuildable typed graph, spatial, Prolog or RDF view over canonical records.
- *Qualified assertion*: Statement with traceable provenance, evidence, time, status, context and optional proof.
- *World event*: Occurrence independent of its reports, hypotheses, notices and workflow signals.
- *Workflow signal*: Bounded, evidence-linked detection output for an independently authorized workflow controller; not a confirmed event.
- *Valid time*: Period when a source claims a relationship or condition held in the world, separate from observation and ingestion time.
- *Digest pin*: Runtime verification of immutable package bytes and transitive imports against an expected cryptographic hash.
- *Replay-safe fan-out*: Bounded actor dispatch with durable acceptance, idempotency, cancellation and terminal result accounting.
