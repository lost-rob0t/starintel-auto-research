* Status of This Design

This file is the approved normative API specification for the logic/expert runtime.

Project maintainer approval was recorded on 2026-08-15 after rendered-site review.

It does *not* approve STAR-LANG-RESEARCH-023 and does not claim the logic runtime is implemented today.

STAR-LANG-007 remains the broader selectable-backend/expert-system architecture. This design narrows and hard-locks the public API boundary that STAR-LANG-007 left too broad.

* Normative Language

The key words SHALL, MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in this document.

* Normative Contract

The initial contract identifier SHALL be:

#+begin_example
star.logic.api/1
#+end_example

A runtime or compiler claiming =star.logic.api/1= MUST implement the portable protocol and exact semantics in this file.

Adding a new optional semantic profile does not change =star.logic.api/1=. Reinterpreting an existing operation, terminal state, duplicate policy, ordering rule, mutation identity rule, or error meaning requires a new API/profile version.

* Core Decision

StarLang SHALL expose a small Prolog-inspired Lisp-native source API:

#+begin_example
assert!
retract!
solve
solutions
exists?
explain
#+end_example

These names are StarLang operations. They are not aliases for backend-native functions with the same or similar names.

The portable runtime protocol SHALL remain backend-neutral and SHALL route all behavior through typed normalized operations and capability checks.

Backend-specific semantics SHALL be exposed only through named versioned profiles and profiled operations.

An unsupported profiled operation MUST fail before backend state is mutated.

* Current Source Compatibility

** Closed reader

Current =.star= source is parsed by the StarLang closed reader, not Common Lisp =READ=. The current reader:

- builds syntax objects with source spans;
- rejects host reader syntax;
- rejects package-qualified names;
- rejects dotted lists;
- restricts keyword tokens to an explicit whitelist;
- currently parses integers as numeric literals and rejects unsupported number-like tokens.

The symbols =assert!= and =exists?= are lexically possible ordinary identifier tokens under the current reader rules, but the compiler does not currently implement them as logic forms.

Therefore implementation SHALL add grammar/compiler handling deliberately. It MUST NOT route them through Common Lisp symbol-function lookup or =EVAL=.

** Canonical fact field syntax

For =.star= v1, the normative fact-construction syntax SHALL use field-pair forms:

#+begin_src lisp
(assert!
  (risk
    (transactionId transaction-id)
    (level high)))
#+end_src

General grammar:

#+begin_example
(<fact-type>
  (<field-name> <expression>)
  ...)
#+end_example

Reasons:

1. current StarLang schemas already use explicit field identifiers;
2. field names are lower camelCase at the language boundary;
3. schema-specific =:field= keywords would require weakening or redesigning the current global keyword whitelist;
4. field-pair syntax remains closed and schema-checkable.

Trusted Common Lisp generated constructors MAY continue exposing keyword convenience APIs. That host API is not the untrusted =.star= syntax contract.

The following remains ergonomic inspiration but is NOT canonical =.star= v1 syntax:

#+begin_src lisp
(assert! (entity :type "analyst" :confidence 0.97))
#+end_src

It may become future sugar only after a separate reader/type design safely defines schema-aware keyword labels and decimal literals. Such sugar MUST lower to the same =assert!= IR and MUST NOT alter semantics.

* Source Operation Specification

** =assert!=

Grammar:

#+begin_example
(assert! <typed-fact-expression>)
#+end_example

Semantics:

- constructs exactly one compiler-known typed session fact;
- validates schema/type requirements before mutation;
- allocates a stable StarLang fact identity before adapter mutation;
- applies one =assert= fact delta to the current logic session;
- returns a normalized fact reference;
- journals the mutation according to the enclosing runtime durability policy.

=assert!= MUST NOT:

- mutate a canonical source document;
- accept raw Prolog clauses;
- choose front/back clause order;
- invoke LISA's native macro directly from untrusted source;
- accept a native object;
- silently coerce an incompatible fact mapping.

Backend projection is adapter-private.

** =retract!=

Grammar:

#+begin_example
(retract! <fact-ref>)
#+end_example

Semantics:

- retracts one StarLang session fact by stable identity;
- is idempotency-aware according to the session journal contract;
- returns a normalized mutation receipt;
- MUST NOT mean pattern-based Prolog =retract/1=.

A missing already-retracted fact SHALL produce a defined idempotent/no-op or conflict result according to the mutation policy recorded in the plan. It MUST NOT cause native undefined behavior.

Pattern retraction is a separate Prolog-profile operation.

** =solve=

Grammar:

#+begin_example
(solve <named-operation>
  (<parameter> <expression>)
  ...)
#+end_example

Example:

#+begin_src lisp
(solve ownership-path
  (from source-id)
  (to ?target))
#+end_src

Semantics:

- invokes one compiler-declared named query/goal;
- validates parameter names and types statically where possible and before backend invocation otherwise;
- returns the first normalized answer or a normal no-answer result;
- does not grant access to arbitrary native callable terms.

=solve= is equivalent to answer cardinality =first=. It does not imply Prolog cut semantics outside this operation.

** =solutions=

Grammar:

#+begin_example
(solutions <named-operation>
  (<parameter> <expression>)
  ...
  (limit <integer>)
  (duplicates preserve|remove)
  (order unspecified|canonical))
#+end_example

Options are explicit child forms rather than schema-specific keywords.

Defaults in =star.logic.api/1=:

#+begin_example
limit       deployment/session limit
duplicates  preserve
order       unspecified
#+end_example

Rules:

- =preserve= retains semantically duplicate backend answers;
- =remove= deduplicates using canonical normalized answer identity;
- =canonical= sorts normalized answers by the StarLang canonical term/value ordering defined for the query profile;
- =unspecified= does not promise backend-independent answer order;
- no source program may rely on native answer order unless a stronger profile explicitly promises it.

The adapter MAY stream internally. The language result is bounded by the materialized budget.

** =exists?=

Grammar:

#+begin_example
(exists? <named-operation>
  (<parameter> <expression>)
  ...)
#+end_example

Semantics:

- returns true after the first normalized solution;
- returns false on normal logical failure;
- cancels/closes remaining enumeration for that operation;
- is not equivalent to working-memory =absent=;
- is not an exception-catching construct.

** =explain=

Grammar:

#+begin_example
(explain <result-or-conclusion-ref>)
#+end_example

Semantics:

- returns a normalized proof/derivation record when the active package/profile provides it;
- MUST NOT synthesize missing native proof steps;
- if explanation is required by the plan but unavailable, materialization MUST fail;
- if explanation is optional and unavailable, runtime returns =logic-proof-unavailable= rather than fabricated detail.

* Profiled Source Operations

These are valid only when the materialized semantic profile explicitly permits them.

** Relational conditions

#+begin_example
unify
notProvable
different
#+end_example

=notProvable= means negation as failure under the declared relational query semantics. It MUST NOT be lowered from production =absent=.

** Prolog dynamic-database operations

#+begin_example
assert-clause!
retract-clause!
retract-clauses!
abolish-predicate!
inspect-clause
#+end_example

=assert-clause!= SHALL require an explicit position child:

#+begin_src lisp
(assert-clause!
  (clause ...)
  (position front))
#+end_src

or:

#+begin_src lisp
(assert-clause!
  (clause ...)
  (position back))
#+end_src

These are compiler-owned clause ASTs, never raw strings.

They require =star.logic.prolog-db/1=.

** SWI transactional operations

#+begin_example
with-logic-transaction
with-logic-snapshot
#+end_example

They require the matching profiles.

=with-logic-transaction= MUST specify commit/rollback behavior in the IR. It MUST NOT silently degrade to sequential =assert!=/=retract!=.

=with-logic-snapshot= MUST discard its local dynamic-database changes.

** Tabled operations

Tabling configuration SHOULD normally be package/compiler metadata rather than arbitrary runtime mutation.

If source-level tabling control is added, it MUST be a compiler directive/profiled declaration, not an unrestricted forwarding of SWI directives.

** Production operations

#+begin_example
run-rules
halt-rules!
agenda
focus!
focus-stack
contexts
facts
rules
dependencies
partial-matches
modify-fact!
reset-working-memory!
#+end_example

These require =star.logic.production/1= or =star.logic.production-introspection/1= as appropriate.

=modify-fact!= is not an alias for portable retract+assert. It preserves the exact production-system working-memory modification semantics defined by its profile.

=run-rules= MUST accept a materialized firing/budget limit and has a defined terminal outcome of quiescent, halted, timedOut, or resourceLimited.

** Belief operations

#+begin_example
belief
belief-evidence
#+end_example

The inference package owns evidence combination. StarLang source SHALL NOT expose a generic =combine-belief!= whose mathematics changes by backend.

A result's belief value MUST carry its algebra/profile identity.

* Denied Portable Operations

The following are denied as portable =star.logic.api/1= operations:

#+begin_example
call
cut!
consult
reconsult
eval-prolog
eval-lisp
native-handle
native-clause-ref
native-rete-node
native-engine
#+end_example

Rationale:

- =call= on arbitrary data would bypass the named-operation registry;
- cut changes Prolog control semantics and has no production-system equivalent;
- consult/reconsult introduce ambient file/module loading and executable package mutation;
- eval escape hatches violate the closed source model;
- native handles destroy replay/serialization/ownership boundaries.

A backend adapter MAY internally use equivalent native features. They are not source/runtime public contract.

* Backend Selection Interaction

Source backend policy is owned by STAR-LANG-RESEARCH-026 and uses the compiler-only form:

#+begin_src lisp
(pragma :backend :auto)
(pragma :backend :lisa)
(pragma :backend :swi-prolog)
(pragma :backend :n-prolog)
#+end_src

This API specification does not add a second selector.

For every logic-bearing operation:

1. compile the operation and derive required semantic profiles;
2. combine inherited pragma requirements;
3. resolve package/mapping/proof/budget constraints;
4. filter backend descriptors by exact compatibility;
5. apply explicit pin or deterministic =:auto= selection;
6. freeze backend identity into the plan;
7. only then allow runtime session opening.

An explicit backend pin never suppresses an API/profile mismatch.

* Compiler Lowering

Source forms SHALL lower before runtime to closed IR.

Illustrative lowering:

#+begin_src lisp
(assert!
  (risk
    (transactionId transaction-id)
    (level high)))
#+end_src

becomes conceptually:

#+begin_example
logic-fact-delta
  kind          assert
  factType      <qualified risk type ID>
  factId        <compiler/runtime allocated stable ID>
  normalizedFact <typed value tree>
#+end_example

And:

#+begin_src lisp
(solve ownership-path
  (from source-id)
  (to ?target))
#+end_src

becomes:

#+begin_example
logic-operation
  namedOperationId <qualified ownership-path ID>
  operationKind    query-first
  bindings         <typed normalized bindings>
  answerPolicy     first
#+end_example

The runtime never reparses the source forms.

* Relationship to STAR-LANG-RESEARCH-023

This design deliberately does not approve the entire expert-system language surface.

It only hard-locks the runtime/API semantics that expert-system sugar may target.

If 023 later changes the spelling of =rule=, =goal=, =question=, or its enclosing declaration, those forms MUST still lower to the API/IR semantics here or a future explicitly versioned replacement.

This prevents language-sugar review from destabilizing runtime semantics.

* Relationship to Actor Ownership

A mutable logic session SHALL have one runtime owner.

For stateful expert systems, the ExpertSessionActor or its approved replacement owns:

- session lifecycle;
- fact delta sequence;
- pending operations;
- backend lease/worker identity;
- question/answer state;
- proof/conclusion journal linkage;
- cancellation;
- terminal teardown.

Multiple actors MAY issue requests to an owner through typed messages. They MUST NOT concurrently mutate one native engine object directly.

Replay validation compares normalized outputs under the pinned semantic contract.

=:auto= selection evidence is recorded. Replay does not rerun =:auto= and hope it picks the same backend.

* Ordering and Duplicate Semantics

This is hard-locked because Prolog users often accidentally rely on implementation order.

For =star.logic.api/1=:

- =solve= returns the first answer under the selected backend/profile's enumeration semantics;
- =solutions= with =order unspecified= gives no cross-backend order guarantee;
- =solutions= with =order canonical= sorts after normalization using a StarLang-defined canonical ordering;
- duplicates are preserved by default;
- deduplication occurs only when requested;
- production-system conclusion order is not converted into Prolog answer order unless a profile explicitly defines such mapping.

A change to these defaults requires a new API major version.

* Mutation Semantics

Portable =assert!=/=retract!= operate on StarLang session facts.

They do not expose native clause ordering.

Each mutation has a sequence number assigned by the owning session/journal authority. Adapters apply deltas in that order.

If backend mutation succeeds but durable acknowledgement cannot be recorded, recovery follows the runtime journal/idempotency contract. It MUST NOT issue an untracked best-effort replay that can duplicate state.

Canonical source documents remain immutable from logic rules. Derived conclusions and session facts are separate records.

* Cancellation and Limits

Every operation has a materialized budget.

Budget dimensions MAY include:

#+begin_example
wallTime
cpuTime
inferences
answers
memory
ruleFirings
factMutations
proofNodes
#+end_example

A backend descriptor states which dimensions are hard, cooperative, unsupported, or externally enforced.

One backend's “inference count” MUST NOT be treated as an equivalent CPU bound on another backend.

Cancellation strength is recorded by adapter capability. Hard process termination MAY be the final cancellation mechanism for process-isolated backends.

After hard termination, a dirty worker/session MUST NOT be returned to the pool as healthy.

* Security Invariants

1. Untrusted =.star= never enters Common Lisp =READ= or =EVAL=.
2. Raw Prolog source is not accepted by public source/runtime operations.
3. Arbitrary caller-constructed native callable goals are denied.
4. LISA RHS actions are compiler-generated from a closed action vocabulary.
5. Rule/query packages are exact-versioned and digest-locked.
6. Native engine objects never enter normalized IR, actor messages, journals, or proofs.
7. Backend capabilities are deployment/runtime evidence; source pragmas cannot grant them.
8. External HTTP/file/database/process effects remain ordinary StarLang effect/actor work, not hidden logic-rule effects.
9. Unsupported operations fail before mutation.
10. Error codes are normalized; native strings are diagnostics only.

- =starlang-expert-compiler=: source sugar to closed logic/expert IR;
- =starlang-expert-runtime=: actor-owned session orchestration.

No portable package depends outward on a concrete adapter.

* Implementation Order

1. freeze =star.logic.api/1= records, states, and error codes;
2. add fake adapter conformance before real engines;
3. add compiler syntax objects/validators for the portable source operations;
4. add normalized fact-delta/query IR and canonical serialization;
5. implement LISA/SWI/N-Prolog adapters only behind descriptor claims;
6. land per-profile conformance fixtures;
7. integrate =pragma :backend= materialization;
8. integrate expert-system sugar after the runtime contract is stable;
9. add proof/replay acceptance gates;
10. only then consider optional source sugar such as schema-keyword fact constructors.

* Acceptance Gate

This design is approved for implementation. Implementation completion requires all of the following:

- no two systems own the same logic runtime semantics;
- fake adapter passes portable =star.logic.api/1= conformance;
- every real adapter advertises only fixture-proven profiles;
- unsupported profile tests fail before mutation;
- source API goes through the closed reader/compiler;
- normalized IR contains no native engine objects/source;
- =assert!= and =retract!= use stable StarLang fact identity;
- zero answers are distinct from backend failure;
- duplicate/order defaults match this design;
- cancellation/limit terminal states are replay-visible;
- backend selection is pinned before session opening;
- no transparent cross-engine failover exists.

* Footnotes and Glossary

- *=star.logic.api/1=* — Major-versioned public StarLang logic runtime contract.
- *Portable operation* — Operation whose StarLang observable semantics are defined independently of a concrete inference backend.
- *Profiled operation* — Operation legal only when a versioned semantic profile is required by the plan and advertised by the selected adapter.
- *Fact reference* — Stable StarLang identity for one session fact; not a native Prolog clause reference or LISA object.
- *Named operation* — Compiler-declared query/goal/expert entrypoint identified by stable ID.
- *Answer policy* — Contract for cardinality, limits, duplicate handling, and ordering.
- *Logical failure* — Normal completion with no solution.
- *Quiescence* — Production state with no eligible activation remaining.
- *Canonical ordering* — StarLang-defined stable ordering over normalized result values, independent of native enumeration order.
- *Native escape hatch* — Public API accepting raw engine source, host code, or engine-native handles; denied by this design.
