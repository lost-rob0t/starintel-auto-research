* Research Question

How should StarIntel expose one small Model Context Protocol[fn:mcp] information-retrieval surface over self-hosted search, archival crawl/indexing, external search MCPs, and the full StarIntel service without creating a tool explosion, duplicating provider results, or placing autonomous research reasoning inside an MCP tool?

The implementation constraint is library-first Common Lisp[fn:common-lisp]: protocol, client, server, execution-plan, provider, result, provenance, and fusion behavior must live in reusable ASDF systems. The final StarIntel Meta MCP is a consumer package in the same monorepo, not the first place those semantics are implemented.

* Assess

** MCP protocol direction

The released MCP 2026-07-28 revision makes the protocol core stateless, removes the old protocol-level session model, uses per-request metadata, and makes tool discovery cacheable. Streamable HTTP remains a single POST endpoint; the transport requires Origin validation and recommends proper authentication. Long-running operations can use the Tasks extension, where a tool call may return a task handle and clients later get, update, or cancel the task.[fn:mcp-release][fn:mcp-http][fn:mcp-tasks]

This supports a Meta MCP that performs bounded search immediately while materializing deterministic long-running crawl work as MCP tasks.

** SearXNG and YaCy

SearXNG exposes an HTTP search API with JSON output when enabled. It has a native YaCy engine and supports YaCy =search_mode= values =global= and =local=; local mode restricts results to the configured local YaCy instance. SearXNG also has a generic JSON engine suitable for integrating additional HTTP search APIs.[fn:searx-api][fn:searx-yacy][fn:searx-json]

The implication is a clean split:

- SearXNG owns broad metasearch and can include the local YaCy index for search.
- Direct YaCy integration remains useful for crawl/index control because SearXNG is not the crawl control plane.
- Meta must track physical provider identity so a source queried through SearXNG and again through an upstream MCP is not counted as independent corroboration.

** External search MCPs

The official Brave Search MCP exposes web, local/place, image, video, news, LLM-context, and summarization capabilities over STDIO or HTTP.[fn:brave-mcp]

The Exa MCP currently defaults to =web_search_exa= and =web_fetch_exa=, offers a more advanced search tool optionally, and deprecates several older provider-specific tools in favor of the smaller search/fetch surface.[fn:exa-mcp]

The Tavily MCP exposes search, extract, map, and crawl operations and supports a remote MCP endpoint with OAuth or API-key authentication.[fn:tavily-mcp]

These are evidence that Meta should compile semantic requests onto provider capabilities instead of mirroring every upstream tool name into the client-visible surface.

** Common Lisp MCP ecosystem

Current Common Lisp MCP implementations are useful references but do not justify coupling StarIntel to one upstream implementation without a conformance gate.

- =40ants/mcp= provides server-side MCP infrastructure, STDIO and Streamable HTTP, JSON-schema-backed tools, and OpenRPC foundations, while its documented client side remains incomplete and its public roadmap still references older protocol work.[fn:40ants-mcp]
- =cl-ai-project/cl-mcp= is a mature Common Lisp MCP server for REPL/development tooling with STDIO, TCP, and Streamable HTTP, worker isolation, tests, and Nix packaging; its product purpose is a trusted development server rather than a reusable Meta search execution plane.[fn:cl-mcp]
- Other Common Lisp MCP projects demonstrate protocol extraction and server patterns, but the official MCP SDK list for 2026-07-28 does not include Common Lisp.[fn:mcp-sdks]

The appropriate response is not a bespoke one-file server. StarIntel should build reusable Common Lisp protocol/client/server libraries behind conformance fixtures, borrowing upstream code or dependencies where evidence supports it.

** Existing StarIntel boundary

The current StarIntel server already advertises documents, search, targets, views, and a capabilities endpoint. The Meta plane must not learn CouchDB, Clouseau, or other persistence internals directly. A full StarIntel MCP should be the authoritative MCP boundary for StarIntel operations, including authorization and resource scope. Meta consumes that MCP like another capability provider.

* Design Hypothesis

The stable client-visible Meta surface should begin with:

#+begin_example
search(...)
fetch(...)
#+end_example

and add:

#+begin_example
crawl(...)
#+end_example

after bounded task semantics and crawl policy are implemented.

=research(...)= is deliberately excluded. Research requires iterative reasoning, branch selection, gap analysis, evidence review, and stopping criteria; that belongs to a future StarIntel Agent exposed through Agent2Agent[fn:a2a]. A2A 1.0 models remote agents through Agent Cards, stateful Tasks, Messages, and output Artifacts, and explicitly separates task outputs from conversational messages.[fn:a2a-spec]

The future StarIntel Agent can use both Meta MCP and the full StarIntel MCP:

#+begin_example
StarIntel A2A Agent
  -> Meta MCP: search / fetch / crawl
  -> StarIntel MCP: full authorized platform abilities
#+end_example

* Attack

** Tool explosion

Directly re-exporting every upstream MCP produces provider-coupled tool names and increases model context. It also makes adding or removing a backend a client-visible breaking change.

Countermeasure: expose semantic Meta tools and keep provider capabilities internal.

** False corroboration

Calling Brave through SearXNG and Brave MCP separately can return the same underlying source family twice. The same problem applies to YaCy if it is searched both through SearXNG and directly.

Countermeasure: normalized results must distinguish adapter, physical provider/origin, source URL or document identity, retrieval time, and content hash. Fusion must deduplicate by source identity before confidence or ranking logic.

** Confused deputy

If Meta receives broad StarIntel credentials and then accepts a narrower caller request, it can accidentally act with more authority than the caller intended.

Countermeasure: the full StarIntel MCP remains authoritative for capability and dataset/resource scope. Meta must propagate or exchange caller authority rather than translating =scope=intel= into unrestricted service authority.

** God-service drift

Once Meta can call StarIntel MCP, there is pressure to expose create, mutate, dispatch, delete, and ingest operations through Meta.

Countermeasure: Meta remains an information execution plane. Full StarIntel actions stay on StarIntel MCP. The future A2A agent may compose both services when an autonomous task legitimately needs them.

** Crawl ambiguity

Crawl can mean temporary traversal, archival indexing, or canonical intelligence ingestion.

Countermeasure: define crawl as bounded traversal/indexing only. Canonical StarIntel ingest remains a separate StarIntel operation. A crawl may produce references or artifacts suitable for later ingest but must not silently promote data into StarIntel.

** Library fragmentation

Implementing protocol parsing, provider adapters, result normalization, and ranking directly inside =starintel-meta-mcp= would make the final package unusable as general Common Lisp LLM tooling.

Countermeasure: every stable semantic boundary becomes a reusable ASDF system first; the application package wires them together.

* Recommend

Proceed to design review with the following boundaries:

1. Build reusable Common Lisp libraries for MCP protocol/types, MCP client, MCP server, capability/provider registration, execution-plan representation and execution, normalized search results/provenance, fusion/deduplication, HTTP provider adapters, and MCP-provider adapters.
2. Keep provider selection deterministic and capability-based initially. Do not introduce Prolog-RLM or an LLM planner into the execution plane without later evidence that ordinary code is insufficient.
3. Treat SearXNG as the broad metasearch front end and search the local YaCy index through SearXNG when appropriate; use a direct YaCy adapter for crawl/index operations.
4. Treat Brave, Exa, Tavily, and future MCPs as capability providers. Track physical provider identity independently from adapter identity.
5. Build the full StarIntel MCP as the authoritative platform interface; Meta calls it rather than bypassing it.
6. Start Meta with =search= and =fetch=. Add =crawl= as a bounded MCP Task-capable primitive after the execution/task contract is proven.
7. Reserve =research= for the future StarIntel A2A agent, which can compose Meta MCP and StarIntel MCP and return research outputs as A2A Artifacts.
8. Keep infrastructure placement, network topology, credentials, and deployment-specific routing out of this public design. Those details belong in downstream infrastructure RAGE work after design approval.

* Decide

Research decision: advance =STAR-RESEARCH-PIPELINE-005 StarIntel Meta MCP Execution Plane= to operator review. This is a research recommendation, not implementation approval.

The design must preserve the library-first rule: the final Meta MCP package contains composition and configuration only; reusable MCP and LLM-tooling semantics live in separate Common Lisp ASDF systems in the same monorepo.

* Footnotes and Glossary

[fn:mcp] Model Context Protocol, or MCP: A protocol for exposing model-controlled tools, resources, and related capabilities through standardized client/server messages.

[fn:common-lisp] Common Lisp: The approved implementation language for the reusable StarIntel runtime libraries in this design track.

[fn:a2a] Agent2Agent, or A2A: An open protocol for interoperable remote agents that discover skills and exchange tasks, messages, status, and artifacts.

[fn:mcp-release] MCP 2026-07-28 release material describing the stateless protocol core, cacheable discovery, authorization changes, and Tasks extension.

[fn:mcp-http] Streamable HTTP: The MCP remote transport using a single HTTP endpoint with one POST per request and request-scoped JSON or SSE responses.

[fn:mcp-tasks] MCP Tasks extension: An extension allowing a tool call to materialize as a durable task that can be polled, updated, or cancelled.

[fn:searx-api] SearXNG Search API: The HTTP search interface that can return JSON, CSV, or RSS when enabled by server configuration.

[fn:searx-yacy] SearXNG YaCy engine: The SearXNG backend adapter supporting local or global YaCy search modes.

[fn:searx-json] SearXNG JSON engine: A configurable adapter for external JSON search APIs.

[fn:brave-mcp] Brave Search MCP: Brave's official MCP server exposing several Brave Search API capability classes.

[fn:exa-mcp] Exa MCP: Exa's MCP server exposing web search, fetch, and optional advanced search capabilities.

[fn:tavily-mcp] Tavily MCP: Tavily's MCP server exposing search, extraction, site mapping, and crawling.

[fn:40ants-mcp] 40ANTS MCP: A Common Lisp MCP framework using OpenRPC with server transports and tool registration.

[fn:cl-mcp] cl-ai-project/cl-mcp: A Common Lisp MCP development server with multiple transports and isolated SBCL workers.

[fn:mcp-sdks] MCP SDK list: The official MCP SDK tier list for the current protocol release; Common Lisp is not currently an official SDK language.

[fn:a2a-spec] A2A 1.0 specification: The released Agent2Agent protocol model defining Agent Cards, stateful Tasks, Messages, Parts, Artifacts, streaming, and discovery.
