* Decision

StarLang SHALL add a backend-neutral =star-logic= layer with exactly three initial concrete inference backend IDs:

#+begin_example
lisa
swi-prolog
n-prolog
#+end_example

StarLang source SHALL support =:backend auto= or an explicit pin to one of those IDs.

StarLang SHALL also add =expert-system= source sugar for typed facts, rules, goals, questions, conclusions, explanations, and optional uncertainty. Expert sugar SHALL lower completely into closed compiler-owned IR before execution. No StarLang source form may embed raw LISA/Common Lisp code, raw Prolog source, a native engine handle, or an unrestricted executable goal.

The selected concrete backend SHALL be resolved before execution and SHALL be immutable for the materialized run plan. Runtime recovery may move work to an equivalent instance of that same pinned backend/build contract; it SHALL NOT silently change engine type.

* Non-Goals

This design does not:

- make LISA, SWI-Prolog, and N-Prolog universally equivalent;
- replace STAR-LANG-006 package extraction;
- implement a new Prolog engine;
- immediately fork/rewrite LISA into =star-rules=;
- expose arbitrary Prolog/Lisp snippets in =.star=;
- make inference engines responsible for HTTP/filesystem/database effects;
- define defeasible/default logic;
- define an unrestricted metaprogramming language for expert rules;
- claim N-Prolog supports SWI tabled semantics;
- claim LISA is always faster than Prolog.

* Architectural Invariants

1. =starlang-compiler= remains the sole implementation of StarLang source parsing and semantic compilation.
2. Untrusted =.star= source never enters Common Lisp =READ= or =EVAL=.
3. Engine-native source or runtime objects never enter normalized IR.
4. Backend selection is deterministic over explicit plan inputs.
5. Explicit backend pins cannot override semantic capability checks.
6. A materialized plan contains exactly one backend ID.
7. Runtime load affects instance selection only, never engine semantics.
8. Canonical source documents are never mutated by an inference backend.
9. Derived conclusions carry stable justification identity when explanation is required.
10. Questions leave the inference engine through a typed question port.
11. Rule/query packages are digest-locked executable artifacts.
12. Backend migration is an explicit comparison run, not transparent failover.
13. Direct/fake runtime tests work without LISA, SWI-Prolog, or N-Prolog installed.
14. Final ASDF systems do not depend on =starlang-prototype=.

** =star-logic-protocol=

Owns:

- stable backend IDs;
- adapter protocol generics;
- engine-neutral conditions;
- operation/session state enums;
- semantic profile identifiers.

Dependencies: portable Common Lisp utilities only.

** =star-logic-types=

Owns:

- backend descriptors;
- backend policy values;
- logic usage records;
- normalized results;
- normalized fact deltas;
- package/mapping identities.

It does not own parser syntax.

** =star-logic-capabilities=

Owns capability vocabulary, compatibility matching, deterministic backend filtering, and selection-policy data.

** =star-logic-packages=

Owns resolved package manifest structures and exact digest/version compatibility checks. It never evaluates package source.

** =star-logic-mappings=

Owns engine-neutral fact mapping records and mapping validation.

** =star-logic-proofs=

Owns =star.logic.derivation/1= normalized proof records and validators.

** =star-logic-budget=

Owns semantic budget reservation/debit records and adapter limit capability declarations.

** =star-logic-replay=

Owns backend-selection events, normalized operation terminal records, verification comparison, and migration comparison records.

** Adapter systems

Each adapter system owns all native-engine integration and depends inward on =star-logic-*= portable systems.

No portable system depends on an adapter.

** =starlang-expert-ir=

Owns expert-system IR records and canonical JSON schema declarations. It depends on portable StarLang schema/type IDs and =star-logic-types= but not on engine adapters.

** =starlang-expert-compiler=

Owns expert sugar parsing/expansion validation, binding/type analysis, semantic-profile derivation, and lowering to expert/logic IR.

It is syntax/source-aware and belongs in the compiler layer.

** =starlang-expert-runtime=

Owns ExpertSessionActor state machine, question port, conclusion store, session journal integration, backend lease coordination, and proof normalization orchestration.

It does not parse =.star= source.

* Variable and Binding Rules

1. Source rule variables use the =?name= convention.
2. Every variable is introduced before use.
3. One variable has one static type in one rule/goal/question trigger.
4. Rule-local variables cannot escape except through typed action fields.
5. Nested rebinding/shadowing is rejected in v1.
6. Compiler emits stable binding IDs.
7. Backend lowering maps binding IDs privately.

* Negation Contract

The compiler SHALL distinguish:

#+begin_example
(absent PATTERN)
(notProvable QUERY)
(different LEFT RIGHT)
(contradicts PROPOSITION)
#+end_example

=absent= requires a semantic profile with working-memory absence semantics.

=notProvable= requires a profile defining closed-world/query negation.

The compiler SHALL reject a construct when the selected/potential backend set cannot support the required semantic profile.

* LISA Adapter

System: =star-logic-adapter-lisa=.

Initial target: maintained LISA version pinned by Nix/ASDF source identity.

Adapter responsibilities:

- create isolated engine/session state;
- install compiler-generated trusted rule artifacts;
- map checked fact values;
- apply ordered deltas;
- run/walk engine under budgets;
- observe activations/firings/conclusions;
- normalize explanation events;
- reset/close session;
- report exact capabilities.

Prohibitions:

- no arbitrary =eval= of StarLang-supplied forms;
- no arbitrary method/function calls from rule RHS;
- no global shared expert working memory across sessions;
- no unsupported claim that LISA implements SWI tabled semantics.

Performance promotion gate:

The adapter may be functionally supported before being an =auto= default for large workloads. =auto= routing to LISA for high-volume production rules requires benchmark records satisfying LISA-RESEARCH-001 gates.

* SWI-Prolog Adapter

System: =star-logic-adapter-swi=.

Phase-one transport: SWI MQI over local Unix-domain socket where supported.

Adapter responsibilities:

- launch exact pinned SWI worker/saved state;
- authenticate MQI connection;
- perform capability/version handshake;
- expose only StarIntel-owned wrapper predicates;
- load digest-locked packages;
- map typed facts/parameters;
- stream normalized answers;
- enforce timeout/answer/output limits;
- optionally use inference limits as one logical-work dimension;
- cancel cooperatively then escalate to connection/process termination;
- normalize proof-carrying query results;
- reset or discard workers according to isolation class.

No user-selected arbitrary module/predicate indicator may cross MQI.

* N-Prolog Adapter

System: =star-logic-adapter-nprolog=.

Phase-one transport: child process with StarIntel-owned framed request/response wrapper.

Responsibilities:

- launch exact pinned =npl= binary;
- record binary hash/version;
- load exact bootstrap/rule package;
- configure JSON/string mode deterministically;
- one active query per worker initially;
- normalize answers/failure/errors;
- terminate worker for hard cancellation when necessary;
- discard killed/unclean workers;
- advertise only fixture-proven capabilities.

No transparent fallback from SWI-specific packages.

* Fake Adapter

System: =star-logic-testing= SHALL provide an engine-free fake adapter.

It supports deterministic fixture scripts such as:

#+begin_src lisp

* Replay

Recorded session data SHALL be sufficient to:

- restore source/session/question facts in logical order;
- reproduce backend selection identity;
- rerun the same pinned backend/package in verify mode;
- compare normalized conclusions/proofs;
- replay question answers without asking the external question port again;
- create an explicit migration run against a different backend.

Question prompt presentation changes do not change logical replay if question ID, parameters, answer schema, and returned answer remain identical.

* Security Invariants

1. Expert and logic packages are executable artifacts and require exact digest identity.
2. The compiler generates backend artifacts; untrusted source cannot supply backend artifact bytes directly.
3. Prolog adapter calls named wrapper operations only.
4. LISA adapter actions come from a closed action IR only.
5. File/network/process/FFI/database effects are absent from expert rule actions.
6. Question answers are schema-validated before becoming facts.
7. Prompts cannot inject executable engine syntax.
8. Backend environment contains minimum necessary variables/files.
9. Rule/query package output is size-bounded.
10. Proof data is bounded and validated.
11. Dataset/case/session scope is enforced in fact projection.
12. Secrets do not enter packages, proofs, journals, or generated fixtures.

* Static Negative Tests

Required failures:

- unknown backend ID;
- pinning LISA for tabled-only profile;
- pinning N-Prolog for SWI-only package;
- using salience in relational-only profile;
- unbound rule variable;
- mismatched variable type;

* Migration From STAR-LANG-RESEARCH-021

STAR-LANG-RESEARCH-021 remains valid as the parent architecture: one =star-logic= semantic boundary, engine-neutral =logic-call= IR, capability routing, proof normalization, replay pinning, and no native engine objects.

This design refines it in two places:

1. SWI-Prolog and N-Prolog become separate public backend identities even though both may use shared Prolog protocol/term infrastructure.
2. A first-class =expert-system= source layer is added above =star-logic=.

Implementation SHOULD reuse shared =star-prolog= process/query infrastructure where available rather than duplicating it inside StarLang.

* Interaction With STAR-LANG-006

STAR-LANG-007 SHALL NOT create final compiler/runtime packages that depend back on =starlang-prototype=.

If logic implementation begins before full prototype extraction completes:

- portable =star-logic-*= systems may land when their dependencies are final-owned;
- compiler integration waits for the relevant final compiler ownership or uses a thin compatibility forwarder with one-authority semantics;
- new engine adapters live only in final adapter systems;
- no second logic implementation is added under =prototype/=.

* Footnotes and Glossary

- *Adapter* — Final ASDF system that translates portable =star-logic= operations into one native inference engine and normalizes results back into portable records.
- *Backend pin* — Explicit selection of one concrete engine runtime in source/deployment policy; still subject to semantic validation.
- *ExpertSessionActor* — Single actor owner of one interactive expert session, including ordered fact changes, goals, questions, conclusions, budget, and journal state.
- *Question port* — Typed runtime effect interface for requesting missing expert information from an external participant without coupling the inference backend to UI/LLM/operator I/O.
- *Selection evidence* — Machine-readable record showing candidates, rejection reasons, selected backend, and versioned policy used during materialization.
- *Engine artifact* — Trusted compiler-generated LISA/Prolog package consumed by an adapter; not direct StarLang source.
- *One-authority migration* — STAR-LANG-006 invariant that a migrated behavior has one implementation owner, with prototype code reduced to compatibility forwarding rather than duplicated logic.
