* Research Question

Can the maintained Common Lisp LISA production-rule engine be extended into the correct high-performance incremental rule backend for StarIntel, and what source-level changes are required before it should be selected by Star-Lang?

* Scope

This research evaluates the maintained =youngde811/Lisa= fork at commit =ae3715d74548e451bb08b432c5d25ec93e2a02c1=. It focuses on the RETE matcher, fact update path, agenda, truth maintenance, belief hooks, actor integration, persistence, explanations, and measured allocation behavior.

This is not a proposal to replace Prolog with LISA. It determines the workloads where an improved LISA-derived runtime can outperform a process-isolated Prolog query backend while preserving explicit semantics and replay.

* Current LISA Strengths

The maintained fork already provides:

- Common Lisp and CLOS-native fact templates;
- forward chaining;
- alpha and beta RETE nodes;
- shared network nodes between rules;
- negative, existential, and test patterns;
- salience and depth-first or breadth-first conflict strategies;
- logical dependencies and automatic retraction;
- pluggable belief-system hooks;
- rule tracing, partial-match inspection, and reset facilities;
- dynamic rule addition and removal;
- active maintenance and SBCL profiling artifacts.

These features make LISA a useful source base. They do not make its current matcher suitable for high-volume StarIntel monitoring.

* Current Performance Evidence

The repository includes two SBCL profiles of =(run-mab 500)=, the Monkey-and-Bananas production-rule workload.

| Profile | Real time | Run time | Bytes allocated |
|---+---+---+---|
| baseline | 3.297 seconds | 1.777990 seconds | 2,348,043,312 |
| inline experiment | 3.729 seconds | 1.649148 seconds | 2,347,738,656 |

The inline experiment changes:

- run CPU time: approximately 7.25% lower;
- wall time: approximately 13.10% higher;
- total allocation: approximately 0.013% lower.

The allocation reduction is effectively zero. The optimization moved work between functions but did not change the fundamental cost model.

In the baseline profile, =TEST-TOKENS= accounts for approximately 1.30 seconds and 1.95 GB allocated over 2,611,500 calls. In the inline profile, =TEST-TOKENS= itself drops to approximately 0.63 seconds and 161 MB, but token combination, remembering, forgetting, and add/remove token construction inherit the cost.

Conclusion: additional inlining and declarations are not the next performance step. The matcher must change its data representation, indexing, update semantics, and propagation strategy.

* Source-Level Bottlenecks

** Token replication

The reference RETE compiler calls =replicate-token= when entering join networks from both left and right inputs. This creates copied token structures across partial-match paths.

The profile confirms that token copying, stack manipulation, token combination, hash-key generation, and memory bookkeeping dominate execution.

** Broadcast to root nodes

Every fact add, remove, or reset loops across every root node and sends a token. Root-level class tests reduce downstream work, but the ingress path still broadcasts rather than routing directly by compiled fact type and discriminator.

** Full retract and assert on modify

=modify-fact= performs:

1. retract the complete fact;
2. mutate all requested slots;
3. assert the complete fact again.

The engine does not compute a changed-slot mask. A modification to one irrelevant slot invalidates every partial match involving the fact.

** Eager propagation

Current LISA follows classic eager RETE behavior. Insert, update, and delete operations immediately produce and remove partial matches across all affected rules. This is wasteful when only a small subset of rules can become activatable or when many rules never fire.

Modern Drools replaced this behavior with Phreak, which uses lazy evaluation, node/segment/rule memories, linking, set-oriented propagation, and isolated rule evaluation for improved large-system scalability.

** Agenda lookup

Activations are stored in a heap, but lookup and collection operations use predicate scans over heap contents. Cancellation or deduplication of a known activation should use a direct activation index.

** Truth-maintenance representation

The current TMS maps a dependency set to a list of dependent facts and retracts those facts when the dependency is removed. It does not retain a first-class justification graph, alternative justifications, assumptions, contradiction environments, or an explanation-oriented derivation record.

** Global and dynamic execution state

LISA uses dynamic variables around rule execution and RETE state. A StarIntel deployment requires explicit engine/session ownership and actor isolation. A rule session cannot depend on ambient global focus, context, belief system, or tracing state.

* Recommended Fork

Create a StarIntel-maintained fork or compatibility layer named =star-rules=. Preserve LISA rule-language compatibility where practical, but treat the matcher as a new versioned runtime rather than claiming a transparent performance patch.

* Correct Matching Model

Do not preserve classic eager RETE as the only execution mode. Implement a hybrid delta matcher inspired by RETE/UL, TREAT, LEAPS, collection-oriented match, and Phreak.

The first implementation should retain alpha and beta memories but add:

- typed ingress routing;
- indexed beta memories;
- immutable compact tuple records;
- changed-slot-aware updates;
- batched insert/update/delete propagation;
- segment and rule linking;
- lazy evaluation for inactive rules;
- isolated rule evaluation;
- explicit yield and budget points.

Call this implementation model =Rete-Delta= in StarIntel documents until its semantics and name are frozen.

* Priority Zero Performance Work

** Compact immutable tuples

Replace copied token stacks with compact immutable partial-match tuples.

#+begin_src lisp
(defstruct (match-tuple
            (:constructor make-match-tuple
                (id parent-id fact-id binding-vector hash)))
  (id 0 :type fixnum)
  (parent-id 0 :type fixnum)
  (fact-id 0 :type fixnum)
  (binding-vector #() :type simple-vector)
  (hash 0 :type fixnum))
#+end_src

A tuple references its parent and one fact rather than copying the entire matched-fact sequence. Materialization occurs only for rule firing, proof output, or diagnostics.

Required consequences:

- hash computed once;
- structural sharing across successor nodes;
- tuple IDs usable as stable activation keys;
- slab or arena allocation possible per session;
- no generic list traversal in the hot join path.

** Indexed alpha ingress

Compile a fact-router key from template/class and selective constant tests.

#+begin_example
(template-id, discriminator-slot, discriminator-value) -> alpha node vector
#+end_example

An asserted fact visits only candidate alpha paths. Generic predicate tests remain supported after indexed filters.

** Indexed beta memories

Each join node declares its join key during compilation. Left and right memories maintain hash indexes by normalized join value.

#+begin_src lisp
(defstruct beta-memory
  left-by-key
  right-by-key
  tuple-store
  cardinality
  selectivity-stats)
#+end_src

A right insertion probes only matching left tuples. A left insertion probes only matching right tuples. Non-indexable predicates use an explicit fallback and emit a performance diagnostic.

** Slot-aware modification

Facts are versioned immutable values with stable fact IDs.

#+begin_src lisp
(defstruct fact-version
  fact-id
  version
  template-id
  values
  changed-slots
  provenance)
#+end_src

The compiler records which slots every alpha test and beta join reads. Updating a fact computes a changed-slot bitmap. Nodes whose read set does not intersect the changed set retain their matches.

This replaces unconditional retract-plus-assert.

** Batched delta propagation

Represent changes as sets:

#+begin_src lisp
(defstruct delta-batch
  inserted
  updated-before
  updated-after
  deleted
  sequence
  checkpoint-id)
#+end_src

Nodes consume and emit batches. Duplicate additions and removals are collapsed before entering downstream nodes. Batches provide natural actor mailbox units and reduce function-call overhead.

** Segment and rule linking

Compile the beta graph into segments. A segment records which required inputs are populated. A rule is linked only when all mandatory segments can produce a match.

Unlinked rules receive queued deltas but are not fully evaluated. The agenda selects a linked rule goal, evaluates its segments, and can pause at a budget or actor-yield point.

This directly attacks eager RETE churn in large rule sets.

** Direct activation index

Maintain both:

- a heap or calendar queue ordered by salience and deterministic tie breakers;
- a hash index from =(rule-id, tuple-id)= to activation.

Removal, refraction checks, and duplicate suppression become constant-time expected operations without scanning the heap.

* Priority One Feature Work

** Truth maintenance and explanations

Replace dependency-set lists with justification objects.

#+begin_src lisp
(defstruct justification
  id
  conclusion-fact-id
  rule-id
  supporting-fact-ids
  supporting-justification-ids
  assumptions
  status
  created-sequence)
#+end_src

Required behavior:

- multiple justifications per conclusion;
- conclusion survives while one valid justification remains;
- recursive invalidation through a dependency graph;
- contradiction records;
- optional JTMS assumptions;
- proof and explanation queries;
- deterministic hash of the normalized justification graph.

ATMS environments are deferred until a real workload requires competing assumption sets. The data model must not block them.

** Rule packages and manifests

Rules are loaded only from digest-locked packages that declare:

- package ID, semantic version, digest, source revision;
- accepted fact schemas;
- emitted conclusion schemas;
- rule IDs and salience;
- required matcher capabilities;
- mutation and truth-maintenance assumptions;
- expected performance profile;
- proof policy;
- deterministic ordering policy;
- fixture and benchmark IDs.

** Compiled network snapshots

Compile rule packages into a serializable engine-neutral network plan plus an SBCL-optimized runtime image.

A snapshot pins:

- rule and mapping digests;
- node graph and IDs;
- join keys;
- slot dependency masks;
- segment topology;
- agenda policy;
- compiler and optimizer versions.

The runtime reconstructs mutable memories from the plan. It never deserializes arbitrary executable Common Lisp objects from an untrusted package.

** Deterministic agenda semantics

Define a total order:

1. agenda/focus group order;
2. salience;
3. activation logical time;
4. rule package and rule ID;
5. tuple identity.

Depth-first and breadth-first become named policies over the same total-order fields. Replay records every fired activation and validates that the next eligible activation matches.

** Rule-session actor

Each active working memory belongs to one actor or managed component.

#+begin_example
StarRulesDomainSupervisor
├── RulePackageRegistryActor
├── RuleSessionSupervisor
│   ├── RuleSessionActor(case-42)
│   └── RuleSessionActor(monitor-news)
├── RuleBudgetLedgerActor
└── RuleMetricsActor
#+end_example

Only the owning actor mutates session state. Parallelism occurs across independent sessions and through pure worker tasks, not concurrent mutation of one RETE graph.

** Persistence and recovery

Persist:

- fact input deltas;
- package and network-plan digests;
- activation selected and fired events;
- emitted fact/conclusion events;
- justification changes;
- budget debits;
- checkpoints;
- terminal state.

Checkpoint state may include compact alpha/beta memories after the event-log implementation is proven. The event journal remains authoritative.

** Observability

Metrics per session, rule, segment, and node:

- input deltas;
- alpha tests and rejects;
- beta probes and matches;
- tuple allocations and live tuple count;
- segment links and unlinks;
- activations created, cancelled, and fired;
- justification nodes;
- retraction cascade depth;
- queue and batch sizes;
- elapsed and CPU time;
- allocated bytes and GC time;
- budget trips.

A hot-node report must identify low-selectivity joins and non-indexable constraints.

* Priority Two Work

- optional TREAT-style execution for rule packages with low temporal redundancy where beta-memory cost exceeds recomputation;
- adaptive choice between stored beta memory and recomputation based on measured cardinality and update/query ratio;
- partitioned rule sessions for independent fact namespaces;
- parallel pure alpha evaluation for large batches;
- persistent cold memories backed by LMDB or another local store;
- native-code specialization of compiled testers after data structures stabilize;
- SIMD equality/range filtering for homogeneous batches where SBCL can prove representations;
- rule-package migration with side-by-side result comparison.

Do not begin with GPU execution, shared mutable parallel RETE, or distributed beta memories. The synchronization and proof costs are not justified before the single-process matcher passes its targets.

* Belief and Uncertainty Model

Keep uncertainty outside the hot match identity unless a rule explicitly matches on it.

The current belief protocol is useful, but belief recomputation must not be an implicit side effect of every token operation. A conclusion carries one or more evidence/justification records; a separate pluggable algebra computes certainty factors, Dempster-Shafer values, probabilistic scores, or domain-specific confidence.

Each algebra declares:

- combination operation;
- identity and absorbing values;
- update and retraction behavior;
- determinism;
- numeric precision;
- explanation contribution.

* Concurrency Model

Correct default:

- one owner actor per rule session;
- immutable input batches;
- no locks in the session hot path;
- process isolation available for untrusted rule packages;
- bounded parallelism across sessions;
- pure compilation and projection workers may run concurrently;
- deterministic sequence numbers define input order.

Attempting to put locks around the current global/dynamic RETE state would preserve its allocation problems and add contention.

* Benchmark Suite

The MAB example remains a compatibility benchmark but cannot drive the architecture decision alone.

Required benchmark families:

** B1 Package compilation

- 10, 100, 1,000, and 10,000 rules;
- shared and unshared alpha/beta paths;
- cold compile and cached plan load.

** B2 Initial fact load

- 1,000, 100,000, and 1,000,000 facts;
- high and low alpha selectivity;
- memory and time to quiescence.

** B3 Selective joins

- indexed equality joins with 1:1 and 1:many cardinality;
- range and predicate joins;
- verify expected probe counts.

** B4 Cross-product stress

- deliberately low-selectivity joins;
- enforce tuple and output budgets;
- report hot nodes rather than exhausting memory.

** B5 One-slot modification

- change an unused slot;
- change an alpha-index slot;
- change a beta-join slot;
- compare full retract/assert with slot-delta invalidation.

** B6 Continuous monitoring

- append-only 100, 1,000, and 10,000 deltas/second;
- p50, p95, p99 time to qualified alert;
- rule sets with 1%, 10%, and 90% linked rules.

** B7 Negation and retraction

- creation and invalidation of negative matches;
- repeated fact disappearance/reappearance;
- truth-maintenance cascades.

** B8 Proof overhead

- disabled, summary, and full justification modes;
- conclusion throughput and proof bytes.

** B9 Actor behavior

- cancellation latency;
- checkpoint time;
- crash recovery;
- independent session scaling.

** B10 Cross-engine semantic fixtures

- implement equivalent nonrecursive rules in =star-rules= and SWI-Prolog;
- compare normalized conclusions and proof sets;
- measure the same fact projection and output validation costs.

* Required Metrics

- p50, p95, and p99 latency;
- facts or deltas per second;
- activations and firings per second;
- alpha tests and beta probes per input;
- tuples allocated and retained per input;
- bytes allocated per input, match, and firing;
- peak RSS;
- GC count and time;
- package compile and load time;
- cancellation and checkpoint latency;
- proof size;
- deterministic replay equality.

Report raw data and confidence intervals. Do not publish only aggregate throughput.

* Performance Gates

The redesigned engine is eligible for Star-Lang =:incremental-forward-chaining= only when all of these hold on the reference monitoring workload:

1. one-slot updates do not execute unconditional full retract-plus-assert;
2. an update to a slot unused by any rule produces no beta-memory churn;
3. indexed equality joins perform expected constant-time memory probes per matching bucket rather than scans;
4. p99 qualified-alert latency is below 10 ms at the declared reference scale;
5. total allocation is at least 10 times lower than current LISA on the MAB compatibility run;
6. no benchmark relies on disabling proof, budget, or validation requirements that production enables;
7. cancellation completes at the next bounded yield point;
8. two runs from the same snapshot and event sequence produce identical conclusion and proof hashes;
9. one failed rule session cannot corrupt another;
10. the optimized engine is at least 1.5 times faster than SWI-Prolog on the incremental workload after including projection and proof normalization.

If the final gate fails, SWI-Prolog remains the backend even for that workload.

* Comparison with SWI-Prolog

LISA-derived =star-rules= has a potential performance advantage when:

- a working memory remains hot for a long time;
- changes are small relative to total facts;
- many queries are implicit standing rules;
- rule firing and agenda semantics are required;
- avoiding a process/query boundary matters;
- prior partial matches can be reused efficiently.

SWI-Prolog has the advantage when:

- the workload is query driven;
- recursive graph traversal or cyclic relations dominate;
- tabling avoids repeated recursive work;
- constraints or well-founded negation are required;
- large predicates benefit from JITI;
- immutable snapshots are acceptable;
- a mature process-isolated engine is preferable to a new matcher.

SWI incremental tabling invalidates affected tables and re-evaluates them on demand. Monotonic tabling can propagate additions without full recomputation for monotonic programs, but its documentation marks the feature experimental and notes limitations around negation and concurrency. =star-rules= should not merely duplicate this functionality; it should focus on standing production rules, deterministic agendas, explicit update masks, and low-latency event deltas.

* Comparison with N-Prolog

N-Prolog's repository benchmark reports approximately 1.7 to 6.8 million logical inferences per second across several microbenchmarks on an older 2.9 GHz i5. These values show that its C interpreter/compiler can execute compact Prolog workloads quickly, but they do not establish production-rule, incremental-update, proof, or actor performance.

N-Prolog remains a compatibility and experimental backend. It is not a substitute for LISA's forward-chaining semantics or SWI-Prolog's mature capability set.

* Implementation Sequence

** Phase 0: Reproducible baseline

- pin LISA commit and SBCL version;
- turn MAB profile into an automated benchmark;
- add synthetic join, update, and retraction benchmarks;
- record allocations and raw samples.

** Phase 1: Representation

- immutable versioned facts;
- compact parent-linked tuples;
- cached tuple hashes;
- direct activation index;
- no semantic changes.

** Phase 2: Indexes and deltas

- typed alpha routing;
- beta join indexes;
- changed-slot masks;
- batched propagation;
- correctness differential tests against current LISA.

** Phase 3: Lazy segments

- segment compilation;
- node/segment/rule memories;
- linking and unlinking;
- set-oriented staged propagation;
- bounded stack-based evaluation.

** Phase 4: Truth maintenance

- first-class justifications;
- multiple supports;
- deterministic explanations;
- retraction cascade tests.

** Phase 5: StarIntel runtime

- actor-owned sessions;
- manifests and package registry;
- budgets and cancellation;
- journal and replay;
- =star-logic.rules= adapter.

** Phase 6: Adaptive model

- TREAT-style recomputation option;
- workload statistics;
- benchmark-backed per-package matcher profile;
- no runtime adaptation that changes a pinned plan.

* Rejected Approaches

** More inlining as the main optimization

Rejected because the existing inline profile barely changes total allocation and worsens observed wall time.

** Keep retract-plus-assert modification

Rejected because StarIntel monitoring will frequently update metadata fields that do not affect most rules.

** Shared mutable parallel RETE

Rejected because it adds locks and nondeterministic ordering to the hottest state. Parallelize across sessions first.

** Replace Prolog entirely

Rejected because recursive query, tabling, constraints, and well-founded semantics are not the same workload as standing production rules.

** Use current LISA as the universal Star-Lang engine

Rejected because its measured allocation behavior and eager update semantics are not acceptable at the intended scale.

* Result

LISA is the correct source base for a specialized Common Lisp production-rule backend, but current LISA is not the correct universal reasoning model. The performance path is structural: compact shared tuples, indexed beta memories, slot-delta updates, batched propagation, lazy segment linking, direct activation indexes, actor-owned sessions, and explicit justification graphs.

After those changes pass the common benchmark gates, =star-rules= should serve low-latency incremental forward chaining. SWI-Prolog remains the default recursive and query engine. N-Prolog remains optional and experimental.
