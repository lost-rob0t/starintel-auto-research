* Question

How should StarIntel reason about solver selection when source actors encounter open-world CAPTCHA and adjacent browser, device, behavioral, proof-of-work, Web Application Firewall, media, puzzle, custom, and unknown challenges?

* Core Research Finding

Do not select one global CAPTCHA provider. Solver selection needs two logically separate stages:

1. *hard eligibility*: reject any actor that cannot satisfy an exact request and policy boundary;
2. *ranking*: compare only eligible actors using deterministic evidence.

The exact final ordering and wire protocol remain design decisions and therefore remain unapproved.

* Candidate Hard-Eligibility Dimensions

Research supports treating these dimensions as non-substitutable constraints before cost optimization:

- authenticated requester and =captcha:solve= authorization;
- target policy and approved purpose;
- provider/solver allowlist;
- issuer, challenge family, variant, and integration version;
- required normalized fields and required result kind;
- result binding: source session, network identity, proxy, cookie, user agent, mobile/app runtime, or other exact context;
- source-session and network fidelity;
- execution class and worst-case disclosure class;
- provider contract state and fixture freshness;
- provider/account health and concurrency;
- deadline feasibility;
- reserved budget ceiling.

There must be no implicit widening from reCAPTCHA v2 to v3, standard hCaptcha to Enterprise, Turnstile to Cloudflare Challenge, token to cookie/proof/coordinates/selections, proxyless to proxy-bound, remote provider to same-session browser execution, automated-only to human-exposure-possible, or unknown to a known issuer.

* Ranking Evidence

The current research supports the following ranking dimensions, but their exact precedence is still a broker-design question:

- explicit operator pin among otherwise eligible actors;
- contract confidence;
- fixture freshness;
- source-context and result-binding fidelity;
- exact-capability downstream acceptance rate;
- provider health;
- available concurrency and request-pacing headroom;
- deadline fit;
- observed cost per downstream accepted result;
- price/cost confidence;
- operator preference and deterministic tie-break.

Cost must remain subordinate to hard context and disclosure eligibility. A cheaper token that cannot be applied in the target's required session/network context is not an alternative.

* Price and Cost Confidence

Provider pricing is not stable enough to compile into the broker. Current research found contradictory price/credit statements inside official provider documentation for more than one provider.

Every runtime cost observation should therefore distinguish:

- =advertisedCost= and its source/retrieval time;
- =configuredReservationCeiling=;
- =providerReportedCharge= when available;
- =actualAccountDebit= when observable;
- =costConfidence=;
- downstream =accepted= / =rejected= / =expired= / =replaced= / =inconclusive= outcome.

When official price evidence conflicts, eligibility can still be researched under a conservative configured ceiling, but low-confidence advertised cost should not win a ranking decision against reliable observed billing.

* Execution and Disclosure Classes

Provider research now requires a worst-case execution/disclosure classification. The exact enum is a pending design choice, but research distinguishes at least:

| Research class | Example | Important implication |
|----------------+---------+-----------------------|
| local automated | local browser/OCR/image/audio actor | no third-party challenge disclosure, but local resource cost and source integration matter |
| remote automated | exact provider capability with no human fallback | approved challenge context leaves the local boundary |
| human exposure possible | provider normally automates but may escalate to humans | target policy must permit possible human exposure before submission |
| human-assisted vendor | worker-backed task service | human disclosure is expected, not exceptional |
| managed browser vendor | provider controls a browser/session workflow | materially wider session/fingerprint/cookie disclosure; separate boundary from ordinary token APIs |
| manual operator | local review queue | local human access, latency, retention, and audit policy required |
| custom first-party | owned-system test hook or explicitly modeled custom solver | bound to named target policy and schema |

Unknown execution or disclosure class is insufficient evidence for automatic provider selection.

* Source-Context and Result-Binding Fidelity

Context fidelity includes whether a solver can preserve:

- same browser session;
- same cookie state;
- same network identity or required caller proxy;
- same user agent;
- mobile application binding;
- Enterprise challenge data;
- bounded page/challenge data;
- target-specific action and challenge instance.

Result binding must be explicit. Examples from current research include:

- ordinary token result;
- token requiring source-consistent network identity;
- =cf_clearance= cookie result;
- DataDome special cookies requiring application back into the browser;
- proof-of-work result;
- coordinates/selections requiring source-side interaction;
- managed-browser state that cannot safely be represented as a generic token.

A local browser actor may be the only eligible class for some same-session challenges even when external providers advertise the issuer.

* Current Provider-Class Research Seeds

These are not provider winners and do not activate capabilities.

| Challenge/context | Research candidate classes |
|-------------------+----------------------------|
| hCaptcha token | local browser for session-bound cases; exact NoneCap or NopeCHA capability when context permits; 2Captcha currently =unsupported= for hCaptcha on official API evidence |
| reCAPTCHA v2/v3/Enterprise | local browser where binding requires it; exact NopeCHA, 2Captcha, Anti-Captcha, CapSolver, or CapMonster rows after fixture validation |
| Turnstile standalone | local browser or exact Turnstile provider task |
| Cloudflare Challenge Platform | isolated local browser or exact provider capability that returns the required token/cookie with matching context |
| DataDome | browser/context-preserving actor or exact provider task with caller-proxy/user-agent/cookie contract |
| AWS WAF | isolated browser or exact proxy/proxyless AWS WAF provider row |
| Arkose/GeeTest puzzle | browser/local recognition or exact documented provider task; do not infer Arkose support from a provider marketing page when its current exact support index omits it |
| text/image/audio | local recognition first when exact; remote recognition/worker task only when disclosure permits |
| unknown/custom | custom first-party or manual operator path; no generic provider coercion |

* Acceptance and Reliability Metrics

Metrics need segmentation by exact capability, source-runtime class, target-policy class, and result binding:

- provider task completion;
- downstream =accepted=;
- downstream =rejected=;
- =expired=, =replaced=, and =inconclusive=;
- p50/p95 latency;
- provider and contract errors;
- rate-limit/backoff incidents;
- ambiguous-charge rate;
- cancellation success;
- provider-reported and observed account cost;
- cost per accepted result;
- result expiry before application;
- redaction conformance.

Provider completion is not target acceptance.

* Fallback Research Constraints

Fallback should never be assumed merely because another provider advertises the same issuer. Research supports requiring:

- a new independently eligible exact capability;
- prior attempt terminality or safe cancellation;
- no blind fallback after ambiguous create when the first provider may already have accepted/billed the task;
- a new attempt identity and budget reservation;
- disclosure count and total cost within policy;
- sufficient deadline remaining;
- equivalent or acceptable result binding;
- complete redacted attempt telemetry.

Whether fallback is disabled by default and the exact state machine remain design decisions.

* Speculative Execution Research Constraints

Concurrent provider attempts multiply cost and disclosure. If a future design allows speculation, it needs separate approval and must bound:

- exact capabilities where speculation is permitted;
- maximum simultaneous solver count;
- total reservation ceiling;
- disclosure authorization for each solver;
- winner selection;
- loser cancellation;
- late-result deletion;
- ambiguous provider-task handling;
- rollback and telemetry.

Speculation is not implied by fallback.

* Test Evidence Required Before Design Approval

- positive/negative exact-match matrix;
- unknown/custom challenge behavior;
- forbidden issuer/family/variant/version/result/context widening;
- source-session/network/proxy/cookie/user-agent/mobile binding cases;
- all capability-state transitions;
- worst-case disclosure-class denials before secret dereference;
- provider pricing contradiction and conservative reservation behavior;
- actual/provider-reported cost reconciliation;
- exact acceptance segmentation;
- deterministic tie scenarios;
- ambiguous create preventing blind retry/fallback;
- late result deletion and cancellation races;
- request pacing/rate-limit behavior;
- no paid provider in continuous integration.

* Footnotes and Glossary

- *Hard eligibility* — All-or-nothing exact constraints that must pass before an actor can be meaningfully compared.
- *Source-context fidelity* — Ability to preserve the source session, network, cookies, user agent, app runtime, challenge instance, and application context.
- *Result binding* — Context that must remain stable for a returned result to work.
- *Cost confidence* — Confidence that advertised/configured price evidence matches current provider billing.
- *Cost per accepted result* — Total exact-capability spend divided by results verified downstream as accepted.
- *Speculative execution* — Concurrent attempts before an earlier attempt becomes fallback-eligible.
