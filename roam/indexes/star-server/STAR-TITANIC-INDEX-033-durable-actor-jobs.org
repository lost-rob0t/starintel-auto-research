* Purpose

This stack revives the 2023 StarIntel =Titanic= concept as a modern durable actor-job protocol without recreating a second broker beside RabbitMQ.

The historical design was already recognizably descended from ZeroMQ's stable Titanic Service Protocol: persistent asynchronous request submission, worker dispatch, retained results, and later client retrieval. Modern StarIntel has enough broker machinery that Titanic can move up one layer and become the durable execution contract.

Sento remains the local actor runtime. Star Router remains the client/cross-process routing boundary. RabbitMQ remains the durable distributed transport. Titanic owns durable *job meaning*.

* V1 Required Semantics

1. stable =job_id= and idempotency scope;
2. durable admission with publisher confirmation/reconciliation;
3. capability queues and bounded worker concurrency;
4. at-least-once delivery with explicit terminal settlement;
5. durable job/attempt journal;
6. typed terminal results and disconnected result lookup;
7. bounded retry with backoff and dead-lettering;
8. cooperative cancellation and absolute deadlines;
9. target lease/fencing integration where manifests require exclusive authority;
10. deterministic fake/model contract tests before Rabbit adapter promotion.

* Explicit Non-Goals

- replacing Sento local actor mailboxes;
- replacing Star Router;
- replacing RabbitMQ in v1;
- promising exactly-once execution;
- reviving the original LMDB-backed proxy literally;
- using Rabbit delivery tags as stable protocol identity;
- putting every high-frequency local actor message through durable storage;
- introducing Temporal or Kafka merely to implement a job queue.

* Suggested Next Design Pass

After review, create a design node covering only the v1 seam:

- =star.titanic/1= schema;
- Common Lisp protocol structs/validators;
- =job-store= interface plus deterministic fake;
- Rabbit durable-admission producer with confirms;
- one capability queue pilot;
- result/status API;
- contract tests from STAR-RESEARCH-036.

Do not start by generalizing every actor or backend.
