* Verified Findings

** =:pinned= is a reserved mailbox mode, not a usable custom shared-dispatcher identity

Current Sento =%message-box-for-dispatcher-id= handles =:pinned= in a =case= before it looks up a named shared dispatcher. Therefore an actor created with =:dispatcher :pinned= receives a =message-box/bt= pinned-thread mailbox. It does not resolve the custom dispatcher registered under the same identifier.

The current StarIntel =(:dispatchers (:pinned ...))= configuration therefore creates a shared dispatcher whose intended application callers cannot select through normal actor creation. Meanwhile each CouchDB/producer agent that requests =:pinned= receives its own pinned mailbox/thread semantics.

Requirement: retire =:pinned= as a custom dispatcher name. Named shared dispatchers must use non-reserved logical IDs.

** A Sento shared dispatcher is already a worker router, and every worker is pinned

Current =disp:make-dispatcher= creates a =shared-dispatcher=. Initialization creates a Sento router and one dispatcher worker per configured worker. Each dispatcher worker is itself created with =:dispatcher :pinned= and therefore owns a thread.

Requirement: every named shared-dispatcher worker count must consume a grant from the process-wide thread-budget authority. Adding dispatchers is not free isolation.

** Dispatcher mailboxes serialize one actor's state but do not promise global arrival order

The canonical Sento audit records that a dispatcher-backed actor has its own mailbox and lock, preventing concurrent state mutation by two workers, while ordering is not guaranteed when submissions arrive concurrently from multiple threads.

Requirement: workload isolation may rely on one-message-at-a-time state access, but ordering-sensitive application contracts require explicit keyed/serialized ownership rather than assuming dispatcher order.

** Current routers are static and selection-poor

The current router supports random, round-robin, or a custom function that receives only routee count. It supports routee addition and stop-all but no message-aware selection, keyed affinity, readiness/health, generation, routee replacement, lifecycle watching, or dynamic pool management.

Requirement: round-robin is sufficient only for stateless equivalent routees. Stateful target/dataset/resource work cannot claim keyed routing through the raw router API. Either StarIntel uses a lifecycle-owned pool manager with an explicit key-to-routee table/hash policy, or the generic Sento managed-router capability must be implemented before that use case.

** Current StarIntel isolation intent is real, but execution classes are conflated

The server already tries to isolate Rabbit publishing and CouchDB access from shared actor work. Issue #35 also identifies control, ingest, storage, Rabbit, target, CPU, and research workloads. The concrete source shows why this matters: target routing, persistence, asynchronous tasks, publication, and normal actor handlers currently share or bypass unrelated executors.

Requirement: define logical workload classes first, then map them to granted runtime executors/dispatchers. Do not create one dispatcher per conceptual label when the workload is absent or when two classes can safely share an executor under the same isolation contract.

* StarIntel Requirements

1. =star.runtime= remains the process lifecycle/composition authority; #35 must not create a second runtime owner.
2. The thread-budget plan from #176/#177 grants capacity. Dispatcher/pool construction consumes those grants and cannot self-size from =*ingest-workers*=.
3. Use explicit non-reserved logical dispatcher IDs. =:pinned= remains only Sento's dedicated-thread mailbox mode.
4. Preserve a small control class whose capacity cannot be consumed by normal data-plane work.
5. Separate blocking storage work from control and latency-sensitive target/lease coordination.
6. Rabbit connection/channel ownership remains on its required owner/reactor boundary; a Rabbit dispatcher class does not authorize arbitrary concurrent channel use.
7. CPU transforms use bounded CPU capacity and cannot borrow reserved control capacity implicitly.
8. Research jobs use bounded execution and remain lower-priority than control/lease/lifecycle work.
9. Stateless equivalent routees may use deterministic round-robin.
10. Stateful/keyed routees require an explicit message-aware affinity owner; raw Sento =router= does not provide this capability.
11. Router/pool membership, generation, health, pressure, dispatcher allocation, and owner component ID must be observable through the runtime/component model.
12. #36 owns queue capacity, ingress admission, overload policy, prefetch and structured overload results. #35 exposes capacity/pressure boundaries needed by #36 but does not duplicate admission policy.
13. #37/#183 owns start/stop/quiesce/drain/reconnect component lifecycle. Dispatchers and managed pools register there rather than owning a second shutdown mechanism.
14. No new StarLang syntax is required for this runtime-internal slice. Future StarLang manifests may name an abstract workload/dispatch policy, but host thread/dispatcher construction remains a Common Lisp runtime effect.

* Proposed Workload Model

Use a closed logical workload class rather than arbitrary dispatcher symbols:

- =platform/control= — lifecycle, component registry, health, pool management, overload decisions.
- =platform/ingest= — document validation/normalization coordination.
- =platform/storage= — blocking CouchDB operations.
- =platform/rabbit= — Rabbit owner/reactor coordination, not concurrent channel sharing.
- =platform/target= — target scheduling, lease coordination, keyed target state.
- =platform/cpu= — bounded CPU-heavy transforms.
- =platform/research= — resumable research coordination.

The runtime may map multiple logical classes to one executor only when an explicit deterministic plan says they share capacity/isolation. A logical class therefore is not automatically one new OS-thread pool.

* Evidence-backed Research Decision

Research is sufficient to design the StarIntel-specific #35 slice. No new generic Sento rewrite is required for the first bounded implementation: StarIntel can first add logical workload classification, explicit non-reserved shared dispatchers, thread-grant consumption, and a stateless managed pool wrapper using existing round-robin routing. Keyed/stateful pools remain blocked until the design provides a real message-aware affinity owner rather than claiming unsupported raw-router behavior.

Implementation authorization remains operator-only.

* RED-First Targets for Design

The first implementation slice should be pure planning/validation, before creating runtime threads:

- a dispatcher plan using reserved ID =:pinned= must be rejected;
- requested dispatcher worker totals must be charged against explicit #177 grants;
- a control workload cannot be assigned to a data-plane-only grant;
- a stateful/keyed pool cannot select =:random= or raw =:round-robin= as its affinity contract;
- deterministic equivalent plans produce identical logical dispatcher/pool assignments.

A later real-runtime RED should saturate a fake/blocking storage routee and prove a control probe still executes on independent granted capacity.

* Unresolved Questions

- Whether current StarIntel should vendor/fork additional generic Sento managed-router behavior or keep the first keyed-affinity owner application-side behind a narrow adapter requires implementation-time source/API review against the exact pinned dependency revision.
- Exact default grant sizes require measurement; research does not choose production worker counts from historical benchmark numbers.
- Least-mailbox-depth routing requires a stable public pressure API and belongs after the basic deterministic topology is proven.

* Footnotes and Glossary

- *Dispatcher* :: A Sento execution pool used by dispatcher-backed actor mailboxes; its workers are pinned actors with OS threads.
- *Pinned mailbox* :: Sento mailbox mode selected by the reserved =:pinned= dispatcher identifier; it owns a dedicated processing thread.
- *Router pool* :: A set of actor routees selected through an explicit routing policy.
- *Keyed affinity* :: Stable routing of messages sharing an application key to the same state owner while that generation is active.
- *Workload class* :: StarIntel logical execution/isolation category that is mapped to runtime capacity by a deterministic plan.
