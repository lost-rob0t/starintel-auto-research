#+title: STAR-PRO-CAPTCHA-003 2Captcha Adapter
#+description: Experimental disabled-by-default StarIntel Pro Actor design for a 2Captcha hCaptcha adapter gated by live contract discovery.
#+status: REVIEW
#+filetags: :starintel:design:starintel-pro-actors:captcha:hcaptcha:2captcha:experimental:

* Decision

Implement the =TwoCaptchaAdapterActor= only as an experimental, disabled-by-default adapter. The generic 2Captcha version-two application-programming-interface[fn:api] is current, but the hCaptcha task contract is not consistently present in the current public navigation. The actor must not advertise an hCaptcha capability until a contract probe succeeds.

This design exists to test provider neutrality and preserve an implementation path. It is not approval to enable the adapter against arbitrary sites.

* Startup Contract Probe

On explicit operator request, the adapter performs a bounded probe against an operator-owned hCaptcha test page or a provider sandbox:

1. submit the configured hCaptcha task type;
2. confirm a provider job identifier is returned;
3. retrieve the terminal result;
4. confirm the token field and optional response-key fields;
5. record a redacted fixture and contract fingerprint;
6. advertise =captcha.hcaptcha.*= only after the probe passes.

The probe has a strict maximum cost and may not run automatically on every startup.

The default candidate task names are configuration values, not trusted constants. Historical names include =HCaptchaTaskProxyless= and =HCaptchaTask=.

* Generic Provider Contract

| Broker operation | 2Captcha operation |
|------------------+---------------------|
| =submitSolve= | =POST /createTask= |
| =pollSolve= | =POST /getTaskResult= |
| =cancelSolve= | unsupported in the researched generic contract |
| =getBalanceOrQuota= | =POST /getBalance= |
| =reportOutcome= | =reportCorrect= or =reportIncorrect= when applicable |
| =healthSnapshot= | balance probe plus local circuit and contract state |

Callbacks are excluded from version one. Polling keeps the inbound server surface closed and makes provider behavior consistent with the other adapters.

* Capability States

The adapter exposes one of these states:

- =disabled=: no probe has passed or the operator disabled the provider;
- =probing=: a bounded contract probe is active;
- =verified=: the configured task and result mapping passed;
- =degraded=: recent provider failures exceed policy thresholds;
- =invalidContract=: provider responses no longer match the verified fixture.

Only =verified= advertises solve capabilities to the broker.

* Submission Mapping

After verification, the adapter maps the broker request to the discovered task object. The expected historical mapping is:

| Broker field | Candidate 2Captcha field |
|--------------+--------------------------|
| =challenge.pageUrl= | =websiteURL= |
| =challenge.siteKey= | =websiteKey= |
| standard or invisible mode | configured task type plus discovered invisible flag where supported |
| enterprise =rqdataRef= | no mapping until explicitly verified |
| proxy reference | configured proxy task fields after verification |

The actor rejects enterprise mode unless the live contract probe proves an =rqdata= field and an accepted enterprise result.

* Result Mapping

The generic provider states are expected to be =processing= and =ready=. On =ready=, the contract fixture identifies the token field. The adapter copies the token directly into the ephemeral secret store[fn:ephemeral-secret-store] and returns only an opaque reference.

Cost, creation time, completion time, provider Internet Protocol address[fn:ip-address], and solve count are normalized when present. Unknown additive fields are ignored after redaction. Missing required verified fields move the adapter to =invalidContract= and stop new routing.

* Error Mapping

The adapter uses the current 2Captcha error table at implementation time. Minimum normalized handling:

- invalid key -> =providerAuthenticationFailed= and open circuit;
- zero balance -> =providerInsufficientBalance= and open circuit;
- unsupported or incorrect task -> =unsupportedChallenge= and mark contract invalid;
- bad proxy -> =providerRejectedRequest=;
- unsolvable challenge -> =providerUnsolvable=;
- request limit -> =providerConcurrencyLimited=;
- network or server failure -> =providerUnavailable=;
- ambiguous create failure -> =ambiguousSubmission=;
- local deadline -> =deadlineExceeded= with =chargePossible= determined conservatively.

* Idempotency and Cancellation

The provider does not expose a documented create idempotency key or cancellation operation in the researched generic contract.

The adapter therefore:

- journals the broker attempt before creation;
- records the provider task identifier immediately;
- attaches duplicate deliveries to the journaled attempt;
- never retries an ambiguous create automatically;
- treats cancellation as local polling cancellation;
- reports =providerCancellationSupported: false=;
- records that a provider charge may still occur.

* Testing

- Startup disabled state.
- Successful and failed contract probes.
- Unsupported-task response causes =invalidContract=.
- Verified response fixture drift disables capability.
- Generic create, processing, ready, balance, and feedback mocks.
- Duplicate and ambiguous submission tests.
- Local cancellation tests.
- Secret and token redaction tests.
- No callback listener tests.
- Opt-in live canary with a one-task ceiling against an operator-owned page.

* Footnotes and Glossary

[fn:ephemeral-secret-store] Ephemeral secret store: A temporary protected store used so sensitive token values are represented in messages only by opaque references.
