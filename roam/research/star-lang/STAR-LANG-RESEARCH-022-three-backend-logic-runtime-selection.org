* Research Question

How should StarLang expose exactly three inference backends—LISA, SWI-Prolog, and N-Prolog—so an author can explicitly select a runtime when needed without sacrificing semantic validation, deterministic replay, safe resource boundaries, or backend-neutral expert-system authoring?

Requested concrete runtime IDs:

#+begin_example
lisa
swi-prolog
n-prolog
#+end_example

The three engines are not semantically interchangeable. A RETE production-rule engine and a Prolog resolution engine differ in conflict resolution, working-memory mutation, negation, answer enumeration, recursion, and proof behavior. StarLang must expose selection without pretending those differences do not exist.

* Executive Decision

Retain the =star-logic= semantic boundary from STAR-LANG-RESEARCH-021 and refine its backend model so the public backend registry contains three stable IDs:

#+begin_example
lisa
swi-prolog
n-prolog
#+end_example

StarLang source may declare one of four policies:

#+begin_example
auto
lisa
swi-prolog
n-prolog
#+end_example

=auto= means deterministic capability-based selection during plan materialization. It does not mean runtime failover between engine types.

Once selected, the concrete backend ID, engine build identity, adapter version, rule/query package digest, fact mapping digest, semantic profile, proof contract, and budget become immutable fields of the executable run plan.

An explicit backend pin is a reproducibility/deployment policy. It never bypasses capability checking. A tabled recursive program pinned to LISA fails before execution unless a future LISA-compatible adapter truthfully advertises the required semantics. A salience/agenda-dependent production system pinned to SWI-Prolog or N-Prolog likewise fails instead of being silently translated into ordinary clauses.

* Current StarLang Boundary

The current StarLang implementation uses a closed source reader and normalized compiler data. This matters because backend selection can safely be source data while native engine objects remain excluded.

Three categories must remain distinct:

| Category | Example | Allowed in source/IR |
|----------+---------+----------------------|
| semantic requirement | recursive query, production agenda, proof | yes |
| backend policy | auto, swi-prolog, lisa | yes |
| native runtime object | Prolog engine handle, LISA network, process/socket | no |

The Common Lisp StarLang implementation remains authoritative. LISA, SWI-Prolog, and N-Prolog are inference dependencies behind adapters; they do not become alternate StarLang implementations.

* Primary-Source Backend Findings

** SWI-Prolog

The official SWI-Prolog Machine Query Interface (MQI) is designed to run SWI-Prolog as a local implementation detail of another language. It launches a dedicated Prolog process, supports local TCP or Unix-domain socket connections, authenticates connections, assigns a consistent Prolog thread per connection, and uses a framed request/response protocol.

SWI-Prolog also supports tabled execution. Tabling memoizes answers and avoids ordinary left-recursive nontermination for tabled predicates. Incremental tabling tracks dependencies between dynamic predicates and tables, invalidates affected tables after changes, and reevaluates them on demand.

SWI provides =call_with_inference_limit/3=. Its own documentation notes that some primitive VM operations and foreign predicates do not contribute proportionally to the inference count, so it is useful as one budget dimension rather than a complete CPU bound.

Research conclusion: SWI-Prolog is the strongest initial general-purpose backend for recursive inference, tabled graph closure, constraints, nondeterministic named queries, and relational expert systems.

** N-Prolog

The current Sasagawa N-Prolog project describes itself as an interpreter/compiler compatible with ARITY/PROLOG and explicitly says it is not ISO Prolog, while implementing most ISO core features needed for its intended educational use.

Its CLP(FD) documentation explicitly says heuristic optimizations are deliberately omitted and that the implementation is primarily intended for interpreter use. Its JSON library provides =term_json/2= conversion and changes string representation while JSON mode is active.

Research conclusion: N-Prolog is valuable as an explicit compatibility and portable-Prolog backend, but it must advertise only fixture-proven capabilities. It is not a transparent replacement for arbitrary SWI-specific packages.

** LISA

The maintained =youngde811/Lisa= source implements a Common Lisp forward-chaining expert-system shell using RETE. Its language implementation exposes =defrule= with salience, context, belief, and auto-focus options, along with assertion, retraction, modification, contexts/focus, agenda inspection, and rule execution. Its maintained MYCIN example demonstrates belief-bearing forward-chaining rules.

The existing LISA-RESEARCH-001 source audit identified allocation and matcher-architecture concerns for high-volume workloads and recommends measured modernization rather than assuming LISA is always the fastest backend.

Research conclusion: LISA is the natural initial production-rule and persistent working-memory expert backend. Functional support and =auto= promotion for large workloads are separate decisions; large-workload routing remains benchmark-gated.

* Semantic Profiles

Backends advertise versioned semantic profiles rather than one vague =logic= capability.

Initial profile vocabulary:

#+begin_example
star.logic.query/1
star.logic.tabled/1
star.logic.constraints/1
star.logic.production/1
star.logic.expert-session/1
star.logic.portable-prolog/1
#+end_example

** =star.logic.query/1=

Defines named query invocation, typed parameter binding, logical failure, answer enumeration/streaming, cancellation, exception normalization, and optional normalized proof output.

Initial preferred backend: SWI-Prolog.

** =star.logic.tabled/1=

Adds tabled recursion and declared well-founded-negation semantics.

Initial backend: SWI-Prolog only.

** =star.logic.constraints/1=

Defines an exact constraint vocabulary and answer contract. Shared names such as CLP(FD) do not imply identical semantics across implementations.

Initial default: SWI-Prolog. N-Prolog may expose a narrower fixture-proven subprofile.

** =star.logic.production/1=

Defines working-memory deltas, rule matching, activation creation, conflict resolution, firing, assertion/retraction, quiescence, and optional truth maintenance.

Initial backend: LISA.

** =star.logic.expert-session/1=

Defines typed facts, goals, questions, conclusions, explanation behavior, uncertainty policy, journal state, and multi-turn consultation. It can be implemented over production or relational semantics only when the package declares a compatible implementation profile.

** =star.logic.portable-prolog/1=

Defines the conservative conformance-tested subset shared by SWI-Prolog and N-Prolog. No engine-specific directive is portable just because both parsers accept similar syntax.

Proposed StarLang forms:

   :capability recursiveGraphQuery)

   :capability recursiveGraphQuery)

#+end_src

These are proposed StarLang forms parsed by the closed reader. They are not Common Lisp reader forms executed by the host.

* Deterministic Selection Algorithm

Selection is pure over explicit inputs.

#+begin_src lisp
(defun select-logic-backend (request registry benchmark-set policy)
  (let* ((by-profile (profile-compatible request registry))
         (by-capability (capability-compatible request by-profile))
         (by-package (package-compatible request by-capability))
         (by-limits (limit-compatible request by-package))
         (by-isolation (isolation-compatible request by-limits))
         (by-pin (apply-explicit-pin request by-isolation)))
    (choose-by-stable-policy request by-pin benchmark-set policy)))
#+end_src

Required order:

1. validate source backend policy;
2. resolve logic/expert package by ID, version, and digest;
3. derive semantic profile and required capabilities;
4. reject incompatible descriptors;
5. reject package/backend mismatches;
6. reject inability to enforce mandatory limits/isolation;
7. apply explicit pin;
8. if =auto=, rank by a versioned stable policy and matching benchmark identity;
9. reject unresolved ties unless policy defines a total order;
10. write machine-readable selection evidence into the plan.

Current machine load is not semantic selection input. Load balancing occurs among equivalent instances of the already-selected backend.

* Initial Default Routing

| Requirement | Default runtime |
|-------------+-----------------|
| recursive graph closure | =swi-prolog= |
| tabled query | =swi-prolog= |
| general named query | =swi-prolog= |
| persistent production rules | =lisa= |
| agenda/salience semantics | =lisa= |
| LISA-compatible belief expert | =lisa=, capability-gated |
| portable Prolog package | =swi-prolog= by default; =n-prolog= when explicitly pinned |
| N-Prolog-specific package | =n-prolog= |

=N-Prolog= is never selected merely because SWI is unavailable. Backend unavailability is an operational failure, not permission to change semantics.

* What =auto= Must Not Mean

=auto= MUST NOT:

- try engines until one returns an answer;
- select the currently least busy engine type;
- switch engine type on timeout;
- compile arbitrary LISA rules into Prolog at runtime;
- weaken proof/budget requirements;
- treat N-Prolog as an SWI fallback;
- alter backend based on answer contents.

It chooses once, records the result, and pins it.

* LISA Adapter

The LISA adapter owns engine/session construction, fact conversion, compiler-generated rule installation, working-memory deltas, focus/agenda policy, rule execution, activation/firing observation, belief hooks when enabled, reset, and teardown.

StarLang never exposes native =defrule=, =assert=, =modify=, or arbitrary Common Lisp expressions. The compiler emits closed expert/rule IR, then a trusted adapter-owned compiler lowers that IR to allowed LISA forms.

One actor owns one mutable LISA working memory. Mutable RETE state is not shared across arbitrary actor threads.

* SWI-Prolog Adapter

The first production SWI adapter should use MQI rather than direct =libswipl= embedding.

Benefits include process isolation, an official cross-language embedding interface, Unix-domain socket support, multiple connections for concurrency, and cancellation escalation from query cancellation to connection/process termination.

The adapter exposes only StarIntel-owned named wrapper predicates. Typed parameters are data. They are never concatenated into caller-selected Prolog source.

Each session records worker identity, SWI build/version, wrapper/package digest, fact mapping digest, module/session ID, limits, and active query IDs.

* N-Prolog Adapter

N-Prolog remains process-isolated.

The adapter launches the exact pinned =npl= binary with a digest-locked bootstrap package and communicates through a StarIntel-owned framed protocol. Human REPL output is not the protocol.

Initial restrictions:

- one active query per worker process;
- no SWI module/table assumptions;
- hard cancellation may terminate the process;
- killed workers are discarded;
- JSON/string mode is deterministic session bootstrap state;
- every advertised capability is backed by a conformance fixture.

* Fact Mapping

A fact is not portable merely because it can be printed in three syntaxes.

Define versioned mappings:

#+begin_src lisp
(define-logic-mapping transactionV1
  (:source "star.funds.transaction/1")
  (:lisa transactionFact)
  (:swi-prolog transaction)
  (:n-prolog transaction)
  (:identity id)
  (:fields id amount currency merchant observedAt)
  (:provenance documentId contentHash sourceSpan))
#+end_src

Canonical mapping data is engine-neutral. Native CLOS classes and Prolog terms remain adapter-private.

* Mutation Semantics

Define explicit logical operations:

- =assertSourceFact= — add an input fact to session state;
- =retractSourceFact= — retract only an explicitly mutable session projection;
- =deriveConclusion= — create derived state with a justification;
- =revokeConclusion= — invalidate a derived conclusion when support disappears.

Canonical source documents are never mutated by a backend.

Packages declare whether they support immutable snapshots, append-only facts, session-local retraction, truth-maintained derivations, or incremental updates. The compiler rejects incompatible backend/package combinations.

* Negation

Do not use one unqualified =not= for incompatible meanings.

At minimum distinguish:

- =notProvable= — negation as failure under declared query semantics;
- =absent= — no matching fact in production working memory at a logical sequence;
- =different= — inequality;
- =contradicts= — explicit contradictory evidence.

Portable packages may use only negation constructs defined by their semantic profile.

* Uncertainty

LISA has belief-system support, but SWI-Prolog and N-Prolog do not thereby inherit identical semantics.

Uncertainty is a named versioned algebra:

#+begin_example
boolean
certainty-factor-v1
dempster-shafer-v1
custom:<package-id>@<digest>
#+end_example

A backend may implement an algebra natively or through an adapter-owned library. Cross-backend portability exists only when normalized conclusions and derivation semantics pass conformance fixtures within defined numeric tolerances.

* Proof and Explanation

Backends normalize required explanations to =star.logic.derivation/1=.

Normalized node kinds include source fact, session fact, derived conclusion, rule/clause application, goal/query, parameter binding, assumption, contradiction, uncertainty combination, and truncation/budget marker.

Each node records package/rule identity and supporting node IDs. Native traces remain diagnostic attachments rather than the portable proof.

LISA can normalize activation/logical-dependency events. Prolog should use proof-carrying predicates or instrumented named wrappers rather than treating interactive tracer text as an API.

* Failure and Restart Model

Required conditions include:

#+begin_example
logicBackendUnknown
logicBackendUnavailable
logicBackendIncompatible
logicSemanticProfileUnsupported
logicPackageIncompatible
logicFactMappingFailed
logicBudgetExhausted
logicBackendCrashed
logicOperationCancelled
logicProofInvalid
logicReplayMismatch
logicBackendMigrationRequired
#+end_example

Legal automatic recovery may retry the same operation on an equivalent instance of the same pinned backend/build, recreate a worker from the same immutable package/snapshot, replay recorded results, or abort.

Recovery may not change engine type. Cross-backend execution is an explicit migration/comparison run.

* Budget Contract

Use multidimensional budgets:

| Budget | LISA | SWI-Prolog | N-Prolog |
|--------+------+------------+----------|
| wall time | actor deadline plus engine checks | query timeout plus process deadline | process deadline |
| memory | session/process policy | process/cgroup boundary | process/cgroup boundary |
| answers/conclusions | output cap | answer cap | answer cap |
| logical work | matcher/firing counters | inference limit plus external limits | adapter counters where proven |
| output bytes | normalized output cap | protocol/result cap | protocol/result cap |
| proof nodes | proof builder cap | proof builder cap | proof builder cap |
| restarts | supervisor intensity | supervisor intensity | supervisor intensity |

Backend descriptors state whether each limit is hard, cooperative, approximate, or unsupported. A mandatory hard limit rejects an adapter that cannot enforce it.

* Security Model

Logic packages are executable artifacts even when StarLang source is declarative.

Requirements:

1. packages resolve by ID, exact version, and digest;
2. untrusted source never becomes Common Lisp =READ=/=EVAL= input;
3. Prolog adapters call named wrappers rather than arbitrary goals;
4. LISA lowering emits only closed allowed condition/action nodes;
5. filesystem/network/process/FFI/shell effects are denied by default;
6. process backends receive minimum filesystem/environment visibility;
7. secrets never enter packages, proofs, journals, or fixtures;
8. output/proof sizes are bounded;
9. case/dataset/session scope is attached to fact projections;
10. adapters cannot widen capabilities or limits.

* Deterministic Replay

A terminal operation records:

- source and normalized IR digests;
- plan digest;
- backend ID;
- adapter and engine build identities;
- semantic profile;
- package and mapping digests;
- input snapshot/delta hashes;
- ordered parameters;
- budget;
- normalized answer/conclusion hashes;
- proof hash;
- usage;
- terminal state.

Replay modes:

1. =recorded= — return checked recorded output;
2. =verify= — rerun the same pinned backend/build contract and compare;
3. =migrate= — intentionally run another backend/package and create a comparison record.

Migration never rewrites original history.

* Conformance Strategy

** SWI/N-Prolog portable suite

Test deterministic facts/rules, non-tabled recursion, nondeterministic answer enumeration, agreed numeric/list/term ranges, logical failure, exceptions, Unicode, structured JSON boundary behavior, and only the exact CLP(FD) subset declared portable.

** LISA production suite

Test alpha patterns, joins, negative/existential conditions, salience and tie-breaking, context/focus if exposed, assertion/retraction/modification, quiescence, truth maintenance where enabled, belief algebra fixtures, and normalized firing traces.

** Expert-session suite

Compare normalized conclusions, question requests, state transitions, and derivation graphs. Do not compare private engine traces as if they were portable semantics.

* Benchmark Contract

=auto= routing must use workload-matched benchmarks, not generic microbenchmarks.

Dimensions:

- fact count;
- rule/clause count;
- static versus small-delta state;
- recursion/cycle density;
- join selectivity;
- answer cardinality;
- proof disabled/summary/full;
- cold versus warm session;
- one-shot versus persistent session;
- assertion/retraction churn;
- cancellation point;
- uncertainty enabled/disabled.

Metrics include p50/p95/p99 latency, throughput, startup/package-load time, peak RSS, allocation/GC where measurable, answer/conclusion counts, proof size, cancellation latency, reset latency, replay equality, and semantic mismatch count.

Semantic mismatch always dominates speed.

* Rejected Alternatives

** Raw native engine syntax in StarLang

Rejected because it defeats the closed source boundary, static validation, portability, and stable replay identity.

** One universal rule language silently compiled to every engine

Rejected as an unconditional promise. A portable subset exists only where observable semantics are precisely specified and fixture-proven.

** Runtime failover across engine types

Rejected because it changes semantics under failure.

** N-Prolog as transparent SWI fallback

Rejected because N-Prolog explicitly does not claim ISO equivalence and exposes a different supported feature set.

** LISA-only or SWI-only inference

Rejected because the workloads are genuinely different and the requested N-Prolog portability backend has independent value.

* Acceptance Criteria

1. Source accepts exactly =auto=, =lisa=, =swi-prolog=, and =n-prolog= as initial policies.
2. Materialized plans record exactly one concrete backend.
3. Explicit pins still fail when semantics/capabilities are incompatible.
4. Runtime load cannot change engine type.
5. Normalized IR contains no native engine object or raw executable engine source.
6. SWI-Prolog and N-Prolog remain separate descriptors even when sharing portable term/query infrastructure.
7. LISA production semantics are not mislabeled as Prolog semantics.
8. Portability is fixture-proven per semantic profile.
9. Every adapter reports limit/isolation capabilities honestly.
10. Replay distinguishes same-backend verification from cross-backend migration.
11. Expert-system sugar can compile to this protocol without embedding native forms.
12. Fake adapter tests compiler/runtime logic with no inference engine installed.

* Result

StarLang should expose three real selectable inference runtimes through one engine-neutral semantic protocol. Backend identity is explicit policy data; backend internals remain hidden. SWI-Prolog is the initial general recursive/query default, LISA is the production-rule/persistent expert backend, and N-Prolog is an explicit compatibility/portable-Prolog runtime.

=auto= selects once from declared semantics and a versioned policy, records the exact choice, and never silently changes engines during execution.

* Footnotes and Glossary

- *Backend policy* — Source/deployment declaration selecting =auto= or explicitly pinning one inference runtime.
- *Backend descriptor* — Versioned data record advertising one adapter's exact profiles, capabilities, limits, isolation classes, and build identity.
- *Semantic profile* — Versioned contract defining observable inference behavior independent of native engine APIs.
- *Materialized plan* — Fully resolved immutable run plan in which backend selection, package digests, mappings, limits, and adapter identities are fixed.
- *Portable Prolog subset* — Conformance-tested subset intentionally shared by SWI-Prolog and N-Prolog; smaller than either engine's full language.
- *Production rule* — Forward-chaining rule matched against working memory, generally creating an agenda activation before firing.
- *Tabling* — Memoized logic-program execution that can avoid repeated work and some recursive nontermination patterns.
- *Working memory* — Mutable fact state owned by one production-rule inference session.
- *Migration replay* — Explicit comparison run using a different backend/package while preserving original execution history.
