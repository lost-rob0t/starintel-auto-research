* Question and Existing Authority

The operator wants *StarIntel itself* to act as an extensible ontology-backed knowledge system, not merely to accept an optional ontology document. It must support online/offline communities, evidence-backed real-world events, richer geography, arbitrary versioned domain concepts, and symbolic actor outcomes without encoding specific detector names, incident classifications, escalation thresholds, workflows or target dataset rules into core StarIntel schema authority.

This is a child *execution/compatibility design* of [[id:star-research-007-starintel-ontology-foundations][STAR-RESEARCH-007]] and [[https://github.com/lost-rob0t/starintel-auto-research/issues/252][ontology design authority #252]], not an independent class catalog. Issue #252 already enumerates =Collective=, =OnlineCommunity=, =Event=, =Place=, geographic classes, =MembershipRelationship= and versioned namespaces. Adding another hard-coded class tree would be duplication.

* Finding: Existing Types Are Real; Their Semantics Are Fragmented

1. =entityClass= is an unpinned string; a tenant-supplied class and built-in class have no cross-language contract unless bundled and pinned.
2. =concept= describes taxonomic concepts but is not itself an authoritative ontology-package resolver with class/range, cardinality, namespaced values, imports, migration and digest verification.
3. =relation= is a useful record; a graph edge can still collapse a source's *allegation*, an analyst's conclusion and a rule's inference unless each edge is tied to qualified assertions and evidence state.
4. =event= denotes a domain record, while broker events, audit logs, actor completions, rule signals, and world occurrences have different identities and responsibilities.
5. =geo= geometry is not the same as a claim that a person/device/event occupied a geometry at a certain time. An inferred location must retain method, accuracy, spatial scope, valid/observed time and evidence.
6. Dynamic downstream classes must not require ten hand-edited SDKs or unrestricted keys at trusted ingest.

* Alternatives and Tradeoffs

| Option | Benefit | Serious cost or failure mode | ARADR finding |
|--------+---------+------------------------------+---------------|
| A. Every new real-world concept gets a new fixed =dtype=/code enum | Familiar static generated validators | Class explosion, migrations and downstream library churn; community subtypes become compiler changes | Reject as default; retain fixed dtypes for stable storage profiles only |
| B. Replace canonical JSON/CouchDB with mandatory RDF store/OWL runtime | Native triples and expressive entailment | Second persistence/authorization plane, open-world/closed-world surprises, expensive migration, conditional support on edge clients | Reject as primary authority; keep optional interoperable RDF projection |
| C. Canonical StarLang semantic/ontology bundle + existing typed StarIntel JSON documents + qualified assertions + generated JSON-LD/Prolog/geo/graph projections | Ontology-native, portable, offline-capable, extensible, preserves server ownership | Requires bundle resolver, cross-language semantic validation, migration and truth-maintenance gates | Recommend for design review |

The phrase *ontology-native* means each canonical document is interpreted under a resolved type/predicate registry with a stable evidence/semantics contract. It does not require the database itself to store RDF triples.

* Communities: Collection, Group and Role Aren't the Same Thing

Model =Community=, =Collective=, =OnlineCommunity=, =InformalGroup=, =PlaceBasedCommunity=, =ForumCommunity= as ontology-defined classes, not automatically new core =dtype= values. Start with canonical =entity= plus ontology class URI(s); a specialized =community= storage profile should be considered only if independent persistent invariants justify a new dtype and corresponding schema bump.

Required evidence-backed patterns:

- community identity and external identifiers; platform account, chat room/channel, and legal =org= remain distinct resources;
- parent/child, overlap, affiliated/hosted-by, moderation and geographic catchment are separately named predicates;
- membership is an assertion with source, role/context, valid interval, observed time, confidence and correction state;
- active, historical, claimed, disputed, invited, followed, subscribed, merely mentioned and physically co-present must not be flattened to =memberOf=;
- an informal community can exist with no incorporation, manager, legal address or public member roster.

Counterexample: posting a comment about a community is not evidence of membership or endorsement. Repeated co-location on a map is not proof of organizational affiliation. The ontology must preserve =mentions= / =observed-near= separately.

* World Events and Other Kinds of Event

Event semantics should separate these identities and projections:

| Kind | Canonical meaning | Candidate representation |
|------+-------------------+--------------------------|
| Real-world occurrence | A bounded or ongoing occurrence in the world | existing =event= document plus pinned ontology class and evidence/participant/time/space assertions |
| Source report of occurrence | Someone reported or described something; unverified | source/document + =claim= or =observation= referencing an event candidate |
| Hypothesized/predicted event | Model/rule suggests an event may be occurring or occur later | qualified derived candidate assertion, not an undisputed =event= fact |
| Runtime/actor/broker event | Internal message, change, alert or job transition | existing runtime/event-bus/append-only journal authority, not a world-event ontology class by mere name |
| Workflow signal | A rule-driven typed indication for review or work scheduling | Star KB rule outcome consumed by policy/workflow actor, not new domain truth or core hard-coded classification |

Events need category URIs, occurrence bounds (instant/interval/ongoing/unknown), observation and recorded time, uncertain/multiple competing locations, participant *role assertions* rather than guilt/association, claimed source IDs, correction/retraction, duplicate-candidate semantics and links to subevents. An online event (conference, broadcast) need not have physical geometry. Repeated reports do not establish independent corroboration.

* Geo and Spatiotemporal Semantics

Retain 0.10.1 geometry families and their WGS84 longitude/latitude orientation. Carry forward the useful existing geo-profile policy:

- explicit direct vs anchored vs Prolog-derived spatial association, with canonical reference path;
- place/region administrative and physical hierarchy as ontology classes and dated =partOf=/=inside= assertions, not geometry type aliases;
- =observedAt= vs =validFrom= / =validTo= vs =recordedAt=, optional duration/time interval and motion/trajectory;
- source accuracy radius, vertical accuracy, covariance/polygon region where warranted, incompatible candidate geometries and coarse-only claims;
- polygon holes/rings, antimeridian, CRS transforms, invalid geometries and altitude/unit conformance under an explicit geometry query contract;
- geo query/index in =star-geo= / PostGIS and optional OGC/GeoJSON projections remain rebuildable and authorization-filtered;
- license/attribution metadata for external features. Wi-Fi/IP/provider-reported geography is evidence, not a person's present physical location.

Negative test: a city-only source does not emit or render a precise home coordinate; a map anchor derived from a document association does not write inferred coordinates into the entity as direct GPS.

* Extensibility: Version Every Semantic Boundary

Candidate package contract (not valid current StarIntel document wire):

#+begin_example
ontologyPackage: namespace + package ID + semver + digest + imports
  classes: URI, parent classes, meaning, deprecation
  predicates: URI, domain, range, inverse, symmetry, temporal semantics
  shapes: typed value constraints + evidence/membership cardinality
  mappings: versioned crosswalks, exact/close/lossy
  ruleContracts: named safe Prolog fact/query vocabulary, required rule-package lock
  fixtures: deterministic positive/negative/round-trip tests
#+end_example

- Only the governed StarLang schema/semantic source can alter core document wire or built-in ontology meaning; every such normative change gets a new schema version.
- Namespaced, versioned *domain ontology packages* may introduce terms without changing the core document-wire version **when the immutable extensibility envelope already supports them**. Their own package versions and digests must still change on normative package edits.
- Custom packages cannot shadow core URIs, override security or storage validation, dereference untrusted remote contexts at runtime, or load executable Prolog code into a trusted engine from an arbitrary document.
- A runtime resolves a package by exact locally verified digest (including transitive import closure), rejects unknown/incompatible versions, and preserves unknown authorized extension values losslessly.
- Rule packages and tenant policies are separately pinned; ontology vocabulary does not grant a capability to execute tools.
- Reject automatic schema creation from mined data. Rule/class candidates follow proposal/review/approved immutable release, with downgrade/rollback and collision checks.

* External Workflow: Non-Normative Consumer Pattern

Illustrative ONLY; =possible-public-safety-incident= below is a tenant-defined *candidate signal*, not a StarIntel core dtype, built-in label or factual designation.

#+begin_example
authorized source / observation / claim
    -> canonical StarIntel validated ingest
    -> star-kb safe named Prolog rule over evidence + time + ontology
    -> candidate signal (rule id+version, proof, source refs, uncertainty)
    -> tenant policy/review gate (not schema authority)
    -> supervised workflow actor with explicit capabilities and budget
    -> bounded actor fan-out / human review / enrichment / notification
    -> validated documents with chosen authorized dataset + provenance
#+end_example

The rule does not write to an arbitrary dataset, approve its own finding or issue privileged commands. Workflow policy alone chooses targets, dataset and subsequent actors. Use existing server Target/Operation acceptance, lease/fencing, idempotent outbox, cancellation, tenant isolation and actor registry. A mere classifier positive does not assert that a real-world threat has occurred; high-consequence escalation must have evidence thresholds and appropriate review/authorization outside the ontology.

* Adversarial Review

| Attack/failure | Required countermeasure |
|----------------+-------------------------|
| Ontology term shadows =Person= or redefines =memberOf= in a tenant import | Namespace isolation, immutable term URIs, import lock validation |
| Actor loads URL-supplied JSON-LD context | No ambient remote context fetch; only pinned locally validated contexts |
| False social membership / guilt-by-association | Qualified evidence-backed membership assertions; mentions/follows/proximity not equivalence |
| Multiple copied posts falsely corroborate same alleged event | Upstream-source dependency grouping, competing reports, reviewer-visible candidate states |
| Prolog inferred fact persists after an input is retracted | Truth-maintenance dependency graph, stale marking/retraction, replay |
| Geo inference yields false precision or reveals protected location | Granularity/uncertainty preservation and per-field/dataset authorization |
| Detector emits repeated signals and workflow re-fans-out forever | Stable run/event identity, budgeted fan-out, event-sourced idempotency, causal depth and stop rules |
| Workflow can select an arbitrary output dataset from a document | Tenant-authoritative dataset policy; no data-driven capability minting |
| A schema migrator silently relabels 0.10.1 as 0.11.0 | Source+target digest locks, field-level reviewed mapping, quarantine |
| RDF map/graph/Prolog projection gains writes and diverges | Only canonical validated StarIntel ingest mutates facts; projections are deterministic rebuilds |

* Research Outcome and Open Decisions

Research is sufficient for the dependent [[id:starintel-star-server-065-ontology-native-platform][STAR-SERVER-065]] *design proposal*. It is **not** proof that the full ontology round trip runs in current server, Star KB, SDKs or geo projection. Unresolved for review:

1. Final data-only extension-envelope shape (optional =semantic= member vs canonical typed assertion refs) and whether/when =community= warrants its own =dtype=.
2. Single canonical authoring format and release resolver: align StarLang source/compiled model with the JSON-LD vocabulary described in issue #252 without two write authorities; deprecate/reconcile old =star-spec= 0.9.1.2 profile material deliberately.
3. Exact 0.10.1 → candidate 0.11.0 identity, source field and evidence migration; a major bump is required if backward compatibility fails.
4. Provenance/claim retraction semantics, partial spatial-query states and offline import conflict handling.
5. Review/policy thresholds, workflow signal contracts, and source-specific datasets are defined by their own owners and must never be guessed here.

* Proposed RED-First Fixture Queue

- X01: old 0.10.1 canonical fixture validates untouched; 0.11.0 writer emits a genuinely version-bumped release lock.
- X02: offline third-party namespaced =Community= class loads from digest-pinned ontology package, validates on CL/Python/TS/Nim/Prolog without per-language source changes.
- X03: a malicious extension redefining a core predicate is rejected before import.
- X04: comment/mention/follower event does not produce a =memberOf= assertion without separately validated evidence.
- X05: one source reports an occurrence, another contradicts; projected event stays contested, with both reports and timestamps.
- X06: a rule-proposed event candidate never silently becomes an adjudicated world event.
- X07: point/polygon hole/antimeridian cases agree across WGS84 and GeoJSON conversion, with explicit uncertainty.
- X08: geo-derived anchor does not rewrite a person/entity as directly located there.
- X09: rule-output replay/correction retracts or stales prior derived facts; workflow signal remains traceable to its old proof.
- X10: duplicate signal causes only one authorized bounded workflow dispatch, with no cross-tenant leak or unapproved dataset write.
- X11: ontology export to RDF/JSON-LD and back preserves typed literals, assertion/proof identity and provenance or reports explicit loss.
- X12: unknown package digest, wrong schemaVersion or bad migration quarantine only the affected record, not an entire ingest batch.

No fixture in this list has been executed by this research PR.

* Footnotes and Glossary

- *Ontology-native*: Every canonical document has semantics derived from a pinned vocabulary and qualified assertions, rather than relying on application-specific string conventions.
- *Qualified assertion*: A statement with subject, predicate, object, source, time, confidence/status and optional proof; not an unqualified graph edge.
- *Ontology package*: Immutable namespaced class/predicate/constraint declaration bundle with version, import closure, integrity digest and conformance.
- *Semantic class*: Machine-readable ontology type independent of a persisted storage =dtype=.
- *World event*: An occurrence in reality, distinct from a report about it, an actor message, a detection signal or a hypothesis.
- *Bitemporal*: Separate effective/valid time from when a claim was observed and persisted.
- *Derived projection*: Rebuildable graph, spatial, Prolog or RDF view whose authority remains canonical source data.
- *ARADR*: Analyze, research, design and adversarial-review process requiring separate operator approval for implementation.
