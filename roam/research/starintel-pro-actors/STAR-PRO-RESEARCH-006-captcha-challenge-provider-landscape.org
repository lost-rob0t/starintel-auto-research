* Research Question

What challenge and solver capability model lets StarIntel detect, route, apply, and verify authorized CAPTCHA[fn:captcha] and browser-challenge work without assuming that hCaptcha is the only issuer, every result is a token, or one paid provider is globally valid or invalid?

* Finding

The old one-dimensional question—“does this provider solve hCaptcha?”—is invalid. The subsystem research must model these concepts separately:

1. challenge issuer;
2. challenge family;
3. challenge variant;
4. integration version;
5. required source context;
6. required result kind;
7. required result binding;
8. solver execution/disclosure class;
9. provider capability contract;
10. downstream application;
11. downstream verification;
12. cost and contract confidence.

Provider completion proves only that the selected solver returned a result matching its adapter contract. It does not prove that the target accepted the result. Acceptance is a later source-runtime verification event.

The catalog is open-world. A challenge remains =unknown= until positive and negative evidence support a more specific classification.

** Non-token challenge families

The normalized research taxonomy also represents:

- text and distorted-image text;
- arithmetic/question challenges;
- image grids and object selections;
- coordinates and bounding boxes;
- draw-around tasks;
- audio challenges;
- slider, rotation, and drag-and-drop puzzles;
- proof-of-work;
- behavioral/device verification;
- WAF clearance and cookie-producing tasks;
- managed-browser workflows;
- mobile-native challenges;
- custom first-party challenges;
- unknown challenges.

Challenge family and result kind are independent. A grid can return =selectionSet=, a coordinate task =coordinates=, a browser workflow a cookie or bounded browser-state reference, and a provider puzzle an =interactionPlan= or issuer token according to its exact contract.

* Normalized Challenge Descriptor Research Shape

Provider task names do not belong in the provider-neutral descriptor. A research shape needs at least:

The exact schema is a design decision. The research requirement is that absent fields never authorize capability widening.

* Required Result Kinds

Research supports a typed result union containing at least:

- =token=;
- =assessment=;
- =cookie=;
- =proof=;
- =textAnswer=;
- =coordinates=;
- =selectionSet=;
- =interactionPlan=;
- =customTypedResult=;
- a bounded opaque reference for separately approved managed-browser state if such a design is later accepted.

Sensitive results should never be treated as ordinary StarIntel documents. The exact secret-store implementation remains a design question.

* Result Binding

A result is not fully described by its kind. Research must also capture binding such as:

- unbound/ordinary application;
- same source browser session;
- same network identity;
- caller-owned proxy;
- user-agent match;
- cookie/session bundle;
- mobile/app runtime;
- exact challenge instance;
- custom target-specific binding.

Current provider documentation demonstrates why this matters: DataDome tasks can require caller-owned proxy and matching user-agent/cookie application, while a Cloudflare Challenge provider can return either a token or =cf_clearance= cookie. These cannot safely share a generic “token solved” contract.

* Solver Actor / Execution Research Classes

| Research class | Examples | Principal constraint |
|----------------+----------+----------------------|
| local automated browser | isolated Playwright/browser-process worker | resource cost and target-specific source integration |
| local recognition | OCR/image/audio/model actor | exact typed output and fixture confidence |
| remote automated provider | exact automated provider task | third-party data disclosure and context fidelity |
| human exposure possible | provider with automation plus possible worker fallback | target policy must permit possible human exposure |
| human-assisted vendor | worker-backed task provider | explicit human disclosure and bounded target data |
| managed-browser vendor | provider-controlled browser/session product | substantially broader session/cookie/fingerprint disclosure; separate boundary from token APIs |
| manual operator | local review queue | latency, retention, audit, operator availability |
| custom first-party | owned-system test hook | named target policy and explicit schema |

The exact actor classes/enums remain a design decision. Unknown execution/disclosure class is insufficient evidence for automatic routing.

* Capability State Vocabulary

Every exact provider capability uses one research state:

| State | Meaning |
|-------+---------|
| =verified= | current official contract and local fixture agree |
| =experimental= | plausible documented contract; fixture/canary incomplete |
| =degraded= | usable with a known limitation/reduced confidence |
| =invalidContract= | request/result contract contradicts current evidence or fails validation |
| =disabled= | operator/circuit policy prevents selection |
| =unsupported= | provider does not currently advertise or cannot satisfy exact capability |

Contract drift is capability-local unless a shared provider/account failure affects every task.

* Provider Capability Record

Research says every exact capability record needs:

- provider and official source;
- retrieval date and contract fingerprint;
- issuer, family, variant, integration version;
- request/result operations;
- authentication and credential location;
- required/optional request fields;
- result kind and required result fields;
- result binding;
- proxy/cookie/user-agent/browser-session/network/mobile requirements;
- delivery model;
- cancellation and idempotency;
- ambiguous-submission behavior;
- concurrency/rate-limit/pacing evidence;
- execution and worst-case disclosure class;
- advertised/configured/observed billing data;
- =costConfidence=;
- retention;
- error contract;
- fixtures/live-probe requirements;
- unsupported variants and documentation contradictions;
- current capability state.

No static actor manifest should advertise a runtime capability merely because a vendor catalog or SDK once named it.

* Provider Findings Refreshed 2026-08-09

** NoneCap

NoneCap remains a narrow hCaptcha candidate. Current API evidence exposes standard =hcaptcha= and =hcaptcha_enterprise= operations, documented cancellation, thirty-day solve-record retention, default account concurrency guidance, and Enterprise =rqdata=. It is not a generic provider.

** NopeCHA

NopeCHA remains two distinct surfaces: Token and Recognition. Current hCaptcha documentation adds a meaningful same-network/proxy concern for Enterprise and excludes at least one box-drawing interaction shape. Current official pages also disagree on hCaptcha-token credit cost, making cost confidence independent from request/result validity.

** 2Captcha

The current API v2 catalog is broad, but current official navigation/pricing do not advertise hCaptcha. Therefore hCaptcha is =unsupported= on current official evidence rather than merely “uncertain.” Current documentation describes AI-first solving with possible human fallback for difficult tasks, so worst-case human exposure must be modeled unless a capability proves automated-only. The separate managed Browser API is a distinct research boundary from ordinary =createTask/getTaskResult= tasks.

** Anti-Captcha

Current task documentation covers multiple reCAPTCHA variants, Arkose/FunCaptcha, GeeTest, Turnstile, Friendly, Prosopo, AWS WAF, ALTCHA, image/coordinate, and programmable AntiGate tasks. hCaptcha is absent from the current task index. Worker-backed execution and AntiGate's programmable browser workflow create distinct disclosure classes; AntiGate cannot be a wildcard generic solver.

** CapSolver

The current exact support index lists token tasks for GeeTest, reCAPTCHA v2/v3, MTCaptcha, DataDome, AWS WAF, Cloudflare Turnstile/Challenge and recognition tasks including ImageToText, reCAPTCHA v2, AWS WAF, and VisionEngine. hCaptcha is absent. Arkose/FunCaptcha should not be inferred from broad marketing because the current exact support index does not list it. Current official CapSolver pages also conflict on advertised Turnstile pricing, so cost is drift-prone evidence.

** CapMonster Cloud

The refreshed current catalog is much broader than the older snapshot: reCAPTCHA, GeeTest, Turnstile, Cloudflare Challenge/Waiting Room, DataDome, AWS WAF, Imperva, Prosopo, Friendly, MTCaptcha, ALTCHA, FunCaptcha, image/complex-image and several regional/vendor tasks. hCaptcha is absent. Cloudflare Challenge can return token or =cf_clearance= cookie; DataDome requires caller proxy context and returns cookies for browser application. Exact result binding is therefore mandatory.

* Detection Research Contract

Every detector registry entry should ultimately declare evidence for:

- detector ID/version;
- issuer/family/variant/integration version;
- required observations;
- positive and negative signatures;
- extracted fields;
- confidence computation;
- collision cases;
- fixture set/retrieval date;
- state =verified=, =experimental=, or =disabled=.

Detection signatures drift independently from provider contracts. Exact detector interfaces remain a design question.

* Security and Operational Research Boundaries

Research requires future designs to account for:

- requester authorization and target policy before external disclosure;
- purpose and provider/solver allowlists;
- session/network/proxy/cookie/user-agent/mobile bindings;
- worst-case human exposure;
- managed-browser/custom-browser disclosure as separate from token APIs;
- budget reservation before potentially billable work;
- duplicate-delivery idempotency and ambiguous-create safety;
- cancellation/deadline/shutdown behavior;
- capability-local contract drift;
- request pacing and account blocking/rate limiting;
- no raw public “solve arbitrary URL” relay;
- redacted cost/outcome telemetry;
- opt-in, credential-gated, cost-bounded canaries on operator-owned or explicitly authorized systems only;
- no paid providers in continuous integration.

The exact mechanisms remain unapproved designs.

* Research Gaps

- Capture current exact fixtures for high-value CapSolver rows and reconcile contradictory official pricing evidence.
- Capture CapMonster Cloud token-vs-cookie Cloudflare Challenge and DataDome proxy/cookie fixtures.
- Separate Anti-Captcha ordinary worker tasks from AntiGate programmable-browser workflows.
- Measure provider retention/cancellation semantics by exact task.
- Build the StarIntel observed challenge-frequency matrix before optimizing provider breadth.
- Keep 2Captcha hCaptcha =unsupported= unless current provider-supported contract evidence appears; an old SDK symbol is insufficient.
- Mobile-native and account-gated challenge families need dedicated source-runtime research when encountered.
- Unknown/custom challenges remain schema-on-evidence, not wildcard provider tasks.

* Footnotes and Glossary

[fn:captcha] CAPTCHA: Completely Automated Public Turing test to tell Computers and Humans Apart; this research also covers adjacent browser, device, behavioral, proof-of-work, and WAF challenge mechanisms.

- *Capability widening* — Treating evidence for one issuer/variant/result/context as evidence for another without proof.
- *Contract drift* — Provider request/result/error/billing/lifecycle behavior changing after a fixture was captured.
- *Downstream verification* — Source-runtime evidence that the target accepted, rejected, expired, replaced, or could not determine an applied result.
- *Result binding* — Session/network/proxy/user-agent/app/challenge context required for a returned result to work.
- *Cost confidence* — Confidence that current billing evidence matches an advertised/configured cost.
- *Source runtime* — Browser, HTTP, mobile, or first-party process that owns target interaction and must apply/verify the result in its own context.
