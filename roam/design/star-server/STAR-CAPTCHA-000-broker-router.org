#+title: STAR-CAPTCHA-000 Authorized CAPTCHA Broker and Capability Router
#+description: Provider-neutral StarIntel design for detecting, classifying, routing, solving, applying, and verifying authorized CAPTCHA and browser-challenge encounters.
#+status: REVIEW
#+filetags: :starintel:design:star-server:captcha:actors:routing:detection:authorization:uml:

* Decision

Implement a provider-neutral =CaptchaBrokerActor= inside =starintel-server=.[fn:star-server] Implement detection and source-session orchestration in a separate =CaptchaDetectActor= design. Implement paid vendors, local recognition engines, browser workers, and human-review integrations as separately deployed capability actors.[fn:capability-actor]

The protocol is open-world: it never assumes that hCaptcha is the only challenge issuer, that token generation is the only solve method, or that one vendor supports every challenge. Unknown issuers and custom first-party challenges are represented explicitly and are never coerced into a known type.

The broker owns authorization, normalized request validation, exact capability matching, provider selection, deduplication, budget reservation, cancellation, health-based routing, audit metadata, and ephemeral result delivery. Solver actors own vendor-specific or runtime-specific authentication, network requests, browser execution, recognition, polling, error translation, job state, and billing observations.

The subsystem is not a public solve relay. It accepts work only from authenticated StarIntel principals with =captcha:solve= and an active target-policy record.

* Two Independent Axes

A CAPTCHA encounter has two independent classifications.

1. The *challenge issuer* is the system encountered by the source actor, such as Google reCAPTCHA, hCaptcha, Cloudflare Turnstile, Arkose Labs FunCaptcha, GeeTest, Amazon Web Services Web Application Firewall, DataDome, Friendly Captcha, ALTCHA, MTCaptcha, Prosopo, Tencent, Yandex SmartCaptcha, or a custom first-party challenge.[fn:issuer]
2. The *solver provider* is the actor capable of handling that descriptor, such as a local browser actor, local optical-character-recognition actor, manual-review actor, NoneCap, NopeCHA, 2Captcha, Anti-Captcha, CapSolver, CapMonster Cloud, or another registered adapter.[fn:solver-provider]

A provider that lacks hCaptcha may still be valid for Turnstile, reCAPTCHA, GeeTest, Arkose, image recognition, Amazon WAF, or another advertised family. The registry records exact capabilities and does not label a provider globally supported or unsupported.

* Normalized Challenge Taxonomy

The broker accepts these top-level challenge families. The list is versioned and extensible.

| =challengeFamily= | Meaning | Typical output |
|-------------------+---------+----------------|
| =token= | Site-key or context-bound verification token | token reference |
| =score= | Risk assessment or score-producing execution | assessment reference and score metadata |
| =imageText= | Distorted text image | text answer reference |
| =imageSelect= | Grid, object selection, coordinates, or bounding region | coordinate or selection reference |
| =audio= | Spoken challenge | text answer reference |
| =puzzle= | Slider, rotate, drag, shape, or logic puzzle | interaction plan or provider token reference |
| =proofOfWork= | Computational browser challenge | proof or clearance reference |
| =wafInterstitial= | Browser/session challenge that returns a cookie or clearance token | cookie or clearance reference |
| =behavioral= | Passive browser, device, or behavior verification | browser-bound result reference |
| =custom= | First-party or unrecognized challenge with an explicit schema | provider-specific opaque result reference |
| =unknown= | Evidence exists but classification is insufficient | no solve; return detection evidence |

=challengeVariant= refines a family without changing the family contract. Examples include =checkbox=, =invisible=, =managed=, =enterprise=, =v2=, =v3=, =v4=, =grid=, =coordinates=, =slider=, =rotate=, =silent=, and =interactive=.

* Provider Capability Contract

Every solver actor registers a versioned capability document containing:

- =providerId= and adapter version;
- exact issuer, family, variant, and integration-version predicates;
- required and optional descriptor fields;
- result kind;
- browser-session, proxy, cookie, user-agent, and Internet-Protocol binding requirements;
- local, automated-vendor, human-worker, or operator-review execution class;
- cancellation, feedback, callback, balance, and quota support;
- configured concurrency, health, and circuit state;
- contract confidence: =verified=, =experimental=, or =disabled=;
- official-contract retrieval date and fixture fingerprint.

Capabilities are additive and exact. A registration such as =captcha.googleRecaptcha.token.v2= does not imply v3, Enterprise, score, mobile, or audio support.

* Routing Rules

The registry first performs a hard capability match. The broker then ranks only matching candidates by:

1. target-policy allowlist and disclosure class;
2. required browser, proxy, cookie, user-agent, and session binding;
3. contract confidence;
4. current health and open circuit breakers;
5. available concurrency;
6. remaining provider and local budget;
7. downstream acceptance rate for the exact capability;
8. latency and cost;
9. operator preference.

Cost never overrides authorization, exact capability, source-context requirements, or disclosure policy. Automatic fallback and speculative execution require explicit policy because they can disclose challenge data to another party and create another charge.

* Detection and Source-Actor Boundary

The broker never scrapes arbitrary pages itself. =CaptchaDetectActor= accepts a =sourceActorRef= and bounded observation references from a source actor. It classifies evidence, asks for missing inspection data through the source actor, submits a normalized solve request, returns apply instructions, and verifies whether the source actor resumed successfully.

The source actor retains ownership of its browser or HTTP session. The detector and broker receive only capability-scoped references. The full protocol and example code are defined by [[id:star-captcha-001-detection-resolution-orchestrator][STAR-CAPTCHA-001]].

* Durable and Ephemeral State

Durable state may contain request and principal identifiers, approved purpose, target-policy identifier, normalized host, issuer/family/variant, provider and provider-job identifiers, state transitions, timestamps, retries, cancellation outcome, cost, redacted errors, and downstream accepted or rejected outcome.

The following values are never persisted: provider keys, solve tokens, answer text, coordinates, interaction plans, clearance cookies, proxy credentials, cookie bundles, enterprise data, challenge page data, authorization headers, and full provider bodies containing secrets.

* Deduplication and Ambiguous Submission

=requestId= is the logical idempotency key. The journal state machine is:

#+begin_example
reserved -> submitted -> providerPending -> succeeded
                               |             failed
                               |             cancelled
                               +-----------> uncertain
#+end_example

An ambiguous provider-creation transport failure enters =uncertain=. The broker first attempts provider-job recovery. It never blindly creates a replacement paid task. Duplicate RabbitMQ deliveries attach to the existing run or replay its terminal normalized result.

* Cancellation and Shutdown

A requester sends =captchaSolveCancel= with =requestId=. The run actor marks cancellation requested, invokes provider cancellation where supported, deletes unconsumed results, emits the normalized cancellation state, and records whether work may still complete or charge.

Shutdown stops new runs, drains or cancels active runs within a configured deadline, deletes result leases, and reports unresolved provider jobs. Provider actors are not silently abandoned.

* Failure Taxonomy

Normalized failures include =policyDenied=, =invalidRequest=, =detectionInsufficient=, =unsupportedChallenge=, =sourceContextRequired=, =providerDisabled=, =providerAuthenticationFailed=, =providerInsufficientBalance=, =providerConcurrencyLimited=, =providerRejectedRequest=, =providerUnsolvable=, =providerTimeout=, =providerUnavailable=, =ambiguousSubmission=, =resultApplicationFailed=, =verificationFailed=, =deadlineExceeded=, =cancelled=, and =internalError=.

Every failure includes =retryable=, =chargePossible=, =providerCode= when present, and a redacted message.

* Actor Manifest Requirements

The server manifest declares =star.actor.captchaBroker= with roles =captchaBroker= and =authorizedExternalServiceRouter=. It accepts solve, cancel, provider-registration, provider-health, and outcome-report messages. It requires =captcha:route=, =secret:lease=, =budget:reserve=, and =policy:evaluate=. It contains no provider hosts or credentials.

Each solver actor manifest declares exact capabilities, permitted network hosts, required secret references, and execution class. Actor Manifests do not contain =documentIds=.

* Testing

Required tests include:

- every taxonomy family and unknown/custom handling;
- exact capability matching without family or version widening;
- authorization, target host, purpose, context, and disclosure denials;
- camelCase schema validation;
- duplicate RabbitMQ delivery and ambiguous provider submission;
- browser/session-bound versus proxyless routing;
- health, circuit breaker, quota, and budget behavior;
- fallback disabled and explicitly enabled;
- cancellation supported and unsupported;
- one-read result expiration;
- complete log, event, trace, and persistence redaction;
- source-actor apply and verification outcomes;
- shutdown with active runs;
- provider capability downgrade and contract drift;
- fake provider actors for every result kind;
- no paid-provider calls in continuous integration.

* Footnotes and Glossary

[fn:star-server] StarIntel Server: The Common Lisp service that owns core control, routing, persistence, authorization, search, and actor hosting.

[fn:capability-actor] Capability actor: An actor that advertises a precise operation it can perform, the input context it requires, and the result it returns.

[fn:issuer] Challenge issuer: The product or first-party system that generated the challenge encountered by a source actor.

[fn:solver-provider] Solver provider: A local, remote, automated, human-assisted, or operator-driven actor that attempts an authorized challenge resolution.

[fn:actor] Actor: A small independent software unit that owns its state and processes messages one at a time.

[fn:secret-reference] Secret reference: An opaque identifier that allows an authorized component to read a sensitive value without embedding that value in ordinary messages.

[fn:circuit-breaker] Circuit breaker: A failure-control mechanism that temporarily stops routing work to an unhealthy dependency and later probes recovery.
