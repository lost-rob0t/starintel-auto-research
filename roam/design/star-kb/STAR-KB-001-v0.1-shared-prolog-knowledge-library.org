* Purpose

This document specifies *how V0.1 will be built if and only if this design is approved*. Research approval is already recorded separately. Design approval is not.

The ARADR authority lives in =lost-rob0t/starintel-auto-research=. The implementation repository is =lost-rob0t/star-kb=. This design must remain here under =roam/design/star-kb/= until the operator explicitly approves it; only then may the control-plane copy move into =roam/implement/star-kb/= and product changes begin in =star-kb=.

V0.1 has one job:

#+begin_quote
Prove that a human or agent can write reusable Prolog facts and rules in =star-kb=, compose them into a named bundle, deterministically compile them into the existing safe =prolog-query-server= document format, stage and validate an immutable release, and query/explain that release without executing arbitrary source Prolog.
#+end_quote

V0.1 does *not* implement the production dialect corpus or the StarIntel dialect actor. Those become later slices after the generic knowledge pipeline works.

* Source Module Contract

A module is the smallest reusable source unit. One module directory contains one =module.json= plus explicitly listed source files.

#+begin_src json
{
  "schema": "star-kb.module.v1",
  "name": "core.test",
  "version": "0.1.0",
  "files": ["facts.pl", "rules.pl"],
  "requires": [],
  "provides": [
    {"predicate": "human", "arity": 1},
    {"predicate": "mortal", "arity": 1}
  ],
  "sources": ["source-star-kb-owned"]
}
#+end_src

Normative rules:

- =schema= MUST equal =star-kb.module.v1=.
- =name= MUST be globally unique.
- Module names use lower-case ASCII dot-separated components, with hyphens allowed where needed for language/region identifiers.
- =version= is SemVer-style review metadata, not runtime release identity.
- =files= MUST stay inside the module directory; path escape is rejected.
- File order is retained for diagnostics, but clause identity does not depend on file order.
- =requires= names source modules, not SWI runtime modules.
- =provides= explicitly inventories public predicates; every listed predicate must be defined by the module.
- Duplicate predicate ownership across unrelated modules is rejected unless a later design adds extension points.
- =sources= references existing source-record IDs.

* Bundle Contract

A bundle is the thing a consumer wants to query. V0.1 maps one bundle one-to-one to one PQS KB name.

#+begin_src json
{
  "schema": "star-kb.bundle.v1",
  "name": "star.core.test",
  "version": "0.1.0",
  "roots": ["core.test"],
  "exports": [{"predicate": "mortal", "arity": 1}],
  "runtime": {"kind": "prolog-query-server", "kb": "star.core.test"}
}
#+end_src

The builder computes the complete transitive dependency closure of =roots=. Module dependency cycles are build errors; logical recursion among Prolog predicates may still be valid. =exports= must resolve inside the closure. V0.1 performs no runtime cross-KB imports: the resolved closure is materialized into one PQS release.

* Source Record Contract

A source record describes where reusable knowledge came from. It is metadata, not executable logic.

#+begin_src json
{
  "schema": "star-kb.source.v1",
  "id": "source-star-kb-owned",
  "kind": "first-party",
  "title": "Star KB authored fixture knowledge",
  "canonical_url": "https://github.com/lost-rob0t/star-kb",
  "retrieved_at": "2026-09-10",
  "license": {"id": "repository-license", "url": null},
  "notes": "Synthetic fixture knowledge used to prove the compiler/runtime path."
}
#+end_src

V0.1 validates presence, uniqueness, and source references. More elaborate license-policy resolution is deferred, but source/license metadata MUST survive into generated provenance.

* Restricted Prolog Source Profile V1

Only ordinary facts and Horn-style rules are accepted:

#+begin_src prolog
predicate_name(Arg1, Arg2).

predicate_name(Arg1) :-
    Goal1,
    Goal2.
#+end_src

Allowed data terms are atoms, strings, supported finite numbers, lists, compound terms, variables in rules, and nested terms representable by PQS's safe JSON AST. Persisted facts MUST be ground.

Allowed body goals are predicates defined inside the bundle closure, PQS safe builtins, and explicit =\+ Goal= negation compiled to PQS's structured =not= representation. Arithmetic must use PQS's safe vocabulary, e.g. =calc(Adjusted, add(Input, 10))=, rather than unrestricted =is/2= execution.

The validator MUST reject at least: top-level directives; =?-=; DCGs; disjunction; if-then/cut; =call/N= and other meta-call surfaces; dynamic assertion/retraction; consult/load/module directives; shell/process/filesystem/environment/socket/HTTP/database/foreign calls; expansion hooks; coroutining/attributed-variable constructs; unapproved module qualification; definitions colliding with PQS builtins; unresolved body predicates; and any term not losslessly representable in current PQS safe AST.

Unknown executable forms fail closed.

* Parse-Only Reader Design

=src/star_kb_reader.pl= SHALL parse configured source with SWI-Prolog's term reader but SHALL NOT =consult=, =load_files=, or call parsed clauses.

#+begin_src prolog
read_term(Stream, Term,
          [ variable_names(VariableNames),
            term_position(Position),
            syntax_errors(error)
          ]).
#+end_src

For each term retain module name, repository-relative file, term index, source position, original term, and source variable names. Directives are parsed only so the validator can reject them; they are never executed.

* Normalization Design

Canonicalization occurs before hashing and JSON generation:

1. Validate and preserve predicate/functor atoms.
2. Keep Prolog atoms distinct from strings in PQS JSON.
3. Alpha-normalize variables by first occurrence to =V0=, =V1=, ... while retaining source names for diagnostics.
4. Preserve body-goal order.
5. Preserve list order.
6. Sort only semantically unordered inventories such as source IDs/dependency sets.
7. Serialize hash input with deterministic key ordering and deterministic numeric/string encoding.

Thus =mortal(X) :- human(X).= and =mortal(Person) :- human(Person).= have the same logical identity.

* Identity Model

** Logical clause ID

#+begin_src text
clause_id = sha256(
  "star-kb-clause-v1" ||
  module_name ||
  canonical_clause_ast
)
#+end_src

Git commit and runtime release are excluded so non-semantic rebuilds/variable renames preserve clause identity.

** Bundle content hash and release ID

Build the full normalized dependency closure, canonicalize its semantic manifests/source records/generated clauses, sort generated clauses by full =clause_id=, and hash the resulting canonical bytes. Runtime release ID is =r-<first-24-hex-of-content-hash>=.

** Runtime document ID

#+begin_src text
runtime_document_id =
  "skb-" + short(bundle_hash) +
  "-" + short(release_hash) +
  "-" + short(clause_id)
#+end_src

Full hashes remain in provenance. Non-semantic build provenance such as Git head and compiler version is attached only after semantic identity is known.

* Generated PQS Mapping

A source fact such as =human(socrates).= becomes a PQS =prolog_fact= with exact bundle KB/release, explicit atom representation, deterministic =_id=, and =star_kb= provenance containing bundle/module versions, clause ID, source path, term index, source-record IDs, content hash, source commit, and compiler version.

A source rule such as =mortal(X) :- human(X).= becomes a PQS =prolog_rule= whose variables use canonical names such as =V0= and whose body order is preserved.

If current PQS validation is stricter than the proposed provenance shape, the compiler adapts provenance to fields PQS accepts. PQS validation is never weakened merely to accommodate STAR-KB metadata.

* Generated Build Directory

A successful build creates a Git-ignored directory:

#+begin_src text
build/star.core.test/r-<hash>/
  release.json
  documents.ndjson
  query-fixtures.json
  build-report.json
#+end_src

=release.json= records schema, bundle/version, PQS KB/release, full content hash, source commit, compiler version, resolved modules/sources, document count, and serialized byte count.

* CLI Contract

The product CLI is implemented in SWI-Prolog; a tiny launcher is acceptable, but build/domain logic stays in =src/*.pl=.

#+begin_src text
star-kb validate
star-kb build BUNDLE
star-kb diff BUILD_A BUILD_B
star-kb stage BUNDLE --pqs URL --token-file PATH
star-kb check BUNDLE --pqs URL --token-file PATH
star-kb activate BUNDLE --release RELEASE --expected-rev REV --pqs URL --token-file PATH
#+end_src

=validate= is local-only. =build= validates then emits deterministic artifacts. =diff= compares modules/sources/clauses using stable IDs. =stage= writes a non-active release only. =check= verifies staged identity/content, invokes PQS analysis, and runs pinned query/explain fixtures. =activate= is a separate cutover and always sends =strict:true= plus caller-supplied current manifest =_rev=. There is no V0.1 option to disable strict activation and no unattended build-through-activate command.

* Publication State Machine

#+begin_src text
SOURCE
  -> VALIDATED
  -> BUILT
  -> STAGING --failure--> PARTIAL_STAGED
  -> STAGED
  -> CHECKED
      |-- analysis/fixture/proof failure --> REJECTED_FOR_ACTIVATION
      v
  ACTIVATE(expected _rev, strict=true)
      |-- stale _rev --> ACTIVATION_CONFLICT
      v
  ACTIVE
      |-- rollback --> prior CHECKED release becomes ACTIVE
#+end_src

Normal tooling MUST NOT permit =BUILT= or =PARTIAL_STAGED= to jump directly to =ACTIVE=.

* Stage Idempotency and Partial Failure

CouchDB bulk writes are not one transaction over a release, so =stage= must be replay-safe. For target =(kb, release)= it reads existing documents by deterministic ID, creates missing documents, accepts exact-equivalent already-staged documents, and fails on mismatched documents as =release_collision=. After bounded-batch upload, it re-reads and verifies the exact expected ID/content set. Unexpected extra documents are a hard error and are not silently deleted.

* PQS Check Contract

=star-kb check= performs, in order: local artifact hash verification; exact staged-set verification; =POST /v1/analyze= for exact KB/release; require =valid:true=; pinned =/v1/query= fixtures; =/v1/explain= proof mapping back to STAR-KB provenance; and resource-limit checks. Any fixture hitting a resource limit fails even if partial answers exist. Analyzer warnings are recorded; structural errors fail.

* Activation Contract

Activation sends exact KB, release, caller-supplied current manifest =_rev=, and =strict:true=. Before activation, the CLI verifies a successful =check= for the exact release. A stale revision aborts. It MUST NOT automatically refetch a new revision and retry because that could overwrite another operator's decision. Successful activation is followed by release-status verification and a default-release smoke query.

* Rollback Contract

Rollback means activating a previously checked immutable release using the current manifest revision and =strict:true=. Old releases are not mutated.

* Test Boundaries

- Reader tests: parse-only behavior, source positions, syntax errors, no directive execution.
- Profile tests: table-driven acceptance/rejection for every forbidden capability.
- Normalization tests: alpha-renaming, atom/string distinction, nested terms, body/list order, deterministic JSON bytes.
- Manifest tests: schemas, path containment, duplicates, missing dependencies/sources/exports, cycles, predicate ownership, deterministic closure order.
- Compiler tests: exact Prolog-to-PQS JSON for facts/rules/negation/compounds/atoms/strings/variables/safe arithmetic.
- Build tests: deterministic identities/artifacts and semantic-change sensitivity.
- PQS integration tests: stage/check/strict activate, pinned query/explain, proof mapping, partial-stage resume, collision failure, stale revision conflict, rollback.

* Error Model

Commands return nonzero on incomplete/ambiguous operations and expose stable machine-readable classes including =source_parse_error=, =source_profile_error=, =manifest_error=, =dependency_cycle=, =missing_source=, =predicate_conflict=, =unresolved_predicate=, =build_mismatch=, =pqs_unavailable=, =pqs_unauthorized=, =pqs_forbidden=, =release_collision=, =partial_stage=, =analysis_rejected=, =fixture_failed=, =proof_mapping_failed=, =resource_limit_hit=, =manifest_revision_conflict=, and =activation_failed=.

Zero Prolog solutions is an inference result, not a transport failure.

* Logging and Secrets

Tokens come from token files or a later approved secret provider, never from examples that place them in argv. Authorization headers are never logged. Build logs may contain module/source/predicate/clause/hash/query identifiers and bounded repository-owned source excerpts, but not runtime StarIntel evidence. Generated build material contains no credentials.

* Large-Corpus Scaling Rules

Source is modular, each clause has independent logical identity, dependency closure is manifest-driven, build reports record document counts/bytes, stage uses bounded batches, exact staged sets are verified before activation, and large raw observations/training data remain outside Git.

Known runtime constraint: current PQS same-KB workloads may serialize behind a per-KB mutex. V0.1 does not redesign PQS concurrency; benchmark realistic workloads before opening that separate design.

* Common Lisp Consumer Boundary — Later Slice

The later =starintel-server= client consumes stable bundle KB names and PQS =/v1/query=/=/v1/explain=, omits release for normal live operation, pins release for replay/audit, preserves query/release/budget/proof metadata, and never loads =star-kb= source. It needs transport/config/error handling, not an embedded Prolog runtime.

* Dialect Consumer — Later Slice

After V0.1 and the generic client are proven, create =star.dialect.en-us= using the same module/bundle/source mechanism. Keep linguistic, contextual-geography, named-geography, and learned-model evidence separate. Dialect evidence is not proof of exact current residence.

* StarLang Boundary — Later Slice

StarLang consumes a generic knowledge-query capability and stays unaware of Prolog source syntax.

* Footnotes and Jargon Glossary

- *Alpha-normalization*: rename variables into a canonical order so variable-name-only edits do not change logical identity.
- *AST*: structured representation of parsed source instead of raw executable source text.
- *ARADR control plane*: research/design/implementation-state documents. For STAR-KB they live in =starintel-auto-research=.
- *Bundle*: named knowledge package containing root modules plus dependencies; V0.1 publishes one bundle as one PQS release.
- *Canonical knowledge*: reviewed reusable facts/rules, distinct from one run's observations.
- *Clause*: one Prolog fact or rule.
- *Content hash*: SHA-256 fingerprint of canonical semantic build material.
- *CouchDB =_id=*: unique document key.
- *CouchDB =_rev=*: optimistic-concurrency revision token used to reject stale writes.
- *Dependency closure*: requested modules plus all recursive dependencies.
- *Directive*: =:- ...= source normally executed while loading; STAR-KB parses it only to reject it.
- *Fail closed*: reject/stop when correctness or safety cannot be established.
- *Fixture*: fixed test input and expected output.
- *Ground fact*: fact containing no variables.
- *Idempotent/replay-safe*: repeating an operation reaches the same correct state without duplicate side effects.
- *KB*: knowledge base, a named set of facts and rules.
- *Manifest*: metadata describing a module, bundle, source, or release.
- *Meta-call*: dynamically executing a term as code, e.g. =call(X)=; forbidden in V0.1 source.
- *Meta-interpreter*: PQS's restricted interpreter over persisted safe rules.
- *Negation as failure*: =\+ Goal= succeeds when Goal cannot be proved; it is not explicit proof of falsehood.
- *PQS*: =lost-rob0t/prolog-query-server=.
- *Predicate/arity*: a named relation and its argument count, e.g. =human/1= or =located_in/2=.
- *Proof/explanation*: machine-readable derivation showing which stored facts/rules supported a result.
- *Provenance*: source/version chain for knowledge and derived results.
- *Release*: immutable runtime version of a KB.
- *Release collision*: deterministic release ID already exists but its content differs from the expected build; this fails instead of overwriting.
- *Restricted Prolog profile*: deliberately small safe source subset accepted by STAR-KB.
- *Rollback*: activate a previously checked immutable release.
- *Semantic build artifact*: deterministic generated material derived from knowledge content; timestamps/Git head are separate provenance.
- *Stage*: upload a release without making it active.
- *Strict activation*: activation with =strict:true= so analyzer errors block cutover.
- *Transitive dependency*: dependency of a dependency.
