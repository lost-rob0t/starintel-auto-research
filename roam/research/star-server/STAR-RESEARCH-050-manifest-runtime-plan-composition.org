* Non-Negotiable Ownership Invariant

The actor/service registry lives in *StarLang*.

StarLang is the sole semantic authority for:

- canonical =star://<authority>/<resource-kind>/<resource-path>= identity;
- actor/service semantic manifests;
- deterministic actor/service registry construction and lookup;
- accepted/produced types, capabilities, domain ownership, and semantic digests;
- runtime-directory semantics that resolve a declared StarLang resource to a live runtime incarnation;
- the semantic distinction between declared, missing, unavailable, and live resources.

StarIntel Server is a *consumer* of that registry. It owns only application/deployment concerns around StarLang resources:

- deployment/component bindings;
- dataset bindings;
- authentication and authorization;
- target lifecycle and lease/fencing composition;
- canonical ingest and persistence;
- trusted transport/adapter selection;
- RuntimePlan application/deployment policy;
- safe HTTP projections that join StarLang semantic data with deployment/runtime state.

A StarIntel route index keyed by =resourceUri= is a derived deployment/application projection. It is never a semantic actor/service registry and never becomes the source of truth for actor existence.

* Current-Source Findings

** StarIntel server composition is still largely imperative

Current server source retains process-global composition state such as =*actors-start-hook*=, =*document-patterns*=, =*ingest-workers*=, =*sys*=, =*actor-index-agent*=, producer/CouchDB/target globals, and hard-coded startup order.

That confirms the server problem: deployment/application topology is not yet compiled from one validated deterministic plan before effects.

It does *not* justify moving semantic actor registration into the server.

** StarLang already owns actor/domain semantics

StarLang compiler/runtime work already owns actor/domain declarations, accepted/produced contracts, capabilities/tools, restart/mailbox semantics, and runtime-directory behavior. The canonical =star://= work in StarLang #72 extends that ownership into explicit actor/service registry semantics.

Any server-local document that independently defines those semantics would create a second authority and is rejected.

** Dataset manifests are a different authority

A Dataset Manifest describes data/catalog/storage/governance and bindings to already-declared StarLang resources. It may select/narrow compatible resources and flows but may not define actor capabilities, create semantic actor identities, or become a workflow language.

* Research Decision

Use four explicit layers.

** Layer 1 — StarLang actor/service registry

StarLang compiler/runtime output is authoritative for:

- =resourceUri= and =resourceKind=;
- semantic name/version/digest/spec-lock identity;
- accepted/produced message/document types;
- owned/keyed domain semantics;
- capabilities/tools;
- semantic restart/failure/mailbox constraints;
- declared ports/runtime requirements.

The StarLang registry is keyed by canonical STAR URI and provides deterministic exact lookup plus bounded lookup by kind/capability/type where the language/runtime contract permits it.

StarIntel does not construct a second registry from these manifests.

** Layer 2 — StarIntel deployment binding

A StarIntel deployment binding references one exact StarLang registry resource/digest and may add only deployment/runtime facts such as:

- stable =componentId= and deployment version;
- exact =resourceUri= / semantic digest reference;
- trusted adapter kind/reference;
- component dependencies;
- workload/dispatcher demand and routee bounds;
- mailbox/admission narrowing;
- local/Rabbit/remote adapter binding references;
- authorization/lease/idempotency policy references;
- configuration/options schema and opaque secret refs;
- health/readiness adapter refs;
- operator-safe labels.

It must not redefine accepted/produced types, capabilities, domain ownership, semantic identity, or executable actor behavior.

** Layer 3 — StarIntel Dataset Manifest

Dataset Manifest remains data-only:

- dataset/tenant/owner identity;
- schema/spec compatibility;
- storage/index/materialization/graph refs;
- normalization/validation/governance refs;
- selected compatible StarLang =resourceUri= values;
- typed =flowBindings=;
- provenance/retention/publication/lease/research policy refs.

Bindings may narrow compatible resources. They cannot widen StarLang semantics.

** Layer 4 — StarIntel RuntimePlan

RuntimePlan is a pure deterministic *deployment/application plan referencing StarLang registry resources*.

It is explicitly not an actor/service registry.

Conceptual form:

#+begin_example
RuntimePlan
  planVersion
  sourceManifestIds[]
  starRegistryRefs[]
  semanticDigests[]
  deploymentBindings[]
  typedRoutes[]
  lifecycleGraph
  datasetBindings[]
  threadDemand[]
  sentoLaneDemand[]
  mailboxAdmissionDemand[]
  storageBindings[]
  diagnostics[]
  planDigest
#+end_example

Equivalent inputs produce an equivalent plan/digest. Compilation has zero actor/thread/network/database/timer/listener/plugin side effects.

        v

        |

Rabbit routing keys, HTTP endpoints, Sento refs, Pykka refs, queues, process names, sockets, and host ports are adapter/runtime details and never canonical actor identity.

* Cross-Authority Validation Rules

The server linker must reject at minimum:

1. deployment binding to an unknown StarLang registry URI;
2. semantic digest mismatch;
3. wrong resource kind;
4. duplicate =componentId=;
5. deployment widening of StarLang capabilities/types/authority;
6. dataset binding to incompatible StarLang type/capability;
7. route whose payload contract is not accepted by the StarLang resource;
8. forbidden lifecycle dependency cycle;
9. unknown dependency/schema/policy reference;
10. raw secret/credential literals where a secret reference is required;
11. unsatisfiable thread/Sento/mailbox demand;
12. ambiguous deployment route ownership without explicit deterministic arbitration;
13. any field that attempts to construct a second semantic registry or URI parser.

* Relationship to Runtime Work

- StarLang #72 owns actor/service registry + canonical URI + runtime-directory semantics.
- Server #34 owns total process-thread budget.
- Server #35 owns aggregate Sento execution-lane accounting.
- Server #36 owns bounded mailbox/admission semantics.
- Server #37 owns server component lifecycle.
- Server #40/#41 own application ports and concrete adapters.
- Server #42 owns StarIntel component incarnation handles/generation/readiness, never semantic registry truth.
- Server #43 consumes StarLang registry resources and compiles server deployment/application policy.

* Rejected Architectures

1. *StarIntel-owned actor/service registry* — duplicates StarLang and is forbidden.
2. *RuntimePlan contains/projects the semantic registry* — wrong ownership; it may contain only references and derived deployment indexes.
3. *Server-local Actor Manifest restates accepted types/capabilities* — semantic drift.
4. *Dataset Manifest embeds actor semantics or workflow code* — crosses authority boundaries.
5. *Raw Rabbit/Sento/Pykka/HTTP endpoints become actor identity* — transport is not identity.
6. *Legacy global actor-name index remains authoritative* — compatibility aliases may delegate only.
7. *Manifest capability declaration grants authorization* — discovery is not auth.
8. *Compile while realizing components* — invalid topology must fail before effects.

* Proposed Implementation Handoff

Dependency order is mandatory:

1. =lost-rob0t/star-lang#72= implements canonical URI, StarLang manifest registry, deterministic lookup, and runtime-directory migration.
2. =lost-rob0t/starintel-server#43= consumes StarLang registry fixtures/artifacts and implements pure deployment/Dataset/RuntimePlan linking.
3. Pro Actors and star-bbpd publish/consume compatible StarLang semantic manifests while their Rabbit/Pykka/Sento details remain adapters.
4. StarIntel HTTP discovery may expose a safe joined projection without claiming registry ownership.

First server RED:

* Glossary

- *StarLang actor/service registry* :: Canonical semantic registry keyed by STAR URI. Sole actor/service registry authority.
- *Deployment binding* :: StarIntel data-only binding from a StarLang registry resource to concrete server/runtime adapter policy.
- *Dataset manifest* :: StarIntel data-only dataset/catalog/governance and compatible-resource binding contract.
- *RuntimePlan* :: Pure deterministic StarIntel deployment/application plan containing StarLang registry references, not a semantic registry.
- *Runtime directory* :: StarLang runtime semantics for resolving declared resources to live incarnations.
