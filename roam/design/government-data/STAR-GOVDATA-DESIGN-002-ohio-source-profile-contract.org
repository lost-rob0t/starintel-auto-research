* REVIEW Objective

Define one durable national-compatible contract for Ohio state systems, county systems, components, delegated vendor portals, shared deployments, static files, APIs, dashboards, form-driven searches, document archives, applicability decisions, and explicit coverage gaps without creating a schema fork per county.

* REVIEW Invariants

1. Search results and adapter observations create proposals, never verified canonical state.
2. Every verified profile revision links to official ownership or delegation evidence.
3. Every canonical profile, deployment, search plan, subfamily decision, gap, and route assessment is revisioned and immutable.
4. Every revision declares its logical ID, revision ID, immediate predecessor, and the revisions it supersedes.
5. Route assessments bind exact profile, search-plan, decision, gap, evidence, deployment, policy, and applicability-contract revisions.
6. Shared vendor deployments are separate from jurisdiction-specific authority and coverage.
7. A source profile does not imply complete route coverage.
8. Negative findings are evidence-bearing, expiring decisions.
9. =:not-applicable= requires positive authority or service-topology evidence.
10. Source state and human review state are independent.
11. Current, historical, and future-effective content are measured separately.
12. A later revision never changes the evidence basis of an older decision.
13. Browser and OCR output cannot become evidence without replayable artifact boundaries.
14. Personal-data fields and access restrictions are recorded before acquisition is authorized.

** Evidence record

#+begin_src lisp
(defstruct source-evidence
  evidence-id retrieval-event-id evidence-kind locator-id
  content-hash captured-at observed-title observed-organization
  observed-links assertion assertion-scope confidence notes)
#+end_src

Evidence kinds include official-domain declaration, official page link, government document citation, delegated vendor link, authority or service-topology record, DNS/TLS observation, redirect chain, platform fingerprint, API sample, file metadata, browser capture bundle, OCR result with source-image references, negative-search record, archived-source record, and predecessor/successor declaration.

A browser capture bundle contains the final URL, redirect chain, normalized DOM or rendered-text hash, public network-request metadata, submitted public form parameters, browser/runtime version, navigation sequence, screenshot metadata, and raw-artifact references. Screenshot metadata alone is insufficient.

OCR is a bounded last resort. Until a reviewed OCR adapter exists, an image-only document returns =:ocr-required= and enters manual review.

* REVIEW Official Status

=:official-status= is one of =:verified-official=, =:verified-delegated=, =:candidate-official=, =:candidate-delegated=, =:unverified=, =:rejected=, or =:retired=.

=:verified-official= requires government-controlled-domain, authoritative-registry, or authenticated-publication evidence. =:verified-delegated= requires an official government page, document, or authority record linking the vendor system to the unit or component. Logos, names, TLS certificates, and search results are insufficient by themselves.

** Initial Ohio county route contract

This table is the minimum version-1 route inventory. Machine-readable rule records must encode the same requirements before Franklin County begins.

| Route | Kind | Required and conditional subfamilies |
|-------+------+------------------------------------------|
| identity | source | county identity and canonical domains; elected and administrative component identities; delegated hosting; service-provider topology |
| open data | inventory | official catalog or open-data landing inventory; data.json/DCAT/CKAN/Socrata/ArcGIS Hub or equivalent probes; downloadable bulk/export inventory; reviewed negative result when none is published |
| GIS | source | countywide GIS/parcel service or resolved provider; auditor and parcel services; engineer/planning geospatial services when operated; OGC/ArcGIS/bulk-file inventory |
| law | source | charter or reviewed non-charter applicability; resolutions and ordinances; county code/policy repository; authenticated or authoritative version relationships where exposed |
| meetings | source | commissioners; statutory boards and commissions; agendas/packets/minutes; votes and recordings when maintained; calendar/feed inventory |
| finance | source | adopted/proposed budgets; annual financial reports and audits; payroll/checkbook/vendor payments when maintained; debt, grants, and revenue reports when published |
| procurement | source | bids/solicitations; awards/contracts; purchase orders and vendor payments when maintained; delegated procurement portal and attachment inventory |
| property | source | auditor/assessment; recorder/deeds; treasurer/tax; parcel/GIS; resolved external provider for any function not county-operated |
| courts | source | county court and clerk topology; authoritative links to local courts serving the county; public docket/case-index/document capability when authorized; explicit access restrictions |
| elections | source | board of elections identity; candidates and precincts; unofficial/official/canvassed/historical results; local campaign-finance filings when maintained |
| public safety | source | sheriff identity; jail/booking when county-operated and lawfully public; incident/dispatch/enforcement data when published; inspection and reporting systems where applicable |
| permits | source | building, zoning, planning, health, environmental, licensing, and code-enforcement providers according to service topology; permit/search/export capabilities when public |
| public records | source | request policy; portal or submission method; contacts; fees; retention schedules; appeal or escalation instructions when officially published |
| feeds | inventory | sitemaps; RSS/Atom/iCalendar; alerts/newsletters; public APIs/exports/change feeds; reviewed negative result for absent update mechanisms |
| archives | inventory | retired domains; predecessor/successor locators; archive candidates; historical repositories/exports; migration evidence; visible temporal boundaries |
| operational metadata | cross-cutting | for every bound source and negative decision: platform/vendor/deployment; locators; auth/access; rate/lease; pagination/cursor; refresh; temporal and jurisdictional scope; artifact/provenance policy; truncation; gaps and reassessment |

The operational-metadata route is derived from the completeness of all bound revisions. No independent source profile can satisfy it by itself.

* REVIEW Independent State Models

** Source state

Allowed states are =:candidate=, =:observed=, =:active=, =:changed=, =:blocked=, =:retired=, and =:rejected=.

#+begin_example
:candidate -> :observed -> :active
:active -> :changed -> :active
:active -> :blocked -> :active
:active -> :retired
:candidate -> :rejected
#+end_example

Workers propose candidate or observed state. The Source Profile Authority writes canonical transitions.

** Review state

Allowed states are =:unreviewed=, =:evidence-collected=, =:verification-pending=, =:reviewed=, =:changes-requested=, and =:invalidated=.

#+begin_example
:unreviewed -> :evidence-collected -> :verification-pending -> :reviewed
:verification-pending -> :changes-requested -> :evidence-collected
:reviewed -> :invalidated
#+end_example

The independent review authority performs reviewed, changes-requested, and invalidated decisions. A changed source creates a new unreviewed revision; it never mutates the previously reviewed revision.

* REVIEW Validation Rules

A profile revision is invalid when authority, locator, deployment, scope, adapter capability, temporal evidence, artifact/provenance, access, browser/OCR, or independent-review requirements are missing.

A route-assessment revision is invalid when:

- the applicability contract, policy snapshot, or exact revision bindings are missing
- a required subfamily lacks a reviewed decision revision
- a non-applicable decision lacks positive authority evidence
- a referenced profile, decision, search plan, deployment, or gap is mutable or unresolved
- a negative state lacks a completed search-plan revision, reviewed gap revision, and reassessment deadline
- a stale negative result is used for current completion
- =:verified-partial= lacks explicit missing scope and reviewed gaps
- a nonterminal state passes a pilot or county gate
- a new result mutates an old revision instead of superseding it
- the operational-metadata route is marked verified while any bound source or gap lacks required operational fields

* REVIEW Parent Actor Contract Requirement

Before implementation, =STAR-RESEARCH-PIPELINE-003= must expose revision-aware message fields and durable ownership for route assessments and independent reviews. Until the parent actor design defines those capabilities, the Ohio design may be reviewed but cannot enter implementation.

* REVIEW Versioning and Migration

- logical IDs remain stable; revision IDs are immutable
- every superseding revision names the revision or revisions it replaces
- locator IDs remain stable while the logical endpoint remains the same
- vendor migrations create new locators and deployment/profile revisions
- retired revisions remain queryable
- applicability or policy migrations force new decision revisions
- unknown newer fields are preserved and never silently discarded
- latest-state materialization never erases historical decision basis

* REVIEW Acceptance Criteria

1. State, county, component, and shared-deployment sources use one revisioned schema.
2. Verified profile revisions always have authority evidence.
3. All sixteen routes have explicit machine-readable subfamily requirements.
4. Operational metadata is a cross-cutting derived route.
5. Route assessments pin exact profile, decision, search-plan, deployment, policy, evidence, and gap revisions.
6. Decisions, gaps, and assessments are append-only and explicitly superseding.
7. =:not-applicable= requires positive authority or topology evidence.
8. Negative findings expire under a declared freshness class.
9. Source and review state are independent.
10. Changed sources create new unreviewed revisions.
11. Browser and OCR evidence have reproducible boundaries.
12. Proposals and canonical writes are separated.
13. The parent actor protocol must become revision-aware before implementation.

* REVIEW Required Fixtures

- verified official and delegated sources
- rejected lookalike domain
- shared deployment used by multiple jurisdictions
- all sixteen route definitions and subfamily rules
- legitimate and rejected =:not-applicable= decisions
- incomplete current-year and participating-unit sources
- scanned PDF returning =:ocr-required=
- browser source with replayable capture bundle
- source migration with predecessor and successor
- expiring negative result and stale-result reassessment
- gap, decision, profile, and assessment supersession replay
- later profile revision that does not alter an older route assessment
- applicability-contract and policy-snapshot migration
