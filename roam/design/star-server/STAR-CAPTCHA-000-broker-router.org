#+title: STAR-CAPTCHA-000 Authorized CAPTCHA Broker and Capability Router
#+description: Provider-neutral StarIntel broker design for authorization, exact solver capability matching, budgeted routing, idempotent external work, opaque result delivery, contract drift, cancellation, and downstream outcome telemetry.
#+status: REVIEW
#+filetags: :starintel:design:star-server:captcha:actors:routing:authorization:secrets:uml:

* Decision

Implement =CaptchaBrokerActor= inside =starintel-server=.[fn:star-server] Keep challenge detection and source-runtime orchestration in =CaptchaDetectActor=. Keep local browser, optical-character-recognition, image-recognition, audio-transcription, manual-operator, custom first-party, and external provider solvers in separately registered capability actors.[fn:capability-actor]

The broker is not a public solve relay. It accepts only authenticated StarIntel actor messages, verifies =captcha:solve= and target policy, and exposes no raw public solve endpoint.

The broker owns:

1. normalized request validation;
2. authentication;
3. =captcha:solve= authorization;
4. target-policy verification;
5. purpose verification;
6. disclosure-class verification;
7. provider allowlist verification;
8. source-session and network-context verification;
9. exact capability matching;
10. rejection of capability widening;
11. budget reservation before external work;
12. attempt journaling before submission;
13. idempotent duplicate RabbitMQ handling;
14. ambiguous create handling without blind retries;
15. cancellation;
16. capability-local contract drift;
17. deadlines;
18. controlled fallback;
19. separately gated speculative execution;
20. opaque result references;
21. redacted cost and outcome telemetry;
22. active-work drain or cancellation during shutdown;
23. terminal normalized replies.

Solver actors own provider-specific authentication, request mapping, browser or recognition execution, polling or callbacks, result validation, error normalization, provider cancellation, provider billing observations, and runtime capability registration.

* Independent Axes

A request separates:

- challenge issuer;
- challenge family;
- challenge variant;
- integration version;
- required source context;
- required result kind;
- solver actor;
- external provider adapter;
- downstream application;
- downstream verification.

A provider lacking hCaptcha support may still be eligible for a separately verified reCAPTCHA, Turnstile, Arkose, GeeTest, Amazon Web Services Web Application Firewall, image, text, audio, puzzle, or custom capability. A successful provider task does not prove target acceptance.

* Capability Contract

Every runtime capability registration records:

- actor and provider identifier;
- adapter version;
- official source and retrieval date;
- issuer, family, variant, and integration-version predicates;
- required and optional request fields;
- result kind and required result fields;
- proxy, cookie, user-agent, browser-session, same-network, and mobile requirements;
- execution class: local automated, external automated, human worker, or operator review;
- disclosure class;
- request and result operations;
- polling or callback model;
- cancellation, idempotency, and ambiguous-create behavior;
- concurrency, health, circuit, quota, and billing model;
- retention and error contract;
- fixture fingerprint and freshness;
- live-probe requirements;
- unsupported variants and contradictions;
- capability state.

Allowed capability states are:

| State | Broker behavior |
|-------+-----------------|
| =verified= | Eligible when every hard requirement matches |
| =experimental= | Eligible only under explicit experimental policy |
| =degraded= | Eligible only when the known limitation does not violate the request |
| =invalidContract= | Ineligible; isolate the failed capability and require contract repair |
| =disabled= | Ineligible by operator, circuit, or deployment policy |
| =unsupported= | Ineligible because the exact capability is not advertised |

Static manifests describe discovery and possible registration. They do not advertise an unverified runtime capability as active.

* Exact Eligibility

Phase 1 is a hard filter. Reject any solver that fails any exact requirement:

- issuer;
- family;
- variant;
- integration version;
- required fields;
- result kind;
- source-session binding;
- network binding;
- cookie support;
- proxy support;
- user-agent fidelity;
- mobile runtime requirements;
- execution class;
- disclosure class;
- provider allowlist;
- provider contract state;
- deadline feasibility;
- available concurrency;
- reserved budget.

A v2 capability does not imply v3. A token capability does not imply assessment, cookie, coordinates, selections, or interaction plans. A proxyless task does not imply same-network support. An automated capability does not imply human-worker disclosure permission.

* Ranking Eligible Solvers

Phase 2 ranks only hard-eligible solvers in this order:

1. operator pin;
2. contract confidence;
3. fixture freshness;
4. source-context fidelity;
5. exact-capability downstream acceptance rate;
6. provider health;
7. available concurrency;
8. deadline fit;
9. cost per accepted result;
10. operator preference.

Cost cannot override authorization, context fidelity, disclosure, exact capability, or contract validity. A provider name alone is never enough to select an adapter.

Never persist raw API keys, result tokens, cookies, text answers, coordinates, selection sets, interaction plans, proxy credentials, cookie bundles, enterprise data, page data, authorization headers, or authenticated browser-session material.

* Idempotency and Ambiguous Submission

=requestId= is the logical request key. =attemptId= identifies one reserved external or local attempt. The broker journals =reserved= before submission and =submitted= before handing work to a solver.

Duplicate RabbitMQ deliveries attach to the active run or replay its terminal normalized result. They do not reserve another budget or create another provider task.

An ambiguous create enters =uncertain=. The adapter uses only provider-supported idempotency, client keys, or lookup/recovery operations. It never blindly creates a replacement paid task. A terminal ambiguous failure sets =chargePossible=true= when billing cannot be excluded.

* Fallback and Speculation

Fallback is disabled by default. It requires:

- another exact eligible capability;
- remaining reserved budget;
- disclosure permission for the next actor;
- deadline fit;
- a terminal or explicitly fallback-eligible prior outcome;
- an incremented attempt ID;
- no blind retry of an ambiguous create.

Speculative parallel execution is a separate policy gate because it can disclose challenge data to multiple parties and incur multiple charges. Enabling fallback does not enable speculation.

* Cancellation and Shutdown

=captchaSolveCancel= identifies =requestId=. The run actor records cancellation requested, calls adapter cancellation when supported, releases unused budget, deletes unconsumed result leases, emits whether work may still complete or charge, and returns one terminal cancellation result when possible.

Shutdown stops new reservations, drains active work until a bounded deadline, cancels remaining jobs where possible, expires result leases, records unresolved provider jobs, and terminates run actors. Active provider work is not silently abandoned.

* Downstream Verification Telemetry

The detector reports =accepted=, =rejected=, =expired=, =replaced=, or =inconclusive= with a redacted evidence reference. Ranking uses acceptance rate only for the exact issuer, family, variant, integration version, result kind, binding, and solver capability. Provider task success alone never counts as accepted.

* Actor Manifest Requirements

The server actor manifest declares the broker role and accepted message types, authorization requirements, secret-lease dependency, budget dependency, policy dependency, and runtime capability-registry dependency. It contains no provider hosts, credentials, raw task contracts, or active capability claims.

Each solver actor manifest declares possible operations and runtime registration behavior. Exact active capabilities are registered only after configured credentials, current contract checks, and fixtures establish their state. Actor manifests do not contain =documentIds=.

* Footnotes and Glossary

[fn:star-server] StarIntel Server: The Common Lisp service that owns core control, routing, persistence, authorization, search, and actor hosting.

[fn:capability-actor] Capability actor: An actor that advertises a precise operation, required input context, result kind, execution class, disclosure class, and current contract state.

- *Ambiguous create* — A provider task-creation request whose transport outcome is unknown, so another creation could duplicate work or cost.
- *Capability widening* — Treating one issuer, variant, version, field set, result kind, binding, execution class, or disclosure class as another without evidence.
- *Cost per accepted result* — Total capability-specific cost divided by results later verified as accepted by the target, not merely completed by the provider.
- *Opaque result reference* — A short-lived identifier that authorizes one bounded secret read without putting sensitive result material in actor messages.
- *Speculative execution* — Concurrently sending the same logical challenge to multiple solvers before a prior attempt reaches a fallback-eligible state.
