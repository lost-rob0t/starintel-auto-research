* Final Language Decision

Common Lisp is the sole approved Star-Lang implementation language.

Every alternate parser, compiler, semantic engine, dispatcher, and runtime implementation is DENIED.

The language and architecture decision is final. The implementation remains active until its acceptance ledger is complete.

LISA, SWI-Prolog, and N-Prolog are inference backends called by the Common Lisp StarLang runtime. They do not implement the StarLang parser/compiler/runtime and therefore do not reopen the language decision.

Initial backend contract:

| Backend | Initial role |
|---------+--------------|
| =swi-prolog= | Default recursive, tabled, constrained, and named-query reasoning runtime |
| =lisa= | Production-rule, agenda/salience, persistent working-memory, and classic expert-session runtime; large-workload =auto= promotion remains benchmark-gated |
| =n-prolog= | Explicitly supported portable-Prolog/compatibility runtime with fixture-backed capability claims |

StarLang source selects backend policy only through =(pragma :backend ...)= as specified by STAR-LANG-RESEARCH-026. =:auto= selects deterministically during plan materialization. The selected backend is then immutable for the run; runtime load/failure cannot silently switch engine type.

The portable =star.logic.api/1= contract does not expose native engine semantics through misleading generic names. In particular:

- =assert!= adds one typed StarLang session fact; it is not Prolog =assertz= and not raw LISA =ASSERT=;
- =retract!= retracts by stable StarLang fact identity; it is not Prolog pattern =retract/1=;
- =solve=/=solutions=/=exists?= invoke compiler-declared named operations, never caller-selected raw native goals;
- Prolog clause order/retraction, SWI transactions/snapshots/tabling, and LISA agenda/focus/modify/belief behavior require explicit semantic profiles.

The proposed future =star-rules= optimization may replace or extend the LISA adapter implementation only after its semantic compatibility and benchmark gates pass. StarLang source must not depend on that internal optimization name unless it becomes a genuinely distinct semantic backend.

* Expert-System Decision

=expert-system= will be a StarLang compiler surface, not an embedded native rule language.

Initial expert features under review:

- typed facts reusing StarLang schemas;
- named rules with lexical typed variables;
- explicit conjunction/disjunction/existence/absence/negation semantics;
- checked conclusions separated from canonical source facts;
- goals;
- typed questions through an ExpertSessionActor question port;
- normalized proof/explanation graphs;
- explicit uncertainty algebra, with boolean reasoning required first;
- backend compatibility validation and selection evidence.

Raw =(prolog "...")= and raw LISA/Common Lisp =defrule= escape hatches are denied.

STAR-LANG-009 does not approve the complete STAR-LANG-RESEARCH-023 surface. It specifies the runtime/API contract that any approved expert sugar must lower into.

* Invariants

- Star-Lang implementation code is Common Lisp only.
- Untrusted =.star= source never enters the Common Lisp reader.
- No unrestricted =EVAL= enters compilation or execution.
- Source macros do not execute arbitrary Common Lisp transformer code.
- Macro dependencies are exact-versioned and digest-locked.
- Macro expansion is hygienic, deterministic, resource-bounded, and source-traceable.
- Macros and expert sugar expand completely before runtime execution and do not enter runtime as executable source forms.
- Normalized IR does not contain cl-gserver object types.
- Normalized IR does not contain native Prolog terms, LISA objects, sessions, sockets, engine handles, or raw engine code.
- Versioned JSON is an interchange format, not another implementation.
- Direct execution works without cl-gserver.
- Sento is accessed through a Common Lisp compatibility port.
- Every generated actor has bounded mailbox and restart declarations.
- Durable jobs are not mailbox contents.
- Retry creates a new lease-bound attempt.
- Capability grants come from manifests, never retrieved content.
- Durable artifact success requires a durable evidence-delivery intent or one transactional downstream release.
- Logic backends are selected and pinned before execution; runtime load does not change engine semantics.
- Explicit backend pins still require semantic-profile/capability compatibility.
- Backend recovery may replace an instance only with an equivalent instance of the same pinned backend/build contract.
- Expert source facts cannot be mutated by inference rules; conclusions and session facts are separate state classes.
- Expert questions are typed effect requests and are journaled before answers become facts.
- Ambiguous bare negation is denied; absence, negation as failure, inequality, and contradiction remain distinct.
- Portable =assert!= and =retract!= operate on stable StarLang session-fact identity, never native clause ordering or pattern semantics.
- Logical zero-answer completion is distinct from backend failure.
- Native Prolog =call=/cut/consult and raw LISA/Common Lisp execution are denied as portable source operations.
- Backend-specific API semantics require versioned profiles and fixture-backed descriptor claims.
- Research nodes never extend the StarIntel schema.
- Auto-dig and Quasar consume contracts rather than defining them.
- Alternate implementation languages remain DENIED.

* Footnotes and Glossary

- *Implementation index* — Active ledger connecting approved architecture, research/design under review, work order, invariants, and completion gates.
- *Inference backend* — LISA, SWI-Prolog, or N-Prolog engine accessed by the Common Lisp StarLang runtime through a checked adapter.
- *Backend policy* — =auto= or an explicit backend pin in StarLang source/deployment configuration; source syntax is =(pragma :backend ...)=.
- *Expert system surface* — Closed StarLang syntax for facts, rules, goals, questions, conclusions, proofs, and uncertainty that lowers to engine-neutral IR.
- *Engine conformance* — Fixture-backed evidence that an adapter implements the semantic profiles/capabilities it advertises.
- *Logic API contract* — =star.logic.api/1= portable session/fact/query/result/cancellation contract, separate from profiled backend-native semantics.
