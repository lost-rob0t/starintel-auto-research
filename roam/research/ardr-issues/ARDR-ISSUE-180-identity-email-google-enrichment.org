* Verified Existing-State Finding

Current StarIntel server research found no existing Holehe/GHunt/email-enrichment implementation. The older `user-hunt` shape is already being replaced by the Identity Domain Server direction, so email enrichment should extend that domain and its Platform Probe Registry rather than revive a separate tool service.

* Upstream Semantics

Holehe-style modules commonly use provider-specific signup/registration availability requests, response/status predicates, and fields representing existence and rate-limit state. A key semantic risk is collapsing rate-limit/transport/blocking paths into `exists=false`; StarIntel must preserve uncertainty instead of turning failure into a false negative. Multi-step probes fit closed Source Acquisition definitions rather than arbitrary Python callbacks.

GHunt-style enrichment composes multiple Google-facing public/profile sources. Upstream schema drift and missing nested fields have caused real failures, so missing/changed fields must degrade to `unknown`/`partial`, never `notFound` or a process crash. Google credential/session material must never be embedded in StarLang definitions, fixtures, logs, provenance, or normal messages.

* Research Conclusion

Keep one Identity Domain Server with two capability families:

1. Email account-existence probes using the same versioned Platform Probe Registry generalized to `identifierType=email`.
2. Richer Google public-profile enrichment as an Identity provider/source that emits independent typed observations for evidence-supported public surfaces.

Per-provider outcomes must distinguish `found | notFound | unknown | blocked | unavailable | failed`; aggregate runs distinguish `success | partial | cancelled | failed`. `notFound` requires explicit current negative evidence. Network failure, rate limits, challenges, parse drift, or missing optional fields never mean absence.

Probe definitions require explicit side-effect classification. Default policy allows read-only/account-availability checks that do not create accounts, send recovery email/SMS, mutate remote state, or notify targets. Potentially notifying/mutating/unknown probes fail closed unless specifically authorized.

Reuse shared StarLang Source Acquisition and bounded orchestration work for fan-out, deadlines/cancellation, typed partial outcomes, opaque credential/session/artifact refs, provenance propagation, and local/remote lifecycle. No email-specific syntax is justified.

Common Lisp Identity implementation owns normalization, registry validation, policy, provider selection, typed classification, and canonical ingest. A GHunt-compatible Python process is only a later last-resort isolated provider adapter if a valuable surface cannot reasonably use approved HTTP/browser/source ports.

Accepted observations enter canonical ingest as observations, not automatic same-person merges. Entity correlation remains the expert/entity-resolution layer.

* Adversarial Findings

Rejected: Holehe or GHunt as the control plane, a second email registry, false-negative collapse, recovery/reset side effects by default, registry-defined arbitrary callbacks, cross-principal Google sessions, automatic identity merge, Python-first provider logic, unlimited provider sweep, and raw response persistence by default.

* RED-First Targets

Required future negative fixtures include email probe-registry schema absence, transport/rate-limit not becoming `notFound`, default rejection of side-effecting probes, mixed provider outcomes producing terminal `partial`, missing Google nested metadata producing `unknown`/`partial`, rejection of raw credential literals, and canonical ingest/provenance without auto-merge.

* Research Decision

Evidence is sufficient for design; implementation remains operator-only.

* Footnotes and Glossary

- *Side-effect class* :: Probe metadata declaring whether a collection action is read-only, may notify the target, may mutate remote state, or is unknown.
- *Partial* :: A terminal aggregate where some providers/sub-sources yielded usable observations while others were blocked, unavailable, unknown, or failed.
