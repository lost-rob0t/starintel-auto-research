* Operator Direction / Supersession

This revision supersedes the first STAR-SERVER-042 design shape that attempted to make a closed StarIntel workload topology and managed-router pool model the center of #35.

The corrected requirement is:

#+begin_quote
Preserve Sento's router and dispatcher behavior. Add total concurrency accounting at the backend where Sento actually creates execution threads.
#+end_quote

Workload-specific named dispatchers remain available exactly as Sento already supports them. Routers retain their existing strategies and routee semantics. Neither needs a replacement abstraction for this P0.

* Decision

Add one aggregate *Sento execution-lane authority* beneath the existing actor-system dispatcher/pinned-mailbox realization path.

The authority receives a numeric grant from StarIntel's already-defined process-wide thread planner. It tracks the Sento-owned actor-execution contribution to that process budget.

The invariant is:

#+begin_example
used-sento-execution-lanes <= granted-sento-execution-lanes
#+end_example

No new user-facing total-thread configuration is introduced. The canonical process ceiling remains the existing process-wide authority from #177.

* Preserve Existing Behavior

The implementation MUST retain:

- actor-system named dispatcher configuration;
- per-dispatcher =:workers= counts;
- dynamic =register-new-dispatcher= semantics;
- shared dispatcher's internal Sento router;
- router =:random= strategy;
- router =:round-robin= strategy;
- custom count-to-index router strategies;
- =message-box/dp= for actors on shared/named dispatchers;
- =message-box/bt= for actors selecting reserved =:pinned=;
- one-message-at-a-time state protection of dispatcher-backed actors;
- existing dispatcher/router public behavior and tests.

This feature changes whether new execution capacity may be realized, not how already-admitted actor messages are routed.

* Execution-Lane Model

A *Sento execution lane* is one long-lived Sento-owned actor processing thread.

| Owner | Lane cost |
|-------+-----------|
| one shared-dispatcher worker | 1 |
| shared dispatcher with N workers | N |
| ordinary actor using =:pinned= | 1 |
| ordinary actor using =message-box/dp= | 0 |
| router object | 0 |
| router routee membership | 0 |

The model follows directly from the pinned dependency implementation: shared-dispatcher workers are themselves =:pinned= actors; =message-box/bt= owns one thread; =message-box/dp= owns no thread; routers only choose and forward to routees.

* Authority Placement

The concurrency ledger is process-scoped for StarIntel composition and may be referenced by the Sento actor system(s) created under that composition.

Conceptual state:

#+begin_example
sento-concurrency-authority
  grant: integer
  used: integer
  owners: owner-id -> lane-reservation
#+end_example

Useful read-only projection:

#+begin_example
(:grant 8
 :used 6
 :free 2
 :owners ((:dispatcher :shared 4)
          (:dispatcher :storage 1)
          (:pinned-actor "/user/rabbit-owner" 1)))
#+end_example

Exact Common Lisp representation is implementation detail. A lock-protected counter and ownership hash table are sufficient.

The authority MUST NOT become a scheduler, priority engine, dispatcher replacement, or second process-budget owner.

* Startup Preflight

Configured shared dispatchers are known before worker creation. Their requested worker counts must be summed before the first dispatcher worker is realized.

Given:

#+begin_example
:shared  workers=4
:storage workers=4
Sento grant=6
#+end_example

actor-system startup fails with a typed capacity condition before creating dispatcher worker threads.

Given:

#+begin_example
:shared  workers=4
:storage workers=2
Sento grant=6
#+end_example

startup is an exact fit: =used= becomes 6 and =free= becomes 0.

This preserves every local =:workers= setting while finally giving those settings one aggregate ceiling.

* Dynamic Dispatcher Registration

=register-new-dispatcher= remains supported.

Before creating its worker actors, the operation atomically reserves the requested number of lanes.

If capacity is insufficient:

- signal a typed =sento-concurrency-exhausted= or equivalent condition;
- create no worker threads;
- do not partially register the dispatcher.

If realization fails after reservation:

- stop any workers already created;
- remove incomplete registration;
- release the entire reservation exactly once.

* Pinned Actor Creation

An ordinary actor created with =:dispatcher :pinned= consumes one lane.

Reservation must occur before constructing the =message-box/bt= that starts its Bordeaux thread.

If =free= is zero, actor creation fails before thread creation.

This requires a narrow internal hook in the actor-context/message-box realization path. It does NOT change what =:pinned= means to callers.

* Dispatcher Workers Are Not Double-Charged

A shared dispatcher first reserves N lanes as one atomic dispatcher realization.

Its internal N workers are then created as pinned actors under that existing reservation. Internal worker construction receives reservation ownership/tokens so the normal pinned-actor path does not increment the ledger again.

Required invariant:

#+begin_example
dispatcher workers=4 -> used increases by exactly 4, never 8
#+end_example

How reservation tokens are represented is private Sento/runtime machinery.

* Pinned Thread Restart Semantics

=message-box/bt= can restart its processing thread if that thread died while the mailbox remains live.

Concurrency ownership belongs to the live pinned mailbox/actor, not to one particular thread object. Restarting the same mailbox therefore consumes no additional lane.

A leaked restart must not increase =used=.

* Release Semantics

Reservations are released on confirmed owner termination, exactly once.

** Ordinary pinned actor

- stop requested: reservation remains owned while the mailbox thread may still be active;
- actor/mailbox terminal stop: release one lane;
- duplicate stop/notification: no second decrement.

** Shared dispatcher

- each worker reservation is associated with the dispatcher reservation;
- dispatcher shutdown eventually releases N lanes after its workers terminate;
- partial construction rollback releases any reserved but unrealized/terminated ownership;
- duplicate dispatcher stop cannot release more than N.

Unknown owner release is a deterministic error/diagnostic in tests rather than silently corrupting the counter.

* Router Boundary

Routers remain unchanged.

A router has no execution lane of its own. Adding or removing a routee does not alter total concurrency merely because membership changed.

If the routee is an already-existing pinned actor, its lane is already owned by that actor. If it is dispatcher-backed, its lane cost remains zero. The router never becomes a second capacity owner.

Current limitations such as message-unaware custom strategy functions or lack of keyed affinity are separate future research. They are intentionally removed from this P0 implementation gate.

* Dispatcher Identity

=:pinned= remains the built-in dedicated-thread selection and MUST NOT be used as a custom named shared-dispatcher ID in StarIntel configuration.

This is independent of total accounting but must be corrected because current Sento resolves =:pinned= before named-dispatcher lookup.

StarIntel may retain whatever non-reserved named dispatcher IDs best express its existing workload separation. This design does not require a new closed workload-class schema.

* Process-Budget Integration

The process-wide planner remains authoritative for:

- =*max-process-threads*=;
- =*reserved-control-threads*=;
- non-Sento runtime thread demands;
- the number of Sento execution lanes granted to this authority.

Sento does not independently read or reinterpret the process maximum as if every process thread belonged to it.

Conceptually:

#+begin_example
process plan
  max process threads = 32
  reserved control = 4
  non-Sento planned threads = X
  granted Sento lanes = G

Sento ledger
  limit = G
  used <= G
#+end_example

This keeps one process authority while allowing Sento to enforce its own exact realization boundary.

* Observability

Expose, at minimum:

- granted Sento lanes;
- used Sento lanes;
- free Sento lanes;
- reservation count by owner;
- owner kind;
- dispatcher ID or actor path where applicable.

These values are useful to #36 admission/overload policy, but #36 remains responsible for queue admission, rejection, dropping, blocking, prefetch, and overload result semantics.

No raw thread object needs to be exposed through the StarIntel product API.

* Proposed Implementation Slices

Every slice remains =AWAITING_OPERATOR_IMPLEMENTATION_APPROVAL=.

** Slice 1 — pure concurrency ledger + startup demand preflight

No production thread behavior is changed until the ledger tests are RED.

Implement a small concurrency authority with atomic reserve/release and owner tracking. Add a pure configured-dispatcher demand calculation used before dispatcher initialization.

Mandatory RED-first fixtures:

1. requested dispatcher workers 4 + 4 with grant 6 -> typed failure;
2. exact fit 4 + 2 with grant 6 -> success, used=6/free=0;
3. duplicate owner reservation rejected;
4. over-release/unknown release rejected;
5. duplicate release cannot decrement twice;
6. deterministic owner snapshot/counts.

** Slice 2 — shared-dispatcher realization integration

Reserve configured/dynamic dispatcher workers before their internal pinned actors start.

RED-first fixtures:

- 4-worker dispatcher raises used by exactly 4;
- its internally pinned workers do not double-charge;
- failed worker construction rolls back all four units;
- dispatcher stop returns exactly four units.

** Slice 3 — ordinary pinned actor integration

Reserve one unit before =message-box/bt= starts.

RED-first fixtures:

- grant exhausted -> pinned actor construction fails before starting a thread;
- dispatcher-backed actor creation leaves used unchanged;
- pinned actor stop releases one;
- pinned mailbox thread restart leaves used unchanged.

** Slice 4 — StarIntel process-plan wiring

Feed the Sento authority its numeric grant from #177's process planner and remove the dead StarIntel custom =:pinned= shared-dispatcher configuration.

Do not replace Sento routing or change dispatcher worker strategies.

** Slice 5 — diagnostics / #36 handoff

Expose read-only total/used/free/owner counts to runtime health/diagnostics and as an input to later #36 admission policy.

* Adversarial Review

** Reject: replace Sento routers with a StarIntel pool manager for this feature

Routers create no execution threads. Replacing routing policy does not solve the multiplicative dispatcher/pinned-thread count.

** Reject: invent a closed workload-class DSL as the concurrency authority

The existing Sento named-dispatcher model already expresses dispatcher separation. The missing invariant is aggregate capacity, not another naming layer.

** Reject: remove per-dispatcher =:workers=

Local worker counts remain useful. The total authority constrains their sum; it does not flatten every dispatcher to one shared size.

** Reject: count actors rather than execution lanes

Dispatcher-backed actors own no thread. Counting them would artificially cap actor population and destroy the reason Sento has shared dispatchers.

** Reject: count router routees

Routees may be pinned or dispatcher-backed. Membership is not capacity ownership and would double-count pinned actors.

** Reject: let each dispatcher maintain its own maximum only

That preserves the original multiplication defect. Independent maxima need one aggregate ceiling.

** Reject: reserve once for the dispatcher and again through each internal =:pinned= worker

That double-counts every shared-dispatcher worker.

** Reject: decrement on stop request instead of termination

That advertises capacity as free while its previous worker thread may still be alive.

** Reject: use =bt:all-threads= as the authority

Process thread enumeration cannot distinguish ownership reliably and includes unrelated runtime threads. Accounting must be explicit at creation/release boundaries.

** Reject: add another user-facing max-concurrency config competing with =*max-process-threads*=

StarIntel already has the process authority. Sento receives a grant from it.

** Reject: change random/round-robin/custom router semantics in the same slice

No evidence requires that change to enforce total concurrency. Preserve existing behavior and tests.

* Acceptance Criteria

- existing Sento dispatcher/router/mailbox semantics remain intact;
- existing router strategy tests remain green unchanged;
- existing dispatcher behavior remains green except where new capacity failure is intentionally exercised;
- all configured shared-dispatcher workers fit one aggregate Sento grant before worker realization;
- dynamic dispatcher creation reserves atomically;
- every shared-dispatcher worker costs exactly one lane;
- every ordinary pinned actor costs exactly one lane;
- dispatcher-backed actors cost zero additional lanes;
- routers and routee membership cost zero additional lanes;
- no double charging of internally pinned dispatcher workers;
- no capacity leak on construction failure, stop, or thread restart;
- total/used/free and ownership diagnostics are available;
- StarIntel process thread budget remains the sole canonical process maximum;
- =:pinned= is no longer used as a custom named StarIntel shared dispatcher;
- no new StarLang syntax, routing system, scheduler, external supervisor, or Python controller is introduced;
- implementation remains blocked until an exact slice receives operator authorization.

* Footnotes and Glossary

- *Execution lane* :: One Sento-owned long-lived actor-processing thread reserved by a shared-dispatcher worker or ordinary pinned actor.
- *Concurrency authority* :: Small reservation ledger enforcing Sento's granted aggregate execution-lane maximum.
- *Dispatcher-backed actor* :: Actor whose =message-box/dp= runs on existing shared-dispatcher workers and owns no dedicated thread.
- *Pinned actor* :: Actor whose =message-box/bt= owns one dedicated processing thread.
