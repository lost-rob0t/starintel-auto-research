* Research Question

How should the existing =discord.js-selfbot-v13= Discord Watch prototype be ported into StarIntel so that it:

1. preserves controlled user-session collection required by the authorized prototype;
2. runs as a supervised actor subsystem rather than a single unstructured process;
3. enforces case, account, guild, channel, thread, time, and collection boundaries;
4. emits deterministic StarIntel documents with complete provenance;
5. publishes without silently losing documents;
6. supports reconnect, resume, backfill, edits, deletes, replies, reactions, attachments, and checkpoints;
7. can migrate away from an archived JavaScript dependency;
8. ends with a native Common Lisp collector without coupling the rest of StarIntel to Discord protocol drift.

* Authorization Assumption

This research assumes a controlled law-enforcement prototype with recorded authority, approved accounts, approved Discord locations, an explicit collection period, and operator audit requirements.

Authorization is represented as runtime data, not as a comment or deployment convention. Every target must carry a non-secret authorization reference, case identifier, approved scope, activation time, expiration time, and collection capabilities. The actor must stop when the target expires or is revoked.

This assumption permits the design to preserve user-session collection. It does not make the public bot-oriented Gateway documentation a complete specification for user sessions. User-client-specific behavior remains isolated behind a replaceable adapter and must be verified with fixtures.

* Existing Prototype Audit

The current JavaScript prototype proves the minimum vertical slice:

- retrieve Discord Watch targets from Star Server;
- start one Discord client per supplied credential;
- receive =messageCreate= events;
- create User, Message, and Relation documents;
- publish documents to the =documents= topic exchange;
- consume new target configurations from =actors.discordwatch.new.target=.

It is useful seed code, but it is not yet a reliable collector.

** Immediate correctness defects

1. =target.hasOwn(options, "type")= is invalid. =target= does not provide that method and =options= is unbound. The intended check is equivalent to =Object.hasOwn(target.options, "type")=.
2. The Relation document is created but never published.
3. =await channel.publish(...)= does not wait for broker acceptance. =amqplib= publishing is not a promise-based delivery confirmation.
4. The consumer acknowledges a target immediately after =createClient= returns even though login and readiness have not been established.
5. A parse, validation, login, or startup failure has no dead-letter or negative-ack policy.
6. =message.edited= is not the stable Discord.js edit timestamp field expected by current message objects; =editedTimestamp= or =editedAt= must be preserved.
7. =message.guild.name= fails for direct messages and can be absent during partial-cache conditions.
8. =message.channel.name= can be absent or incomplete for direct messages, partial channels, and some thread states.
9. The code generates a new ULID for every observed message. Replays and reconnect duplicates therefore create duplicate Message documents.
10. The user identity does not explicitly preserve the Discord snowflake as the stable native identifier.
11. The Relation identity is not deterministic.
12. The raw Discord event and original content are not preserved.

** Scope and lifecycle defects

1. The =target= argument is not used to filter guilds, channels, threads, users, time ranges, or event classes.
2. Clients are keyed by the raw API key. This keeps credentials in ordinary process memory structures and makes logging or inspection dangerous.
3. One credential can only create one client entry. Additional datasets or scopes using the same authorized account are silently ignored.
4. The listener is installed inside the =ready= callback. Repeated ready transitions can install duplicate listeners.
5. There is no explicit stop, revoke, expire, rotate, reconnect, resume, shutdown, or graceful-drain path.
6. There is no checkpoint containing session ID, sequence number, last message snowflake, or backfill cursor.
7. There is no supervisor or restart-intensity policy.
8. The full Axios response is logged and target retrieval may expose credential-bearing configuration.
9. The token is stored in =target.target=, mixing a secret with target semantics and making it likely to enter StarIntel documents, queues, logs, exports, or audit views.
10. There is no account-to-case or session-to-authorization audit record.

** Data-loss and coverage defects

1. No publisher confirms are enabled.
2. Published messages are not marked persistent.
3. =mandatory= routing and returned-message handling are absent.
4. User and Message are published independently without a durable operation envelope, so partial publication can leave dangling relations.
5. Attachments, embeds, stickers, polls, references, replies, reactions, mentions, thread metadata, edits, and deletes are not handled.
6. =cleanContent= is used as the only content representation. Raw content and resolved display text must both be preserved.
7. There is no raw-event artifact, event hash, or replay fixture.
8. There is no deduplication on Discord message ID and revision.
9. There is no historical backfill.
10. There is no audit record proving why an event was accepted or rejected by scope.

* External State

The current =discord.js-selfbot-v13= repository was archived on 2025-10-11 and is no longer maintained.[fn:discord-js-self-archive] It remains a useful behavioral reference and short-term adapter, but it should not be the permanent protocol foundation.

Discord's official Gateway documentation defines the WebSocket lifecycle, dispatch envelope, sequence numbers, heartbeats, Identify, Ready, Resume, reconnect, invalid-session handling, and Gateway intents.[fn:discord-gateway] The Message Create event carries the message object plus guild/member context where available.[fn:discord-gateway-events] Those documents describe supported application behavior and do not fully document user-client-specific fields.

Current Common Lisp Discord libraries are not suitable as the direct foundation:

- Lispcord describes itself as a bot API wrapper and explicitly says it is not alpha quality.[fn:lispcord]
- Dithcord is an incomplete modular layer over Lispcord and still requires Lispcord functions.[fn:dithcord]

The maintained Python =discord.py-self= project is a viable temporary compatibility adapter because it implements user-account API behavior and asynchronous event handling.[fn:discord-py-self] It is not the selected core because it would leave StarIntel supervision, normalization, checkpoints, and transport semantics in a second runtime.

RabbitMQ documents that a socket write does not prove broker acceptance, and recommends publisher confirms for reliable publishers. Persistent messages, durable queues, confirms, and unroutable-message handling must be combined; none alone is sufficient.[fn:rabbitmq-publishers][fn:rabbitmq-confirms]

* Decision

Create a new Common Lisp subsystem named =star-discord-watch=.

The subsystem has two boundaries:

1. a StarIntel-native collection core implemented in Common Lisp;
2. a replaceable Discord session adapter.

The collection core owns:

- target and authorization validation;
- credential leases;
- session supervision;
- scope filtering;
- deterministic document identity;
- raw-event preservation;
- normalization;
- edit and deletion revision handling;
- attachment scheduling;
- checkpoints;
- reliable publication;
- audit events;
- metrics;
- replay tests.

The adapter owns only Discord protocol behavior:

- connect;
- authenticate using a credential lease;
- heartbeat;
- reconnect;
- resume;
- emit normalized transport events;
- perform bounded historical fetches;
- fetch referenced messages and attachments;
- expose protocol capability and version metadata.

The first operational port may run the existing Node implementation or =discord.py-self= as a supervised sidecar adapter while the Common Lisp core is built. The final target is a native Common Lisp passive-collection adapter implementing only the Gateway and HTTP behavior required by Discord Watch.

Do not port the entire =discord.js-selfbot-v13= API surface. Port the passive collection state machine and required resource fetches.

* Port Candidate Evaluation

| Candidate                                      | Time to first event | Maintenance risk | Native supervision | User-session coverage | Decision |
|------------------------------------------------+---------------------+------------------+--------------------+-----------------------+----------|
| Keep current Node process unchanged            | Very low            | Very high        | No                 | Existing              | Reject   |
| Supervise current Node library as an adapter    | Low                 | High             | Yes                | Existing              | Bridge   |
| Python =discord.py-self= sidecar                | Low                 | Medium           | Yes                | Strong                | Fallback |
| Fork Lispcord                                  | Medium              | Very high        | Yes                | Weak/unknown          | Reject   |
| Build on Dithcord                              | Medium              | Very high        | Yes                | Weak/unknown          | Reject   |
| Native Common Lisp minimal Gateway adapter      | Medium/high         | Controlled       | Yes                | Purpose-built         | Target   |
| Port all of =discord.js-selfbot-v13= to Lisp    | Extreme             | Extreme          | Yes                | Broad                 | Reject   |

The selected path is a strangler migration:

1. freeze observable behavior with raw-event fixtures;
2. move scope, normalization, IDs, publication, audit, and checkpoints into Common Lisp;
3. run the old JavaScript client behind a narrow adapter;
4. add a Python adapter as an independent compatibility oracle;
5. implement the native Common Lisp adapter;
6. compare all adapters against the same fixtures and live bounded test scope;
7. remove the archived JavaScript dependency when native acceptance tests pass.

#+begin_example

├── credential-lease-supervisor

├── session-supervisor

├── replay-supervisor
└── audit
#+end_example

One Discord account session may serve multiple authorized target subscriptions. A target does not own a token and does not create a duplicate client. The session registry keys sessions by account and credential reference, while the subscription registry keys collection scopes by target ID and dataset.

Recommended restart policy:

- root: =one-for-one=;
- per-session subtree: =rest-for-one=, ordered adapter, scope filter, journal, normalizer, publisher;
- attachment workers: temporary children with bounded concurrency;
- publisher failure: pause event acknowledgement and retain journaled operation batches;
- credential revocation or target expiration: permanent stop, no automatic restart;
- repeated authentication failure: quarantine the credential lease;
- protocol drift: stop the adapter and preserve the last raw frame plus version metadata.

* Scope Evaluation

Every event is evaluated against every active subscription attached to its session.

Evaluation order:

1. target active;
2. current time inside =valid_from=/=expires_at=;
3. session account approved;
4. event type approved;
5. guild approved;
6. channel or thread approved;
7. optional user filter approved;
8. backfill time window approved;
9. collection capability approved;
10. duplicate/revision check.

The audit actor records a compact decision:

* Document Identity and Revision Rules

Use Discord snowflakes as native identifiers and deterministic StarIntel IDs.

Recommended identifiers:

- User: =discord:user:<user-snowflake>=
- Guild: =discord:guild:<guild-snowflake>=
- Channel: =discord:channel:<channel-snowflake>=
- Message: =discord:message:<message-snowflake>=
- Posted relation: =discord:relation:posted:<message-snowflake>=
- Reply relation: =discord:relation:reply:<message-snowflake>:<referenced-message-snowflake>=
- Attachment: =discord:attachment:<attachment-snowflake>=
- Raw event: =discord:event:<session-id-hash>:<sequence>=

A replay of the same message updates or confirms the same document. It does not allocate a fresh ULID.

Message updates create a new document revision under the stable message ID. Preserve:

- Discord message ID;
- event type;
- Gateway sequence;
- =created_at=;
- =edited_at=;
- collection timestamp;
- raw content;
- clean/resolved content;
- author ID;
- guild ID;
- channel ID;
- thread and parent channel IDs;
- message reference;
- mentions;
- attachments;
- embeds;
- stickers;
- components;
- flags;
- poll data when present;
- raw-event artifact reference;
- adapter name and version;
- target and authorization references;
- content hash;
- revision hash.

Deletes create a tombstone revision. Do not erase prior retained revisions from the evidence store.

* RabbitMQ Publishing Rules

The publisher actor must:

- use a long-lived confirm channel;
- declare the =documents= topic exchange as durable;
- publish with =persistent=true=;
- publish with =mandatory=true=;
- register returned-message handling;
- correlate each publish with =batch_id= and operation ID;
- wait for asynchronous publisher confirms;
- retry unconfirmed operations with bounded exponential backoff;
- retain pending batches in the local journal;
- use deterministic document IDs so retries are idempotent;
- expose confirm latency, nack count, return count, retry count, and pending batch count;
- pause upstream acknowledgement when the journal or publisher exceeds its budget.

Routing keys remain:

- =documents.new.user=
- =documents.new.message=
- =documents.new.relation=
- =documents.new.attachment=
- =documents.new.guild=
- =documents.new.channel=

An optional future =documents.batch.discord= route may carry the whole operation batch, but downstream consumers must not be forced to adopt it before they support atomic batches.

* Native Common Lisp Core Example

The following code is the transport-independent normalization slice. It demonstrates stable IDs, scope checks, raw and clean content preservation, and creation of the missing posted relation.

#+begin_src lisp
(defpackage #:star.discord-watch.core
  (:use #:cl)
  (:export
   #:make-watch-scope
   #:watch-scope-dataset
   #:event-in-scope-p
   #:normalize-message-create))

(in-package #:star.discord-watch.core)

(defstruct (watch-scope
            (:constructor make-watch-scope
                (&key dataset guild-ids channel-ids user-ids)))
  (dataset "" :type string)
  (guild-ids '() :type list)
  (channel-ids '() :type list)
  (user-ids '() :type list))

(defun field (object key &optional default)
  (multiple-value-bind (value presentp) (gethash key object)
    (if presentp value default)))

(defun required-field (object key)
  (or (field object key)
      (error "Missing Discord field ~S" key)))

(defun allowed-id-p (id allowlist)
  (or (null allowlist)
      (and id (member id allowlist :test #'string=))))

(defun discord-id (kind snowflake)
  (format nil "discord:~(~A~):~A" kind snowflake))

(defun make-document (&rest fields)
  (let ((document (make-hash-table :test #'equal)))
    (loop for (key value) on fields by #'cddr
          do (setf (gethash key document) value))
    document))

(defun event-in-scope-p (scope payload)
  (let* ((author (required-field payload "author"))
         (author-id (required-field author "id"))
         (guild-id (field payload "guild_id"))
         (channel-id (required-field payload "channel_id")))
    (and (allowed-id-p guild-id (watch-scope-guild-ids scope))
         (allowed-id-p channel-id (watch-scope-channel-ids scope))
         (allowed-id-p author-id (watch-scope-user-ids scope)))))

(defun normalize-message-create (scope payload collected-at)
  (unless (event-in-scope-p scope payload)
    (return-from normalize-message-create nil))

  (let* ((author (required-field payload "author"))
         (user-snowflake (required-field author "id"))
         (message-snowflake (required-field payload "id"))
         (user-id (discord-id :user user-snowflake))
         (message-id (discord-id :message message-snowflake))
         (relation-id
           (format nil "discord:relation:posted:~A" message-snowflake))
         (dataset (watch-scope-dataset scope))
         (user
           (make-document
            "_id" user-id
            "dtype" "user"
            "dataset" dataset
            "platform" "discord"
            "platform_id" user-snowflake
            "name" (field author "username" "")
            "global_name" (field author "global_name")
            "bot" (field author "bot" nil)
            "sources" (list "discordwatch")))
         (message
           (make-document
            "_id" message-id
            "dtype" "message"
            "dataset" dataset
            "platform" "discord"
            "platform_id" message-snowflake
            "user" user-id
            "guild_id" (field payload "guild_id")
            "channel_id" (required-field payload "channel_id")
            "raw_content" (field payload "content" "")
            "clean_content" (field payload "clean_content")
            "created_at" (field payload "timestamp")
            "edited_at" (field payload "edited_timestamp")
            "collected_at" collected-at
            "attachments" (field payload "attachments" #())
            "embeds" (field payload "embeds" #())
            "message_reference" (field payload "message_reference")
            "sources" (list "discordwatch")))
         (relation
           (make-document
            "_id" relation-id
            "dtype" "relation"
            "dataset" dataset
            "source" user-id
            "target" message-id
            "predicate" "posted"
            "platform" "discord"
            "sources" (list "discordwatch"))))
    (list user message relation)))
#+end_src

The actor wrapper journals the raw envelope, invokes =normalize-message-create=, adds provenance fields, validates the documents against the active StarIntel schema, and submits one operation batch to the publisher actor.

* Native Gateway Adapter Scope

The native adapter should initially implement only passive collection:

- Gateway URL discovery;
- secure WebSocket connection;
- JSON payload decoding;
- Hello handling;
- heartbeat scheduling;
- heartbeat acknowledgements;
- sequence tracking;
- Identify;
- Ready;
- Resume;
- Resumed;
- Reconnect;
- Invalid Session;
- Dispatch routing;
- zlib-stream support when enabled;
- bounded REST history fetch;
- attachment retrieval;
- rate-limit observation;
- adapter health and protocol telemetry.

Initial dispatch events:

- =MESSAGE_CREATE=;
- =MESSAGE_UPDATE=;
- =MESSAGE_DELETE=;
- =MESSAGE_DELETE_BULK=;
- =MESSAGE_REACTION_ADD=;
- =MESSAGE_REACTION_REMOVE=;
- =THREAD_CREATE=;
- =THREAD_UPDATE=;
- =THREAD_DELETE=;
- =CHANNEL_CREATE=;
- =CHANNEL_UPDATE=;
- =GUILD_CREATE= for cache hydration;
- =GUILD_UPDATE=;
- =READY= and =RESUMED= metadata.

Do not initially implement message sending, reactions, voice, slash commands, presence manipulation, billing, relationships, or the full Discord desktop-client surface. Every omitted capability reduces protocol drift and review surface.

* Historical Backfill

Backfill is a separate bounded actor run, not an unbounded loop inside the live Gateway actor.

Rules:

- require explicit target capability;
- enforce guild/channel/thread allowlists;
- enforce =after= and =before=;
- page newest-to-oldest or oldest-to-newest under a declared strategy;
- store every cursor;
- stop on authorization expiration;
- deduplicate against live events by message ID and revision hash;
- preserve fetch response metadata;
- rate-limit per account and route;
- publish progress and remaining estimates;
- resume from the last confirmed cursor;
- terminate when the declared message, byte, request, or time budget is exhausted.

* Attachments and Media

The Message document records attachment metadata immediately. Download actors run separately.

Each attachment record must include:

- Discord attachment ID;
- parent message ID;
- original filename;
- media type;
- declared size;
- source URL and proxy URL;
- collection timestamp;
- HTTP response metadata;
- content length;
- cryptographic hash;
- storage artifact ID;
- download status;
- target ID;
- authorization reference.

Downloads use bounded concurrency, maximum byte sizes, content-type validation, quarantine, and immutable artifact storage. A failed download does not block publication of the parent Message document.

* Replay and Fixture Strategy

Before replacing the JavaScript library, capture bounded raw event fixtures from the authorized test scope:

- Ready;
- guild cache hydration;
- ordinary message;
- reply;
- thread message;
- attachment;
- embed;
- edit;
- delete;
- bulk delete;
- reaction add/remove;
- reconnect;
- resume;
- invalid session;
- partial or missing cache objects;
- direct message if in scope.

Fixtures must remove or replace case content while retaining structure, types, nullability, and ordering. Every adapter runs against the same fixture suite. The normalized document batches must match canonical hashes.

* Implementation Sequence

** Phase 0: Stabilize the JavaScript Prototype

- fix target validation;
- stop logging Axios responses and credentials;
- register listeners once;
- publish Relation documents;
- use stable Discord IDs;
- preserve raw payloads;
- add actual scope filters;
- add graceful shutdown;
- add confirm-channel publishing;
- add persistent and mandatory publishing;
- add target dead-letter handling;
- capture replay fixtures.

** Phase 1: Common Lisp Collection Core

- implement target validation;
- implement credential references and leases;
- implement session and subscription registry;
- implement scope evaluator;
- implement raw-event journal;
- implement deterministic normalizer;
- implement operation batches;
- implement reliable publisher;
- implement audit decisions;
- implement fake adapter and fixture replay.

** Phase 2: Supervised Sidecar Adapter

- define the adapter protocol;
- wrap the existing Node client behind JSON Lines, ZeroMQ, or a local socket;
- let Common Lisp own process startup, restart, health, scope, normalization, and publication;
- remove direct RabbitMQ and StarIntel document creation from Node;
- compare sidecar output against fixtures.

** Phase 3: Independent Python Compatibility Adapter

- implement the same adapter contract with =discord.py-self=;
- use it as a cross-check for event shape and reconnect behavior;
- do not let Python own case data or document semantics.

** Phase 4: Native Common Lisp Gateway Adapter

- implement WebSocket lifecycle;
- implement heartbeat and sequence state machine;
- implement identify/resume;
- implement dispatch routing;
- implement HTTP rate-limit state;
- implement history fetch;
- implement attachment retrieval;
- pass replay fixtures;
- pass bounded live test scope.

** Phase 5: Native Cutover

- run Node and native adapters in shadow mode;
- compare event counts, IDs, revision hashes, and document batches;
- investigate mismatches;
- cut publication authority to native Common Lisp;
- retain the sidecar only as a diagnostic fallback;
- remove it after a defined compatibility window.

* Acceptance Tests

1. A target containing a credential value instead of =credential_ref= is rejected.
2. A target without =authorization_ref=, =case_id=, or =expires_at= is rejected.
3. Expired and revoked targets stop collection without restart.
4. One account session supports multiple datasets and scopes without duplicate Gateway connections.
5. An out-of-scope guild event is rejected and creates only a compact audit decision.
6. An out-of-scope channel event is rejected.
7. A Message Create event emits User, Message, and posted Relation documents.
8. Replaying the same Message Create event does not allocate new document IDs.
9. A Message Update creates a new revision under the same Message ID.
10. A Message Delete creates a tombstone revision.
11. A reply emits a deterministic replied-to Relation.
12. A direct message does not crash guild or channel normalization.
13. Missing cache names do not block ID-based document creation.
14. An attachment failure does not block the Message document.
15. A RabbitMQ publish is not considered complete until confirmed.
16. An unroutable mandatory publish is journaled and retried or quarantined.
17. A process crash restarts only the affected session subtree.
18. Repeated authentication failure quarantines the credential lease.
19. Resume uses the last sequence and session checkpoint when valid.
20. Failed resume falls back to a fresh session plus deduplicated backfill.
21. The Node, Python, and Common Lisp adapters produce equal canonical batches for the fixture corpus.
22. Raw events identify adapter name, adapter version, account, session, sequence, and collection time.
23. No token or session secret appears in logs, documents, audit records, RabbitMQ messages, or checkpoints.
24. Every accepted document links to target, authorization, dataset, raw event, and adapter provenance.
25. Shutdown drains journaled batches or records them for replay before process exit.

* Rejected Alternatives

** Treat authorization as a deployment note

Rejected. Scope and expiration must be machine-enforced and auditable.

** Continue keying clients by raw token

Rejected. Tokens are secrets, multiple targets may share one account session, and token rotation must not change actor identity.

** Keep document creation inside every language adapter

Rejected. It creates divergent schemas, IDs, provenance, edit semantics, and RabbitMQ behavior.

** Rewrite all of Discord.js in Common Lisp

Rejected. Discord Watch requires passive collection, not the full desktop client or command surface.

** Adopt Lispcord or Dithcord unchanged

Rejected. Both are bot-oriented, incomplete for this use, and would still require a major protocol audit.

** Use only random ULIDs

Rejected for source-native entities. Random IDs break replay idempotence and duplicate detection. ULIDs remain useful for run IDs, target IDs, batches without native identifiers, and audit records.

** Ack target messages before startup validation

Rejected. A target is acknowledged only after schema validation and durable registry insertion. Session startup may then proceed asynchronously with explicit state.

* Result

The port should not be a line-by-line Common Lisp translation of the JavaScript file.

The correct port is:

- a Common Lisp supervised collection core;
- deterministic StarIntel document normalization;
- durable raw-event and checkpoint journals;
- reliable RabbitMQ publishing;
- one session per authorized account with multiple scoped subscriptions;
- a replaceable Discord adapter;
- a short bridge through the existing Node library;
- a native Common Lisp passive Gateway adapter as the final runtime.

This preserves the authorized prototype's required access model while removing the archived library from StarIntel's core architecture.
