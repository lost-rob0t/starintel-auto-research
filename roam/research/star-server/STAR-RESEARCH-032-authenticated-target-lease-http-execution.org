* Research Question

Given the current =starintel-server= implementation, what exact boundaries are still required so an authenticated target can be durably accepted, scheduled, recovered, and executed only while a current Valkey-backed lease/fencing authority permits the effect, without creating a second scheduler or lease system?

* Current System

The current server already contains the major primitives that older versions of this research treated as future work. The remaining problem is their composition.

#+begin_example
client / embedded caller
        |
        v
authenticated target ingress
        |
        +--> target-lease application authority   [partially WIP in PR #101]
        |          |
        |          v
        |      lease-store protocol
        |          |
        |          v
        |      memory / Valkey backend
        |
        v
CouchDB document + durable outbox
        |
        v
outbox replay/publication
        |
        v
Rabbit documents.new.target.*
        |
        v
handle-target / accept-target-delivery
        |
        v
persist target acceptance
        |
        v
Common Lisp timer-wheel schedule
        |
        v
due local actor / Rabbit effect
#+end_example

The architectural roles are now clear:

- **Common Lisp timer-wheel** is the target scheduler for one-shot and recurring delivery.
- **CouchDB** owns durable target, acceptance, mutation, and outbox state required for restart/recovery.
- **Valkey** is the distributed lease/fencing authority. It is not a scheduler.
- **RabbitMQ** transports target/document events and remote target work.
- **The application/service layer** must authenticate, authorize, create immutable execution intent, and project typed outcomes without exposing backend internals.

No new scheduling database, Redis/Valkey sorted-set scheduler, cron service, delayed-message scheduler, or second actor scheduler is justified by this issue.

* Implemented Authority and Scheduling Primitives

** Lease store

The server already has a backend-neutral =star.leases= protocol with memory and Valkey implementations. The Valkey backend already uses atomic scripts, backend-authoritative time, TTL/expiry handling, monotonic fencing generations, idempotent request/digest behavior, revoke/release semantics, corrupt-state fail-closed handling, and real-Valkey integration coverage.

The runtime now owns lease-store composition through =initialize-lease-store= / shutdown lifecycle. The default memory backend preserves local behavior; =STAR_LEASE_STORE_BACKEND=valkey= selects the durable distributed adapter. Therefore issue #32 must not redesign lease storage or invent another KV abstraction.

** Target scheduler and acceptance

Current =source/target-dispatch.lisp= already provides:

- =register-target-schedule=;
- one-shot and recurring wheel scheduling;
- =process-target-dispatch-envelope=;
- =accept-target-delivery=;
- local/Rabbit destination resolution;
- schedule identity and target acceptance documents;
- explicit delay/deadline/recurrence validation;
- an in-process active-schedule registry.

Issue #18 already repaired the basic recurrence, routing, and destination semantics. The remaining problem is not whether a timer can be registered; it is whether that timer represents valid current execution authority.

** Durable outbox

Current =source/databases/outbox.lisp= atomically records document mutation state plus pending outbox state, assigns stable mutation/event identity, republishes pending entries after restart, and marks publication afterward.

The generic outbox currently builds a public-document event payload and later calls the publisher with:

#+begin_src lisp
(routing-key payload event-id)
#+end_src

That interface preserves logical event identity but has no separate trusted server-private execution-authority sidecar. A process restart can recover the document event, but the authenticated service context that originally authorized target creation is not thereby recovered.

** Rabbit target ingress

Current =source/rabbit.lisp= routes target deliveries through =handle-target= and then =star.actors:accept-target-delivery=. This is the correct place to re-enter application execution policy, but the generic durable publication path currently provides document payload/event identity rather than a proved current lease authority.

** Current dispatch-envelope defect

Current =make-target-dispatch-envelope= accepts optional lease metadata but, when it is absent, generates a new ULID as =lease-id= and defaults =fencing-token= to =1=. The resulting target acceptance document persists those values.

Those defaults are useful historical placeholders, but they are not valid distributed execution authority. A random lease identifier plus constant fence cannot prove ownership of the current Valkey lease. Required-lock target execution must stop fabricating authority at this boundary.

* WIP Branch Reality

PR #101 contains substantial useful work toward #32, including an application-service direction, target-lease HTTP operations, server-side lease resolution, fenced-intent/receipt concepts, and stale-fence tests. It also records the same durable-ingress problem identified here: trusted principal/service context is lost across the CouchDB outbox -> Rabbit target-consumer path.

PR #101 is not the source of truth:

- it remains open/WIP;
- current =master= has continued changing after the branch diverged;
- its HTTP surface uses the older =/api/v1= convention, while #58 now owns the canonical =/v1= direction;
- useful code must be reconciled into current contracts rather than merged blindly.

The branch should be mined for tested implementation pieces, especially immutable fenced-intent/receipt behavior, but the implementation decision must be made against current =master=.

* Core Finding

The remaining safety gap is **durable execution-authority handoff and revalidation**, not scheduling and not lease storage.

An authenticated caller can create a target whose document and outbox event survive restart. Separately, the runtime can maintain a current Valkey lease. Separately, the timer wheel can schedule target work. What is not yet proven on current =master= is one continuous invariant connecting those systems:

#+begin_quote
A target may become durably accepted, scheduled, and authoritatively effective only when the server can prove that the exact immutable target intent is authorized by the current lease/fencing generation at each authority-changing boundary.
#+end_quote

The target document, Rabbit payload, actor process, timer handle, historical acceptance row, lease id string, or fencing-token number is not authority by itself.

* Required Execution-Authority Model

The server should create an immutable **target execution intent/receipt** only after authenticated authorization and current lease validation. The durable target pipeline may carry an opaque locator for that receipt, but every consumer must treat the locator as untrusted input until server-side resolution and current-lease comparison succeed.

The immutable receipt must bind enough data to prevent cross-scope/confused-deputy reuse. At minimum it should bind directly or by deterministic digest:

- canonical target identity;
- schedule/logical-operation identity;
- tenant and dataset;
- applicable program/namespace scope;
- actor/destination identity;
- lease identity;
- lease owner/service-instance identity where the lease contract requires it;
- fencing generation/token;
- immutable target/request fingerprint;
- relevant deadline/expiry;
- receipt schema/version.

It must not contain reusable credentials, Authorization headers, API keys, OAuth material, raw secret references, or another principal's private lease metadata.

The target execution receipt is historical proof of what the server authorized at ingress. It is **not** proof that the lease remains current later.

* Durable Outbox Composition

The durable outbox should preserve the same logical execution-authority locator across retry and restart without turning the public target document into the authority store.

Recommended shape:

#+begin_example
authenticated target mutation
  -> create immutable server-owned execution receipt R
  -> persist target mutation + pending outbox entry + server-private locator(R)
  -> crash is allowed here
  -> recovery republishes the same event identity + same locator(R)
  -> target consumer resolves R and current lease
#+end_example

Important properties:

1. outbox replay must not mint a fresh receipt or fresh lease merely because the first publication result was lost;
2. client-controlled =extensions= cannot inject or overwrite server-private receipt state;
3. =public-document-copy= and normal document reads must not expose server-private authority records;
4. normal non-target outbox behavior must remain generic and unchanged;
5. the added transport projection should be the narrowest trusted sidecar/envelope needed by target consumers;
6. same mutation/event identity must map to the same durable execution intent.

A Rabbit header can transport an opaque locator if and only if it is emitted by trusted server outbox code and the consumer still resolves/revalidates it. Arbitrary inbound headers are not authority.

* Consumer Gate Before Scheduling

Before =accept-target-delivery= persists authoritative target acceptance or calls =register-target-schedule=, the server must prove current execution authority.

The required sequence is:

1. strict-schema decode/validate the canonical target document;
2. obtain the trusted durable authority locator from the server-owned delivery envelope;
3. resolve the immutable receipt from server-owned storage;
4. verify the receipt binds to this exact target/schedule/scope/actor intent;
5. resolve the current lease through the configured lease-store/application authority;
6. require exact current lease-id/owner/service-instance/fencing-generation compatibility;
7. require backend-authoritative time/deadline policy to still permit execution;
8. only then persist authoritative acceptance and register the timer-wheel schedule.

Any missing, forged, cross-scope, stale, revoked, expired, corrupt, unavailable, or outcome-unknown authority must fail closed before schedule registration.

Backend unavailable/timeout/unknown mutation outcomes must remain typed and settle through the existing retry/quarantine policy; they must never be normalized to accepted work.

* Timer-Wheel Scheduling and Delayed Authority

Registering a timer while a lease is current is insufficient. A target may wait long enough for its lease to expire, be revoked, or be superseded by generation N+1.

Every delayed authoritative effect must therefore re-enter current lease/fencing validation immediately before the effect.

#+begin_example
schedule registered under receipt R / fence N
        |
        | time passes
        v
timer fires
        |
        v
resolve R + current lease
        |
        +-- current fence still N --> fenced effect boundary
        |
        +-- current fence N+1 / expired / revoked / unavailable --> reject/fail closed
#+end_example

Recurring schedules make this especially important: registration is not perpetual authority. Every due occurrence must validate current authority before producing an authoritative local/Rabbit effect.

This issue should not collapse identity boundaries that belong to #47/#59:

#+begin_example
schedule id != recurring occurrence id != retry attempt id
#+end_example

The receipt/fence must attach to the correct execution/occurrence semantics without turning one historical lease receipt into permanent authority for all future recurrences.

* Fenced Effect Acceptance

A separate Valkey preflight followed by an unconditional CouchDB mutation, Rabbit publish, or terminal settlement is a TOCTOU race and does not satisfy #32.

The authoritative effect boundary itself must reject stale generations. The smallest production seam should be chosen from current persistence/publication code; PR #101's fenced-intent work is useful evidence but must be reconciled against current =master=.

Mandatory proof:

#+begin_example
A owns generation N and reaches a barrier before authoritative effect
A stalls
A loses authority
B acquires generation N+1
B effect is accepted
A resumes with N
A effect is rejected
final authoritative state contains no post-N+1 effect from A
#+end_example

The barrier must be deterministic. Sleep-based timing is not sufficient evidence.

A test showing stale =renew= or =release= rejection is necessary lease-store coverage but does not prove stale target work cannot mutate/publish.

* Local and Rabbit Equivalence

Local actor delivery and Rabbit remote delivery must consume the same immutable execution-authority semantics.

Transport can differ in mechanics, but not in authority:

- same target/scope/receipt binding rules;
- same current-lease/fence validation;
- same stale-generation classification;
- same deadline policy;
- same fail-closed backend-unavailable behavior;
- same requirement for fenced authoritative effects.

A local actor reference or in-process call must not bypass lease validation merely because it avoids Rabbit.

* HTTP and Embedded Application Boundary

Current =master= has runtime lease-store composition, but the full merged target-lease application-service/HTTP surface described by #32 is still not present as one canonical production contract. PR #101 contains WIP implementation evidence.

The desired application boundary remains:

#+begin_example
explicit star.runtime
+ existing service-call-context
+ typed target-lease request
        |
        v
target-lease application service
        |
        v
existing star.leases protocol
#+end_example

Requirements:

- HTTP and embedded Common Lisp callers use the same service result algebra;
- authentication is not equivalent to =targets:lease= authorization;
- target/program/dataset/actor scopes are checked before lease-store mutation/disclosure;
- one absolute deadline propagates through the operation;
- idempotency request/digest mismatches fail before mutation;
- unknown mutation outcome is distinguishable from known timeout/failure;
- current authorization still applies when replaying a previous result;
- backend keys/scripts/private owner metadata never leak through client errors.

HTTP route spelling must follow #58. Canonical new-client operations are under =/v1=; older =/api/v1= forms are compatibility only where explicitly retained.

* Recovery Boundary with #33

#32 must create the production authority seams; #33 owns the exhaustive recovery/race matrix around those seams.

#32 should prove:

- current authority is required before schedule activation;
- delayed effects are fenced;
- durable replay preserves the same authority locator;
- local/Rabbit behavior is equivalent.

#33 then proves:

- expiry and renew races;
- process/actor crash while lease active;
- reacquire after orphaned work;
- stale generation classification;
- unknown-outcome reconciliation using original request identity;
- revoke while old work continues;
- backend restart/failover and fencing-floor safety;
- startup reconciliation of persisted running/scheduled state against the current lease store.

Persisted =running=, actor liveness, timer presence, or historical target acceptance must never grant authority during recovery.

* Relationship to #59 Target Lifecycle

#59 remains the product-level target lifecycle authority:

- =queued=;
- =scheduled=;
- =running=;
- =completed=;
- =failed=;
- =cancelled=;
- one-shot/recurring lifecycle semantics;
- occurrence identity;
- client create/read/control/cancel/recovery API.

#59 should consume #32/#33's execution authority. It must not build another lease store or another scheduler to compensate for missing fencing integration.

* Security and Data-Boundary Conclusions

- Caller-supplied target JSON cannot mint lease authority.
- A lease id and fencing token are locators/claims until resolved against server-owned state.
- A signed or opaque receipt can prove server issuance but still cannot prove the lease remains current; current-state validation is required.
- Principal/tenant fields copied into document payloads are data, not authenticated context.
- Rabbit headers from an arbitrary producer are not trusted merely because they use expected names.
- Durable outbox recovery must preserve logical authority identity rather than silently authorizing new work.
- Server-private receipt data must not leak into canonical StarIntel documents.
- Lease backend failure must fail closed for required-lock work.
- Actor/process liveness is not lease authority.
- Timer registration is not execution authority.

* Alternatives Rejected

** Use Valkey as the scheduler

Rejected. Valkey owns lease/fencing state. Replacing the existing timer-wheel with sorted sets/key expiry would create a second scheduling architecture and does not solve the authority handoff problem.

** Put lease/fence/principal fields in the target document

Rejected. The document is caller-influenced application data and can survive longer than the lease. Copying claims into a durable document does not make them authoritative.

** Trust Rabbit headers

Rejected as an authority source. Trusted server code may transport an opaque locator in transport metadata, but the consumer must still resolve server-owned receipt state and the current lease.

** HMAC/sign the old lease tuple and skip Valkey on execution

Rejected. Authenticity of an old tuple does not establish current lease authority after expiry/revoke/reacquire.

** Validate only when registering the timer

Rejected. The lease can change before the delayed effect runs.

** Fresh acquire on outbox replay

Rejected. Replay of one accepted logical mutation must reconcile to its original authority identity; silently acquiring fresh authority can resurrect stale work and allocate a new generation.

** CouchDB acceptance row as execution authority

Rejected. Acceptance state is durable history/recovery input, not proof of the current fencing generation.

** Valkey preflight followed by unconditional effect

Rejected. This is a TOCTOU race. The effect boundary must enforce fencing.

** Merge PR #101 wholesale

Rejected. It is valuable implementation evidence but diverged from current =master= and the canonical API direction.

* Research Conclusion

The server does not need a new scheduler and does not need a new lease backend.

The required design is a narrow composition of systems that already exist:

1. authenticate/authorize the target operation;
2. resolve current lease authority;
3. create one immutable server-owned execution intent/receipt;
4. durably bind its opaque locator to the target outbox event without exposing it as public document authority;
5. recover/replay the same locator after crash;
6. resolve receipt + current lease before durable schedule activation;
7. keep the existing Common Lisp timer-wheel for one-shot/recurring scheduling;
8. revalidate current lease/fence when delayed work becomes due;
9. enforce fencing at the authoritative local/Rabbit effect boundary;
10. hand full crash/reacquire/failover proof to #33;
11. let #59 consume the resulting authority for target lifecycle rather than duplicating it.

This is the smallest architecture that preserves crash-safe target persistence, distributed single-writer authority, and the existing scheduler while closing the current stale-worker and durable-provenance gaps.

* Implementation Handoff

Owning repository: =lost-rob0t/starintel-server=, issue #32.

Recommended bounded order after explicit operator authorization:

1. **RED: durable authority-loss fixture** — authenticated target accepted far enough to persist document/outbox state, crash before publication, recover the outbox, and prove current =master= cannot carry/re-establish trusted execution authority into the target consumer.
2. **Immutable execution receipt** — reconcile/salvage PR #101 concepts against current lease protocol and current =master=; caller-controlled fields cannot create it.
3. **Outbox sidecar/envelope** — persist and replay the same opaque receipt locator without changing generic document semantics.
4. **Consumer gate** — no target acceptance/schedule registration until receipt + current lease exact-match succeeds.
5. **Delayed revalidation** — timer callbacks revalidate before authoritative effect.
6. **Fenced effect RED/GREEN** — deterministic N vs N+1 stale-writer rejection at one real production effect seam.
7. **Local/Rabbit parity** — same authority semantics across both destinations.
8. **#33 handoff** — exercise expiry/crash/reacquire/revoke/restore matrix through the production seams.

Required RED cases before claiming completion:

- target document supplies fake lease id/fence -> rejected;
- no receipt -> no schedule;
- forged receipt -> no schedule;
- receipt for another tenant/dataset/target/actor -> no schedule;
- receipt generation N while current lease is N+1 -> no schedule/effect;
- lease backend unavailable/unknown -> fail closed with typed retryability;
- outbox crash/recovery -> same event id + same receipt locator, no fresh authority minted;
- recurring later occurrence after lease loss -> effect rejected;
- local/Rabbit paths -> equivalent authority classification;
- stale N resumes after B/N+1 commit -> no A authoritative effect;
- server-private authority/credentials -> absent from client document/Rabbit payload/log disclosure.

Implementation authorization remains =PENDING / AWAITING_OPERATOR_APPROVAL=.

* Open Design Questions

These are bounded implementation choices, not open architectural questions:

1. What exact current persistence location should hold immutable execution receipts: reuse/salvage PR #101's fenced-intent store, a server-private CouchDB structure, or another already-owned lease-protocol seam?
2. Should the opaque locator travel as trusted Rabbit metadata, a server-private internal event envelope, or another existing transport metadata structure? It must not become a caller-controlled canonical document field.
3. Which current production side-effect boundary is the smallest useful first fenced sink: acceptance-state update, durable outbox mutation, remote target publication, or another existing authoritative sink?
4. How should recurring occurrence identity bind to receipts while preserving #47/#59's distinction between schedule, occurrence, and retry attempt?
5. Which exact HTTP operations survive after #58's =/v1= contract reconciliation? Route naming must not drive the lease/application design.

* Footnotes and Glossary

[fn:starintel] StarIntel is the actor-based intelligence platform owning the target execution and document service boundary.
[fn:fence] A fencing token is a monotonically increasing generation used by side-effect receivers to reject stale workers.
[fn:receipt] A server-created immutable record binding an authorized target execution intent to a specific lease/fencing generation and scope. Its locator is not current authority by itself.
[fn:service-context] A service-call context is explicit caller authority, scope, correlation, and deadline data passed to an application service.
[fn:outbox] The durable CouchDB mutation/publication mechanism that preserves logical event identity across crash/restart.
