* Objective

Give StarLang one portable symbolic-reasoning surface while preserving the real
semantic differences between production-rule engines and Prolog engines.

A StarLang program should be able to declare facts, named reasoning operations,
expert rules, goals, questions, conclusions, explanation requirements, budgets,
and backend policy without embedding native LISA/Common Lisp or Prolog code.

* Approved Decision

StarLang SHALL provide a backend-neutral =star-logic= layer with these initial
concrete backend IDs:

#+begin_example
lisa
swi-prolog
n-prolog
#+end_example

Source may request =auto= or explicitly pin one backend. =auto= is a deterministic
selection policy, not a fourth backend.

The selected backend SHALL be resolved before execution and recorded in the
materialized run plan with its adapter version, engine version/build identity,
package digest, mapping digest, semantic profiles, and capability evidence.

A durable run SHALL NOT silently change backend type. Recovery may use an
equivalent instance of the same pinned backend/build contract. Cross-backend
execution is an explicit comparison or migration run.

* Approved Public Feature Set

The portable public logic API remains the approved =star.logic.api/1= contract
from STAR-LANG-009:

#+begin_example
assert!
retract!
solve
solutions
exists?
explain
#+end_example

The expert layer adds closed compiler-owned forms for:

- typed facts and fact roles;
- rules and rule conditions;
- goals and answer cardinality;
- questions with typed answers;
- checked conclusions;
- explanation requirements;
- optional uncertainty profiles;
- explicit backend policy;
- resource budgets;
- session mutation policy.

No public form exposes a native engine object, arbitrary Lisp form, arbitrary
Prolog goal, module name, predicate indicator, =call/1= term, FFI operation,
filesystem effect, network effect, shell command, or database effect.

* Architectural Invariants

1. =starlang-compiler= is the sole StarLang source parser and semantic compiler.
2. Untrusted =.star= source never enters Common Lisp =READ= or =EVAL= as engine source.
3. Native LISA or Prolog source never enters normalized StarLang IR.
4. Backend selection is deterministic over explicit materialization inputs.
5. Explicit pins cannot bypass semantic capability checks.
6. One materialized session has exactly one backend ID.
7. Runtime load may choose an instance, not reinterpret semantics.
8. Canonical StarIntel documents are never backend-owned mutable state.
9. Derived conclusions have stable identities.
10. Required explanations use normalized proof records rather than fabricated traces.
11. Questions leave inference through a typed question port.
12. Executable rule/query packages are digest-locked artifacts.
13. Budgets and cancellation capabilities are declared truthfully as hard, cooperative, or unsupported.
14. Engine-free fake-runtime tests remain possible without installing any real backend.
15. Final logic systems MUST NOT depend on =starlang-prototype= or files under =prototype/=.

* Semantic Profiles

Initial profile vocabulary includes:

#+begin_example
star.logic.runtime/1
star.logic.query/1
star.logic.tabled/1
star.logic.constraints/1
star.logic.production/1
star.logic.expert-session/1
star.logic.portable-prolog/1
star.expert.relational/1
star.expert.production/1
star.expert.consultation/1
#+end_example

Profiles are versioned semantic promises. Two backends producing similar answers
does not make their agenda, negation, duplicate, answer-order, mutation, tabling,
constraint, or proof semantics equivalent.

* Compiler Pipeline

The approved compiler flow is:

#+begin_example
READ
  closed StarLang reader
EXPAND
  hygienic language macros
EXPERT-EXPAND
  expert sugar -> closed expert core
CORE-VALIDATE
  structural grammar
TYPE-BIND
  schemas, patterns, variables, expressions
EXPERT-SEMANTIC
  negation, mutation, agenda, uncertainty, question rules
LOGIC-POLICY
  semantic profiles + required capabilities + backend policy
LOWER
  expert IR + logic operation IR
MATERIALIZE
  package/mapping resolution + deterministic backend selection
EMIT
  canonical runtime plan + generated backend artifact requests
#+end_example

Every phase retains source spans and origin chains for diagnostics.

* Expert IR

The compiler-owned IR SHALL represent at least:

- expert-system ID/version;
- backend policy;
- semantic profiles;
- typed fact roles;
- rules and stable rule IDs;
- condition tree;
- checked actions;
- goals;
- questions;
- uncertainty policy;
- explanation policy;
- mutation policy;
- budgets;
- required capabilities;
- source spans/origins.

Closed rule actions in v1 are limited to:

#+begin_example
conclude
assert-session-fact
retract-session-fact
#+end_example

External side effects require a separate capability/idempotency/replay design.

* Variables and Negation

- Rule variables use the =?name= convention.
- Variables must be introduced before use and have one static type in a rule/goal.
- Nested shadowing is rejected in v1.
- Compiler emits stable binding IDs; adapters map them privately.

Negation remains explicit and semantically distinct:

#+begin_example
absent
notProvable
different
contradicts
#+end_example

The compiler rejects a construct when the selected backend/profile cannot
provide the required semantics.

* Mutation and Authority

Fact roles include:

#+begin_example
source
session
derived
questionAnswer
#+end_example

Source facts and canonical StarIntel documents are immutable from the inference
runtime. Session facts may change only under the declared session mutation
policy. Question answers are journaled session facts. Derived conclusions belong
to the proof/inference layer and never become canonical StarIntel writes merely
because an engine produced them.

* Proof Contract

Required explanation output uses:

#+begin_example
star.logic.derivation/1
#+end_example

Normalized proof nodes may include source facts, session facts, question answers,
rule/clause applications, goals, bindings, assumptions, contradictions,
conclusions, uncertainty combination, and budget truncation.

Backend-native diagnostics may be attached as bounded namespaced metadata but do
not replace the normalized proof. Missing proof evidence is reported as proof
unavailable; it is never synthesized.

* Backend Selection

Materialization filters registered backend descriptors by:

1. semantic profile;
2. required capabilities;
3. package and mapping compatibility;
4. required isolation class;
5. required hard limits;
6. proof policy;
7. explicit pin when present;
8. otherwise a stable versioned default/benchmark policy.

Unresolved ties fail rather than depending on runtime registration order.
Selection evidence records accepted/rejected candidates and the exact reason.

* Approved LISA Role

LISA is the primary production-rule backend for:

- persistent working memory;
- RETE incremental matching;
- agenda/firing behavior;
- salience;
- negative/existential conditional elements where fixture-proven;
- object-backed StarIntel facts;
- incremental fact deltas.

It does not automatically claim SWI tabling, generic recursive-query, or
constraint semantics.

* Approved SWI-Prolog Role

SWI-Prolog is the primary relational backend for:

- recursive named operations;
- tabled evaluation;
- bounded multi-answer enumeration;
- identity-preserving relational projection;
- approved constraint profiles such as CLP(FD);
- process-isolated workers through the approved SWI adapter protocol.

It does not automatically claim LISA production agenda or salience semantics.

* Approved N-Prolog Role

N-Prolog is an approved conservative relational backend for a deliberately small,
fixture-proven portable subset.

It uses a pinned external worker and StarIntel-owned framed protocol. Features are
advertised only after they are independently proven against the exact pinned
N-Prolog build. SWI feature names do not grant N-Prolog capability by analogy.

Hard cancellation may terminate and replace a worker. A killed or uncertain
worker is never reused.

* Expert Session Runtime

One =ExpertSessionActor= owns one logical expert session. The runtime coordinates:

- pinned backend lease;
- fact projection;
- ordered fact deltas;
- goals;
- typed questions;
- conclusions;
- normalized proofs;
- budgets;
- cancellation;
- session journal;
- replay.

Question UI, LLM, or operator interaction is an adapter to the typed question
port and is not inference semantics.

Replay records enough information to rerun the same backend/package contract and
compare normalized conclusions/proofs. Replaying recorded question answers does
not ask the external question port again.

* Security Invariants

1. Only compiler-generated digest-locked engine artifacts execute.
2. Prolog adapters expose named operations only.
3. LISA rule RHS behavior comes only from closed action IR.
4. Engine artifacts cannot grant file/network/process/database/FFI capabilities.
5. Prompts and question answers cannot inject executable engine syntax.
6. Projected StarIntel facts retain identity and provenance.
7. Session mutable state is isolated.
8. Output and proof data are bounded and validated.
9. Secrets do not enter generated packages, fixtures, proofs, or journals.
10. Hard-cancelled or uncertain external workers are replaced.

* Approved Prototype Retirement

The new symbolic stack SHALL accelerate removal of the old prototype rather than
extend it.

- No =star-logic= implementation may be added under =prototype/=.
- No LISA, SWI-Prolog, or N-Prolog production adapter may live under =prototype/=.
- No new expert-system parser, IR, runtime, proof system, backend selector, or
  package loader may be prototype-owned.
- If temporary compiler integration still enters through a prototype API, it
  SHALL immediately forward into one final owner and contain no duplicate logic.
- Every implementation slice SHALL migrate its direct tests and fixtures to the
  final systems and remove superseded prototype tests/implementations.
- Final logic/expert ASDF systems SHALL load and test in a fresh process without
  =starlang-prototype=.
- Nix feature sets SHALL compose final systems directly.
- Product docs/examples SHALL teach final systems once available, not prototype
  package-qualified names.
- The repository-wide completion audit SHALL inspect source, tests, fixtures,
  ASDF, Nix, CLI, scripts, workflows, examples, and docs for prototype
  dependencies.
- When the overall StarLang port is proven complete, =prototype/= SHALL be
  deleted rather than retained as a fallback implementation.

* Implementation Order

1. portable logic protocol/types/capabilities/conditions and fake adapter;
2. logic operation IR and deterministic backend policy;
3. SWI adapter and relational fixtures;
4. N-Prolog adapter and independent portable-subset fixtures;
5. LISA adapter and production-rule fixtures;
6. expert parser/core IR and source-aware diagnostics;
7. ExpertSessionActor, question port, journal, budgets, replay;
8. backend-specific expert lowering;
9. normalized proofs and boolean explanation fixtures;
10. gated uncertainty profiles only after exact semantics exist;
11. benchmark-informed =auto= routing only after functional conformance;
12. remove each superseded prototype implementation as its final owner becomes authoritative.

* Acceptance Gates

Portable logic is complete when final systems load independently, fake selection
is deterministic, incompatible pins fail before execution, canonical records are
stable, and no final logic system loads =starlang-prototype=.

Real backend support is complete when LISA, SWI-Prolog, and N-Prolog each pass
their backend-specific design gates, report exact build identity, support
explicit pinning, normalize failures, prove cancellation behavior, and replay
deterministically for their canonical fixtures.

Expert systems are complete when the closed reader parses the approved surface,
expert sugar lowers fully into closed IR, typed facts/rules/goals/questions work,
required proofs normalize correctly, source facts remain immutable, unsupported
backend/profile combinations fail before execution, and tutorials require no
native engine syntax.

This design's implementation is complete only when every approved behavior has a
final package owner and there is no duplicated prototype implementation.
Repository-wide StarLang completion additionally requires the dedicated
proof-and-delete issue to verify whether =prototype/= can be removed and, if so,
remove it.

* Footnotes and Glossary

- *Backend pin* — Explicit request for one inference backend; still subject to capability/profile validation.
- *Semantic profile* — Versioned statement of observable inference semantics rather than a backend marketing label.
- *ExpertSessionActor* — Actor that owns one durable expert session and coordinates its backend, facts, questions, proofs, budgets, and replay.
- *Named operation* — Compiler/package-declared logic entrypoint with a fixed typed contract; never an arbitrary native goal.
- *Selection evidence* — Machine-readable explanation of backend candidates, rejection reasons, and final deterministic selection.
- *Engine artifact* — Trusted compiler-generated LISA/Prolog package consumed by an adapter.
- *Prototype retirement* — Migration discipline that removes =prototype/= ownership as final systems become authoritative and deletes the tree once the complete port is proven.
