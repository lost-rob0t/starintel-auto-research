* Decision

nsaspy approves =STAR-DISCORD-001= and =STAR-RESEARCH-006= on 2026-08-03.

Approval means the design may proceed into focused implementation. It does not claim that the runtime has already been implemented, tested against live Discord behavior, packaged, or released.

* Public Eligibility

The architecture must not restrict =cl-discord-self= to law enforcement, government, enterprise, or another privileged operator class.

Anyone may run, inspect, modify, and integrate the library subject to its license and the platform rules applicable to their own account and deployment.

StarIntel-specific scope, case, dataset, audit, storage, and publication rules belong in =star-discord-watch= or another application layer. They are not prerequisites for using the protocol library independently.

Any occurrence of “LEO authorization logic” in the approved research should be read as obsolete terminology for deployment-specific policy. The intended boundary is generic application policy, not law-enforcement eligibility.

* Initial Capability Profile

The approved first implementation is read-only.

Included:

- account-session startup and shutdown;
- Gateway event receipt;
- heartbeat, reconnect, resume, and checkpoint state;
- bounded message-history retrieval;
- bounded message and attachment retrieval;
- typed event and model parsing;
- raw-event preservation;
- rate-limit handling;
- deterministic fixture replay and compatibility testing.

Excluded from the initial profile:

- sending messages;
- interaction or application-command invocation;
- command frameworks;
- task automation frameworks;
- unsolicited messaging;
- mass-account operation;
- automatic fingerprint rotation;
- anti-abuse bypass automation.

The exclusions are implementation scope controls, not user eligibility controls.

* Future Client Surface

A broader Discord client may be built later on top of the same protocol library.

That future work may include additional client capabilities, but it must be proposed as a separate compatibility profile or project. It is not approved by this decision, and it must not delay or contaminate the read-only core.

The architecture must keep read-only operations separable from sending and automation capabilities so downstream applications can depend on the narrow profile without importing a broader client surface.

* Security and Abuse Boundary

Common Lisp is not an abuse-prevention mechanism. The language may reduce ecosystem scale or casual reuse in practice, but that is not a reliable technical control and must not appear as one in the architecture.

The design instead relies on explicit capability boundaries, bounded requests, rate-limit compliance, secret isolation, deterministic state, supervised lifecycle, and application-level policy.

* Consequences

- =cl-discord-self= is designed as a reusable public library rather than a private LEO component;
- =star-discord-watch= remains one application of the library, not its owner or eligibility gate;
- the first merge target remains a narrow read-only protocol and collection kernel;
- write, interaction, and automation functionality remain outside the current approval;
- =STAR-RESEARCH-005= is superseded by =STAR-RESEARCH-006=;
- implementation planning should follow =STAR-DISCORD-001=.
