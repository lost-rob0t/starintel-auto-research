* Context

The CAPTCHA broker coordinates authorization, target policy, provider selection, budgets, deduplication, cancellation, provider health, and ephemeral result delivery. Provider adapters may execute in the StarIntel server process or across a process/container/host boundary.

Paid provider task creation can have external side effects. The transport design must therefore tolerate duplicate delivery, broker/consumer restart, ambiguous publication, and provider-job races without claiming exactly-once execution.

* Candidate Decision

Subject to design approval, use this boundary:

#+begin_example
same process
  Sento actor mailbox

process, container, or host boundary carrying durable paid work
  RabbitMQ durable queue

future explicitly non-durable component boundary
  ZeroMQ only after binding/runtime/failure gates pass
#+end_example

The normalized application envelopes remain transport-neutral. Application code should address logical capabilities/routes, not RabbitMQ exchange names or ZeroMQ sockets directly.

* Rationale From Approved Research

- Current =starintel-server= packaging already includes =rabbitmq-c=, =cl-rabbit=, and Sento.
- RabbitMQ primary documentation provides publisher confirms, manual acknowledgements/redelivery, mandatory returns, and quorum queues as relevant data-safety primitives.
- These primitives still require idempotent application state and do not create exactly-once provider side effects.
- ZeroMQ's own reliability guide builds reliable request/reply and durable/disconnected patterns in user space; selecting it for paid work would move more reliability scope into StarIntel.
- Provider solve latency dominates raw local transport latency for this workload.

These findings justify RabbitMQ as the leading architecture candidate but do not approve this specific topology or implementation.

* Candidate RabbitMQ Topology

A candidate topology uses one versioned topic exchange, provisionally =captcha=, with logical routes such as:

#+begin_example
captcha.v1.provider.<providerId>.solve
captcha.v1.provider.<providerId>.cancel
captcha.v1.provider.<providerId>.health
captcha.v1.broker.result
captcha.v1.broker.state
captcha.v1.dead
#+end_example

Names and partitioning remain design-review items. Provider deployment queue names must not leak into the provider-neutral application protocol.

* Candidate Delivery Semantics

A future approved design should settle and test at least:

1. persistent messages for durable solve commands and terminal results;
2. publisher confirms before reporting broker acceptance;
3. mandatory returns or equivalent explicit unroutable detection;
4. manual consumer acknowledgement;
5. provider-adapter acknowledgement only after durable local recording of provider job identity or terminal pre-submission failure;
6. stable logical =requestId= and distinct provider =attemptId=;
7. bounded retry/dead-letter policy rather than infinite requeue;
8. message expiry plus application deadline;
9. durable attempt/outbox/journal semantics around paid provider creation;
10. no provider credentials, result tokens, proxy credentials, cookie bundles, or raw sensitive challenge context in RabbitMQ messages.

The design must explicitly state that these mechanisms provide at-least-once delivery and duplicate-safe recovery, *not* exactly-once external execution.

* Queue-Type Design Question

The approved research does not require one queue type.

- A local single-node deployment may use durable classic queues when host-level HA is not claimed.
- A multi-node hosted deployment may use quorum queues when replicated queue state is required.

The final queue-type policy must be validated against realistic message volume, queue backlog, failure model, and operational cost before design approval.

* Required Producer Design Work

Before any paid provider is enabled, the design must define and implementation must prove:

- structured publication outcomes;
- confirm activation/ack/nack handling;
- returned mandatory-message handling;
- persistent delivery properties;
- bounded reconnect and connection-state handling;
- ambiguous publication behavior tied to durable attempt/outbox state;
- metrics for confirmed, negatively confirmed, returned, timed out, redelivered, and ambiguous publications.

Do not fork =cl-rabbit= merely to wrap functionality already exposed by the pinned dependency. A fork/replacement needs a reproducible missing capability or defect.

* Local Actor Boundary

The research favors direct Sento mailboxes for tightly coupled same-process actors. This ADR still needs explicit design review for which actors are process-local, which provider adapters may be embedded, and where the durable external boundary begins.

Do not introduce RabbitMQ or ZeroMQ between ordinary actors in the same supervisor tree without a separate reason.

* ZeroMQ Deferral Candidate Gate

A future ZeroMQ route should require evidence that:

1. the Common Lisp binding/runtime path passes lifecycle, ownership, polling, monitoring, shutdown, security, and Nix packaging tests;
2. the route is intentionally non-durable or has a separately tested durable replay source;
3. queue limits, reconnect behavior, authentication/encryption, and failure visibility are explicit;
4. the route does not duplicate paid RabbitMQ submission without migration/fallback semantics;
5. end-to-end benchmarks identify RabbitMQ transport as a meaningful bottleneck;
6. failure injection proves paid work cannot be silently lost or duplicated.

* Planning-Cost Consequence

Approved research currently estimates the RabbitMQ incremental path at roughly =5–10= engineer-days and the ZeroMQ production path at roughly =23–52= engineer-days. These are planning ranges, not ADR-approved schedules. They should be re-baselined during design review against current wrapper/runtime code.

* Testing Gate Before Design Approval / Implementation

The design should not be approved for paid provider enablement until tests cover:

- publisher confirmation and negative confirmation;
- unroutable mandatory publication;
- broker disconnect before/after publish;
- consumer restart before ack;
- duplicate/redelivered messages;
- expired/poison/retry-exhausted messages;
- provider-job creation followed by process crash;
- ambiguous provider submission/publication;
- cancellation race;
- bounded shutdown/drain;
- secret/result redaction and RabbitMQ payload exclusion.

Continuous integration uses fake providers. Paid live probes remain separate, explicit, credential-gated, operator-owned canaries.

* Security Constraints Requiring Review

- transport messages carry opaque references rather than raw provider credentials/results where sensitive;
- TLS/authentication and broker credential distribution need a deployment policy;
- target authorization and disclosure checks happen before billable external submission;
- logs/metrics/dead letters must preserve redaction;
- dead-letter queues must not become accidental secret-retention stores.
