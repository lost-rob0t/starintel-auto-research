* Active ARDR Policy

ARDR researches only concrete StarIntel features/problems and directly attached source, actor/domain-server, scraping/acquisition, service/plugin, expert/researcher, StarLang/runtime, search/ingest/document/graph/provenance, Quasar, security, durability, resource, or deployment concerns.

When evidence is sufficient for an authorized scope, ARDR may transition research to `READY_FOR_DESIGN`, produce/update the canonical design, run adversarial review, and finish at `DESIGN_READY_FOR_OPERATOR_REVIEW`. It may create proposed implementation issues in `AWAITING_OPERATOR_IMPLEMENTATION_APPROVAL` state.

ARDR may never emit or infer implementation approval. RAGE may execute only operator-approved implementation work and must start RED-first where required.

* Durable Research Amendment

Every issue-backed ARDR research transaction now requires a tracked `roam/research/ardr-issues/ARDR-ISSUE-<issue-number>-<slug>.org` file, plus updates to coherent canonical domain research nodes when applicable. Chat, issue prose, task metadata, scratch state, or remote-only state cannot substitute for the research file.

Agents must use the authoritative local `~/starintel/starintel-auto-research` checkout for research state. If it does not exist, they stop and ask the user for the correct checkout path rather than cloning, guessing, or silently substituting a remote repository view.

* Footnotes and Glossary

- *ARDR* :: The StarIntel-scoped Analyze/Research/Design/Review workflow that can prepare design-ready work but cannot grant implementation authority.
- *Operator implementation gate* :: The explicit human decision required before proposed implementation work becomes executable by RAGE.
