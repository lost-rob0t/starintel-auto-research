#+title: STAR-PRO-CAPTCHA-002 NopeCHA Multi-Family Adapter
#+description: StarIntel Pro Actor design for separate NopeCHA Token and Recognition capabilities with exact challenge mappings, typed ephemeral results, quota accounting, and contract-drift gates.
#+status: REVIEW
#+filetags: :starintel:design:starintel-pro-actors:captcha:nopecha:adapter:token:recognition:uml:

* Decision

Implement =NopeChaAdapterActor= as a supervised multi-family provider actor behind [[id:star-captcha-000-broker-router][STAR-CAPTCHA-000]]. It exposes separate Token and Recognition capability ports. It does not advertise one broad =nopecha solves captcha= wildcard.

The actor accepts only broker-normalized =captchaProviderSubmit= messages that already passed authorization and target-policy checks.

* Provider Ports

| Broker operation | NopeCHA Token port | NopeCHA Recognition port |
|------------------+--------------------+--------------------------|
| =submitSolve= | =POST /token/= | capability-specific Recognition endpoint |
| =pollSolve= | =GET /token/?key=...&id=...= | endpoint-specific polling where required |
| =cancelSolve= | unsupported in researched contract | endpoint-specific; unsupported unless proven |
| =getBalanceOrQuota= | local subscription ledger plus provider status | same shared subscription ledger |
| =reportOutcome= | unsupported unless a current endpoint proves it | unsupported unless current contract proves it |
| =healthSnapshot= | configured probe and local circuit | configured probe and local circuit |

The provider key can appear in create bodies and retrieval queries. Disable request-body and request-line logging and sanitize exception objects before actor events.

* Capability Model

Each capability record declares:

- Token or Recognition port;
- exact issuer, family, variant, and integration version;
- required normalized fields and artifact kinds;
- expected result kind;
- proxy, cookie, browser, and network-binding requirements;
- configured credit cost and concurrency;
- contract fixture fingerprint and retrieval date;
- =verified=, =experimental=, =degraded=, =invalidContract=, or =disabled=.

Initial candidates include hCaptcha token, reCAPTCHA v2 token, reCAPTCHA v3 score/token execution, Turnstile token, Arkose recognition, AWS WAF recognition, GeeTest recognition, hCaptcha subchallenge recognition, and text-image recognition. Only fixture-backed candidates enter the manifest capability list.

* Actor State

The actor owns provider credential reference, endpoint configuration, per-capability costs, daily quota and refill interval, active jobs keyed by broker =attemptId=, provider job identifiers, local concurrency, polling schedules, quota reservations, circuit state, contract state, and redacted telemetry. It owns no durable token, answer, cookie, proxy, or enterprise data.

* Token Mapping

| Normalized capability | Provider type | Important context |
|-----------------------+---------------+-------------------|
| hCaptcha token | =hcaptcha= | site key, page URL, optional Enterprise data, proxy, user agent |
| reCAPTCHA v2 token | =recaptcha2= | site key, page URL, Enterprise context where applicable |
| reCAPTCHA v3 | =recaptcha3= | site key, page URL, action, minimum score where supported |
| Turnstile token | =turnstile= | site key, page URL, action, challenge data where applicable |

Exact provider field names are isolated in mapper modules and may change without changing the broker protocol.

* Recognition Result Mapping

| Provider answer shape | Normalized result kind |
|-----------------------+------------------------|
| decoded text | =textAnswer= |
| selected indexes | =selectionSet= |
| points or rectangles | =coordinates= |
| slider, rotate, drag, or ordered actions | =interactionPlan= |
| family-specific structure | =customTypedResult= with versioned schema |

The source actor applies Recognition results through its own browser/session and reports issuer acceptance. Recognition success is not equal to target acceptance.

* Quota Accounting

The provider uses subscription credits refreshed every twenty-three hours. Costs differ by capability and official pages can disagree. Every enabled capability requires =creditsPerAttempt= configuration or a verified discovery fixture.

Reserve credits before submission. Reconcile on terminal completion. Release only when the contract proves no charge. Roll windows from configured provider refill time, not local midnight.

* Authentication Hygiene

Because retrieval can place the key in a query:

- build the uniform resource locator only inside the Hypertext Transfer Protocol client call;
- disable request-target logging;
- never attach the final URL to an error condition;
- scrub query parameters from traces;
- use redacted telemetry descriptions;
- search every test log and event sink for the real key.

Proxy, cookie, and source-session context are disabled unless target policy and exact capability require them.

* Cancellation and Ambiguity

Provider cancellation is unsupported unless a specific current contract proves it. Local cancellation stops polling and deletes local material, while reporting =chargePossible: true=.

Journal the attempt before creation. Duplicate submissions attach to the journaled job. An ambiguous create is never blindly retried.

* Contract Drift

Unexpected required fields, result-kind mismatch, or unsupported-task responses disable only the affected capability. Shared authentication or account failures may open the provider-wide circuit.

* Testing

- Separate Token and Recognition fixtures.
- Per-capability request mapper and result validator.
- Pending token job behavior.
- Text, token, coordinates, selection, and interaction-plan results.
- Per-capability quota and refill-window behavior.
- Cancellation without provider cancellation.
- Proxy and cookie policy denial before dereference.
- Query key, cookie, proxy, artifact, and result redaction.
- One failed capability does not disable unrelated verified capabilities.
- Capability-specific opt-in canaries.
