* Scope

This pass reviews the canonical StarLang[fn:starlang] implementation in =lost-rob0t/star-lang= and asks one narrow language-design question:

How should StarLang gain macros[fn:macro] without losing its closed parser, deterministic compiler, source diagnostics, reproducible manifests, and Common Lisp-only implementation boundary?

This is implementation research, not a reopened host-language comparison. Common Lisp[fn:cl] remains the sole approved implementation language. Racket, Scheme, Rust, Lean, and Julia are examined only as evidence about macro-system design; none is proposed as a StarLang implementation host.

* Executive Finding

StarLang should add an explicit hygienic macro-expansion phase between parsing and semantic compilation.

The first release should support declarative, pattern-directed macros only. A =.star= file must not contain arbitrary Common Lisp transformer code, must not enter the Common Lisp reader, and must not gain access to =EVAL=, the filesystem, the network, the clock, randomness, environment variables, packages, or runtime objects.

The required pipeline is:

#+begin_src text
.star source
    |
    v
closed StarLang reader
    |
    v
syntax objects with per-occurrence spans, scopes, and origin metadata
    |
    v
locked declarative macro environment
    |
    v
bounded hygienic expansion into a small core surface
    |
    v
semantic validation
    |
    v
normalized IR
    |
    v
runtime binding and execution
#+end_src

The current source is not ready for this phase yet. It first needs a syntax-object layer[fn:syntax-object] because parsed atoms are represented as ordinary strings, keywords, integers, and booleans, while source positions are attached only to list objects. That representation cannot distinguish every identifier occurrence and cannot carry a complete macro origin chain[fn:origin-chain].

* Canonical Source Audit

** The closed reader is the correct boundary

The canonical parser in [[https://github.com/lost-rob0t/star-lang/blob/main/prototype/core-surface-prototype.lisp][=prototype/core-surface-prototype.lisp=]] reads =.star= text with a dedicated character parser. It rejects Common Lisp reader syntax beginning with =#=, ='=, backquote, and comma; rejects dotted lists; rejects package-qualified names; and maps source identifiers to lowercase strings.

This is the right security direction. Macro support must preserve it. The implementation must not solve macros by calling Common Lisp =READ= on StarLang source or by translating user text into a host =DEFMACRO= form.

** Source positions are currently list-level, not occurrence-level

The parser records a position when it finishes a parenthesized list and stores that position in an =EQ=-tested hash table keyed by the resulting list object. =with-star-source-position= later looks up the current list object in that table.

Atoms do not receive equivalent per-occurrence objects or spans[fn:source-span]. Repeated identifiers with the same spelling therefore do not carry independent lexical identity, source extent, scope set, or expansion provenance.

This is sufficient for the current declaration compiler, but insufficient for hygienic expansion. A macro expander must distinguish:

- an identifier written at the macro use site;
- an identifier written in the macro definition;
- an identifier synthesized by the expander;
- two identical spellings that belong to different scopes;
- the source span of each occurrence;
- the expansion steps that produced each generated form.

** The current compiler has no expansion phase

The normalized intermediate representation[fn:ir] compiler in [[https://github.com/lost-rob0t/star-lang/blob/main/prototype/compiler-ir-prototype.lisp][=prototype/compiler-ir-prototype.lisp=]] performs direct declaration dispatch. =compile-program= validates that one specification graph exists, gathers target names, and maps =compile-declaration= across the source declarations.

The host macro =define-star-program= only quotes its body and invokes =compile-program=. It is a Common Lisp convenience wrapper around the prototype compiler. It is not a StarLang macro system and does not establish hygiene, phases, syntax objects, locked macro imports, expansion limits, or source-level macro definitions.

** The current work order already points at the prerequisite

[[file:../../indexes/star-lang/STAR-LANG-INDEX-001-implementation.org][STAR-LANG-INDEX-001]] lists first-class source spans and origin chains near the front of the implementation work order. Macro expansion makes that item urgent rather than optional. Building macro substitution on raw lists now would create a second incompatible source representation that would later need replacement.

* Research Findings

** Syntax objects are the durable unit

Racket separates reading from expansion and represents program fragments as syntax objects containing source location and lexical binding information. Its expander uses that information to preserve lexical meaning through transformation. Racket also records an =origin= property describing the sequence of macro expansions that produced generated syntax.

Sources:

- [[https://docs.racket-lang.org/reference/syntax-model.html][Racket Reference: Syntax Model]]
- [[https://docs.racket-lang.org/guide/stx-obj.html][Racket Guide: Syntax Objects]]
- [[https://docs.racket-lang.org/reference/stxprops.html][Racket Reference: Syntax Object Properties]]

StarLang does not need Racket's full module and phase system, but it does need the same core separation: parsed syntax must be richer than plain data, and expansion metadata must survive until diagnostics and manifest emission.

** Hygiene should be structural, not naming convention

The scope-set model described in Matthew Flatt's “Binding as Sets of Scopes” associates identifiers with sets of scopes created by binding forms and macro expansions. Binding resolution then depends on scope membership rather than textual renaming alone.

Source:

- [[https://users.cs.utah.edu/plt/scope-sets/][Binding as Sets of Scopes]]

Lean 4 independently applies automatic hygiene to its extensible syntax system and identifies the two main capture failures: macro arguments accidentally captured by introduced binders, and macro-introduced references accidentally resolving to use-site names.

Source:

- [[https://lean-lang.org/doc/reference/latest/Notations-and-Macros/Macros/][Lean Reference: Macros and Hygiene]]

StarLang should use a compact scope-set model even though its current surface has fewer lexical binders than a general-purpose language. Dataflow bindings, generated actor names, generated message names, future local forms, and imported macro libraries will otherwise create the same capture problems later.

** Declarative pattern macros are the correct first tier

Scheme's standardized =syntax-rules= model demonstrates that useful hygienic macros can be built from declarative patterns and templates without giving source programs arbitrary compile-time execution. SRFI 72 further shows that source-object correlation and expansion traces can be retained as independent expansion records.

Sources:

- [[https://r7rs.org/][Revised7 Report on Scheme]]
- [[https://srfi.schemers.org/srfi-72/srfi-72.html][SRFI 72: Hygienic Macros]]

For StarLang, this is a better V1 fit than unrestricted procedural macros. The language is intended to declare documents, actors, domain servers, capabilities, adapters, and dataflows. Repetition and abstraction over those forms can be expressed through pattern matching and templates while keeping compilation finite, inspectable, and reproducible.

** Host macros are useful internally but are not the language boundary

Common Lisp =DEFMACRO= defines expansion functions over host forms, and =MACROEXPAND= repeatedly applies host macro expansion. Those facilities are appropriate for implementing the StarLang compiler itself and for trusted internal code generation.

Sources:

- [[https://www.lispworks.com/documentation/HyperSpec/Body/m_defmac.htm][Common Lisp HyperSpec: DEFMACRO]]
- [[https://www.lispworks.com/documentation/HyperSpec/Body/f_mexp_.htm][Common Lisp HyperSpec: MACROEXPAND]]

They are not appropriate as the direct source-level extension API for untrusted =.star= files. A host macro body can execute arbitrary Common Lisp at compile time. Exposing that power would bypass the closed reader and make reproducible, capability-bounded compilation impossible.

** Unhygienic procedural systems expose predictable failure modes

Rust procedural macros deliberately operate on token streams with spans, but the Rust Reference states that they are unhygienic and therefore require authors to defend against name collisions and path capture manually.

Source:

- [[https://doc.rust-lang.org/stable/reference/procedural-macros.html][Rust Reference: Procedural Macros]]

This is useful negative evidence for StarLang. “Generate unlikely names” is not an acceptable language invariant. StarLang should make capture impossible by default and require an explicit, reviewable operation for intentional capture if that operation is ever added.

* Recommended Macro Model

** Tier 1: locked declarative macros

V1 macro definitions should be data, not executable host code. Each macro contains:

- a stable name;
- one or more patterns;
- a template for each pattern;
- literal identifiers that must match exactly;
- pattern variables;
- optional repetition markers;
- a declared output context such as =declaration=, =dataflow-stage=, =field=, or =type-expression=;
- a macro format version;
- a source-library name, exact version, and digest.

Illustrative surface syntax:

#+begin_src lisp
(macro bounded-worker
  (:context declaration
   :rules
   (((bounded-worker ?name ?message ?handler ?capacity)
     (actor ?name
       (:accepts (list ?message)
        :produces (list ?message)
        :handler ?handler
        :mailbox (bounded ?capacity)
        :restart transient))))))
#+end_src

This example is a proposed StarLang form, not Common Lisp code. Identifiers beginning with =?= are pattern variables. The expansion result must consist entirely of recognized StarLang core forms after recursive expansion.

** Tier 2: trusted packaged transformers, deferred

A future procedural tier may be useful for complex schema generation or adapter declarations. It must not be defined inside ordinary =.star= source.

A trusted transformer would instead be:

- implemented in Common Lisp inside a reviewed ASDF[fn:asdf] system;
- registered through an explicit compiler port;
- identified by package, transformer name, version, and digest;
- invoked with immutable syntax objects and an explicit expansion context;
- denied direct I/O and runtime access unless a narrowly defined capability[fn:capability] is granted;
- required to return syntax objects plus structured diagnostics;
- included in the compilation lock and manifest.

This tier should not begin until Tier 1, syntax objects, provenance, determinism tests, and expansion limits are complete.

* Syntax Object Contract

Every parsed occurrence should become a StarLang syntax object with at least:

#+begin_src lisp
(star-syntax
 :datum <atom-or-children>
 :kind <identifier-keyword-string-number-list>
 :span <pathname-start-end>
 :scopes <immutable-scope-set>
 :origin <ordered-expansion-frames>
 :introduced-by <macro-id-or-nil>)
#+end_src

The representation may be a Common Lisp structure, but it must remain internal compiler data. It must not expose Common Lisp package symbols as StarLang identifiers.

Required properties:

1. every identifier occurrence has independent identity;
2. every node has a complete source span, not only a starting line and column;
3. generated nodes retain the macro use-site span and macro definition span;
4. scope sets are immutable values or treated immutably;
5. conversion to plain datum is explicit and lossy;
6. normalized IR never depends on syntax-object identity;
7. canonical serialization excludes process-local object addresses and random scope IDs.

* Expansion Phases

StarLang needs a small, explicit phase model[fn:phase-separation]:

** Phase 0: read

The closed parser converts characters into syntax objects. It performs only lexical validation and balanced-form validation. It does not resolve imports, run macros, or construct runtime values.

** Phase 1: collect and lock macro bindings

The compiler resolves macro libraries from the already locked specification graph. Macro libraries require exact versions and SHA-256 digests. Remote paths must be resolved before compilation, matching the existing specification-library rule.

A macro definition cannot depend on a macro defined later in an unordered import cycle. Import cycles must be rejected or topologically resolved by an explicit module rule.

** Phase 2: expand

Expansion is top-down and recursive:

1. inspect the head identifier in the current expansion context;
2. resolve it against the macro environment using name plus scope set;
3. if it is a macro, match one rule;
4. instantiate the template with use-site syntax preserved;
5. assign a fresh macro-introduction scope to generated identifiers;
6. append an origin frame;
7. recursively expand the result;
8. stop when only core forms remain.

** Phase 3: validate core syntax

After expansion, every form must belong to the versioned StarLang core grammar. Unknown macro names, leftover pattern variables, malformed templates, context violations, and generated unknown declarations are errors.

** Phase 4: semantic compilation

Only fully expanded core syntax reaches the existing semantic validators and normalized IR builders. Macro definitions and syntax objects do not enter runtime IR.

* Hygiene Rules

The default rules should be:

1. syntax copied from a macro argument keeps its use-site scopes;
2. identifiers written in a macro template receive a fresh macro-introduction scope;
3. literal core-form names resolve in the macro definition context;
4. macro-generated binders bind only references generated in the matching intended scope;
5. identical spellings do not imply identical bindings;
6. intentional capture is unavailable in V1;
7. macro expansion cannot intern source identifiers into arbitrary Common Lisp packages.

StarLang may later add an explicit =capture= or =datum-to-syntax= equivalent, but only after a concrete use case and separate review. It should be noisy in source, restricted by context, and visible in expansion traces.

* Determinism and Resource Limits

Macro expansion must be deterministic[fn:determinism] for a fixed source tree, compiler version, core grammar version, macro-library lock, and transformer lock.

The expander must reject or bound:

- recursive expansion cycles;
- expansion depth;
- total transformer invocations;
- total generated syntax nodes;
- pattern backtracking work;
- template repetition output;
- diagnostic origin-chain length;
- imported macro-library count.

Recommended initial limits are configuration values recorded in the compilation manifest, not hidden constants. A build that changes limits must produce a different manifest or compiler configuration digest.

Declarative expansion must not observe:

- wall-clock time;
- random state;
- process identifiers;
- filesystem contents outside locked inputs;
- network state;
- environment variables;
- mutable global registries;
- actor runtime state;
- hash-table iteration order.

* Provenance and Diagnostics

Each expansion frame should record:

- macro qualified name;
- macro-library version and digest;
- rule identifier;
- macro definition span;
- invocation span;
- parent expansion identifier;
- deterministic expansion ordinal;
- output-context kind.

A compiler error in generated syntax should report:

1. the final generated location;
2. the user-written macro invocation;
3. the macro definition and rule;
4. the ordered expansion chain;
5. the semantic validator that rejected the expanded form.

The primary diagnostic should point to user-authored source whenever possible. Generated spans should not erase the call site.

For review tooling, the compiler should expose:

- =expand-1= for one expansion step;
- =expand= for full expansion;
- =expansion-trace= for structured provenance;
- =expanded-source= for a stable human-readable rendering;
- =macro-dependencies= for lock and manifest inspection.

These are StarLang compiler APIs, not Common Lisp =MACROEXPAND= aliases.

* Library and Versioning Rules

Macros should be shipped in versioned StarLang libraries. A macro library is part of the source contract and therefore participates in reproducibility.

Required rules:

- exact version and digest, never floating latest;
- canonical macro-definition serialization;
- macro format version independent from runtime IR version;
- explicit exported macro names;
- explicit import aliases or qualified names;
- collision errors by default;
- no implicit global macro registry;
- expansion output tied to compiler and macro-library versions;
- lock digest included in emitted manifests and compilation cache keys.

A macro library may depend on core specification libraries, but macro expansion must not mutate those libraries or extend the StarIntel document schema implicitly. Generated schema declarations remain ordinary declarations subject to the same validators and approval process as handwritten declarations.

* Interaction with Normalized IR and Runtime

Macros are compile-time surface abstractions. They should disappear before normalized IR.

The normalized IR should contain:

- the expanded core declaration;
- optional source-map references to expansion records;
- the macro lock digest;
- the compiler version and core grammar version.

The normalized IR should not contain:

- executable transformer functions;
- Common Lisp closures;
- syntax-object scope sets used only for expansion;
- host package symbols;
- mutable macro environments;
- runtime macro dispatch.

Runtime behavior must be identical for a handwritten core program and a macro-generated program whose fully expanded core syntax is alpha-equivalent[fn:alpha-equivalence].

* Rejected Designs

** DENIED: expose Common Lisp =DEFMACRO= in =.star=

Reason: arbitrary compile-time execution, host reader exposure, package leakage, nondeterministic dependencies, and violation of the closed-language boundary.

** DENIED: textual substitution

Reason: no structural validation, no reliable spans, accidental replacement inside unrelated syntax, and unavoidable capture bugs.

** DENIED: raw list rewriting without syntax objects

Reason: identical spellings cannot carry distinct scopes or per-occurrence provenance. Current list-level source-position tracking is not enough.

** DENIED: unhygienic macros with generated unique-name conventions

Reason: naming conventions are not a binding model. They fail under composition, imports, recursive macros, and future local binding forms.

** DENIED: arbitrary procedural macros in V1

Reason: expands the trusted computing base[fn:tcb] before StarLang has syntax objects, resource accounting, provenance, deterministic transformer ports, or a stable macro core.

** DENIED: runtime macro expansion

Reason: runtime expansion breaks reproducible compilation, complicates recovery and replay, and mixes language construction with actor execution.

** DENIED: expand after semantic compilation

Reason: semantic validators would need to understand both surface macros and core forms, duplicating logic and weakening the normalized core boundary.

* Implementation Order

1. Replace the parser's plain-data output with per-occurrence syntax objects while retaining the closed character reader.
2. Record full spans for atoms and lists, including start and end offsets, line, and column.
3. Replace the dynamic =EQ= position side table with first-class syntax metadata or a stable occurrence table keyed by syntax node identity.
4. Add origin-frame structures and source-map serialization.
5. Split the compiler entry point into =read-star-syntax=, =expand-star-syntax=, =validate-star-core=, and =compile-star-core=.
6. Define the versioned core-form grammar and expansion contexts.
7. Implement declarative pattern matching without backtracking ambiguity.
8. Implement template instantiation with fresh macro-introduction scopes.
9. Add exact-version macro-library imports to the existing specification lock model.
10. Add cycle detection, expansion budgets, and deterministic ordering.
11. Add =expand-1=, full expansion, trace, and stable expanded-source APIs.
12. Integrate macro lock data and source maps into manifests and cache keys.
13. Add conformance fixtures and adversarial tests.
14. Consider trusted packaged procedural transformers only after the declarative system is approved and stable.

* Acceptance Tests

The macro system is not complete until automated tests prove at least the following:

1. a macro argument is not captured by a binder introduced by the macro;
2. a generated identifier does not capture a use-site identifier with the same spelling;
3. two invocations of one macro receive distinct introduction scopes;
4. a copied use-site identifier keeps its original binding;
5. an imported literal identifier resolves to the macro definition context;
6. identical source, locks, compiler version, and limits produce byte-identical expanded core output;
7. a recursive macro cycle fails with a bounded expansion trace;
8. expansion-depth and output-size limits fail deterministically;
9. malformed patterns and ambiguous rule matches produce source-located errors;
10. generated unknown core forms are rejected before semantic compilation;
11. generated schema declarations pass the same validators as handwritten declarations;
12. remote or digest-mismatched macro libraries are rejected before expansion;
13. expansion traces include invocation and definition spans;
14. manifest and cache keys change when the macro lock changes;
15. handwritten and macro-generated alpha-equivalent core programs compile to equivalent normalized IR;
16. no =.star= source reaches Common Lisp =READ= or =EVAL=;
17. no macro can observe clock, randomness, network, environment, or runtime actor state;
18. parser errors still identify exact source spans after syntax-object migration;
19. all existing non-macro fixtures compile unchanged;
20. direct execution and optional CL-GServer[fn:cl-gserver] binding remain equivalent after expansion.

* Review Decisions Required

The research recommends approval of the architecture, but the following details remain explicit review choices:

1. approve declarative macros as V1 and defer procedural transformers;
2. approve scope sets as the hygiene model rather than rename-only hygiene;
3. choose the first legal expansion contexts: declarations only, or declarations plus dataflow stages and fields;
4. choose whether macro definitions live inside ordinary specification libraries or a distinct =macro-library= top-level form;
5. choose initial expansion budgets and whether projects may lower but not raise repository policy limits;
6. choose whether expansion traces are embedded in manifests or stored as separate compiler artifacts referenced by digest;
7. choose whether the first release includes explicit intentional capture; this research recommends no.

* Conclusion

StarLang can gain Lisp-grade language extensibility without becoming arbitrary Common Lisp source.

The safe path is not to expose host macros. It is to build a small StarLang expander over first-class syntax objects, use hygienic declarative patterns, lock every macro dependency, bound all expansion work, preserve complete origin chains, and erase macros before normalized IR.

The immediate source task is therefore syntax identity and provenance, not template substitution. Implementing raw list macros first would be fast but structurally wrong and would force a rewrite as soon as StarLang gains imported macro libraries, nested bindings, or serious diagnostics.

* Footnotes and Glossary

[fn:starlang] StarLang: the Common Lisp-implemented domain-specific language and runtime that defines StarIntel documents, actors, domain servers, capabilities, adapters, and dataflows.

[fn:cl] Common Lisp (CL): the standardized Lisp language used as the sole approved implementation language for the StarLang parser, compiler, runtime, and supporting systems.

[fn:macro] Macro: a compile-time language feature that transforms one source form into other source forms before ordinary semantic compilation. For example, one compact worker-pool declaration could expand into several ordinary actor declarations.

[fn:syntax-object] Syntax object: a compiler value that combines a source form with metadata such as its exact location, lexical scopes, and expansion history. It is richer than a plain list or string.

[fn:origin-chain] Origin chain: the ordered record of macro invocations and rules that produced generated syntax, allowing diagnostics to trace an error back to user-written source.

[fn:source-span] Source span: the exact extent of one source occurrence, normally including pathname, starting and ending offsets, line numbers, and columns.

[fn:ir] Intermediate representation (IR): the normalized compiler data produced after parsing, expansion, and validation. Runtime adapters consume this representation rather than raw StarLang source.

[fn:asdf] ASDF: Another System Definition Facility, the standard Common Lisp build and system-loading tool used to package StarLang components.

[fn:capability] Capability: an explicit authorization object or declaration granting a narrowly defined operation. A capability-based transformer interface denies all undeclared powers by default.

[fn:phase-separation] Phase separation: the rule that reading, macro expansion, semantic compilation, and runtime execution are distinct stages with controlled data passed between them.

[fn:determinism] Determinism: the property that the same locked inputs and compiler configuration always produce the same expansion and output, independent of clock time, process state, or hash-table ordering.

[fn:alpha-equivalence] Alpha-equivalence: two programs being structurally identical except for consistent renaming of bound identifiers. A hygienic macro-generated form should behave like its handwritten equivalent even when generated internal names differ.

[fn:tcb] Trusted computing base (TCB): the code and components that must behave correctly to preserve system security. Adding arbitrary procedural macro execution would make the TCB much larger.

[fn:cl-gserver] CL-GServer (Sento): the optional Common Lisp actor runtime adapter used by StarLang after compilation; it must not define source-language macro semantics.
