* APPROVED Implementation Ownership

All Star-Lang implementation code is Common Lisp.

Common Lisp owns:

- closed =.star= parsing;
- source spans and import origins;
- declaration and type validation;
- normalized IR;
- canonical manifests;
- lifecycle envelopes;
- deterministic dispatch;
- persistence and recovery;
- direct handlers;
- optional cl-gserver integration;
- transport adapters;
- document construction;
- the public API.

Versioned JSON may be emitted at system boundaries. No other language implements Star-Lang.

* Existing Common Lisp Implementation

The repository currently includes prototypes or research implementations for:

- closed file parsing and structured source errors;
- local and digest-locked remote imports;
- normalized IR and semantic validation;
- canonical JSON manifests;
- lifecycle envelopes;
- deterministic dispatch;
- transport settlement and resumable output publication;
- standalone execution;
- optional cl-gserver execution;
- runtime directory and liveness separation;
- domain remoting and durable journals;
- StarIntel document runtime and constructor generation.

These artifacts establish the implementation baseline. They do not by themselves close the acceptance ledger below.

* Repository Boundary

- Racket, Scheme, and Guile runtimes are not retained as Star-Lang implementations.
- Cross-language implementation CI is not retained.
- Generated Python and TypeScript boundary bindings remain permitted because they consume versioned JSON contracts and do not parse or execute Star-Lang.
- The Common Lisp workflow enforces the absence of alternate parser and runtime artifacts.

* Non-Negotiable Boundaries

1. Untrusted Star-Lang source never enters the Common Lisp reader.
2. No unrestricted =EVAL= enters compilation or execution.
3. Core IR never contains cl-gserver object types.
4. Actor readiness never defines program validity.
5. Research nodes never become StarIntel object types, predicates, or fields.
6. Auto-dig and Quasar consume contracts rather than define semantics.
7. Field access remains explicit; dot syntax is denied.
8. No alternate-language Star-Lang implementation is permitted.
