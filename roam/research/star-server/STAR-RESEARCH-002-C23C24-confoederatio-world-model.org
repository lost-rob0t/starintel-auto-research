* Operator Seed

A Disboard listing surfaced a Discord community advertising open-source mapping/programming work and databases for borders, economics, militaries, populations, and cities from roughly 10000BC to the present. The listing points to:

- https://github.com/ConfoederatioVF/
- https://confoederatio.org/
- https://confoederatiodocs.info/Home

The advertisement is treated only as a discovery seed. Claims below are based on the project's public repositories, website, project mirror, and Zenodo record rather than on the Disboard copy.

* Finding

*KEEP AS A HIGH-VALUE C-23/C-24 SOURCE CANDIDATE.* Confoederatio is not merely a Discord server or link directory. Its public project surfaces expose a coherent historical-geospatial dataset family, a temporal GIS/editor, stable downloadable artifacts for at least part of the corpus, methodology material, and active repository development.

The strongest StarIntel value is the *Naissance World Model*: long-run polity boundaries, economic estimates, population/land-use estimates, and city-level historical data that can be represented as versioned temporal/geospatial datasets. This is unusually aligned with StarIntel's typed document, provenance, temporal-relation, and Quasar map/timeline model.

Do *not* treat these reconstructions as ground truth. Large portions are modeled or interpolated estimates derived from heterogeneous upstream sources. StarIntel should preserve the distinction between observed source material, reconstructed/modelled values, and any later StarIntel inference.

* Primary Classification

At the provider level, classify =Confoederatio / Naissance World Model= primarily as =dataset=.

Component classifications:

| Component | Primary StarIntel classification | Reason |
|-----------+----------------------------------+--------|

No Confoederatio component should currently be registered as a StarIntel =actor=. A stable StarIntel-facing machine API, provider contract, rate/failure semantics, and source-by-source provenance boundary have not been established. Downloadable versioned datasets are the clean first integration surface.

* Verified Public Surface

** Naissance World Model

The current Naissance repository describes the World Model as a combined historical/livemap dataset family and exposes these machine-oriented shapes:

- =Atlas=: vector de-facto polity extents through 2026 in GeoJSON, with sub-yearly resolution; de-jure extents use C-Shapes 2.0.
- =Eoscala=: raster economic estimates including GDP PPP and related measures, reaching from 10000BC into the 2020s at 5-arcminute resolution.
- =Stadestér/Velkscala=: raster/vector population, land-use, urban extent, and city data from deep history into 2025; city observations/estimates cover 41k+ cities.
- =Collation=: livemap material for ORBATs, territorial control, and geospatialised news aggregation.

Naissance also supports CSV, GeoJSON, GeoTIFF, NetCDF, KML/KMZ, OSM, Shapefile, TopoJSON, WKT, and its own =.naissance= format. That makes a format-preserving StarIntel import path plausible without depending on its UI.

** Stadestér release quality

Zenodo exposes Stadestér 1.0.1 as an open dataset with a versioned record, fixed archive names and MD5 hashes, a methodology paper, and roughly 840 MB of downloadable data. Its abstract describes approximately 41,214 cities from 3000BC to 2025AD, annualized through interpolation/weighted aggregation, with explicit source families and calibration/validation notes.

This is materially better than a loose Git repository full of generated files: StarIntel can pin the release record, file hash, artifact name, acquisition timestamp, and exact transformation version.

** Activity and liveness

The GitHub organization remained active through late August and early September 2026. Naissance, EoscalaVelkscala, Collation, Stadester, and related tooling have recent updates. This is an active source family, not a dead Awesome-OSINT-style link that should be rejected at =V-01=.

* Source-Drift and Quality Warnings

** Coverage statements drift between project surfaces

Current public pages disagree on some exact endpoints and counts. Examples include:

- Atlas is described as beginning at either 3000BC or 3300BC depending on the project surface.
- Eoscala pages variously state 2023, 2025, or "present" as the current endpoint.
- Stadestér descriptions have moved from older ~32k-city wording to 41k+ cities.

Treat these as versioned metadata drift, not as proof of deception. Import manifests must pin the exact dataset/release version instead of copying a mutable website description into canonical metadata.

** Reconstructed data is not direct observation

Eoscala, Velkscala, and large parts of Stadestér are estimates assembled from historical scholarship, HYDE/GHSL-type datasets, interpolation, calibration, and fallback models. The early historical portions necessarily have very different epistemic quality from modern data.

StarIntel should therefore preserve at least:

- source artifact identity and release version;
- model/methodology version;
- temporal resolution and uncertainty;
- whether a value is observed, sourced estimate, interpolation, calibrated reconstruction, or derived StarIntel value;
- upstream source references where available;
- source-specific license/citation obligations.

A raster cell or annualized city value must not silently become an unqualified =fact=.

** Licensing needs artifact-level verification

Confoederatio states that its released projects and accessible datasets are MIT licensed, and GitHub identifies Naissance as MIT. That is useful but not sufficient to infer that every upstream source incorporated into a derived dataset carries identical redistribution terms. =V-02= should record licenses and citation obligations per released artifact and methodology source before mirroring bulk data.

** Collation is not yet a clean ingestion contract

Collation says some original historical/livemap source material is too large for GitHub and may need to be manually populated from references or obtained separately. Its live map capabilities are interesting, but StarIntel should not convert browser scraping or opaque workers into an actor merely because code exists. First enumerate exact public sources, identifiers, update cadence, and provenance emitted by each worker.

* StarIntel Data Model Fit

The cleanest initial projection is temporal/geospatial evidence, not a special Confoederatio object model.

Candidate normalized objects and claims:

| Source shape | StarIntel projection |
|--------------+----------------------|
| polity polygon + validity time | location/polity entity + temporal geometry claim |
| combatant extent + validity time | organization/polity relation + temporal geometry claim |
| city + year + population | city entity + population estimate claim with model/source metadata |
| raster GDP/Gini cell + period | bounded geographic statistic claim or dataset-backed raster observation |
| raster population/land-use cell + period | bounded geographic statistic claim or raster observation |
| source/methodology citation | source/evidence document linked to derived claims |
| release/archive | immutable dataset artifact with checksum, version, acquisition time, and lineage |

The raw source artifact should remain immutable. Normalization creates new StarIntel documents; it does not rewrite the upstream artifact.

* Quasar Fit

This source family is also a strong test case for existing Quasar research:

- map + timeline synchronization for changing boundaries;
- temporal relation inspection;
- raster/vector layer selection;
- source-support drill-down from a rendered boundary or statistic;
- comparison of two model versions without erasing the older one;
- time-slice transforms such as =polity -> boundaries at date=, =city -> population series=, or =region -> modeled GDP/population layer=;
- explicit display of uncertainty/model provenance in the inspector.

Naissance should be studied as product/interaction prior art, but StarIntel should not adopt its canonical object model wholesale. Quasar remains the StarIntel investigation surface.

* Collation / Contemporary OSINT Fit

The screenshot's claim about "militaries" has a narrower source-backed interpretation than the marketing text implies. Current Naissance documentation shows Collation/Livemap examples involving ORBATs, territorial control, naval data, and geospatialised news. That is relevant to StarIntel's geopolitical situational-awareness work, but it is not evidence of one complete historical military database spanning the entire advertised period.

Treat military/ORBAT coverage as a separate provider/source-contract audit. Do not generalize it from the existence of Atlas combatant polygons or Collation screenshots.

* Reproducible Access Probe

Performed 2026-09-05:

- The public Atlas 0.5 JSON link resolves to a machine-readable artifact. The web retrieval path reported a payload of about 8.2 MB; the artifact was not fully parsed in this reconnaissance pass.
- The current Stadestér Zenodo record resolves as version =1.0.1= and publishes stable file names, sizes, and MD5 checksums for the JSON/raster archives and methodology PDF.
- The active GitHub/Projects mirrors expose current source repositories and versioned project metadata.

This is sufficient to establish that a deterministic acquisition test is possible. It is *not* yet a data-accuracy validation.

* Required Validation Before Ingestion

1. Pin one Atlas release/artifact and one Stadestér Zenodo release by URL, version, and cryptographic hash.
2. Preserve the upstream artifact unchanged in the raw store.
3. Parse a bounded sample without Naissance itself: at least five regions/time slices for Atlas and ten city/year records for Stadestér.
4. Verify BCE/year-zero semantics explicitly; do not assume astronomical year numbering.
5. Record CRS, raster resolution, no-data encoding, geometry validity, and temporal granularity.
6. Confirm stable identifiers or define deterministic StarIntel source-record IDs when upstream IDs are unstable.
7. Compare a small sample against independent upstream/academic references cited by the methodology; record disagreements instead of forcing a winner.
8. Verify license and citation obligations for the exact release and its major upstream data dependencies.
9. Run =V-04= coverage measurement so early-history density and modern coverage are not summarized by one global percentage.
10. Only after those gates, design a scheduled update actor that checks release metadata and hashes. The importer itself should remain deterministic and replayable.

* Recommended Implementation Order

1. Register Confoederatio as a =C-23/C-24= source candidate in =STAR-RESEARCH-002=.
2. Start with *Stadestér Zenodo*, because it has the strongest visible release/version/checksum boundary.
3. Add *Atlas* second as the temporal-boundary/geometry test case.
4. Add *Eoscala/Velkscala* only after raster semantics, uncertainty, and upstream-license handling are explicit.
5. Evaluate *Naissance HGIS* only as an optional local tool/library or interchange surface after raw format import works independently.
6. Research *Collation* separately for contemporary GEOINT/ORBAT/news workflows; do not couple its scraping stack to the historical dataset importer.

* Decision

*KEEP and prioritize for focused validation.* This is one of the better matches found for =C-23= and =C-24=: active, open, strongly geospatial, unusually deep temporal coverage, and at least partly distributed through stable research artifacts.

The first StarIntel integration should be a *versioned dataset importer*, not a remote actor and not a wholesale Naissance integration. All historical/economic/population values must retain reconstruction/model provenance and temporal uncertainty.
