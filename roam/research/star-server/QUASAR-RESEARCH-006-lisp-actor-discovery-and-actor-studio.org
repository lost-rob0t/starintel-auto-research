* Research Question

How should Quasar discover and present Common Lisp actors that an operator can intentionally run against selected targets or documents, while still using cl-gserver/Sento for execution and liveness without exposing every internal supervisor, router, worker, coordinator, or transport actor in Actor Studio?

The motivating examples are:

- a normalization actor that accepts =person= documents and emits canonical document updates;
- an OSINT actor that accepts a =username= or =person= target and emits account/evidence documents;
- a lookup actor backed by a supervised cl-gserver subsystem whose internal workers are implementation details.

* Current Browser Actor Surface

Actor Studio currently builds its visible catalog from browser definitions:

#+begin_src javascript
[...BUILTIN_ACTORS, ...customActors]
#+end_src

The editor treats these entries as browser actor manifests with JavaScript source. That model is appropriate for browser actors, but it cannot represent a Common Lisp actor capability merely by serializing a running Sento actor instance.

* Current Common Lisp Runtime Surface

The Common Lisp control plane already starts a Sento actor system and creates the =quasar-control-plane= actor. The Melissa subsystem creates a supervisor, request router, lookup workers, normalizer, forwarder, and optional HTTP bridge.

Those facts prove two things:

1. Quasar already has a native actor runtime;
2. most running actors are runtime implementation objects, not operator commands.

The original 0.1 research incorrectly leaned toward exposing intentionally public native runtime instances. The operator clarification establishes a stricter product boundary: *runtime existence alone does not make an actor an Actor Studio entry*.

* Existing cl-gserver Research Already Separates Contract From Runtime

STAR-LANG-RESEARCH-013 defines cl-gserver as an optional execution adapter. It explicitly keeps semantic actor contracts separate from runtime topology and describes an optional runtime directory using =all-actors=, =find-actors=, and =running-p=.

That is the correct pattern for Quasar:

#+begin_example
semantic actor capability
        |
        | may bind to
        v
cl-gserver actor/runtime instance
        |
        v
runtime observation / liveness
#+end_example

The semantic contract answers =what can the operator run?=.
The runtime observation answers =is its native execution backing alive?=.

Neither should be substituted for the other.

* Core Finding: Two Different Discovery Surfaces

Quasar needs two distinct discovery surfaces.

** Operator Actor Capability Catalog

This is the normal Actor Studio source.

It contains only actor definitions explicitly marked operator-facing. Each definition describes semantic inputs, outputs, requirements, and invocation behavior independent of transient runtime paths.

Examples:

- =normalize-person= accepts =person= documents;
- =normalize-account= accepts =account= documents;
- =username-hunt= accepts =person= and =username= targets;
- =melissa-lookup= accepts supported person/contact inputs while hiding its worker pool.

** Runtime Topology / Observation

This is an operational/debug/admin source.

It may contain:

- control-plane actor;
- supervisors;
- routers;
- workers;
- coordinators;
- bridges;
- plugin-owned runtime actors.

It exists to report liveness, topology, generation/restart state, and diagnostics. It MUST NOT automatically populate normal Actor Studio entries.

* Actor Capability Is the Stable Product Object

The stable object presented to Quasar should be an =ActorCapability= or equivalent semantic actor definition.

Minimum research shape:

#+begin_src json
{
  "schema_version": "1.0",
  "actor_id": "star.actor.normalize-person",
  "label": "Normalize person",
  "kind": "document-transform",
  "operator_visible": true,
  "accepts": {
    "targets": [],
    "documents": [
      {"dtype": "person", "schema": "0.9"}
    ]
  },
  "produces": {
    "documents": [
      {"dtype": "person", "mode": "update"}
    ]
  },
  "execution": {
    "runtime": "native",
    "backend": "cl-gserver"
  },
  "capabilities": ["run", "preview"]
}
#+end_src

Important properties:

- =actor_id= is semantic and stable;
- =operator_visible= is explicit and defaults closed for native internals;
- accepted target/document types drive selection filtering;
- produced types make expected effects inspectable before execution;
- execution backend is metadata, not semantic identity;
- the same semantic contract may later bind to a standalone Common Lisp handler, cl-gserver actor, remote Star service, or another approved adapter.

* Target Acceptance

Target actors should declare the target forms they accept rather than appear universally runnable.

A target selector may include:

- canonical target type, such as =person=, =username=, =domain=, =email=, or =organization=;
- optional document-derived target compatibility;
- cardinality limits;
- required fields or predicates;
- runtime/service requirements.

Example:

#+begin_src json
{
  "actor_id": "star.actor.username-hunt",
  "kind": "target-actor",
  "accepts": {
    "targets": ["username", "person"],
    "documents": []
  },
  "produces": {
    "documents": ["account", "relation", "evidence"]
  }
}
#+end_src

Quasar can therefore show the actor only when the active selection can satisfy the declared contract.

* Document Acceptance and Normalization Actors

Normalization actors are a first-class reason not to model discovery as raw runtime enumeration.

A normalization actor should be able to declare:

- accepted document =dtype= values;
- optional schema/version range;
- optional required fields/predicates;
- selection cardinality;
- whether it is deterministic/idempotent;
- whether it previews changes;
- produced document/update classes.

Example Common Lisp/Star-style declaration direction:

#+begin_src lisp
(actor normalize-person
  (:runtime native
   :kind document-transform
   :operator-visible t
   :accepts-documents ((person :schema "0.9"))
   :produces-documents ((person :mode update))
   :capabilities (preview run)
   :handler normalize-person))
#+end_src

The exact syntax is not approved by this research; the semantics are.

A normalization actor MUST NOT need to be represented as a long-lived visible worker in order to appear in Actor Studio. Its contract may resolve to a handler or supervised actor only when invoked.

* Runtime Observation Model

When the execution backend is cl-gserver, Quasar may reconcile the semantic capability with a runtime observation such as:

#+begin_src json
{
  "actor_id": "star.actor.normalize-person",
  "runtime_id": "quasar.local.sbcl",
  "backend": "cl-gserver",
  "available": true,
  "state": "running",
  "runtime_path": "/user/document-normalizers/normalize-person",
  "generation": 3
}
#+end_src

The runtime path and generation are diagnostic. They do not define the actor capability.

For pooled/supervised implementations, one semantic actor may map to several runtime actors. The catalog should still contain one operator-facing capability.

Example:

#+begin_example
Actor Studio: Melissa Lookup
          |
          v
semantic actor capability
          |
          v
Melissa subsystem supervisor
   /       |       \
worker 0 worker 1 worker 2
#+end_example

Actor Studio shows =Melissa Lookup=, not four infrastructure rows.

* Matching Model in Quasar

Quasar should derive runnable actions from the current selection.

Conceptually:

#+begin_example
selected targets/documents
        |
        v
normalize selection types
        |
        v
match ActorCapability.accepts
        |
        +---- reject incompatible actors
        |
        v
check execution availability/capabilities
        |
        v
show runnable actions
#+end_example

This permits context-sensitive actor UX:

- select a =person= document -> show person normalization and compatible enrichment actors;
- select an =account= document -> show account normalization/lookup actors;
- select a =username= target -> show username collectors;
- select incompatible mixed documents -> hide or explain actors whose cardinality/type contract cannot be satisfied.

* Browser Actors and Native Actors Can Share the Semantic Catalog

The catalog view model can unify presentation without unifying execution authority.

Browser built-ins/custom actors may be adapted into the same semantic fields:

- stable ID;
- kind;
- accepts;
- produces;
- capabilities;
- runtime origin.

Execution remains delegated to the correct runtime adapter.

This removes the current assumption that every visible actor is JavaScript while preserving the standalone browser runtime.

* What MUST NOT Be Exposed by Default

Normal Actor Studio MUST NOT list an actor merely because =all-actors= returns it.

Default-hidden runtime actors include:

- Quasar command-authority actor;
- subsystem supervisors;
- routers;
- worker pool members;
- internal normalizer pipeline workers that are not independently operator-invokable;
- forwarders;
- transport bridges;
- coordinators;
- telemetry actors;
- plugin infrastructure actors.

An internal actor becomes operator-facing only through an explicit semantic capability definition.

* Operational Topology Still Has Value

The runtime directory remains useful for:

- health/debug views;
- supervisor tree inspection;
- verifying that declared native capabilities have execution backing;
- diagnosing restart loops;
- viewing mailbox pressure where safely exposed;
- comparing expected and observed runtime topology.

This should be a separate advanced/runtime surface, not Actor Studio's default catalog.

* Smallest Useful Vertical Slice

After approval, the first implementation slice should:

1. define a versioned operator actor capability descriptor;
2. add explicit native capability registration with =operator_visible= defaulting false;
3. expose a bounded capability catalog through the existing control-plane/runtime adapter;
4. add accepted target/document selectors and produced document declarations;
5. represent at least one document-normalization actor fixture;
6. represent at least one target actor fixture;
7. reconcile capability availability against cl-gserver runtime observation without leaking the whole topology;
8. update Actor Studio to display/filter compatible browser and native actor capabilities;
9. keep raw runtime topology available only through a separate/admin-facing interface;
10. prove the behavior with Common Lisp, frontend, and real-stack tests.

* Research Acceptance Evidence

Implementation evidence should prove:

- internal gserver actors do not appear in Actor Studio merely because they run;
- one semantic capability may map to multiple runtime workers;
- a document normalization actor appears for compatible =dtype= and not incompatible documents;
- a target actor appears only for accepted target types;
- native availability reflects cl-gserver observation when required;
- browser actors remain usable while the native runtime is disconnected;
- an operator-facing capability remains identified by semantic =actor_id= across worker restarts/path changes;
- metadata is bounded and scrubbed;
- capability matching does not require loading/serializing arbitrary Lisp actor objects.

* Research Conclusion

Quasar should not expose “the Lisp actors” as a raw list of running Sento/cl-gserver processes.

It should expose *operator-facing semantic actor capabilities* whose contracts declare which target types and document types they accept and what they produce. cl-gserver provides an execution backend and runtime observation plane for those capabilities, while its supervisors, routers, workers, and other internal topology remain hidden from the normal Actor Studio catalog.

This model directly supports future normalization actors: a normalization capability can be discoverable for compatible documents even if its implementation is a handler, a lazily spawned actor, or a supervised pool.

* Footnotes and Glossary

- *Actor capability*: Stable semantic definition of an operator-invokable actor action, including accepted inputs, produced outputs, execution requirements, and capabilities.
- *Actor Studio*: Quasar UI surface for discovering, inspecting, creating where applicable, and running operator-facing actor capabilities.
- *cl-gserver*: Common Lisp actor runtime used as an optional native execution backend; Sento is the actor-system implementation used by current Quasar code/research.
- *runtime observation*: Bounded liveness/topology information about an execution instance, separate from the actor capability contract.
- *target type*: Canonical class of investigation target accepted by an actor, such as person, username, domain, email, or organization.
- *document dtype*: Canonical StarIntel document type, such as person, account, entity, relation, or evidence.
- *normalization actor*: Actor capability that validates/canonicalizes existing documents and emits proposed canonical updates rather than being identified by a persistent worker process.
- *operator-visible*: Explicit policy bit declaring that a semantic actor capability may appear in normal Actor Studio discovery.
