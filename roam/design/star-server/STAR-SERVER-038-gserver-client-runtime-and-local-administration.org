* Normative Status

This document defines the first implementation-ready client architecture after approval of STAR-RESEARCH-038.

The words MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, and MAY are normative.

The machine-readable contract/code-generation mechanism in STAR-RESEARCH-039 is still under research review. This design establishes the seam that generated operations will use but MUST NOT require the first implementation commit to settle every OpenAPI/export detail.

The implementation sequence may therefore land the handwritten runtime first, then attach generated operations when STAR-RESEARCH-039 is approved, without changing the public runtime boundary.

* Goals

The first client slice MUST:

1. turn =starintel-gserver-client= into a real reusable remote SDK rather than a Dexador convenience wrapper;
2. keep the SDK separately loadable from the full server runtime;
3. make transport replaceable for deterministic tests;
4. represent bearer/API-key authentication without mutating shared header state;
5. normalize HTTP/StarIntel failures into a stable Common Lisp condition hierarchy;
6. preserve correlation and response metadata;
7. provide explicit deadline/timeout options;
8. avoid unsafe automatic mutation retries;
9. support generated operation wrappers without generated transport logic;
10. cover login, auth context, user lifecycle, credential lifecycle, health, and server metadata first;
11. make =star-cli= consume named SDK operations rather than raw routes;
12. add local break-glass administration under the existing =star-server= binary;
13. allow local admin recovery without starting RabbitMQ, actor supervision, or the HTTP listener;
14. reuse =star.auth= lifecycle services rather than manipulating CouchDB records directly.

* Non-Goals

This slice does NOT:

- redesign every legacy document/search/view endpoint at once;
- replace Dexador as the default HTTP transport merely for novelty;
- introduce GraphQL or gRPC;
- require async actors for ordinary request/response calls;
- make =star-cli= and =star-server admin= the same implementation;
- make the remote client capable of direct CouchDB access;
- implement a universal generic OpenAPI client interpreter;
- define long-lived streaming/WebSocket semantics;
- automatically persist human credentials in the core SDK;
- weaken server-side authorization because an operation comes from an official client.

remote Common Lisp caller

          +-----------------------+
          | generated operations  |

                      |

                 HTTP API

host/container operator
        |

 minimal server config + auth store initialization

The two administration paths share service/domain semantics below HTTP. They do not share transport implementation above HTTP.

* Package and File Boundary

Retain the public ASDF system name:

#+begin_example
starintel-gserver-client
#+end_example

Retain =star.api.client= as the public package nickname for compatibility where practical.

Refactor implementation into conceptual layers:

#+begin_example
cli/client/package.lisp
cli/client/conditions.lisp
cli/client/config.lisp
cli/client/transport.lisp
cli/client/runtime.lisp
cli/client/auth.lisp
cli/client/generated/models.lisp
cli/client/generated/operations.lisp
cli/client/convenience.lisp
#+end_example

Exact filenames MAY vary, but ownership MUST remain equivalent.

Generated files MUST be clearly marked and MUST NOT contain handwritten transport/auth/retry behavior.

The =star-cli= ASDF system depends on =starintel-gserver-client=. The client system MUST NOT depend on =star-cli= or the full =starintel-gserver= executable system.

* Client Object

The current mutable =star-client= object contains a base URL and a header alist. Replace that behavior with an effectively immutable configuration object.

The public client MUST contain or reference:

- normalized base URI;
- transport object;
- authentication provider or anonymous auth marker;
- default request timeout/deadline policy;
- user-agent/caller identity;
- safe default headers;
- optional compatibility/capability cache.

Changing principal identity MUST create a derived/new client or session value rather than mutating a shared header list.

Conceptual public construction:

#+begin_src lisp
(make-star-client :base-url "https://star.example")

(client-with-api-key client api-key)
#+end_src

Exact constructor keyword names MAY change during implementation review, but the immutable-identity rule MUST NOT.

* Authentication Provider

Authentication is a runtime concern, not generated operation code.

Define a small internal/public protocol equivalent to:

#+begin_src lisp
(defgeneric apply-authentication (provider request))
#+end_src

Initial providers:

- anonymous/no authentication;
- bearer API key.

The bearer provider MUST:

- add one =Authorization: Bearer ...= value;
- redact the secret in printing/logging;
- never expose the raw key through ordinary object inspection;
- support explicit construction from login/credential creation results.

The raw API key necessarily exists in memory after login. The design goal is containment and redaction, not magical erasure from Common Lisp memory.

* Login Semantics

=POST /auth/login= is an unauthenticated operation and returns a raw API key plus credential/user metadata.

The SDK login operation MUST return a structured login result.

The runtime MUST NOT silently mutate the client passed to =login=.

Preferred flow:

#+begin_src lisp
(let* ((anonymous (make-star-client :base-url base-url))
       (login (login anonymous username password))
       (client (client-with-api-key anonymous
                                    (login-result-api-key login))))
  (auth-context client))
#+end_src

This is explicit, thread-safe, and easy to test.

A convenience helper MAY combine login and client derivation later, but the primitive semantics remain explicit.

* Secret Types and Printing

Represent credential-bearing values so normal printing is safe.

At minimum:

- =star-client= printing MUST omit/redact credentials;
- auth-provider printing MUST omit/redact credentials;
- conditions MUST NOT embed =Authorization= values;
- login/credential secret result printing SHOULD redact raw keys by default;
- passwords MUST NOT appear in condition reports or debug logs;
- generated models MUST respect secret metadata from the contract.

Provide explicit accessors for raw returned keys because callers need them, but never make raw secrets part of generic =print-object= output.

* Transport Protocol

Dexador remains the initial concrete transport, but client operations MUST NOT depend on Dexador conditions or function signatures.

Define a transport protocol around StarIntel-owned request/response values.

Conceptual data:

#+begin_example
client-request
  method
  uri
  headers
  body/octet or string
  timeout/deadline
  stream flag

client-response
  status
  headers
  body/octet or string
  correlation-id
  content-type
#+end_example

Conceptual generic:

#+begin_src lisp
(defgeneric perform-client-request (transport request))
#+end_src

The initial =dexador-transport= implements that generic.

Tests can use =function-transport= or =fake-transport= without a live server.

* Why No Actor Is Required for Ordinary Client Calls

The StarIntel server is actor-oriented, but a synchronous HTTP client operation has no independent lifecycle merely because actors are fashionable.

Do not wrap each request in Sento/cl-gserver actors.

Use actors later where lifecycle actually matters, for example:

- long-running job subscriptions;
- reconnecting streams;
- background refresh/capability monitoring;
- concurrent bulk orchestration with bounded mailboxes.

Ordinary SDK calls stay simple synchronous functions over a replaceable transport.

* Request Options

Per-request behavior MUST be explicit and separate from operation data.

Define a request-options value supporting at least:

- correlation identifier override;
- whole-request timeout or absolute logical deadline;
- additional safe headers;
- explicit idempotency key when the operation supports/requires one;
- raw-response/debug mode where allowed.

Operation wrappers pass request options to the runtime.

Do not make generated functions grow transport-specific keyword arguments such as Dexador socket knobs.

* Deadline and Timeout Model

The client MUST distinguish caller intent from transport implementation details.

The initial runtime MUST support:

1. a bounded client-side request timeout;
2. propagation of =X-Request-Timeout-Ms= when the operation/server contract supports it;
3. an absolute internal deadline representation so retries or nested convenience operations cannot restart a full logical timeout.

The Dexador adapter converts remaining budget into supported transport timeout settings.

If no time remains before dispatch, fail locally with =client-deadline-exceeded=.

* Retry Policy

Default: no hidden retries for mutation operations.

The runtime MAY automatically retry only when all required evidence says replay is safe, for example:

- transport failed before bytes were sent and this is known;
- operation is declared safe/idempotent;
- operation has a server-backed idempotency contract and the exact idempotency key is retained;
- retry remains inside the original deadline.

The first slice SHOULD implement no mutation retries rather than invent incomplete commit-outcome detection.

GET retry behavior may be added later under an explicit bounded policy.

* Error and Condition Hierarchy

All Dexador/network/server errors cross one normalization boundary.

Required conceptual hierarchy:

#+begin_example
star-client-error
  client-configuration-error
  client-request-error
  client-transport-error
    client-timeout-error
    client-connection-error
  client-protocol-error
    malformed-server-response
    incompatible-server-response
  client-http-error
    client-authentication-error
    client-authorization-error
    client-not-found-error
    client-conflict-error
    client-validation-error
    client-rate-limit-error
    client-server-unavailable-error
#+end_example

Do not create a subclass for every StarIntel error code.

Every =client-http-error= MUST retain fields for:

- HTTP status;
- StarIntel stable code when present;
- safe message/detail;
- correlation identifier;
- content type;
- selected safe headers;
- bounded raw body where safe;
- operation identifier.

Callers can branch by condition class and/or stable server code.

* Legacy and Problem-Details Errors

The runtime MUST decode both:

- current/legacy StarIntel JSON errors;
- RFC 9457 =application/problem+json= once/versioned routes provide it.

Both normalize into the same condition hierarchy.

Generated operation wrappers merely declare expected error responses. The handwritten runtime performs normalization.

* Response Metadata

A normal convenience operation may return the decoded domain value as its primary result, but response metadata must remain obtainable.

Preferred Common Lisp convention:

#+begin_src lisp
(multiple-value-bind (value response)
    (auth-context client)
  ...)
#+end_src

The first value is decoded protocol data. The second is the =client-response= metadata object.

This preserves idiomatic CL use without wrapping every domain value in a mandatory envelope.

* Generated Operation Boundary

When STAR-RESEARCH-039 is approved, generated functions MUST target one handwritten primitive equivalent to:

#+begin_src lisp
(call-operation client operation-id
                :path-parameters ...
                :query-parameters ...
                :headers ...
                :body ...
                :request-options ...)
#+end_src

The runtime resolves a generated/compiled operation descriptor that contains:

- method;
- path template;
- request serialization rules;
- authentication requirement;
- response status/content mappings;
- idempotency/deadline metadata;
- secret/redaction metadata.

Generated wrappers MUST NOT know about Dexador.

* First Generated/Named Operation Slice

Whether handwritten briefly or generated immediately, the first stable named SDK surface is:

** Server/discovery

- health;
- server metadata;
- later contract/capability metadata.

** Authentication

- login;
- authentication context.

** Human users

- create user;
- list users;
- administrator password reset;
- self-service password change.

** API credentials

- create credential;
- list credentials;
- rotate credential;
- revoke credential;
- disable credential.

Bootstrap secret operations SHOULD remain available when required by deployment bootstrap, but the normal remote management flow is authenticated user/credential administration.

* Remote CLI Boundary

=star-cli= becomes a presentation/interaction adapter over SDK functions.

A command handler MAY:

- parse flags;
- load/select a server profile;
- acquire password/key input;
- construct a client;
- call an SDK operation;
- format human/JSON output;
- map conditions to process exit codes;
- request confirmation for destructive actions.

It MUST NOT:

- contain normal endpoint path strings;
- call Dexador directly;
- construct bearer headers;
- parse StarIntel error envelopes itself;
- implement password policy;
- write server auth storage directly.

The existing =api-request= raw escape hatch MAY remain publicly available for debugging/forward compatibility but ordinary shipped CLI commands MUST NOT depend on it after migration.

* CLI Machine Output

Every new remote administrative CLI command MUST support a machine-readable JSON output mode derived from decoded SDK values.

Human text/table output is separate presentation.

Exit status MUST be based on normalized client conditions, not substring matching of server messages.

* Local Administration Is Part of star-server

The operator explicitly prefers the local administration path inside the server binary.

Add a top-level command tree under the existing Clingon executable:

#+begin_example
star-server
  start
  admin
    user
    credential
#+end_example

The existing =start= command remains the runtime launcher.

The =admin= branch is server-local management and recovery. It is not a remote HTTP client hidden inside the server executable.

* Local Admin Runtime Boundary

=star-server admin= MUST NOT invoke =star.runtime:start-runtime=.

It must initialize only what its operation needs.

Conceptual lifecycle:

#+begin_example
star-server admin ...
    |
    v
load/validate init configuration
    |
    v
initialize auth store
    |
    v
star.auth lifecycle function
    |
    v
print result / exit
#+end_example

For current CouchDB-backed authentication this means the command can use the existing configuration and =star.auth:initialize-auth-store= path without starting:

- RabbitMQ connections;
- document ingest consumers;
- actor supervisors;
- HTTP listener;
- recurring target scheduler;
- unrelated databases/services.

This is a hard recovery invariant.

If future auth storage changes, =admin= follows the =star.auth= abstraction rather than depending on CouchDB details.

* Local Admin Trust Model

Remote HTTP administration is authorized by StarIntel credentials/scopes.

Local =star-server admin= authority comes from OS/container execution access plus access to the server's configuration/secrets and authentication store.

Therefore local admin commands do not require an API key merely to loop back through HTTP.

They MUST still:

- call =star.auth= lifecycle functions;
- validate server configuration;
- obey password policy;
- preserve credential lifecycle invariants;
- reject malformed scopes/principal types;
- avoid raw persistence writes;
- produce auditable structured logs without secrets.

The command is intentionally privileged. Documentation must say so plainly.

* Local Admin Command Tree

Initial required user commands:

#+begin_example
star-server admin user create
star-server admin user list
star-server admin user set-password
#+end_example

Initial required credential commands:

#+begin_example
star-server admin credential create
star-server admin credential list
star-server admin credential rotate
star-server admin credential revoke
star-server admin credential disable
#+end_example

A separate =bootstrap= convenience command MAY be added if it maps cleanly onto the same lifecycle services, but direct user/credential recovery must not depend on the HTTP bootstrap endpoint.

Exact option spellings remain reviewable, but the command hierarchy is normative.

* Shared Init Option

The existing =star-server start= accepts =--init= / =STAR_SERVER_INIT_FILE=.

Refactor the option definition so =start= and =admin= can use the same init-file selection semantics without duplicating parsing.

=admin= loads configuration but does not start the full runtime.

The init file MUST be treated as privileged server configuration. Local admin output MUST NOT dump it or echo secret configuration values.

* Password Input

Do not make plaintext password command-line arguments the preferred path because argv and shell history are poor secret channels.

The local and remote CLI layers should share a small terminal secret-input abstraction where appropriate.

Required modes:

- interactive TTY input without echo;
- stdin/file input for automation under explicit flags;
- clear error when no safe input source is available in non-interactive use.

An environment-variable input MAY exist for controlled automation but should not be the only automation path.

The exact flag names are implementation details.

* Local Admin Output

Local admin commands MUST support:

- concise human output;
- JSON machine output;
- nonzero exit status on lifecycle/config/store failure.

Secret-returning operations such as credential creation/rotation MUST print raw secret material only when the caller explicitly requested/used an output mode that can receive it. Normal logs MUST remain redacted.

A JSON result containing a newly created raw key is acceptable because returning the key is the operation's purpose; logging that result is not.

* Local Admin Error Handling

Do not route local lifecycle failures through HTTP status codes.

Map =star.auth= conditions into local admin exit classifications while preserving the stable lifecycle code and safe message.

Conceptual JSON error:

#+begin_src json
{
  "status": "error",
  "code": "user_conflict",
  "message": "User already exists"
}
#+end_src

No CouchDB stack traces, password values, verifier material, or pepper/bootstrap secrets in normal output.

* First Implementation Slice

The first implementation PR SHOULD be intentionally narrow.

** Client runtime

1. split the public client from Dexador-specific transport;
2. introduce immutable client/auth configuration;
3. add response metadata and normalized conditions;
4. add fake/injected transport tests;
5. implement named =health= and server-metadata operations;
6. implement login/auth-context operations;
7. implement user lifecycle operations;
8. implement credential lifecycle operations;
9. migrate corresponding =star-cli= handlers away from raw =api-request=.

** Local server admin

10. refactor =source/main.lisp= to add =admin= beside =start=;
11. factor shared init-file option/config loading;
12. add minimal auth-store initialization path;
13. implement =admin user create/list/set-password=;
14. implement =admin credential create/list/rotate/revoke/disable=;
15. add safe secret input/output helpers;
16. prove admin commands do not start HTTP/RabbitMQ/actor runtime.

** Codegen seam

17. make named client operations use an operation-descriptor/call boundary compatible with STAR-RESEARCH-039;
18. if STAR-RESEARCH-039 is approved before implementation completes, generate those operation wrappers instead of hand-writing them;
19. otherwise keep descriptors isolated so generation can replace endpoint boilerplate without changing runtime APIs.

Use an isolated auth store/config fixture and prove:

- credential lifecycle works;
- password policy is enforced through =star.auth=;

- machine JSON output works;

- HTTP server start is not invoked;
- direct CouchDB document mutation is absent from command handlers.

* Failure and Recovery Semantics

Local =admin= must remain useful specifically when the remote plane is impaired.

Required scenarios:

| Failure | Remote star-cli | Local star-server admin |
|---------+-----------------|--------------------------|
| HTTP listener down | unavailable | works if auth store reachable |
| admin API key lost | cannot authenticate | can create/reset local admin credentials |
| auth HTTP route regression | impaired | works through lifecycle service |
| RabbitMQ down | unrelated commands may degrade | auth admin remains usable |
| actor runtime broken | remote server may fail to start | auth admin remains usable |
| CouchDB auth store down | unavailable | fails clearly; cannot bypass persistence truth |
| invalid server auth config | remote uncertain | fails closed with explicit config error |

Local admin is not magic recovery from loss of the authoritative auth store itself.

* Compatibility Plan

Do not break existing Common Lisp callers unnecessarily.

During migration:

- retain =star-client= symbol;
- keep =make-url= or a compatibility wrapper if downstream code uses it;
- retain raw =api-request= as deprecated escape hatch initially;
- add named operations with structured decoded results;
- deprecate direct header mutation;
- update =star-cli= first so the repository itself proves the new API;
- search known downstream repos before deleting exported compatibility symbols.

A later major client version may remove deprecated raw APIs after migration evidence exists.

* Observability

The client runtime SHOULD attach a bounded user-agent identifying:

- StarIntel client library version;
- optional caller identity such as =star-cli=.

Requests SHOULD carry correlation IDs according to server contract.

Debug hooks MAY emit:

- operation ID;
- method/path template identity;
- duration;
- status;
- correlation ID;
- retry count;
- response size.

They MUST NOT emit passwords, API keys, =Authorization= values, or sensitive bodies by default.

Local admin logs SHOULD identify:

- operation family;
- target username/credential ID when safe;
- success/failure code;
- correlation/audit identifier if introduced;
- duration.

Do not log raw secrets.

* Security Invariants

1. Official client code grants no authority by itself.
2. Remote operations are authorized only by server policy.
3. Local admin never silently falls back from failed remote auth; it is an explicit separate command path.
4. Local admin requires privileged server configuration/store access.
5. Client/admin printed representations redact secret values.
6. Passwords and bearer keys are not placed in ordinary logs or condition messages.
7. Generated code cannot embed test/real credentials.
8. Remote client never gains direct credential-store access.
9. Local admin writes only through =star.auth= lifecycle services.
10. Failed/partial mutations are reported without inventing retries.

* Acceptance Criteria

The design is implemented when all of the following are true:

- =starintel-gserver-client= loads without starting the server runtime;
- a fake transport can exercise named operations without network access;
- =star-cli= auth/user/credential commands contain no endpoint paths or Dexador calls;
- login can derive an authenticated client without mutating the anonymous client;
- normalized conditions expose status/code/correlation metadata;
- secret-bearing objects print safely;
- request deadlines are bounded and cannot silently restart;
- mutations are not implicitly retried;
- =star-server --help= exposes both =start= and =admin=;
- =star-server admin --help= exposes =user= and =credential= groups;
- local admin user and credential lifecycle works with HTTP/RabbitMQ/actors disabled;
- local admin command handlers contain no direct CouchDB record writes;
- machine-readable JSON output exists for remote and local administration;
- the operation-call seam can be generated from STAR-RESEARCH-039 without redesigning the runtime.

* Design Decision

Implement one reusable Common Lisp remote client runtime with a replaceable transport and explicit authentication/error/deadline semantics. Endpoint-specific wrappers sit above that runtime and are designed to become generated code from the machine-readable HTTP contract.

Keep =star-cli= thin and remote.

Put local recovery administration directly in the existing =star-server= binary under =star-server admin=. That command tree loads server configuration and the auth store, calls =star.auth= lifecycle services, and deliberately does **not** start the full StarIntel runtime or loop back through HTTP.

This gives StarIntel three clean layers instead of one giant CLI-shaped ball of mud:

#+begin_example
remote protocol SDK
remote human CLI
server-local recovery CLI
#+end_example

They share protocol/domain semantics where they should and remain operationally independent where failure recovery requires it.

* Open Questions for Review

- Should the public raw request escape hatch be exported as =api-request= for one deprecation cycle or renamed immediately to make its low-level status obvious?
- Should control-plane generated values use =defstruct= or small CLOS classes? This design prefers structures unless polymorphic behavior is needed.
- Should =client-response= always be returned as a second value or only when requested? This design prefers always returning it as a second value because ignored multiple values are cheap in CL.
- What exact secret-input flags should remote and local CLIs share?
- Should local =admin credential create= allow arbitrary scopes or require named scope presets in addition to explicit scopes?
- Should local admin produce a durable audit document immediately, or is structured server-local logging sufficient for the first slice?
- Which existing =star-cli= command groups outside auth should be migrated in the second client slice?

* Footnotes and Glossary

[fn:remote-sdk] Remote SDK: The reusable Common Lisp client that speaks the authenticated HTTP protocol and contains no direct server-store access.

[fn:break-glass] Break-glass administration: An explicit privileged local recovery path intended to work when normal remote management is unavailable.

[fn:transport] Transport: The replaceable component that converts a StarIntel-owned client request into an HTTP exchange and returns a StarIntel-owned client response.

[fn:generated-operation] Generated operation: Endpoint-specific wrapper/descriptor code produced from the machine-readable HTTP contract while calling the handwritten runtime for transport and policy semantics.
