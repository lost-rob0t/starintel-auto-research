* Decision

The approved design makes =https://auto-dig.starintel.actor/= the primary StarIntel Auto-Dig[fn:auto-dig] corpus dashboard rather than the complete dataset/catalog listing.

The complete topic and source dataset catalog moves to a dedicated =/datasets.html= browser.

The root dashboard becomes a real data product with pre-aggregated charts, ranked entities/findings, corpus totals, source metrics, and direct drill-downs into datasets, documents, sources, and the relationship graph.

Auto-Dig and Auto-Research[fn:auto-research] receive a shared product-shell visual language and reciprocal cross-site navigation, but they do not receive identical page layouts:

- Auto-Dig is an =Operate= surface optimized for scanning, filtering, comparison, and drill-down.
- Auto-Research is a =Read= surface optimized for research comprehension, links, backlinks, search, and graph navigation.

The operator approval recorded by [[file:../../research/auto-dig/ADAR-APPROVAL-001-dashboard-ux.org][ADAR-APPROVAL-001]] authorizes implementation of this exact design. Implementation completion and publication remain separate evidence gates.

* Product Boundary

This ADAR changes two public site surfaces and their generators:

1. =lost-rob0t/starintel-gpt-auto-dig= owns the generated Auto-Dig dashboard, dataset browser, per-target dashboards, graph/document/source views, and data projections used by those pages.
2. =lost-rob0t/starintel-auto-research= owns the generated Auto-Research research-reading surface, navigation shell, search, graph, and research/design review pages.

This ADAR does not change Quasar graph authority, canonical StarIntel document semantics, research promotion semantics, or dataset schema rules.

* Dashboard Composition

** Global filter strip

The dashboard should expose a compact filter strip when useful, not a permanent enterprise-filter jungle.

Initial filters:

- time range: 30 days / 90 days / 1 year / all;
- review state: reviewed default / all;
- optional dataset filter when the generated catalog can support it cheaply.

The default view must make sense with no configuration.

** Documents added by day

Primary chart: one large line/area chart using canonical =date_added= values.

Requirements:

- 30d, 90d, 1y, all toggles;
- tooltip with exact date and count;
- click/keyboard action may open the document browser filtered to that day/range;
- text summary below the chart for accessibility;
- no animated infinite sweep.

** Document type breakdown

Primary chart: doughnut chart of canonical =dtype= counts excluding =relation=.

Relations are excluded because they otherwise dominate a chart intended to explain the corpus’s document/entity composition.

Each segment should expose count and percentage and may drill into the document browser.

** Relation type breakdown

Separate chart; never combine relation types into the document-type chart.

The relation chart uses canonical relation predicate/type values and may switch from doughnut to ranked bars when category count is high enough that slices become unreadable.

** Top connected people

Default: reviewed relationship degree for person documents.

Each row includes:

- person name;
- reviewed connection count;
- dataset count;
- small relation-mix indicator;
- entity/document link;
- graph-focus action when supported.

An analyst control may switch to all relations.

No unexplained “influence score” is introduced.

** Top findings

Default: reviewed, evidence-backed candidate records only.

Ranking must be deterministic and display a rank explanation. It may consider evidence count, unique source count, explicit assessment/confidence, reviewed relation degree, and recency as a tie-breaker.

The implementation must not use a language model to silently invent a “top” label at page-load time.

** Sources

Show one large total for normalized unique sources plus a compact source-domain breakdown.

The source KPI links to the source inventory.

** Active datasets

Show only a compact subset on the root dashboard, for example top recently growing or recently updated datasets.

A =Browse all datasets= action opens =/datasets.html=.

** Latest activity

Show recent reviewed documents and/or research passes using the canonical timestamps already present in the corpus.

* Dataset Browser

New route:

#+begin_src text
https://auto-dig.starintel.actor/datasets.html
#+end_src

The page shows every generated topic dataset and every source dataset.

** Default casual view

- search field;
- =All / Topic / Source= segmented filter;
- sort menu;
- responsive dataset cards with title, type, record count, source count, recent growth, and updated-through date;
- =Open dashboard= primary action;
- download action where available.

** Analyst view

A visible =Table= switch changes the same catalog into a dense sortable table with columns for:

- dataset;
- class;
- records;
- people;
- organizations;
- relations;
- sources;
- recent additions;
- updated-through;
- open/download actions.

The two views consume the same generated =dataset-catalog.json= projection[fn:projection].

** Dataset browser performance

The page must not load the full corpus.

If the catalog becomes large, use pagination or virtualized rendering[fn:virtualization] rather than rendering every detailed card at once.

* Shared Shell, Different Surface Modes

The shared shell owns:

- brand treatment;
- typography families;
- primary interaction color;
- semantic state colors;
- focus rings;
- navigation height and spacing;
- button/link treatments;
- mobile navigation behavior;
- light/dark token rules if multiple themes remain supported.

The shell does not force identical content layouts.

Auto-Dig uses a dashboard grid and dense controls. Auto-Research keeps a readable line length, clear document hierarchy, backlinks, and research-oriented navigation.

* Visual System

The implementation should use the Impeccable[fn:impeccable] rules summarized by ADAR-RESEARCH-001.

** Required changes from current Auto-Dig styling

- stop using Inter as the default visual identity;
- reduce the number of rounded gradient cards;
- use larger uninterrupted chart/data surfaces with thin dividers and alignment instead of nested containers;
- replace generic template-like gradients with deliberate tinted surfaces and data color;
- make typography hierarchy do more of the work;
- preserve dark mode but use tinted ink/navy rather than pure black;
- reserve cyan/ice for interaction and amber/gold for evidence/highlight emphasis;
- keep semantic colors for states and document classes;
- use motion only for entry, state transition, or direct manipulation feedback.

** Typography direction

Preferred direction for implementation evaluation:

- interface/display: IBM Plex Sans or another distinctive, highly legible open font approved during implementation;
- identifiers/data: IBM Plex Mono or an equivalent monospace;
- fallbacks must preserve readability when custom font assets are unavailable.

The implementation may substitute another approved family if it better matches the final visual prototype. It may not silently fall back to the current generic Inter-first choice and call the redesign complete.

* Eye-Candy Boundary

One data-driven ambient element is allowed on the root dashboard.

Preferred examples:

- corpus-growth sparkline integrated into the status/hero area;
- compact recent-relations constellation generated from a bounded sample;
- subtle first-render chart animation.

Rejected:

- full animated graph on page load;
- looping particles unrelated to corpus state;
- expensive WebGPU[fn:webgpu] just for decoration;
- parallax/blur effects that obscure charts or evidence;
- decorative motion that ignores reduced-motion preferences.

* Dashboard Data Contract

Add a generated root projection such as =dashboard-data.json=.

Version it explicitly so UI code can fail clearly if the generator and browser code drift.

  "summary": {
    "documents": 0,
    "people": 0,
    "organizations": 0,
    "relations": 0,
    "datasets": 0,
    "sources": 0,

  "documents_by_day": [],
  "document_types": [],
  "relation_types": [],
  "top_connected_people": [],
  "top_findings": [],
  "active_datasets": [],
  "latest_activity": []
}
#+end_src

All values are generated from canonical repository documents. This file is a projection, not a second database.

* Chart Adapter

Use a small browser-side chart adapter[fn:chart-adapter] so page code consumes the dashboard data contract rather than a library-specific structure.

Preferred first renderer: locally vendored Chart.js[fn:chartjs].

Reasons:

- line, doughnut, and horizontal-bar charts are all required;
- the site is static and framework-free;
- one library is simpler than maintaining separate bespoke renderers for each chart;
- the library can be vendored into =site-assets= so runtime rendering does not require a third-party network request.

The adapter must preserve semantic text/table fallbacks and should allow a later renderer replacement without changing =dashboard-data.json=.

* Accessibility and Interaction Invariants

1. Charts have text or table equivalents.
2. Chart tooltips are not the only place exact values exist.
3. Color is never the only review/document/relation encoding.
4. All filters and switches are keyboard reachable with visible focus.
5. Motion honors =prefers-reduced-motion=.
6. Mobile layout remains functional without horizontal page scrolling.
7. Dense analyst tables remain readable using horizontal table containment only where unavoidable.
8. Direct links and downloads remain available when JavaScript is unavailable wherever practical.
9. Root content renders useful corpus totals before charts finish initializing.

* Performance Invariants

1. The root dashboard does not fetch the complete corpus JSONL.
2. The root dashboard does not initialize the full graph renderer.
3. Dashboard charts consume only pre-aggregated JSON.
4. Dataset browsing consumes only the dataset catalog projection.
5. Chart and dashboard JavaScript are deferred.
6. Generated page size and assets remain within the existing GitHub Pages[fn:github-pages] publication budget.
7. Large list rendering uses pagination or virtualization before it becomes a browser stability problem.

* Non-Goals

- Do not replace the Quasar graph workbench with dashboard charts.
- Do not load the entire graph into the root dashboard.
- Do not move canonical document logic into JavaScript.
- Do not turn Auto-Research into a second operational dashboard.
- Do not remove source, document, graph, or download drill-downs.
- Do not make “top findings” an opaque model opinion.
- Do not broaden implementation beyond the explicitly approved ADAR-001 scope without a new operator approval record.

* Footnotes and Glossary

[fn:auto-dig] Auto-Dig: The StarIntel generated research and dataset site at =auto-dig.starintel.actor=.

[fn:auto-research] Auto-Research: The StarIntel Org-roam research and design site at =auto-research.starintel.actor=.

[fn:projection] Projection: A derived data view generated from canonical documents for one interface purpose; it can be rebuilt and is not the database of record.

[fn:virtualization] Virtualized rendering: Showing only the currently visible part of a large list or table to reduce browser memory and rendering work.

[fn:impeccable] Impeccable: The frontend design guidance project used as the UI/UX quality and anti-pattern reference for this redesign.

[fn:webgpu] WebGPU: A modern browser graphics/compute API. It is relevant to large graph rendering research but is intentionally not required for dashboard decoration.

[fn:chart-adapter] Chart adapter: A small interface between generated dashboard data and the specific browser chart library so the library can be replaced without changing the data contract.

[fn:chartjs] Chart.js: A browser charting library supporting line, doughnut, and bar charts. This design recommends a locally vendored build behind the chart adapter.

[fn:github-pages] GitHub Pages: GitHub’s static website hosting system used by the StarIntel publication workflows.
