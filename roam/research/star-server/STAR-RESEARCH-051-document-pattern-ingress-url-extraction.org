* Current-Source Findings

** The matcher subsystem is loaded but has no ingest consumer

=starintel-gserver.asd= loads =actor-systems/matcher-actor=, and =start-url-extractor= registers a pattern in global =star:*document-patterns*=. Current source contains no component that consumes canonical incoming documents and iterates that registry. The URL extractor actor can therefore be created and registered while the pattern remains operationally dead.

** Pattern definitions are executable global process state

The current =pattern= object stores a Common Lisp =match-fn= function and raw actor subscriptions. =add-pattern= mutates process-global =*document-patterns*= under a lock. This prevents runtime/dataset isolation, bypasses the manifest/RuntimePlan direction from #43, and makes a data-plane registry an executable callback bag.

The replacement is not another server-local matcher registry. Matcher declarations, predicate/combinator semantics, field selection, extraction behavior, and transform result semantics belong to StarLang.

** URL output bypasses canonical ingest

The URL extractor constructs URL and relation documents, calls =as-json=, then publishes them directly to =documents.new.<dtype>= through the process-global producer agent. Current server persistence already has mutation IDs and durable outbox/event semantics. Generated documents should re-enter the canonical validated ingest/application boundary instead of pretending a Rabbit publication is equivalent to accepted persistence.

** Existing URI extraction is not a safe URI contract

The current PCRE scanner embeds an ad-hoc HTTP(S) URL grammar. RFC 3986 defines URI syntax as structured scheme, authority, path, query, and fragment components; a single handwritten domain/path regex is not a substitute for parsing and normalization.

For unstructured plain text, standards do not define where prose punctuation ends and a URI begins. Candidate discovery therefore needs a deliberately conservative bounded lexical step followed by an actual URI parser/normalizer. HTML/source acquisition should use structured link extraction at its source adapter when markup structure is available instead of flattening markup and regex-scanning it.

The URI primitive should be a closed StarLang matcher/transform primitive. Its implementation may use a Common Lisp URI library inside StarLang, but the server must not call a private Lisp matcher function or expose arbitrary regex callbacks as the language model.

** StarLang has a real runtime surface, but its stable embedding boundary is incomplete

The final =starlang-runtime= system already exports concrete runtime, actor, lifecycle, mailbox, dispatcher, and shutdown APIs. This is substantial implementation and is enough to prove that in-process Common Lisp embedding is the right direction rather than introducing another process boundary.

However, the complete compiler/load/document API is still exposed through =prototype/star-lang-api.lisp= and delegates to prototype-era parser/compiler/loader/document packages. The final =starlang-compiler= system does not yet own the complete production parser → expansion → validation → normalized IR path. StarLang #6 still records incomplete conformance, while #47 and #52 explicitly require prototype authority to be retired.

Therefore StarLang is *not yet ready as a stable production dependency boundary for starintel-server*. It is ready enough for this design to target embedding, but #44 implementation must not bind directly to prototype packages and then fossilize them as a server API.

* Requirements Derived from Evidence

1. There must be one typed document-transform ingress boundary that receives already validated canonical documents; it must not be a second persistence or broker ingress authority.
2. Matcher definitions and matcher evaluation semantics are owned by StarLang. The server may configure/select compiled matcher programs and provide typed ports, but it may not define a parallel Lisp callback matcher DSL.
3. StarLang must expose a stable final-system embedding API sufficient to compile/check/load approved =.star= programs, create isolated runtime instances, bind explicit host ports/capabilities, execute programs, and shut them down deterministically. Prototype packages are not an acceptable production dependency.
4. Transform definitions must be inert, versioned, and deterministic after compilation. They may contain only closed StarLang semantics and references to explicitly installed typed adapter/port capabilities; they may not contain arbitrary Common Lisp callbacks, shell commands, raw actor refs, credentials, broker/database handles, or host Lisp objects.
5. Dataset/actor deployment manifests from #43 select compatible compiled StarLang matcher/transform bindings. They cannot widen StarLang-declared input/output types or capabilities and cannot inject replacement matcher code.
6. Runtime execution resolves destinations through #42 component identities/handles and explicit StarLang runtime/program handles, never long-lived raw actor references.
7. Fan-out is bounded by input bytes, enabled transforms, candidates per matcher, outputs per transform, aggregate outputs, deadline, and mailbox/admission capacity. #34-#36 remain server resource authorities.
8. One transform failure is isolated and represented as a typed StarLang outcome; it cannot suppress unrelated transforms.
9. Generated documents are validated and submitted through the canonical application/ingest mutation boundary, inheriting idempotency/outbox/persistence semantics. Direct =documents.new.*= publication is not authoritative acceptance.
10. Every generated document carries provenance linking source document ID/revision or digest, StarLang transform ID/version/program digest, extraction location/field, and run/correlation identity.
11. URL extraction uses bounded candidate discovery plus URI parsing/normalization. Initial policy accepts explicit =http= and =https= absolute URI candidates only; adding schemes is a versioned StarLang semantic/policy change.
12. Duplicate URI candidates within one source document normalize before emission. Cross-request/retry duplicate suppression belongs to canonical idempotency (#47), not an in-memory set pretending to be durable authority.
13. Matching/extraction itself is pure with respect to network and storage. Dereferencing URLs belongs to Source Acquisition, not this matcher.
14. The server supplies application/effect ports, including canonical generated-document ingest, through explicit bounded StarLang capability bindings. StarLang does not become persistence authority.
15. Multiple StarLang runtime instances must be able to coexist in one SBCL image without a process-global matcher registry. Shutdown/restart must invalidate runtime-local references and release all owned resources.
16. Compatibility code may delegate old =start-url-extractor=/pattern APIs during migration, but global =*document-patterns*= cannot remain a second authoritative registry after cutover.
17. Implementation of the production matcher cutover is gated on the =STARLANG_EMBED_READY= acceptance contract tracked by StarLang #53. Design work may proceed before that gate is green.

* StarLang-First Boundary

The semantic order is:

1. define document matcher/transform declarations, selectors, predicates, combinators, extraction primitives, result types, provenance, and limits in StarLang;
2. compile those declarations through the final =starlang-compiler= path into immutable runtime-neutral IR/program artifacts;
3. embed final StarLang systems directly in =starintel-server= through a documented public Common Lisp library API;
4. compile selected matcher/transform programs into the server #43 RuntimePlan as immutable StarLang program identities/bindings, never Lisp function objects;
5. instantiate/run those programs in explicit StarLang runtime instances with bounded server-provided ports/capabilities;
6. return typed generated-document candidates/results to the server application boundary;
7. submit generated documents through canonical ingest;
8. use external processes only for capabilities that actually require them.

The StarLang implementation itself remains Common Lisp. “Matcher is StarLang” means matcher behavior is authored, typed, compiled, versioned, and invoked as StarLang semantics rather than exposed as arbitrary host Lisp callbacks.

* Proposed StarLang Matcher/Transform Contract

A normalized StarLang transform declaration/program needs at least:

- stable =transformId= and version/program digest;
- accepted input dtype/schema range;
- emitted dtype set;
- typed matcher/predicate/extractor expression;
- selected source fields or typed selectors;
- maximum inspected input bytes;
- maximum candidate count;
- maximum emitted documents;
- deadline/budget reference;
- provenance policy;
- dataset/component binding compatibility;
- required typed host capabilities/ports;
- failure policy limited to typed continue/fail-current-transform semantics.

The compiled representation must not contain live actor references, arbitrary function objects, credentials, Rabbit routing keys, database handles, host executable names, or a pointer to the retired server =*document-patterns*= registry.

A host port may be implemented internally by a Common Lisp function/object, but that implementation detail is owned by the final StarLang adapter boundary. The StarLang program sees only the closed typed port/capability contract.

* URL Extraction Semantics

The first bounded URL transform should be written as a StarLang matcher/transform and should:

1. inspect only explicitly configured textual fields valid for the input document type;
2. scan at most the declared input-byte/candidate ceiling;
3. recognize explicit =http://= or =https://= candidate starts through a closed bounded StarLang lexical primitive;
4. conservatively trim surrounding prose delimiters without attempting to invent a universal natural-language URL grammar;
5. pass each candidate to a closed StarLang URI parse/normalize primitive and require a valid authority/host under the selected scheme;
6. normalize scheme/host and other components according to the chosen versioned policy without deleting semantically meaningful path/query data;
7. deduplicate normalized candidates within the source document;
8. emit typed canonical URL plus source→URL relation candidates with extraction provenance;
9. hand those typed candidates to the server-provided canonical-ingest application port rather than publishing directly to Rabbit.

The extractor does not fetch the URL, resolve DNS, follow redirects, classify content, or infer identity.

If StarLang implements the URI primitive using QURI or another Common Lisp library, that dependency belongs behind the StarLang final-system primitive implementation. The server should not carry a second URL-matching semantic implementation.

* StarLang Embedding Readiness

Current determination: *NOT READY YET for stable production embedding*.

StarLang #53 owns the consumer-facing =STARLANG_EMBED_READY= gate. The minimum relevant blockers are:

- the complete production parser/compiler/check/load path must be final-system owned;
- the public embedding API must import no =*.prototype= package;
- normal embedding must not load =starlang-prototype= or files under =prototype/=;
- relevant #6 conformance blockers must be green;
- the #47/#52 final-system migration gates required by the embedding path must be green;
- two isolated runtimes must coexist safely in one process;
- deterministic shutdown must leave no StarLang-owned worker/thread/process/resource behind;
- compiled programs must not contain raw Lisp callbacks/objects or actor refs;
- StarLang-owned bounded matcher/transform semantics must pass the URL extraction fixtures;
- a downstream StarIntel integration test must compile and execute a =.star= transform using final systems only.

This is an implementation dependency, not a reason to create another temporary server matcher architecture. The correct response to “StarLang is not ready yet” is to finish the embedding boundary in StarLang, not to make the server-local callback registry permanent.

* Adversarial Review

Rejected alternatives:

1. *Wire the existing global list into a new actor* — revives dead code but preserves arbitrary callbacks, raw actor refs, global authority, and unbounded fan-out.
2. *Replace the list with another server-local matcher DSL* — creates a second language beside StarLang and guarantees semantic/configuration drift.
3. *Embed =prototype/star-lang-api.lisp= as the permanent server contract* — converts a transitional implementation path into a de facto public ABI and works against StarLang #47/#52.
4. *Publish generated documents directly to Rabbit* — bypasses validated persistence/outbox/idempotency and confuses event transport with canonical acceptance.
5. *Use a larger URL regex* — increases complexity without establishing URI parsing or stable normalization semantics.
6. *Expose arbitrary regex + Common Lisp callback pairs as StarLang matcher declarations* — only renames the callback bag; it does not make matcher semantics StarLang-owned or portable.
7. *Make the matcher a generic server workflow engine* — orchestration belongs to StarLang bounded playbook/domain semantics; the server side is a host/runtime/application boundary.
8. *Let dataset manifests contain Lisp callbacks/regex code* — makes inert configuration executable and creates a shadow language.
9. *Fetch every extracted URL immediately* — couples pure extraction to Source Acquisition and creates unbounded SSRF/network effects.
10. *Use raw actor names as subscriptions* — stale references survive component replacement; #42 generation-bearing handles and StarLang runtime-local identities own runtime identity.
11. *Treat an extraction as evidence that the URL is reachable or owned by the source entity* — the result is only an observed textual reference until separately acquired/verified.
12. *Spawn StarLang as a separate process only because the embedding API is unfinished* — adds an unnecessary transport/lifecycle boundary around a Common Lisp language/runtime. Finish the in-process embedding contract instead.
13. *Let StarLang persist generated documents directly* — makes the language runtime a shadow persistence authority and bypasses server canonical ingest.

* Lifecycle State

Research evidence is sufficient for =READY_FOR_DESIGN=.

The server matcher implementation dependency chain is intentionally explicit: #43 RuntimePlan, #42 component handles, canonical application/ingest ports from #40/#41, bounded admission #36, durable idempotency #47, and StarLang #53 =STARLANG_EMBED_READY= all constrain realization. That affects implementation readiness, not the ability to complete the revised design now.

The existing server matcher registry is already operationally dead, so there is no justification for rushing a prototype-backed production embedding merely to preserve it. The target remains one StarLang-owned matcher authority.

* Unresolved Questions

- Which exact canonical v0.9 field selector contract should the first StarLang message/text transform use after current top-level =content=/=bio= legacy assumptions are reconciled with actual schemas?
- Which canonical relation predicate/name should represent textual URL extraction in the current document specification?
- What is the smallest closed StarLang matcher expression surface needed for the first vertical: selectors + boolean predicates + bounded extraction primitives, or does an existing approved StarLang transform/playbook construct already cover it without a new declaration form?
- Which final StarLang system should own the URI parse/normalize primitive and its dependency so it remains reusable without bloating the core compiler?
- How should the server #43 RuntimePlan reference compiled StarLang matcher programs: immutable program digest + declaration ID, artifact handle, or another already-approved final StarLang program identity? This should align with StarLang #53 rather than inventing a server-only representation.

* Footnotes and Glossary

[fn:transform] A bounded StarLang operation that consumes one typed document and returns typed candidate/generated results without owning transport or persistence authority.

[fn:matcher] A StarLang-owned typed predicate/extraction expression used to decide whether and how a document transform applies. It is not an arbitrary Common Lisp callback.

[fn:canonical-ingest] The server application boundary that validates and persists a canonical document and coordinates durable event/outbox behavior.

[fn:embedding] Loading final StarLang compiler/runtime systems directly into the same Common Lisp process through stable public APIs, with explicit runtime instances and host ports rather than prototype package coupling or a separate language process.

[fn:uri] Uniform Resource Identifier as defined by RFC 3986; URL is used here for HTTP(S) URI observations emitted as StarIntel URL documents.
