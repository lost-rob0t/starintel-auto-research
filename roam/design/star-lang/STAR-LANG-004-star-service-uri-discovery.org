* Amendment Scope

This document no longer defines a private StarLang URI grammar.

The original implementation proved that transport-neutral =star:= identities are useful for actor manifests and dispatch. The URI syntax itself has since been generalized by [[file:../star-server/STAR-SERVER-041-star-uri-authority-routing-protocol.org][STAR-SERVER-041]] into the RFC 3986 hierarchical authority/resource model.

This amended document owns only the StarLang projection of that shared protocol:

- actor and service identity in StarLang source and portable manifests;
- deterministic manifest-only resolution;
- runtime-directory representation of live StarLang services;
- mapping from canonical STAR identity to runtime-specific actor references;
- compatibility treatment of legacy StarLang actor-tuple URIs;
- the boundary between StarLang domain servers and authority routing.

STAR-SERVER-040 and STAR-SERVER-041 own cross-process authority registration, leased routing, transport-profile selection, deadlines, cancellation, and canonical STAR operation/result semantics.

* Decision

New StarLang source and manifests SHALL use canonical RFC 3986 STAR resource identities.

Generic form:

#+begin_example
star://<authority>/<resource-kind>/<resource-path>
#+end_example

Actor form:

#+begin_example
star://<authority>/actor/<actor-resource-path>
#+end_example

Service form:

#+begin_example
star://<authority>/service/<service-resource-path>
#+end_example

Illustrative examples:

#+begin_example
star://gserver.starintel.actor/actor/user-hunt
star://gserver.starintel.actor/actor/quasar/user-hunt
star://bbpd.starintel.actor/actor/nmap
star://bbpd.starintel.actor/service/recon
#+end_example

The example authority names are illustrative and do not define production deployment names.

The canonical URI names a logical resource. It does not select HTTP, RabbitMQ, Sento remoting, ZeroMQ, a process, a host port, or an actor-system object.

The StarLang/runtime split is:

#+begin_example
StarLang source / portable manifest
        |
        v
canonical STAR resource URI
        |
        +--> deterministic manifest-only resolution
        |
        +--> local runtime-directory resolution
        |
        +--> StarRouter authority resolution for cross-process routing
                         |
                         v
                runtime descriptor
                         |
                         v
                selected runtime adapter
#+end_example

* Normative URI Authority

STAR-SERVER-041 is normative for:

- RFC 3986 parsing and canonicalization;
- authority representation;
- path-segment representation;
- global resource-kind semantics;
- rejection of userinfo, transport ports, dot segments, query, and fragment in canonical v1 identities;
- percent-encoding normalization;
- legacy URI compatibility boundaries;
- authority registration and resource-prefix routing.

StarLang MUST reuse the shared URI value model and conformance fixtures. It MUST NOT maintain a second actor-specific canonicalizer.

The reusable value model exposes at least:

#+begin_example
authority
path-segments
resource-kind
resource-path
#+end_example

It does not expose new canonical URIs as fixed =domain=, =address=, or =actor-name= URI fields.

* Legacy StarLang URI Compatibility

The original syntax:

#+begin_example
star://domain:address:actor-name
#+end_example

is compatibility input only.

Examples such as:

#+begin_example
star://quasar:localhost:user-hunt
star://bbp:localhost:nmap
#+end_example

MUST NOT be emitted by new StarLang manifests.

There is no universal automatic rewrite from the old tuple into a new hierarchical identity. Migration requires an explicit canonical target URI or an application-owned migration map.

Conceptually:

#+begin_src lisp
(migrate-legacy-star-uri
 old-uri
 :to "star://gserver.starintel.actor/actor/user-hunt")
#+end_src

The compatibility layer validates the explicit target against the shared STAR URI rules. It does not infer a new authority from the old =domain= or =address= fields.

* Manifest Model

Actor manifests may declare one optional canonical actor resource URI.

#+begin_src lisp
(actor user-hunt
  (:runtime native
   :service-uri "star://gserver.starintel.actor/actor/quasar/user-hunt"
   :accepts (username-search)
   :produces (username-search-result)
   :handler user-hunt-handler
   :restart permanent
   :mailbox (bounded 256)))
#+end_src

The compiled actor IR and portable manifest retain =:service-uri= as canonical data. The manifest does not contain a live Sento actor cell, socket, RabbitMQ queue, ZeroMQ endpoint, host object, or process identifier.

For a StarLang actor declaration:

1. the URI must be canonical under the shared STAR URI profile;
2. the resource kind must be =actor=;
3. one canonical URI may identify at most one actor contract in a manifest;
4. duplicate URI claims are invalid;
5. authority-specific actor path semantics may add stricter naming rules, but the generic StarLang compiler does not resurrect a fixed =domain/address/actor-name= grammar.

Service declarations use =/service/= and follow the service resource contract instead of pretending every callable boundary is an actor.

* Static Manifest Versus Runtime Registration

Manifest declaration and runtime registration remain distinct.

Manifest declaration:

#+begin_example
star://gserver.starintel.actor/actor/quasar/user-hunt
  actor = user-hunt
  capabilities = username-search
#+end_example

Runtime observation:

#+begin_example
service-uri = star://gserver.starintel.actor/actor/quasar/user-hunt
runtime = cl-gserver
alive = true
ref = runtime-specific reference
endpoint = runtime metadata, if applicable
#+end_example

The manifest answers what logical service an application declares. A runtime directory answers which local/runtime instance is reachable. StarRouter answers which authority instance/prefix/transport should receive a cross-process operation.

No transport endpoint becomes canonical identity merely because it is currently reachable.

* Runtime Directory Extension

The existing optional StarLang runtime-directory port remains the local/runtime discovery boundary.

Directory entries MAY include:

#+begin_src lisp
(:name "user-hunt"
 :service-uri "star://gserver.starintel.actor/actor/quasar/user-hunt"
 :authority "gserver.starintel.actor"
 :resource-kind "actor"
 :resource-path ("quasar" "user-hunt")
 :runtime :cl-gserver
 :alive t
 :capabilities ("username-search")
 :ref <opaque-runtime-reference>)
#+end_src

The generic StarLang layer validates portable URI/resource metadata but treats =:ref= and transport endpoint data as opaque runtime material.

A concrete Sento/cl-gserver adapter may source local liveness and actor references from the real actor system. Other runtime backends may implement the same directory contract without changing logical URI identity.

* Resolution

** Deterministic resolution

Deterministic execution does not perform network or authority discovery.

For a canonical actor URI:

#+begin_example
command :actor = star://gserver.starintel.actor/actor/quasar/user-hunt
  -> parse/canonicalize with shared STAR URI library
  -> require resource kind = actor
  -> find the manifest actor with the exact canonical URI
  -> dispatch through the registered deterministic handler
#+end_example

Actor-name dispatch may remain as a bounded source/runtime compatibility feature where the language contract still allows it.

** Local runtime resolution

A local runtime may resolve the exact canonical URI through its injected runtime-directory snapshot and obtain a live opaque actor reference.

Typed failures distinguish at least:

- malformed or noncanonical STAR URI;
- unsupported resource kind for the requested operation;
- resource not registered;
- resource registered but unavailable/stopped;
- duplicate local registration;
- incompatible capability/runtime binding.

** Cross-process resolution

StarLang MUST NOT invent a second distributed registry.

For cross-process destinations, resolution delegates to the STAR-SERVER-040/041 StarRouter authority model:

#+begin_example
canonical STAR URI
  -> authority registration
  -> longest matching resource prefix
  -> eligible leased/generation-fenced authority instance
  -> compatible transport profile
  -> canonical STAR operation forwarding
#+end_example

StarLang remains responsible for its actor/message semantics. StarRouter remains responsible for authority routing and transport selection.

* Domain Servers

A StarLang =domain-server= is not represented by a URI =domain= field.

A domain server is a runtime/supervision boundary that may:

- own keyed StarLang actor state;
- expose actors and services;
- claim its own STAR authority; or
- operate beneath an explicitly delegated prefix of another authority;
- advertise capabilities and runtime transport profiles through the authority-routing layer.

Examples of two valid ownership models:

#+begin_example
independent authority:
  star://bbpd.starintel.actor/actor/nmap

explicitly delegated beneath a gserver authority:
  star://gserver.starintel.actor/actor/bbpd/nmap
#+end_example

These are different authority/ownership decisions. The generic URI parser must not treat =bbpd= as a magic language-level domain component.

STAR-LANG-RESEARCH-014 remains the historical domain-remoting prototype and must be revised against this authority model before its registration/routing design is promoted as current domain-server architecture.

* Runtime Dispatch

Runtime-backed StarLang execution receives or resolves a runtime descriptor, then dispatches through the selected adapter.

#+begin_example
star://bbpd.starintel.actor/actor/nmap
  -> local directory or StarRouter authority resolution
  -> runtime descriptor
  -> selected adapter
  -> tell / ask / transport operation
#+end_example

The logical STAR URI remains stable when the implementation moves between same-process Sento, remote Sento, ZeroMQ, HTTP, or another approved transport profile.

Durable RabbitMQ work remains a separate settlement/dataflow concern where the application contract requires broker durability.

* Wire Semantics

Existing StarLang message envelopes may continue carrying a canonical STAR URI as the actor/destination string where the current protocol field permits it.

At system boundaries, sender and destination identity should remain canonical STAR URIs. Runtime adapters may map those URIs to local names, opaque references, or transport routes internally.

Transport routing metadata must not rewrite logical request identity.

* Capabilities

Capabilities remain manifest and runtime registration metadata, not URI syntax.

Discovery may return canonical STAR URIs by authority, resource prefix, or capability, but a capability selector is not embedded into canonical resource identity.

* Relationship to Runtime Endpoint Materialization

STAR-LANG-RESEARCH-015 remains valid in its core separation: runtime endpoints are deployment material, not language identity.

Example:

#+begin_example
logical identity:
  star://bbpd.starintel.actor/actor/nmap

resolved runtime descriptor:
  runtime = sento
  endpoint = sento://worker.internal:4912/user/nmap
#+end_example

or:

#+begin_example
logical identity:
  star://bbpd.starintel.actor/actor/nmap

resolved runtime descriptor:
  runtime = zeromq
  endpoint = tcp://worker.internal:5555
#+end_example

The canonical STAR URI does not change when the transport endpoint changes.

* API Design

The StarLang URI API should consume the shared reusable STAR URI implementation rather than retain actor-tuple accessors.

Conceptual public operations include:

#+begin_src lisp
(parse-star-uri "star://gserver.starintel.actor/actor/user-hunt")
(star-uri-string uri)
(star-uri-authority uri)
(star-uri-path-segments uri)
(star-uri-resource-kind uri)
(star-uri-resource-path uri)
(resolve-star-service-uri directory context uri)
#+end_src

Legacy parsing and migration live in an explicit compatibility module/API.

Exact exported Common Lisp names remain implementation-owned and must follow the final shared URI package API rather than this design inventing a parallel parser package.

* TDD-First Migration Slice

Implementation follows STAR-SERVER-041 Phase A and Phase C:

1. write shared RFC 3986 STAR URI conformance fixtures first;
2. extract/generalize the existing StarLang URI parser into the reusable shared URI boundary;
3. implement canonical authority/path parsing and serialization once;
4. retain the old tuple parser only in a compatibility module;
5. require explicit legacy migration targets;
6. update StarLang actor/service manifests to emit RFC-based canonical URIs;
7. update runtime-directory entries and deterministic dispatch to use shared URI values;
8. add tests proving one- and multi-segment actor resource paths do not recreate fixed =domain= semantics;
9. add local Sento/runtime integration evidence using canonical URIs;
10. add domain-server fixtures for independent-authority and delegated-prefix ownership without committing to one deployment topology;
11. keep StarRouter authority routing outside StarLang runtime ownership;
12. run the full StarLang and cross-language STAR URI conformance gates before migration completion.

* Deferred Work

This document does not define:

- the authority trust root or credential format;
- operator policy for delegated authority/prefix claims;
- the production authority name for starintel-gserver or BBPD;
- the complete domain-server v2 registration/control protocol;
- distributed consensus beyond STAR-SERVER-040 leased registration semantics;
- application authorization implied by URI ownership;
- transport-specific security profiles;
- Quasar registry UI.

The starintel-gserver authority integration formerly deferred by this document is now designed in STAR-SERVER-041 and is no longer an unowned gap.

* Acceptance

The amended design is conformant when:

1. new StarLang actor/service manifests emit only RFC-based canonical STAR URIs;
2. URI parse/serialize behavior is shared with STAR-SERVER-041 conformance fixtures;
3. new code has no canonical URI dependency on =domain= or =address= tuple fields;
4. legacy tuple URIs are accepted only through explicit compatibility APIs;
5. legacy migration requires an explicit new target URI or mapping;
6. deterministic dispatch resolves exact canonical manifest actor URIs;
7. runtime-directory resolution returns the exact live entry without embedding transport into identity;
8. stopped, missing, duplicate, malformed, and incompatible entries remain distinguishable;
9. one- and multi-segment =/actor/= paths are valid without assigning fixed domain semantics;
10. cross-process routing delegates to StarRouter rather than adding a second distributed registry;
11. domain-server fixtures support both independent-authority and delegated-prefix models;
12. existing actor-name compatibility behavior remains explicit and bounded where retained;
13. full StarLang and shared URI conformance tests are green at the exact implementation head.

* Footnotes and Glossary

- *STAR URI* — Canonical transport-neutral resource identity using RFC 3986 hierarchical =star://authority/path= syntax as specialized by STAR-SERVER-041.
- *Authority* — Stable logical owner/resolver of a STAR namespace, independent from the current network endpoint or process instance.
- *Resource kind* — Reviewed first path segment such as =actor= or =service=.
- *Resource path* — Ordered path segments following the resource kind; their semantics belong to the resource contract, not the generic URI parser.
- *Runtime directory* — Injected StarLang boundary returning observed local/runtime descriptors and liveness without defining distributed authority ownership.
- *Manifest identity* — Stable portable service metadata compiled from StarLang source; it contains canonical URI data but no live runtime object or transport endpoint.
- *Runtime descriptor* — Runtime-specific observation that may include liveness, opaque actor references, and endpoint metadata while preserving canonical STAR identity.
- *Legacy actor URI* — The superseded =star://domain:address:actor-name= syntax retained only as bounded compatibility input.
- *Domain server* — Independently supervised StarLang runtime/domain boundary that may own keyed actors and either claim an authority or operate under an explicitly delegated authority prefix.
