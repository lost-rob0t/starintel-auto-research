#+title: STAR-RESEARCH-037 Titanic Polyglot ZeroMQ Research Boundary Correction
#+description: Clarify that ZeroMQ is valuable polyglot transport research, not the selected Titanic v1 architecture. Titanic v1 uses RabbitMQ for brokered work delivery and LMDB for the first authoritative journal.
#+status: REVIEW
#+last_modified: [2026-08-10 Mon]
#+filetags: :starintel:star-server:titanic:rabbitmq:lmdb:couchdb:zeromq:polyglot:actors:transport:correction:research:org-roam:

* Purpose

This node corrects a research-to-design promotion error in the Titanic stack.

The prior version correctly found that ZeroMQ is technically attractive for polyglot process boundaries and correctly recovered historical StarIntel router-socket work. It then promoted that finding into a canonical Titanic implementation requirement.

That promotion was not justified by the research alone.

ZeroMQ remains useful research and an available transport option. It is not the selected Titanic v1 worker transport merely because another StarIntel ADR approves ZeroMQ for some process/language boundaries.

* Research Is Not Architecture Approval

The earlier argument collapsed three different claims:

1. ZeroMQ is technically suitable for heterogeneous workers.
2. StarIntel has prior ZeroMQ architecture/research that may be reused where appropriate.
3. Titanic therefore must use ZeroMQ.

The research established the first two. The third is a separate design choice.

The current v1 direction is intentionally simpler and aligned with deployed StarIntel infrastructure:

#+begin_example
actor / producer
      |
      v
  RabbitMQ
      |
      v
 Titanic coordinator
      |
      v
     LMDB
 authoritative job journal
#+end_example

* Selected Titanic V1 Direction

For Titanic v1:

- RabbitMQ is the brokered actor-job transport and scheduling plane.
- LMDB is the first authoritative durable job-store implementation.
- Titanic owns stable job identity, state transitions, attempts, retries, cancellation, deadlines, idempotency, retained results, dead-letter/replay lineage, and reconciliation semantics.
- Sento remains the local Common Lisp actor runtime.
- The =star.titanic/1= envelope remains transport-neutral even though the first adapter is RabbitMQ.
- ZeroMQ is not a mandatory Titanic v1 dependency.

This matches [[id:starintel-star-server-research-034][STAR-RESEARCH-034 Titanic Durable Actor Job Protocol]], which already models RabbitMQ as the initial durable cross-process work-delivery adapter.

* Why RabbitMQ First

RabbitMQ already exists in StarIntel and already supplies the broker mechanics Titanic needs:

- durable exchanges/queues;
- persistent publication;
- publisher confirms;
- explicit ACK/NACK settlement;
- dead-letter routing;
- competing consumers;
- routing keys;
- prefetch/backpressure;
- redelivery and reconnect behavior.

The stable Titanic contract must still avoid leaking AMQP details.

Do not make delivery tags, exchange names, channel numbers, queue arguments, connection objects, or Rabbit-specific queue types part of =star.titanic/1=.

The public contract belongs to StarIntel-owned fields and semantics such as =job_id=, =attempt_id=, =capability=, =operation=, =deadline=, =idempotency_key=, correlation/causation, result, retry class, and terminal state.

* Why LMDB First

LMDB remains a strong fit for the first local Titanic journal:

- embedded in the coordinator rather than another network service;
- full local ACID transactions;
- one write transaction can cover multiple keys/sub-databases;
- readers do not block the writer and the writer does not block readers;
- very small operational footprint;
- historically present behind Titanic in the recovered StarIntel architecture.

The single-writer model must be benchmarked against expected admission/state-transition rates, but a coordinator-owned state-machine journal naturally provides a serialization point anyway.

The backend remains hidden behind a =job-store= interface so this decision is replaceable.

* CouchDB Finding

[[id:starintel-star-server-research-038][STAR-RESEARCH-038 Titanic CouchDB Backend Fit]] evaluates CouchDB separately.

CouchDB is a serious candidate and an excellent projection/operator store. It can also implement an authoritative journal if each logical job is modeled as one aggregate document and =_rev= is used for compare-and-transition semantics.

It is not the preferred first v1 journal because CouchDB lacks atomic multi-document updates and its cluster/replication conflict model adds distributed-state concerns Titanic does not need in the smallest implementation.

Recommended v1 role:

#+begin_example
RabbitMQ -> Titanic -> LMDB
                    |
                    v
                 CouchDB
          query/projection/replication
#+end_example

Do not use CouchDB revision history or =_changes= as the canonical Titanic lifecycle audit trail.

* ZeroMQ Research Role

Keep all ZeroMQ research.

It remains relevant for:

- Sento cross-process transport;
- future remote actor gateways;
- specialized low-latency worker pools;
- language-neutral ROUTER/DEALER experiments;
- cases where broker durability is deliberately not wanted;
- interoperability testing across Common Lisp, Nim, Python, and JavaScript.

The earlier Common Lisp/Nim/Python/JavaScript ZeroMQ conformance matrix remains useful as transport research. It is no longer a Titanic v1 implementation gate.

A later design may add a =zmq= Titanic adapter if an actual requirement justifies it. That adapter must satisfy the same Titanic backend/transport contract rather than redefining job semantics.

* Historical Router Socket

The recovered 2023 diagram approximately showed:

#+begin_example
actors -> Broker <-> Titanic <-> LMDB
                         |
                    router socket
                    /           \
               worker         worker
#+end_example

This is useful lineage evidence. It demonstrates that the historical system separated broker traffic, durable Titanic persistence, and a router socket.

It does not require the modern v1 to preserve every historical edge.

The durable idea worth preserving is Titanic itself: persistent request/job identity and disconnected result retrieval. The exact worker transport is replaceable.

* V1 Reliability Rule

The difficult correctness boundary in v1 is not ZeroMQ versus RabbitMQ. It is the dual-write boundary between the authoritative journal and RabbitMQ.

Use the failure model from [[id:starintel-star-server-research-036][STAR-RESEARCH-036 Titanic Failure Semantics and Contract Tests]]:

1. create or recover one stable logical job;
2. durably record job state plus an outbox/reconciliation record;
3. publish the attempt through RabbitMQ with publisher confirmation;
4. mark publication confirmation durably;
5. process with explicit broker settlement;
6. make side effects idempotent/fenced;
7. durably record terminal outcome before reporting completion;
8. reconcile every crash window rather than claiming a distributed transaction that does not exist.

* Decision

Correct the Titanic research stack as follows:

- RabbitMQ is the selected Titanic v1 brokered worker transport.
- LMDB is the selected first authoritative Titanic v1 journal.
- CouchDB is a serious alternate backend and excellent derived projection; see STAR-RESEARCH-038.
- ZeroMQ remains valid and valuable research, but it is not the canonical Titanic v1 transport.
- The stable =star.titanic/1= contract remains transport/backend neutral.
- Historical ZeroMQ/TSP/router-socket work is lineage and implementation research, not a binding architectural mandate.
- NATS JetStream, Kafka, Temporal, and other alternatives stay comparative until an explicit requirement promotes them.

This node supersedes its previous claim that ZeroMQ was the required canonical Titanic worker transport.
