* REVIEW Objective

Build a reusable Common Lisp Model Context Protocol[fn:mcp] and large-language-model tooling substrate first, then implement =starintel-meta-mcp= as a thin package in the same monorepo.

The Meta MCP[fn:meta-mcp] is a deterministic information execution plane. It accepts bounded retrieval operations, resolves permitted semantic capabilities to providers, executes a plan, normalizes and fuses results, and returns attributable output.

It is not the StarIntel platform API and it is not an autonomous research agent.

The target layering is:

#+begin_example
client / LLM / agent
        |
        v
StarIntel Meta MCP
  search / fetch / later crawl
        |
        +--> SearXNG
        +--> YaCy crawl/index adapter
        +--> external MCP providers
        +--> full StarIntel MCP

future StarIntel A2A Agent
        +--> Meta MCP
        +--> full StarIntel MCP
#+end_example

The intended public search service name may be =search.starintel.actor=, but host placement, network topology, private addresses, credentials, reverse-proxy layout, and deployment routing are explicitly outside this public design and belong to downstream infrastructure RAGE work after approval.

* REVIEW Invariants

1. Reusable library systems are implemented before application-specific Meta MCP composition.
2. The final =starintel-meta-mcp= package contains tool definitions, composition, configuration, and StarIntel-specific policy only; it does not become the canonical implementation of generic MCP protocol/client/server behavior.
3. The client-visible Meta surface stays small and semantic. Provider-specific upstream tool names are not mechanically re-exported.
4. =search= and =fetch= are the initial public Meta operations.
5. =crawl= is a later bounded deterministic operation and may materialize as an MCP Task[fn:mcp-task].
6. =research= is not a Meta MCP tool. Iterative research belongs to the future StarIntel Agent exposed through Agent2Agent[fn:a2a].
7. The full StarIntel MCP is the authoritative interface for StarIntel capabilities, authorization, resource scope, and mutation.
8. Meta never reads or writes CouchDB, Clouseau, internal queues, or other StarIntel persistence internals directly.
9. Search scope is an authority ceiling. A planner cannot invoke a provider outside the caller-selected and authorized information universe.
10. Provider selection is deterministic and capability-based in the first implementation.
11. Adapter identity and physical provider/origin identity are separate so duplicate access paths do not create false corroboration.
12. Search, fetch, and crawl never silently promote retrieved content into canonical StarIntel data.
13. Partial provider failure is represented explicitly and does not automatically fail a federated request when useful results remain.
14. Raw fetched content and upstream MCP output are untrusted data and cannot expand capabilities.
15. Every output that influences ranking, evidence, or later StarIntel work retains provenance sufficient to reconstruct its retrieval path.

* REVIEW Reusable Library Systems

System names in this section are semantic boundaries and may be renamed during monorepo reconciliation. The boundaries are normative; exact package names are not.

** =cl-mcp-core=

Owns:

- protocol version negotiation
- JSON-RPC[fn:json-rpc] message types
- MCP request, result, error, notification, capability, resource, prompt, and tool data types needed by dependent systems
- canonical protocol serialization and decoding boundaries
- typed protocol conditions
- version-specific compatibility fixtures

It performs no application routing and no provider-specific search behavior.

** =cl-mcp-transport=

Owns implementation-neutral transport interfaces and shared request metadata. Concrete systems may include:

- =cl-mcp-transport-stdio=
- =cl-mcp-transport-http=

Remote HTTP support must implement the current Streamable HTTP requirements, including Origin validation, bounded request handling, authentication integration points, cancellation, and explicit response lifetimes.

** =cl-mcp-client=

Owns:

- initialization and capability negotiation
- tool/resource/prompt discovery
- cacheable discovery state
- request dispatch and correlation
- timeout and cancellation
- upstream MCP authentication hooks
- typed remote errors
- reconnect/retry policy boundaries

It must be usable independently of StarIntel.

** =cl-mcp-server=

Owns:

- server initialization and capability advertisement
- declarative tool registration
- JSON Schema[fn:json-schema] input/output contracts
- request validation
- tool dispatch
- structured errors
- transport-neutral server lifecycle
- authorization hook points

It must support application packages other than StarIntel.

** =cl-mcp-tasks=

Owns the optional MCP Tasks extension:

- task identifiers and state
- task creation from eligible tool calls
- get/update/cancel semantics
- task result materialization
- terminal-state invariants
- extension capability negotiation

Meta crawl may depend on this system after the task conformance suite is green. Initial search/fetch must not depend on Tasks.

** =cl-tool-capability=

Owns semantic capability and provider registration independent of MCP transport.

A provider descriptor includes at least:

#+begin_src lisp
(:provider
 (:id :brave-mcp)
 (:adapter-kind :mcp)
 (:physical-origin :brave)
 (:capabilities (:web-search :news-search :image-search :place-search))
 (:result-kinds (:web :news :image :place))
 (:authority-class :external-network)
 (:cost-class :metered)
 (:freshness :live)
 (:health :unknown)))
#+end_src

Provider descriptors never contain secrets in durable public configuration.

** =cl-exec-plan=

Owns a deterministic execution-plan[fn:execution-plan] abstract syntax tree and executor contract.

Initial node kinds:

#+begin_example
call
parallel
fallback
race
limit
merge
normalize
dedupe
rank
#+end_example

A plan is data. Provider code does not recursively call arbitrary other providers outside the compiled plan.

The executor must support:

- per-call and whole-plan deadlines
- cancellation propagation
- bounded concurrency
- partial-result collection
- typed provider failure
- deterministic merge order where semantics require it
- tracing and correlation identifiers

The first planner is ordinary Common Lisp code. Prolog, Prolog-RLM, or model-driven routing is not part of this design.

** =cl-search-model=

Owns one normalized retrieval model shared by HTTP and MCP providers.

A normalized result contains at least:

#+begin_src lisp
(:search-result
 (:id "stable-request-local-id")
 (:kind :web)
 (:title "...")
 (:snippet "...")
 (:locator "https://example.org/item")
 (:timestamp nil)
 (:score nil)
 (:content-hash nil)
 (:provenance
   ((:adapter :searxng
     :physical-origin :brave
     :source-locator "https://example.org/item"
     :retrieved-at "RFC3339"))))
#+end_src

StarIntel-native result identifiers may use opaque StarIntel references instead of public URLs.

** =cl-search-fusion=

Owns:

- canonical locator normalization
- content-hash-assisted duplicate detection
- physical-provider/origin deduplication
- result clustering
- initial Reciprocal Rank Fusion[fn:rrf] or another explicitly benchmarked fusion strategy
- deterministic tie-breaking
- preservation of every contributing provenance edge

Fusion must never interpret two adapters to the same physical provider as two independent confirmations.

** =cl-search-provider=

Defines the provider protocol consumed by the planner/executor:

#+begin_example
provider-capabilities
provider-health
provider-search
provider-fetch
provider-crawl     ; optional
provider-cancel    ; optional
#+end_example

Concrete adapters depend on this protocol rather than the final Meta MCP package.

** HTTP provider adapters

Initial reusable adapters:

- SearXNG search adapter
- YaCy crawl/index adapter

SearXNG is the default broad metasearch path. Local YaCy search should normally be exposed through SearXNG's YaCy engine rather than a duplicate direct search path. Direct YaCy integration exists for crawl/index operations and for explicitly justified diagnostics or conformance tests.

** MCP provider adapter

A generic upstream-MCP provider maps discovered MCP tools onto declared semantic capabilities. The adapter must not infer dangerous authority solely from a tool name or description.

Provider onboarding requires a reviewed mapping such as:

#+begin_src lisp
(:mcp-capability-map
 (:server :brave-search)
 (:tool "brave_web_search")
 (:capability :web-search)
 (:physical-origin :brave)
 (:authority :read-only-network))
#+end_src

Dynamic =tools/list= discovery updates runtime availability, but the reviewed semantic mapping determines which tools are eligible for a Meta plan.

** =starintel-mcp-client-adapter=

This adapter uses the generic MCP client and search-provider contracts to access the separately defined full StarIntel MCP.

It owns no StarIntel database access. It maps only authorized StarIntel MCP capabilities into Meta retrieval capabilities such as intelligence search, document fetch, entity lookup, or relation lookup.

** Final =starintel-meta-mcp= package

The final package owns only:

- public Meta tool schemas
- StarIntel-specific scope and result-kind vocabulary
- provider composition/configuration
- planner policy
- authorization/scope projection into eligible capabilities
- service startup and health aggregation

It consumes all generic systems above.

* REVIEW Meta Tool Contract

** =search=

Initial semantic shape:

#+begin_src lisp
(:search
 (:query "required string")
 (:scope :auto)
 (:type :auto)
 (:filters ())
 (:limit 20))
#+end_src

Initial scope vocabulary:

| Scope | Meaning |
|-------+---------|
| =auto= | Planner may choose any caller-authorized information universe required by deterministic request classification |
| =web= | Public/external web retrieval only; private StarIntel data is ineligible |
| =archive= | StarIntel-owned archival/indexed web retrieval, initially local YaCy-backed paths |
| =intel= | Authorized StarIntel MCP retrieval only; public web providers are ineligible |
| =all= | Union of the caller-authorized web, archive, and intelligence universes |

Initial result types may include =auto=, =web=, =news=, =images=, =places=, =documents=, =entities=, and =relations=. Unsupported scope/type combinations fail deterministically rather than silently broadening scope.

=scope= constrains the set of legal capabilities before provider selection. It is not a post-search filter.

** =fetch=

=fetch= retrieves a known result reference or locator through the best eligible retrieval path while preserving provenance.

Resolution may use:

- a StarIntel MCP document/entity reference when the caller is authorized
- a local indexed copy
- an upstream extraction/fetch MCP capability
- bounded live HTTP retrieval through an approved provider

The caller can request a stricter scope; resolution cannot broaden it.

** =crawl= — later phase

=Crawl= means bounded deterministic traversal and optional search-index retention.

The contract must include explicit ceilings for at least:

- starting locator or source reference
- allowed scope/domain boundary
- maximum depth
- maximum pages or documents
- wall-clock deadline
- byte budget
- concurrency
- retention/index mode
- cancellation

A crawl may be executed directly when small or materialized as an MCP Task when long-running. It never means canonical StarIntel ingest.

* REVIEW Planner and Execution

The planner receives:

#+begin_example
normalized operation
+ requested scope
+ caller authority projection
+ desired result kind
+ filters
+ provider capability registry
+ provider health
+ explicit cost/latency policy
= execution plan
#+end_example

The first implementation must use deterministic rules and fixtures. Example:

#+begin_src lisp
(:plan
 (:parallel
   (:call :searxng :search ...)
   (:call :starintel-mcp :search ...))
 (:normalize)
 (:dedupe :physical-origin :locator :content-hash)
 (:rank :rrf)
 (:limit 20))
#+end_src

This is execution planning, not autonomous research. A plan does not generate new questions, reinterpret task goals, or decide when an investigation is complete.

* REVIEW Provider Selection and Duplicate Origins

Adapter identity and physical origin are independent fields.

Examples:

| Adapter path | Physical origin | Normal interpretation |
|--------------+-----------------+-----------------------|
| SearXNG -> Brave engine | Brave | one Brave source family |
| Brave MCP | Brave | same source family, richer capability path |
| SearXNG -> non-Brave engine | corresponding upstream engine | independent only if origin differs |
| SearXNG -> local YaCy | local YaCy index | archival/index source family |
| direct YaCy crawl/index adapter | local YaCy | same local index authority, different operation class |
| StarIntel MCP | StarIntel | authorized private intelligence source family |

The planner should prefer one route to a physical provider for one ordinary search. Multiple adapters to the same physical origin are used only when an explicit comparison, fallback, or capability requirement justifies it.

* REVIEW Authority and Service Boundary

The Meta service is a potential confused deputy[fn:confused-deputy] and therefore must not hold unrestricted StarIntel authority on behalf of narrower callers.

Required properties:

1. Caller authentication terminates at a reviewed boundary.
2. The normalized request contains an immutable authority projection with correlation identity.
3. Scope compilation intersects requested scope with caller grants; it never unions new authority.
4. StarIntel operations are sent through the full StarIntel MCP.
5. The full StarIntel MCP performs the authoritative capability/resource decision.
6. Meta does not derive access from route strings, provider names, dataset text, or client-supplied claims alone.
7. Credentials and secret verifier material are never included in normalized results, provenance, public logs, or published plans.

The exact token exchange, service identity, credential location, and deployment topology are deferred to the private implementation/topology phase.

* REVIEW Failure Semantics

Provider outcomes are typed:

#+begin_example
success
partial-success
timeout
rate-limited
auth-denied
unavailable
invalid-result
cancelled
policy-denied
#+end_example

A federated search may return =partial-success= when at least one eligible provider produced usable results and no invariant requires all providers. The response must identify omitted/degraded provider classes without exposing secrets or internal topology.

Fallbacks are bounded and specified by the plan. Providers cannot trigger unbounded recursive retries.

* REVIEW Crawl Contract

Crawl is separated into operation and retention semantics.

Operation modes may include:

- =ephemeral=: traverse and return bounded references/artifacts without durable search-index retention
- =indexed=: traverse and retain approved documents in the archival/search index

Neither mode implies StarIntel canonical ingest.

Canonical promotion remains:

#+begin_example
search/fetch/crawl result
        |
        v
explicit authorized StarIntel ingest/action through full StarIntel MCP
#+end_example

The crawl adapter must enforce network and content safety policy, including bounded redirects, host/domain policy, response ceilings, cancellation, hostile-content handling, and prevention of accidental access to prohibited internal resources.

* REVIEW Agent Boundary

The future StarIntel Agent is a separate Agent2Agent service.

Its semantic responsibility is:

#+begin_example
research goal
  -> decide questions and subquestions
  -> search/fetch/crawl through Meta MCP
  -> inspect authorized StarIntel state through StarIntel MCP
  -> identify evidence gaps
  -> iterate within task budget
  -> produce research artifacts
#+end_example

The A2A agent owns iterative reasoning, gap analysis, branch selection, stopping criteria, and research artifacts. Meta MCP remains a bounded capability execution plane.

The agent may have additional StarIntel abilities only through the full StarIntel MCP and its normal authorization model.

* REVIEW Monorepo Rule

The implementation must live in one Common Lisp MCP/LLM-tooling monorepo with independent ASDF systems.

Repository layout is intentionally non-normative until the target monorepo is selected, but the dependency direction is normative:

#+begin_example
protocol/types
   ^
transports   client   server   tasks
   ^          ^        ^
   +----------+--------+
              ^
capabilities / execution-plan / search-model / fusion
              ^
provider adapters: SearXNG / YaCy / generic MCP / StarIntel MCP
              ^
starintel-meta-mcp
#+end_example

No generic lower-level library may depend on =starintel-meta-mcp=.

* REVIEW Phased Implementation

** Phase 0 — conformance fixtures

- pin the targeted MCP protocol revision
- define protocol/client/server compatibility fixtures
- define normalized result/provenance fixtures
- define execution-plan and cancellation fixtures
- define provider-origin deduplication fixtures
- define fake providers; continuous integration makes no paid provider calls

** Phase 1 — reusable MCP and execution libraries

- implement MCP core/types
- implement STDIO and Streamable HTTP transports
- implement reusable MCP client/server
- implement capability registry
- implement execution-plan AST/executor
- implement search result/provenance and fusion libraries
- prove these systems with non-StarIntel example applications/tests

** Phase 2 — search providers and initial Meta MCP

- implement SearXNG adapter
- implement generic upstream MCP provider adapter
- implement reviewed capability mappings for initial external search MCPs
- implement StarIntel MCP retrieval adapter once the full StarIntel MCP contract exists
- ship Meta =search= and =fetch=

** Phase 3 — crawl

- implement direct YaCy crawl/index adapter
- implement MCP Tasks extension if not already completed
- ship bounded =crawl=
- prove cancellation, partial completion, retention, and no-implicit-ingest invariants

** Phase 4 — future A2A agent

- implement reusable A2A protocol/client/server support as separate libraries if needed
- implement StarIntel Agent as a consumer of Meta MCP plus full StarIntel MCP
- place autonomous =research= behavior here, not in Meta MCP

* REVIEW Acceptance Criteria

The design is implementation-ready only when:

1. The canonical research node is reviewed.
2. Every reusable ASDF boundary has a declared API and dependency direction.
3. MCP client and server conformance fixtures cover the pinned protocol revision and transport behavior.
4. A non-StarIntel demo proves the MCP libraries are reusable outside =starintel-meta-mcp=.
5. Fake SearXNG, YaCy, upstream MCP, and StarIntel MCP providers can execute one normalized plan without network access.
6. Provider-origin fixtures prove Brave-through-SearXNG plus Brave-through-MCP is not counted as independent corroboration.
7. =scope=intel= can never generate a public-web provider call in deterministic plan tests.
8. =scope=web= can never generate a private StarIntel MCP call.
9. A degraded provider returns partial results without hiding the degradation.
10. Search/fetch never mutate StarIntel.
11. Crawl tests prove explicit ceilings, cancellation, retention mode, and no implicit StarIntel ingest.
12. The full StarIntel MCP remains the only Meta path to private StarIntel capabilities.
13. No Prolog-RLM or model planner is required to pass the initial conformance suite.
14. No infrastructure topology, secret, private address, or production credential is encoded in the public libraries or public research docs.
15. Downstream infrastructure RAGE receives implementation/topology requirements only after separate approval.

* Footnotes and Glossary

[fn:mcp] Model Context Protocol, or MCP: A protocol for exposing model-controlled tools, resources, prompts, and related capabilities through standardized client/server messages.

[fn:meta-mcp] Meta MCP: The StarIntel execution-plane service that composes multiple retrieval providers behind a small semantic MCP tool surface.

[fn:mcp-task] MCP Task: A durable asynchronous operation created through the MCP Tasks extension and queried or cancelled through task operations.

[fn:a2a] Agent2Agent, or A2A: A protocol for interoperable remote agents that discover skills and exchange tasks, messages, status, and artifacts.

[fn:json-rpc] JSON-RPC: The request/response message format underlying MCP protocol messages.

[fn:json-schema] JSON Schema: A machine-readable schema language used to validate structured tool inputs and outputs.

[fn:execution-plan] Execution plan: A bounded data structure describing which providers to call, how calls compose, and how their outcomes are normalized and fused.

[fn:rrf] Reciprocal Rank Fusion, or RRF: A ranking method that combines ordered result lists by adding reciprocal functions of each result's rank.

[fn:confused-deputy] Confused deputy: A security failure where a service with broad authority is tricked into using that authority for a caller who lacks it.
