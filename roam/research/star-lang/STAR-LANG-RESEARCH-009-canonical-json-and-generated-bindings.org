* Purpose

Loop 008 established one normalized specification and actor-contract model. This pass makes that model consumable outside Common Lisp without inventing a second schema language.

The compiler now projects the same manifest into:

- canonical JSON manifest data
- schema-validated canonical JSON message envelopes
- Python typing bindings
- TypeScript typing bindings

* Field Naming

All document fields, message-payload fields, and serialized envelope keys use lower camelCase. Canonical JSON and generated bindings preserve the source spelling exactly; they do not translate kebab-case fields at generation time. A kebab-case field is rejected during parsing or semantic validation. Declaration and type identifiers remain outside this rule.

* Numeric Model

Star-Lang distinguishes approximate binary floating-point values from exact base-10 decimal values.

- =integer= is exact and serializes as a JSON number.
- =float= is an approximate finite IEEE-754 binary64 value and serializes as a JSON number. It is appropriate for latitude, longitude, altitude, accuracy, measurements, scores, and scientific data where approximate arithmetic is expected.
- =decimal= is an exact base-10 value and serializes as a canonical JSON string. It is appropriate for money, rates, quantities with contractual scale, and values that must not change through binary floating-point conversion.

Float serialization rejects NaN, positive infinity, and negative infinity because JSON has no interoperable representation for them. Finite float values use a deterministic shortest round-trip decimal representation. Negative zero is canonicalized to =0= so equivalent values do not produce different canonical bytes.

The current Star-CL geo schema uses decimal latitude, longitude, altitude, and accuracy fields. Those approximate geospatial fields should migrate to =float= while =decimal= remains available for exact fixed-precision domains.

* Canonical JSON

Canonical output uses:

- lexicographically sorted object keys
- declaration order for arrays
- UTF-8 strings with JSON escaping
- integers as JSON numbers
- finite float values as canonical JSON numbers
- booleans as JSON booleans
- exact decimal values as canonical JSON strings
- omitted absent optional envelope members
- qualified Star-Lang identifiers as wire type names

Numeric encoding follows the declared schema type. A JSON number is valid for an =integer= or =float= field but not for an exact =decimal= field. A decimal string is valid for =decimal= but must not be silently accepted for =float=.

* Schema-Aware Envelopes

Envelope serialization resolves =messageType= against the portable manifest before encoding =payload=. The encoder validates:

- required fields
- closed message field names
- list shapes
- integer and boolean values
- finite float values for float-typed fields
- precision-safe decimal strings for decimal-typed fields
- enumeration membership
- scalar aliases
- map and reference object shapes
- local qualified types

The existing envelope remains transport-neutral. RabbitMQ, HTTP, Unix sockets, NATS, ZeroMQ, and subprocess transports may carry the same bytes and contract identifiers.

* Python Bindings

The generator emits Python 3 typing definitions using:

- =TypedDict=
- =Required=
- =NotRequired=
- =Literal=
- exact lower-camelCase source field strings
- flattened inherited document fields
- actor contract metadata

Star-Lang field names use lower camelCase and remain exact dictionary keys; generators do not silently rename them. Scalar and enumeration type names become PascalCase aliases. Float wire types map to Python =float=; decimal wire types map to =str=.

* TypeScript Bindings

The generator emits:

- scalar aliases
- string-literal enumeration unions
- document interfaces
- interface inheritance
- message interfaces
- lower-camelCase source field names
- actor contract metadata with =as const=

Float wire types map to TypeScript =number=. Decimal wire types map to =string= for the same exactness rule used by Python and canonical JSON.

* FEC and Geo Conformance Output

The FEC fixture produces four CI artifacts:

- =star-lang-fec-manifest.json=
- =star-lang-fec-envelope.json=
- =star_lang_fec.py=
- =star_lang_fec.ts=

The Star-CL fixture additionally exercises geo latitude, longitude, altitude, and accuracy fields as floats. CI parses generated JSON, compiles the generated Python source, and verifies deterministic TypeScript structure until a pinned TypeScript compiler is added.

* Compiler Boundary

The flow is:

#+begin_example
source.star
  -> normalized specification IR
  -> semantic validation
  -> portable manifest
  -> canonical JSON
  -> Python / TypeScript bindings
#+end_example

No generator reads the original source independently. All language adapters consume the same validated manifest.

* Tests

The pass checks:

1. repeated manifest serialization is byte-identical
2. qualified type names survive serialization
3. envelope object keys are canonicalized
4. list fields encode as JSON arrays
5. geo latitude, longitude, altitude, and accuracy float values encode as JSON numbers
6. finite float values round-trip through canonical binary64 serialization
7. NaN and positive or negative infinity fail validation
8. negative zero canonicalizes to JSON =0=
9. decimal strings pass and JSON-number decimal values fail
10. float fields reject decimal strings unless an explicit conversion is requested
11. invalid enum values fail
12. Python preserves exact lower-camelCase source keys
13. Python document bindings include inherited fields
14. TypeScript preserves interface inheritance
15. Python and TypeScript map float values to native numeric types and decimal values to strings
16. actor contracts appear in both generated languages
17. generated manifest and envelope files parse as JSON
18. generated Python bindings compile
19. kebab-case field declarations fail before binding generation

* Boundary

This pass does not:

- define a transport acknowledgement protocol
- implement actor registration or discovery
- generate Rust, Java, Go, or Prolog bindings yet
- pin a TypeScript compiler toolchain
- publish an SDK package
- start native or external actors
- select the final Star-Lang host implementation
- define arbitrary-precision binary floating-point types beyond binary64
- bypass the comparative language and promotion gates

The next wire pass should define acknowledgements, errors, correlation, cancellation, and idempotency semantics before transport adapters are treated as production interfaces.
