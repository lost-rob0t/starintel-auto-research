* Decision

CAPTCHA solving is a first-class StarIntel domain server.

The domain server owns the shared CAPTCHA protocol, capability discovery, authorization, routing, lifecycle, health, deadlines, result typing, solver selection, and configuration policy. Individual OSINT actors do not embed solver implementations and do not depend directly on a specific CAPTCHA provider.

Actors encountering a challenge MAY use the CAPTCHA Domain Server when it is enabled by init configuration, registered, healthy, authorized for the current target/purpose, and able to satisfy the exact challenge contract. Absence or disablement of the domain server is not a fatal runtime dependency.

The implementation preference is:

1. StarLang orchestration and domain behavior;
2. extend StarLang when a required runtime, configuration, or language primitive is missing;
3. Common Lisp libraries/adapters for implementation details that belong below the StarLang surface;
4. Python only when neither StarLang nor Common Lisp can reasonably implement or wrap the required dependency.

* Init-File Configuration

CAPTCHA solving is configured through the normal StarIntel init/config file. Operators must not edit provider or actor source code to change solver policy.

The init configuration expresses desired policy and preference. Runtime capability registration remains authoritative for actual installed and healthy solver availability.

The configuration surface must support at least:

- =enabled=: enable or disable =CaptchaDomainServer=;
- =autoSolve=: enable or disable automatic solve attempts by callers;
- =prefer=: ordered solver/provider preference;
- provider allow/deny controls;
- preference for the private/local solver when it is registered;
- external-provider enable/disable independent of the private/local solver;
- provider credential references;
- default solve timeout/deadline;
- maximum attempts;
- fallback policy;
- paid-provider cost/budget ceilings;
- operator/human fallback enablement;
- challenge-family allow/deny policy;
- telemetry/logging policy with mandatory secret redaction.

Credentials, cookies, browser sessions, challenge secrets, and result tokens must not be stored as plain literals in the init file when StarIntel can represent them as opaque secret/session references.

A conceptual configuration shape is:

#+begin_src lisp
(:captcha
  (:enabled t)
  (:auto-solve t)
  (:prefer (:private-local :nonecap :nopecha :2captcha))
  (:external-providers t)
  (:operator-fallback nil)
  (:max-attempts 2)
  (:timeout-seconds 90)
  (:max-cost-microunits 5000))
#+end_src

This is conceptual only. The final syntax follows the normal StarIntel init/config schema. If StarLang owns configuration schema compilation by implementation time, CAPTCHA configuration must be represented through StarLang and compiled into runtime configuration rather than introducing a separate CAPTCHA-specific parser.

A configured preference such as =:private-local= does not assert that the private solver is installed. The domain server resolves preference against live capability registration. A missing preferred solver is skipped according to configured fallback policy rather than treated as malformed configuration.

Calling actors must not read provider preference directly. They read only the domain-level policy they need, such as whether automatic solving is enabled, and delegate provider selection to =CaptchaDomainServer=.

* Domain Boundary

The logical service is =CaptchaDomainServer=.

It exposes bounded internal capabilities such as:

- =captcha.detectedChallenge=
- =captcha.solve=
- =captcha.applyResult=
- =captcha.providerHealth=
- =captcha.capabilities=

These are capability contracts, not promises that every challenge family is supported.

The domain server coordinates the existing broker/router and detection-resolution designs:

- [[id:star-captcha-000-broker-router][STAR-CAPTCHA-000 Authorized CAPTCHA Broker and Capability Router]]
- [[id:star-captcha-001-detection-resolution-orchestrator][STAR-CAPTCHA-001 CAPTCHA Detection and Resolution Orchestrator]]

The broker, run supervision, policy, capability registry, budgets, deduplication, telemetry, and ephemeral-result references are domain-server internals. Provider adapters and local solvers register exact capabilities with the domain server.

* Opportunistic Actor Integration

An actor that encounters a supported challenge follows this flow:

1. preserve the source request/session and emit a typed challenge observation;
2. honor the current init-file CAPTCHA policy, including =enabled= and =autoSolve=;
3. query the runtime capability catalog for a healthy =captcha.solve= capability;
4. if the CAPTCHA Domain Server is disabled, absent, or unhealthy, return a typed =blockedByChallenge= or partial result and continue according to the caller's policy;
5. if present, submit only the bounded challenge descriptor and opaque session/artifact references required by the exact capability;
6. the domain server authorizes the request and selects an eligible solver using init policy plus runtime capability state;
7. the solver returns an opaque typed result reference;
8. the source actor or authorized apply capability applies the result in the required source context;
9. downstream acceptance is recorded separately from solver completion;
10. the original actor resumes its collection workflow.

No actor should busy-loop, brute-force retry, or silently reinterpret a challenge as =notFound=.

* StarLang Requirements

The preferred StarLang surface must support or be extended to support:

- domain-server declaration and runtime registration;
- normal init/config schema declarations and access;
- capability discovery by typed contract;
- optional capability dependencies;
- supervised request actors/runs;
- bounded deadlines and cancellation;
- opaque artifact/session/result references;
- exact capability matching;
- typed partial and blocked outcomes;
- health-aware routing;
- cross-domain request/reply;
- resumable continuation after a challenge result;
- policy/capability checks before dispatch;
- provenance linking the challenge, solver attempt, result application, and downstream acceptance;
- bounded preference/fallback selection compiled from init policy.

If one of these cannot currently be expressed in StarLang, the first implementation task is to add the missing StarLang primitive rather than bypassing the language with an ad-hoc Python controller.

* Server and Plugin Repository Boundary

The 2026-09-16 operator directive supersedes the earlier instruction to migrate ordinary CAPTCHA actors into =lost-rob0t/starintel-server=. Specialized CAPTCHA providers, recognition workers, operator review, and headless browser actors belong to =lost-rob0t/starintel-pro-actors=, packaged as one trusted Common Lisp[fn:common-lisp] add-on[fn:add-on] loaded by StarIntel Server[fn:starintel-server].

The split follows ownership, not language convenience:

- =starintel-server= owns the provider-neutral CAPTCHA domain service, authorization, policy, broker/router, runtime-facing registry and discovery, secret/reference services, budgets, and optional integration used by ordinary actors;
- =starintel-pro-actors= owns specialized solver/provider actors and the shared WebDriver actor system, defines their actor manifests, and registers them through the server add-on lifecycle;
- a Pro Actors contract library defines the canonical Lisp request, result, error, deadline, cancellation, capability, and lifecycle values;
- Python and Nim libraries are thin callers of that versioned Lisp-owned contract and do not create a second registry, router, or control plane;
- StarLang remains authoritative for actor/domain semantics, and Star Router remains authoritative at client-facing or cross-authority routing boundaries.

#+begin_src plantuml
@startuml
package "starintel-server" {
  [CAPTCHA Domain Server]
  [Deployment Registry]
}
package "starintel-pro-actors Lisp add-on" {
  [Canonical Lisp Contract]
  [CAPTCHA Actors]
  [WebDriver Actors]
}
package "external callers" {
  [Python / Nim Clients]
}

[CAPTCHA Domain Server] --> [CAPTCHA Actors] : authorized exact solve
[Deployment Registry] --> [CAPTCHA Actors] : registered manifest
[Deployment Registry] --> [WebDriver Actors] : registered manifest
[Canonical Lisp Contract] --> [CAPTCHA Actors]
[Canonical Lisp Contract] --> [WebDriver Actors]
[Python / Nim Clients] --> [Canonical Lisp Contract] : versioned operations
[CAPTCHA Actors] --> [WebDriver Actors] : artifact ref + bounded apply
@enduml
#+end_src

* Private In-House Solver Boundary

StarIntel's own in-house solver is explicitly NOT open source.

The public repositories may expose only the stable interface required for a private solver to register and execute as an exact CAPTCHA capability. They must not contain or reconstruct the private implementation.

Keep private:

- in-house solver source code;
- private model weights;
- training pipeline implementation where it reveals the private solver;
- private training and evaluation corpora;
- private challenge-specific heuristics;
- model selection/routing logic unique to the private solver;
- private tuning data and production acceptance telemetry that would disclose solver internals;
- deployment secrets and private inference endpoints.

The private solver MAY register at runtime exactly like another solver provider. Public code must not require it to exist.

The existing self-sourced research remains architectural evidence but does not authorize publishing the private implementation:

- [[id:star-pro-research-008-self-sourced-captcha-solver-stack][STAR-PRO-RESEARCH-008 Self-Sourced CAPTCHA Solver Actor Stack]]
- [[id:star-pro-captcha-004-self-sourced-local-solver-actors][STAR-PRO-CAPTCHA-004 Self-Sourced Local Solver Actors]]

STAR-PRO-CAPTCHA-004 is therefore implementation-sensitive design material. Any public successor must describe only the stable registration/request/result boundary and must omit in-house solver internals.

* Security Boundary

The CAPTCHA Domain Server is not a public arbitrary-target solve relay.

Required invariants:

- internal authenticated actor/domain-server calls only;
- explicit authorization and target/purpose policy before solving;
- exact challenge capability matching;
- opaque session and result references instead of raw cookie/token transport;
- init-file credentials are opaque references rather than literal secrets when supported;
- bounded retries, deadlines, concurrency, and budgets;
- no proxy rotation or anti-detection behavior intended to evade target controls;
- no persistent logging of solution tokens or browser secrets;
- explicit unsupported/blocked outcomes;
- downstream acceptance verification distinct from provider completion.

* Repository and Plugin Plan

** Phase 1 — Design normalization

- make this domain-server design the repository-boundary authority;
- treat the 2026-09-16 Lisp-plugin directive as superseding the earlier actor-migration instruction while retaining the approved domain-server and private-solver decisions;
- preserve research citations and capability contracts;
- define the normal init-file CAPTCHA schema;
- mark private in-house solver material as non-public implementation detail.

** Phase 2 — Canonical contract and add-on boundary

Define the Lisp contract library, trusted add-on lifecycle, manifest registration/unregistration behavior, and Python/Nim conformance surface before implementing either actor system.

Do not copy private solver implementation, private models, private corpora, credentials, or production secrets.

** Phase 3 — StarLang domain server and Pro Actors plugin

Express the domain server, solver capability interface, init/config schema, optional dependency semantics, and challenge continuation flow in StarLang. Implement the specialized CAPTCHA and WebDriver actors inside the Pro Actors Lisp add-on only after their review-stage designs are approved. Add missing StarLang primitives before falling back to lower-level workarounds.

** Phase 4 — Actor adoption

Update OSINT actors incrementally. Actors that can encounter CAPTCHAs should declare an optional =captcha.solve= dependency, honor domain-level init policy, and resume from a typed result. Initial candidates include browser-backed collection, identity enumeration, web search/scraping, and infrastructure discovery actors where their normal authorized source path can encounter a challenge.

* Acceptance Criteria

- CAPTCHA is represented as one coherent domain server rather than a loose group of unrelated actors.
- CAPTCHA solving is configurable through the normal StarIntel init/config file.
- Init configuration controls enablement, automatic solving, solver preference, provider policy, deadlines, fallback, budgets, operator fallback, challenge-family policy, and secret-safe credential references.
- Runtime capability registration remains authoritative for actual solver availability.
- Actors can discover and use the domain server when available without making it a hard startup dependency.
- Actors honor =enabled= and =autoSolve= without embedding provider-specific configuration.
- Absence, disablement, or unavailability produces typed blocked or partial outcomes.
- Specialized provider, local-inference, operator, and WebDriver actors are packaged in =starintel-pro-actors= rather than embedded in the generic server core.
- The Lisp contract is canonical and Python/Nim clients pass the same conformance corpus without owning routing or actor lifecycle.
- The private in-house solver registers through the public contract but its implementation is absent from public repositories.
- StarLang is the preferred orchestration/configuration surface and missing primitives produce StarLang work rather than immediate Python workarounds.
- Tests cover init enable/disable, provider preference, provider allow/deny, missing private solver, external-provider disablement, fallback, deadlines, and budget limits.
- No public arbitrary-target solve endpoint exists.

* Footnotes and Glossary

[fn:common-lisp] Common Lisp: The implementation language of StarIntel Server and the canonical Pro Actors add-on contract.

[fn:add-on] Add-on: An optional trusted ASDF system loaded through StarIntel Server lifecycle hooks; it is a packaging boundary, not a security sandbox.

[fn:starintel-server] StarIntel Server: The Common Lisp service owning authorization, policy, deployment-facing discovery, persistence, and local actor hosting.

- *Domain server* — One logical optional service contract coordinating policy, capability selection, lifecycle, and typed outcomes across multiple implementations.
- *Plugin contract* — The versioned Lisp-owned request/result/error/cancellation/capability schema implemented by the add-on and consumed by language clients.
- *Opaque reference* — A short-lived identifier granting bounded access to sensitive artifact, session, or result material without copying it into ordinary messages.
- *Specialized actor* — A provider, inference, operator, or browser actor packaged outside the generic server core while using server-owned authorization and discovery.
