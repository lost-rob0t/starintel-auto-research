* Scope

2Captcha is a broad asynchronous task provider. Its value cannot be assessed from hCaptcha alone. Current official API navigation covers token systems, Web Application Firewall challenges, image and text recognition, coordinates, grids, rotation, draw-around, drag-and-drop, and multiple issuer-specific families.

Every task family has its own required fields and result schema. The generic =createTask= operation does not make task contracts interchangeable. Current official API navigation and pricing do not advertise hCaptcha, so hCaptcha is a capability-local absence and must not disable unrelated verified families.

The adapter rejects forbidden result-kind widening. Coordinates are not selections; a provider token is not downstream acceptance; a cookie is not a generic token.

* hCaptcha Contract State

Historical client material has referenced task names such as =HCaptchaTaskProxyless= and =HCaptchaTask=. The current official API v2 navigation, supported-task catalog, and public pricing reviewed on 2026-08-09 do not advertise hCaptcha or expose a current hCaptcha task page.

Therefore =captcha.hcaptcha.*= is =unsupported= for runtime registration on current official evidence. It may move out of =unsupported= only after one of these exists:

1. a current official task page with complete request and result schema;
2. written provider confirmation paired with a supported sandbox fixture; or
3. a credential-gated, cost-bounded probe against an operator-owned hCaptcha integration that is then backed by a stable documented contract.

An old software-development-kit symbol alone is insufficient. No hCaptcha absence changes the state of independently verified reCAPTCHA, Turnstile, GeeTest, Arkose, image, coordinate, grid, rotation, or other task capabilities.

* Execution and Human-Worker Disclosure

Current 2Captcha API documentation describes an AI-first service in which difficult or ambiguous tasks can be escalated to verified human workers. Older/provider-facing material also describes direct worker solving. StarIntel therefore must model execution conservatively:

- default external-disclosure class is =humanExposurePossible=;
- an exact task may be narrowed to =remoteAutomated= only when current provider evidence explicitly guarantees no human fallback for that capability;
- target policy must permit the worst-case disclosure class before challenge data is dereferenced or submitted;
- later provider telemetry cannot retroactively justify disclosure that policy denied at submission time.

The provider may receive target URLs, site keys, prompts, challenge images, task instructions, proxy/network context, cookies, or other bounded data required by the exact task. Authenticated page content, full browser snapshots, private session material, and personal data are not sent by default.

* Proxy, Cookie, User-Agent, Session, Network, and Mobile Rules

Each task declares its exact context requirements. The broker rejects a task when:

- a proxy type or same-network binding is required but unavailable;
- cookies are required but disclosure is not authorized;
- user-agent fidelity is required but cannot be preserved;
- the source browser session cannot consume the result safely;
- the capability is mobile-specific and no supported mobile context exists;
- the provider task would widen from proxy-required to proxyless or vice versa.

Context values remain behind ephemeral references.

* Budget, Pricing, and Accepted-Result Cost

Record the current provider price with the exact task contract and retrieval date. Current public pricing includes, for example, Turnstile at a fixed advertised per-thousand rate and reCAPTCHA ranges, but separate official provider pages make conflicting claims about whether load affects prices. That makes price a runtime contract field rather than a source-code constant.

Reserve cost before =createTask=. Reconcile only from provider evidence. Local cancellation or a failed downstream application does not prove that the provider did not charge.

Selection compares cost per downstream accepted result for the exact capability, not raw advertised task price or provider completion rate.

* Request Pacing, Idempotency, Duplicate Delivery, Cancellation, and Ambiguity

The adapter journals =attemptId= before creation and records =taskId= immediately after a successful create response. Duplicate local or RabbitMQ messages attach to the same active task or replay its terminal normalized result.

Provider request-limit guidance currently recommends waiting before the first result poll and using multi-second retry intervals; specific errors such as no-slot and zero-balance have longer minimum retry guidance. The adapter must encode those responses into policy-classified backoff rather than a uniform tight polling loop. Incorrect pacing can temporarily block the account or client IP.

No universal provider cancellation operation is assumed. Local cancellation stops polling, deletes unconsumed local result material, and reports =chargePossible=true= when the provider task may continue.

An ambiguous create without a recoverable =taskId= is not retried automatically. Fallback requires a terminal non-ambiguous prior state, new attempt ID, remaining budget, exact capability, and disclosure authorization.

* Browser API Boundary

2Captcha also documents a separate managed Browser API/CDP surface. That is not automatically part of the provider-neutral =createTask/getTaskResult= adapter. Treat managed-browser execution as a separate capability/provider boundary with its own session, proxy, fingerprint, disclosure, cost, lifecycle, and security research before any design is proposed.

* Error Contract and Capability-Local Drift

Normalize provider authentication, balance, invalid task, invalid fields, unsupported task, processing, unsolvable, timeout, service failure, malformed result, request pacing/rate limit, and callback-related errors. Every normalized failure records =retryable= and =chargePossible=.

Move only the affected capability to =invalidContract= when:

- a required field disappears;
- an unexpected result kind or required-field omission appears;
- the provider returns task-not-supported;
- the task page contradicts current fixtures;
- a capability probe fails its exact contract.

Shared client-key, balance, generic API, account block, or provider outage may temporarily disable all 2Captcha tasks.

* Security and Retention

Never persist or publish client keys, result tokens, cookies, text answers, coordinates, selections, interaction plans, proxy credentials, cookie bundles, page data, authorization headers, callback secrets, or full provider request/response bodies.

Provider retention and possible human-worker exposure must be reviewed from current terms and task documentation before enabling a capability. Result values remain in the ephemeral secret store and are consumed by the authorized source runtime through one-read references.

* Required Fixtures and Tests

- generic create, processing, ready, balance, feedback, and every relevant error;
- one current request/result fixture for every enabled task family;
- token, assessment, cookie, proof, text, coordinates, selections, interaction plan, and custom typed results;
- forbidden family, version, variant, field, result-kind, proxy, and session widening;
- hCaptcha remains unsupported until current contract evidence exists, independent of other tasks;
- duplicate delivery and task replay;
- ambiguous create without task ID;
- local cancellation with possible provider charge;
- human-exposure-possible disclosure denial before secret dereference;
- task-specific request pacing and temporary-block behavior;
- public-price contradiction detection and operator budget ceiling;
- managed Browser API kept outside the ordinary task adapter;
- budget exhaustion and cost reconciliation;
- client key, challenge context, provider response, and result redaction;
- capability-local drift;
- shutdown with active tasks;
- no callback listener in version one;
- no paid provider in continuous integration;
- per-family opt-in canaries on operator-owned systems only.

* Decision

Retain 2Captcha as a broad exact-capability provider candidate with possible human exposure. Implement family-specific request mappers and result validators only after design approval. Keep hCaptcha =unsupported= on current official evidence. Do not enable any task solely from an old software-development kit, marketing page, or shared =createTask= operation.

* Footnotes and Glossary

- *Human exposure possible* — Provider execution class in which the provider may escalate a task to a human even if automation is normally attempted first.
- *Task family* — One provider operation with a distinct request and result contract, such as Turnstile, reCAPTCHA v2, coordinates, or grid selection.
- *Capability-local drift* — A contract failure isolated to one exact task rather than a global provider rejection.
- *Ambiguous create* — A task-creation request whose provider-side outcome is unknown and may already be billable.
