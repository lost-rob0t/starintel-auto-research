* Objective

Use LISA where StarLang needs production-rule semantics: persistent working
memory, RETE-style incremental matching, agenda scheduling, salience, and
rule-driven conclusions. Keep LISA behind the portable StarLang logic contract
so native engine objects and executable host-language forms never leak into
=.star= source or portable runtime records.

* Approved Decision

StarLang SHALL implement LISA through the final-owned ASDF system:

#+begin_example
star-logic-adapter-lisa
#+end_example

LISA is the primary backend for =star.expert.production/1= and related
production-rule profiles.

It SHALL support persistent session working memory, ordered fact deltas,
RETE-style incremental matching, agenda activation/firing, compiler-validated
salience, negative/existential conditional elements where fixture-proven,
checked conclusions, bounded explanations, cancellation, budgets, and replay
under the same pinned backend/package/build contract.

LISA SHALL NOT claim SWI-Prolog tabling, generic recursive query semantics, or
constraint profiles merely because equivalent behavior could be hand-coded.

* Backend Boundary

#+begin_example
StarLang source
     |
     v
starlang-expert-compiler
     |
     v
closed expert / logic IR
     |
     v
trusted digest-locked LISA artifact
     |
     v
star-logic-adapter-lisa
     |
     v
isolated LISA session
     |
     v
normalized conclusions + proofs + usage
#+end_example

Native LISA engine handles, CLOS implementation details, agenda nodes,
activations, RETE nodes, or native working-memory objects MUST NOT cross the
portable =star-logic= boundary.

* StarIntel Object-Backed Fact Contract

Direct identity-preserving StarIntel object reasoning is required.

Conformance target:

#+begin_example
FAIL: StarIntel Person -> unrelated expert-person copy -> LISA
PASS: StarIntel Person -> identity-preserving object-backed fact -> LISA rules
#+end_example

The adapter SHALL preserve or map at least:

- authoritative StarIntel object/document ID;
- schema ID and version;
- provenance/evidence references;
- relation/document references required by the rule package;
- session fact identity;
- object generation/revision when freshness matters;
- proof/verification metadata required by the active profile.

LISA working memory is disposable session state. It is never a second canonical
StarIntel datastore.

* Object Lifecycle

The final adapter SHALL support:

1. project/register an authoritative StarIntel object into one session;
2. assert the identity-preserving object-backed fact;
3. mark an approved mapped change;
4. retract session visibility without deleting canonical state;
5. rebuild working memory from authoritative inputs plus journaled deltas;
6. reject stale or unmappable generations where the mapping contract requires freshness.

The portable runtime sees only StarLang fact identities and normalized deltas.

* Rule Artifact Contract

Only the compiler may produce executable LISA rule artifacts.

Each artifact records exact identity including:

#+begin_example
packageId
packageVersion
packageDigest
mappingDigest
compilerVersion
semanticProfile
engineCompatibility
#+end_example

Allowed rule actions come from closed StarLang action IR:

#+begin_example
conclude
assert-session-fact
retract-session-fact
#+end_example

Arbitrary Common Lisp calls, FFI, network/filesystem/database effects, shell
execution, or user-supplied LISA RHS code are forbidden.

* Working Memory and Authority

Fact roles are:

#+begin_example
source
session
derived
questionAnswer
#+end_example

- source facts are immutable from rules;
- session facts are local to one ExpertSessionActor;
- derived conclusions are inference/proof records;
- question answers are journaled session facts;
- cross-session global working memory is forbidden;
- no rule may directly write canonical StarIntel documents.

* Agenda and Salience

LISA owns the implementation of the production agenda, while StarLang owns the
observable profile semantics.

Salience is compiler-validated and serialized in the trusted artifact. Dynamic
host expressions for salience are forbidden. A profile that requires a stable
ordering must define all ordering inputs; otherwise StarLang does not promise an
incidental engine order.

* Conclusions and Proofs

Every normalized conclusion carries stable conclusion identity, rule identity,
supporting fact/object IDs, logical session sequence, proof reference when
required, and uncertainty contribution only under an approved uncertainty
profile.

Proof output uses:

#+begin_example
star.logic.derivation/1
#+end_example

Normalized nodes may include source/session facts, question answers, rule
applications, parameter bindings, conclusions, assumptions, contradictions,
uncertainty combination, and budget truncation.

Native activation/RETE diagnostics may be attached as bounded namespaced
metadata. The adapter MUST NOT fabricate proof steps.

* Uncertainty

Boolean reasoning is required for v1.

Potential certainty-factor or Dempster-Shafer profiles remain capability-gated
until exact combination, conflict, retraction, precision, serialization, and
proof semantics are fixture-proven. Native LISA belief features are evidence,
not automatic portable capability claims.

* Session Isolation and Lifecycle

One ExpertSessionActor owns one logical LISA session.

Permitted deployment classes may include trusted in-process integration or a
dedicated worker process when stronger isolation is required. The descriptor
must state the actual isolation class.

Lifecycle includes backend start, session open, package load, initial facts,
ordered deltas, run/walk to goal/quiescence/budget, question-answer resume,
conclusion/proof observation, cancellation, reset/close, and backend stop.

Recovery reconstructs the session from StarLang journaled inputs; arbitrary
native LISA memory structures are not the replay format.

* Budgets and Cancellation

The backend descriptor truthfully declares hard/cooperative/unsupported limits.
Potential budgets include wall time, conclusions, rule firings, questions, proof
nodes/bytes, output bytes, and memory where enforceable.

A cooperative limit MUST NOT be advertised as hard.

* Target Capability Set

After fixture proof, the adapter may advertise:

- typed facts via mapping;
- direct identity-preserving StarIntel object-backed facts;
- production agenda;
- salience;
- negative/existential conditional elements;
- persistent working-memory deltas;
- normalized explanation when package/profile supplies evidence;
- optional process isolation.

It does not initially advertise tabling or CLP(FD). Runtime descriptors remain
the source of truth; this document is the approved target contract, not evidence
that code exists.

* Security Invariants

1. Untrusted StarLang source never enters Common Lisp =READ= or =EVAL= as LISA rule source.
2. Only compiler-generated digest-locked rule artifacts execute.
3. Rule RHS behavior is closed and effect-free except approved session mutations/conclusions.
4. Arbitrary host function invocation is unavailable.
5. Canonical StarIntel objects/documents cannot be mutated by the backend.
6. Object mappings preserve identity, provenance, and authority boundaries.
7. Proof/output size is bounded and validated.
8. Session scope is enforced.
9. Secrets are excluded from generated packages, proofs, fixtures, and journals.

* Approved Prototype Retirement

The LISA backend SHALL exist only in final systems.

- No production LISA adapter, rule compiler, session owner, proof normalizer, or
  capability descriptor may be implemented under =prototype/=.
- Temporary prototype call sites may forward to =star-logic-adapter-lisa= while
  being migrated, but may contain no independent LISA behavior.
- LISA fixtures and tests move to final adapter/expert test systems as each slice lands.
- Any superseded prototype LISA or generic expert implementation is deleted in the same migration slice once callers move.
- Final LISA tests and Nix composition SHALL run without =starlang-prototype=.
- Repository-wide StarLang completion requires proving no product path still needs the prototype and deleting =prototype/= when that proof passes.

* Implementation Order

1. final adapter system and exact backend descriptor/handshake;
2. one real identity-preserving StarIntel object family;
3. assert/change/retract lifecycle and replay fixture;
4. production joins, negative/existential conditions, salience, deterministic agenda fixtures;
5. ExpertSessionActor integration, ordered deltas, question resume, cancellation, isolation;
6. normalized proof graph and proof budgets;
7. uncertainty/performance profiles only after boolean conformance;
8. remove each superseded prototype implementation/test as final ownership lands.

* Acceptance Gate

Implementation is complete when:

1. =star-logic-adapter-lisa= has final package ownership;
2. one real StarIntel object family is reasoned over without an unrelated expert-only duplicate;
3. identity/provenance survives mapping and appears in normalized proof support;
4. typed assert/change/retract deltas work in an isolated session;
5. joins, negative/existential conditions, and salience have deterministic fixtures;
6. rules emit normalized conclusions rather than native engine values;
7. a required-proof fixture produces =star.logic.derivation/1=;
8. source facts cannot be mutated by rules;
9. arbitrary RHS host calls and raw LISA source are rejected;
10. cancellation and budget behavior are fixture-proven;
11. same-backend replay is deterministic;
12. the descriptor advertises only fixture-proven capabilities;
13. no final LISA path loads =starlang-prototype= or =prototype/=.

* Footnotes and Glossary

- *Object-backed fact* — LISA-visible fact that preserves the authoritative StarIntel object identity instead of creating an unrelated expert-only canonical copy.
- *Production profile* — Versioned StarLang semantics for persistent working memory and agenda-driven rule firing.
- *Trusted rule artifact* — Compiler-generated digest-locked LISA package; never direct untrusted =.star= source.
- *Working-memory delta* — Ordered session mutation represented through stable StarLang fact identity.
- *Prototype retirement* — Removal of transitional prototype ownership as final LISA systems become authoritative.
