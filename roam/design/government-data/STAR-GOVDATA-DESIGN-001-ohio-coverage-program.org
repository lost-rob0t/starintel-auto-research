* REVIEW Objective

Make Ohio the first state executed from the generated jurisdiction catalog.

The program produces reviewed source profiles and append-only route-assessment revisions for the State of Ohio and all 88 counties. It identifies official domains, delegated vendor systems, source families, acquisition methods, temporal and jurisdictional scope, refresh behavior, provenance requirements, explicit gaps, applicability decisions, and historical source identity.

This is a bounded execution design. It does not claim Ohio coverage is complete and does not implement the production actor runtime.

* REVIEW Architecture Decision

Ohio is a state-scoped run over reusable government-data authorities, actors, and adapters.

There is no permanently running Ohio actor and no permanent actor per county. Government units and components are durable records and bounded job keys. The run coordinator carries state code =OH=, state FIPS =39=, county GEOIDs, policy bounds, contract versions, and checkpoint identifiers.

#+begin_example

The run requires these durable authorities before any live wave:

- Government Identity Authority
- Source Profile Authority
- Route Assessment Authority
- Raw Artifact Authority
- Provenance Validator
- Coverage Ledger
- Official Domain Resolver Pool
- Platform Fingerprint Pool
- Adapter Registry
- bounded adapter workers
- independent review authority

A live wave cannot begin until the durable records and authorities needed by its exit gate exist and pass deterministic replay fixtures.

* REVIEW Scope

** Included

- State of Ohio identity and official-domain spine
- all 88 Ohio county GEOIDs
- state systems used directly by the state or shared with local governments
- official and delegated county and component systems
- the shared sixteen-route catalog contract
- source discovery, verification, fingerprinting, bounded probing, and profile review
- Franklin County as the first complete county pilot
- fingerprint-driven diverse-county validation
- current-source identity plus immediately visible predecessor, successor, and archive relationships
- explicit unsupported, inaccessible, retired, ambiguous, records-request-required, and not-applicable states

** Deferred

- exhaustive municipality, village, township, school district, and special-district coverage
- production crawling
- automatic public-records request sending
- account creation or credential enrollment
- bypass of access controls or CAPTCHAs
- acquisition of protected personal information
- production normalization into final StarIntel document schemas
- continuous scheduling before pilot acceptance
- exhaustive historical acquisition beyond the minimal historical identity required in every wave

* REVIEW Ohio Identity Set

The initial state set is:

- State of Ohio
- 88 counties with state FIPS =39=
- county components discovered during source profiling, including auditors, recorders, clerks, boards of elections, prosecutors, sheriffs, engineers, treasurers, courts, commissions, health districts, and planning bodies

A component is not automatically an independent government. Each component record declares its parent, function, legal or administrative authority, service geography, source authority, identity confidence, and whether the function is county-owned, independently elected, shared, regional, municipal, state-provided, or not applicable to the county.

| finance | Ohio Checkbook, Auditor of State | budget, audit, payroll, checkbook, debt, grants, scope gaps |

* REVIEW Cross-Wave Historical Identity

Every discovery and profiling wave records the minimal historical identity visible during bounded work:

- first-seen and last-seen observations
- predecessor and successor locators
- redirects and documented vendor migrations
- archive candidates and retired-domain evidence
- immediately visible earliest and latest coverage dates
- current, prior, and future-effective distinctions when exposed

This requirement does not authorize exhaustive archive crawling. It prevents current ownership and source identity from being reconstructed later from scratch.

* REVIEW Execution Waves

** Wave 0: Identity, legal baseline, and fingerprint census

1. load Ohio and all county GEOIDs
2. verify state identity and authoritative domain relationships
3. capture current public-records, open-meetings, retention, and archival authorities
4. create unresolved county and component domain candidates without promotion
5. collect bounded platform, vendor, delegation, shared-service, court, and health-system fingerprints
6. record minimal historical identity for every observed locator

Exit gate:

- State of Ohio identity is verified
- all 88 county records exist with stable GEOIDs
- legal and policy sources have content hashes and effective-date metadata
- a preliminary platform and organizational variation matrix exists
- every observed active locator has minimal historical identity fields
- no county is marked complete

** Wave 1: State source systems

Profile Ohio Laws, Legislature, OhioBuys, Ohio Checkbook, OGRIP/OSIP/LBRS, Secretary of State, Supreme Court, Auditor of State, and state archival/retention systems.

Exit gate:

- each source family has a reviewed profile revision or explicit reviewed blocked/unsupported result
- acquisition methods are ranked by stability
- rate, pagination, file-size, browser, authentication, and scope requirements are recorded
- raw evidence exists for every promoted profile revision
- county-indexed discovery seeds and participating-unit crosswalks are stored where exposed
- Checkbook participation remains a discovery/reconciliation signal rather than a finance completion decision
- minimal historical identity is recorded

** Wave 2: Franklin County pilot

Franklin County GEOID =39049= is the first complete end-to-end county pilot.

The pilot enumerates at least:

- county and component identities and domains
- commissioners and meeting systems
- auditor, parcel, property, GIS, recorder, deed, treasurer, and tax systems
- court and clerk components where public
- board of elections and local election data
- sheriff, jail, public-safety, and inspection sources where applicable and lawfully public
- procurement and vendor-payment sources
- budget, audit, payroll, debt, and grant sources
- zoning, planning, permit, health, and code-service providers
- public-records policy, portal, contacts, fees, and retention
- current and minimal historical source identity

Franklin exit gate:

- all sixteen routes have reviewed route-assessment revisions under one pinned applicability-contract version
- every required subfamily has a reviewed result
- each route ends in =:verified=, =:verified-partial=, =:not-published=, =:records-request-required=, =:authentication-required=, =:paywalled=, =:blocked=, =:retired=, or =:not-applicable=
- =:candidate-found=, =:ambiguous=, and =:unassessed= cannot pass the pilot gate
- every =:not-applicable= result identifies the responsible function or service provider and includes applicability evidence
- every negative terminal result binds a completed search-plan revision and a gap with =reassess-after=
- the pilot decision pins exact source-profile revision IDs, search-plan revisions, evidence IDs, and gap IDs
- every promoted profile resolves to official ownership or delegation evidence
- deterministic replay reproduces the same assessment basis and state
- unresolved manual-review work is zero for required subfamilies

** Wave 3: Fingerprint-driven diverse-county pilot

The Wave 3 set is provisional until Wave 0 fingerprinting is reviewed. Initial candidates are:

- Cuyahoga County =39035= — large metro
- Hamilton County =39061= — large metro and legacy-system candidate
- Lucas County =39095= — northwest urban candidate
- Delaware County =39041= — fast-growing suburban candidate
- Athens County =39009= — Appalachian and university-centered candidate
- Vinton County =39163= — low-population rural candidate
- Hancock County =39063= — mid-sized northwest agricultural and industrial candidate

Final selection maximizes observed variation across:

- vendor and platform families
- official-domain versus delegated hosting
- publication maturity and negative-finding burden
- independent-office fragmentation
- shared or regional services
- court and health-service topology
- geography, population, and urbanicity
- archive and migration patterns

A candidate may be replaced only by a recorded selection decision showing that another county increases variation. The final set must include a mid-sized non-large-metro or western/northwestern agricultural case unless the fingerprint matrix proves equivalent coverage elsewhere.

Wave 3 exit gate:

- all selected counties pass the Franklin terminal-state and immutable-binding rules
- the contract requires no county-specific schema fork
- every selected variation dimension is backed by fingerprint evidence
- reusable platform families cover at least 70 percent of successful acquisition endpoints, excluding deliberately unsupported sources
- every one-off adapter proposal identifies stable reusable semantics and a fixture
- deterministic replay succeeds for every promoted profile and assessment revision
- unexplained adapter truncation is zero
- duplicate logical source deployments are reconciled before statewide scheduling
- manual-review time and unresolved-route rates are measured per route and county
- all negative findings have a route-volatility reassessment date

** Wave 4: All 88 counties

Schedule counties in bounded batches of no more than eight active county runs. Batch ordering is a versioned run policy selected from geographic, population, risk, or detected-platform strategies. It must respect host, vendor, tenant, API-key, credential, and browser-pool leases.

Each county produces:

- identity and component assessment
- route-assessment revisions pinned to the applicability contract
- verified source-profile revisions
- unverified candidates
- negative findings and completed search plans
- gaps, blockers, reassessment dates, and review state
- minimal historical identity

A county cannot be marked complete while any required subfamily is unassessed, candidate-only, ambiguous, missing applicability evidence, or bound only to mutable logical profile IDs.

** Wave 5: Historical acquisition and change reconciliation

After current profiles are reviewed:

- expand archive and historical-export inventories
- reconcile predecessor and successor relationships captured in earlier waves
- establish refresh and retirement schedules
- define source replacement and tombstone rules
- reconcile state-level datasets, prior captures, and current profiles
- acquire historical content only within declared policy bounds

Wave 5 expands history; it does not introduce historical identity for the first time.

* REVIEW County Court Scope

County coverage includes county courts, clerks, and publicly exposed local-court systems that serve the county or are linked from an authoritative county or state directory.

Each court is modeled as a component or linked government unit with its own profile revisions. A linked court subprogram may execute the work, but the county courts route cannot be marked complete until the linked assessment revisions are reviewed and bound into the county route decision. Absence of a unified statewide local-case API does not make the route not applicable.

* REVIEW Negative-Finding Freshness

Every negative terminal result sets =reassess-after= from the assessment date unless a stronger source-specific policy applies:

| Volatility class | Default maximum age | Typical routes |
|------------------+---------------------+----------------|
| high | 30 days | feeds, meetings, procurement, permits, operational metadata |
| medium | 90 days | open data, finance, elections, public safety, public records |
| low | 180 days | identity, GIS, property, courts, archives |
| legal-versioned | next effective date or 180 days, whichever comes first | law and legal policy |

A stale negative finding cannot satisfy a pilot or county completion gate. Reassessment creates a new append-only assessment revision; it does not mutate the old result.

* REVIEW Acceptance Criteria

Ohio design acceptance requires:

1. all 88 county GEOIDs are in scope
2. every route uses a versioned subfamily and applicability contract
3. route decisions pin immutable profile, search-plan, evidence, and gap revisions
4. state-system candidates are separated from verified profiles
5. no permanent actor is created per county
6. Franklin passes the strengthened terminal-state and replay gate
7. the diverse-county set is selected from fingerprint evidence and includes required organizational variation
8. historical identity is captured in every wave
9. Checkbook participation is not treated as county finance completeness
10. county court coverage is linked into the county route decision
11. negative findings use route-volatility reassessment defaults
12. rate, replay, cancellation, and checkpoint behavior follows =STAR-RESEARCH-PIPELINE-003=
13. source profiles use =STAR-GOVDATA-DESIGN-002=
14. adapters use =STAR-GOVDATA-DESIGN-003=
15. production implementation remains blocked until parent designs are approved

* REVIEW Deterministic Fixtures

Required fixtures include:

- state portal redirecting to a delegated subdomain
- one official domain serving multiple agencies
- one county department using a vendor domain
- one shared or regional service provider
- county function that is legitimately not applicable with authority evidence
- stale negative finding that must be reassessed
- OGRIP directory with multi-gigabyte files
- ArcGIS viewer with discoverable REST service
- current, prior, and future-effective legislation
- public procurement search with login-only supplier actions
- court form with no unified local-case API
- campaign-finance search and file-transfer export
- source migration with predecessor, successor, and archive evidence
- partial current-year statistics
- replay of a county gate decision after a later profile revision

* REVIEW Failure and Recovery

- one county failure cannot stop another county
- timeouts create typed failures and checkpoints
- browser-required sources route only to declared browser workers
- oversized files are recorded without silent truncation
- profiles cannot be promoted without raw and authority evidence
- restarts replay from durable checkpoints without resetting route state
- migrations create successor relationships and tombstones
- stale negative findings reopen assessment without mutating prior revisions
- a changed source reopens review before it can satisfy a current gate

* REVIEW Open Decision

- statewide batch order after the pilots: geographic, population, risk, detected platform family, or a documented hybrid policy

This is an operational policy choice and does not alter completion semantics.
