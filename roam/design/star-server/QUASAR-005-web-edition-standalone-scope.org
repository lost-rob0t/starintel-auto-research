* Decision

=lost-rob0t/quasar-ui= is the browser-based Quasar[fn:quasar] implementation and standalone web edition.

It owns browser presentation, mobile behavior, renderer integration, offline/browser-local operation, and bounded browser workers. It may own browser-local state while disconnected or intentionally running in standalone mode.

It does *not* own the complete Quasar or StarIntel capability set. Persistent runtime supervision, privileged host integrations, backend ingest/storage/search/routing, distributed queues, and external tool services belong to their owning runtime/service repositories.

When a workspace or subject is connected to and migrated behind canonical =lost-rob0t/quasar= runtime commands, =quasar-ui= becomes a client and projection surface for those migrated operations. It must not silently become a competing durable writer.

* Capability Stack

#+begin_src text
quasar-ui
  browser UI / graph renderer / standalone subset
        |
        | typed commands, projections, capability discovery
        v
quasar
  canonical Common Lisp control plane/runtime
        |
        | StarIntel service APIs and adapters
        v
starintel-server
  persistent ingest / storage / search / routing / RabbitMQ
        |
        +-----------------------------+
        |                             |
        v                             v
star-bbpd                       other actor services
  external recon actors          collectors / analyzers / tools
#+end_src

The layers are complementary rather than mutually exclusive.

- =quasar-ui= presents browser controls, documents, graphs, status, results, and errors.
- =quasar= owns canonical Common Lisp command/revision authority for migrated durable operations, persistent Sento supervision, privileged local integrations, reconnect/replay, and runtime capability discovery.
- =starintel-server= owns persistent backend responsibilities assigned to it, including document ingest, storage/query/search, RabbitMQ routing, and distributed service coordination.
- =star-bbpd= is a concrete external actor service that consumes RabbitMQ targets, runs Subfinder, Nmap, Httpx, Katana, and DNS workflows, and publishes derived StarIntel documents, relations, and actor events.

A browser control that invokes a service does not make that service a browser capability. The UI should discover service availability and expose only capabilities actually present in the connected deployment.

* Standalone Mode

Standalone browser mode must remain a first-class supported mode.

Acceptable standalone capabilities include:

- open and inspect local or imported StarIntel documents;
- edit graphs and documents through browser-local command handling;
- save and reopen browser-local workspaces;
- import and export supported formats;
- run browser-safe local actions and bounded workers;
- operate without a running Common Lisp[fn:common-lisp] process.

Standalone mode may use browser storage such as IndexedDB[fn:indexeddb] or PouchDB[fn:pouchdb] when the selected implementation requires it.

Standalone mode is a *bounded subset deployment*. It must not be documented as feature-equivalent to a connected Quasar + StarIntel deployment.

Capabilities requiring any of the following are outside the standalone-browser guarantee unless a separate browser-safe implementation is explicitly designed and validated:

- persistent service supervision;
- privileged host or native process access;
- server-side CouchDB/search infrastructure;
- RabbitMQ distributed routing;
- long-running collectors or analyzers;
- external native reconnaissance tools.

* Connected Mode

When connected to canonical =quasar= runtime services:

1. the browser may retain transient interaction state and caches;
2. high-frequency renderer movement may stay local until a commit boundary;
3. durable migrated mutations must be submitted through the canonical command contract;
4. command rejection or revision conflict must be surfaced rather than overwritten locally;
5. reconnect must reconcile browser projection state with canonical runtime state;
6. backend and external-service capabilities are discovered rather than assumed;
7. unavailable services disable only their dependent UI and do not break unrelated standalone features;
8. the browser must not silently substitute weaker JavaScript behavior for a missing privileged/runtime service.

* Service Boundary

Connected Quasar may expose =starintel-server=, BBPD, and other actor/service capabilities through typed adapters and capability discovery.

This does not require those services to run inside the =quasar= process. The runtime may coordinate them while preserving independent deployment, supervision, queue topology, credentials, logs, and failure semantics.

For BBPD specifically, the UI may expose:

- service availability/health;
- supported recon capability list;
- target submission;
- job/progress state;
- logs and errors;
- resulting StarIntel documents and graph projections.

The actual Subfinder/Nmap/Httpx/Katana/DNS execution remains in =star-bbpd=.

* Package Boundary

The browser core should remain independent of framework and transport details where practical.

Core graph/document operations should not require React[fn:react], Cytoscape[fn:cytoscape], a specific storage engine, or a specific network transport merely to represent valid commands and state transitions.

Renderer, storage, provider, runtime, and external-service integration layers remain adapters around the core contracts.

* Accepted Claims

- The web edition can run without the canonical runtime.
- Browser-local operation is useful and supported.
- Browser workers may implement bounded local actors or tools.
- Connected mode may use canonical runtime capabilities when present.
- StarIntel Server and external actor services may expand the connected capability set without moving their implementations into browser JavaScript.
- Quasar UI may present and control a service without owning that service implementation.

* Rejected Claims

- The browser permanently owns every durable operation after a workspace has migrated to canonical =quasar= authority.
- Common Lisp runtime integration is forbidden rather than optional.
- Browser-local caches overrule newer canonical runtime revisions.
- A renderer library is the canonical store.
- Standalone =quasar-ui= has feature parity with the full Quasar + StarIntel service deployment.
- BBPD/native recon tooling becomes a browser capability merely because the UI can submit a target or render its results.

* Acceptance Gates

| Gate | Required proof |
|------|----------------|
| Standalone open/edit/save | Open a fixture, edit it, reload the browser, and recover the same durable browser-local state. |
| Standalone import/export | Round-trip supported fixture data without semantic loss. |
| Connected mutation | Submit a migrated mutation through the canonical command channel and observe accepted/rejected result handling. |
| Reconnect | Reconnect after stale browser state and reconcile to the canonical revision without hidden overwrite. |
| Browser-only fallback | Canonical runtime unavailable; standalone mode remains usable rather than failing the entire application. |
| Capability discovery | Connected UI reflects which runtime/server/external-service capabilities are actually available. |
| Missing-service behavior | Removing StarIntel Server/BBPD access disables dependent controls without relabeling browser substitutes as equivalent services. |
| BBPD boundary | Target submission/result rendering can occur through the UI while native recon execution remains in =star-bbpd=. |

* Non-Goals

- Do not define the canonical runtime authority here; QUASAR-004 owns that decision.
- Do not define graph command schemas here; QUASAR-003 owns them.
- Do not define large-graph renderer tiers here; QUASAR-007 owns them.
- Do not define Auto-Dig fork rules here; QUASAR-006 owns them.
- Do not redefine StarIntel Server or BBPD internal service architecture here.
