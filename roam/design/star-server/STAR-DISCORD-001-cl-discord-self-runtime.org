* Decision

Implement =cl-discord-self= as a standalone Common Lisp library beneath =star-discord-watch=.

The first supported profile is a passive collection profile derived from the protocol kernel of =dolfies/discord.py-self=. It supports account-session startup, Gateway state, read-only HTTP collection, typed dispatch events, bounded history retrieval, attachments, checkpoints, and deterministic fixture replay.

The library does not contain StarIntel case policy, target authorization, RabbitMQ publication, CouchDB storage, or document normalization. Those remain in =star-discord-watch=.

The library does not attempt to provide stealth, fingerprint rotation, anti-abuse bypass automation, mass-account operation, unsolicited messaging, or a complete Python-compatible command framework. A transport profile is pinned, named, versioned, and auditable.

* Architectural Rule

The system has three separately testable layers:

1. =libcldiscordcurl=: a small C transport shim with a stable, poll-based ABI;
2. =cl-discord-self=: Common Lisp protocol, state, model, event, and compatibility systems;
3. =star-discord-watch=: supervised collection policy, journaling, normalization, attachments, and publication.

No actor calls raw libcurl functions. No C transport callback directly invokes arbitrary Lisp code from a foreign worker thread. No Discord protocol parser imports StarIntel document packages.

* Stable Native Transport ABI

The Common Lisp layer binds only to =libcldiscordcurl=. The shim binds to a pinned curl impersonation build and may adapt to native symbol or option changes without forcing protocol code changes.

** ABI version

#+begin_src c
#define CDC_ABI_VERSION 1u

uint32_t cdc_abi_version(void);
const char *cdc_runtime_version(void);
const char *cdc_native_curl_version(void);
#+end_src

Startup fails before any network operation when the reported ABI version does not equal the version expected by the Lisp package.

** Opaque handles

#+begin_src c
typedef struct cdc_runtime cdc_runtime;
typedef uint64_t cdc_request_id;
typedef uint64_t cdc_socket_id;
#+end_src

Lisp never receives a raw =CURL*=, =CURLM*=, socket descriptor, callback pointer, or native allocation address as an application-level identifier.

** Runtime lifecycle

  uint32_t max_websockets;

Creation validates the named transport profile. Unknown profiles fail closed. Runtime shutdown stops intake, cancels outstanding operations, emits terminal events, joins native threads, and then permits destruction.

** Poll-based event delivery

#+begin_src c
typedef enum {
  CDC_EVENT_NONE = 0,
  CDC_EVENT_HTTP_HEADERS,
  CDC_EVENT_HTTP_BODY,
  CDC_EVENT_HTTP_COMPLETE,
  CDC_EVENT_WS_OPEN,
  CDC_EVENT_WS_FRAME,
  CDC_EVENT_WS_CLOSED,
  CDC_EVENT_CANCELLED,
  CDC_EVENT_ERROR,
  CDC_EVENT_RUNTIME_STOPPED
} cdc_event_type;

typedef struct {
  cdc_event_type type;
  uint64_t operation_id;
  int32_t native_code;
  uint32_t flags;
  uint16_t close_code;
  const uint8_t *data;
  size_t data_len;
} cdc_event;

int cdc_poll(cdc_runtime *runtime,
             uint32_t timeout_ms,
             cdc_event **out_event);
void cdc_event_free(cdc_event *event);
#+end_src

The native runtime places events into a bounded queue. One Lisp transport-poller component calls =cdc_poll= and sends translated events to owning actors. This is selected over native-to-Lisp callbacks because it gives explicit memory ownership, backpressure, shutdown behavior, and thread control.

** Memory ownership

- Input pointers remain owned by the caller only for the duration of the submission call; the shim copies accepted input.
- Every returned =cdc_event*= is owned by the caller until =cdc_event_free=.
- Event payload pointers are valid only until their event is freed.
- No foreign pointer is stored in a StarIntel document, checkpoint, mailbox, or log.
- Large response bodies are emitted as bounded fragments rather than one unbounded allocation.

** Error contract

Every C function returns zero on accepted operation and a stable negative =CDC_ERR_*= code on immediate failure. Asynchronous transport failures arrive as =CDC_EVENT_ERROR= with both a stable shim code and the original native code.

Stable categories:

- invalid argument;
- ABI mismatch;
- profile unavailable;
- runtime stopping;
- queue full;
- operation not found;
- timeout;
- cancelled;
- DNS failure;
- TLS failure;
- certificate failure;
- proxy failure;
- HTTP protocol failure;
- WebSocket protocol failure;
- response limit exceeded;
- internal native failure.

Raw authorization headers, tokens, cookies, and message bodies are never included in native error strings.

* Transport Concurrency Model

=libcldiscordcurl= owns one native event-loop thread per runtime and one bounded command queue. It uses a curl multi interface or an equivalent pinned native mechanism internally.

The Common Lisp side owns one transport-poller managed component per native runtime. The poller is not the Discord account actor. It routes events by operation ID to account-session, HTTP, and Gateway owners.

Recommended initial limits:

| Resource                         | Default |
|----------------------------------+---------|
| Native runtimes per process      | 1       |
| Account sessions per runtime     | 8       |
| WebSockets per account           | 1       |
| Concurrent HTTP requests/account | 4       |
| Native event queue               | 4096    |
| Maximum Gateway frame            | 16 MiB  |
| Maximum HTTP body by default     | 32 MiB  |
| Poll interval when idle          | 250 ms  |

Limits are configuration defaults and must be overridable downward by an actor manifest.

The Sento or managed-component tree owns lifecycle above the library:

#+begin_example

        ├── scope-router
        ├── raw-event-journal

        ├── checkpoint-writer

Ownership rules:

- =account-session= owns the =cl-discord-self= session object.
- =gateway-heartbeat= never owns the socket; it sends scheduled commands to =account-session=.
- =rest-rate-limit-registry= owns server bucket state and request admission.
- =rest-worker-pool= owns bounded HTTP jobs but not account authorization.
- =state-projection= stores only bounded lookup state required by active scopes.
- target expiration stops subscriptions first; the account session remains only when another active target uses it.
- credential revocation stops the complete account subtree.

A checkpoint is valid only when account ID, client-context digest, Gateway profile, schema version, and expiration rules match the current session configuration.

* Heartbeat Actor Protocol

The heartbeat component uses messages rather than shared mutable timers:

#+begin_src lisp
(:gateway-hello :interval-ms 41250)
(:schedule-heartbeat :generation 4 :deadline 123456789)
(:send-heartbeat :generation 4 :sequence 99182)
(:heartbeat-sent :generation 4 :sent-at 123456790)
(:heartbeat-ack :generation 4 :received-at 123456811)
(:heartbeat-timeout :generation 4)
#+end_src

Generation numbers discard stale scheduled events after reconnect. The account session records send and acknowledgement timestamps and decides whether to reconnect.

* HTTP Rate-Limit Actors

The HTTP subsystem separates route identity, server bucket identity, and request execution.

#+begin_src lisp
(defstruct discord-route
  method
  template
  major-parameters
  route-key)

(defstruct discord-bucket-state
  bucket-id
  scope
  limit
  remaining
  reset-at
  updated-at)
#+end_src

Request path:

1. construct immutable route and request;
2. ask rate-limit registry for admission;
3. queue by known bucket or provisional route key;
4. submit through transport;
5. parse headers and remap route to server bucket;
6. complete, retry within policy, or return a typed condition;
7. release the next admitted request.

Cancellation removes queued requests and cancels submitted operations when their collection scope expires.

* Client Context

A client context is immutable and digest-addressed.

The context source may be a pinned fixture, a controlled metadata service response, or a locally derived profile. The source and digest are recorded in session telemetry and checkpoints.

Do not rotate contexts automatically. A context change is an explicit configuration revision that invalidates incompatible checkpoints.

* Model Generation

The Python type declarations are used as input material, not as the runtime dependency.

Create two tools:

1. =tools/export-discord-types.py=: read a pinned upstream checkout and emit a neutral JSON type inventory;
2. =tools/generate-discord-models.lisp=: generate immutable Lisp structures, slot presence masks, raw-extension maps, and parser tables.

Generated code is checked into the implementation repository. Generation is deterministic and records:

- upstream repository;
- upstream commit;
- generator version;
- source module paths;
- output digest.

Hand-written semantic parsers remain responsible for message references, partial updates, timestamp normalization, snowflakes, enums, unions, and event-specific context.

* Partial Updates

Discord update events frequently omit unchanged fields. A missing key is not the same as a JSON null value.

Every generated or hand-written update model must preserve three states:

- field absent;
- field present with null;
- field present with value.

Use explicit presence masks or a sentinel object. Do not collapse missing fields into =nil=.

* Raw Event Preservation

Every Gateway dispatch produces:

#+begin_src lisp
(defstruct discord-dispatch-event

  name

  session-id

The event ID is deterministic from account ID, session identity, sequence, event name, and raw digest. Replays preserve the same ID.

The library returns the event. =star-discord-watch= decides whether to journal it, reject it by scope, normalize it, or attach it to multiple datasets.

* Compatibility Oracle

Pin one =discord.py-self= commit as the behavioral oracle for the active compatibility profile.

** Oracle runner

The reference runner accepts raw fixture JSON and emits canonical JSON records containing only stable semantics:

- event name;
- snowflake identifiers;
- timestamps;
- content and revision metadata;
- guild, channel, thread, author, member, and reference IDs;
- attachment, embed, sticker, poll, mention, and reaction metadata;
- missing/null/value presence state;
- unknown input fields.

It must not emit Python repr strings, memory addresses, private cache state, or tokens.

** Differential test

#+begin_example
raw fixture
  -> pinned Python oracle -> canonical expected JSON
  -> Common Lisp parser  -> canonical actual JSON
  -> semantic diff
#+end_example

A changed upstream commit cannot become the compatibility baseline until all fixture differences are classified as accepted, rejected, or requiring implementation.

* Replay Transport

Implement a replay transport before live Discord integration.

The replay transport consumes an append-only transcript:

#+begin_src json
{"direction":"in","kind":"ws","at_ms":0,"flags":["text"],"payload_ref":"hello.json"}
{"direction":"out","kind":"ws","at_ms":12,"match_ref":"identify.match.json"}
{"direction":"in","kind":"ws","at_ms":20,"flags":["text"],"payload_ref":"ready.json"}
{"direction":"in","kind":"ws","at_ms":42000,"flags":["text"],"payload_ref":"heartbeat-ack.json"}

The harness can run in real time, accelerated time, and deterministic virtual time. It tests reconnect races, stale heartbeat messages, invalid sessions, close codes, fragmented frames, compressed payloads, and out-of-order cancellation.

* StarIntel Integration Contract

=star-discord-watch= receives =discord-dispatch-event= and produces a durable operation batch:

#+begin_src lisp
(defstruct discord-watch-operation-batch
  batch-id
  target-id
  dataset
  authorization-ref
  raw-event-id
  accepted-scope
  documents
  relations
  attachments
  checkpoint-candidate
  audit-records)
#+end_src

Processing order:

1. evaluate target and authorization scope;
2. journal accepted raw event;
3. normalize deterministic StarIntel documents;
4. stage attachment jobs;
5. persist operation batch;
6. publish with confirms and mandatory routing;
7. record publication result;
8. advance the StarIntel event cursor;
9. persist the Discord checkpoint candidate.

Gateway sequence advancement and durable StarIntel publication are related but distinct. Reconnect replay must be idempotent because Discord may resend events that were already journaled.

* Security and Secret Handling

- Tokens enter the actor through credential leases.
- Tokens are copied into the minimum required transport request and never returned in event data.
- Authorization headers are redacted before debug hooks.
- Core dumps are disabled for production collector services.
- Checkpoints contain no token, cookie, authorization header, or proxy password.
- Native allocations containing credentials are zeroed before release where the native API permits it.
- Structured logs use account and credential references, never raw secrets.
- Fixture capture tooling rejects headers containing authorization or cookies unless an explicit sealed-fixture mode is active.

* Implementation Phases

** Phase 0: Repository and contracts

- create repository and Nix flake;
- add upstream license and porting notice;
- define public packages and conditions;
- commit the C header before implementation;
- define event, transport, and fixture schemas;
- pin the upstream oracle revision.

Exit gate: ASDF loads, C header compiles, fixture schema validates, and no network code exists.

** Phase 1: Native transport fixture spike

- implement runtime lifecycle;
- implement bounded command and event queues;
- implement one HTTP GET against a local fixture server;
- implement WebSocket open, fragmented receive, send, close, and cancellation against a local fixture server;
- report native version and selected profile;
- verify clean shutdown under load.

Exit gate: 10,000 repeated fixture connections complete without leaked handles or foreign callbacks into Lisp.

** Phase 2: Protocol-neutral Lisp core

- FFI wrapper;
- managed transport poller;
- conditions;
- snowflakes;
- missing/null/value JSON representation;
- immutable dispatch event;
- virtual clock;
- replay transport.

Exit gate: deterministic replay works without Discord or Python.

** Phase 3: Gateway kernel

- HELLO;
- heartbeat scheduler;
- IDENTIFY and RESUME;
- READY and RESUMED;
- reconnect, invalid session, and close classification;
- sequence checkpoints;
- compressed and fragmented frames.

Exit gate: all Gateway state-machine transcripts pass under accelerated and virtual time.

** Phase 4: HTTP and rate limits

- immutable routes;
- request headers and client context;
- global and bucket limits;
- bounded retries;
- cancellation;
- history, message, and attachment endpoints required by Profile A.

Exit gate: deterministic fixture server tests cover bucket remapping, 429 handling, global limits, cancellation, and response limits.

** Phase 5: Event models and oracle

- generated type inventory;
- hand-written message, user, member, channel, thread, reaction, and attachment semantics;
- Python oracle export;
- semantic differential tests.

Exit gate: every supported Profile A fixture has zero unexplained semantic differences.

** Phase 6: Discord Watch integration

- account-session actor;
- scope router;
- raw journal;
- deterministic StarIntel normalization;
- attachment supervisor;
- reliable publisher;
- checkpoint coordination.

Exit gate: one authorized bounded session survives reconnect, replays duplicate events without duplicate documents, and drains cleanly on target expiration.

** Phase 7: Upstream drift automation

- watch selected upstream modules;
- produce a review queue for changed protocol behavior;
- run oracle tests against candidate revisions;
- update compatibility manifest only after review.

Exit gate: an upstream change produces a bounded actionable report instead of silently changing runtime behavior.

* Acceptance Tests

1. Production =cl-discord-self= loads without Python.
2. ABI mismatch stops startup before any request.
3. No native worker thread invokes Lisp callbacks.
4. Every foreign allocation has one documented owner and release path.
5. Queue saturation returns structured overload instead of dropping events.
6. WebSocket frame fragmentation reconstructs exact raw payloads.
7. Gateway compressed streams survive arbitrary native fragment boundaries.
8. Stale heartbeat generations cannot terminate a new connection.
9. Resume uses only checkpoints matching account and client-context digests.
10. Invalid sessions clear only fields required for re-identification.
11. Terminal close codes do not enter infinite restart loops.
12. HTTP route-to-bucket remapping is deterministic.
13. Global and route limits block admission without blocking unrelated actors.
14. Target expiration cancels queued and active bounded HTTP work.
15. Missing JSON fields remain distinguishable from explicit null values.
16. Unknown fields survive parsing and replay.
17. Raw dispatch digests are stable across replay.
18. Python-oracle records contain no tokens or cookies.
19. Supported fixtures have zero unexplained semantic differences.
20. Duplicate Gateway events produce identical StarIntel identifiers.
21. Publisher failure does not advance the durable StarIntel cursor.
22. Credential revocation stops the complete account subtree.
23. Shutdown drains or cancels all native operations before unloading the library.
24. Nix checks reproduce the same generated model and fixture digests.
25. Logs and conditions contain references, not raw credentials.

* Explicit Non-Goals

- automatic transport-profile rotation;
- CAPTCHA handling;
- anti-abuse challenge solving;
- unsolicited messaging;
- mass-account orchestration;
- voice transport;
- Discord command-framework compatibility;
- complete parity with every =discord.py-self= model;
- direct StarIntel mutation from the transport library;
- treating a successful socket write as durable StarIntel publication.
