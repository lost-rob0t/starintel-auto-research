* Independent Proposal Review

Independent review: revise the assurance claims, retain the proposed testing architecture.

The SWI-Prolog oracle/runner, canonical StarLang contracts, real-process adapters, persistent-state observation, fuzzing and replay are useful conformance infrastructure. They do not establish that arbitrary application implementations satisfy the contracts for all executions. Preserve the prior synthetic/conformance research as a complementary evidence layer.

** 1. Minimum credible formal assurance

Adopt a small explicit transition-system specification separately from the executable oracle:

- Abstract state, initial states, legal transitions, environmental assumptions and observable outputs
- Safety invariants and separately stated progress properties
- A lower-level staged-import/recovery model with a documented abstraction/refinement mapping
- Exhaustive finite-model checking initially; a parameterized inductive proof only when needed
- An explicit distinction between model-to-model refinement and evidence connecting actual code to the lower-level model

A minimal safety refinement obligation is: concrete initialization maps to abstract initialization, and every concrete transition maps to an allowed abstract transition or stuttering, under an inductive invariant. A corresponding theorem about two models still does not automatically prove the application implements either model. Lamport gives the initialization/step proof obligations and treatment of refinement mappings in [[https://lamport.org/tla/proving-safety.pdf][Proving Safety Properties, Part II]].

** 2. Practical first model: staged import/migration

This is a proposed design target, not a claim about StarIntel’s current implementation.

Use a finite domain containing several record IDs, two schema versions, overlapping batches and repeated operation IDs. Model these state components:

- Original durable generation, staged generation and active-generation pointer
- Batch identity plus content identity
- Validation outcome and migration version
- Durable commit/replay metadata
- Volatile processing state, crash and restart
- Reader observations, if reads can overlap migration

Candidate transitions: stage, validate, prepare publication, publish, acknowledge, crash, recover and replay. Split transitions at actual persistence boundaries. Do not make several disk writes atomic merely because they belong to one application operation.

Recommended properties:

- No unapproved loss: old records remain available, or have an explicitly authorized migration/replacement outcome.
- Semantic preservation: define which fields/relationships must survive migration; schema validity and matching counts are insufficient.
- Publication integrity: only fully validated generations become active.
- No mixed-generation reads, if atomic publication is the intended contract.
- Durable success: an acknowledged commit remains committed after a modeled crash.
- Replay idempotence: replaying the same operation/content has the same semantic effect as executing it once.
- Identity collision handling: reusing an operation ID with different content cannot silently produce a successful replay.
- Failure isolation: invalid batches cannot alter active data.
- Recoverability: an interrupted operation resolves consistently to committed, resumable or rejected state.

A particularly valuable counterexample target is a crash between publication and durable replay bookkeeping. It can reveal duplicate effects on retry. Another is acknowledgement before publication is durably recoverable.

Define idempotence at the semantic level: harmless retry logs or attempt counters need not remain byte-identical.

** 3. Safety, liveness and assumptions

Check safety even while crashes and delays occur. Require eventual completion only under explicit environmental assumptions, such as eventual storage availability, an eventual crash-free interval and fair execution of enabled recovery work. “Every accepted import eventually commits or rejects” is a useful progress property.

A timeout in an application test establishes only a bounded response requirement for that run. It cannot prove eventual response over arbitrary executions. Avoid adding fairness to failure-producing actions accidentally. Lamport’s [[https://lamport.azurewebsites.net/tla/tutorial/session11-2.html][liveness tutorial]] explains why fairness belongs on relevant progress actions and why loss actions should not automatically be fair. P’s [[https://p-org.github.io/P/advanced/importanceliveness/][liveness guidance]] also explains the vacuity risk: a system that serves nothing can satisfy many safety properties.

Assumptions that must be explicit: storage durability/atomicity, whether power loss differs from process kill, single versus concurrent writers, reader consistency, canonicalization semantics, allowed lossy migrations, retry identity lifetime, and observability completeness.

** 4. Tool recommendation

- First choice: TLA+ with TLC for the small crash/recovery and publication model. TLC supports finite-system model checking; report the actual model constants, configuration and completed exploration. [[https://docs.tlapl.us/using%3Atlc%3Astart][TLC documentation]]
- Add Apalache when symbolic state exploration or inductiveness checking is advantageous. Its default checking is bounded and explicitly incomplete beyond the selected depth; distinguish this from an inductiveness result. [[https://apalache-mc.org/docs/apalache/running.html][Running Apalache]], [[https://apalache-mc.org/][supported approaches]]
- ProB is credible for B/Event-B, relation-heavy specifications and refinement workflows. Its handbook explicitly notes that its refinement checker does not check the gluing invariant, so do not treat that result alone as a complete refinement proof. [[https://prob.hhu.de/][ProB]], [[https://prob.hhu.de/w/index.php?title=Full_Handbook][handbook]]
- P fits event-driven protocol models and monitors. Ordinary checker execution is schedule exploration; the documented default is one schedule. Record schedule strategy, count and seed. [[https://p-org.github.io/P/getstarted/usingP/][P checker]], [[https://p-org.github.io/P/manual/monitors/][monitors]]
- SPIN is credible for bounded concurrent protocol models and temporal properties. Exhaustive and bitstate modes must receive different assurance labels; bitstate can miss errors. [[https://spinroot.com/spin/Man/4_SpinVerification.html][SPIN verification]], [[https://spinroot.com/spin/Man/Quick.html][bitstate limitations]]

Do not initially adopt all five tools. TLA+/TLC plus the proposed Prolog runner is the smallest coherent starting point.

** 5. Implementation evidence and gates

Adapters must record actual requests, responses, fault boundaries and independently observed persisted state. Application-emitted “committed” events are insufficient evidence of durability. Missing observations, adapter failure and unsupported operations must produce incomplete/unsupported outcomes, never pass.

For concurrent operations, specify allowed ordering or linearization points; comparing only final snapshots can miss illegal intermediate behavior. Version and test the StarLang-to-model and StarLang-to-oracle translations. Shared canonical contracts reduce drift but can also reproduce the same specification error in both implementations.

Pass the research gate when:
- Scope, assumptions, invariants, progress properties and abstraction mapping are reviewable
- The first model and its required evidence are specified
- Every assurance label states its bounds and trusted components
- Prior conformance research remains intact

Revise/block implementation claims if:
- A passing fuzz run is called proof
- Model checking is described as verifying arbitrary adapters/apps
- Crash semantics or commit boundaries remain undefined
- Finite bounded exploration is presented as unbounded assurance
- Canonical syntax is mistaken for formal semantics

** 2. Reviewable transition model

Scope: one Quasar plane, one Tek9 environment, serial command handling, one initial workspace, explicit IDs and canonical fixtures. Black-box and optionally instrumented test, not whole-program proof. Include one unrelated canonical mutation for revision conflict. Exclude arbitrary postcommit deletion or qualify persistence by later mutations. Retain synthetic/schema-conformance research separately.

Durable variables: C finite ID→payload map; R revision; N canonical count; G default-graph metadata presence; S session map, absent or state OPEN/FAILED/COMMITTED, baseRevision, staged final payload per ID, acceptedThrough, chunks sequence→digest/operationCount/byteCount, operationCount, byteCount, lastActivity, optional committedRevision/operationId; active session or none; J compact journal by commit identity; D aggregate durable tuple.

Volatile/observer variables: alive, epoch; pending request/proposed result; txn none or private tentative state; pc processing location including hooks and postcommit/pre-response; sentReplies versus receivedReplies; eventsEmitted versus eventsReceived; controller-retained history surviving app restart; outcomeKnowledge unknown/committed/aborted-or-rejected. Timeout remains unknown. txn.state COMMITTING may coexist with durable OPEN, never stable crash-recovered COMMITTING under model.

Initial states: fresh C empty/R0/no stages/journal/active, or one seeded doc/R1/matching metadata/count/no stages. App running, no txn/pending, empty observer history. Storage schema record from opening store outside abstraction.

Actions:
1 Begin(s): fresh ID, baseline=R, no active OPEN/COMMITTING. Atomic OPEN metadata/empty stage/chunks/acceptedThrough=-1/zero counts/base=R/active=s. Reply after commit. Busy/conflict otherwise. TTL cleanup separate.
2 AcceptChunk(s,q,ops): OPEN, bounds/validation hold, q=acceptedThrough+1. Ordered create/update against staged overlay over C. Atomic overlay/digest/counters/activity. C,R,N,J unchanged. Any failure discards whole tentative txn.
3 ReplayChunk: OPEN, q≤acceptedThrough, matching stored digest. No durable change; current cumulative count/acceptedThrough, replayed=true. Mismatch/gap reject. Digest equality is implementation behavior; identical-content claim needs no-collision assumption.
4 StartPromotion: OPEN and baseline=R, establish tentative state, step through hooks, D unchanged.
5 CommitPromotion: one outer-completion linearization: C overridden by staged; R+1; N+new IDs; ensure G; one journal; COMMITTED receipt/original operation ID/revision/count; delete stage/chunks; clear matching pointer. Later event/reply cannot undo.
6 PromotionConflict: OPEN/base≠R. Atomic FAILED/conflict code/activity/pointer clear; canonical unchanged. Optional separate CleanupFailed abort. Return workspace.revision-conflict, no import event.
7 ReplayCommit: COMMITTED. Stored original revision/op ID/count, replayed=true. No canonical/revision/journal/event changes. Works across restart while receipt retained.
8 Abort: COMMITTED rejects import.invalid-session. Otherwise atomically delete stage/chunks/meta/matching pointer. Absent succeeds aborted=true. Canonical/revision/journal unchanged. Source https://github.com/lost-rob0t/quasar/blob/9079604f766990db7f9b8998705862c4fa914c45/control-plane/src/phase2-stage-cleanup.lisp#L3-L36
9 ExternalMutation: permitted canonical write increments R; keep ID separate from imported IDs for simple durability assertions.
10 EmitImported/SendReply/ReceiveReply/DropMessage: explicit postcommit steps. Observer history external. Initial commit may emit; replay suppresses. Emitted≠received.
11 Crash: discard txn,pending,queue/cache,connection,volatile events; retain D/history. Unknown timing relative to LMDB completion permits precommit or postcommit outcome, never partial tuple.
12 Restart: reopen same path in new process/epoch; rebuild volatile from D. No implicit promotion, loss of accepted chunks or guaranteed event replay. OPEN stages and COMMITTED receipts survive.
13 Optional Expire: active OPEN only, now-lastActivity strictly greater than TTL, abort. Initial model freezes time below TTL; later fresh/expired finite clock. Crash alone never expires stage.


** 3. Properties

Safety invariants:
1 Precommit invisibility: acceptance/replay/in-flight promotion do not change canonical records/revision. For updates old payload remains; creates exact document.not-found. Durable staged rows allowed.
2 Atomic promotion: overlay, revision increment, count, journal, receipt, active removal, stage cleanup together at durable boundary.
3 Abort isolation: successful abort leaves canonical/revision unchanged by session; no import journal; later commit rejects. Never reverses committed import.
4 Acknowledged commit durability: every controller-received successful commit response matches durable receipt session/revision/op ID; restart retains affected payloads absent later modifying operations.
5 Replay idempotence: commit replay changes neither revision, journal cardinality nor payload, returns original identity. Chunk replay while OPEN changes neither overlay nor counters.
6 Failure atomicity: pre-outer-commit injected failures retain preceding D; transient promotion fault leaves OPEN retryable.
7 No phantom recovery: restart exposes neither transaction-private COMMITTING nor partial promotion.
8 Conflict safety: no canonical overwrite/import event; FAILED cleanup separate and possibly incomplete.
9 Count correctness: canonical count=distinct canonical IDs; session/result count=accepted operations. Not generally equal.

Liveness assumptions: finitely many crashes then working storage/actor scheduling, sufficient space and eventual retry processing; valid OPEN neither aborted/expired/conflicted can eventually promote; committed session can eventually yield replay response under retry and fair delivery. Events not guaranteed: crash after commit before emission permanently loses documents.imported because replay suppresses. Do not make Crash fair or claim every submitted request gets response without retry/transport assumptions.

Finite bounds: 1 workspace; 2 session IDs without reuse; 2 doc IDs with 2 payload versions; ≤2 chunks/session, ≤2 ops/chunk; finite digest identities plus optional collision class; revisions 0–3 with guarded increments; ≤1 unrelated mutation and 1 crash/restart per bounded scenario; operation-bounded counters; bytes abstracted withinLimit/tooLarge. Separate 2-workspace scenario for isolation. Temporal liveness needs finite crash-budget or eventually-stable assumption, not finite trace-length claim. Bounds test ordering/replay, not arbitrary-volume correctness.

** 6. Deliberately faulty variant

AckBeforeCommit emits observable successful commit response after tentative promotion prepared but before outer commit.
Expected trace:
1 canonical empty/R0.
2 begin s, durable OPEN.
3 accept chunk0 with d, durable staged d/canonical absent.
4 start promotion, tentative canonical d/revision1.
5 faulty success received, session s/revision1/op o.
6 crash before transaction completion.
7 restart durable OPEN, canonical d absent/R0/no import journal.
8 get(d) returns document.not-found.
Violates acknowledged-commit durability. With internal invariant fails at step5; black-box decisive at step8. Later successful replay must not erase counterexample. Expected counterexample only, model checker NOT executed.

* Footnotes and Glossary

- StarTest: proposed application-validation framework in =lost-rob0t/star-test=; no implementation is asserted.
- Star Language (StarLang): canonical StarIntel contract and language project; schema authority is not replaced by this research.
- SWI-Prolog: Prolog implementation proposed for an executable semantic oracle.
- TLA+: Temporal Logic of Actions specification language. TLC is its finite-state model checker.
- Refinement: a justified mapping relating lower-level transitions to permitted abstract transitions or stuttering.
- Stuttering: an implementation step that leaves the modeled abstract state unchanged.
- Safety: a property excluding a forbidden state or behavior. Liveness: progress under explicitly stated environmental and fairness assumptions.
- MQI: SWI-Prolog Machine Query Interface. Current StarLang transport support does not imply query-operation implementation.
- SBCL: Steel Bank Common Lisp. ASDF: Another System Definition Facility, the Lisp build/system loader.
- LMDB: Lightning Memory-Mapped Database. Tek9 is the reviewed storage wrapper; process-kill evidence is not power-loss proof.
- CI: continuous integration. SHA: Secure Hash Algorithm digest used here to identify exact source revisions or artifacts.
- Nix closure: the explicitly resolved transitive runtime/build dependencies. Docker is the proposed container packaging/runtime route.
- FNV-1a: non-cryptographic hash used by the reviewed chunk-replay implementation; equal hash is not unconditional content identity.
- TTL: time to live. JSON: JavaScript Object Notation. DAG: directed acyclic graph.
- LTL: linear temporal logic. CLPFD: constraint logic programming over finite domains.
- Inconclusive: available evidence, bounds, or resources do not justify a passing or failing property verdict.
