* Authority

This node records the explicit operator reversal on 2026-09-21.

The earlier 2026-09-20 version of STAR-LANG-014 incorrectly framed Kotlin/JVM as
a single replacement runtime and Common Lisp as temporary migration debt. That
direction is superseded.

The approved direction is now **polyglot**:

- Common Lisp remains a permanent first-class StarLang compiler and runtime.
- Kotlin/JVM is added as a peer runtime backend.
- Portable generated/boundary targets remain supported across Common Lisp,
  Python, TypeScript, Nim, Java, Kotlin, Go, Rust, Emacs Lisp, and Prolog.
- Language-neutral StarLang specifications, normalized IR, wire contracts,
  canonical fixtures, and conformance tests own semantics across implementations.

This reversal does not reopen the closed-source parser safety model and does not
authorize raw host-language evaluation.

* Decision

1. Common Lisp remains a permanent supported implementation for the closed
   parser, macro expander, validator, normalized IR producer, compiler, and actor
   runtime.
2. Kotlin/JVM is an additive peer runtime target, not the canonical replacement
   for Common Lisp.
3. The compiler retains deterministic IR->Kotlin generation.
4. Runtime behavior may be implemented in multiple conforming backends.
5. Reaching parity in Kotlin does not authorize deletion, demotion, or
   fallback-only treatment of the Common Lisp runtime.
6. A supported backend may be removed or demoted only by a new explicit
   operator-approved decision.
7. Public Kotlin runtime APIs MUST remain Java-friendly.
8. Nim MAY implement isolated native/edge adapters behind versioned StarLang
   wire/effect contracts.
9. C remains thin FFI glue unless separately approved.
10. Generated bindings and external adapters are not automatically full native
    runtimes; the language matrix must distinguish those capabilities clearly.

* Runtime Ownership Model

#+begin_src text
.star source
  -> closed Common Lisp front end
  -> normalized runtime-neutral IR
       +-> Common Lisp runtime
       |    +-> mailbox/lifecycle/supervision/journal/leases/capabilities
       |
       +-> Kotlin backend
            -> Kotlin source / JVM bytecode
            -> Kotlin/JVM peer runtime
                 +-> same portable semantics
                 +-> Java-compatible public API

Portable boundaries / generated bindings:
  Common Lisp | Python | TypeScript | Nim | Java | Kotlin | Go | Rust | Emacs Lisp | Prolog
#+end_src

No runtime language owns the semantic contract by itself. The specification,
normalized IR, portable protocol, canonical fixtures, and conformance suite are
the cross-language authority.

* Language Selection

| Layer | Common Lisp | Kotlin/JVM | Other languages |
|-------+-------------+------------+-----------------|
| Parser / source spans / macro expansion | Permanent first-class owner | Consume normalized output | No alternate parser without separate approval |
| Normalized IR / canonical manifests | Permanent compiler implementation | Consume shared contracts | Consume shared contracts |
| Executable code generation | Native CL path + Kotlin generator | Generated Kotlin | Portable binding generators as supported |
| Runtime actor semantics | Permanent supported backend | Peer supported backend | Future conforming runtimes may be added |
| JVM consumer ABI | N/A | Kotlin with Java-compatible API | Java consumer surface |
| Android runtime | May interoperate remotely/through protocol | Kotlin/JVM peer backend | Boundary clients/adapters |
| Native/edge effects | Supported through ports | Supported through ports | Nim when justified |
| Native library glue | Through FFI where needed | Through JVM/native boundary | C only when unavoidable |

* Conformance Rule

Every runtime implementation must execute the same shared fixtures against the
real runtime boundary.

For every Kotlin parity slice:

1. freeze behavior as portable fixtures and canonical traces;
2. execute the fixture against the real Common Lisp implementation;
3. execute the fixture against the real Kotlin/JVM implementation;
4. compare normalized outputs, lifecycle trace, errors, generations,
   replay/idempotency state, and externally visible ordering;
5. keep both implementations green after parity;
6. add new semantic behavior to the language-neutral contract and then implement
   it in supported runtimes rather than silently privileging one backend.

Parity is not a cutover trigger.

* Required Kotlin Parity Order

1. portable value model and actor/reference types;
2. bounded FIFO mailbox;
3. runtime registry, generations, start/stop/restart/shutdown;
4. deterministic tell/ask/dispatch loop;
5. runtime directory and star:// resolution;
6. lifecycle wire dispatcher, cancellation, deadlines, idempotency, retry/deferred settlement;
7. supervisor/restart policies;
8. journal/replay;
9. leases and capability enforcement;
10. artifact and verification contracts;
11. adapter SDK and HTTP/process ports;
12. durable/distributed transport integration;
13. CLI/backend selection and packaging;
14. prototype compatibility retirement where unrelated to permanent Common Lisp runtime support.

* Transpiler Contract

The Kotlin backend MUST:

- consume normalized runtime-neutral IR, never raw .star source;
- emit deterministic source for identical normalized IR;
- preserve source identifiers and manifest lowerCamelCase field spelling;
- avoid host-language eval or arbitrary Kotlin escape hatches;
- generate explicit actor definitions, contracts, effect requirements, and runtime registration;
- keep external effects behind typed ports;
- produce source maps/provenance back to StarLang source spans where available;
- support canonical formatting so generated-source hashes are stable.

* Shared Runtime Contract

Every full runtime backend MUST preserve:

- bounded mailboxes and explicit full/closed delivery outcomes;
- per-runtime ownership with no process-global actor registry;
- generation-fenced actor references and stale-reference rejection;
- deterministic single-message actor transition semantics;
- transition-time state isolation before commit;
- typed contract validation;
- lifecycle/idempotency/correlation/causation/attempt/deadline semantics;
- cooperative cancellation and deterministic terminal replay;
- bounded supervision and restart accounting;
- durable journal/replay and lease fencing;
- capabilities and effect-port isolation.

Concurrency is an implementation detail and MUST NOT change externally visible
semantic ordering.

* Java ABI

Kotlin public types must remain straightforward for Java callers:

- avoid Kotlin-only public type tricks at the boundary;
- expose stable constructors/factories and immutable DTO-style protocol values;
- use explicit nullable contracts;
- provide Java-callable static/factory entry points where useful;
- maintain binary-compatibility checks once the API is released.

* Nim / C Boundary

Nim is preferred over handwritten C for standalone native helpers when a JVM is
unavailable or materially inappropriate.

Allowed examples include OS/device integration, native codecs/packet adapters,
and constrained edge workers.

C is allowed only for thin ABI/FFI integration unless a separate explicit
operator decision expands its role.

* Acceptance Gates

- Common Lisp runtime/compiler tests remain mandatory and green.
- Kotlin runtime tests execute the real Kotlin runtime.
- Shared fixtures prove Common Lisp/Kotlin parity for each implemented slice.
- Generated Kotlin is deterministic after canonical formatting.
- JVM tests include Kotlin and Java consumer compilation.
- Android-compatible tests cover the portable runtime subset where applicable.
- No Kotlin runtime slice depends on prototype/.
- CI rejects documentation or agent contracts that mark Common Lisp as
  temporary, fallback-only, retired, or scheduled for deletion.
- Portable generated/boundary targets remain enumerated and tested according to
  their supported capability tier.
- Native adapters cannot mutate runtime-owned state except through typed
  messages/effect responses.

* Toolchain Baseline

Implementation currently targets Kotlin 2.4.20 and Gradle 9.7.1. Exact versions
are implementation pins rather than language semantics and may be upgraded with
CI proof.

* Relationship to STAR-LANG-001

STAR-LANG-001 remains authoritative for the closed parser, declarative source
model, safety boundaries, normalized IR discipline, and deterministic semantics.

Its old "Common Lisp is the sole runtime implementation language" restriction is
superseded only to permit additional conforming runtimes. It is **not**
superseded in a way that removes Common Lisp.
