* Source Model: Where Concurrency Actually Exists

** Shared dispatcher

=disp:make-dispatcher= constructs a =shared-dispatcher=. The dispatcher owns a Sento router. During initialization it creates exactly =:workers= dispatcher-worker actors and adds them as routees.

Crucially, every dispatcher worker is created with:

#+begin_src lisp
:dispatcher :pinned
#+end_src

Each worker therefore owns a =message-box/bt= and one Bordeaux thread.

For concurrency accounting purposes:

#+begin_example
shared dispatcher with N workers = N execution lanes
#+end_example

The router is selection machinery around those already-created lanes; it is not another lane.

** Dispatcher-backed ordinary actor

An ordinary actor selecting =:shared= or another named shared dispatcher receives a =message-box/dp=.

The =message-box/dp= documentation explicitly states that it does not own a thread. It queues the actor's messages and submits execution functions to the selected dispatcher. A mailbox-local lock keeps one actor's state from being mutated concurrently by multiple dispatcher workers.

For concurrency accounting:

#+begin_example
actor using message-box/dp = 0 additional execution lanes
#+end_example

Thousands of dispatcher-backed actors may therefore share a bounded worker set without multiplying threads.

** Pinned ordinary actor

=:pinned= is handled specially by =%message-box-for-dispatcher-id= before named-dispatcher lookup. It creates a =message-box/bt= directly.

=message-box/bt= starts one thread during initialization and its own documentation states that each such actor requires exactly one thread.

For concurrency accounting:

#+begin_example
ordinary actor using :pinned = 1 execution lane
#+end_example

This also proves that registering a custom shared dispatcher whose ID is =:pinned= cannot provide the intended shared pool to actors selecting =:pinned=. That identifier is reserved by behavior, not merely convention.

** Router

The router contains a routee vector and a strategy function. Existing strategies are:

- =:random=;
- =:round-robin=;
- a custom function receiving routee count and returning a routee index.

=tell=, =ask-s=, and =ask= select a routee and forward the operation.

For concurrency accounting:

#+begin_example
router object = 0 execution lanes
add-routee = 0 execution lanes by itself
#+end_example

A routee may independently own a lane because it is pinned, or may own zero because it is dispatcher-backed. The router must not double-charge that existing ownership.

* Why Current Configuration Multiplies Concurrency

Sento's actor-system config gives every named dispatcher an independent =:workers= value. The default =:shared= dispatcher alone defaults to four workers. Adding another dispatcher with four workers produces another four pinned dispatcher-worker threads.

Nothing at the pinned revision sums these worker counts against a total actor-system or process grant.

The multiplication is therefore not a router defect and not a reason to replace dispatcher semantics. It is an absent aggregate-capacity invariant.

* Correct Accounting Unit

Use one unit: *Sento execution lane*.

One lane is a long-lived Sento-owned actor execution thread capable of independently processing actor work.

| Sento object/path | Lane cost | Reason |
|-------------------+-----------+--------|
| shared dispatcher worker | 1 | worker is a pinned actor with =message-box/bt= |
| shared dispatcher with N workers | N | exactly N pinned worker actors |
| ordinary =:pinned= actor | 1 | owns one =message-box/bt= thread |
| ordinary actor on named dispatcher | 0 | =message-box/dp= owns no thread |
| router | 0 | selection/forwarding only |
| adding an existing actor as routee | 0 | capacity belongs to routee/mailbox, not router membership |

This accounting intentionally does not claim to count every process thread. HTTP, Rabbit consumers, timers, lparallel, remoting, and other runtime threads remain under the broader process-wide #176/#177 authority. This slice accounts the Sento actor-execution contribution to that authority.

* One Authority, Two Views

The process-wide StarIntel ceiling remains the existing canonical globals from #177. Sento must not introduce a competing user-facing maximum.

The process planner grants Sento some number of execution lanes after accounting for non-Sento process demands and reserved control capacity.

Conceptually:

#+begin_example
StarIntel process budget
        |
        +-- non-Sento allocations
        |
        +-- Sento execution-lane grant = G
                 |
                 +-- total used
                 +-- total free
                 +-- owner -> lane-count registry
#+end_example

Sento may expose its own read-only accounting view, but =G= is a grant from the existing process authority, not a new independent sizing knob.

* Preserve Existing Sento Logic

The corrected design MUST preserve these semantics unless separately approved:

1. named shared dispatchers still have local =:workers= counts;
2. shared dispatchers still use their existing router;
3. =:random= remains =:random=;
4. =:round-robin= remains =:round-robin=;
5. custom count-to-index strategy remains supported;
6. dispatcher-backed actors still use =message-box/dp=;
7. pinned actors still use =message-box/bt=;
8. mailbox serialization behavior remains unchanged;
9. router membership does not become execution-capacity ownership;
10. existing dispatcher/router tests must remain valid without semantic rewrites.

The new invariant is simply:

#+begin_example
sum(all live Sento execution-lane ownership) <= granted Sento concurrency
#+end_example

* Reservation and Release Semantics

** Startup dispatchers

Before the actor system starts its configured shared-dispatcher workers, sum the configured worker demand and prove it fits the granted Sento concurrency.

Example:

#+begin_example
:shared workers = 4
:storage workers = 4
Sento grant = 6
=> reject before creating the first dispatcher worker thread
#+end_example

This preserves the existing local dispatcher sizes while preventing their aggregate from exceeding the total.

** Dynamic shared dispatcher

=register-new-dispatcher= must atomically reserve its requested worker count before realizing workers. If insufficient capacity exists, signal a typed capacity condition and create zero new workers.

If worker creation fails after reservation, stop any workers already created and return the entire reservation.

** Ordinary pinned actor

Creating a user actor with =:dispatcher :pinned= must reserve one lane immediately before the =message-box/bt= thread can be started.

If no lane is available, actor creation fails with a typed capacity condition and no thread starts.

** Dispatcher worker double-count prevention

Dispatcher workers are internally pinned actors. They must be charged exactly once.

The clean model is a dispatcher reservation containing N lane tokens; each internally created pinned dispatcher worker consumes one token from that reservation rather than performing another global increment.

This is an internal mechanism, not a new public actor semantic.

** Restart of a pinned mailbox thread

=message-box/bt= may restart its processing thread if the previous thread died while the mailbox remains active. That restart does not consume a second lane. The reservation belongs to the live mailbox/actor ownership, not to a particular Bordeaux thread object.

** Release

A lane is released exactly once when its owner has actually terminated.

For a pinned actor, release follows terminal actor/mailbox stop. For a shared dispatcher, each worker ownership is released when that worker terminates; dispatcher shutdown therefore eventually returns all N lanes.

Do not release capacity merely because stop was requested while the worker thread is still live.

* Required Accounting State

The minimum useful state is deliberately small:

- granted concurrency;
- used concurrency;
- free concurrency;
- owner ID -> reserved lane count;
- optional owner kind (=dispatcher-worker= or =pinned-actor=);
- optional dispatcher ID for diagnostics.

A lock/atomic protected counter plus an ownership table is sufficient. This research does not justify a scheduler, token market, workload DSL, or second runtime controller.

Accounting operations must be idempotent against duplicate release and must reject unknown/unowned release in deterministic tests.

* Router Conclusions

No router replacement is required for this concurrency feature.

The current router does not create execution capacity, so it should remain ignorant of the total-count ledger. Its existing strategy behavior and routee operations stay intact.

The earlier #188 emphasis on message-aware keyed routing is a valid separate capability gap but is NOT part of this P0 concurrency-accounting correction. It should not block preserving current router behavior while adding aggregate concurrency enforcement.

* StarIntel Requirements

1. Keep the existing Sento router/dispatcher architecture.
2. Keep local =:workers= values as requested dispatcher shape, but enforce their sum against one granted Sento total.
3. Count every shared-dispatcher worker exactly once.
4. Count every ordinary pinned actor exactly once.
5. Count dispatcher-backed ordinary actors as zero additional lanes.
6. Count routers and router membership as zero additional lanes.
7. Reject impossible startup dispatcher totals before worker threads start.
8. Reject dynamic dispatcher/pinned-actor creation before starting new threads when the grant is exhausted.
9. Release ownership exactly once on real termination.
10. Preserve the broader StarIntel process-budget authority; do not add a competing canonical configuration object.
11. Expose total/used/free plus owner counts for runtime diagnostics and #36 admission logic.
12. No new StarLang syntax is required; this is a Common Lisp runtime backend invariant.

* RED-First Targets

The revised first implementation slice should test the Sento accounting primitive directly.

1. =:shared= 4 + =:storage= 4 under grant 6 -> typed over-capacity failure before dispatcher worker realization.
2. 4 + 2 under grant 6 -> exact-fit success; total used = 6, free = 0.
3. Internally pinned dispatcher worker -> charged once, not twice.
4. Ordinary =:pinned= actor when free = 0 -> typed failure before =message-box/bt= starts a thread.
5. Ordinary actor on =message-box/dp= -> used count unchanged.
6. Router creation/add-routee -> used count unchanged.
7. Stopping one pinned actor -> frees exactly one lane.
8. Stopping an N-worker dispatcher -> frees exactly N lanes, exactly once.
9. Failed partial dispatcher construction -> no leaked reservation.
10. Existing Sento random, round-robin, custom-strategy, dispatcher, and mailbox behavior tests remain green unchanged.

* Evidence-backed Decision

Research is sufficient to revise design #189/#42 around Sento total concurrency accounting.

The P0 feature is not a new StarIntel workload-routing model. It is an aggregate execution-lane invariant at the Sento dispatcher/pinned-mailbox realization boundary, fed by the already-approved process thread planner.

* Footnotes and Glossary

- *Execution lane* :: One long-lived Sento actor execution thread reserved by a dispatcher worker or ordinary pinned actor.
- *Dispatcher-backed actor* :: Actor using =message-box/dp= and therefore sharing an existing dispatcher worker set rather than owning a thread.
- *Pinned actor* :: Actor using reserved =:pinned= semantics and a one-thread =message-box/bt=.
- *Grant* :: Maximum Sento execution-lane ownership allocated by the broader StarIntel process thread planner.
