#+title: STAR-PRO-CAPTCHA-002 NopeCHA Token and Recognition Adapter
#+description: StarIntel Pro Actor design for separate NopeCHA Token and Recognition runtime capability surfaces, typed ephemeral results, per-capability quota accounting, context policy, and isolated contract drift.
#+status: REVIEW
#+filetags: :starintel:design:starintel-pro-actors:captcha:nopecha:adapter:token:recognition:uml:

* Decision

Implement one supervised NopeCHA provider service with sibling =NopeChaTokenAdapterActor= and =NopeChaRecognitionAdapterActor= children. They share credential, quota, provider-health, and circuit services but register exact capabilities independently.

The actors accept only broker-normalized messages that already passed authentication, target policy, purpose, disclosure, provider allowlist, session/network context, and budget checks. They expose no public solve route and no wildcard “NopeCHA solves CAPTCHA” capability.

* Provider Operations

| Broker operation | Token actor | Recognition actor |
|------------------+-------------+-------------------|
| submit | =POST /token/= with exact task mapping | official exact recognition operation |
| result | bounded retrieval with provider job identifier | synchronous result or task-specific retrieval |
| cancel | local only unless current provider operation proves support | capability-specific; unsupported unless documented |
| quota | shared configured subscription ledger | shared configured subscription ledger |
| health | token endpoint and local circuit evidence | recognition endpoint and local circuit evidence |
| outcome feedback | unsupported unless a current documented operation exists | unsupported unless a current documented operation exists |

Provider-specific URLs and field names are immutable adapter configuration, not broker request input.

* Runtime Capability Record

Every registered capability contains:

- port: Token or Recognition;
- actor and provider identifiers;
- adapter version;
- official source and retrieval date;
- issuer, family, variant, and integration version;
- request/result operations;
- required and optional fields;
- result kind and required result fields;
- proxy, cookie, user-agent, browser-session, same-network, and mobile requirements;
- execution and disclosure class;
- configured credit cost;
- delivery, cancellation, idempotency, and ambiguous-create behavior;
- concurrency, quota, health, circuit, billing, retention, and error contract;
- fixture fingerprint and freshness;
- live-probe requirement;
- unsupported variants and contradictions;
- state: =verified=, =experimental=, =degraded=, =invalidContract=, =disabled=, or =unsupported=.

Static manifests contain no active capabilities. Runtime registration may report all configured candidate records with their states, but the broker routes only records allowed by policy and state.

* Token Request and Result Mapping

The Token actor:

1. validates exact capability and required context;
2. reserves configured credits;
3. dereferences the provider key and only the authorized context references;
4. constructs the provider request inside the HTTP client call;
5. submits the task;
6. records the provider job identifier immediately;
7. polls with bounded backoff and deadline;
8. validates the exact token/result fields;
9. writes sensitive values to the ephemeral secret store;
10. reconciles charge evidence;
11. returns only result reference and non-sensitive metadata.

A missing required field or unexpected token shape moves only the exact capability to =invalidContract=.

* Recognition Request and Result Mapping

The Recognition actor:

1. validates artifact kind, size, media type, prompt/task format, and exact capability;
2. checks disclosure policy before dereferencing the artifact;
3. reserves configured credits;
4. submits the bounded challenge media and exact task fields;
5. follows the capability's synchronous or asynchronous result model;
6. validates text, coordinates, selections, interaction steps, or custom schema;
7. writes the result to the ephemeral secret store;
8. returns the exact normalized result kind.

No generic list, string, or coordinate shape is accepted across task families without a versioned validator.

* Quota and Billing

NopeCHA credits and refill behavior are stored as operator configuration linked to each capability's official source and retrieval date. Costs can differ or public pages can disagree; no global cost constant is allowed.

Reserve credits before submission. Release only when the contract proves no charge. Refill windows use the configured provider cycle, not local midnight. Local cancellation does not prove credit recovery.

* Credential, Proxy, Cookie, Session, and Network Handling

Because retrieval can put the key in a query:

- construct the final URL only inside the HTTP client;
- disable request-target and body logging;
- never attach the final URL or raw response to an error;
- scrub query parameters from traces and metrics;
- use only a credential reference in actor state;
- scan tests and generated output for the real key.

Proxy credentials, cookies, authenticated sessions, challenge data, Enterprise data, images, and audio remain behind ephemeral references. The actor dereferences only fields permitted by target and disclosure policy. Same-network or same-session requirements are explicit hard constraints.

* Idempotency, Cancellation, and Ambiguous Submission

The actor journals =attemptId= before submission and records provider job identifiers immediately. Duplicate local or RabbitMQ deliveries attach to the journaled job or replay its terminal normalized result.

Provider-side cancellation is =unsupported= unless an exact current contract proves it. Local cancellation stops polling, deletes unconsumed local material, releases only provably unused quota, and reports =chargePossible=true=.

An ambiguous create without a recoverable provider identifier is never blindly retried. Fallback requires a terminal non-ambiguous state and a new broker attempt.

* Contract Drift and Health

- Token capability drift changes only that exact token record.
- Recognition capability drift changes only that exact recognition record.
- Token endpoint failure does not disable recognition when the shared provider remains healthy.
- Shared key, account, quota, or provider outage may mark both actors =disabled=.
- Result-kind mismatch, required-field omission, unsupported task, or documented contradiction moves the exact record to =invalidContract=.
- A repaired adapter returns through =experimental= and new fixtures before =verified=.

Health reports include active concurrency, exact-capability state, fixture age, recent provider completion, downstream acceptance, quota evidence, latency, and circuit state. No raw credential or result data enters telemetry.

* Error Normalization

Normalize authentication, quota, invalid request, unsupported task, incomplete job, unsolvable, timeout, service error, malformed result, local cancellation, ambiguous create, and internal adapter errors. Every failure contains =retryable=, =chargePossible=, and a safe redacted provider code.

* Footnotes and Glossary

- *Token actor* — Provider actor that returns an issuer verification token for an exact integration.
- *Recognition actor* — Provider actor that returns text, coordinates, selections, or interaction data rather than an issuer token.
- *Sibling actor* — Separately supervised actor under one provider service, allowing one API surface to fail without stopping the other.
- *Runtime capability record* — Exact current provider task contract reported at startup with state and fixture evidence.
