* Research Findings

The reusable architectural target is a StarLang-owned Source Acquisition/Scraping Domain Server rather than embedding Scrapy/Twisted or giving every actor/researcher its own fetch/browser stack.

Current StarLang runtime semantics already cover important local/remote lifecycle behavior, typed domain messages, correlation, deadlines, cancellation, idempotency/replay, and remoting; source acquisition should reuse one request/reply contract for local and remote callers.

Required StarLang/source-definition work includes a small declarative scraper/source surface with stable version identity, typed input/output schemas, bounded request/navigation/extraction steps, pagination/iteration ceilings, partial results, incremental item emission, provenance inheritance, and closed capability references for HTTP, DOM, browser, and feed adapters.

Lower adapters own implementation mechanics: Common Lisp HTTP/DOM/feed ports where practical and an isolated Chromium/Playwright-style browser capability where JavaScript rendering/interactions are required. StarLang remains the definition/control language.

HTML, JavaScript pages, JSON/XML APIs, RSS/Atom feeds, YaCy, and SearX/SearXNG must all be expressible through the same source-acquisition primitives. CAPTCHA handling composes through `captcha.solve` and resumes bounded continuation state without hard-coding provider/private-solver details.

Expert systems remain effect-closed: an expert concludes evidence is needed or selects a collection strategy; the owning actor/researcher issues the acquisition command. Research supervisors retain planning/promotion authority; the acquisition domain only owns source mechanics and typed evidence return.

Security requirements include SSRF and redirect revalidation, DNS-rebinding considerations, browser isolation, response/decompression/parser ceilings, bounded concurrency/pagination/fan-out, credential/session isolation through opaque refs, cancellation cleanup, and no automatic replay of effectful browser actions.
