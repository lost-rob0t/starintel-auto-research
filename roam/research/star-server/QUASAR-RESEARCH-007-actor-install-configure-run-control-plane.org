* Research Question

How can Quasar become the operator's one-stop place to discover, install, configure, start, run, observe, update, and remove actors while preserving StarLang semantic authority, the StarIntel server registry, deployment ownership, secret isolation, and standalone browser behavior?

The desired product experience is one coherent Actor Center. The architectural question is not whether the UI should be unified; it is which authority owns each effect behind that UI.

* Analysis: What Quasar Already Has

** Browser actors

=frontend/src/components/ActorManager.jsx= already lets a user create, persist, configure, and run custom browser actors. Their JavaScript executes in a disposable opaque-origin sandbox. This is a legitimate standalone capability, but it is not a package installer for native or service actors.

The same surface reads server actor entries from =/v1/actors=. Those entries are intentionally read-only and cannot be run from the browser actor executor.

** Server actor catalog

=frontend/src/lib/starintel-server.js= consumes =starintel-actor-registry-v1=. The public projection includes semantic identity, accepted and produced types, capabilities, source package, and bounded liveness. It omits queues, internal endpoints, credentials, and internal topology.

The starintel-server registry implementation is a safe catalog and observation projection. Its internal function named =install-actor-manifests= atomically replaces registry entries in memory; it does not install software. Treating it as a package manager would collapse two different meanings of installation and create the wrong authority.

** Pro actor configuration and runs

=frontend/src/components/ProActorManager.jsx= discovers canonical actor-manifest documents, derives ordinary target options from =configuration_schema=, and submits authorized targets. Fields marked =writeOnly= remain absent from browser configuration. This already establishes a useful distinction:

- per-run target options may be entered in Quasar;
- deployment secrets must stay behind the actor deployment boundary.

It does not install an actor deployment, configure its persistent instance, rotate credentials, start or stop its runtime, or provide transactional update and rollback.

** StarLang and deployment manifests

StarLang owns portable actor semantics and runtime identity. Prior manifest work correctly separates the compiler-produced semantic program manifest from a data-only StarIntel Actor Deployment Manifest. The latter can carry =configurationRef= and opaque =secretRefs= and compiles, together with semantic inputs, into a pure =RuntimePlan= before effects begin.

That separation should be reused. Quasar must not invent a parallel actor language, semantic registry, or executable manifest.

** Existing actor packaging

starintel-pro-actors already describes implementations, entrypoints, runtime kinds, dependencies, configuration schemas, lifecycle, and authorization. Its deployment docs offer Nix, containers, Python development installation, and Common Lisp plugin loading. However, these are repository/operator installation paths, not a stable authenticated package-management API that Quasar can safely call.

* Gap Model

The current product has four partial surfaces:

| Concern | Current owner/surface | Missing product capability |
|---------+-----------------------+----------------------------|
| Semantic actor discovery | StarLang manifests and starintel-server registry | Installability, trust, and deployed-instance projection |
| Browser actor execution | Quasar Actor Studio | Native/service installation and persistent lifecycle |
| Per-run actor options | Quasar Pro Actor Manager | Versioned deployment configuration and secret references |
| Fleet/package deployment | Repository-specific Nix, container, and service workflows | Narrow actor-scoped plan/apply/status/rollback provider contract |

The missing layer is not another registry. It is an *authenticated Actor Administration control plane* that relates a catalog entry to a deployed instance and a trusted package provider.

** Host sandbox gap

Installed native and service actors are expected to run in operating-system-enforced sandboxes on the Quasar host. The current control-plane policy marker =sandboxed-p= is an authorization input, not evidence of isolation. The unpublished =feat/python-actor-runner= worktree also launches a Python child process directly and overlays the parent environment plus a checkout =.env=. That prototype demonstrates dispatch and output ingestion, but not filesystem, network, identity, privilege, resource, secret, process-tree, or cleanup isolation.

Installation and execution must therefore remain distinct. A trusted deployment provider may stage an immutable artifact, while a host-sandbox execution provider consumes a bounded run plan and returns an evidence-bearing receipt. Remote execution is not the default and is researched separately in QUASAR-RESEARCH-008.

* Authority Model

The one-stop UX should compose four different authorities:

| Plane | Canonical question | Authority |
|-------+--------------------+-----------|
| Semantic catalog | What is this actor and what can it accept/produce? | StarLang-derived semantic manifest and starintel-server safe projection |
| Deployment instance | Which immutable artifact is installed with which non-secret config and secret references? | Actor deployment manifest plus trusted deployment provider |
| Runtime observation | Is the deployed instance ready, healthy, and at the expected generation/digest? | Runtime owner projected through the control plane |
| Run state | What happened to this requested invocation? | Execution owner with durable run identity and idempotency |

Discovery never grants installation, configuration, lifecycle, or run authority. Each operation requires an authenticated principal, an explicit scope, and policy evaluation.

* Recommended Product: Actor Center

Quasar should present one Actor Center with capability-dependent views:

1. *Catalog* — available actors, trust source, installability, compatible targets/documents, and installed version.
2. *Configure* — schema-derived ordinary configuration, secret-presence controls, validation, pending changes, and restart impact.
3. *Lifecycle* — install, update, enable, start, stop, restart, rollback, quarantine, and uninstall where the provider grants them.
4. *Run* — context-sensitive target/document selection, per-run options, start/cancel, progress, output, logs, and history.
5. *Diagnostics* — safe health/readiness and runtime observations without exposing private topology or credentials.

Capabilities depend on the connected environment:

- standalone Quasar retains browser actors and must remain usable without a server;
- a connected local deployment may grant package installation and native lifecycle control;
- a hosted multi-user deployment may expose catalog and run operations while restricting install/configure actions to administrators;
- a provider that cannot roll back or uninstall must omit those capabilities rather than simulate them.

* Installation Model

An actor package must resolve to an immutable identity before any host mutation:

- Nix store path or closure identity with locked inputs;
- OCI image digest, never only a mutable tag;
- signed release asset digest where an approved provider supports it;
- exact semantic and deployment manifest digests;
- publisher/trust-policy decision.

Installation is an asynchronous transaction:

#+begin_example
catalog entry
    -> resolve immutable artifact
    -> pure install plan
    -> policy and capacity checks
    -> stage
    -> verify digest/signature/manifests
    -> activate deployment generation
    -> readiness check
    -> commit or rollback/quarantine
#+end_example

The browser never receives shell access, arbitrary package URLs, Docker/Nix sockets, or permission to execute installer text. A narrow provider performs bounded effects and records receipts.

* Configuration Model

Three classes of values must remain distinct:

| Value class | Example | Storage and visibility |
|-------------+---------+------------------------|
| Deployment configuration | concurrency, endpoint policy, model choice | Versioned and schema-validated; readable only within authorized scope |
| Secret input | API token, private key | Written to a credential store; represented elsewhere only by opaque reference and configured/unconfigured status |
| Run options | current target, depth, dry-run | Bound to one invocation; not silently promoted to deployment config |

Configuration needs =preview/validate/apply= behavior, optimistic concurrency or generation checks, an explicit restart requirement, and rollback to the prior valid generation. Fields marked =writeOnly= must never reappear in reads, logs, receipts, errors, or browser persistence.

Scopes must be explicit: principal, tenant/workspace, actor identity, and deployed instance. A secret configured for one instance cannot satisfy another merely because their actor IDs match.

* Lifecycle and Run State

Recommended lifecycle states are:

#+begin_example
available -> planning -> staged -> verified -> installed
                                      |            |
                                      v            v
                                  quarantined   configured -> starting -> ready
                                                                 |          |
                                                                 v          v
                                                               failed     stopped

installed/configured/ready -> updating -> ready | rolled_back | quarantined
installed/stopped          -> uninstalling -> removed | failed
#+end_example

Runs are separate durable objects:

#+begin_example
accepted -> queued -> running -> succeeded | failed | cancelled | outcome_unknown
#+end_example

Every mutating request requires an idempotency key. A client retry must return the same job/run rather than duplicate an install or invocation. A crash between effect and acknowledgement must reconcile from provider receipts and runtime observation.

* Research-Level Administration Contract

Exact wire names belong to the approved design, but the capability set is clear:

- list catalog and deployed instances;
- plan, apply, inspect, and cancel installation/update jobs;
- read configuration schema and redacted configuration state;
- validate, preview, and apply configuration generations;
- start, stop, restart, quarantine, roll back, and uninstall an instance;
- create, inspect, stream, and cancel runs;
- stream bounded job, lifecycle, readiness, and run events.

Responses must carry stable semantic actor identity, deployment-instance identity, immutable artifact digest, configuration generation, runtime generation, and current authorization capabilities. UI labels are never authority.

* Adversarial Review

| Threat or failure | Unsafe shortcut | Required defense |
|-------------------+-----------------|------------------|
| Remote code execution | Browser sends shell commands, Compose text, or arbitrary package URLs | Closed provider actions over digest-pinned catalog artifacts |
| Package substitution | Install a mutable tag or latest release | Resolve and verify immutable digest before plan approval and again before activation |
| Plan/apply race | Apply a stale plan after policy, capacity, or catalog changes | Plan digest, expiry, exact prerequisite generations, and apply-time revalidation |
| Secret exfiltration | Return saved config or include secrets in logs/errors | Opaque secret refs, write-only API, redaction tests, bounded diagnostics |
| Confused deputy | Ordinary user invokes admin install/configure through Quasar | Principal-, workspace-, actor-, and action-scoped authorization at the effect owner |
| Registry as authorization | Actor is visible, therefore runnable/installable | Separate advertised capabilities from granted capabilities |
| Concurrent mutation | Two installs/config changes interleave | Idempotency keys, per-instance serialization, generation preconditions |
| Partial activation | Package is staged but config/service activation fails | Transaction receipt, explicit non-ready state, rollback/quarantine |
| Crash after effect | Client retries and duplicates work | Durable job identity plus reconciliation against provider receipt |
| False readiness | Actor says ready while wrong version is live | Observation includes expected artifact/config/runtime generations and provider attestation |
| Configuration migration | Update silently reinterprets old settings | Versioned schema, explicit migration preview, validation, rollback |
| Destructive uninstall | State or evidence is removed without preview | Data-impact plan, retention/export policy, explicit confirmation capability |
| Dependency collision | Actor update mutates shared dependency for another actor | Provider-owned dependency graph and isolation; fail closed on incompatible plans |
| SSRF or local socket abuse | User chooses fetch URL or provider endpoint | Catalog allowlist, outbound policy, no browser-visible privileged sockets |
| Topology leakage | Catalog exposes queues, paths, credentials, or internal workers | Preserve safe registry projection; admin diagnostics separately authorized and scrubbed |
| Browser sandbox confusion | Browser custom actor is treated as trusted installed actor | Explicit runtime/trust badge and separate adapter capabilities |
| Stale observation | UI treats an old registry snapshot as live state | Observation timestamp/TTL and UNKNOWN state after expiry |
| Rollback failure | UI claims recovery despite failed rollback | First-class =rollback_failed=/=quarantined= state and required operator action |

* Rejected Alternatives

** Put the package manager in React

Rejected. It would expose privileged host interfaces to browser code, make installation impossible to authorize safely in hosted deployments, and couple the UI to Nix/Docker/service details.

** Extend =/v1/actors= into a mutable registry and installer

Rejected. The endpoint is deliberately a safe catalog/liveness projection. Mutating it would mix semantic publication, deployment ownership, authorization, and package effects and would create a second registry authority.

** Store all configuration in local browser storage

Rejected. Persistent deployment configuration must follow instance generations, principals, backup/rollback policy, and server-side validation. Secrets cannot be safely read back into browser storage.

** Treat repository Compose files as the public API

Rejected. Compose is one deployment mechanism, not an actor-scoped, authenticated, transactional contract. It cannot provide the required multi-tenant, idempotency, receipt, and rollback semantics by itself.

** Make every visible actor installable and runnable

Rejected. Visibility is discovery, not authority. Some actors are browser-only, preinstalled, remotely managed, quarantined, untrusted, incompatible, or restricted to specific principals and inputs.

* Recommendation

Proceed to a design for one Quasar Actor Center backed by an authenticated Actor Administration contract and pluggable trusted deployment providers.

Preserve these non-negotiable boundaries:

1. StarLang and its resolved schema/release chain remain semantic authority.
2. starintel-server remains the canonical safe actor catalog projection; Quasar creates no second registry.
3. Deployment manifests bind immutable semantic artifacts to instances using inert configuration and opaque secret references.
4. Provider adapters own package effects and receipts; the browser owns presentation and user intent only.
5. Catalog, deployment, observation, and run states remain separate and explicitly related.
6. Standalone browser actors continue to work without a native installer.
7. Implementation cannot begin until the StarIntel lock authority chain is repaired and the operator explicitly approves the design.
8. Installed native and service actors execute in a real local host sandbox by default; neither a policy flag nor a direct child process qualifies.
9. Optional remote execution remains a separate QUASAR-010 approval and must not weaken the local boundary.

* Proposed Delivery Order After Approval

1. Define contract/state fixtures and a no-side-effect fake deployment provider.
2. Build the unified Actor Center projection over existing browser actors, Pro Actor manifests, and server catalog entries.
3. Add configuration generations, write-only secret-reference behavior, and lifecycle/run jobs against the fake provider.
4. Integrate one trusted local deployment provider, one real host-sandbox execution provider, and one digest-pinned actor as a vertical slice with plan/apply/readiness/run/cleanup/rollback evidence.
5. Add update, uninstall, recovery, and additional providers only after the first provider passes adversarial acceptance.

This order proves the authority split and UX before giving Quasar access to any privileged deployment effect.

* Research Acceptance Evidence for a Future Implementation

The implementation design should require, at minimum:

- deterministic contract and state-machine tests;
- no side effects before plan validation and authorization succeed;
- exact immutable artifact identity from plan through readiness;
- a secret canary that never appears in read APIs, events, logs, errors, browser storage, or receipts;
- idempotent concurrent install/config/run requests;
- process-crash recovery and outcome reconciliation;
- update and configuration rollback, including observable rollback failure;
- proof that the safe server catalog remains read-only and topology-scrubbed;
- proof that disconnected browser actors retain current behavior;
- real-stack browser evidence for install/configure/run flows;
- exact-head repository checks and repaired StarIntel lock conformance.
- proof that the actor cannot observe the repository, home, parent environment, undeclared network/mounts, or privileged sockets, and that cancellation kills descendants and cleans temporary state.

* Footnotes and Glossary

[fn:actor-center] Actor Center: The unified Quasar product surface for catalog, installation, configuration, lifecycle, execution, and observation. It is a UI composition, not a new semantic or deployment authority.

[fn:deployment-provider] Deployment provider: A trusted, narrow adapter that can plan and perform bounded package/deployment effects for an approved runtime while returning durable receipts.

[fn:semantic-catalog] Semantic catalog: The operator-safe projection describing what an actor is and what it accepts or produces, independent of its current installation or runtime topology.

[fn:secret-reference] Secret reference: An opaque identifier for a value held by an authorized credential store. It proves only a binding reference, never permission to reveal the secret.

[fn:host-sandbox] Host sandbox: An operating-system-enforced execution boundary on the Quasar host with explicit identity, filesystem, network, resource, privilege, secret, and cleanup controls.
