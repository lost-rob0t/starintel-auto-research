* Research question
How should a library-first Common Lisp Meta MCP compose SearXNG, YaCy, external search MCPs, and the full StarIntel MCP while keeping the model-visible tool surface small and leaving autonomous research to a future A2A agent?

* Current working constraints
- Reusable Common Lisp libraries come first; the final Meta MCP is a package in the same monorepo.
- The Meta MCP is an execution plane, not an autonomous research agent.
- Public primitives are initially search, fetch, and later crawl.
- A future StarIntel A2A agent owns iterative research behavior and can use both Meta MCP and full StarIntel MCP.
- Full StarIntel capabilities remain behind the authoritative StarIntel MCP rather than being reimplemented in the Meta layer.
- Provider topology must not leak into every client-visible tool name.

* Research backlog
- Current MCP server/client composition and gateway patterns.
- MCP tasks for long-running crawl execution.
- SearXNG JSON API, YaCy integration, and provider duplication concerns.
- Brave, Exa, Tavily and other search MCP capability surfaces.
- Result normalization, provenance, deduplication, ranking and physical-provider identity.
- Common Lisp library boundaries for MCP server/client tooling, plan execution, provider adapters, and reusable LLM tooling.
- Full StarIntel MCP boundary, capability propagation, and confused-deputy risks.
- A2A boundary for later autonomous research.
