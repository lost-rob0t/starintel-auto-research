* Research Question

What challenge and solver capability model lets StarIntel detect, route, apply, and verify authorized CAPTCHA[fn:captcha] and browser-challenge work without assuming that hCaptcha is the only issuer, every result is a token, or one paid provider is globally valid or invalid?

* Finding

The old one-dimensional question—“does this provider solve hCaptcha?”—is invalid. The subsystem must model these concepts separately:

1. challenge issuer;
2. challenge family;
3. challenge variant;
4. integration version;
5. required source context;
6. required result kind;
7. solver actor;
8. external provider adapter;
9. downstream application;
10. downstream verification.

Provider completion proves only that the selected solver returned a result matching its adapter contract. It does not prove that the target accepted the result. Acceptance is a later source-runtime verification event.

The catalog is open-world. A challenge remains =unknown= until positive and negative evidence support a more specific classification.

** Non-token challenge families

The normalized catalog must also represent all of the following without coercing them into token tasks:

- text CAPTCHAs;
- arithmetic challenges;
- question challenges;
- distorted-image text;
- image grids;
- coordinate selection;
- bounding boxes;
- draw-around challenges;
- audio challenges;
- slider puzzles;
- rotation puzzles;
- drag-and-drop puzzles;
- proof-of-work challenges;
- behavioral verification;
- device verification;
- mobile-native software-development-kit challenges;
- custom first-party challenges;
- unknown challenges.

Challenge families and result kinds are independent. A grid may return =selectionSet=, a coordinate task may return =coordinates=, a browser puzzle may return =interactionPlan=, and an issuer-specific integration may convert an interaction into a token only inside the source runtime or provider adapter.

* Required Result Kinds

The result union is typed and supports at least:

- =token=;
- =assessment=;
- =cookie=;
- =proof=;
- =textAnswer=;
- =coordinates=;
- =selectionSet=;
- =interactionPlan=;
- =customTypedResult=.

Sensitive results remain in an ephemeral secret store. Actor and RabbitMQ messages carry only opaque result references. The system never persists raw API keys, tokens, cookies, text answers, coordinates, selection sets, interaction plans, proxy credentials, cookie bundles, enterprise data, page data, authorization headers, or authenticated browser-session material.

* Solver Actor Classes

| Solver actor class | Examples | Appropriate use | Principal constraint |
|--------------------+----------+-----------------+----------------------|
| Local browser actor | Playwright or browser-process worker | Same-session and browser-bound challenges | Resource cost and target-specific source integration |
| Local optical-character-recognition actor | OCR model | Distorted text and text images | Produces text, not an issuer token |
| Local image-recognition actor | Classifier, detector, segmentation model | Grids, coordinates, boxes, draw-around | Result schema and fixture quality must be exact |
| Local audio-transcription actor | Speech-to-text model | Audio accessibility challenge | Audio acquisition and language coverage |
| Manual operator actor | Local review queue | Unknown or unusual authorized challenge | Latency, operator availability, and disclosure policy |
| Custom first-party solver actor | Owned-system bypass or test hook | Organization-defined challenge | Explicit schema and target policy |
| External provider adapter | NoneCap, NopeCHA, 2Captcha, Anti-Captcha, CapSolver, CapMonster Cloud | Exact documented provider capability | Third-party disclosure, contract drift, cost, and context binding |

Execution class is a hard policy input. Local automated execution, provider automation, human-worker execution, and operator review are not interchangeable.

* Capability State Vocabulary

Every provider capability uses exactly one state:

| State | Meaning |
|-------+---------|
| =verified= | Current official contract and local fixture agree |
| =experimental= | Plausible documented contract; fixture or bounded canary incomplete |
| =degraded= | Capability remains usable with a known limitation or reduced confidence |
| =invalidContract= | Current request or result contract is contradictory or fails validation |
| =disabled= | Operator or circuit policy prevents selection |
| =unsupported= | Provider does not advertise or cannot satisfy the exact capability |

Contract drift is capability-local. One =invalidContract= task must not disable unrelated verified capabilities from the same provider.

* Provider Findings

** NoneCap

NoneCap is a narrow hCaptcha adapter candidate, not a universal reference provider. Its current API exposes active hCaptcha operations and a separate Enterprise task name while reserving other task names for future use. The adapter must separate standard, invisible, and Enterprise behavior; preserve polling, cancellation, feedback, billing, retention, and ambiguous-create analysis; and keep reserved task names =unsupported= until an active contract and fixture exist.

** NopeCHA

NopeCHA has two distinct surfaces:

1. the Token API, which returns integration tokens for supported issuer families; and
2. the Recognition API, which returns text, selections, coordinates, or recognition-specific outputs.

Per-capability credit cost, authentication exposure, redaction, required fields, and result type must be recorded separately. Browser-extension marketing is not automatically a server API capability.

** 2Captcha

2Captcha exposes a broad asynchronous task catalog. The adapter must use family-specific request mappers, result validators, typed results, and human-worker disclosure classification. Current hCaptcha task uncertainty is capability-specific and cannot disable reCAPTCHA, Turnstile, Arkose, GeeTest, AWS WAF, image-to-text, coordinates, grids, rotate, draw-around, drag-and-drop, or other separately verified tasks.

** Anti-Captcha

Anti-Captcha documents multiple reCAPTCHA, Arkose, GeeTest, Turnstile, Friendly Captcha, Prosopo, AWS WAF, ALTCHA, image-to-text, coordinate, and custom AntiGate tasks. Lack of a current hCaptcha contract is one capability gap, not a global rejection. Human-worker execution and custom-task disclosure require explicit policy.

** CapSolver

CapSolver documents selected reCAPTCHA, Turnstile, GeeTest, AWS WAF, Arkose, and related automated capabilities. Each task remains independent. Adapter selection must compare exact missing coverage, contract quality, cost, disclosure, fixture quality, and redundancy rather than provider name.

** CapMonster Cloud

CapMonster Cloud documents selected reCAPTCHA, Turnstile, Arkose, GeeTest, and related task families. As with CapSolver, the absence of a specific hCaptcha task does not invalidate unrelated capabilities. Runtime registration is limited to current fixture-backed tasks.

* Detection Research Contract

Every detector registry entry must declare:

- detector ID;
- version;
- issuer;
- family;
- variant;
- integration version;
- required observations;
- positive signatures;
- negative signatures;
- extracted fields;
- confidence computation;
- collision cases;
- fixture set;
- retrieval date;
- state: =verified=, =experimental=, or =disabled=.

Detection signatures drift independently from provider contracts. A detector retains rejected candidates and reasons, selects only the challenge blocking the current source action, and requests missing evidence from the source actor rather than scraping outside the source-runtime boundary.

* Security and Operational Boundaries

- Authenticate every requester and verify =captcha:solve=.
- Verify target policy, purpose, disclosure class, provider allowlist, source-session binding, and network binding before external work.
- Reserve budgets and journal attempts before provider submission.
- Treat duplicate RabbitMQ deliveries idempotently.
- On ambiguous create, recover a provider job or stop for review; never blindly resubmit a paid task.
- Support cancellation, deadlines, capability-local drift, controlled fallback, and explicit speculative execution policy.
- Drain or cancel active work during shutdown.
- Expose no raw public solve endpoint.
- Record only redacted cost and outcome metadata.
- Keep live probes opt-in, credential-gated, cost-bounded, capability-specific, and restricted to operator-owned or explicitly authorized systems.
- Continuous integration never invokes a paid provider.

* Research Gaps

- Arkose and DataDome expose some integration detail only through account-gated or product-oriented material; exact detector and adapter fixtures remain unresolved.
- Tencent and some regional provider contracts need a dedicated primary-source pass.
- Current CapSolver and CapMonster task snapshots need capability-by-capability fixture capture.
- 2Captcha hCaptcha documentation contradictions need a bounded contract probe without widening unrelated task states.
- Mobile-native challenges need application-specific source-runtime contracts.
- Unknown and custom challenges require fixture-driven schema registration as encountered.

* Footnotes and Glossary

[fn:captcha] CAPTCHA: Completely Automated Public Turing test to tell Computers and Humans Apart; this document also covers adjacent browser, device, behavioral, proof-of-work, and Web Application Firewall challenge mechanisms.

- *Capability widening* — Treating support for one issuer, variant, integration version, result kind, or context as support for another without evidence.
- *Contract drift* — A provider request, response, error, billing, or lifecycle contract changing after an adapter or fixture was created.
- *Downstream verification* — Source-runtime evidence showing whether the target accepted, rejected, expired, or replaced an applied result.
- *Opaque result reference* — A short-lived identifier that authorizes one bounded read from an ephemeral secret store without putting the result in a document or actor message.
- *Source runtime* — The browser, HTTP, mobile, or first-party process that owns the target interaction and must apply and verify the result in its own context.
