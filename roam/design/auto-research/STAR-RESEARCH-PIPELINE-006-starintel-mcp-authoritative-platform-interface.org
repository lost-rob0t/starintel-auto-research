* REVIEW Objective

Build a full, safe, feature-rich StarIntel MCP without turning the MCP into a second server implementation.

The dependency direction is normative:

#+begin_example
reusable Common Lisp MCP/LLM libraries
      |
      +--> cl-mcp-* / resource/tool/schema/discovery primitives
      |
      +--> starintel-mcp-adapter
      |       |
      |       v
      |   starintel-gserver-client
      |       |
      |       v
      |     StarIntel
      |
      `--> starintel-mcp
               |
               +--> resources/templates
               +--> query tools
               +--> mutation tools
               `--> caller-aware discovery

starintel-meta-mcp
      |
      `--> starintel-mcp (read/search integration only)

future StarIntel A2A agent
      +--> starintel-meta-mcp
      `--> starintel-mcp
#+end_example

=starintel-gserver-client= is the existing remote StarIntel SDK boundary established by STAR-RESEARCH-038. PIPELINE-006 MUST reuse/extend it rather than creating another MCP-specific HTTP client.

If later monorepo consolidation relocates that ASDF system, its public semantic boundary and compatibility contract must be preserved; relocation is not required by this design.

* REVIEW Invariants

1. Generic MCP protocol, transport, schema, server/client, resource, tool, and discovery behavior lives in reusable Common Lisp libraries.
2. =starintel-mcp= is a StarIntel-specific application package consuming those libraries.
3. =starintel-mcp-adapter= is a reusable thin library translating =starintel-gserver-client= operations/results/conditions into MCP-facing domain values; it contains no duplicate HTTP route implementation.
4. =starintel-gserver-client= remains the authoritative Common Lisp remote SDK for StarIntel.
5. The MCP does not depend directly on Dexador, Ningle route strings, CouchDB, Clouseau, RabbitMQ, or Sento actor refs.
6. StarIntel's closed authorization policy remains authoritative for every protected read/call.
7. Caller-visible discovery is the intersection of authorization, canonical resource visibility, runtime availability, and reviewed MCP exposure policy.
8. Discovery hides unavailable/unauthorized operations but never substitutes for call-time authorization.
9. Capabilities with =501= or stubbed runtime backends are not advertised as usable MCP operations.
10. Addressable read objects use MCP resources/templates when practical.
11. Search and semantic view execution remain tools because they perform bounded computation.
12. Large query results return compact structured results plus resource links rather than entire source documents.
13. Legacy route aliases never become stable MCP operation names.
14. Login, bootstrap, password handling, and operations that return new raw bearer keys are not model-controlled MCP tools in v1.
15. Internal actor/broker/database capabilities are not exposed merely because they exist inside the server; an authoritative StarIntel service/SDK operation must exist first.
16. Current StarIntel bulk-job handles are not labeled MCP Tasks until lifecycle semantics pass a separate conformance gate.
17. Meta MCP cannot integrate private StarIntel data through direct HTTP/database shortcuts; it consumes the full MCP.
18. Future MCP additions reuse the same capability/resource authorization vocabulary rather than inventing MCP-only policy strings.

* REVIEW Existing StarIntel SDK Boundary

STAR-RESEARCH-038 already establishes this dependency:

#+begin_example
star-cli / Emacs / Quasar / CL applications
                 |
                 v
       starintel-gserver-client
                 |
                 v
             StarIntel HTTP
#+end_example

PIPELINE-006 extends the consumer set:

#+begin_example
starintel-mcp-adapter
        |
        v
starintel-gserver-client
#+end_example

Required SDK properties for MCP consumption are either already planned in STAR-SERVER-038 or must be added there rather than duplicated:

- immutable/effectively immutable client/auth configuration;
- replaceable transport for hermetic tests;
- named semantic operations rather than caller-owned route strings;
- typed StarIntel protocol errors;
- correlation/deadline propagation;
- safe credential redaction;
- capability/version discovery;
- stable decoded control-plane values;
- explicit mutation retry/idempotency behavior.

The MCP adapter may define an interface for fakes, but the real remote implementation delegates to =starintel-gserver-client=.

* REVIEW Machine-Readable Contract Alignment

STAR-RESEARCH-039 proposes a Common Lisp contract registry that can mount server operations, emit OpenAPI, and generate client operation wrappers/models.

PIPELINE-006 does not block on that research becoming implementation-ready. However:

1. MCP schemas MUST NOT become an independent third source of StarIntel request/response truth.
2. Where the StarIntel contract registry exposes stable JSON Schema/operation metadata, the MCP adapter SHOULD derive or validate its schemas against it.
3. Stable operation IDs SHOULD map deliberately to MCP semantic operations rather than mechanically mirroring route paths.
4. Contract drift CI SHOULD eventually prove server contract, SDK operation, and MCP projection remain compatible.

* REVIEW Authority Model

Conceptual request path:

#+begin_example
MCP transport authentication
        |
        v
resolved StarIntel principal or delegated service context
        |
        v
starintel-mcp operation/resource
        |
        v
starintel-gserver-client request
        |
        v
StarIntel policy engine
 capability + canonical resource dimensions + quota
        |
        v
service operation
#+end_example

MCP MUST NOT infer StarIntel authority from:

- MCP client name/version;
- connection locality;
- tool annotations;
- =starintel://= URI text alone;
- caller-supplied policy decision IDs;
- caller-supplied principal/scopes without verified transport/delegation context;
- arbitrary dataset/actor/target strings without server authorization.

The exact remote OAuth/token-exchange/service-identity mechanism is deferred to private implementation/topology RAGE. It must preserve StarIntel principal/resource semantics.

* REVIEW Discovery Contract

For each caller, discovery computes:

#+begin_example
verified StarIntel capability grants
INTERSECT canonical resource-scope visibility
INTERSECT current implemented/healthy SDK operations
INTERSECT reviewed MCP exposure policy
= visible resources/templates/tools
#+end_example

Requirements:

- deterministic result for same authority + runtime capability revision;
- private cache scope for caller-specific discovery;
- no raw grant/credential secret leakage;
- direct tool/resource attempts still reauthorize;
- unimplemented lease/replay tools are absent;
- admin-only safe operations are absent for ordinary callers;
- list-change notification support is optional for v1, not required.

* REVIEW Resource Contract

Use custom URI scheme =starintel://= for MCP-addressable StarIntel values.

** Identity context

#+begin_example
starintel://identity/context
#+end_example

Safe projection only:

- principal ID/type;
- non-secret granted capability/resource scope summary as allowed by policy;
- correlation/deadline metadata when safe.

Never expose bearer key, verifier, salt, pepper, password, bootstrap secret, or auth-store internals.

** Document template

#+begin_example
starintel://documents/{id}
#+end_example

Read flow:

1. parse/validate resource URI;
2. call named =starintel-gserver-client= document operation;
3. server resolves stored document and performs tenant/dataset authorization;
4. return canonical JSON/content with private cache scope.

Missing and unauthorized reads follow the server's non-leaking policy.

** Bulk-job template

#+begin_example
starintel://bulk-jobs/{id}
#+end_example

Returns actual StarIntel job state subject to submitter/admin authorization. It does not promise persistence/cancellation semantics beyond the underlying StarIntel job contract.

** Target collection template

Candidate:

#+begin_example
starintel://targets/{actor}
#+end_example

Only if the SDK exposes the authorized target collection semantic operation and the MCP resource remains bounded.

** Enumeration rule

Do not enumerate the corpus through =resources/list=. Large collections are reachable through templates and bounded query tools.

* REVIEW Tool Contract

Exact JSON schemas are implementation artifacts, but semantic names and authorization mapping are stable design concerns.

** =search=

Purpose: authorized StarIntel full-text/intelligence search.

Candidate input:

#+begin_src lisp
(:search
 (:query "required")
 (:tenant nil)
 (:dataset nil)
 (:limit 25)
 (:bookmark nil)
 (:sort nil))
#+end_src

Properties:

- maps to =search:read=;
- read-only;
- closed-world relative to StarIntel corpus;
- tenant/dataset scope applied by StarIntel before backend execution;
- bounded structured hit output;
- returns =starintel://documents/{id}= links for readable documents;
- full documents fetched only on selected resource reads.

** =view_query=

Purpose: execute one registered semantic StarIntel view/query.

Candidate input:

#+begin_src lisp
(:view-query
 (:view "semantic-view-id")
 (:tenant nil)
 (:dataset nil)
 (:key nil)
 (:start-key nil)
 (:end-key nil)
 (:limit 50)
 (:descending nil)
 (:skip 0)
 (:reduce nil))
#+end_src

Properties:

- maps to =views:read=;
- only reviewed semantic view IDs from SDK/contract registry are accepted;
- caller cannot choose arbitrary CouchDB design/view names;
- server-side row filtering/count rewriting remains authoritative;
- compatibility aliases are not separate tools.

** =document_create=

- maps to =documents:write=;
- additive mutation;
- uses SDK operation and server document validation;
- returns structured receipt/resource link when stable ID is known;
- no hidden mutation retry without StarIntel idempotency proof.

** =document_update=

Not exposed until the current update path has an explicitly authorized, contract-tested SDK operation.

When approved:

- maps to existing or separately approved update authority;
- handles revision/conflict semantics through StarIntel, not raw CouchDB mechanics;
- idempotency hint follows proven contract only.

** =document_delete=

- maps to =documents:delete=;
- destructive hint true;
- server resolves stored document scope before delete;
- no raw CouchDB revision authorization in MCP.

** =documents_bulk=

- maps to =documents:bulk= plus per-document StarIntel checks;
- bounded count/size;
- whole batch authorization occurs before side effects;
- returns inline result or =starintel://bulk-jobs/{id}=;
- no MCP Task claim in v1.

** =target_dispatch=

- maps to =targets:dispatch=;
- actor/target/tenant/dataset/namespace/program authorization remains server-owned;
- =openWorldHint=true= is appropriate because downstream actors may reach external systems;
- returns StarIntel target/document reference, not Rabbit routing data.

** Deferred unavailable operations

Do not discover until implemented and conformance-tested:

- =target_lease=;
- =target_force_release=;
- =event_replay=;
- event write if its authoritative service remains stubbed/incomplete.

* REVIEW Administrative Boundary

"Full StarIntel MCP" means broad safe model-facing StarIntel capability, not every auth endpoint.

** Candidate safe later

After explicit review and SDK support:

- credential metadata read under =credentials:read=;
- credential revoke;
- credential disable;
- bounded audit read/query under =audit:read=;
- principal/user metadata operations that do not require secret input/output.

** Explicitly excluded from model-controlled v1

- authentication bootstrap;
- username/password login;
- password creation/change/reset;
- credential creation returning a raw API key;
- credential rotation returning a new raw API key;
- verifier/salt/pepper/hash/bearer-token retrieval.

These remain operator/security interfaces unless a later design provides an out-of-band secret delivery mechanism that keeps secret material out of LLM/tool content.

* REVIEW Tool Annotation Matrix

Annotations are hints, not policy.

| Operation | readOnly | destructive | idempotent | openWorld |
|-----------+----------+-------------+------------+-----------|
| search / view_query | true | false | true as query hint | false |
| document_create | false | false | false unless server proves otherwise | false |
| document_update | false | contract-specific | contract-specific | false |
| document_delete | false | true | contract-specific | false |
| documents_bulk | false | false | false unless logical request-id contract proves otherwise | false |
| target_dispatch | false | false | contract-specific | true |
| credential revoke/disable | false | true | contract-specific | false |

Unknown semantics use conservative defaults.

* REVIEW Structured Results

Every tool with stable structure defines an =outputSchema= and returns =structuredContent=.

Preferred query result:

#+begin_src lisp
(:search-result
 (:hits
  ((:id "doc-id"
    :title "..."
    :snippet "..."
    :dtype "person"
    :dataset "case-a"
    :score 1.2
    :resource-uri "starintel://documents/doc-id")))
 (:bookmark nil)
 (:correlation-id "..."))
#+end_src

Safe correlation/authorization decision IDs MAY be included when useful. Grant records, auth-store internals, and secrets MUST NOT be returned.

* REVIEW Error Contract

The adapter maps the typed =starintel-gserver-client= condition model into stable MCP failures.

Candidate categories:

#+begin_example
invalid_input
access_denied
not_found
conflict
rate_limited
quota_exceeded
unavailable
not_implemented
backend_timeout
cancelled
internal_error
#+end_example

Requirements:

- preserve safe StarIntel code/message/correlation metadata;
- do not expose grant existence, secret values, or policy internals;
- keep JSON-RPC protocol errors distinct from normal tool/domain failures where MCP requires;
- an unavailable/stubbed operation should normally be absent from discovery before call time.

* REVIEW Internal Actor Boundary

StarIntel internally uses CouchDB, RabbitMQ, Sento actors, event actors, timers, and experimental actor systems.

These are not MCP APIs by default.

A future actor capability enters =starintel-mcp= only when:

1. StarIntel defines a stable authorized service/SDK operation for it;
2. its action/resource dimensions enter the canonical policy vocabulary if required;
3. runtime capability discovery can prove availability;
4. MCP schema/risk semantics pass review.

This keeps the full MCP extensible without exposing implementation internals.

* REVIEW Current Runtime Gap Register

1. =http-capabilities.lisp= is not a complete typed description of the newer authorization/runtime surface.
2. historical HTTP docs contain stale pre-auth behavior and are negative evidence for route-driven MCP generation.
3. target lease/force release and event replay have authorization vocabulary but absent =501= backends.
4. event write remains incomplete/stubbed.
5. document update requires an authoritative authorization/SDK contract before MCP exposure.
6. bulk jobs are process-local runtime objects, not proven MCP Tasks.
7. current view aliases must collapse behind semantic SDK/view IDs.
8. STAR-RESEARCH-039 contract/codegen work is not yet approved, so v1 must interoperate with it without depending on unfinished codegen.
9. STAR-SERVER-038 client runtime design is still under review, but its parent research boundary establishing =starintel-gserver-client= as the reusable remote SDK is approved.

* REVIEW Conformance Fixtures

The hermetic suite must use a fake/replaceable =starintel-gserver-client= transport or adapter and prove:

1. document resource reads cannot bypass tenant/dataset authorization;
2. caller-specific =tools/list= omits ungranted operations;
3. caller-specific resource discovery does not leak inaccessible collections;
4. direct calls to omitted operations are still denied by StarIntel;
5. =501= lease/replay operations are absent;
6. read-only principals cannot create/update/delete/bulk/dispatch;
7. search/view never leaks unauthorized rows, counts, bookmarks, or links;
8. search resource links independently reauthorize on read;
9. admin-safe operations are absent for ordinary principals;
10. login/password/bootstrap/raw-key-returning operations never appear as model tools;
11. legacy HTTP aliases do not influence stable MCP names;
12. structured outputs validate against their schema;
13. typed SDK errors map deterministically into MCP failures;
14. correlation/deadline metadata propagates without secrets;
15. MCP tests need no live CouchDB, RabbitMQ, Clouseau, or StarIntel deployment;
16. adapter tests prove no direct route/Dexador dependency inside =starintel-mcp=;
17. contract-registry metadata can be compared against MCP schemas when STAR-RESEARCH-039 becomes implemented.

* REVIEW Phase Order

** Phase 0 — canonical capability and contract inventory

- inventory current implemented/stubbed StarIntel actions;
- freeze v1 MCP semantic operation/resource vocabulary;
- map each operation to StarIntel capability/resource dimensions;
- map each operation to existing/planned =starintel-gserver-client= operation;
- create fake SDK transport/fixtures;
- define =starintel://= URI and tool schema fixtures.

** Phase 1 — reusable MCP/LLM libraries

Consume PIPELINE-005 generic library work:

- MCP protocol/types;
- STDIO and Streamable HTTP transports;
- reusable server/client;
- schema validation;
- tool/resource registration;
- authorization hook points;
- caller-aware discovery/cache behavior;
- conformance harness.

** Phase 2 — StarIntel SDK readiness

Work in the existing StarIntel client boundary rather than inventing a new one:

- add/complete named =starintel-gserver-client= operations required by the v1 MCP read surface;
- ensure replaceable transport and typed condition behavior required by tests;
- preserve correlation/deadline/auth semantics;
- align with machine-readable contract/generated-operation work when available;
- keep raw route strings below the SDK boundary.

This phase may be implemented in the StarIntel repository while the MCP packages remain in the Common Lisp MCP/LLM-tooling monorepo.

** Phase 3 — reusable StarIntel MCP adapter library

Inside the MCP/LLM-tooling monorepo:

- implement =starintel-mcp-adapter=;
- translate SDK values/errors/capabilities into MCP-facing semantic objects;
- provide fake adapter/testing surface;
- implement runtime availability and reviewed exposure mapping;
- contain no HTTP transport implementation.

** Phase 4 — full =starintel-mcp= read surface

Inside the same MCP/LLM-tooling monorepo:

- implement =starintel-mcp= on reusable MCP server libraries;
- identity context resource;
- document resource template;
- bulk-job resource template;
- bounded target resource if accepted;
- =search=;
- =view_query=;
- authorization/runtime-aware discovery;
- structured results/resource links;
- private cache behavior;
- full read/search conformance suite.

**This is the minimum gate before PIPELINE-005 Meta MCP may integrate StarIntel.**

** Phase 5 — full mutation surface

After read conformance:

- document create;
- document update only after authoritative SDK/auth contract exists;
- document delete;
- bounded bulk;
- target dispatch;
- separately accepted safe non-secret admin operations.

Stubbed/unimplemented actions remain absent.

** Phase 6 — Meta MCP integration

PIPELINE-005 implements =starintel-mcp-client-adapter= against the conformance-tested full MCP and validates =scope=intel= / =scope=all=.

Meta MUST NOT call =starintel-gserver-client= directly; its StarIntel backend is the full MCP.

** Phase 7 — future A2A StarIntel agent

Future agent uses:

- Meta MCP for external/federated =search= and =fetch=;
- full StarIntel MCP for platform state/actions.

Autonomous research remains agent behavior, not an MCP =research= tool.

* REVIEW Acceptance Criteria

PIPELINE-006 is implementation-ready only when:

1. STAR-MCP-RESEARCH-001 is reviewed.
2. Existing STAR-RESEARCH-038 client boundary is explicitly preserved.
3. No duplicate MCP-specific StarIntel HTTP client/service SDK is introduced.
4. Generic MCP library APIs exist or have an approved implementation sequence.
5. v1 operation/resource inventory maps to authoritative StarIntel capabilities and implemented runtime services.
6. required read-surface operations exist behind =starintel-gserver-client= or have explicit SDK work scheduled.
7. =starintel-mcp-adapter= has a fakeable contract and no direct HTTP/Dexador dependency.
8. read-only full MCP conformance runs without live infrastructure.
9. caller-aware discovery is deterministic and private-cache safe.
10. every resource/tool reauthorizes independently.
11. search/view results preserve isolation and return bounded structured results/resource links.
12. raw-secret-returning authentication operations are absent from model tools.
13. =501=/stubbed operations are absent from discovery.
14. bulk job resources do not claim unsupported MCP Task guarantees.
15. legacy HTTP aliases do not become MCP names.
16. contract/codegen integration cannot create a second schema authority.
17. Meta cannot integrate StarIntel until Phase 4 read/search suite is green.
18. no public document contains infrastructure secrets/private topology.
19. infrastructure/topology details are handed only to infra RAGE after approval.

* REVIEW Implementation and Topology Handoff Rule

Public Auto-Research owns reusable architecture, contracts, risk boundaries, and phase ordering.

After approval:

- generic MCP libraries, =starintel-mcp-adapter=, =starintel-mcp=, and =starintel-meta-mcp= belong in the selected Common Lisp MCP/LLM-tooling monorepo;
- =starintel-gserver-client= work remains within its established StarIntel SDK boundary unless a separately approved monorepo migration preserves that public system/API;
- deployment placement, DNS/TLS, service networking, credential delivery, production storage, observability, and private routing go only to automatic infrastructure RAGE.
