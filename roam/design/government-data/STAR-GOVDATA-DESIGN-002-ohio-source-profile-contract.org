* REVIEW Runtime Contract Identity

This design document is version =0.5.1=. After approval it defines runtime source-record contract:

#+begin_example
source-contract-id      = star.govdata.source-profile
source-contract-version = 1.0.0
#+end_example

The design-document version and runtime contract version are separate. Every canonical record, command, result, checkpoint, adapter job, review, and gate that interprets these fields pins the runtime source-contract ID/version. The contract version snapshot itself requires an Independent Review decision before current use.

* REVIEW Invariants

1. Workers emit proposals/evidence, never verified canonical state.
2. Every canonical subject is self-describing with source-contract ID/version.
3. Subject and review authorities are disjoint.
4. Subject transitions create new immutable subject revisions.
5. Reviews create separate immutable review revisions.
6. One stable review stream per subject revision is CAS-linear; timestamps never resolve forks.
7. Every revision declares logical ID, revision ID, predecessor, and superseded revisions.
8. Route assessments bind exact profile, deployment, search, subfamily, gap, evidence, source/applicability contract, and policy revisions.
9. Completion uses an atomic time-bounded gate binding exact subject/review revisions.
10. Shared deployments do not prove delegation.
11. A profile does not imply route completion.
12. Negative findings expire.
13. Not-applicable requires positive authority/topology evidence.
14. Later revisions never alter older replay.
15. Browser/OCR evidence requires replayable artifacts.
16. Access/privacy restrictions precede acquisition authorization.

Subject kinds include source contract, deployment, profile, applicability contract, policy, manifest/runtime sets, search plan, gap, subfamily decision, assessment, and gate.

One review ID exists per subject revision. Commits CAS against expected head. One unsuperseded head is current; forks/timestamp resolution are forbidden. Absence means unreviewed. Decisions are reviewed, changes-requested, rejected, or invalidated. Subject owners cannot self-review.

Only a reviewed currently valid passed jurisdiction gate satisfies catalog =DONE=.

Canonical basis follows =PIPELINE-004=: reviewed source/applicability contracts, policy, manifest/runtime sets; applicability route ordering; subject kind/logical/revision ordering; UTF-8 strings; UTC RFC 3339 timestamps; explicit nulls; key-sorted maps; declared hash algorithm (default SHA-256).

=valid-through= is the earliest source/applicability contract, policy, subject, review, manifest/runtime, or freshness validity limit. Completion becomes false immediately after it or review invalidation without waiting for an expiry write.

* REVIEW Validation and Acceptance

Reject mutable/unresolved references, source-contract mismatches, review forks, self-review, unsupported not-applicable, stale negative chains, nonterminal routes in passed gates, missing route/review pairs, canonical hash mismatch, invalid contract/policy/reviews, passed gates after valid-through, or ledger-derived completion without a reviewed gate.

Acceptance requires self-describing immutable records; CAS-linear reviews; disjoint writers; sixteen machine-readable routes; exact reviewed assessment bindings; deterministic time-bounded gates; expiring negatives; replayable browser/OCR evidence; unambiguous versions; and approved =PIPELINE-004=.

* REVIEW Fixtures

Fixtures cover source-contract mismatch/migration, review CAS/self-review, canonical hash equivalence/mismatch, all-route Franklin gate, automatic expiry, route changes after old gates, contract/policy gate supersession, observations without DONE, and v1 subject/review/gate migration.
