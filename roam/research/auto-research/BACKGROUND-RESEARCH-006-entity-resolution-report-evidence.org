* Research Question

How should Auto Dig resolve source records to people and organizations and assemble a report without collapsing candidates, contradictions, historical states, or source-specific meanings?

* Executive Finding

*RESOLVE CLAIMS, NOT JUST NAMES.* Mirroring public datasets only creates source records. A background report requires a second layer that decides which records are candidates for the same person or organization, preserves conflicting candidates, and emits evidence-bearing assertions.

The existing StarIntel research already establishes the required primitives: contradictions remain first-class, duplicate storage is separate from corroboration, relations carry validity time, and important derived state must be replayable from preserved raw inputs. Background-report entity resolution should reuse those primitives directly.

* Source Record Versus Entity

A source record is not the person.

Examples:

- one Ohio voter row
- one PACER party record
- one deed grantee
- one NPPES provider row
- one FAA airman record
- one corporate filing role
- one LEIE exclusion row

Each receives a stable source-record identifier tied to its source release. Resolution creates assertions that one or more source records refer to the same StarIntel entity.

* Resolution Stages

** Stage 1: candidate generation

Generate candidate records using inexpensive deterministic keys:

- normalized full name
- aliases or former names
- city/state/ZIP
- address tokens
- organization names
- source-native identifiers
- known case, license, NPI, CIK, FRN, N-number, entity, or filing identifiers

Candidate generation is recall-oriented. It is allowed to produce false positives.

** Stage 2: evidence comparison

Compare candidate pairs using source-backed attributes:

- name components
- aliases
- age or date-of-birth evidence where public and present
- historical address overlap
- geography
- employer or organization overlap
- related entity overlap
- unique or semi-unique source identifiers
- temporal compatibility
- contradictory fields

** Stage 3: resolution assertion

Emit one of:

- =same-entity-confirmed=
- =same-entity-probable=
- =same-entity-possible=
- =different-entity=
- =unresolved=

The assertion stores the evidence used, resolver version, score if applicable, threshold version, and contradictory evidence.

No actor destructively rewrites the underlying source records.

* Confidence Is Multi-Dimensional

One scalar score is insufficient for the report surface. At minimum preserve:

- identity confidence
- source authenticity confidence
- extraction confidence
- current-status confidence
- temporal confidence
- role confidence

For example, a court PDF may be authentic with high confidence while the identity match between a common-name party and the target remains weak.

* Role Preservation

Source roles must survive normalization.

Do not reduce:

- statutory agent
- incorporator
- filing signer
- beneficial owner
- director
- officer
- trustee
- grant recipient
- secured party
- debtor
- licensee
- registrant
- defendant
- plaintiff
- witness
- attorney

into generic =associated-with= or =employee-of= edges during acquisition.

Generic graph projections can be derived later while the precise role remains available.

* Temporal Model

Every report assertion may require four clocks:

- =validFrom/validThrough= — when the real-world relationship held, if known
- =sourceAssertedAt= — when the source record or filing asserted it
- =retrievedAt= — when StarIntel obtained the evidence
- =processedAt= — when the current parser or resolver produced the assertion

Historical address, business role, license status, court disposition, and ownership assertions must not be overwritten by later states.

* Contradictions

Contradictions are expected and useful.

Examples:

- two different birth years for a same-name candidate
- two sources reporting different current addresses
- a stale business filing showing an old statutory agent
- a court docket amended after an earlier charge listing
- a monthly exclusion list removing a previously active exclusion

The report layer may present a current assessment, but the evidence graph keeps both source assertions and the explicit contradiction or supersession relationship.

* Corroboration and Source Dependence

Multiple records are not automatically independent corroboration.

Examples of dependent evidence:

- a news page copying a court press release
- a people-search page reproducing a county record
- several mirrors of the same government CSV
- repeated parsing of the same filing

The evidence graph should carry =derivedFrom= or shared-artifact lineage so confidence does not increase merely because the same source was duplicated.

The report assembler does not own these findings. It projects them into a human-readable background report.

* Report Sections as Queries

A background report should be a versioned query over evidence families rather than a separate manually maintained schema.

Initial sections:

- identity candidates and aliases
- address history
- court cases and dispositions
- corrections and public registries
- property and recorded instruments
- business entities and filing roles
- UCC or secured-interest records
- professional and regulatory licenses
- sanctions and exclusions
- securities and adviser records
- aircraft and FCC licenses
- nonprofit and Form 990 roles
- federal awards
- unresolved candidates
- contradictions
- explicit coverage gaps

Each section must report the source coverage and freshness basis used to produce it.

* Report Completeness

Completeness is vector-valued, not boolean.

Example:

#+begin_example
federalCourts: searched-current
franklinCountyCommonPleas: searched-current
ohioOtherCounties: not-requested
propertyFranklin: searched-current
nppes: mirrored-current
leie: mirrored-current
brokercheck: research-needed
telecomContactEnrichment: source-not-found
#+end_example

The report's scope can therefore be reproduced exactly.

* Deterministic Replay Requirement

Given the same:

- source release IDs
- raw artifacts
- parser versions
- normalization versions
- entity-resolution version
- threshold configuration
- report query

StarIntel should regenerate the same evidence graph and report findings, aside from explicitly non-deterministic analyst or model assessments that are stored as separate append-only assertions.

* Research Gaps

- Define deterministic normalization for names, suffixes, transliteration, and business names.
- Create calibration fixtures with common-name collisions, twins/family members, stale addresses, and amended court records.
- Decide which resolver stages are rules, statistical models, Prolog rules, or human review.
- Define confidence thresholds separately by source family and report use.
- Define report versioning so a later source release can produce a new report without deleting the prior report basis.

* Footnotes and Glossary

- *Entity resolution*: Determining whether records from one or more sources refer to the same real-world entity.
- *Source record*: A parsed record scoped to one source release before cross-source resolution.
- *Evidence envelope*: Metadata linking a finding to assertions, source records, retrievals, raw artifacts, versions, and coverage basis.
- *Coverage basis*: The exact set and state of source families searched to produce a report.
