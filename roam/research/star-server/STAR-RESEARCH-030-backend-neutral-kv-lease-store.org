* Correction and Authority

The original research draft selected etcd as the first production adapter. That conflicts with the authoritative issue sequence: issue 31 explicitly selects Valkey[fn:valkey] as the first deployable backend. This revision corrects that decision.

The backend-neutral protocol still rejects silent semantic weakening. Valkey is accepted with explicit topology, persistence, replication, failover, and recovery assumptions. A later etcd or Consul adapter can provide stronger consistency without changing target or HTTP code.

* Research Question

How should StarIntel[fn:starintel] define a key-value lease store[fn:kv-store] that:

- preserves issue-29 lease and fencing semantics;
- supports the Valkey atomic-script implementation required by issue 31;
- remains backend-neutral for future stronger-consistency adapters;
- distinguishes known failure from uncertain mutation outcome;
- closes resources with the server runtime;
- provides one conformance suite for every implementation?

* Repository Findings

The current =starintel-server= runtime starts CouchDB, authentication, actors, HTTP, RabbitMQ consumers, and timers procedurally. It has no single object owning all resources. Issue 30 should introduce an explicit managed lease-store component now and later place it under a broader server runtime.

The authentication layer already carries correlation identifiers and request deadlines. The lease protocol should accept an explicit request context rather than reading dynamically bound HTTP variables.

The security design already defines canonical scope binding, no secret storage in leases, compare-based renew and release, fencing, fail-closed behavior, and audit requirements. The storage protocol must implement those guarantees without duplicating authorization.

* Distributed-System Findings

** Product neutrality is a capability contract

A backend-neutral protocol must describe required behavior, not the lowest common denominator. Every adapter reports its capabilities and deployment assumptions.

Required production capabilities:

- atomic conditional mutation for one logical lease;
- atomic update of active lease, fencing counter, and request receipt;
- monotonic fencing counter that survives normal release and expiry;
- exact compare-and-delete release;
- authoritative current-state reads for ownership decisions;
- backend-controlled expiration or an atomic expiration test;
- bounded requests and explicit lifecycle;
- safe same-request replay.

A backend that cannot meet the selected deployment profile fails startup.

** Fencing state is more durable than active lease state

The active lease expires. The fencing counter must not expire or reset. A release script deletes only the active record.

After failover or restore, the system must not issue a token lower than one previously accepted by downstream persistence. The recovery process therefore needs an effective fence floor[fn:fence-floor] derived from authoritative downstream state or a durable external checkpoint.

** Timeouts require an unknown-outcome variant

A Valkey script may commit and the response may be lost. The protocol must distinguish:

- =deadline-exceeded=: known not committed;
- =outcome-unknown=: may have committed.

The caller resolves =outcome-unknown= by replaying the same operation with the same request identifier. It must not create a new request identifier.

** Durable request receipts make mutations replay-safe

Each mutating script receives:

- operation name;
- request identifier;
- canonical request fingerprint;
- receipt retention duration.

Inside the same atomic script, the adapter checks for an existing receipt, rejects mismatched reuse, performs the lease mutation, and writes the final result receipt.

A retry returns the original result. This covers acquire, renew, release, and revoke.

* Valkey Findings

** Atomic scripts are the correct first implementation

Valkey guarantees atomic execution of a Lua script: other server activities do not interleave during script execution.[fn:valkey-scripting]

The adapter should use versioned scripts or server functions for:

- acquire;
- renew;
- release;
- revoke;
- read-and-classify when an atomic view is required.

Scripts must access only explicitly supplied keys. Dynamic hidden key discovery is forbidden by Valkey's scripting contract and is unsafe for cluster routing.[fn:valkey-eval]

** Cluster deployments require one hash slot

Valkey Cluster permits multi-key scripts only when all keys map to the same hash slot. Hash tags force related keys into one slot.[fn:valkey-cluster]

For one logical target lease, use a canonical slot tag derived from the lease-key digest:

#+begin_example
starintel:{lease-v1:<digest>}:active
starintel:{lease-v1:<digest>}:fence
starintel:{lease-v1:<digest>}:request:<request-id-digest>
#+end_example

The braces contain the identical tag for all keys in one script. Raw target values never appear in the backend key.

Request receipts for an operation must share the lease slot. Global listing indexes, if added, are separate diagnostic structures and must not participate in ownership correctness.

** Server time and TTL are authoritative

The acquire and renew scripts should use Valkey's server-side time and set expiration in the same atomic execution. =PTTL= provides remaining milliseconds, while =TIME= exposes server time.[fn:valkey-time][fn:valkey-pttl]

Scripts execute with a conceptually frozen server time for expiry behavior, preventing a key from expiring halfway through a script.[fn:valkey-replication]

The lease response should derive =expires_at= and =renew_after= from server-returned time and TTL, not the client wall clock.

** Asynchronous replication is an explicit limitation

Valkey replication is asynchronous by default. =WAIT= confirms receipt by replicas and =WAITAOF= confirms append-only-file fsync, but neither turns Valkey into a strongly consistent system and acknowledged writes can still be lost during failover.[fn:valkey-replication][fn:valkey-wait][fn:valkey-waitaof]

The deployment contract must declare:

- standalone, Sentinel, or cluster topology;
- append-only-file and snapshot policy;
- required local and replica acknowledgements;
- =min-replicas-to-write= and maximum lag policy when used;
- automatic restart rules;
- failover and restore recovery procedure;
- fencing floor source.

The adapter's health result must report whether the configured safety profile is currently satisfied.

** Script success and durability acknowledgement are separate phases

The atomic script returns a committed primary result. The client may then issue =WAIT= or =WAITAOF= on the same connection according to policy.

Possible outcomes:

- script failed before commit: known failure;
- script committed and required acknowledgements succeeded: success at configured durability level;
- script committed but acknowledgement threshold timed out: mutation outcome is committed on the primary but durability is degraded;
- connection lost after script dispatch: outcome unknown until receipt replay.

The service result should preserve these distinctions instead of flattening all failures to =backend-unavailable=.

* Valkey Script Contracts

** Acquire script

Inputs:

- active key;
- fence key;
- request receipt key;
- canonical request fingerprint;
- owner and lease fields;
- requested TTL and maximum lifetime;
- serialization version.

Algorithm:

1. return cached result when the receipt fingerprint matches;
2. reject receipt-key reuse when fingerprint differs;
3. read and validate the active lease;
4. treat a valid unexpired active lease as conflict;
5. increment the fence counter with =INCR=;
6. create the active record and expiry;
7. write the request receipt and receipt expiry;
8. return the lease record, fencing token, server time, and remaining TTL.

Valkey itself expires stale active keys, so an absent active key is acquirable. The script still validates serialized records and rejects active keys missing an expiry.

** Renew script

The script validates:

- schema version;
- lease identifier;
- owner identity;
- fencing token;
- current active record;
- positive remaining TTL;
- maximum lifetime.

It updates the active record and expiration without incrementing the fence counter. It writes a replay receipt atomically.

** Release script

The script compares the exact lease identifier, owner, and fencing token. On match it deletes only the active key and writes the release receipt. It never deletes the fence key.

** Revoke script

The script optionally compares an expected lease identifier and token, deletes the active key, preserves the fence, and writes the receipt. Authorization and required reason are enforced by the application service before script dispatch.

* Canonical Key Encoding

The protocol owns one canonical logical key tuple:

- tenant identifier;
- program identifier when applicable;
- dataset identifier when applicable;
- actor or workflow;
- operation class;
- canonical target identifier.

Each component is validated, Unicode-normalized when permitted, UTF-8 encoded, and included in a deterministic binary tuple. A SHA-256 digest of that tuple becomes the opaque Valkey hash tag and audit fingerprint.

The protocol can also render a readable versioned form for diagnostics, but adapters must use the canonical tuple or digest rather than concatenate raw identifiers.

* Serialization

Persisted envelopes:

#+begin_example
starintel.target-lease/1
starintel.target-lease-fence/1
starintel.target-lease-request/1
#+end_example

Unknown versions fail closed. Records are bounded and contain no credentials, authorization headers, backend endpoints, or arbitrary executable data.

The active lease record contains owner identifiers, lease identifier, fencing token, acquired/renewed/expiry timestamps, maximum lifetime, execution identifier, trace identifier, and bounded metadata.

The fence record contains the current counter and update metadata. The request receipt contains operation, request fingerprint, final result, lease identifier, token, completion time, and retention deadline.

* Result Algebra

Every operation returns a structured immutable result, not a boolean.

Required kinds:

#+begin_example
:acquired :renewed :released :revoked :found :not-found :listed :healthy :closed
:conflict :expired :stale-token :not-owner :request-id-reused
:deadline-exceeded :outcome-unknown
:backend-unavailable :durability-degraded :recovery-required
:malformed-record :unsupported-capability :store-closed :invalid-request
#+end_example

Common fields:

- operation and request identifier;
- result kind and retryability;
- lease handle when successful;
- safe observed state;
- backend health and durability acknowledgement counts;
- started and finished times;
- diagnostic code;
- replayed-receipt flag.

* Runtime Ownership

A =managed-lease-store= owns:

- Valkey client or pool;
- TLS and authentication configuration;
- cluster or Sentinel discovery state;
- loaded script versions and digests;
- capability profile;
- monotonic clock and deadline helpers;
- retry policy;
- metrics and audit sinks;
- lifecycle state.

Lifecycle:

#+begin_example
:created -> :opening -> :ready -> :draining -> :closed
                     \-> :failed
                     \-> :recovery-required
#+end_example

Only =:ready= accepts mutations. =:recovery-required= rejects acquisition until the fencing floor has been restored or advanced.

Close transitions to =:draining= before closing connections. New calls return =store-closed=. Close is idempotent.

* Metrics and Audit

Low-cardinality metrics:

- operation count by operation, result, adapter, and durability state;
- latency histogram;
- in-flight operations;
- script reloads and =NOSCRIPT= recovery;
- cluster redirections and retries;
- unknown outcomes;
- durability acknowledgement shortfalls;
- recovery-required state;
- pool health.

Identifiers are not metric labels.

Audit events include request and correlation identifiers, canonical key fingerprint, safe owner identifiers, token, result class, replay status, durability level, and latency. Secrets and raw backend errors are forbidden.

* Backend Contract Suite

Every adapter factory runs the same suite:

1. canonical key round-trip and collision resistance;
2. one concurrent acquisition winner;
3. strictly increasing fencing tokens after release, expiry, and revoke;
4. stale renew and release rejection;
5. exact request replay;
6. mismatched request reuse rejection;
7. unknown-outcome recovery;
8. malformed version fail-closed behavior;
9. bounded listing and cursor behavior;
10. close rejects new operations and closes resources once;
11. metrics and audit sink failure isolation;
12. no adapter imports from HTTP or target actor packages.

Valkey integration tests additionally cover:

- 100 concurrent acquire attempts;
- standalone and cluster hash-slot behavior;
- script cache loss and reload;
- connection loss before and after script commit;
- =WAIT= and =WAITAOF= threshold failures;
- expiry and reacquisition;
- Sentinel or cluster failover;
- restart and restore;
- recovery fence advancement above downstream accepted state;
- credential and metadata redaction.

* Future Adapters

An etcd adapter may use linearizable transactions and native leases. A Consul adapter may use sessions and transactional KV operations. Those adapters must return the same result algebra and pass the same contract suite.

The stronger adapter does not change issue-29 semantics or issue-32 APIs.

* Decision

Implement a backend-neutral =star.lease-store.protocol= with Valkey as the first adapter required by issue 31. Use one atomic same-slot script per mutation, server-authoritative TTL, persistent fence keys, atomic request receipts, explicit durability acknowledgements, structured uncertain outcomes, runtime-owned resources, recovery fencing floors, and a shared contract suite.

* Footnotes and Glossary

[fn:valkey] Valkey: An open-source in-memory key-value server compatible with the Redis protocol and selected by issue 31 as the initial StarIntel lease backend.

[fn:starintel] StarIntel: A local-first intelligence platform that collects, validates, connects, searches, analyzes, and exports structured documents through actor-based services.

[fn:kv-store] Key-value store: A database that retrieves a value by a key. Different products provide different consistency, transaction, expiration, and failover guarantees.

[fn:fence-floor] Fencing floor: The minimum next token value required to remain greater than every generation already accepted by authoritative downstream storage.

[fn:valkey-scripting] Valkey, “Scripting with Lua.” Documents atomic script execution and effects replication. [[https://valkey.io/topics/eval-intro/][official documentation]].

[fn:valkey-eval] Valkey, “EVAL.” Requires every key accessed by a script to be supplied explicitly, including in clustered deployments. [[https://valkey.io/commands/eval/][official documentation]].

[fn:valkey-cluster] Valkey, “Cluster specification.” Documents hash tags, same-slot multi-key operations, asynchronous replication, and acknowledged-write loss windows. [[https://valkey.io/topics/cluster-spec/][official documentation]].

[fn:valkey-time] Valkey, “TIME.” Returns server time. [[https://valkey.io/commands/time/][official documentation]].

[fn:valkey-pttl] Valkey, “PTTL.” Returns remaining key lifetime in milliseconds. [[https://valkey.io/commands/pttl/][official documentation]].

[fn:valkey-replication] Valkey, “Replication.” Documents asynchronous replication, expiry behavior, and failover limitations. [[https://valkey.io/topics/replication/][official documentation]].

[fn:valkey-wait] Valkey, “WAIT.” Documents replica acknowledgement and states that it does not make Valkey strongly consistent. [[https://valkey.io/commands/wait/][official documentation]].

[fn:valkey-waitaof] Valkey, “WAITAOF.” Documents append-only-file fsync acknowledgement and its consistency limitations. [[https://valkey.io/commands/waitaof/][official documentation]].
